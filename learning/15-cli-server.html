15 CLI 与 HTTP Server

两个「非交互」外壳。CLI 面向脚本与管道，Server 面向进程外调用—— 它们的设计约束比 TUI 更硬，因为对外接口是契约而不是体验。

学习目标

  • 列出全部启动参数并说出每个参数的归属模式；
  • 解释「零参数 = -tui」的兜底判据为什么写死在参数个数上；
  • 说清 CLI 的输出契约（stdout / stderr 分工）与退出码的分类依据；
  • 背下 Server 的路由清单与 SSE 事件名；
  • 说清 ApiKeyGuard / OriginGuard / bind 校验三者的分工与豁免规则；
  • 能复述 Router 的匹配规则（段数相等、{name} 只吃单段、先到先得、405 带 Allow）；
  • 知道 ServerConfig 的八项里只有三项能用命令行设，以及这样设计的理由；
  • 说清「流太多回 503」为什么优于「排队等许可」。

校验集中在 build()（:238-297）：模式缺失 / 模式重复 / 位置参数多于 1 个 / 端口重复且不一致。 注意「模式重复」不在 build() 里，而在解析期的 requireSingleMode（:328）—— 它是「扫到第二个模式旗标就当场报错」，而 build() 处理的是「扫完之后才知道」的那些约束。

设计依据：为什么手写解析器而不是用 picocli / args4j？

因为需求里有几个标准库不支持的定制语义：

  • 「零参数才兜底」——几乎所有参数库的默认值机制都是「字段级」的，没法表达「参数个数为 0 时才有默认模式，否则必填」。
  • 模式归属校验——「--agent 只在 CLI 下合法」，这是跨字段的条件约束，得自己写。
  • -server 9096 的位置参数——把位置参数当端口，同时又要拒绝「位置参数多于一个」。
  • 退出码按「失败阶段」分类，而不是按异常类型。

这些规则加起来不到 500 行手写代码，用参数库反而要写一堆注解 + 自定义校验器 + 后处理。 对「8 个旗标 + 8 个带值参数」这个规模，手写是更划算的。规模再大一倍就该换库了。

这一行是整个参数解析里最值得琢磨的。三个要点：

  • 判据是「参数个数为零」，不是「没有模式旗标」。 所以 jellyfish --verbose 会报「请指定启动模式」并退 2，而不是「默认 TUI + 详细日志」。
  • null 在 build() 里变成用法错误（:254-255）——刻意不默认成 -cli。
  • 注释里那句「以后也不会因为多认出一个开关而悄悄放宽」正是要点： 如果判据写成「没有模式旗标就默认 TUI」，那么每加一个新参数，兜底的适用范围都会悄悄变大一格， 最终变成「随便敲什么都能进 TUI」。写死参数个数，让兜底范围永远只有一种输入。
设计依据：为什么「带了参数就必须显式给模式」？

README（:112-116）给了两个非常具体的理由： 「这样『敲了没反应』和『悄悄挂在等 stdin』都不会发生」。

场景一：用户敲 jellyfish --model openai/gpt-4o，以为会执行点什么——如果这时默认进 TUI， 它会启一个交互界面，而用户以为自己在做一次性调用。

场景二更糟：如果默认成 -cli 且没有 -p，CLI 会从 stdin 读到 EOF—— 在终端上这意味着静默地一直等下去，看起来就像卡死。

「拒绝而不是静默忽略」是这个项目里反复出现的立场，和06 页的 「权限判定不返回 ASK 给调用点」是同一个思路：宁可让用户多敲四个字符，不要让他猜为什么没反应。

设计依据：为什么回答要「缓冲到终态再写一次」？

因为 CLI 的 stdout 是机器接口。README（:141-148）明确说 「重定向是安全的」，并给了 > answer.txt 2> diag.txt 的例子。

如果流式边收边输出，那么当一个回合中途失败或被插件拦下时，stdout 里已经有半截回答—— 脚本拿到的是一份「不完整但看起来正常」的输出。而退出码 7 的语义是 「stdout 保持为空，原因在 stderr」（README.md:157）—— 这条语义只有在「缓冲到终态」的前提下才成立。

这也解释了 TUI 与 CLI 的结构差异为什么这么大：TUI 要的是即时反馈（流式渲染到消息区）， CLI 要的是可判定的结果。同一个内核，两种消费方式。

坑点：工具轨迹默认不打参数，而且参数不脱敏

默认只有两行：→ shell 和 ← shell 完成（N 字符）。 加 --show-tool-args 才补上参数，且是单行、最多 200 字 （README.md:161-166）。

关键的一句在 README 里：「参数不脱敏」。理由是外壳按参数名猜不出哪个是密钥， 遮不住命令原文与写入正文这些真正会出事的地方。所以 --show-tool-args 的日志不要往共享的地方传—— 它可能包含完整的写入内容。TUI 的 Ctrl+E 同此口径。

设计依据：为什么 Chat 用 SSE 而不是 WebSocket？

因为需求是严格单向的流式输出：客户端发一次请求，服务端持续推事件直到回合结束。 这正好是 SSE 的形状——它比 WebSocket 少一整层状态管理（握手、心跳、重连协商、双向消息类型）， 而且天生可以穿 HTTP 代理、可以被 curl 直接观察： 

curl -N -X POST localhost:9096/sessions/<id>/chat -d '{"message":"hi"}'

需要客户端「回话」的场景（审批、提问）走独立的 HTTP POST， 而不是在同一条连接上做双向——这条分界线让 Chat 这条连接永远不需要处理「客户端消息」， 也就没有并发读写同一连接的问题。

守门规则位置
ApiKeyGuard Authorization: Bearer <key>；用 MessageDigest.isEqual 做常时比较； 豁免只有 GET /health（路径归一化后比较）；不接受 query 里的密钥 ApiKeyGuard.java:89-101（常时比较在 :100）、:114-117（探活判定，:116 做路径归一化）

每个规则的动机都值得单独记
  • 常时比较（MessageDigest.isEqual）而不是 String.equals： 后者会在第一个不同字符处提前返回，攻击者可以据此逐字节猜出密钥（时序攻击）。
  • 豁免只有 /health：负载均衡器需要探活，但除此之外没有例外。 路径是先归一化的——否则 /health/../sessions 这类写法可能绕过。
  • 不收 query 里的密钥：query 会进访问日志、浏览器历史、Referer 头。 只认请求头。
  • OriginGuard 只管写方法：读取操作被跨站发起的危害小， 而「拒绝无 Origin 的请求」会误伤 curl 与非浏览器客户端——所以缺省放过。
  • "null" 字面量拒绝：某些浏览器在特定场景下会发 Origin: null， 它代表「来源不可知」——正好是最可疑的那一类，不能当成「没有 Origin」放过。
坑点：-server 缺省不鉴权

缺省只绑 127.0.0.1（README.md:130），本机之外访问不到， 所以「默认没有鉴权」在缺省配置下是安全的。但一旦你用 --host 0.0.0.0 暴露出去， 任何能访问端口的人都能读到全部会话正文、执行命令、批准审批—— 这也是「非回环 + 无密钥 = 拒绝启动」这条硬校验存在的原因。

配密钥的推荐方式是用环境变量而不是 --api-key： 命令行参数会出现在 ps 输出里，同机其他用户能看到。

7. Router：手写 HTTP 路由的取舍

Server 没引路由框架（没有 JAX-RS、没有 Spark），Router 只有 301 行。它的规则值得逐条记：

行为规则行号
注册 route(method, template, handler) 追加进有序列；启动期装好、运行期只读 :51-53
匹配 遍历全表，先到先得（方法名忽略大小写，命中即返回） :102-115
段数必须相等 if (segments.size() != pathSegments.size()) return null;—— 所以 /sessions/{id} 不会匹配 /sessions/a/b :188
{name} 只吃一段 参数段捕获任意单段，不跨 /（因为先按 / 切好了） :195、:126
尾斜杠 路径先过 RequestPath.normalize，忽略尾斜杠 :127-135
404 固定文案 "没有这个接口"，错误码 NOT_FOUND :71
405 带 Allow 头：把同路径其他方法拼成 "GET, POST" 放进响应头， 错误码 METHOD_NOT_ALLOWED :76-81
已知异常 catch (ApiException e) → 用异常自带的 status / code / message 写出 :84-85
未知异常 记日志后返回固定文案 "服务内部错误" + 500 + INTERNAL_ERROR—— 不把异常消息透给客户端 :88-91
IO 线程 若在 IO 线程上，先 exchange.dispatch(this) 再到工作线程 （否则阻塞操作会占住 IO 线程，docs/constraints.md 有明确禁止） :57-63
设计依据：手写路由凭什么够用？

因为需求里没有那些让路由库变复杂的东西：没有正则路由、没有通配符、没有路径优先级、 没有内容协商、没有过滤器链。16 个端点、两级路径（/sessions/{id}/xxx）， 「段数相等 + 先到先得 + 单段捕获」三句话就能描述完整语义。

代价与收益都很清楚：这条路由是线性扫描（O(端点数)），端点数上百时会开始有感受； 换来的是「没有一整套无法调试的匹配规则」——出问题时读 301 行就能确定匹配结果， 而路由库的优先级规则往往要靠读源码才能推断。

「未知异常统一成固定文案」这条也值得学：把异常消息透给客户端会泄露内部结构（类名、SQL、路径）， 而真正的排查信息在服务端日志里——两边各拿一半才是对的。

坑点：五个「调不了」的服务端参数

maxBodyBytes / maxStreams / keepaliveSeconds / writeTimeoutSeconds / workerThreads 都没有命令行入口—— ServerRunMode 只把 host / port / apiKey 三项传进构造函数 （ServerRunMode.java:131-133）。

也就是说：想提高并发流上限（默认 16）只能改代码重新打包。 如果你打算把 Jellyfish 当后端服务用，这是第一个会撞到的限制。 其余四项在大多数场景下够用（1 MiB 请求体、15 秒 keepalive、60 秒写超时、2×核数工作线程）。

8.1 两个必须成对理解的超时

writeTimeoutSeconds 的注释（ServerConfig.java:41）写明它 必须大于 keepaliveSeconds，理由也给了： 「活着的流每 15 秒有一帧 keepalive 要写」。

这是一条成对约束：keepalive 的目的是「让连接看起来还活着」， 而写超时的目的是「掐掉真的死掉的连接」。如果写超时 ≤ keepalive 间隔， 那么一条完全健康的、只是没数据的流也会在两次 keepalive 之间被写超时掐断—— 保活机制反而成了超时的牺牲品。默认 15 / 60 留了 4 倍余量。

设计依据：为什么两个值都只有代码里的常量？

因为它们必须满足一个不等式（writeTimeout > keepalive）。 如果两个都能从命令行随便设，用户很容易配出 keepalive=30, writeTimeout=20 ——一个「能启动、能连上、但所有长流都会莫名断开」的配置。 这类「配对参数」限制住其中一部分不可配，比加一条运行期校验更省事，也更不容易被绕过。

设计依据：流太多为什么返回 503，而不是排队等许可？

因为 SSE 是长连接。排队等许可意味着客户端已经建立了 TCP 连接、发完了请求， 然后「挂在那里不响应」——客户端无法区分「在排队」和「服务卡了」，超时策略也没法设。

503 是可诊断的：客户端立刻知道「是我请求太猛，该退避重试」， 而且 Retry-After 这类标准重试语义能接上。这与 16 页那条「宁可丢事件、也不内联降级」是同一个取向： 选一个立刻可见的结果，而不是一个「看起来还在工作」的状态。

9. 本页坑点小结

CLI / Server 的坑
  • SSE 事件名前缀不统一：只有 turn_start / turn_blocked 带 turn_， 其余八个是裸名。按直觉写客户端会一个事件都收不到。
  • chat 请求体字段是 message 不是 input； input 属于命令执行接口（CommandExecRequest）。
  • 五个服务端参数只能改代码：maxBodyBytes / maxStreams / keepaliveSeconds / writeTimeoutSeconds / workerThreads。
  • writeTimeout 必须大于 keepalive，否则健康的空转流会被写超时掐断。 想改这两个值要一起改。
  • 流上限（默认 16）满了返回 503，不是排队；客户端应当退避重试，而不是无限等。
  • 七条命令在服务模式被禁（new / resume / reload / session(s) / delete / rm），一律 403 COMMAND_NOT_ALLOWED。
  • 会话不存在的 404 文案不含 id：这是刻意的（不确认 id 是否曾存在）。
  • 未知异常对外是固定文案「服务内部错误」，真实原因只在日志里。
  • Router 是线性扫描 + 先到先得：端点数上百后会开始有感受，且注册顺序会影响匹配。
  • jellyfish --verbose 会报「请指定启动模式」退 2——兜底只认「参数个数为零」。
  • --key=value 写法被明确拒绝，必须写 --key value。
  • -p / --agent / --model / --show-* 只归 CLI， -tui / -server 带上即退 2（拒绝而不是静默忽略）。
  • CLI 的 stdout 只等于最终回答：思考、工具轨迹、错误全走 stderr； 被拦下的回合 stdout 为空且退 7。
  • --show-tool-args 的参数不脱敏，可能含写入正文，别往共享日志传。
  • Server 缺省不鉴权（靠只绑回环保证安全）；绑非回环地址且无密钥拒绝启动退 3。
  • 密钥走环境变量，不要走 --api-key（会出现在 ps 里）。
  • GET /health 是唯一免鉴权路由；路径会先归一化再比对。
  • 同一份 agents.json 在 CLI 与 TUI 行为不同：CLI 无审批者，askTools 命中即拒。
  • Server 不支持 --session / --agent / --model：会话由 HTTP 按 id 寻址。

关键结论

  1. CLI 与 Server 的设计约束不是「体验」而是「契约」：CLI 的 stdout 是机器接口（所以回答要缓冲到终态）， Server 的 HTTP 是进程间接口（所以鉴权、同源、暴露校验都要显式）。
  2. 「零参数兜底判据写死在参数个数上」是一个很小的决定，但它示范了一条更普遍的原则： 兜底的适用范围必须是一个不会随代码演化而变大的量。
  3. 「拒绝而不是静默忽略」在参数校验上体现得最彻底：不属于当前模式的参数一律退 2。 代价是用户要多敲几个字符，收益是不会有「敲了没反应」。
  4. 三道守门的分工是按威胁模型定的：ApiKeyGuard 防未授权访问、 OriginGuard 防跨站发起的写操作、暴露校验防止「以为只在本机其实在公网」。 每一条的豁免规则（/health、无 Origin 放过、字面量 null 拒绝）都有明确理由。
