28 学习路径与阅读顺序

一个 8.5 万行的 Java 仓库，逐文件读是读不完的。这一页给一条可执行的路线： 三阶段、每阶段有明确目标和自测题。

学习目标

  • 拿到一条按依赖顺序、每步都有产出的阅读路线；
  • 用自测题检验自己是否真的理解了，而不是「读过」；
  • 知道哪些文件应该精读、哪些只读类注释、哪些可以跳过；
  • 会用 docs/constraints.md（跨模块规则的单一真源）与 README.md（使用者文档）的分工。

阶段一：跑起来（约 1 小时）

目标不是理解代码，而是先建立「它是什么样」的直觉。没跑过就读架构，容易把设计问题想歪。

#做什么产出
1.1 mvn -o clean package -DskipTests，然后 java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "/help" 确认「没有模型也能跑命令」这件事——它直观说明了命令域不走 LLM
1.2 看一眼不装插件时的样子：模型一个工具都调不了（只有系统命令可用） 理解「工具即插件」不是概念，而是可观察的事实
1.3 跑 Jellyfish-Plugins 的 mvn package + ./cpPlugins.sh， mkdir -p ~/.jellyfish/plugins 并重启 体会「插件变更必须重启进程」
1.4 配一份 models.json（先放全局级 ~/.jellyfish/，避开信任闸），跑一次 -cli -p "…" 拿到第一个「模型 → 工具 → 回答」的完整回合
1.5 把同样的文件放到 ./.jellyfish/，再跑一次 亲眼看到项目级配置默认不生效——这是全项目最独特的一条设计，先见一次比先读文档更有效
1.6 跑 -tui，敲一句话，按 Ctrl+S 发送 理解为什么发送键不是 Enter（试一下 Enter 就知道了）
自测：这三个问题能答上来就可以进阶段二
  • 不装任何插件时，Jellyfish 还能做什么？为什么？
  • 为什么 ./.jellyfish/models.json 默认不生效？它防的是什么？
  • 三种模式（-cli / -tui / -server）里，哪一种「当前会话」这个概念不成立？

对应答案在 01 页、02 页、03 页。

阶段二：顺一条工具调用读到底（约 4–6 小时）

这是整条路线的核心。不要按模块读，要按一条数据流读—— 从一个用户输入开始，跟到一次工具调用结束。这条路径会把所有核心模块都串一遍。

读代码的具体技巧（针对这个仓库）
  • 先读类注释，再看方法。这个仓库的类注释质量高于方法注释，很多「为什么不能那样做」直接写在类注释里。 典型例子：PermissionManager.intercept() 的 javadoc 用四段篇幅解释「插件抛异常为什么按拒绝处理」。
  • 注释里带「为什么」的那几句不要跳。例如 ReActLooper 里 「压缩与这一轮的模型调用并发」「用下标循环而不是 for-each」，都是一句话解释一个设计决策。
  • 看到「不可挪」「必须早于」「不能」这类词，停下来想清楚依赖关系。 这些词标记的都是硬约束，是排查问题的第一手材料。
  • javadoc 里的行号/数字可能过时，遇到「有几个方法」「第几步」这类数字先自己数一遍。 本套文档就改过 JellyfishRuntime 类注释里一处过时的访问器计数。以代码为准。
自测：能答上来就说明主干道通了
  1. 「一轮」和「一个回合」分别指什么？回合有几种终态？
  2. 为什么一批工具调用是串行的？想要并行该怎么做？
  3. ToolExecutor 的七步里，为什么参数改写必须在权限判定之前？
  4. 插件拦截为什么不需要 ALLOW？插件抛异常时会发生什么，为什么？
  5. 「没写 temperature」与「写了 temperature: 0」在代码里怎么区分？
  6. 为什么裁剪只裁本次请求、不写回会话？
  7. 为什么 flushAll() 必须早于 pluginManager.close()？

第四份资料：docs/constraints.md 怎么用

前面三阶段都在讲「读代码」。但还有一份资料必须在动手改代码之前读—— Jellyfish/docs/constraints.md。1253 行、10 章， 而它在前面十几页里只被零散引用了三处（子代理、审批、外壳）， 这里给它一个导读，因为它是这个项目里唯一一份「跨模块规则」的载体。

它是什么：三层解释的最上一层

Jellyfish/docs/constraints.md:1-6（开头自述，逐字）
# Jellyfish 约束与规范

> 本文件是内核仓库的技术约束单一真源：跨模块的规范、边界条件与「不要这么做」。
> 三层解释的分工是 代码自身 → javadoc（某个类自己的为什么与实测数据）→ 本文件（跨类的规则）。
> 面向使用者的说明在 [`../README.md`](../README.md)；类内部的设计推导与实测数据在对应类的 javadoc 里，本文不重复。
> 文档与代码之间容易产生偏移，因此能在类注释里说清的事不写在这里——剩下的每一条都是「改坏了会静默出错」的规则。
这段话本身就是一份「文档分工」的规范

它明确划了三层，并给每层指定了只写什么：

层写什么在哪
代码事实本身源码
javadoc某个类自己的「为什么」与实测数据各类的注释
constraints.md跨类的规则、边界与「不要这么做」本文件
README.md面向使用者的说明（不是开发者）仓库根

最后半句是全篇最有信息量的：「能在类注释里说清的事不写在这里——剩下的每一条都是 『改坏了会静默出错』的规则」。 也就是说，这份文件不是「完整的规范」，而是「按静默故障风险筛选过的规范」。 读它的时候可以假设：没写的部分，要么不重要，要么已经写在类的 javadoc 里。

这条筛选标准也解释了为什么这个文件只有 1253 行——它刻意不做百科。 更妙的是它给了一个「什么时候该往这里加内容」的判据： 只加「改坏了会静默出错」的规则。能防止文档无限膨胀。

## 边界与明确不做（46 行）列的是有意不实现的功能。 读它的收益是双向的：作为使用者，它告诉你「这件事别指望」；作为贡献者， 它告诉你「这个请求大概会被拒，而且不是你实现得不好」。

这与 02 页讲的「配置错误要么立刻可见、要么别生效」是同一个取向： 把「不做」明确写下来，比让每个人自己试探要省下大量来回。

你的处境先看哪

坑点：这份文件也会滞后

它自己也承认了这一点（:5）：「文档与代码之间容易产生偏移，因此能在类注释里说清的事不写在这里」—— 这是用「少写」来降低漂移概率。

本套文档在审计过程中就发现了两处注释滞后（ 03 页的 chat 定位、JellyfishRuntime 的访问器计数）， 两处都已在本套文档编写期间更正。 实践建议：规则类内容以 constraints.md 为准，行号与具体签名以代码为准。 这也正是本套文档每页给 文件:行号 而不是只给结论的原因。

不该怎么读

四个常见的低效读法
  • 从 jellyfish-api 的 144 个类开始逐个读。那是「契约清单」，不是「知识」。 正确做法：需要哪个扩展点就查那一页表（16 页）。
  • 一开始就读 ConversationCompactor.java（1139 行）。 压缩是最复杂的一块，但它建立在「boundary（边界）」「PromptAssembler」「缓存前缀」三个概念之上。 顺序错了会读得很痛苦。
  • 把 di/ 当成「样板代码」跳过。「哪些实例必须唯一」这条知识只在这里， 而它出错时是静默故障。至少读一遍 JellyfishRuntime 的类注释与 EventModule ↔ JellyfishAssembler 的对照。
  • 读 TuiApp.java 的 2239 行。先只读 configure / onStart / render 三个回调（加起来不到 200 行），理解「一帧要做什么」，按键分支用到再查。
一条经验：找「注释里的为什么」

这个仓库里最值钱的不是代码，是注释里那些解释「为什么不是另一种做法」的段落。 例如 AskChannel.java:44-49 解释永不超时为什么不会自愈； PromptAssembler.java:44-47 把「system prompt 里塞易变状态」定性为 bug 信号； PermissionManager 用四段说明插件故障为什么必须收敛成拒绝。

这类段落读一段顶读十个方法。阅读时可以按关键词搜： 为什么、不能、必须、否则、而不是。

关键结论

  1. 读这个仓库的正确单位不是「模块」，而是一条数据流：从用户输入到一次工具调用结束。 那条路径把所有核心模块都串起来了。
  2. 三阶段的分界线是「能不能不看文档复述主干道」。阶段二的自测题就是验收标准。
  3. 精读与略读的分界要明确：ToolExecutor / PermissionManager / Launcher / AgentHarness 的 shutdown() 值得逐行读；TuiApp / ConversationCompactor / 各厂商客户端只读关键路径。
  4. 最省时间的技巧是按关键词找「为什么」类注释——这些是这个仓库里密度最高的知识。
  5. 这套项目的文档分四层且各有分工：代码（事实）→ 类 javadoc（本类的为什么）→ constraints.md（跨类规则，按「改坏了会静默出错」筛选）→ README.md（使用者说明）。 弄清这四层，就不会在错的地方找答案。
  6. constraints.md 只有 1253 行却在前面各页只被零散引用三次，说明它的价值不在「被引用」， 而在于动手改代码前该主动查它——尤其是 ## 边界与明确不做 那一章。
