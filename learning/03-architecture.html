03 整体架构与三外壳装配

这一页回答「三外壳怎么共享一个内核」这个具体问题，并给出启动时序与那张必须背下来的不变量清单。

学习目标

  • 说出 7 个模块各自依赖谁、为什么依赖方向必须单向；
  • 解释 jellyfish-di 为什么存在，以及 JellyfishRuntime 接口刻意不声明生命周期的理由；
  • 复述 Launcher.launch() 的启动时序，以及三步「必须排在 bootstrap 之前」的原因；
  • 说出 bootstrap() 十三步里哪几步的位置是硬约束（订阅先于 refresh、插件配置先于插件启动、目录与恢复后于插件启动）；
  • 解释 RunPermit 为什么只有 suspend/resume 而没有 release，以及看门狗为什么必须独立于执行池；
  • 知道 TUI / Server 启动期为什么不建会话；
  • 记住那份「改任何一处前先确认不会破坏」的不变量清单，并知道其中一条与源码 javadoc 有冲突。

设计依据

为什么把 infra 放在 core 下面而不是同级？ 因为 core 承载的是「流程」：先组装提示词、再调模型、再执行工具、再回灌。 流程要调用基础设施，反过来基础设施不该知道流程。这条边界一旦糊了， 典型症状是 SessionManager 里出现「回合」概念、LlmClient 里出现「会话」概念， 然后任何一次流程调整都要改基础设施，测试面跟着爆炸。

为什么 tui/server 依赖 core 而不是反过来？ 因为内核要能在外壳缺席时独立工作——-cli 不带 TUI 也不带 Undertow， 但它仍然要能跑完一个回合。如果 core 依赖 tui， fat jar 里就永远拖着 TamboUI，而 -server 部署不需要终端库。 内核与外壳之间的通信方向因此统一成「外壳订阅内核」（EventChannel / ShellStreams）， 而不是「内核回调外壳」。

2. 为什么要一个专门的装配层

先说这个接口存在的理由，它的类注释把答案写得很直接：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishRuntime.java:27-46（类注释，逐字）
/**
 * 内核运行时门面：装配完成后的对象图向外交付的那一组入口。
 * <p>
 * <b>为什么要有这个接口</b>：装配知识此前只以 Dagger2 组件的形式存在（{@link JellyfishComponent}），
 * 而 Dagger 的实现类是注解处理器生成的——任何想复用内核的外壳都必须先依赖 Dagger 代码生成。
 * 把入口抽成一个<b>不含任何 DI 注解的普通接口</b>之后，装配方式与交付形态解耦：
 * 外壳只认这 23 个访问器，至于对象图是 Dagger 生成的还是手写的，它不关心。
 * <p>
 * <b>本接口刻意不声明生命周期</b>：启动与收敛是 {@link AgentHarness#bootstrap()} /
 * {@link AgentHarness#shutdown()} 的事，外壳按自己的时机调（CLI 在 {@code Launcher} 里，
 * Spring 外壳在 {@code SmartLifecycle} 里）。接口里再放一对 start/stop 只会多出「谁先谁后」的
 * 第二处说法，而启动顺序是内核的硬约束，只能有一处。
 * <p>
 * <b>实现者必须保证「同一实例」约束</b>：例如 {@code EventPublisher} 与 {@link #eventChannel()}
 * 必须是同一个对象、{@link ExtensionRegistry} 与 {@link EventChannel} 必须共用同一份
 * {@code TypeRegistry}。这些约束不体现在方法签名上，只能靠各实现自己守住；两套实现的一致性
 * 由 {@code JellyfishAssemblerTest} 断言。
 */

这段注释里有三个可以直接拿去用的知识点：

  1. 抽接口的动机是「摆脱代码生成」，不是「面向接口编程好看」。Dagger 的实现类由注解处理器生成， 任何想嵌入内核的产品都被迫依赖那套生成物——抽成普通接口后就解耦了。
  2. 接口不声明生命周期是刻意的。启动顺序是内核的硬约束（见第 4 节）， 如果接口上再放一对 start/stop，就等于给出第二处「谁先谁后」的说法，早晚会不一致。
  3. 「同一实例」约束不体现在方法签名上。这是这套设计的真实弱点，作者承认了它， 并用 JellyfishAssemblerTest（同一段行为对两种装配各跑一遍）当护栏。
注意：这处过时数字已被更正

这段注释原先写「这 21 个访问器」，但 JellyfishRuntime 现在有 23 个方法 （多出来的是 runEventBus()、healthCheck() 等新增项）。 本套文档编写期间已把注释里的数字改成 23。

留着这个例子是因为它很典型：注释里的「有几个」「第几步」这类数字最易落伍， 而且改注释不会导致编译失败，没人会被提醒。读注释遇到数字，先自己数一遍。

坑点：分叉的故障是静默的

少写一行 EventPublisher publisher = eventChannel; 的后果不是异常， 而是「配置 / 模型 / agent 的告警发进一个没人订阅的通道」——现象是 「我配错了但一点提示都没有」。判断这类问题的办法只有一个： 改完装配先跑 mvn -q -Dtest=JellyfishAssemblerTest test。

还有一类更隐蔽的分叉是顺序：JellyfishAssembler.java:222-237 有明确硬约束—— 插件运行时必须在 ReAct 链与压缩链之后装配（因为插件要在 start() 里注册扩展点， 那时消费方得已经存在）。手册顺序抄一遍清单是不管用的，以 AgentHarness.shutdown() 与这些装配注释为准。

3. 三种外壳怎么共享内核

答案简单到有点朴素：RunMode 接口只有三个方法，差异全在实现类里。

Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/mode/RunMode.java（三个方法：checkEnvironment / shell / run）
实现构造时拿到什么run() 做什么启动期建会话？
CliRunMode（229 行） ConversationService、ShellStreams、SessionManager 取输入（-p 或从 stdin 读到 EOF）→ 先订阅再提交 → awaitTurn 等终态 → 映射退出码 建（SessionBootstrap 立即 create + switchTo）
TuiRunMode（228 行） 13 个门面（含 UI 贡献、审批通道、提问通道等） 挂接审批 / 提问通道（TuiRunMode.java:198）→ 起 TamboUI 不建（首页先进，用户敲第一句话才建）
ServerRunMode（179 行） 门面 + ServerConfig 解析端口 / host / api-key → 起 Undertow → 阻塞直到关闭 不建（会话由 HTTP 按 id 寻址创建）
设计依据：为什么 TUI / Server 启动期不建会话？

两个理由，SessionBootstrap.java:18-23 里写清了：

  • TUI 先进首页。用户可能第一件事就是 /session 去看历史会话，或者 --session <id> 直接恢复一个。启动就建一个空会话等于凭空多了一条「退出即消失」的垃圾记录 （SessionManager.create() 刻意不落盘，见 08 页）。
  • Server 的会话由 HTTP 请求带 id 决定。一个进程可能同时服务多个会话， 「当前会话」这个概念在 Server 模式下根本不存在。

判据在代码里就一行：SessionBootstrap.deferCreation 里 mode != CLI 即延后（:83, :103）。 这也解释了另一条规则：--session / --agent / --model 都是「新建会话时的绑定」， 所以它们在 Server 下没有意义，一律判用法错误退 2（见 10 页）。

4. 关键代码：启动时序

下面这段是 Launcher.launch() 的前半段。它的注释密度很高，因为每一步的位置都是有理由的—— 括号里的三条前置就是「必须排在 bootstrap() 之前」的全部原因。

Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:73-137（签名在 :73）
public int launch(StartupOptions options) {
    Objects.requireNonNull(options, "options must not be null");
    RunMode mode = modeFor(options);
    // 环境自检必须排在启动内核之前：不满足时白起插件扫描、事件线程与 HTTP 客户端池毫无意义。
    // 这一步只做判定，不产生任何需要回收的资源。
    Optional<String> problem = mode.checkEnvironment(options);
    if (problem.isPresent()) {
        LOG.error("环境不满足：{}", problem.get());
        console.writeErrLine("错误：" + problem.get());
        return ExitCodes.STARTUP_ERROR;
    }
    // 运行时信息必须在 bootstrap 之前写入：插件在 start() 里就会读它
    // （例如「没有审批通道就不注册需要写权限的工具」），晚一步插件拿到的就是缺省值。
    component.runtimeInfoHolder().set(
            RuntimeInfo.forShell(mode.shell(), System.console() != null));
    AgentHarness harness = component.agentHarness();
    // 项目级配置的信任表态必须排在 bootstrap 之前：配置就是在 bootstrap 里装载的，
    // 晚一步问等于问了也不生效。它也不依赖任何需要回收的资源
    new ProjectConfigTrustConsent(console, component.projectConfigTrust())
            .resolve(component.appConfig(), options, mode.shell() == RuntimeInfo.Shell.TUI);
    Thread hook = new Thread(harness::shutdown, SHUTDOWN_HOOK_NAME);
    Runtime.getRuntime().addShutdownHook(hook);
    try {
        try {
            harness.bootstrap();
        } catch (RuntimeException e) {
            LOG.error("启动失败：{}", messageOf(e), e);
            console.writeErrLine("启动失败：" + messageOf(e));
            return ExitCodes.STARTUP_ERROR;
        }

逐段解释：

  • 环境自检在最前：TUI 没有可交互终端、Server 绑非回环地址却没 api-key， 这些都不需要先付出「起插件扫描 + 事件线程 + HTTP 客户端池」的代价就能判定。
  • runtimeInfoHolder().set(...) 在 bootstrap 之前—— 这条最容易被忽略。插件在 start() 里就会读它， 典型用法是「发现当前外壳没有审批通道，就不注册需要写权限的工具」。 晚一步的效果是插件拿着缺省值做决策，从而注册了不该注册的工具。
  • 信任表态在 bootstrap 之前：因为配置就是在 bootstrap 里装载的。晚一步问等于问了也不生效。
  • shutdown hook 在 try 之前注册，finally 里移除并显式 shutdown： 正常退出走 finally（有确定顺序），被 kill 走 hook（兜底）。
  • 三层 try 按「失败发生在哪一步」分类：内核没起成 3、参数不可满足 2、跑挂了 4。 注释里那句「都接 RuntimeException，不只 JellyfishException」是关键—— 只认后者的话，别的运行时异常会一路穿透到进程入口被当成「初始化失败」退 3， 而那时内核往往已经起来了，脚本会照着退 3 去改一份本来没问题的配置。
这段代码值得学的写法

把「异常类型」换成「失败发生的阶段」来决定对外契约。异常类型是实现细节（重构时会变）， 阶段是业务事实（不会变）。脚本 / 监控 / 上层容器需要的是后者。这里的 ExitCodes 就是把这个阶段语义固化下来。

5. 关键不变量清单

AGENTS.md 这份清单是「改任何一处前先确认不会破坏它们」的。原文很长，这里把最核心的十条与它们的落点并到一起：

#不变量落点破坏了会怎样
1 AgentHarness.chat(sessionId, input, listener) 是内核的回合入口（不是外壳接口：外壳经 ConversationService.submit + ShellStreams.subscribe），在 react 线程池上异步推进。第 6 节详述 core/AgentHarness.java:229, 242 外壳若想同步拿结果，会在 UI 线程上阻塞

5 权限两层：核心策略 → 插件拦截；插件拦截三态且没有 ALLOW；审批 fail-closed PermissionManager.java:170-216、PermissionVerdict.java:29-38 插件若拿到 ALLOW，它就成了权限的最终决定者

7 压缩是插件能力、内核只提供机制；没有策略插件即整体不可用，不回退内置 core/compact/ConversationCompactor.java:208 内置一份「兜底策略」会让行为随内核版本漂移
8 提示词组装走 PromptAssembler；裁剪只裁本次请求（ContextWindow 成组丢弃），历史一条不动 core/prompt/PromptAssembler.java、ContextWindow.java:14-16 写回会话会让 /resume 后的历史与屏幕不一致
9 ProjectConfigTrust：项目级配置默认不加载；信任单位是「文件路径 + 内容指纹」；任何新增的项目级配置读取点都必须过这道闸 infra/config/ProjectConfigTrust.java、RuntimeConfig.java:241-256 新增读取点不过闸 = 在闸上开了一个洞
10 子代理：嵌套回合调度到独立的 agent-run 池，绝不进 react 池；run 起止走运行时的 RunEventBus core/runtime/RunScheduler.java:105-139、AgentRuntime.java:82-93 排回 react 池会互等死锁
11 跨边界载荷必须是 api 侧快照值类型，且快照类型恰好只有一个可见构造器；-parameters 不许去掉 api/llm/LlmTransportRequest.java 等 插件能拿到内核可变对象 = 隔离边界消失
12 生命周期收尾硬约束只有一条：flushAll() 必须早于 pluginManager.close() AgentHarness.java:257-290 落盘经扩展点派发给插件，插件一停就没人接了
设计依据：为什么收尾顺序只硬约束一条？

AGENTS.md 里有一句很关键的话：「不要照抄一份「哪一步必须第几个」的清单，以 AgentHarness.shutdown() 为准。」 理由是：真正的约束只有依赖关系（谁写数据、谁接收数据），而不是某个固定的序号。 把序号抄成规范，下次有人插一步进去，清单立刻失效，而代码里依然正确——于是清单比代码更早腐烂。 正确的做法是记住那条依赖：「先静默所有写者、再兜底落盘、最后关插件」。

实际顺序（AgentHarness.java:257-290）：健康检查 → reActLooper.close() → runScheduler.close() → inputDirectives.close() → conversationCompactor.close() → cacheKeepAlive.close() → sessionManager.flushAll() → systemCommands.close() → subAgentTools.close() → pluginManager.close() → eventChannel.close()。

6. bootstrap() 的十三步：顺序不是风格，是依赖

第 4 节讲了 Launcher 的前置三步。真正把内核「启动起来」的是 AgentHarness.bootstrap()——它只有 13 条语句，但几乎每一条的位置都有理由， 而理由全部写在行内注释里：

设计依据：为什么「内核先注册」是硬约束而不是顺手？

类注释（:186-189）把理由写得很清楚：「插件若要覆盖同名系统命令，必须显式声明 override，否则会在插件启动时以 DUPLICATE_HANDLER 当场暴露， 而不是静默地两套并存」。

如果反过来（插件先注册、内核后注册），撞名时内核会覆盖掉插件的—— 用户装了个插件想改 /help 的行为，结果发现没生效，而且没有任何提示。 现在的顺序让这种冲突必然是「启动期报错」，把问题从「运行时说不清」挪到「启动时说不清都难」。

这也解释了 07 页里 TypeRegistry 的「覆盖压链」机制为什么需要它： 覆盖是受支持的能力，但必须是显式声明的。内核先注册 + 要 override 才允许覆盖， 两条合起来才成立。

坑点：规则文档与源码 javadoc 直接冲突——本套文档编写期间已更正

AgentHarness.chat(...) 的 javadoc（AgentHarness.java:219）写着： 「它是内核内部接缝，不是外壳接口：外壳只经 ConversationService.submit + ShellStreams.subscribe 两条边工作，不再自己传监听器。保留本方法是为了让内核能把 「回合执行体」与「事件发布」分开装配……子代理委派也仍然需要一条同步回调。」

而 AGENTS.md 的关键不变量当时写的是「AgentHarness.chat(sessionId, input, listener) 是外壳唯一的智能入口」——两处说法直接冲突：一个说「外壳别用它」，一个说「它是外壳唯一入口」。

按代码判定，javadoc 是较新的立场：三个外壳在 Launcher 里拿到的都是 conversationService() / shellStreams()，没有一处直接调 chat。 因此已把 AGENTS.md 那句改成与 javadoc 一致的表述。 AgentHarness 类注释 :40-42 复述的启动顺序与 bootstrap() 的实际顺序一致，无需改动。

这条坑点真正的价值在方法上：规则文档（AGENTS.md）与源码注释都可能滞后， 两者冲突时以代码与调用点为准，别默认「写进 AGENTS.md 的就是对的」。 本例与上面那处「21 个访问器」是同一批问题，也是本页发现的第二处「文档滞后于代码」。

7.1 RunPermit：为什么只有 suspend / resume，没有 release

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/runtime/RunPermit.java:8-14, 20-26, 33-35（逐字）
 * 为什么需要「让出」：方案 A 下父 run 等孩子时会阻塞在自己的线程上。若它一直占着
 * 并发许可，孩子就可能永远排不上号（全局许可被一群「正在等孩子的父」占满）。因此在
 * {@code AgentRuntime.await} 的等待窗口里先 suspend()、等完再 resume()，
 * 让等待中的 run 不占运行槽位。
 * 

 * 为什么最终释放走同一个 suspend()：run 结束时也是「不再需要这个许可」，
 * 与等待时的语义一致，因此不另设 release 方法，避免两条路径对 held 的维护产生分歧。

final class RunPermit {            // :20  包私有——外部拿不到，只能靠 RunContext 持有
    private final Semaphore permits;   // :23
    private boolean held = true;       // :26  构造即视为「已持有」
    RunPermit(Semaphore permits) { this.permits = permits; }   // :33-35
  • suspend() / resume() 都是幂等的（:40-45、:50-56）， 重复调用不会把许可还两次或取两次。
  • 「最终释放复用 suspend()」是个很省的设计：不做 release 方法， 就没有「释放」与「让出」两条路径各自维护 held 的可能。少一个方法， 就少一类「held 与实际许可状态不一致」的 bug。
  • 类是包私有的（:20）：外部无法直接构造或操作许可， 只能通过 RunContext.permit() 拿到——把「谁能改并发状态」限制在包内。
设计依据：为什么是「让出」而不是「把许可数调大」？

许可数调大只是把死锁推后：只要「父在等子」这个结构与「许可有限」同时存在， 总量永远是有限的，而「在等的父」+「进不去的子」可以无限累积（深度与 spawn 额度允许的前提下）。

让出是消除死锁的结构性解法：一个「正在等待」的 run 本来就不该占运行槽位—— 它没在跑，占着只是浪费。这与 04 页那条「嵌套回合内联执行、 绝不排回 react 池」是同一个思路的两种应用： 把「等待」从「占用」里剥离出来。

为什么用 ThreadLocal 上下文的使用点分布在调用链的两端：循环器在回合一进一出时开闭它， 而委派发生在工具处理器内部——ToolCallRequest 只携带会话标识、 不能携带内核类型。塞进请求对象会逼着 api 认识一个纯内核概念； 显式传参则要穿过整条工具执行链，而中间每层都不需要它 RunContextHolder.java:9-13

设计依据：这条「ThreadLocal 不等于线程封闭」的澄清很关键

大多数人对 ThreadLocal 的直觉是「这个值是这条线程私有的，改它不影响别的线程」。 在单个不可变值的场合这个直觉成立；但这里的 RunContext 里握着 一个共享对象的引用（RunTree）——深度是线程私有的，而树是共享的。

分不清这两层，就会写出两类 bug：以为改树不用同步（其实多个 run 都在往同一棵树上记数）， 或者以为深度也要跨线程同步（其实它是线程私有的，加锁纯属多余）。 写并发代码时，把「什么是线程私有的、什么是共享的」写在类注释里， 比让每个读者自己推要可靠得多。

设计依据：看门狗为什么必须独立于执行池？

类注释（:60-63）原话：「到点要动用的是取消而不是『再跑一个任务』； 把定时器放在执行池里，池一旦被在途 run 占满，超时处理本身就会被饿死， 于是最需要它的时刻它反而不工作。」

一句话点破了一个很常见的坑：把「超时处理」也排进那个可能被占满的池子，等于让它和它的保护对象一起被卡住。 任何监督者都不能与被监督者共用同一个有界资源——这条适用于线程池，也适用于锁、队列、连接。

PERMIT_POLL_MILLIS 取 50 的理由也值得记（:88-93）：它只影响 「本来就要排队的 run」的开始时刻（最多晚 50ms），不排队的 run 走 tryAcquire() 快路径、 完全不受影响；换来的是取消能被及时看见。这是一个典型的「把轮询成本只加在慢路径上」的取舍。

关闭为什么是一个显式动作

类注释（:64-70）解释了 close() 的必要性，逐字摘录：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/runtime/RunScheduler.java:64-70
「不再派新的 run」只是它的一半，另一半是让已经在途与仍在排队的 run 都走到终态——
shutdownNow() 会把排队任务丢掉，那些 run 从此没有人来落终态，等它们的父回合会永久挂住。
顺序是立旗 → 取消 → 丢队列 → 有界等待 → 兜底收尾；
兜底如实落「已取消」（它们此前确实都被取消过），而不是编一个失败原因。
「兜底如实落『已取消』，而不是编一个失败原因」

这句话值得单独看。关停时那些没跑完的 run，最省事的处理是标成 FAILED 加一句 「内核正在关闭」（SHUTDOWN_REASON :97 正好有这句话可用）。 但作者选择了 CANCELLED，理由是它们此前确实都被取消过—— 不是失败，是被取消。

这一点在排查时差别很大：FAILED 会让运维去查「为什么失败了」， 而 CANCELLED 明确表示这是预期的关停行为。 让状态字段说真话，而不是挑一个「看起来更严重所以更安全」的值。

8. 本页坑点小结

装配与启动相关的坑
  • bootstrap() 里 2/3/4 步必须在 runtimeConfig.refresh() 之前： 指标订阅、配置告警订阅、run 观测订阅晚了，就等于丢掉启动期那一批事件—— 而配置告警绝大多数恰好就是那一刻发的。
  • pluginRuntimeConfig.refresh 必须在 pluginManager.bootstrap() 之前： 否则插件按空配置启动，现象是「插件装了也起来了，但配置一个都没生效」。
  • modelManager.refreshCatalogs() 与 sessionManager.restore() 必须在插件启动之后： 它们依赖插件注册的处理器。晚一步没关系，早一步就是「目录为空」「静默恢复 0 个会话」。
  • 内核先注册、插件后注册：插件想覆盖同名命令/工具必须显式声明 override， 否则启动期就抛 DUPLICATE_HANDLER。别把顺序反过来「图方便」。
  • 新增绑定两处都要改，分叉症状是静默故障（配置告警没人收），不是编译错误。
  • runtimeInfoHolder() 与信任表态晚于 bootstrap() → 插件拿到缺省运行时信息、信任表态形同没问。
  • 只 catch JellyfishException → 别的运行时异常穿透到进程入口被归类成「初始化失败」（退 3），脚本据此去改一份本来没问题的配置。
  • 在 TUI / Server 启动期建会话 → 多出一条不落盘的垃圾会话，且 Server 下「当前会话」这个概念根本不成立。
  • 照抄 shutdown 顺序清单 → 清单会腐烂。记住依赖关系即可。
  • di 模块不带任何资源：把资源放进 di 会让 JellyfishAssembler（手写装配）拿不到， 资源该在 infra（内核资源）或 cli（外壳资源）里。

关键结论

  1. 三外壳共享内核的机制不是「继承」也不是「回调」，而是一个不含 DI 注解的普通接口 + 三个 RunMode 实现。共享的是对象图，分化的是交互方式。
  2. jellyfish-di 的存在理由是把「谁依赖谁、哪些实例必须唯一」这件事只写一份，代价是同一绑定两处都要改，用双跑测试兜底。
  3. JellyfishRuntime 刻意不声明生命周期，因为启动顺序是内核的硬约束，只能有一处说法。
  4. 启动时序里三条「必须早于 bootstrap()」的规则，都是同一个原因：插件在 start() 里就会读这些状态。这决定了任何「启动期状态」都必须在插件加载前就位。
  5. 收尾顺序的规范不应写成序号清单，而应写成依赖链：停写者 → 兜底落盘 → 关插件。
  6. bootstrap() 的十三条语句是这个原则的镜像：「订阅先于事件源、配置先于消费者、插件先于依赖插件的查询」。 每条位置的理由都写在行内注释里——这类「顺序即正确性」的代码，注释不是装饰而是规格。
  7. run 的并发安全靠四件东西合力：许可可让出（消除「父等子」死锁）、 ThreadLocal 只装线程私有量（树仍共享）、看门狗独立于执行池（不被饿死）、 关闭显式且有界（不让父回合永久挂住）。缺任何一件都会退化成偶发死锁或静默卡住。
