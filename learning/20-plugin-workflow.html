20 workflow 插件

内置的 task 只能「一件事一个子代理」；一次调研要并行问三个方向、再拿这三份结论去写方案时， 它就无能为力了。jellyfish-plugin-workflow 把这份「几件事、什么顺序、怎么合起来」变成一份 声明式 spec，交给模型提交、由插件校验并把一批子代理排成层序执行。本页逐类读它全部的 16 个源文件。

学习目标

  • 说清 task 的缺口在哪，以及声明式 spec 为什么是补上它的合适形状；
  • 列出本插件的各个类（含面板排版用的那三个）与不可变值类型，说清各自的职责边界；
  • 拿到 spec 的完整字段模型（steps / needs / when / aggregate）与校验清单，知道环检测在哪一行做；
  • 解释「按依赖分层」的调度判据、when 的三个取值，以及一步失败后整条编排的走向；
  • 确认编排的「执行者」是谁：它复用内核的委派端口，还是自己起线程（源码依据，不靠推断）；
  • 说清上游结论如何被转交给下游、为什么只有直接 needs、为什么截断是刻意的；
  • 理解台账与面板的分工、面板怎么把步骤画成一张图、数字为什么能自己跳，以及「进程重启后这次编排会怎样」。

1. 缺口：单次委派做不了「有依赖的几件事」

先给结论：内核只提供「派生一个子代理」这个原语，不解释任何编排。 task 工具把原语包装成一次调用——一句话进去、一个子代理的结论出来。 11 页把这条链路的五跳讲透了（见 11 页）；本页只关心它缺什么。

它缺三样东西，而且三样都只在「多步骤」时才暴露：

  • 并行：模型要在同一回合里问三个方向，只能发三次 task 调用，每次等到结果才发下一次—— 三次调用串行地占着同一条工具执行线程；
  • 依赖：第二次调用的任务描述里想写「结合上面三份结论」，只能靠模型自己把结论抄进新的 prompt， 而抄写会丢、会走样，也不受任何额度约束；
  • 聚合：把三份结论合成一段，要么由模型在正文里手写，要么再发一次 task 让子代理去合—— 后者等于要求模型自己拼出「汇总子代理该看什么」。

于是本插件做的事情是：把这三件事收进一次调用、一份结构化输入里。 模型写下 {"spec": {...}} 的那一刻，它同时声明了「有几件事、谁等谁、最后怎么合」。 插件负责把这份声明变成调度动作——校验它、分层派生它、把上游结论转交给下游、按声明聚合。

2. 插件构成：5 个协作者 + 1 个入口

start() 就九行，但它把整个装配顺序讲完了：先拿端口、再造台账与引擎、最后才注册。 注释给的理由是「处理器一旦注册就可能被调用，依赖必须已经就绪」——注册不是配置，是立即可见的暴露。

Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:37-57（类声明与 start：装配与三条注册）
public final class WorkflowPlugin implements JellyfishPlugin {

    /** 日志。 */
    private static final Logger LOG = LoggerFactory.getLogger(WorkflowPlugin.class);

    @Override
    public void start(PluginContext context) {
        SubAgentPort port = context.delegations();
        // 面板与台账共用同一个时钟：耗时文案（「已跑」「已 38s」）必须和记账时刻同源，
        // 否则注入时钟的单测会在面板上算出「跑了 50 年」这种数字
        LongSupplier clock = System::currentTimeMillis;
        // 先装配台账与引擎再注册：处理器一旦注册就可能被调用，依赖必须已经就绪
        WorkflowTracker tracker = new WorkflowTracker(invalidator(context), clock);
        WorkflowEngine engine = new WorkflowEngine(port, tracker);
        context.handle(ToolCallRequest.class, WorkflowTool.NAME, WorkflowTool.descriptor(),
                new WorkflowTool(engine));
        context.contribute(PromptContributionRequest.class, new WorkflowGuidance());
        context.contribute(PanelContributionRequest.class, new WorkflowPanel(tracker, clock));
        LOG.info("编排插件已启动: tool={}", WorkflowTool.NAME);
    }

注意这三条注册的类型不同，语义也不同：handle 是「按路由键精确匹配，同一请求类型 + 路由键至多一个处理器」， contribute 是「类型级贡献，允许 0..N 个处理器」（ Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java:33-35）。 工具是「内核按名字找它」，提示词与面板是「内核把同类贡献都收一遍」。

那个 clock 也值得看一眼：它被同时交给台账与面板， 于是「记账用哪一刻」「显示算到哪一刻」是同一个钟。这是耗时类文案能被逐字断言的前提—— 测试注一个可控时钟进去，面板就会照着它算出「已跑 39s」，而不是去读真实的墙上时间。

类注释把本插件描述成「只占两个扩展点」（ Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:17-23）， 而 start() 实际注册了三条——多出来的一条是面板贡献。 它不算矛盾：前两条（工具、提示词）属于「模型看得见的能力」，面板属于界面侧的常驻展示，内核收集它们的时机完全不同。

3. spec 的数据模型与校验：全部发生在派生任何子代理之前

spec 的形状只有三个顶层字段：name（展示名，可省）、steps（必填、非空、≤ 12 项）、 aggregate（可省，省略即 collect）。步骤对象里， 只有 id / agent / prompt 三个必填。

字段必填取值执行语义上的作用
spec.name否字符串 仅日志与结果首行、面板标题；缺省时展示 未命名（WorkflowSpec.displayName()）
steps[].id是非空白字符串，spec 内唯一 唯一机器可读键：被 needs 引用、材料标头与失败清单都用它
steps[].name否字符串，不设长度限制 只用于面板展示，缺省时面板退回显示 id；不进任何机器可读位置
steps[].agent是非空白字符串（是否可委派由内核判） 被委派到的 agent 标识，逐字进 DelegationRequest
steps[].prompt是非空白字符串 这一步的任务原文；子代理看不到本次对话，只有这段文字（有 needs 时前面会拼上材料）
steps[].needs否字符串数组，元素必须非空白 前置步骤 id：它们的结论与它们的成败都从这里流向本步
steps[].when否always / on_success / on_failure 本步要不要跑：只按直接依赖的成败判断，不做布尔组合
aggregate.mode否collect / summarize 各步正文是按顺序拼接，还是再派一个子代理汇成一段
aggregate.agent仅 summarize 时非空白字符串 汇总用的子代理；声明 summarize 却不给 agent 直接拒绝

下面这段是校验的主体：唯一性、自依赖、when 的取值、以及「on_failure 必须声明 needs」， 逐条都在这一步做完。它跑完之前，插件没有派生过任何子代理。

三点值得单独看。第一，报错消息一律回显实际收到的值——SpecValues 的类注释讲了理由： 模型看不到这份实现，只说「类型不对」它改不动（它以为自己传的就是对的），会原样重试。第二，空字符串按「没写」处理， 因为模型常把可选字段写成 ""。第三，name 只做「是不是字符串」这一层校验， 连长度都不限——它不影响任何执行语义，为它设限只会拒掉一份本来能跑的 spec（渲染时才截短，见第 8 节）。

环检测是单独一段深度优先遍历。环不是「慢」或「错」，而是整份 spec 永远跑不完： 环里的每一步都在等别人。所以它在解析期被当成拒绝理由，而不是执行期的一个兜底分支。

Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowSpecParser.java:156-178（visit：深度优先遍历找环）
    /**
     * 深度优先地找出环。
     *
     * @param step     当前步骤
     * @param byId     步骤索引
     * @param visiting 正在访问的路径
     * @param done     已访问完的步骤
     * @throws JellyfishException 遇到环时抛出
     */
    private static void visit(WorkflowStep step, Map<String, WorkflowStep> byId, Set<String> visiting,
                              Set<String> done) {
        if (!visiting.add(step.getId())) {
            throw new JellyfishException("依赖成环：" + String.join(" → ", visiting) + " → " + step.getId()
                    + "。声明式 spec 不做循环——环里的每一步都在等别人，谁也跑不了。");
        }
        for (String need : step.getNeeds()) {
            WorkflowStep next = byId.get(need);
            if (next != null && !done.contains(next.getId())) {
                visit(next, byId, visiting, done);
            }
        }
        visiting.remove(step.getId());
        done.add(step.getId());
    }

报错里把环路径整条打出来（String.join(" → ", visiting)）也是同一个思路： 模型拿到的不该是「有环」，而是「哪一步指向哪一步」。visiting 集合同时充当「当前路径」， 因此它天然能打印出环路本身，不必再跑一趟。

5. 执行者是谁：内核的 SubAgentPort，不是插件自己的线程

这是本页最需要回源码确认的一点，答案在 start() 的第二行：SubAgentPort port = context.delegations();。 插件的每一个步骤都走 port.spawn(new DelegationRequest(...))，插件内部没有任何 Thread / Executor / 线程池——这一点可以直接用「源码里没有这些标识符」来验证， 也可以用引擎注释来确认，它把「先全部派生、再逐个等待」写成一条显式设计： 并发靠内核的 agent-run 池，本引擎只是在调用方线程上逐个 await。

子代理之间彼此隔离——它们看不到对方，也看不到父会话（这是 SubAgentLauncher 的刻意设计）。 所以「plan 这一步能拿到 probe-a 与 probe-b 的结论」这件事， 只能由引擎在下发时替它们拼进 prompt。这也是为什么 spec 是一次性提交的却仍然可行： 模型写下下游 prompt 的那一刻上游还没跑，它没有可填的东西。

坑点：链式依赖不会把上游的上游一起转交

现象：A → B → C 的链上，C 的材料里只有 B 的结论，没有 A 的。 根因：promptFor 只取「模型声明的数据依赖」，也就是直接的 needs； 取全部已决步骤会让链式依赖重复转发（A 的结论跟着 B 进 C，A 又直接进 C），材料体积随深度增长，而 A 的内容一个字没变。 规避：要让 C 看到 A，就在 C 的 needs 里把 A 也写上（同时 C 会等到 A 结束—— 这与它的依赖语义一致）。另一种做法是让 B 在自己的结论里带上 A 的关键结论。

坑点：截断发生在「插件转交」这一层，而写 prompt 的模型看不到

现象：模型写了「请把上游全文逐字核对」，下游却只拿到前 N 字，输出的核对结论缺了一块。 根因：每个依赖块的额度由「依赖个数」均分，且是硬上限；截断提示只放在材料块的首行给下游子代理看， 提交 spec 的那个模型在写 prompt 时并不知道会有截断。 规避：把「需要全文」写进下游任务的做法里——材料块在截断时会附上归档路径并提示「可用 read_file 读取」， 下游子代理可以自己按需自取（内核把每次 run 的完整过程归档落盘，路径经委派结果传出来； 归档本身受文件数与字节数上限约束，最旧的会被清理，见 SubAgentSettings.java:111、119）。

                + "优先保留彼此一致的事实，明确指出相互冲突的地方，不要逐条复述，也不要编造材料里没有的信息。\n\n"
                + material;
        progress(sink, "  · 汇总（" + spec.getAggregateAgent() + "）开始\n");
        DelegationResult result = port.spawn(new DelegationRequest(parentSessionId, spec.getAggregateAgent(),
                prompt, token)).await();
        progress(sink, "  · 汇总 " + statusText(result.getStatus()) + "\n");
        return result;
    }

这段有三处克制的设计。第一，没有任何正文时不做汇总：全部步骤都失败或未执行时， 汇总子代理只能拿到一段空材料，「它要么编、要么反问，两者都比『如实汇报没有结果』更糟」。 第二，取消后跳过汇总：调用点在汇总前检查 token.isCancelled()， 理由是「汇总本身也是一次子代理 run（墙钟按单 run 的上限算）。用户已经按了 Esc，就不该再花一次去做一件他不会看的活」 （WorkflowEngine.java:224-231）。第三，汇总也是额度的一部分： requireQuota 里的 needed 会为它加一；而 WorkflowRun 的 totalRounds() / totalTokens() 显式把它算进累计——漏掉它会让「这次一共花了多少」少算最后也是最贵的一步 （WorkflowRun.java:14-15）。

一个容易忽略的收益：汇总是一次「对齐事实」的机会

并行步骤由不同子代理独立完成，彼此可能冲突——材料块的引导语就直说了这件事 （WorkflowEngine.java:74-75）。而汇总提示词明确要求「优先保留彼此一致的事实， 明确指出相互冲突的地方」。这是把「多路并行的代价」（结论可能矛盾）在流程内消化掉，而不是丢回给模型。

8.1 面板画的是什么：链 + 汇合线

这块面板历史上是一列平铺的清单（[x] 名字（agent）），问题是看不出并行： 三步并行与三步串行在清单上长得一模一样。现在按静态层号画成一张图，规则只有三条：

  • 链压一行：某步只有一个上游、而那个上游正好是它所在行的行尾，就接在同一行后面；
  • 汇合：某步有多个上游时，它画在第一个上游那一行的右端， 其余上游各自在自己行尾用 ───┤ / ───┘ 拐上去；
  • 分叉：某步有多个下游时，第一个接在行内，其余从同一列往下引（下行以 └──> 开头）。
调研并写方案 · 1/3 步 · 已跑 39s · 1 在跑
L1 [x] 调研 A（scout） ────────┬──> L2 [ ] 写方案（planner）
L1 [~] 调研 B（scout） 已 38s ─┘

两处细节值得注意。第一，连线的列位置由插件算：┬ 与 ┘ 必须落在同一列， 否则这张图读不懂——而列宽只有外壳知道，插件拿不到终端尺寸，因此它在 WorkflowText 里自带一份显示宽度计算（中日韩算两列、框线字符算一列， 与外壳的 DisplayWidth 同一口径）。 这是一次对「插件不做界面计算」的有意偏离，理由与 jellyfish-plugin-resmon 的 ResmonFormat 相同：插件不许用宽度做对齐， 但把自己内容限制在预算内是它自己的责任——没有尺度，一个中文名字就能把整行顶到折行， 而折行会让图形断开，还额外吃掉一行预算。

第二，算不出就退化成清单，而不是画歪：一行上要出现两个连线字形（同一行既有分叉又有汇合）、 竖线要穿过一行比它更宽的内容、汇合点落在行首（它的左臂没地方去）时，整条编排改用每步一行的清单， 行尾用 <- 上游 标出依赖（WorkflowLayout.java:387-400）。 宁可少画一张图，也不要给一张会让人读错的图——这条取舍写在类的注释里 （WorkflowLayout.java:42-45）。

8.2 行数预算：8 行，先撤已完成的层

面板用了哪些 UI 扩展点，可以说得很具体：贡献类型是 PanelContributionRequest → PanelContribution，落位是 UiRegion.TOP （UiRegion 只有 DOCK 与 TOP 两个取值， Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/ui/UiRegion.java:19-28）， 标题常量是「编排」，行数上限 MAX_LINES = 8 （WorkflowPanel.java:46、54）。

8 这个数是抄外壳的：外壳给 TOP 区域的内容行上限是 ChatLayout.PANEL_MAX_ROWS = 8（Jellyfish/jellyfish-tui/src/main/java/zcd/jellyfish/tui/ChatLayout.java:68， 经 ChatLayout.panelRows 与 ChatShell.panelElement 施加）。 两边口径不一致时，插件精心折叠出来的「…另有 N 步未显示」永远轮不到触发—— 先被外壳换成一句通用的「… 还有 N 行」。这是「插件自己先收一道，不依赖外壳兜底」的一个反例： 可自收的方式由插件定，数额必须与外壳对齐。

放不下时的收口顺序是有讲究的：先撤掉「已完成的层」（该层全部成功或跳过）， 把行让给正在跑与还没跑的；撤掉时下游那一行的行首补 … ───>， 说明「它是从上面接下来的」，而不是编排的起点。失败不在可撤之列—— 失败必须一直看得见，那正是要看面板的时刻。连已完成的层都撤完了还不够，才截断并在末行如实报出 「…另有 N 步未显示」（WorkflowLayout.java:115-141、316-345）。

插件注释给 TOP 的理由是：停靠区里已经排了内核那块「子代理」面板，而一次编排就是批量派子代理—— 两块面板恰好在同一时刻都要看，同区域等于永远只能看见一个；上方是全宽，连线也不会因为纵向栏只有 18 列而折行 （WorkflowPanel.java:22-25，注释同时说明这只是软建议，外壳可以忽略）。

8.3 会自己跳的数字

编排最长的一段是「什么都不输出」的沉默期（几个子代理各自在调模型）。这段时间里， 用户确认「它还在动」的唯一依据就是会变的数字：标题行的「已跑 39s · 1 在跑」， 以及在跑那一步自己的「已 38s」。

关键在于这套东西不需要插件起线程：外壳在回合进行中 每秒主动让插件内容失效一次 （Jellyfish/jellyfish-tui/src/main/java/zcd/jellyfish/tui/TuiApp.java:300 的 LIVE_REFRESH_MILLIS = 1000L，在 render() 里置位）， 于是「面板内容里带有时间」就等于「它会自己跳」。 内核那块「子代理」面板的「已运行 Ns」用的是同一条路 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/subagent/SubAgentPanel.java:133-152）。 插件要做的只有一件事：把时刻记下来（见本节开头），面板只算差值。

耗时文案是三档：一分钟以内说秒（38s）、一小时以内说分秒（1m02s）、 再长说时分（2h05m）（WorkflowText.java:117-126）。 只有正在跑的那一步带耗时：已结束的不需要再证明自己跑过，未开始的没有可说； 真正回答「卡没卡」的是标题行上的整条编排墙钟。

面板上的每一行由状态决定标记与强调档位，标记刻意用 ASCII 而不是符号—— StepState 的类注释解释了原因：终端字体与 East Asian Width 的差异会让 ✓ / ▶ 在不同环境里占 1 格或 2 格，而列宽由外壳算，插件给宽字符会让它算错。

状态标记面板强调档位进度里算不算「已了结」
PENDING[ ] NORMAL否
RUNNING[~] ACCENT否
DONE[x] DIM是
FAILED[!] ERROR是
SKIPPED[-] DIM是

「失败与跳过也算已了结」这条常被忽略，WorkflowProgress.settledCount() 的注释专门解释了它： 它们不会再跑第二次，因此进度条该往前走——否则「3 步跑了 2 步、其中 1 步失败」会显示成 1/3，看起来像卡住了； 失败这件事由标题行的警示档位与步骤标记表达，不靠进度数字（WorkflowProgress.java:111-150、 WorkflowPanel.java:141-155）。

坑点：面板处理器里绝不能发失效事件

现象：界面陷入「失效 → 收集 → 失效」的持续重绘，或日志里出现内核那条 self-loop 告警。 根因：失效事件的意思是「你缓存的我的那块已经过期了」，而收集面板时再发一条就等于说 「我刚给你的东西又过期了」，永远收敛不了。内核把这条写成硬约束（收集期间只 loud 出来，见 UiContributions.java:242-246），WorkflowPanel 的注释也复述了它：处理器「只读一次台账快照、拼几行文本， 不做 I/O、不发失效事件」——通知由 WorkflowTracker 在状态变化时发。 规避：需要「内容变了」的通知，就在写状态的地方发，不要在读状态的地方发。

工具名是路由键（WorkflowTool.NAME = "workflow"，WorkflowTool.java:33）， 注册时用 handle 精确匹配（同一「请求类型 + 路由键」至多一个处理器）， 参数只有一个必填的 spec（WorkflowSpecParser.ARG_SPEC = "spec"， WorkflowSpecParser.java:30）。 三行 handle 把依赖都从请求里取出来：会话（没有会话直接拒绝）、取消令牌、工具输出旁路—— 后两者就是引擎用来做取消传播与写进度的输入（ Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/ToolCallRequest.java:160、169）。

10.2 没有命令，也没有配置项

这一点值得写明确，因为它与「编排」这个名字给人的预期相反：本插件不注册任何命令。 start() 的三条注册里没有 CommandContributionRequest （Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:51-54）， src/main/resources/ 下也只有 plugin.properties 一个文件—— /workflow 这样的命令不存在。编排的入口只有模型主动调用工具， 而工具调用的准入、审批、回灌走的是内核既有的那条路（见 07 页、 08 页）。

配置项同样没有，而且是有意为之：类注释写着「本插件没有配置项：spec 的形状是模型与插件之间的契约，不是部署参数」 （WorkflowPlugin.java:33）。start() 里也从不读 context.configuration()， 而是把「一次编排能多大」写成源码常量 MAX_STEPS = 12。 需要调整规模时，改的是内核侧的 subAgent.maxSpawnsPerTurn（额度）， 而不是插件配置——因为「本回合还能派几个」这件事只有内核知道。

10.3 回灌给模型的东西：首行结论 + 聚合正文 + 失败清单

Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowTool.java:168-185（headerOf：把失败写进首行）
    private static String headerOf(WorkflowRun run) {
        StringBuilder header = new StringBuilder("[workflow ").append(run.getSpec().displayName());
        if (!run.hasFailure() && !run.hasCancellation()) {
            header.append(" 完成");
        }
        header.append(" · ").append(run.getSteps().size()).append(" 步")
                .append(" · ").append(run.totalRounds()).append(" 轮")
                .append(" · ").append(run.totalTokens()).append(" tok");
        StepOutcome failure = run.firstFailure();
        if (failure != null) {
            header.append(" · ").append(failure.getStep().getId()).append(" 失败");
        } else if (run.hasCancellation()) {
            header.append(" · 已取消");
        }
        return header.append(']').toString();
    }

首行只写「归谁」的一个结论——要么 完成、要么只有第一个失败的步骤、要么 已取消； 后面跟一个 —— 分隔的清单，逐条列「失败：id（agent）：原因」与 「未执行：id（原因）」（WorkflowTool.java:191-204）。 顺序是刻意的：模型从上往下读，先读到的是它下一步决策最需要的信息。

元数据键取值谁消费
workflowSteps步骤数工具轨迹行 / 观测
workflowRounds累计轮数（含汇总）同上
workflowTokens累计 token（含汇总）同上
summary（ToolMetadata.KEY_SUMMARY） 「workflow 名字 · N 步 · R 轮 · T tok」 轨迹行的单行摘要

最后一行是个容易读漏的细节：INCOMPLETE 这个字符串是插件自己的取值， 内核只做「有没有这个键、是不是 COMPLETED」这层判断（WorkflowTool.java:44-50）。 也就是说，插件不必与内核共享一份枚举就能表达「这次没正常跑完」。

11. 设计难点与取舍

难点本插件的选择代价 / 边界
编排状态放内存还是落盘 只放内存：WorkflowTracker 里那张 Map（WorkflowTracker.java:30-31） 进程重启即消失，且一次编排没有「续跑」这种状态——它整个活在一次工具调用里； 面板展示的是「此刻在跑什么」而不是历史，因此跑完即移除（WorkflowTracker.java:21-22）。 完整过程另有落点：每次子代理 run 的 transcript 由内核归档，路径经 DelegationResult.getArchivePath() 传出来
归档也不是无限的 依赖内核的归档上限 归档受文件数与字节数上限约束，最旧的会被清理（SubAgentSettings.java:111、119）， 因此材料块里那条路径可能读不到——引用它的下游要容忍这一点
并发上限 交给内核 governor；插件只在开始前查一次额度快照 额度是快照、随时可能过时（同一回合里 task 或另一个编排也会占用它）—— 它足够支撑「该不该开始」的判断，不适合拿来做精确分配（DelegationQuota.java:16-17）
失败重试 没有重试 补救由模型显式写成一步（when = on_failure + needs）， 或重新提交一份 spec；REJECTED（根本没开始）与 FAILED（开始过但失败） 在编排语义上刻意不同：前者重试同一请求没有意义，后者可能是环境问题（DelegationStatus.java:9-11）
表达力上限 三个 when 取值、无循环、无变量、无表达式 需要更复杂的判断时，让模型重新发一份 spec，或把判断拆成更多步骤—— StepCondition 的注释把理由写得很直白：「声明式 spec 一旦允许条件 + 循环 + 变量， 就会在无人察觉时变成一门语言，而维护一门语言（语法、版本兼容、错误语义）的成本远高于它带来的编排收益」
与内核的分工 内核只出原语（委派端口 + 工具/提示词/面板扩展点），spec 的形状与聚合方式全在插件里 插件缺席时 task 薄工具照旧可用，这正是「卸载即回退」； 而编排的表达形式演化时不必动内核的发布节奏（WorkflowPlugin.java:29-33）

「状态只在内存」这一条值得再强调一次，因为它决定了排障方式：如果一次编排跑到一半进程被杀， 你不会在磁盘上找到「跑到第 3 步」这样的记录——编排本身没有持久化，也没有恢复。 能查到的是每个已结束 run 的归档 transcript，以及会话历史里那次失败的 workflow 工具调用。

另一处取舍在「一次编排占一条工具执行线程」：await 是阻塞等待， 因此 12 步并不等于 12 条线程被占，而是「1 条工具线程 + 内核 agent-run 池里的若干个 run」。 这也意味着编排的墙钟时间约等于各层里最慢那一步之和，而不是各步之和——这正是分层的收益。

设计依据：为什么编排不进内核

类注释给的理由是「编排的表达形式（spec 长什么样、怎么聚合）会随着用法演化， 把它放进内核意味着每次调整都要动内核的发布节奏；而内核只需要提供稳定的原语」。 这句话有一个可检验的推论：本插件只需要 jellyfish-api 一个编译期依赖， 而内核侧「接到真端口之后行为如何」由内核自己的测试覆盖—— 插件侧的端到端测试用的是一个脚本化假端口，它照样能跑完整份 spec （Jellyfish-Plugins/jellyfish-plugin-workflow/src/test/java/zcd/jellyfish/plugin/workflow/WorkflowEndToEndTest.java:55-58，测试类注释）。 这既是解耦的证明，也是它的代价：两边各测一半，合起来才是完整的一条链。

12. 坑点小结与测试

坑点：面板的「失效通知」漏了，面板会晚到且已经空了

现象：整条编排期间面板始终不出现，直到跑完之后才闪一下（那时它已经空了）。 根因：外壳只在缓存失效时收集面板，而「某一步跑完了」发生在回合内部的工具调用里，外壳自己看不到。 规避：任何改变面板内容的写操作都要回调一次失效通知——本项目里 WorkflowTracker 的每个写方法都在锁内调 notifyChanged()， 由插件把它变成 UiInvalidatedEvent。漏一个写点，那一类状态变化就永远看不出来。

别把它和「数字会自己跳」混为一谈：外壳在回合进行中每秒会让插件内容失效一次 （TuiApp.java:300 的 LIVE_REFRESH_MILLIS），于是面板上的「已跑 39s」会自己走。 那条机制只对已经在显示的面板生效——它让内容变新，不能让一块从没出现过的面板出现。 两条路径都要有，面板才既出现、又活着。

坑点：把「同层」当成「能互传结论」

现象：两个步骤互相写了对方的 id 想交换结论 → 依赖成环，spec 被整份拒绝； 或者把 B 的结论写进 A 的任务里 → 什么都没注入，因为同层步骤在 blockReason 与 promptFor 执行时对方还没跑。 根因：材料只从直接 needs 流向本步，而同层意味着「依赖都相同或已决」。 规避：要传递结论就写成前后两层（这也是并行调研 + 汇总的标准形状，见图 20-2）。

坑点：把 TRUNCATED 当失败排查

现象：某个子代理明明给了正文，编排却把它算作成功，下游拿到的是「不完整的结论」。 根因：isSuccess 把 COMPLETED 与 TRUNCATED 都算成功 （WorkflowSpecParser.java:190-198），面板上这一步显示 [x]，但它可能没收敛。 规避：判断「结论可不可信」要看材料块本身，以及轨迹行上的状态文本—— statusText 把 TRUNCATED 翻成「达到轮数上限」而不是「完成」 （WorkflowEngine.java:493-505）。

关键结论

  1. 本插件补的是「并行 + 依赖 + 聚合」这三个只在多步骤时才暴露的缺口， 输入是一份一次性提交的声明式 spec（steps / needs / when / aggregate）， 而不是一段可执行的编排语言。
  2. 所有校验都发生在派生任何子代理之前（类型、必填、唯一、自依赖、引用存在、无环、步数上限、 on_failure 必须有 needs），越界即整份拒绝——包括额度不足也是整份拒绝， 不做「能跑几步算几步」。
  3. 调度的全部实现是「反复取就绪层 → 整层先全部 spawn、再逐个 await」； when 只有 always / on_success / on_failure 三个取值， 只按直接依赖的成败判断，且「达到轮数上限」算成功。失败不中断整条编排，只由各步的 when 决定谁被跳过。
  4. 执行者不是插件自己起的线程，而是内核给的 SubAgentPort （context.delegations() → port.spawn(...).await()）， 与 task 工具走同一条代码路径；插件不持有任何线程池，并发度由内核 governor 决定， 它只在本回合额度不够时提前整份拒绝。
  5. 状态只在内存里：WorkflowTracker 是一张锁保护的 Map，跑完即移除； 一次编排的存活期就是那一次工具调用，进程重启后没有续跑，能查的只有各 run 的归档 transcript。
  6. 可观测靠三个站点凑齐：WorkflowTool 的首行结论与元数据（模型可见）、 ToolOutputSink 的单行进度（工具行可见）、WorkflowPanel 落 UiRegion.TOP 的常驻面板 （人可见，靠 UiInvalidatedEvent 才能及时出现，靠外壳每秒的失效让面板上的耗时自己跳）。
