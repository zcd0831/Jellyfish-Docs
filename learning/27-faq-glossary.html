27 常见问题与术语表

阅读过程中随时回来查。术语按主题分组，每条给一句释义 + 源码位置 + 深入阅读的页面。

学习目标

  • 用一句话说清项目里每个专有名词的含义与落点；
  • 遇到高频疑问时能直接跳到解释它的那一页；
  • 知道哪些术语在本项目里有非标准含义（例如 boundary、spill）。

A. 架构与装配

术语释义位置 / 详见
外壳（shell） 与用户交互的那一层：-cli / -tui / -server。三种外壳共享同一内核。 03 页
内核（kernel） api + infra + core 三模块。只提供机制，不提供能力。 01 页
composition root 装配层。jellyfish-di 就是它——「谁依赖谁、哪些实例必须唯一」只写一份。 di/、03 页
JellyfishRuntime 不含任何 DI 注解的普通接口，23 个访问器。外壳只认它，不关心对象图是 Dagger 还是手写的。 JellyfishRuntime.java
AgentHarness 内核的「装配 + 生命周期 + 智能入口」枢纽。chat(sessionId, input, listener) 是内核的回合入口（外壳经 ConversationService.submit + ShellStreams.subscribe）。 core/AgentHarness.java、04 页
RunMode 模式实现接口，只有 checkEnvironment / shell / run 三个方法。三种外壳的差异全在实现类里。 cli/mode/RunMode.java
装配期 vs 运行期 装配期 = bootstrap() 之前/期间（读配置、建对象图）；运行期 = 回合在跑。 某些配置在装配期就被读走，改完必须重启。 25 页 A8

B. Agent 循环与会话

术语释义位置 / 详见
ReAct Reason + Act 交替：模型输出 → 执行工具 → 结果回灌 → 再问模型。本项目的实现是带上限的 for 循环，不是状态机。 core/ReActLooper.java:432-523、04 页
轮（round） 一次模型调用。上限 react.maxRounds（缺省 16）/ subAgent.maxRounds（缺省 8）。 ReactSettings.java:39
回合（turn） 从一次用户输入开始，到得出一个终态为止，可能含多轮。终态四种： completed / truncated / cancelled / blocked。 ReActResult.java:74, 102, 113, 131
在途回合表 / TurnRegistry / Slot 每个会话一个信号量槽位，挡住同一会话的并发提交；Esc 取消也走它。 登记必须带槽位（没有无槽位重载）。 TurnRegistry.java:62, 136, 206, 265
react 线程池 跑顶层回合的固定 8 线程池，队列 128，daemon，线程名前缀 react。 审批 / 提问的等待发生在这里，所以它的容量是个敏感参数。 ReActLooper.java:85, 913-925
agent-run 线程池 跑子代理 run 的独立池。嵌套回合绝不进 react 池——这是避免死锁的结构性设计。 RunScheduler.java:105-139
run 一次子代理执行实例（含自己的会话、上下文、预算）。与「回合」不同层级：一个 run 里可能含多个嵌套回合。 core/runtime/、04 页
RunTree / 额度 / 深度 整棵委派树的形状约束：depth < maxDepth && spawnCount < maxSpawnsPerTurn（缺省 1 / 12）。 RunTree.java:66-67、SubAgentSettings.java:40, 53
许可（permit） Semaphore 许可，控制同时真正在跑的 run 数（缺省 3）。 父 run 在等子 run 时会让出许可，否则会死锁。 RunScheduler.java:432-436、AgentRuntime.java:113-125
STEER / drainTurnBoundary 插件在「工具批次之后、收敛之前」插一条消息，让本回合多跑一轮（而不是开新回合）。 ReActLooper.java:488, 516、ActionDispatcher
提交管线 / Submission 把用户输入分流成「命令 / 输入指令 / 起回合」三类的入口。必须先订阅再提交。 core/conversation/Submission.java、CliRunMode.java:98-100
ephemeral（会话） 不落盘的会话——子代理会话就是。create() 也刻意不落盘。 SessionManager.java:196-206, 1300-1306

C. 权限与插件

术语释义位置 / 详见
核心策略 三段名单的判定：deniedTools > askTools > allowedTools。 精确集合匹配，没有通配符；allowedTools 为 null = 不限制，为 [] = 全拦。 PermissionPolicy.java:118-142、06 页
插件拦截 插件通过 PermissionCheckRequest 参与的判定。三态 ABSTAIN / ASK / DENY， 类型上没有 ALLOW——插件只能收紧。 PermissionVerdict.java:29-38
fail-closed 「说不清楚就拒绝」。审批的三个触发条件：无审批者 / 超时 / 中断。 插件拦截抛异常或返回 null 也按拒绝。 ApprovalChannel.java:304-330、PermissionManager.java:205-216
fail-open 「说不清楚就放行」。ask_user 是 fail-open（无人应答时返回「不可用」让模型继续）， 审批是 fail-closed。两者不同，别混。 AskChannel.java:204-206
TOCTOU 「检查后使用的时间差」。本项目用它解释为什么参数改写必须在权限判定之前—— 否则审批看到参数 A、实际执行参数 B。 ToolExecutor.java:180-184
扩展点 插件接入内核的 27 个位置。类型即地址——不用字符串 ID，请求的 Class 对象就是地址。 api/extension/、16 页
ExtensionRegistry 同步、不可丢的扩展点派发器。调用方要等返回值。 infra/extension/ExtensionRegistry.java
EventChannel 异步、可丢的事件通道。判据是「能否丢弃」而不是「有没有返回值」。 与 ExtensionRegistry 共用同一个 TypeRegistry。 infra/event/EventChannel.java
ShellIngress / 外壳贡献 插件把内容「推」给外壳的信箱（present()），容量 64，满即丢最新。 ShellContribution 是唯一不是 *Request 的扩展点。 infra/shell/ShellIngress.java:64, 75, 209
owner / 命名空间 注册项的来源标记，形如 pluginId::unit。回收按前缀 pluginId::* 一次清干净。 因此 plugin.id 不能含 ::。 PluginOwnerNamespace.java、PluginContextFactory.java:193-206
fail-closed（插件停后） stop() 之后任何注册 / 发布会当场抛错。 注册窗口是「插件存活期」而不是「start() 期间」。 ContextLifecycle.java:34-43
PluginClasspathGuard 运行期护栏，只拦 zcd/jellyfish/api/ 与 org/pf4j/ 两个前缀。 只记 loadError 不抛异常，所以冲突表现为「静默不启动」。 PluginClasspathGuard.java:29-32, 47-60

D. 上下文与提示词

术语释义位置 / 详见
boundary（压缩边界） 本项目的非标准用法：一个消息下标。边界之前的消息已被摘要替代， 组装时从边界之后开始取历史。压缩 = 把 boundary 往前推一格，历史一条不删。 PromptAssembler.effectiveBoundary、10 页
裁剪（crop） ContextWindow 从最新组向最旧组累加，装不下就整组丢； 最新一组永远保留、单独超预算时组内截断。只裁本次请求，不写回会话。 ContextWindow.java:59-79
老化（aging） ToolResultAger 把已落盘的信封换成更短的 stub。 非信封消息一个不动。agingPercent = 0 是切换口径，不是关闭。 ToolResultAger.java:30-40, 121-126
压缩（compaction） 插件能力（CompactionStrategy），内核只给机制。 触发：使用率 ≥ autoCompactPercent（缺省 80）或本次已发生机械裁剪。 非破坏式，屏幕与落盘仍是全文。 ConversationCompactor.java:290-301
cache-safe fork 压缩摘要调用复用父请求的字节前缀 + tool_choice: none， 目的是命中 prompt cache，避免「压缩比被压缩的对话还贵」。 ConversationCompactor.java:427、PromptAssembler.buildFork:197
spill（溢写） 工具输出超过阈值时落盘。SpillCapturingSink 未溢出时全缓冲，超 maxChars 才转溢写、 只留头尾窗口。落盘上限保护的是磁盘，不是 CPU。 SpillCapturingSink.java:78-135, 196-206
回灌信封 落盘之后回灌给模型的那段合法 JSON： _truncated / _tool / _total_chars / _total_lines / _path / _hint / _partial / preview。 _hint 里写明怎么回读。 ToolOutputEnvelope.java:29-57, 259-269
_partial true 表示落盘文件本身也不完整（触及溢写上限），回读拿不到全部。 ToolOutputEnvelope.java:41-56
工具配对（pairing） assistant(toolCalls) 与 tool 结果必须同进同出。 破坏配对（孤儿 / 悬空）会被厂商 400 拒掉，而且之后每次请求都失败。 ToolPairing.java:30-40
PromptPlacement 提示词贡献的三档：STATIC / SESSION / VOLATILE。 分档的意义是缓存前缀，且只有追加、没有替换语义。 PromptPlacement.java:18-39
TurnContextRequest 往本轮用户消息里追加内容的扩展点。 会随轮次变化的状态应该走它，而不是塞进 system prompt（后者会毁掉缓存）。 PromptAssembler.java:660
CacheBreakWatcher 逐轮比对三层指纹（system prompt 散列 / 工具清单散列 / 逐条消息散列），断裂时 WARN 一次。 命中率不在这里统计，由 SessionUsageSnapshot 现算。 CacheBreakWatcher.java:27, 351、SessionUsageSnapshot.java:9-12
keepAliveSeconds 定时重发「复用父前缀 + 最小输出」的请求以续 cache TTL。 缺省 0（关闭），每空闲期最多 3 次，每次都是计费调用，且与 thinking.budget_tokens 互斥。 ProviderCacheSettings.java:34-46、CacheKeepAlive.java:92-208
TokenEstimator 不是「字符数 / 4」：CJK 按 1 token、其余按 0.25，向上取整；每条 +4，每个 toolCall +2。 TokenEstimator.java:14-24, 60-90

F. 常见问题

Q1. 我没有模型 API，能玩吗？

能，但只能用命令域：-cli -p "/help"。命令走 CommandManager，完全不经过 LLM。 但没有模型就没有 agent 能力——工具调用是模型驱动的。

Q2. 我把 models.json 放在项目里了，为什么不生效？

因为项目级配置默认不加载。用 --trust-project-config（仅本次）， 或者在 TUI 的确认框里选择记住。详细理由见 01 页。

Q3. 为什么我配了 allowedTools: ["shell*"] 还是被拒？

因为没有通配符。shell* 是个普通字符串。必须精确列名。见 06 页。

Q4. 我装了插件，但 /reload 之后没生效？

如果变的是jar 本身（新增 / 删除 / 替换），必须重启进程—— PF4J 管理器明确「不做 jar 热部署」。/reload 只管「已加载插件的配置段变化」与「启用 / 禁用名单变化」。 见 25 页 B1。

Q5. 为什么我按 Enter 没反应？

TUI 的发送键是 Ctrl+S，Enter 是换行。 原因是多数终端不解码修饰键，做不出「Enter 发送 / Shift+Enter 换行」。见 14 页。

Q6. 为什么它一直卡着不动？

按可能性排序，三个方向：

  • 在等审批：TUI 会弹框；-cli 无审批者会立即拒绝（不会卡）。 如果是 TUI 卡着，看是否有弹框被别的输出挡住。
  • 配了 timeout: 0（永不超时）：ask.timeoutSeconds 或 permission.approvalTimeoutSeconds 写 0 会永久等待，且不自愈。见 25 页 C1。
  • SSE / 网络空闲超时：流式有 300 秒空闲超时，超时会走 streamFailure，不会无限等。

Q7. 上下文里的内容我看不到了，是丢了吗？

大概率没丢。有四层「上限」，口径完全不同：消息区 500 条（屏幕）、裁剪（本次请求）、老化（本轮 tool 结果形态）、 压缩（后续边界）。四者都不删历史。见 10 页与 25 页 D4。

Q8. 我想让它并行干活，怎么做到？

一个回合内的多个工具调用是严格串行的。要并行得用编排：多个 task 先 spawn 再 await（SubAgentLauncher.java:164-170），或者用 jellyfish-plugin-workflow。 并发由许可门控（缺省 3）。见 04 页。

Q9. 账单比预期高很多，先查什么？

  1. system prompt 是否每轮都在变（插件塞了易变状态）——这会让整个历史按未命中价重发。 用 /usage 看 cacheReadTokens / promptTokens。
  2. 是否开了 keepAliveSeconds——它是计费调用，缺省应关。
  3. 是否标了 cache_control（Claude）——不标命中率恒为 0。
  4. 压缩频率——每次压缩是一次额外 LLM 调用（有 cache-safe fork 优化）。

见 10 页与 25 页 F 组。

Q10. -server 开了之后别人能读我的会话吗？

缺省只绑 127.0.0.1，本机之外访问不到。但如果你用 --host 0.0.0.0 暴露出去， 不配密钥就谁都能读。好在内核会拦住这种情况——绑非回环地址 + 无密钥 = 拒绝启动退 3。 配密钥请用环境变量 JELLYFISH_SERVER_API_KEY，不要用 --api-key（会进 ps）。 见 15 页。

Q11. 同一份 agents.json，CLI 能用，TUI 却被拒，为什么？

因为 -cli 从不挂接审批者，而审批 fail-closed——命中 askTools 就直接拒绝。 挂接审批的有两处：-tui（TuiRunMode.java:198）与 -server（JellyfishServer.java:166）；-cli 从不挂接。见 06 页。

Q12. 我想知道某个改动要不要重启进程？

改动重启进程？
插件配置段（jellyfish.json 里的 plugins.configurations）不用，/reload
启用 / 禁用名单不用，/reload
新增 / 删除 / 替换插件 jar要
plugins.roots（在 config.json）要
config.json 的任何改动要
models.json 的 vendorBody（不在客户端缓存签名里）要（或 /reload / clearCache()）
装配期读到的配置（如 subAgent 并发 / 墙钟）要

Q13. 怎么加一个新工具？

写一个 PF4J 插件，实现 ToolCallRequest 的 handler 并注册。 不需要改内核一行代码。细节见 16 页与 Jellyfish-Plugins 仓库的插件开发教程。 注意两个约束：插件 pom 里 jellyfish-api / pf4j 必须标 provided； 权限判定的通配符不存在，所以工具名要设计得能被精确列举。

Q14. 子代理的「只读模式」在哪配？

内核里没有「只读」这个概念。内核管的是「委派不得提权」（子授权必须是父授权子集）。 只读能力由插件自己声明，例如官方 plan 插件的 plugins.configurations.jellyfish-plugin-plan.readOnlyTools。 见 04 页。

Q15. 为什么日志里什么都看不到？

默认级别是 WARN 且只写 stderr（log4j2.xml:12-16）。 加 --verbose，或 -Djellyfish.log.level=DEBUG。 排查「配了不生效」类问题时必须先做这一步——很多坑都是只告警不报错的。

关键结论

  1. 本页里最需要记住的是三个非标准或反直觉的术语：boundary（压缩边界，不是文件边界）、 spill（输出溢写落盘）、fail-open（ask_user 是它，审批不是）。
  2. 遇到「配了不生效」，第一反应应该是降日志级别——这个项目里大量失败是「只告警不报错」的。
  3. 遇到「卡住了」，按「等审批 → 永不超时配置 → 网络空闲超时」三个方向查。
  4. 遇到「看到了 / 没看到」的困惑，先分清是屏幕、本次请求、本轮工具结果、压缩边界四层里的哪一层。
