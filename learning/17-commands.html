17 命令系统

命令是唯一不经过模型的输入通道：用户敲下的 /xxx 被内核直接执行，回执直接贴屏。 这一页讲清它凭什么能同时服务 CLI、TUI 与 HTTP Server，以及「名字怎么找、找不到怎么办、谁能没有会话」这三件事。

学习目标

  • 说清 CommandManager 为什么无状态、为什么对外壳中立，以及它依赖的注册表结构；
  • 解释注册签名与 owner 的关系，以及 removeAllUnder 回收的匹配规则；
  • 拿到别名与命令名碰撞时的判定优先级，并找到守着它的那条单元测试；
  • 说清 sessionRequired 缺省 true 的理由，以及 false 的两类分别是什么；
  • 解释 shouldRunAsCommand(input, hasSession) 为什么对「未注册名」与「语法错误」仍返回 true；
  • 说清 CommandResult 三态、候选清单与 handoff 接力各自归谁消费；
  • 划清三条边界：内核命令、输入指令（! / @）、外壳自有命令。

1. 命令域的位置与三个入口

命令域落在 jellyfish-infra 的 zcd.jellyfish.infra.command 包，一共四个类： CommandManager（门面）、CommandLineParser（解析）、 ParsedCommand（解析结果，包私有）、CommandInfo（清单项投影）。 公开出去的值对象全部在 api 侧：CommandDescriptor / CommandResult / CommandChoice / CommandArguments / CommandOptions。

门面有四个入口，服务三类调用方 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:39-40 的类注释写明了这个分工）：原文入口给输入框，结构化入口给「本来就有参数对象」的调用方， 结构化清单给「要自己排版」的外壳，只读候选入口给「选中即弹选择页」的外壳。

2. 为什么 CommandManager 无状态、对外壳中立

先给结论：它只注入两个协作者（同步扩展点注册表 + 事件发布入口）， 不注册任何处理器，不缓存索引，公共入口不抛异常。 这四条合起来才让「CLI / TUI / Web 共用同一份命令域」成立。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:28-54（类注释：五条设计约束一次说清）
/**
 * 命令域服务：输入解析 / 别名解析 / 分发 / 结构化清单 / 帮助渲染。
 * <p>
 * <b>只注入 {@link ExtensionRegistry} 与通知入口</b>：命令域不持有会话、不读配置——会话标识由调用方随
 * 输入一起带进来，命令的副作用由处理器自己写回对应域服务。唯一外发的是分发结束后的
 * {@link CommandExecutedEvent}（审计用，best-effort，发布失败不影响命令结果）。
 * <p>
 * <b>不注册任何处理器</b>：系统命令与插件命令都经 {@code ExtensionRegistry.handle(...)} 落同一份注册表，
 * 本类只做「按名字取出来执行」与「按类型取名字与名片」两件事。命令名即路由键，别名与用法来自随处理器
 * 一起落表的 {@link CommandDescriptor}，因此不存在第二份命令清单。
 * <p>
 * <b>对外壳中立</b>：原文入口服务输入框（CLI / TUI / Web 文本框），结构化入口服务直接调用
 * （Web API / TUI 菜单），结构化清单服务自排版的外壳；本类不假设输出到哪里，也不假设谁在调。
 * <p>
 * <b>无索引无缓存</b>：每次执行 / 渲染都从注册表现算，因此插件热部署后立刻可见；命令是人类节奏的调用，
 * O(命令数) 的重建可以忽略。
 * <p>
 * <b>公共入口不抛异常</b>：用户输入错误与插件缺陷都被翻译成 {@link CommandResult} 或清单 / 文案
 * （另打 WARN 日志）。唯一的例外是 api 侧值对象的构造期校验——那是编程错误，立即抛。
 * <p>
 * <b>系统命令已落地</b>：{@code /help} {@code /new} {@code /session} {@code /resume} {@code /model}
 * {@code /agent} {@code /status} {@code /usage} {@code /delete} {@code /compact} {@code /reload} 由
 * {@code core/command/SystemCommands} 以 owner = {@code "core"} 注册进同一份注册表（本类仍不注册任何处理器）；
 * {@code /todo} 归 {@code jellyfish-plugin-todo}，与其它插件命令同源；{@code /exit} 归外壳。
 *
 * @author zcd
 */

逐条读这段注释：

  • 「不持有会话」是硬约束，不是省略：会话标识由调用方随输入一起带进来 （execute(input, sessionId)）。一旦命令域自己去问「当前会话是谁」， 它就必须依赖会话域，也就再也不能被 Server 这种「会话由请求路径提供、根本没有当前会话概念」的外壳复用。
  • 「不注册任何处理器」把命令域和系统命令切开：系统命令落在 jellyfish-core 的 SystemCommands，因为它要读会话、模型、agent 三个域服务； 命令域只认注册表，因此它自己永远不需要那几个依赖。这也解释了为什么 CommandManager 能待在 infra 层而系统命令必须在 core 层。
  • 「无索引无缓存」是热部署的前提：每次 commands() / match() 都现读注册表，所以插件刚注册的命令下一行输入就能用、插件被卸载后立刻消失。 单元测试直接用两条用例守着它：见 Jellyfish/jellyfish-infra/src/test/java/zcd/jellyfish/infra/command/CommandManagerTest.java:251-261 与 Jellyfish/jellyfish-infra/src/test/java/zcd/jellyfish/infra/command/CommandManagerTest.java:263-272。
  • 「不抛异常」是外壳安全的前提：命令清单读不出来（插件注册了一个非 CommandDescriptor 的描述符）时，用户看到的是一条错误文案，而不是外壳崩掉。
设计依据：为什么把「命令名」做成路由键，而不是给每条命令一个 Java 类型

CommandRequest 的类注释给了理由 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/CommandRequest.java:11-12）： 插件自定义的类跨 ClassLoader 传播会类型互不可见，内核也无法为「未知类型」提供调用点。 把命令名放进数据里，注册表就只需要 「请求类型 + 路由键」两个字符串级的事实，插件升级换实现不改变调用点。

代价是命令名成了用户可见契约，必须有别名与冲突规则——这就是第 5 节的内容。

3. 解析层：前缀、命令名与引号

解析被单独放在 CommandLineParser，而且刻意不认识别名、不查注册表。 它只回答「这行输入在语法上是不是命令、命令名是什么、参数怎么切」。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandLineParser.java:8-24（切分口径全表）
/**
 * 命令行解析器：前缀判定 + 命令名提取 + 引号感知切分 + 原文提取。
 * <p>
 * 只认前缀与空白，不查注册表、不认识别名：别名属于注册表事实，由 {@link CommandManager} 解析。
 * <p>
 * 切分口径（刻意保持最小可用）：
 * <ul>
 *     <li>先去掉输入首尾空白，首字符不是 {@link CommandManager#COMMAND_PREFIX} 即为非命令；</li>
 *     <li>命令名 = 前缀之后到第一个空白为止，必须非空，大小写敏感；</li>
 *     <li>{@code raw} = 命令名之后的原文（仅去掉紧随命令名的那段空白），引号与内部空白原样保留；</li>
 *     <li>{@code tokens} 按空白切分，{@code "} 与 {@code '} 成对包裹，引号内空白不切分、引号字符本身不进入
 *     token，{@code ""} 产出一个空 token；双引号内 {@code \"} 与 {@code \\} 转义；</li>
 *     <li>引号未闭合是解析错误：与其猜用户意图（读到行尾？丢掉引号？），不如当场报错。</li>
 * </ul>
 *
 * @author zcd
 */

三个细节值得单独记：

  • 「只有前缀、没有名字」不算命令：parse 在名字为空时返回 ParsedCommand.notCommand()，注释写着「这是『不是命令』，而不是『未知命令』」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandLineParser.java:57-60）。 于是单敲一个 / 会被当成普通文本，而不是报「未知命令 /」。
  • 大小写敏感：/Help 与 /help 是两条不同的名字， 前者会得到「未知命令」。
  • 切分结果有两种视图：tokens 给结构化命令，raw 给自由文本命令。 CommandArguments 的注释说明了为什么两个都要留 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/CommandArguments.java:10-14）： 只给 tokens 会逼处理器把参数重新拼回去，而拼接必然丢信息（连续空格、原引号形态）。
坑点：参数里有引号时，处理器的「两种读法」会给出不同结果

现象：/note "记得 明天 改配置" 这类命令，有的实现读 getTokens() 看到一条参数，有的读 getRaw() 看到带引号的原文。

根因：raw 的定义是「去掉命令名之后，引号与内部空白原样保留」， 引号不被剥掉；而 tokens 里引号字符本身不进入 token。 这不是 bug，是两个刻意设计的视图——但处理器只能选一个口径。

规避：结构化命令（/agent coder）读 tokens 并校验 size()；自由文本命令读 raw。不要混用，也不要自己再切一遍。

4. 注册、owner 与回收

注册的动作永远发生在扩展点注册表上，签名是 handle(请求类型, 路由键, 描述符, 处理器, 选项)。 命令域只是「同一份注册表的另一个读法」：执行时按 CommandRequest + 命令名取处理器， 渲染清单时按 CommandDescriptor 取名字与名片。

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:216-240（内核自己的两行封装：执行处理器与只读候选处理器）
    /**
     * 注册一条命令。
     *
     * @param name       命令名（路由键）
     * @param descriptor 命令名片
     * @param handler    处理器
     * @return 注册句柄
     */
    private Subscription register(String name, CommandDescriptor descriptor,
                                  ExtensionHandler<CommandRequest, CommandResult> handler) {
        return extensions.handle(OWNER, CommandRequest.class, name, descriptor, handler, RegisterOptions.DEFAULT);
    }

    /**
     * 注册一条命令的只读候选处理器。
     * <p>
     * 与执行处理器同路由键、异请求类型，因此互不覆盖；候选处理器没有名片（名片属于命令本身）。
     *
     * @param name    命令名（路由键）
     * @param handler 候选处理器
     * @return 注册句柄
     */
    private Subscription registerOptions(String name, ExtensionHandler<CommandOptionRequest, CommandOptions> handler) {
        return extensions.handle(OWNER, CommandOptionRequest.class, name, null, handler, RegisterOptions.DEFAULT);
    }

这段只有两行有效代码，但它确定了三条事实：

  • owner 就是插件 id，内核固定是 "core" （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:81）。 owner 是回收的唯一依据，也是审计事件里 CommandExecutedEvent.getSource() 的来源—— 所以 dispatch 取的是 bindings 而不是裸 handler（注释见 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:368： 审计要记录「是哪个处理器响应的」）。
  • 同一条命令可以有「执行」与「候选」两个处理器，因为它们请求类型不同 （CommandRequest vs CommandOptionRequest），路由键相同也不冲突。 这是「选中即弹选择页」不用产生副作用的结构基础。
  • 候选处理器没有名片：名片属于命令本身，传 null。

回收：一条命令不会「永久消失」，但也不会「赖着不走」

插件停止时，框架只拿得到 pluginId，而插件可能给自己内部的多个子单元各分了 owner （形如 pluginId::子标识，用来做可归因的诊断）。因此回收用的是 命名空间前缀匹配，而不是精确匹配：

5. 别名解析与冲突规则

匹配只有一条规则，写在 match 里：先按命令名全表扫一遍，命中就立刻返回； 没命中才按别名收集。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:425-449（匹配的两个循环）
    /**
     * 按名字匹配命令：命令名优先，其次别名。
     *
     * @param nameOrAlias 命令名或别名，可为 {@code null}
     * @return 命中列表：0 个未命中、1 个唯一命中、多个表示别名有歧义；保证非 {@code null}
     */
    private List<CommandInfo> match(String nameOrAlias) {
        if (nameOrAlias == null || nameOrAlias.isEmpty()) {
            return Collections.emptyList();
        }
        List<CommandInfo> infos = commands();
        for (CommandInfo info : infos) {
            if (info.getName().equals(nameOrAlias)) {
                // 命令名优先：与命令名同名的别名因此静默不可达（文档已写明）
                return Collections.singletonList(info);
            }
        }
        List<CommandInfo> matched = new ArrayList<CommandInfo>();
        for (CommandInfo info : infos) {
            if (info.getAliases().contains(nameOrAlias)) {
                matched.add(info);
            }
        }
        return matched;
    }

「命令名优先」这条规则最容易被写反，因此有一条专门的测试盯着它。 测试里 mode 既是命令名、又是 model 的别名，敲 /mode 必须执行 mode：

Jellyfish/jellyfish-infra/src/test/java/zcd/jellyfish/infra/command/CommandManagerTest.java:235-248
    @Test
    void execute_should_prefer_command_name_over_alias() {
        // Given："mode" 既是命令名，又是 "model" 的别名
        register("plugin-a", "mode", new CommandDescriptor("切模式", null, null),
                request -> CommandResult.ok("mode"));
        register("plugin-a", "model", new CommandDescriptor("切模型", null, Arrays.asList("mode")),
                request -> CommandResult.ok("model"));

        // When
        CommandResult result = manager.execute("/mode");

        // Then：命令名优先，该别名静默不可达
        assertEquals("mode", result.getOutput());
    }

注意测试注释的最后一句：「该别名静默不可达」。内核不报错、不警告， /mode 永远命中命令 mode，那条别名等于不存在。 这是有意选的：如果报错，就等于要求每条命令名都不能与任何别处声明的别名撞车， 而那是一个全局约束——插件作者根本无法在自己的代码里确认。

别名则有另一个方向的问题：两个不同命令声明了同一个别名。这时匹配结果是 「多个」，分发路径把它翻译成一条带候选列表的错误：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:344-365（分发的三段出口：清单失败 / 未命中 / 歧义）
    private CommandResult dispatch(String name, CommandArguments arguments, String sessionId, String input) {
        long startedAt = System.currentTimeMillis();
        List<CommandInfo> matched;
        try {
            matched = match(name);
        } catch (RuntimeException e) {
            // 清单读不出来时不能报「未知命令」，否则会把插件注册缺陷伪装成用户拼错
            LOG.warn("读取命令清单失败: command={}", name, e);

HTTP 外壳只走半程，这一步必须由客户端补

POST /sessions/{id}/commands 是纯 JSON，与 /chat 的 SSE 契约分开， 服务端刻意不在这里自己起回合 （Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/CommandHandlers.java:46-50）。 因此 CommandResultDto 多一个 handoff 字段 （Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/dto/CommandResultDto.java:17-18）， 客户端要拿它再 POST /sessions/{id}/chat。TUI 与 CLI 由内核一次做完，用户无感。

坑点：外壳自己复制分流顺序，接力的那一格就漏了

现象：TUI 里 /init 只打印了一句「命令已执行」，模型完全没有开始读仓库。

根因：接力文本不进界面（handoff 与 output 互斥， 接力时 output 是 null）。如果外壳自己排了「先判命令、 再改写、再起回合」这条顺序，那它多半是「拿到 CommandResult 就渲染并返回」， 接力这一格就没人处理。

规避：外壳只声明 SubmissionPolicy，交给 ConversationService.submit 统一排顺序，然后按返回的 Submission.Kind 呈现 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/conversation/ConversationService.java:32-41 把这条列成不变量）。顺序不需要、也不允许在外壳里出现第二份。

设计依据：候选查询走一条独立的只读扩展点

执行命令可能有副作用（/new 建会话、/delete 删会话）， 而用户「刚选中命令、还没决定参数」时不该有任何副作用。因此候选查询不复用 CommandRequest，而是 CommandOptionRequest（返回 CommandOptions）——类注释写得很直白： 「用执行结果承载它，会把『查询』与『执行』混成一条语义，也让『选中即弹选择页』这条路径 看起来像发生过副作用。因此给它一个独立结果类型。」 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/CommandOptions.java:12-14）。

代价是每个有候选的命令要注册两个处理器 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:200-203 给 /resume /model /agent /delete 各注册了一个只读候选）。这个代价换来的是「选中即弹页」这条路径结构上不可能有副作用。

查询失败也全部降级：未知名、清单读不出、候选处理器不唯一、处理器抛异常——四种都当作「没有候选」 返回空列表并打 WARN （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:170-174）。 候选只是输入辅助，不该影响用户继续输入。

还有一处值得单独记：补全面板的接受路必须先问外壳自有命令的候选入口。 /ui 不在命令域里，问命令域只会得到空清单，于是它会退化成「回填命令名、 下次发送才弹页」，与 /resume 的「选中即弹」行为不一致。 外壳侧的答复方是 ShellCommand.options，顺序与提交路径一致 （Jellyfish/jellyfish-tui/src/main/java/zcd/jellyfish/tui/TuiApp.java:809-817）。

「以 / 开头」只是一条语法边界，不是能力边界。 内核里同时存在三种「用户敲什么、系统做什么」的约定，它们各有各的落点：

名单里的 sessions 与 rm 是 /session 和 /delete 的别名。 这就是「别名必须一起进拒绝名单」的原因：只写命令名，用户换个别名敲进来就绕过去了。 check 的判定与抛出在 Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/ServerCommandGate.java:57-67； 注意它的命令名解析自己写了一份（nameOf， Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/ServerCommandGate.java:75 起）， 不调用 CommandManager——被判定的一方不该负责解析判定依据。

注意：命令域与对话域同权，密钥泄露等于整机权限泄露

POST /sessions/{id}/commands 能执行 /reload 这类会改进程状态的内核命令， 因此命令端点的鉴权与 /chat 是同一档（docs/constraints.md 的 HTTP 安全一章）。 另外命令端点先校验会话存在（不存在回 404， Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/CommandHandlers.java:143-151）： 不校验的话幽灵会话 id 也能把命令跑起来、回 200 + kind=ERROR， 调用方就分不清「会话不存在」与「命令这次失败」。

DENIED 名单只保护「进程级状态」这一类风险；它不是权限系统。 真正的权限与审批链在工具调用上（见 06 页），命令不经过它。

14. 坑点清单

P1. 打错命令名被当成提示词发给模型

现象：敲 /hlep，模型开始回答一个不存在的命令。

根因：外壳把 shouldRunAsCommand 返回的 false 理解成「这不是命令」， 而保留 true 的场景里包含「未注册的名字」与「语法错误」——它们只该被命令域回一条明确文案。

规避：见第 8 节。判定表与用例一一对应，改代码前先看那 7 条用例。

P2. 别名与命令名碰撞，别名「静默消失」

现象：插件的别名怎么敲都不生效，也没有任何报错。

根因：命令名优先于别名，且判定不提示 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:437-441 的注释明说「文档已写明」）。

规避：别名命名避开内核 11 条命令名与其别名清单（第 11 节表格）；同一插件内也不要让别名与自己的命令名相同。

P3. 以为「命令不过 LLM」就等于「命令不花 token」

现象：调 /compact 或 /init，账单上出现了模型调用。

根因：分发不过模型（CommandManager 只调处理器）， 但命令的副作用可以调用模型：/compact 派发给压缩器 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:550）， handoff 会起一个完整回合 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/conversation/ConversationService.java:143-154）。

规避：把「命令不消耗 token」精确表述为「命令分发本身不消耗 token」。 想只看不发，用 /compact preview （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:564 起只回报计划）。

P4. 外壳自己复制分流顺序，接力的那一格漏掉

现象：/init 只回一句「已执行」，模型没动。

根因：handoff 与 output 互斥，接力文本不进界面； 只有 ConversationService.submit 会用它替换输入。

规避：外壳只声明 SubmissionPolicy，按 Submission.Kind 呈现，不自己排顺序。

P5. 把「清单读不出来」报成「未知命令」

现象：插件注册了一个坏描述符，之后用户敲 /help 得到「未知命令 /help」， 看起来像内核没实现 /help。

根因：match 抛异常时若被当成「没命中」，插件缺陷就伪装成了用户拼错。

规避：内核已经在 dispatch 里把这种情形翻成 ERROR + 「命令清单读取失败：…」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/command/CommandManager.java:349-354）， 并用 Jellyfish/jellyfish-infra/src/test/java/zcd/jellyfish/infra/command/CommandManagerTest.java:204-217 守住。自己写清单派生逻辑时保持同一口径。

关键结论

  1. CommandManager 的全部能力来自「一份注册表的两种读法」：按 CommandRequest + 名字取处理器执行， 按 CommandDescriptor 取名字与名片渲染清单。它不注册处理器、不持有会话、不缓存索引， 因此 CLI / TUI / Web 能共用，插件热部署立刻可见。
  2. 命令名即路由键，owner 即插件 id；回收用 removeAllUnder(pluginId, "::") 做命名空间前缀匹配， 把「插件已停、命令还能用」的幽灵注册一次收干净，并让被它压住的内核实现自动回退。
  3. 别名与命令名碰撞时命令名优先且不提示；两条命令撞同名别名则报 ERROR 并列出候选人。这两条规则都有单元测试守着。
  4. sessionRequired 缺省 true（保守）；声明 false 分两类—— 本来不碰会话的 6 条与降级的 2 条（/model /agent 改 SessionDefaults）。降级类必须真的做到「无会话也能执行完」， 否则这个标志就是在说谎。
  5. shouldRunAsCommand 只在「有会话」或「唯一命中且不需要会话」时执行， 但未注册名与语法错误仍返回 true——把「未知」交给命令域回答， 比把打错的命令名当提示词发给模型安全得多。
  6. CommandResult 三态 + 两处结构化例外：候选（CommandChoice）归外壳渲染， 接力（handoff）归提交管线消费。接力是「只声明、不执行」： 命令没获得起回合的能力，接力文本与用户手敲逐字段一致地过改写、指令、权限链。
