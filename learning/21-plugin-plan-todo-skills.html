21 plan / todo / skills 插件

内核不内置规划器，规划能力全在这三个插件里。这一页逐个拆开它们：注册了什么、状态存在哪、 为什么这样存——最后一节是三者共有的那条硬约束（会话扩展条目的上限）。

学习目标

  • 说清 /plan [on|off] 的取值语义，以及它为什么只有一个布尔开关、没有第三个取值；
  • 解释「模式」为什么存进会话扩展条目，而不是内核字段、也不是插件自建文件；
  • 拿到 todo 插件注册的 1 个命令与 5 个工具，以及一条待办的四个字段；
  • 说清待办为什么落在 ~/.jellyfish/todos/ 下的自建文件里、进程重启后还在不在；
  • 说清 skills 的发现约定（子目录 + SKILL.md）与「清单常驻、正文按需」的三层披露；
  • 对比三者「改提示词 / 加工具 / 存状态」的三种做法，知道什么时候该用哪一种；
  • 知道会话扩展条目的三条硬上限，以及超限时的确切行为。

1. 三个插件回答的是同一个问题：把一种工作方式教给模型

内核只提供机制（循环、工具、权限、会话），「怎么规划」是使用习惯——这句话在 01 页已经论证过：把它内置进循环，意味着想换一种工作方式就得改 ReActLooper。于是规划这件事被拆成三个官方插件，各占一种做法：

设计依据：为什么「模式」不是内核字段，而「待办」不是会话字段

两条硬约束摆在一起看就清楚了。内核这边：没有「权限模式」字段——模式是插件能力， 存于会话扩展条目，内核不存它，新建会话也不接收它（Jellyfish/docs/constraints.md:306）； 同时模式类授权的名单不回内核（Jellyfish/docs/constraints.md:296）。 插件这边：待办只需要 sessionId 作为归属，而命令与工具请求都带它， 于是它可以自己拿一个文件当容器，内核既不用新增会话字段，也不必为它保留任何调用点 （Jellyfish-Plugins/jellyfish-plugin-todo/src/main/java/zcd/jellyfish/plugin/todo/TodoPlugin.java:48-50）。 反过来，plan 的状态是「一小段布尔」，正好落在内核已经有的「插件挂在会话上、随会话落盘、 插件之间互相看不见」那个位置上（PlanState.java:20-24），自己造文件反而要另立格式、 另做并发控制与清理。

2. plan 插件：一条权限策略，四个扩展点

2.1 /plan [on|off]：只有一个布尔开关

命令的实现很直白：无参时报告当前状态并给出候选，带参时接受 on / off， 其余一律报用法错误。真正值得读的是那个「读不出来」的分支。

Jellyfish-Plugins/jellyfish-plugin-plan/src/main/java/zcd/jellyfish/plugin/plan/PlanCommand.java:64-86（无参分支的三态处理，与 on / off 的写入）

这段把三件事一次说清：取值只有两个（PlanCommand.java:36-40 定义 on / off）、无参时给出候选（候选的文案与执行路径共用 PlanOptions.choices(boolean)，见 PlanOptions.java:50-56）、 状态不确定时不假装知道。

为什么不提供第三个取值？源码给的答案很直接：内核此前的 /mode 有 plan / normal 两个取值，那是「模式枚举」；这里只有一个布尔开关， 对外就只有 on / off，少一层「模式名为 normal 的常态」的概念负担 （PlanCommand.java:16-18）。命令声明里还有一处细节：末尾显式写了 sessionRequired=true，因为开关是按会话存的，没有会话就没有可切换的对象 （PlanPlugin.java:55-56，语义见 08 页）。

2.2 模式存哪：会话扩展条目里的一个布尔

状态由一个很薄的对象持有：条目 key 是 enabled（PlanState.java:63）， 写入时由内核补上 owner 前缀，拼成 jellyfish-plugin-plan::enabled （PlanState.java:84）；值是一个只含 enabled 字段的映射 （PlanState.java:136-140）。读取路径要处理三态，因此比写入长得多：

Jellyfish-Plugins/jellyfish-plugin-plan/src/main/java/zcd/jellyfish/plugin/plan/PlanState.java:103-127（沿父链查询，三态返回）
    Switch switchOf(String sessionId) {
        if (sessionId == null || sessionId.trim().isEmpty()) {
            // 没有会话就没有开关：这是「确定没开」，不是「读不出来」
            return Switch.OFF;
        }
        String current = sessionId;
        for (int depth = 0; depth < MAX_ANCESTOR_DEPTH; depth++) {
            Switch here = switchHere(current);
            if (here == Switch.ON) {
                return Switch.ON;
            }
            if (here == Switch.UNKNOWN) {
                return Switch.UNKNOWN;
            }
            current = context.parentSessionId(current);
            if (current == null) {
                // 走到链头了：沿链都没有开
                return Switch.OFF;
            }
        }
        // 到上限还没走到链头：后面的层里可能开着，按「读不出来」处理
        LOG.warn("plan 开关的父链超过回溯上限，按读不出来处理: sessionId={} depth={}", sessionId,
                Integer.valueOf(MAX_ANCESTOR_DEPTH));
        return Switch.UNKNOWN;
    }

图 21-2　开关的三态：UNKNOWN 不是第三种业务状态，而是「谁读它谁负责往哪一侧倒」

三态的存在理由写在同一处：读不到与确定关闭不是一回事。会话还在、条目却读不出来时， 若当作「关闭」，一道按模式收窄的授权就会在插件出故障的一瞬间静默消失，现场没有任何痕迹。 于是取舍留给调用方：权限拦截那侧按「开着」处理（fail-closed），展示那侧按「没开」处理 （PlanState.java:26-46、PlanState.java:139-149）。

为什么判定要沿父链：子代理跑在内核派生的独立会话上，它自己没有这条条目—— 只看本会话的话，「父会话开着 plan、模型借 task 派个子代理去写文件」就能绕过 「只看不改」。父链由内核如实给出（PluginContext.parentSessionId， Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java:379； 这条需求的原文见 PluginContext.java:369-371）。沿链取「或」， 链上任何一层开着就算开着；链上任何一层读不出来，整条链就按读不出来处理。 回溯上限是 16 层（PlanState.java:69），到上限还没走到链头同样按 UNKNOWN 处理—— 「查不全就不放宽任何东西」这条口径贯穿整个插件。

设计依据：为什么不给 plan 自己造一个状态文件

归属天然是「某一个会话」，而内核已经有一处「插件挂在会话上、随会话落盘、插件之间互相看不见」 的位置。自己写文件要另立格式、另做并发控制与清理，且会话删除时还得自己收尾—— 那正是待办插件不得不做的事，而 plan 没有这个必要（PlanState.java:20-24）。 代价是把状态交给了内核的容器，因此受它的上限约束（见本页第 6 节）。 另一条好处是：条目随会话一起恢复，/resume 回到一个开着 plan 的会话，它仍然是开着的 （PlanState.java:26-28）。

Jellyfish-Plugins/jellyfish-plugin-plan/src/main/java/zcd/jellyfish/plugin/plan/PlanPermission.java:51-69（拦截本体：只在「开着」时收窄，判不出来也收窄）
    public PermissionVerdict handle(PermissionCheckRequest request) {
        PlanState.Switch mode = state.switchOf(request.getSessionId());
        if (mode == PlanState.Switch.OFF) {
            return PermissionVerdict.abstain();
        }
        String toolName = request.getToolName();
        if (config.allows(toolName)) {
            return PermissionVerdict.abstain();
        }
        // 白名单为空是合法配置（就是「一个都不许」），但用户多半是漏配，因此补一条每种配置只喊一次的告警
        config.warnIfWhitelistIsEmpty(toolName);
        if (mode == PlanState.Switch.UNKNOWN) {
            // 判不出开着没有就按开着处理：不这样，状态读不出来的那一刻「只看不改」会静默失效，
            // 而模型只看到工具照常放行、用户也不知道自己开着的那道限制已经不在了
            return PermissionVerdict.deny("无法确认 plan 模式的状态（本会话的 plan 开关读不出来），"
                    + "按开启处理：" + config.denialReason(toolName));
        }
        return PermissionVerdict.deny(config.denialReason(toolName));
    }

三个要点。第一，它是类型级贡献：PermissionCheckRequest 的路由键恒为 null（Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/PermissionCheckRequest.java:12）， 因此每一次工具调用的权限检查都会进来，包括别的插件提供的工具——这正是 plan 模式的语义。 第二，它只能收紧：PermissionVerdict 里没有 ALLOW 这一态 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/PermissionVerdict.java:12-14， 三态合并规则见 06 页），所以 plan 关闭时返回 abstain()， 核心策略的结论原样生效。第三，处理器必须只读且快：它跑在权限判定的同步路径上， 因此只读内核内存里的会话扩展条目与启动期解析好的白名单，不碰文件系统、不起进程 （PlanPermission.java:22-27）。

设计依据：为什么拦截写操作，而不是「换一份工具清单」

内核确实有一个「这个工具该不该出现在本次清单里」的扩展点 ToolActivation （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/ToolActivation.java）， 三态而不是布尔。但 plan 不用它，理由写在 PlanPermission.java:11-16： 工具清单进的是缓存前缀里很靠前的位置，一旦按模式换集合，那一轮之后的前缀 （连同全部历史）都会作废；权限拦截则让模型看到的清单逐字节不变，只是写操作在执行时被拒—— 被判拒的理由还会经工具结果回灌给它，比「清单里少了一个工具」信息更全。 同一个取舍也解释了为什么计划模式的状态要随回合消息送达，而不是往 system prompt 里注 （PlanTurnContext.java:13-17）。

配置方面只有一条：plugins.configurations.jellyfish-plugin-plan.readOnlyTools （PlanConfig.java:43-49）。它是「plan 下哪些工具可用」的唯一来源， 不写就等于一个都不许——集合为空时同样拒绝，因为「用户没表态」与「用户不准」 在这里是同一件事（PlanConfig.java:20-24）。白名单为空时它还会补一条 ConfigWarningEvent，且用 CAS 保证每种配置只喊一次（PlanConfig.java:150-168）。

3. todo 插件：从「给人看的计划」到「共享工作队列」

3.1 注册的命令、五个工具与一条待办的数据结构

3.2 待办存在哪：每会话一个 JSON 文件

        String key = requireSafeFileName(sessionId);
        if (runId == null || runId.trim().isEmpty()) {
            throw new JellyfishException("认领待办需要一个 run 标识，当前没有");
        }

                // 未了结的那条优先：已经领了还在做，就不该再领第二条
                return TodoActionResult.ok(item);
            }
        }

                List<TodoItem> updated = new ArrayList<TodoItem>(items);
                TodoItem claimed = item.with(TodoStatus.IN_PROGRESS, runId, null);
                updated.set(i, claimed);
                persist(key, updated);
                return TodoActionResult.ok(claimed);
            }
        }
        return TodoActionResult.failed(TodoActionResult.Code.NONE_PENDING);
    }

不变量是「同一 run 至多一条未了结的认领」：手上还有没做完的那条就直接返回它， 而不是再领一条。做完之后可以接着领下一条——complete 会把状态改成已完成， 于是下一次调用不再命中「未了结」那一支，worker 连着干活因此不需要任何额外机制。 认领不到不等待、不重试，立即返回 NONE_PENDING： 等待会让「这个 run 要跑多久」变得不可预测，而那是拉取式工作队列的形状，本项目明确不做 （TodoStore.java:103-118）。

坑点：父回合的一次「整表覆盖」会把子代理的认领抹掉

现象：模型用 todo_write 重写计划之后，正在干活的子代理突然收到 todo_done 的「不是你的」；或者一条卡住的活丢了原因，看起来像没人做。

根因：todo_write 的语义是整表覆盖，而模型看不到认领者、也可能懒得抄 卡住的原因，写回来的条目自然不带这些（TodoWriteTool.java:26-30）。

规避：仓库在写入前做一次「继承」——内容没变时把上一份里「模型看不见的那部分状态」 （认领者、卡住原因）黏过来，并且已被认领的条目不会被一次重写改回未开始 （TodoStore.java:327-363、TodoStore.java:365-377）。 但 PENDING 不继承认领者：带上旧 owner 的未开始条目谁也领不走、谁也完不成， 而且会被一次次继承下去，模型自己修不回来（TodoStore.java:340-356）。

3.5 为什么值得单独一个插件（而不是让模型自己在回复里列待办）

源码里能直接读到的三条理由，都指向「回复里的待办做不到的事」：

  • 它要能被别人认领：父回合写下计划、派出几个子代理， 「谁做哪一条」在此之前没有落点——每个子代理各自埋头做自己的 prompt，重复干活与漏活 只能靠父回合事后发现。认领把这件事变成一个原子动作：读的时候还没主的条目，写回来时 已经记上了我的 run 标识（TodoClaimTool.java:17-20）。
  • 它要有一个「做不了」的落点：没有 blocked，一条做不了的活只能一直停在 pending，于是一批一批的子代理反复把它领走、又反复失败 （TodoBlockTool.java:17-19）。
  • 它要对人可见、可持久：状态栏给进度、左栏面板给清单、/todo 给带编号的 只读清单；面板还会把认领者的 run 标识翻成子代理类型，并区分「还在跑」与「已结束但没标完成」—— 后者是唯一需要人管一眼的形态（TodoPanel.java:138-149）。

关于「谁在做」还有一层解耦值得点出：RunPresence 只订阅内核的 AgentRunProgressEvent，不认识任何编排插件，因此删掉 workflow 插件， 这里的代码与行为一个字都不变（RunPresence.java:13-17）。 它对丢失的通知做了自愈：超过 15 分钟没等到结束的条目不再算「正在做」， 而是回落成「不知道」（RunPresence.java:42）；写路径另有 4096 条容量上限， 超限先清已过期的，再按最旧淘汰（RunPresence.java:52、RunPresence.java:114-150）。

4.3 缓存与失效：判据是文件系统签名，不是时间

清单贡献每轮组装请求时都会被问一次，而扫描要列举目录、读每个 SKILL.md—— 把这些放进每轮路径，等于让对话的每一轮都付一次磁盘遍历的钱。因此必须有缓存； 而 /reload 只会重启「配置段变了」的插件，编辑一个 SKILL.md 并不改配置， 因此缓存又必须会自动失效，否则「我改了 skill 却不生效」只能靠重启进程解决 （SkillCatalog.java:14-18）。

4.4 相关的命令与 UI 贡献

skills 插件只有一个命令 /skills，它渲染一份台账：启用与否、每个根目录的状态 （不存在 / 不是目录 / 加载了几个）、已加载清单（名称、描述、正文体积、附带文件数）以及全部扫描期问题 （SkillsLedger.java:35-71）。 没有面板贡献，也没有任何状态条目——这三个插件里，它的状态足迹最小。 一个细节：根目录「不存在」要明确写出来，冷启动时项目级根目录通常还不存在， 而用户此刻正要判断「我该把 skill 放哪儿」（SkillsLedger.java:74-89、SkillsLedger.java:67-72）。

坑点：skill「改了没生效」/「模型看不见它」

现象：目录里明明放着 SKILL.md，模型却从不加载它；或者改过描述之后行为没变。

根因：三种成因全部发生在扫描期，且都不报错——① 缺 description （描述是模型选择 skill 的唯一依据，没有它这个 skill 永远不会被加载，扫描期直接跳过并记一条问题， SkillScanner.java:163-168）；② 名称被更靠前的根目录占用（同名先到者胜， 被压掉的那个记一条问题而不是静默丢弃，SkillScanner.java:21-23）；③ 子目录里没有 SKILL.md，或根目录本身不存在 / 不是目录（SkillScanner.java:81-86、 SkillScanner.java:97-100）。

规避：敲一次 /skills。问题与结果是一起打印的——只说「加载了 3 个」 而不说「有 2 个因为缺 description 被跳过」，用户会以为自己的目录里就那 3 个 （SkillsLedger.java:13-14）。另外启动期也会把每个问题打成 LOG.error（SkillsPlugin.java:77-79），但台账是唯一不必翻日志的入口。

坑点：64 条是「每个会话所有插件加起来」的上限

现象：某个插件报 会话的扩展条目已达上限（64 条），请先删旧条目， 而它自己明明只写了一条。

根因：计数是 session.getExtensionEntries().size()， 不按 owner 分组——所有插件在同一个会话里共用这 64 条。注意替换已有 key 不受计数限制 （只有 existing == null 时才查上限），因此 plan 那种「一个会话一个 key、反复覆写」的用法 永远碰不到这条线：它每会话只占一条，值又只是一个布尔。

规避：往条目里放「一份会增长的列表」之前先想清楚——那是待办插件宁愿自建文件的原因之一； 真要在条目里存大东西，只能自己管好条目数量与单条体积，且必须接受「插件卸载不删条目」 （Jellyfish/docs/constraints.md:361）：条目是用户的会话数据，不是插件的私有财产 （PluginContext.java:345-347）。

一句话记住三者的状态位置

plan 的状态借内核的容器（一条布尔，随会话走）；todo 的状态自己造文件 （有格式、有并发、有原子写，也有「会话删除时收尾」的义务）；skills 不留状态 （只有一份每轮校验签名的目录缓存）。选哪一种，取决于「这份东西的归属是不是一个会话」 以及「它会不会长大」。

关键结论

  1. 三个插件的共同立场是工具清单逐字节不变：一个都不注册 ToolActivation； plan 用权限拦截代替「换清单」，skills 把可用的 skill 名单放进提示词贡献而不是参数的 enum（SkillTool.java:25-27）。
  2. plan 的模式是会话扩展条目里的一个布尔（jellyfish-plugin-plan::enabled）， 内核不持有「模式」概念；读取沿父链、返回三态，权限侧按「开着」倒（fail-closed）、展示侧按「没开」倒 （PlanState.java:103-127、PlanPermission.java:51-69）。
  3. todo 的待办是每会话一个 JSON 文件（默认 ~/.jellyfish/todos/）， 进程重启与 /resume 之后还在；只有内核删除会话时由 SessionDeleteRequest 连带删掉（TodoStore.java:48、TodoPlugin.java:82-85）。
  4. 「规则进 STATIC、状态走回合上下文」是 todo 与 plan 共用的同一条纪律： 能在本轮 append 的就别动缓存前缀的第 0 个 token（PromptPlacement.java:12-22）。
  5. skills 的发现约定只有「子目录 / SKILL.md」，缺 description 直接跳过； 披露分三层：清单常驻（名称 + 描述）、正文按需（skill 工具）、附带文件交给已有的 read_file / shell（SkillScanner.java:145-172、SkillTool.java:141-163）。
  6. 会话扩展条目有硬上限（单条 64 KiB / 每会话 64 条 / key 256 字符，计数不按插件分组）， 超限抛异常且不写入；这也是「会增长的清单」不放进条目的原因 （SessionManager.java:503-529）。
