11 坑点与陷阱清单

37 条，全部有源码依据。每条给「现象 → 根因（文件:行号）→ 规避 → 严重度」。 建议先读一遍建立索引，出问题时按现象回来查。

学习目标

  • 建立一份「现象 → 根因」的速查索引，遇到问题能直接定位到源码；
  • 识别出哪些坑是反直觉的（例如 0 表示永不超时、没有通配符）；
  • 知道哪些坑必须重启进程才能解决，哪些可以用 /reload。
严重度说明
  • 高：会导致功能失效、安全问题、或进程卡死，且排查困难；
  • 中：会造成错误行为或误导，但有明确的现象可循；
  • 低：影响体验或效率，不影响正确性。

A. 配置类

A1. 未知字段静默忽略 中

现象models.json / agents.json 里键名拼错，没有任何界面提示，「配了不生效」
根因绑定层把 FAIL_ON_UNKNOWN_PROPERTIES 设为 false（ObjectMapperWrapper.java:43）， 靠 unknownFields()（:159）事后比对，再由 RuntimeConfig.read 发一条 ConfigWarningEvent（:415-419）
规避用 --verbose 或直接看 stderr（日志默认 WARN 且只写 stderr）；怀疑配置没生效时，第一件事就是把日志级别降下来

A2. ${VAR} 缺失 → 整份配置加载失败 中

现象进程起不来，报 environment variable is not set: XXX，退 3
根因SettingsBinder.resolve 对必需变量抛 JellyfishException（:29-31, 184-188），异常经 ConfigLoader.read 上抛——不是局部降级
规避一律写 ${VAR:-默认值}；需要字面量时用 \${VAR} 转义。注意：环境变量存在但为空串时不会用默认值（与 shell 语义一致）

A3. 采样参数被静默丢弃 / 与思考模式冲突 中

现象调了 temperature 没反应
根因三个独立原因：① 非法值被丢弃 + 告警（SamplingSettings.java:52）；② null = 不下发（LlmRequest.java:22，见 05 页）； ③ 思考模式下厂商侧会忽略采样参数且不报错（SamplingSettings 类注释）。 另外 model 级无法单独关掉 provider 级已配项（merge 是覆盖不是删除）
规避在 model 级配全；确认该模型当前是否开着思考模式；要控制采样参数就别在 provider 级配

A4. Claude 代际差异导致 400 中

现象设了 temperature / top_p / top_k 就被 400 拒；或用了 thinking 就被拒
根因Claude 4.7+ 不再接受这三个参数（ClaudeLlmClient.java:180）； thinking.budget_tokens 必须小于本次 max_tokens，未配时取 4096（:62）
规避按模型分开配 sampling；用 thinking 时显式给 maxOutputTokens 并确保它大于 thinking 预算

A5. 项目级配置默认不加载 高

现象./.jellyfish/*.json 写了完全不生效，只有一行 WARN
根因信任单位是「文件绝对路径 + SHA-256 内容指纹」（ProjectConfigTrust.java:46）， 未信任即 UNTRUSTED → 跳过 + 告警（RuntimeConfig.java:264-270）； 内容一变即失效；classpath: 路径不受管辖（:118-122）
规避本次生效：--trust-project-config（不落盘）；持久：TUI 确认框里选「记住」

A6. 项目级段「整对象覆盖」与「只认全局级」的键 中

现象项目级只改了别的段，全局级的 ask.timeoutSeconds = 0 却回退成了缺省的 120
根因0.1.1 修过的真实 bug：旧合并层写成 project != null ? project : global，语义上看着对但永远走左支。 现在按「段声明标记」（isXxxDeclared()）判断，判据不是「段非空」（RuntimeConfig.java:510-524）。 另一类：「收紧安全边界的键」只认全局级（JellyfishPluginDescriptor.java:93）
规避升级到 0.1.1+；用「段非空」推断「段被声明」是错的，理解这一点能省很多排查时间

A7. /reload 失败不回滚 低

现象reload 报错之后，内存状态与磁盘文件不一致，「改回去了但行为还是新的」
根因重载是单向的，失败原样上抛（ConfigReloader.java:48）
规避改配置前备份；出现不一致时重启进程最快

A8. 某些配置在 refresh() 之前就被读了 中

现象subAgent 的并发 / 墙钟预算配了，实际仍按缺省跑
根因RunScheduler 在 RuntimeConfig.refresh() 之前就被构造，读到的是缺省值（CHANGELOG Unreleased / 0.1.1 Fixed）
规避升级版本；这类「装配期读到的配置」改完必须重启，不要指望 /reload

B. 插件类

B1. 新增 / 删除插件 jar 必须重启进程 高

现象把 jar 放进 ~/.jellyfish/plugins，/reload 之后插件没起来
根因PF4JPluginManager.java:118-121 明确「不做 jar 热部署」； /reload 只处理「已加载插件读新配置」与「启用/禁用名单变化」
规避换 jar 之后重启进程；只改配置段才用 /reload。config.json 也不参与热更新

B2. 插件自带 jellyfish-api / pf4j → 类加载冲突 高

现象莫名的 ClassCastException、「PluginContext 有两份」，或者插件静默不启动
根因PF4J 插件类加载器默认子优先（PDA）（PluginClasspathGuard.java:16-21），插件自带这些类会破坏类型同一性。 护栏只拦两个前缀且只记 loadError 不抛异常（:29-32, 47-60）
规避插件 pom 把这两个依赖改成 provided；排查时降日志级别搜 PluginClasspathGuard

B3. 插件 stop() 之后 fail-closed 中

现象插件停掉之后还看到「注册失败」的异常；插件拦截抛错时工具被拒
根因stop() 之后任何注册 / 发布当场抛（ContextLifecycle.java:34-43、PluginContextImpl.java:364-369）； PermissionVerdict 三态无 ALLOW，抛错或 null 一律 DENY（PermissionManager.java:205-216）
规避有注册线程的插件必须在 stop() 里先停那个线程；拦截想「放行」要显式返回 abstain()

B4. "enabled": [] 与「未声明」不是一回事 中

现象写了 plugins.enabled 结果所有插件都不启动；或 /reload 之后手动禁用失效了
根因空数组 = 一个都不启用（用 enabledDeclared 区分「未声明」，PluginsSettings.java:71-73）； /reload 会清空运行期开关（ConfigPluginStatusProvider.java:63, 72-73）
规避想「不限制」就整段删掉该键；别在手动启停之后立刻 /reload

B5. plugin.class 缺失时的报错极具误导性 低

现象插件加载报出一个跟 org.pf4j.Plugin 有关的莫名错误
根因描述符校验只在 plugin.class 存在且非空时才做（JellyfishPluginDescriptorFinder.java:40-51）， 缺失时回退成 PF4J 的默认值。另外 plugin.id 含 :: 会被直接拒绝（:71-97）
规避写全 plugin.properties 里的 plugin.class 与 plugin.id

C. 并发类

C1. 审批 / 提问阻塞 react 池（8 条线程） 高

现象审批配了 0（永不超时）后界面卡死；攒够 8 个等待中的回合，新回合全部排队
根因react 池固定 8 条（ReActLooper.java:85, 913-925）； 审批 / 提问的等待发生在 react 线程上且是同步的（ApprovalChannel.java:304-330、AskChannel.java:30-33）； 0 = 永不超时（AskSettings.isInfinite、PermissionManager.java:248），且不会自愈
规避不要写 0；及时裁决；审批 fail-closed 所以拒绝也比挂住好

C2. 子代理 run 不得进 react 池 中

现象如果把嵌套回合排回 react 池，父子 run 互等，偶发卡死
根因结构性解法：run 跑在独立的 agent-run 池（RunScheduler.java:105-139）， 嵌套用 runNested 内联执行（ReActLooper.java:341-346）， 且等待中的 run 让出许可（AgentRuntime.java:113-125）
规避改委派逻辑时保持这三条；不要「顺手」把嵌套提交到 react 池

C3. 在途回合登记必须带槽位 中

现象Esc 取消静默失效——按键收到了，但没取消掉
根因修过的 bug：曾有不传槽位的登记路径，导致取消时找不到对应的在途回合。 现在 TurnRegistry.bind 只提供 bind(Slot, ReActTurn)， 让「无槽位」在编译期就不可表达（TurnRegistry.java:136, 265）
规避别为了图方便加一个「无槽位」重载

C4. TUI 里 submit 之后 await() 中

现象Esc 失联、审批弹框画不出来、状态栏不再更新
根因界面线程阻塞在等回合上，tamboui 的事件循环停了（TuiApp.java:96-98 明确禁止）
规避回合进行中拒绝新输入（SubmissionPolicy），而不是阻塞等待

D. 上下文类

D1. @ 引用不内联文件内容 低

现象以为 @file 会把文件内容塞进 prompt
根因@ 只把路径写进消息，真正读取由模型调用 read_file 完成—— 好处是权限判定与 max_bytes 限制照旧生效（InputReferenceCompletion、docs/constraints.md:815）。 含空格的路径要写 @my\ file.txt（InputReferenceEscapes）
规避这就是设计意图，不是 bug；指望「大文件被自动读进来」会失望

D2. 工具输出落盘阈值与目录 中

现象长输出被替换成一行 stub；~/.jellyfish/tool-outputs 占空间；换项目后找不到上次的输出
根因react.maxToolOutputChars = 20000；目录在主目录而非项目目录； keepFiles = 200、maxBytes = 50 MiB、spillMaxBytes = 32 MiB、keepRecentMessages = 20 （ToolOutputSettings.java:36-56）。对无界输出（yes）仍会被读取并丢弃—— 落盘上限保护的是磁盘，不是 CPU（SpillCapturingSink.java:196-206）
规避配 react.toolOutput.*；0 是关闭该项（但会丢掉所有溢出输出）；注意 _partial = true 时文件本身也不完整

D3. 截断封顶与 JSON 中

现象对工具输出做 substring 封顶后，模型拿到的 JSON 解析失败
根因docs/constraints.md:734-739 明确禁止对可能是 JSON 的输出做 substring； Server 侧还必须按「待发条数」封顶实时输出
规避用结构化的信封（ToolOutputEnvelope）而不是字符串截断

D4. 四层「上限」口径不同 中

现象「屏幕上没看到」和「上下文里还有」同时为真，排查时互相矛盾
根因① 消息区 500 条 = 屏幕（TranscriptProjector.java:135）； ② 裁剪 ContextWindow = 本次请求； ③ 老化 ToolResultAger = 本轮 tool 结果发全文还是 stub； ④ 压缩 = 后续请求的起始边界。四者都不删历史
规避判断依据永远看 usage 与日志，不要看屏幕

D5. 孤儿 tool / 悬空 toolCalls 会被 400 中

现象一次请求失败之后，之后每一次请求都失败
根因裁剪 / 取消破坏了 assistant(toolCalls) 与 tool 的配对，厂商直接 400（ToolPairing.java:30-40）。 补救点是 startIndexOf 跳孤儿（PromptAssembler.java:914）与 appendNotRunResults（ReActLooper.java:688-712）
规避改裁剪 / 取消逻辑时，第一件要确认的事就是配对没被破坏

D6. 回合内只标脏，关停必须 flushAll() 高

现象Ctrl+C 之后当前回合的内容丢了
根因beginTurn 只标脏（SessionManager.java:996-1009）， flush 才落盘（:1011-1036）。 硬约束：flushAll() 必须早于 pluginManager.close() （AgentHarness.java:251-254, 274, 284）——落盘经扩展点派发给插件，插件一停就没人接了
规避别动收尾顺序；记住依赖关系「停写者 → 兜底落盘 → 关插件」而不是抄序号清单

D7. restore() 早于插件 bootstrap → 静默恢复 0 个会话 中

现象装了持久化插件、会话文件也在，但历史会话列表是空的
根因恢复靠 SessionRestoreRequest 扩展点，插件不启动就没人应答（SessionManager.java:825-830）
规避凡是走扩展点的能力，都必须在插件启动之后才可用

E. TUI 类

E1. 发送键是 Ctrl+S 而不是 Enter 低

现象按 Enter 只换行，消息发不出去，以为程序卡了
根因实测多数终端不解码修饰键，无法实现「Enter 发送 / Shift+Enter 换行」， 于是反转键位（InputKeyMapper.java:9-14）
规避记住 Ctrl+S；这是终端协议限制逼出来的设计，不是任意选择

E2. End 归消息区、\r\n 变两个换行 低

现象编辑器里没有「光标到行尾」；粘贴 CRLF 文本出现额外空行
根因InputKeyMapper 把 END 映射为 TO_BOTTOM（跳到最新消息）； 裸 \r/\n 落成换行（ChatInputView.java:402）。 CRLF 那条在 README:252 有记载，但未在 TUI 源码中定位到显式的归一化逻辑——属「文档记载」而非「源码坐实」
规避粘贴前先在别处把换行统一成 \n

E3. 消息区只投影 500 条 低

现象更早的消息在屏幕上被折叠成一行提示
根因DEFAULT_MAX_MESSAGES = 500（TranscriptProjector.java:135）， 因为「每帧投影是 O(总行数)，必须有界」（09 页）
规避纯展示裁剪，消息一条没删——不代表上下文里没有

E4. 粘贴有上限且超限整段不插入 低

现象粘一大段日志悄悄没进去，只看到一条提示
根因MAX_PASTE_CHARS = 1 MiB（按码点），判插入后总长，超限一字不入（ChatInputView.java:93）
规避改用 @ 引用文件路径，让模型自己读

E5. 消息区必须是单个 richText 中

现象给消息区加子元素（想实现逐条交互），界面卡到不能用
根因布局与按键路由按元素树做，子元素数到 120–180 就是性能断崖（docs/constraints.md）
规避保持单元素 + 预计算视觉行；需要逐条交互就要换渲染方案

E6. TUI 日志必须与终端隔离，且配置要早于第一个 Logger 低

现象日志混进界面把备用屏撕坏；或者「明明配了 log4j2-tui.xml 却不生效」
根因TUI 用备用屏 + raw 模式；Log4j2 的配置在第一次取 Logger 时固化， 晚了切配置无效（JellyfishApplication.java:57, 110, 144-148）
规避别改启动流程里「先扫参数 → 初始化日志 → 正式解析」的顺序；单文件 10 MB × 5 档，可用 -Djellyfish.log.maxSize/maxFiles 调

F. 性能类

F1. prompt cache 命中率与 keepAliveSeconds 的隐性成本 中

现象配了保活，命中率没改善，账单却更高了
根因CacheKeepAlive 的空闲重发是真实计费调用，每空闲期最多 3 次，缺省关闭 （CacheKeepAlive.java:55, 92-151, 188-208）； Anthropic 不标 cache_control 命中率恒为 0（ClaudeLlmClient.java:28）； 保活与 thinking.budget_tokens 互斥；部分模型对输出有最小值要求
规避缺省别开；命中率由 SessionUsageSnapshot 的 cacheReadTokens / promptTokens 现算（分母是总输入），别自己算

F2. system prompt 每轮变化 → 全历史按未命中价重发 高

现象账单突然高很多，但没改任何配置
根因system prompt 是缓存前缀的第一段。PromptAssembler.java:44-47 把「把易变状态塞进 system prompt」 直接视为 bug 信号。会随轮次变的内容必须走 TurnContextRequest（:660 起）
规避插件贡献内容用 PromptPlacement 分档：STATIC 在前、VOLATILE 在后

G. 安全类

F3. 思考 token 花了钱但不进 /usage 中

现象开了思考 / 推理模式后，/usage 的输出明显低于厂商账单，差额说不清
根因LlmUsage 只有五个字段（promptTokens / completionTokens / totalTokens / cacheReadTokens / cacheWriteTokens， LlmUsage.java:38-50），没有 reasoning 字段； 三家的 usage 解析里也都没有读思考数量—— OpenAI / DeepSeek 不读 completion_tokens_details.reasoning_tokens（:357-371）、 Claude 不单独统计思考（:634-635）、Gemini 不读 thoughtsTokenCount（:498-499）
规避这是当前的记账边界，不是配置问题。要精确分摊思考成本只能去厂商后台看明细。详见 05 页 §10.3

F4. Claude 的输入是三项之和 中

现象自己按 /usage 的字段算缓存命中率，结果大于 100%
根因Anthropic 把输入拆成三项（普通输入 / cache_read_input_tokens / cache_creation_input_tokens）， 三者互斥。命中率的分母必须是三者之和； 只拿其中一项当分母就会算出超过 100% 的结果（ClaudeLlmClient.java:634-635）
规避直接用 SessionUsage.getCacheHitRate()（:209-211），不要自己拆字段算

G1. -server 缺省不鉴权 高

现象缺省配置安全（只绑 127.0.0.1）；一旦 --host 0.0.0.0， 任何能访问端口的人都能读全部会话正文、执行命令、批准审批
根因鉴权只在配置了密钥时挂载（JellyfishServer.java:169-176）
规避配 JELLYFISH_SERVER_API_KEY（不要用 --api-key，会出现在 ps 里）； 绑非回环 + 无密钥时内核拒绝启动退 3（:248-258）

G2. 落盘权限与符号链接 中

现象旧版本默认 0644，同机其他用户可读会话正文
根因已修：restrictToOwner 收到 600 / 700，且写临时文件用 NOFOLLOW_LINKS 挡符号链接越权写 （SessionStore.java:172-192，CHANGELOG Fixed / SEC-12）
规避升级；自己实现持久化插件时照抄这两条

G3. 终端注入必须收口 高

现象工具输出里的 ESC 序列能清屏、改标题、甚至伪造一行看起来像内核日志的内容
根因转义字符若直写终端就会被解释。收口在 StyledSegment 的构造器； -cli 侧收口在 SystemConsoleIO 的三个写出方法； 日志是第四条出口，用 log4j2 的 %replace 过滤（docs/constraints.md、CHANGELOG SEC-10/17）
规避不要绕过 StyledSegment 直接往终端写字符串；新增输出出口时要同步加过滤

关键结论

  1. 这 37 条里有很大一部分不是「bug」，而是设计选择的副作用。理解设计意图之后，它们就从「坑」变成了「必须记住的语义」。
  2. 最危险的一类是「静默」：未知字段、类加载冲突、缓存签名不含 vendor 配置、agentId 拼错全拦—— 这些都不会报错，只会安静地按别的逻辑运行。排查任何「配了不生效」的问题，第一步都是把日志级别降下来。
  3. 最需要警惕的一类是「反直觉的 0 / 空」：timeout: 0、allowedTools: []、 enabled: []、agingPercent: 0。它们的语义是设计者定的，不查源码只能猜。
  4. 「哪些改动必须重启进程」值得单独背下来：插件 jar 集合、扫描目录、config.json、装配期读到的配置。 其余（配置段、名单）可以 /reload。
