04 Agent Loop 内核 重点

整个项目的主干道。ReActLooper 925 行，其中 loop() 不到 100 行——但每一行都对应一个踩过的坑。

学习目标

  • 说清主循环的真实形状，以及「一轮」与「一个回合」的区别；
  • 背下 5 条退出条件，并理解「空回复为什么必须重试而不是直接收敛」；
  • 解释工具调用如何嵌入循环，以及为什么是严格串行、为什么先落 assistant 再执行；
  • 说清 ask_user 的阻塞实现、它跑在哪个线程上、为什么「永不超时」会挂死内核；
  • 指出子代理隔离的真实边界（不是「只读」，而是「委派不得提权」）；
  • 知道自动压缩挂在循环的哪一行。

1. 主循环的真实形状：带上限的 for

先纠正一个常见误解：它不是状态机，也不是 while(true)， 而是一个次数固定的 for 循环。轮数是「模型调用次数」， 不是「工具批次次数」——一次模型调用返回 3 个工具调用，仍然只消耗 1 轮。

设计依据：为什么不用 while(true) + 超时？

因为「不收敛」这件事必须是可枚举、可解释的终态，而不是被掐断。 ReActResult 有四种终态：completed / truncated / cancelled / blocked（ReActResult.java:74, 102, 113, 131）。 调用方（外壳、脚本、监控）需要区分「答完了」和「跑不动了」——前者退 0，后者退 6。 如果用 while(true) + 外部超时，被掐断的那个回合只能得到一个模糊的失败， 而且卡死的那条线程还会一直占着 react 池（池子只有 8 条）。

替代方案：用「预算超时」而不是「轮数」。没选，因为在 LLM 场景下轮数比时间更可预测， 而且时间预算会让同一个 prompt 在不同网络条件下得到不同结果——不可复现的失败最难查。 （子代理那边额外有墙钟预算 runTimeoutMillis 与 token 预算，因为嵌套更贵。）

坑点：空回复在形状上和「答完了」一模一样

源码注释写得很清楚（ReActLooper.java:451-455）：「空回复（既没正文也没工具调用）在形状上与「答完了」一模一样， 因此它会被当成一次正常收敛，而用户什么也看不到。」

更关键的是它的位置——这段判定必须排在 appendMessage 之前。因为 「一条空的 assistant 消息对界面与模型都没有信息量，落进会话反而会跟着之后的每一次请求发出去」。 这类「落进历史就变成永久污染」的检查，在 08 页会反复出现。

还有一个细节：重试那一次账照记（sessionManager.recordUsage，:457）， 注释说「这一次调用真的花了钱，只是结果没用」。计费口径与压缩的摘要调用一致。

逐行要点

行 / 片段为什么是这样
turn.isCancelled() 在轮首 取消是协作式的：不做抢占式中断，只在「下一个安全的检查点」响应。轮首是最安全的点——没有半成品状态。
autoCompactIfNeeded 排在组装之后、调用之前 注释解释了时序：压缩与这一轮的模型调用并发。请求已经组装好了，压缩不会拖慢这一轮； 压缩结果在下一轮组装时才生效。如果把压缩放在组装之前，用户每轮都要等一次摘要调用。
response == null → cancel 同步/流式两侧约定：取消时返回 null 而不是抛异常。异常在这个位置会穿透整个循环， 而取消是预期路径不是故障。
appendMessage(assistantMessage(...)) 在工具执行之前 这是 08 页会讲的「会话是界面看到的真源」。 先落 assistant(toolCalls)，再执行工具、再落 tool 结果—— 中途崩溃时历史里至少留有「模型想调什么」，而不是一段无法解释的空白。
预算触达时 appendNotRunResults 补结果 注释点出真正的动机：悬空的 assistant(toolCalls) 会让厂商以 400 拒掉之后的每一次请求。 也就是说，不补这一个「合成结果」，整个会话就废了。这在 Claude / OpenAI 的 tool 配对校验下都是硬约束（ToolPairing.java:30-40）。
if (toolCalls.isEmpty()) 里的 drainConvergence 这是「STEER」机制：插件可以在收敛前插一条消息让本回合多跑一轮， 而不是开一个新回合（continue 不 return）。所以「回合」的边界由内核控制，插件不能自己开回合。
工具循环用下标而非 for-each 注释直说了：取消时要能说出「哪些工具调用还没执行」，才能给它们补结果。for-each 拿不到下标。
outcome.getMetadata() 随结果落会话 注释：「成功与否不落会话，只有元数据才能在重投影 / -resume 之后仍显示标记」。 界面后的重投影只有拿到字段才能渲染警告标记。
末尾的 drainTurnBoundary 注释解释了位置：「放这里而不是轮首，是因为「刚跑完一批工具」正是插件最可能知道「还有一步没做」的时刻」。
设计依据：多工具调用为什么是严格串行？

ReActLooper.java:501 是一个朴素的下标循环，无线程池、无并行分支。 这不是偷懒，有三个现实约束：

  • 审批是逐个发生的。并行执行意味着同时弹出多个审批浮层，或者把审批也并行化—— 而审批通道每会话只有一个头槽位（ApprovalChannel，见 06 页）。
  • 工具之间有隐含顺序。同一批里的「写文件」和「跑测试」如果并行，测试可能读到旧内容。 模型给出的顺序本身就是有意义的信号。
  • react 池只有 8 条线程。在循环内部再开并行，等于把「并发度控制」这件事从一处变成两处， 而并发度一旦失控，审批阻塞会把池子占满（见第 4 节）。

想要并行扇出怎么办？去编排层——多个 task 先 spawn 再 await （SubAgentLauncher.java:164-170）。粒度从「工具」提到「子代理」，每个子代理跑在自己的 agent-run 线程上。这是刻意的分层：并行是编排能力，不是工具执行能力。

3. ask_user：阻塞式提问的实现

先给结论：它的阻塞是 CountDownLatch，跑在 react 线程上，会阻塞 agent loop。

    if (!attached) {
        return AskAnswer.unavailable(NO_ASKER);

一个必须分清的区别：ask 是 fail-open，审批是 fail-closed

AskChannel（ask_user 工具）ApprovalChannel（权限审批）

坑点：0 不是「立即返回」，是「永不超时」

ask.timeoutSeconds = 0 与 permission.approvalTimeoutSeconds = 0 都表示 永久等待（AskSettings.isInfinite()、ApprovalChannel.waitForever）。 由于等待发生在 react 线程上，而 react 池固定 8 条， 所以配了 0 之后只要用户不回答，那条线程就永久占着——攒够 8 个这样的回合，整个内核的智能入口就废了。

更麻烦的是「永不超时」这条路径不会自愈（AskChannel.java:44-49 专门说明了这点）。 想放宽等待时间就写一个很大的秒数（上限受 ProviderCacheSettings 之外的各自校验约束），不要写 0。

顺带一提：嵌套子代理里执行工具时，线程是 agent-run 池的 worker，而不是 react 池。 所以「ask_user 一定阻塞 react 线程」这句话只对顶层回合成立。

嵌套回合里提问会当场被拒，而不是静默等待

上面讲的是顶层回合。子代理里的情况完全不同，而这一点很容易被误解成「子代理也能问用户」：

Jellyfish/docs/constraints.md:503-504（原文）
它的提问不会出现在任何一个界面上；判据是 `ToolCallRequest.getRunId() != null`，
工具直接返回「子代理回合里无法向用户提问」，**绝不进通道等待**（那只会静默卡到超时）。
设计依据：为什么是「当场拒绝」而不是「排队等父回合处理」？

因为子代理的提问没有界面能显示它。子代理跑在 agent-run 池上， 它产生的待提问项不属于任何一个会话的头槽位——外壳每帧读的是 「当前会话有没有待审批/待提问」，读不到子代理的。

如果让它进通道等待，结果会是：模型发起提问 → 通道里排着 → 没人能看到 → 一直等到超时。 用户看到的现象是「子代理卡住了」，而且没有任何提示告诉他为什么。

当场返回一句「子代理回合里无法向用户提问」至少让模型知道此路不通，它会改用别的方式（比如把问题写进结果里 让父代理去问）。这与 06 页那条 「插件故障收敛成一条有理由的拒绝」是同一种做法：把「做不到」变成一条可见、可理解的失败， 而不是一个静默的等待。

坑点：别把这条当成「子代理不能提问」的功能缺失

它是刻意的契约。设计子代理流程时应当假设子代理无法与用户交互： 需要澄清的信息必须在 prompt 里给全，或者由父代理先问清楚再委派。 这也解释了 task 工具的 schema 为什么把 prompt 设为必填—— 它是子代理唯一的输入来源，没有补充提问的机会。

让出许可 父 run 在 await 子代理时主动让出许可，避免父子互等 — AgentRuntime.await（AgentRuntime.java:98-115）
设计依据：「让出许可」为什么是必须的

许可只有 3 个。maxDepth = 1 时，一次 task 会产生 1 个父 run + N 个子 run。 如果父 run 在等待子 run 时继续占着许可，那么当 3 个父 run 都在等子 run 时， 就没有许可可以给子 run 了——经典的线程池死锁，而且现象是「偶尔卡住」， 排查成本极高。让出许可是这个死锁的结构性解法，不是优化。

「嵌套回合不提交 react 池、而是内联执行」也是同一个原因的另一面： react 池只有 8 条线程，任何一个「在池里等池里」的写法都可能占满它。

TurnRegistry：在途回合表

  • 每个会话一个 Semaphore 占位（TurnRegistry.java:62, 109）→ 挡住同一会话的第二个并发提交 （ConversationService.java:199-206），这就是 TurnInProgressException 的来源。
  • bind 把句柄挂到槽位上（:136）；releasing 把「终态回调」与「归还槽位」绑在一起（:265）， 避免回调里抛异常导致槽位永远不还。
  • 取消入口 cancel(sessionId)（:206）——就是 TUI 里按 Esc 走到的地方。
坑点：登记必须带槽位

TurnRegistry.bind 只提供 bind(Slot, ReActTurn) 这一个重载， 没有「无槽位」版本。这是修过的 bug：曾经有个路径不传槽位，结果 Esc 静默失效 （取消时找不到对应的在途回合）。API 上不提供「无槽位」这个选项，是让这类错误编译期就不可表达。

TUI 侧还有一条配套约束：submit 之后不得调 await() （TuiApp.java:96-98），否则界面线程会阻塞在等回合上，Esc 再也收不到。 回合进行中要拒绝新输入——这是 SubmissionPolicy 的职责。

7. 本页坑点小结

循环相关的坑
  • 「主循环是状态机」不成立：就是带上限的 for。「轮次」= 模型调用次数，不是工具批次。
  • 工具是严格串行的：一批 3 个 tool_calls 逐个跑完才进下一轮。
  • ask.timeoutSeconds = 0 / permission.approvalTimeoutSeconds = 0 → 永不超时， 挂死 react 线程且不自愈。池子只有 8 条。
  • ask 是 fail-open，审批是 fail-closed：把 ask_user 的「无人应答」写成「拒绝」是错的。
  • 嵌套回合不在 react 池，而是 agent-run 池 + 内联执行： 「ask_user 一定阻塞 react 线程」只对顶层成立。
  • 删掉 appendNotRunResults 这类补结果逻辑会让悬空的 assistant(toolCalls) 被厂商 400 拒掉，而且之后每一次请求都失败。取消、超预算、异常，三条路径都要补。
  • 在 TUI 里 submit 后 await() → Esc 失联。
  • 子代理额度/深度是按「树」算的：maxSpawnsPerTurn = 12 是每次委派整棵树的总和， 不是每个子代理各 12 个。

关键结论

  1. 主循环的全部复杂度不在「循环」本身，而在它的四个边界：取消、空回复、无工具收敛、轮数用尽。 每一个边界都必须给出可区分的终态，因为外壳要把它们映射成不同的退出码。
  2. 「一轮 = 一次模型调用」这个定义看似细节，实际决定了很多行为：压缩为什么能与本轮并发、为什么工具串行但仍算 1 轮。
  3. ask_user 的阻塞是设计上的自觉选择（工具同步执行 + 阻塞在 react 线程）， 不是实现偷懒。它的代价明确写在了源码注释里，并且给了 0 这个危险的开关。
  4. 子代理的隔离边界是「不得提权」而不是「只读」；只读能力由插件自己声明工具清单来实现（如 plan 插件的 readOnlyTools）。
  5. react 池 8 条 + 审批/提问就地阻塞，是这个架构最需要警惕的组合；所有「在池里等池里」的写法都被结构性排除了 （委派用独立池、等待时让出许可、嵌套内联执行）。
