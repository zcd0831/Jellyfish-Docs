17 官方插件总览

内核只留机制、能力全在插件——那到底有哪些插件、各干什么、怎么组合？这一页给出一份与源码逐条对齐的清单， 以及一套「拿到任意一个 jar 就能认出它」的方法。

学习目标

  • 说清 13 个官方插件各自把什么动作变成能力，并能按职责把它们分成基础能力 / 上层编排 / 跨语言桥三类；
  • 拿到一张「插件 → 职责 → 提供什么扩展点 → 后续页号」对照表，据此按需跳读 18–23 页；
  • 从 plugin.properties 的几个键认出任意一个插件的身份，并知道漏写 plugin.class 会看到什么错误；
  • 解释「13 个插件之间零声明依赖」这一事实的含义，以及 plugin.requires=* 为什么不是版本门控；
  • 知道 plugins.roots 的来源与顺序语义，说清启用 / 禁用名单的判定链；
  • 说清 cpPlugins.sh 做了什么，以及为什么新增 / 删除 jar 必须重启进程；
  • 理解「内核一个能力都不内置」的取舍与代价。

1. 13 个插件：它们分别把什么变成能力

先给结论：仓库里 14 个 Maven 子模块，其中 13 个产出一个 PF4J 插件 jar； 多出来的那个是 jellyfish-script——它是 Python / Node 两条桥接路径共用的 机制层库，不产出到插件目录，由两个桥接插件以 shade 的方式打进各自的插件包 （Jellyfish-Plugins/AGENTS.md:16、Jellyfish-Plugins/AGENTS.md:65）。

顺带把两个易混的事实说清。第一，13 个插件的 plugin.id 都等于模块名， plugin.version 都是 0.1.2、plugin.provider 都是 zcd。 第二，描述符里有一个 jellyfish.tags 键（例如 tools 写 files,tools、 workflow 写 workflow,orchestration,subagent）， 但它是给人看的分类标签，不参与加载判定。

标签不是权限，也不是分类依据

官方描述符里写着「标签仅作诊断与展示；agent 授权只按工具名，不按标签」 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/resources/plugin.properties:14）。 本页第三节的三层划分是本页为了讲清职责人为归纳的，源码里没有与之对应的字段—— 真正的分类依据只有「它注册了哪些扩展点、用到了哪些出向端口」。

2. 从一个 jar 认出插件身份

判断「一个 jar 是不是 Jellyfish 插件」，不需要读它的类，只需要看 jar 根目录里有没有 plugin.properties，以及它的 plugin.class 指向谁。以 tools 为例，完整描述符只有 15 行：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/resources/plugin.properties:1-15（一个插件描述符的最小完整形态）
# Jellyfish 官方工具插件（PF4J 描述符，必须位于插件 jar 根目录）
#
# plugin.id 同时是注册表的 owner：插件卸载时按它批量回收工具注册。
plugin.id=jellyfish-plugin-tools
plugin.class=zcd.jellyfish.plugin.tools.ToolsPlugin
plugin.version=0.1.2
plugin.provider=zcd
plugin.description=文件读取 / 写入 / 编辑、目录列举与文本搜索

# 内核兼容约束刻意写 *：内核未向 PF4J 声明系统版本，缺省值 "0.0.0" 会让这条校验直接放行，
# 因此写 * 是显式声明「不限版本」，而不是一个真在生效的版本门控。
plugin.requires=*

# 标签仅作诊断与展示；agent 授权只按工具名，不按标签。
jellyfish.tags=files,tools

逐个键看它们的实际作用：

键13 个插件里的取值作用
plugin.id 与模块名同名 插件身份，同时是注册表的 owner 根：卸载 / 停止时按它批量回收该插件的全部注册。含 :: 会被加载期直接拒绝（那是「插件内子单元」保留的分隔符）
plugin.class 各插件的 XxxPlugin 类 PF4J 要实例化的入口类，必须实现 JellyfishPlugin，且有一个公开无参构造器（Jellyfish-Plugins/README.md:890）
plugin.version 0.1.2 插件自身版本；缺失时被补成兜底版本，不让下游依赖解析拿到 null
plugin.provider zcd 作者 / 组织，仅展示
plugin.description 一句话职责 展示用；诊断输出（如插件清单）的文案来源
plugin.requires 13 个全是 * 内核兼容约束。它不是真在生效的版本门控：内核未向 PF4J 声明系统版本，缺省值 0.0.0 会让这条校验直接放行，因此写 * 只是「显式声明不限」
jellyfish.tags 逗号分隔的分类词 本项目的私有扩展键，只在描述符解析时读入，作诊断与展示

这些键不是「PF4J 原生读取后就不再管」的：内核在 PF4J 的属性描述符之上加了一层解析器， 把三件事提前到解析期处理——plugin.class 是否为空、 plugin.id 是否带保留分隔符、plugin.requires 是否是合法 semver 约束：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginDescriptorFinder.java:40-48（描述符加固的入口）
    protected PluginDescriptor createPluginDescriptor(Properties properties) {
        JellyfishPluginDescriptor descriptor = (JellyfishPluginDescriptor) super.createPluginDescriptor(properties);
        if (StringUtils.isBlank(properties.getProperty(PluginProperties.PLUGIN_CLASS))) {
            descriptor.addLoadError("缺少必需的 " + PluginProperties.PLUGIN_CLASS);
        }
        descriptor.addTags(properties.getProperty(PluginProperties.JELLYFISH_TAGS));
        rejectNamespaceSeparator(descriptor);
        normalizeVersion(descriptor, properties.getProperty(PluginProperties.PLUGIN_VERSION));
        normalizeRequires(descriptor, properties.getProperty(PluginProperties.PLUGIN_REQUIRES));
        return descriptor;
    }

注意第一处判定用的是 isBlank，而不是「值非空」。这不是洁癖： PF4J 的 DefaultPluginDescriptor 里 pluginClass 的默认值是 org.pf4j.Plugin，父类只在属性非空时才覆盖它。若按「值非空」判定，漏写这个键会被放过去， 最后报出的是「org.pf4j.Plugin 未实现 JellyfishPlugin」—— 一个指错方向的错误。这条加固的理由写在类注释里 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginDescriptorFinder.java:17-21）。

坑点：漏写 plugin.class 报的是别人的名字

现象：插件加载报出一个跟 org.pf4j.Plugin 有关、完全看不懂的错误。
根因：DefaultPluginDescriptor.pluginClass 的默认值就是 org.pf4j.Plugin，属性缺失时它保持不变，于是 PF4J 拿这个默认类去检查是否实现了 JellyfishPlugin，失败的当然是默认类而不是你的类。
规避：描述符里 plugin.class 与 plugin.id 都写全； 另外别在 plugin.id 里用 ::——保留分隔符会让回收范围误伤其它插件的注册， 因此解析期就拦下 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginDescriptorFinder.java:71-84）。 25 页把这条列为 B5。

还有一道与身份相关的检查不在 createPluginDescriptor 里：插件包里不得出现 zcd.jellyfish.api 的类。它需要看 jar 内容，只有拿到路径才能做，因此挂在 find(Path) 上 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginDescriptorFinder.java:54-57）。 原因是类加载隔离——插件自带一份 jellyfish-api 会遮蔽父加载器里的同名类， 于是插件拿到的值类型与内核对不上，表现为「新字段静默丢失」。

3. 依赖与协作：三层能力，零声明依赖

一个反直觉但很关键的事实：13 个描述符里没有任何一个声明了插件间依赖。 plugin.requires 全是 *（那是与内核的兼容约束），13 个文件里也没有出现过 PF4J 的 plugin.dependencies 键。插件之间怎么协作？答案是不通过依赖， 而通过内核注册表里的名字与类型。

先看职责分层（这是本页的归纳，用于讲清谁依赖谁的能力）：

上层编排为什么不需要新扩展点

workflow 是「上层编排」的典型：它自己不起线程池，只把一个 workflow 工具挂到 ToolCallRequest 上，然后向内核要一条出向端口来派生子代理。

Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:43-57
    public void start(PluginContext context) {
        SubAgentPort port = context.delegations();
        // 面板与台账共用同一个时钟：耗时文案（「已跑」「已 38s」）必须和记账时刻同源，
        // 否则注入时钟的单测会在面板上算出「跑了 50 年」这种数字
        LongSupplier clock = System::currentTimeMillis;
        // 先装配台账与引擎再注册：处理器一旦注册就可能被调用，依赖必须已经就绪
        WorkflowTracker tracker = new WorkflowTracker(invalidator(context), clock);
        WorkflowEngine engine = new WorkflowEngine(port, tracker);
        context.handle(ToolCallRequest.class, WorkflowTool.NAME, WorkflowTool.descriptor(),
                new WorkflowTool(engine));
        context.contribute(PromptContributionRequest.class, new WorkflowGuidance());
        context.contribute(PanelContributionRequest.class, new WorkflowPanel(tracker, clock));
        LOG.info("编排插件已启动: tool={}", WorkflowTool.NAME);
    }

这段代码说明三件事。①「编排」没有引入任何内核新概念：一个工具 + 一个提示词贡献 + 一个面板贡献就够。 ②子代理来自 context.delegations()，与内核的 task 工具走同一条代码路径， 因此准入、深度、扇出、并发、预算、取消与归档的行为完全一致——插件不自己起线程池、不自己实现并发上限 （Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:24-26）。 ③委派是「端口」而不是扩展点：方向的本质是「插件请求内核做一件事」， 而扩展点是「内核回头找插件」，两者不能互换 （Jellyfish/docs/constraints.md:203-205）。

跨语言桥：唯一一处插件之间的编译期依赖

python 与 node 是「跨语言桥」。它们与其它 11 个插件的区别在于： 它们的共同机制（探测解释器 → 扫描脚本清单 → 逐脚本注册 → 接通事件桥接与熔断 → 注册语言级命令 → 按序关闭）不写在插件里，而写在一个库里：

Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptBridgePlugin.java:30-33（机制层存在的理由）、Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptBridgePlugin.java:95、Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptBridgePlugin.java:106（子类只需实现这两个抽象方法）

这正是「跨语言桥」与其它插件的结构性差异：jellyfish-script 是普通 Java 库， 被 python / node 以 shade 打进各自的插件包 （Jellyfish-Plugins/jellyfish-plugin-python/pom.xml:89-93、 Jellyfish-Plugins/jellyfish-plugin-node/pom.xml:90-94）。因此桥接插件是 13 个插件里 唯一把第三方依赖（Jackson、commons-exec）与自家机制层一起塞进 jar 的—— shell 塞 commons-exec、mcp 塞 Jackson，也是同一手法：把依赖收拢在需要它的那个插件里。 这条路径与「13 个插件之间零依赖」不矛盾：被 shade 进去的是库，不是另一个插件。

注意：插件仓库是独立 reactor，api 永远要 provided

插件仓库与内核没有编译期依赖，只经 jellyfish-api 的 SPI 交互 （Jellyfish-Plugins/AGENTS.md:13）。jellyfish-api 只作协作者： provided，且 shade 的 includes 里绝不能出现它——插件 jar 里不含 api 的类， 插件拿到的值类型才永远是运行期内核那一份 （Jellyfish-Plugins/jellyfish-script/pom.xml:19-21 是这条规矩的注释现场）。

4. 加载与扫描顺序、启用与禁用名单

「去哪找插件」与「加载之后怎么用」在本项目里是两个不同的配置位置，这一点从 config.json （应用级、单文件定位）与 jellyfish.json（插件段）的分工就能看出：

Jellyfish/jellyfish-cli/src/main/resources/config.json:15-17（出厂配置里的扫描目录）
  "plugins": {
    "roots": ["~/.jellyfish/plugins/"]
  }

roots 的列表顺序就是扫描顺序——字段注释写得很直白 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/PluginPaths.java:29-30）。 未配置时回退到默认目录 plugins（相对进程工作目录）：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/PluginRuntimeConfig.java:37（默认扫描目录）、Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/PluginRuntimeConfig.java:295-297（回退逻辑）
    public static final String DEFAULT_PLUGINS_ROOT = "plugins";

                    roots == null || roots.isEmpty()
                            ? Collections.singletonList(Paths.get(DEFAULT_PLUGINS_ROOT))
                            : Collections.unmodifiableList(new ArrayList<>(roots)),

因为没有一个插件声明对另一个插件的依赖，扫描顺序不影响加载成败——它只决定 PF4J 发现插件的先后。真正会「跳过某个插件」的是启用 / 禁用名单，判定链在 ConfigPluginStatusProvider 里，顺序是「运行期开关 → 禁用名单 → 启用白名单」：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/ConfigPluginStatusProvider.java:77-91（插件是否被禁用的完整判定）
    public boolean isPluginDisabled(String pluginId) {
        if (runtimeEnabled.contains(pluginId)) {
            return false;
        }
        if (runtimeDisabled.contains(pluginId)) {
            return true;
        }
        // 只读一次快照：判定过程中配置被重载也不会出现「启用名单读的是新的、禁用名单读的是旧的」
        Configured current = configured;
        if (current.disabled.contains(pluginId)) {
            return true;
        }
        // 声明了启用名单就是一个白名单（空名单 → 全部禁用）；未声明才是不额外限定
        return current.enabledDeclared && !current.enabled.contains(pluginId);
    }

最后一行是整套语义的关键：「启用名单未声明」与「声明为空数组」必须能区分。 未声明表示不额外限定（全部启用）；声明为空表示一个都不启用。为此反序列化时保留一个「是否声明」的标记， 而不是把两者一起归一成空列表：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/PluginsSettings.java:107-111（保留「是否声明」）
        this.enabled = copyOf(enabled);
        this.disabled = copyOf(disabled);
        this.enabledDeclared = enabled != null;
        this.disabledDeclared = disabled != null;
        this.configurations = copyOfConfigurations(configurations);
坑点："enabled": [] 会把全部插件关掉

现象：写了 plugins.enabled，结果所有插件都不启动；或者 /reload 之后手动启停的状态全部失效。
根因：空数组 = 一个都不启用 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/PluginsSettings.java:109 用「是否 null」区分声明与未声明）；而配置重载会清空运行期开关—— attach(...) 里 runtimeEnabled.clear() 与 runtimeDisabled.clear() 就在重建快照之后 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/ConfigPluginStatusProvider.java:69-73）。 设计意图是「重载的语义就是回到配置说的样子」，代价是它不认运行期的手动开关。
规避：想「不限制」就整段删掉该键，别写空数组；也别在手动启停之后立刻 /reload。 25 页把这条列为 B4。

扫描目录只认「下一层」

扫描目录缺省是 ~/.jellyfish/plugins/，PF4J 在这个目录的下一层找 plugin.properties（Jellyfish/README.md:468）。 因此把 jar 直接放进该目录即可，不必再套一层目录。

5. 插件被使用的两种方式

「装好插件」只是第一步。插件注册进去之后，会被以两种完全不同的方式消费，混起来看就会觉得架构很绕。

方式一：内核按扩展点消费（内核是调用方）

插件把 handler 注册到某个类型 + 路由键上，内核在自己的流程里按需查找并调用。 内核并不知道「是谁注册的」，它只认类型和名字：

内核消费点代码位置消费的是什么
权限判定 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:392 PermissionCheckRequest 的所有贡献者一起决定这次工具调用怎么走
工具分发 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:399 用工具名做路由键找出 ToolCallRequest 的 handler
命令注册 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:226 把插件注册的 CommandRequest handler 收进命令表

这就是「13 个插件彼此不认识、却都能被内核用起来」的原因：类型即地址， 注册表按「类型 + 路由键」找 handler（Jellyfish/docs/constraints.md:205）。 插件拿不到的类型，它想注册也注册不了。

方式二：插件通过注册表里的名字互相约束（插件之间间接协作）

插件之间没有依赖，但会「踩到彼此的注册」。两个真实例子：

例一：plan 的白名单写的是别家插件的工具名。plan 插件自己不注册任何工具， 它的 readOnlyTools 由用户声明，里面的名字必须与 tools / shell 等插件注册的工具名逐字一致，判定就是一次集合包含：

Jellyfish-Plugins/jellyfish-plugin-plan/src/main/java/zcd/jellyfish/plugin/plan/PlanConfig.java:103（白名单判定）
        return toolName != null && readOnlyTools.contains(toolName);

也就是说，plan 与 tools 的耦合点是「工具名」这个字符串， 而不是任何代码依赖。名字由谁提供？tools 注册的 read_file（Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:59）、 shell 注册的 shell（Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellTool.java:41）。 白名单写错一个字的后果不是编译错误，而是 plan 模式下那个工具永远被拒。

例二：MCP 的工具名会和内置工具名撞车。mcp 把外部 server 的工具以 mcp__<server>__<tool> 注册进同一张表，于是「关掉前缀」这种配置会撞上 tools 注册的内置工具名。冲突的表现是注册失败被跳过，而不是整个插件启动失败：

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpToolRegistrar.java:101-113（每个 server 一个子上下文；撞名的工具跳过）
            PluginContext serverContext = context.subContext(server.id());
            long timeoutMillis = server.callTimeoutSeconds() * 1000L;
            for (McpToolDefinition tool : tools) {
                try {
                    created.add(serverContext.handle(ToolCallRequest.class, tool.qualifiedName(),
                            tool.descriptor(), new McpToolCaller(tool, invoker, timeoutMillis)));
                    registeredNames.add(tool.qualifiedName());
                } catch (RuntimeException e) {
                    // 名字被占了（关掉前缀时最容易撞上内置工具）：跳过它，让其余工具照常可用
                    LOG.warn("MCP 工具注册失败，已跳过: server={} tool={} reason={}", server.id(),
                            tool.qualifiedName(), e.getMessage());

注意 context.subContext(server.id())：注册落在 <pluginId>::<serverId> 这个命名空间下。这是「插件内子单元」的标准做法—— python / node 对每个脚本也这么干 （Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptBridgePlugin.java:260）， 好处是诊断输出能指出「这个工具是哪个 server / 哪个脚本提供的」，卸载时又能按命名空间一次性收干净。

设计依据：为什么覆盖是一条链，而不是就地替换

同名注册撞车时，登记不是「新覆盖旧」，而是新登记压在旧登记之上，旧登记仍在表里、只是不生效。 这样做是为了让解除链顶就是一次回退：插件停止时按 owner 回收它的全部登记（含被压住的层）， 被它顶掉的内核工具 / 命令自动重新生效。若就地替换并丢弃旧登记，插件一走， 被顶掉的那个能力就永久消失了（Jellyfish/docs/constraints.md:265-268）。 同理，回收按 owner 判定、与是否生效无关，否则被压住的层会在覆盖者离开后悄悄复活。

根因：重载方法只处理「同在的插件读新配置」与「名单变化」，注释里写得很明白—— 不做 jar 热部署：扫描目录与插件集合在启动期就定了（config.json 不参与热更新）， 新增 / 删除插件 jar 属另一条路径 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/PF4JPluginManager.java:120-121）。 根由是 plugins.roots 属于部署事实、写在 config.json 里， 与 jellyfish.json 那条配置热更新路径不是同一份。
规避：换了 jar 就重启进程。jellyfish.json 里改启用 / 禁用名单与逐插件配置段， 才走 /reload。02 页与 16 页都提过这条界线；插件机制本身（生命周期、扩展点、类加载隔离）在 16 页， 本页只负责「有哪些插件、怎么装」。

插件自己的资源跟着插件走

8. 设计依据：内核为什么不内置任何一个能力

最容易被误解的一点是「为什么连读文件、会话落盘、压缩摘要都要做成插件」。 13 个插件的类注释里，三处给了同一个理由的不同侧面：

  • 能力与内核生命周期无关：「插件侧只能注册回调，工具的实现与内核生命周期无关； 放在插件里还顺带获得两样东西——逐插件配置段，以及热部署能力」 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolsPlugin.java:22-28）。
  • 「压成什么样」是决定，不是机制：内核手里只有机制（读消息、选范围、发模型调用、校验摘要、 推进边界、记用量、落盘）；把摘要策略放进插件有三个直接好处：摘要措辞可以自己改、保留条数可以按团队习惯调、 不想用时直接不启用插件——压缩整体缺席，而不是有个半成品在内核里空转 （Jellyfish-Plugins/jellyfish-plugin-compact/src/main/java/zcd/jellyfish/plugin/compact/CompactPlugin.java:12-19）。
  • 表达形式会演化：编排「spec 长什么样、怎么聚合」会随用法变化， 放进内核意味着每次调整都要动内核的发布节奏；内核只需要提供稳定的原语。 插件缺席时 task 薄工具照旧可用，这正是「卸载即回退」 （Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:29-33）。
设计依据：宁可「没有」，也不要「内核里有个半成品」

这条选择的核心不是「解耦」这类空话，而是把缺席定义成一种受支持的形态： 不装 compact，会话压缩（含自动压缩）整体不可用，命令会直接告诉用户这一条 （Jellyfish-Plugins/jellyfish-plugin-compact/src/main/resources/plugin.properties:4-6）； 不装 tools，模型就没有任何文件工具。代价是真实的：能力变成可选项、部署多一步、 能力之间可能对不上（plan 的白名单写在别家插件的工具名上）。换来的是内核足够小， 以及每个能力的故障范围被限制在它自己的插件里——例如持久化插件拿不到 SessionManager， 它的故障范围就被限制在「存」与「取」两件事上 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionFilePlugin.java:21-24）。

这些取舍的边界在插件仓库的约定里被写成硬规矩，读任何一页插件详解时都会用到： 注册窗口是插件的整个存活期，但 stop() 之后一切注册 / 发布当场失败 （fail-closed，Jellyfish-Plugins/AGENTS.md:87）； 插件停止时必须终止在途子进程，否则用户看到的是「jellyfish 都退出了，那条命令还在跑」 （Jellyfish-Plugins/AGENTS.md:94）。这两条是本页清单里所有插件共同的行为约束。

关键结论

  1. Jellyfish-Plugins 的 14 个 Maven 子模块里，13 个产出插件 jar， jellyfish-script 是给 python / node 用的机制层库，不装进插件目录。
  2. 插件的身份由 plugin.properties 决定：plugin.id 是身份兼注册表 owner， plugin.class 是入口类；plugin.requires=* 不是版本门控， jellyfish.tags 也不是权限依据。
  3. 13 个插件之间零声明依赖：协作全靠「扩展点类型 + 路由键」这套名字空间， 因此注册点在哪里，比插件之间的依赖关系重要得多。
  4. 加载与扫描是启动期行为：plugins.roots 的顺序即扫描顺序， 启用 / 禁用名单的判定链是「运行期开关 → 禁用名单 → 启用白名单」， 且 "enabled": [] 表示「一个都不启用」。
  5. 插件有两种被使用方式：内核在自己的流程里按扩展点消费（工具、命令、权限、持久化）， 插件之间则通过注册表里的名字间接互相约束（plan 的白名单、MCP 与前缀撞名）。
  6. 「内核不内置任何能力」不是口号：它把缺席做成了受支持形态（不装即没有）， 代价是能力可选、部署要重启进程，收益是内核足够小、每个插件的故障范围被限制在它自己的注册面内。
