10 会话持久化与上下文管理

这一页有两半：前半是「状态怎么留住」（会话），后半是「状态怎么送出去」（上下文工程）。 两半通过一条纪律连起来：会话是唯一真源，送出去的东西只是它的一个投影。

学习目标

  • 说清 SessionManager 的「唯一变更入口」与两个落盘例外；
  • 描述会话文件的原子写过程，以及它对符号链接做了什么防护；
  • 解释工具输出落盘的阈值、信封格式，以及模型如何按路径回读；
  • 背下 PromptAssembler 的组装顺序，并说出裁剪「只裁本次请求」的理由；
  • 说清压缩的触发条件、算法主流程，以及「压缩是插件能力」的后果；
  • 理解消息区 500 条投影为什么只是展示裁剪、不影响发给模型的内容；
  • 说清会话分叉的切点为什么要按工具调用组对齐，以及为什么它不复制用量；
  • 读懂token 记账的三个 plus 重载差别，与命中率的分母是什么；
  • 知道工具输出的 _path 有隐含有效期（落盘会被静默清理）。

类注释（SessionManager.java:57-60）把这条规则写成了硬约束： 任何对会话状态的改动都必须经过 SessionManager。 因为它是「变更通知」的唯一发起者——变更之后要把 SessionPersistRequest 派发给插件。 绕过它改会话，插件就收不到通知，落盘也就不会发生。

两个刻意的例外

例外行为为什么位置
创建不落盘 create() 只建内存对象，不触发落盘 避免「用户打开界面又立刻退出」留下一条空会话文件。TUI / Server 启动期不建会话（03 页） 与这条是同一个考虑的两面 :196-206（注释 :200-204）
回合内只标脏 beginTurn 只打脏标记，直到 flush 才真正落盘 一个回合里可能追加几十条消息（工具结果），每条都写一次文件既慢又没必要—— 崩溃时最多丢当前回合，而当前回合本来就没完成 beginTurn :996-1009、flush :1011-1036、markDirtyOrPersist :606-611

会话落盘本身是插件能力（jellyfish-plugin-session-file 提供）。 内核这边只有一个派发点：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:1302-1319
private void doPersist(Session session) {
    if (session.isEphemeral()) {
        return;
    }
    List<HandlerBinding<SessionPersistRequest, Void>> bindings =
            extensions.bindings(SessionPersistRequest.class, null);
    if (bindings.isEmpty()) {
        return;
    }
    session.underPersistLock(() -> {
        SessionPersistRequest request = new SessionPersistRequest(session.captureSnapshot());
        for (HandlerBinding<SessionPersistRequest, Void> binding : bindings) {
            extensions.invoke(binding.getHandler(), request);
        }
    });
}

这段很短但有四个信息点：

  • isEphemeral() 提前退出——子代理会话不落盘（:1300-1306， 也解释了它们为何不进 all()）。
  • bindings.isEmpty() 直接返回——没装持久化插件就什么都不发生， 而且照常清掉脏标记（:1268-1271）。这不会报错，只会「会话退出即消失」。
  • captureSnapshot() 生成的是 api 侧的快照值类型 （SessionSnapshot），与 05 页的传输快照同一个思路： 插件只能读，不能改内存里的会话。
  • underPersistLock 把「拿快照 + 派发」包在一把锁里， 保证落盘时看到的是一个自洽的瞬间，而不是「消息写了一半」的中间态。

插件侧怎么真的写文件

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:172-192（原子写）
private void writeAtomically(Path file, String json) throws IOException {
    Path temp = file.resolveSibling(file.getFileName() + TEMP_SUFFIX);
    try {
        Files.write(temp, json.getBytes(StandardCharsets.UTF_8),
                StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING,
                LinkOption.NOFOLLOW_LINKS);
        restrictToOwner(temp, false);
        try {
            Files.move(temp, file, StandardCopyOption.REPLACE_EXISTING, StandardCopyOption.ATOMIC_MOVE);
        } catch (AtomicMoveNotSupportedException e) {
            Files.move(temp, file, StandardCopyOption.REPLACE_EXISTING);
        }
    } catch (IOException | RuntimeException e) {
        deleteQuietly(temp);
        throw e;
    }
}
步骤作用
写 <id>.json.tmp临时文件后缀固定；写出错时原文件不受影响
NOFOLLOW_LINKS挡符号链接越权写——防止 .tmp 被提前做成指向别处的符号链接
restrictToOwner(temp, false)rename 之前收紧到 600——不能让「已经可读」的文件存在哪怕一瞬间
ATOMIC_MOVE，不支持时退化普通替换同一文件系统上是原子的；跨设备时退化为「先删后移」，此时仍不会出现半截文件
异常时 deleteQuietly(temp)不留残渣；下一个会话列举只认 *.json，.tmp 不算会话
坑点：flush、flushAll、flushQuietly 语义不同

关停时必须 flushAll()，而且它必须排在 pluginManager.close() 之前 （AgentHarness.java:251-254, 274, 284）——因为落盘要经扩展点派发给插件，插件一停就没人接了。 少了这一步，Ctrl+C 会丢掉当前回合。

另外 flushQuietly 失败会保留脏标记并只打 WARN， 而 persist 失败是上抛。两条语义不同：前者是「尽力而为」（关停路径）， 后者是「必须成功」（显式请求）。混用会导致「明明失败了却以为成功了」。

2. 数据结构：什么是不可变的，什么不是

类型可变性关键字段并发
Session 混合：final 的 sessionId / createdAt / kind / parentSessionId / forkPointMessageId， 其余（title / updatedAt / agentId / provider / model / usage / compaction / extensionEntries）可变 List<SessionMessage> messages 全部方法 synchronized；读返回防御性不可变列表（:323-324）
SessionMessage 完全不可变（final 字段 + 无 setter） messageId / timestamp / role / content / toolCallId / name / toolCalls / usage / thinking / metadata 天然线程安全（SessionMessage.java:24-70）
ChatState（TUI） 不存消息，只存投影结果 projected 与上次投影指纹 （lastSessionId / lastMessageCount / lastWidth…） — 界面状态只归渲染线程（ChatState.java:27-28）
设计依据：ChatState 为什么不存消息？

因为「消息的真源只有一个」比「界面读得快」更重要。 如果 TUI 自己存一份消息列表，那么每次压缩、恢复会话、插件追加消息，都要同步两份数据—— 而任何一次漏同步都会造成「屏幕上有、历史里没有」这类无法自愈的不一致。

现在的做法是：ChatState 只保存上一帧的投影结果和一个指纹 （会话 id + 消息条数 + 终端宽度…）。指纹没变就复用上一帧，变了才重新投影。 这是一个纯粹的缓存，丢掉它不影响正确性——这正是「可重建的派生状态」该有的样子。

而回合进行中的「活跃状态」（流式文本、正在跑的工具）由另一个对象 InflightTurn 承载： react 线程写、渲染线程经 snapshot() 读（InflightTurn.java:27-28, 345）， 有硬上限（正文 256K / 思考 64K / 工具输出末 20 行 × 200 字符，:58-67）—— 因为流式内容可能在短时间内无界增长，这个上限是防内存失控的闸。

3. 工具输出落盘与「回灌信封」

一个工具可能返回几兆输出（grep 全仓、cat 大文件）。全塞进上下文会瞬间打爆 token 预算， 所以内核有一条「超限就落盘 + 回灌一个信封」的机制。

配置键缺省值含义
react.maxToolOutputChars20000 字符单次工具输出超过它就触发落盘
react.toolOutput.dir~/.jellyfish/tool-outputs落盘目录（注意是主目录，不是项目目录）
react.toolOutput.keepFiles200保留文件数
react.toolOutput.maxBytes52428800（50 MiB）目录总上限
react.toolOutput.spillMaxBytes33554432（32 MiB）单次溢写上限；实际取 min(spillMaxBytes, maxBytes)
react.toolOutput.keepRecentMessages20与老化策略配合（见第 6 节）

回灌给模型的是一段合法 JSON（ToolOutputEnvelope.java:259-269）：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/tooloutput/ToolOutputEnvelope.java:259-269
public String render() {
    Map<String, Object> payload = new LinkedHashMap<String, Object>();
    payload.put(FIELD_TRUNCATED, Boolean.TRUE);
    payload.put(FIELD_TOOL, toolName);
    payload.put(FIELD_TOTAL_CHARS, totalChars);
    payload.put(FIELD_TOTAL_LINES, totalLines);
    payload.put(FIELD_PATH, path);
    payload.put(FIELD_HINT, hint);
    payload.put(FIELD_PARTIAL, Boolean.valueOf(partial));
    payload.put(FIELD_PREVIEW, preview);
    return ObjectMapperWrapper.writeValueAsString(payload);
}

字段清单是 _truncated / _tool / _total_chars / _total_lines / _path / _hint / _partial / preview （:29-57）。三个设计要点：

  • 始终是一段合法 JSON（:12-20）——不是「一行人类可读的提示」。 这样模型可以直接解析它，而且不会因为里面的引号/换行把上下文结构搞坏。
  • _hint 里明写怎么回读：用 read_file（支持 offset/limit） 或 grep_files 查 _path（:143, 367）。 也就是说回读能力也由插件提供，内核只负责把路径写清楚。
  • _partial = true 表示该文件本身也不完整（:41-56）—— 触及溢写上限时停止写入。模型看到这个标志就该知道「连文件里都不是全部」， 而不是以为回读能拿到完整输出。
坑点：_path 是 ~ 缩写形式，落盘目录在主目录

工具输出默认落在 ~/.jellyfish/tool-outputs，不是当前项目目录。 所以「换个项目跑就找不到上次的输出」是正常的。 另外 _path 里给的是 ~ 缩写，交给需要绝对路径的工具时要先展开。

与截流有关的两个实现细节：SpillCapturingSink 在未溢出时全缓冲， 超过 maxChars 才转为溢写（只留头/尾窗口并边写盘，SpillCapturingSink.java:78-135, 196-206）。 而对「无界输出」的工具（典型是 yes），spill 仍然会被读取并丢弃—— 也就是说落盘上限保护的是磁盘，不是 CPU。

最后一个坑：不要对可能是 JSON 的输出做 substring 来封顶 （docs/constraints.md:735-740）。截断一段 JSON 会得到非法 JSON， 而很多工具的输出恰好就是 JSON。

注意 firstSessionIndex 那一行的用途：它是「发给模型的第 0 条历史，对应会话里的第几条」—— 这个反向映射在日志、UI 高亮、错误定位里都要用。裁剪之所以要记录这个索引， 就是为了「内核知道自己裁了什么」。

提示词贡献：三档，且只有「追加」

PromptPlacement含义
STATIC不随会话/轮次变化的内容
SESSION会话级信息（缺省档）
VOLATILE每轮都可能变的内容

分档的意义是缓存：STATIC 放在前面、VOLATILE 放在后面， 缓存前缀才不会被每轮变化的内容冲掉（PromptPlacement.java:18-39）。 三档都是追加，没有「替换」语义（PromptContribution.java:4 的类注释： 道内按注册的 order 排序；单个 handler 失败只记 WARN 跳过（:652）。

坑点：system prompt 必须逐字节恒定

PromptAssembler.java:44-47 把「把易变状态塞进 system prompt」直接视为 bug 信号： 因为 system prompt 是缓存前缀的第一段，一旦它每轮变化， 整个历史都会按未命中价重发。

第二条相关的坑：摘要不能用 system 角色（:508-520）。 一是会被 Claude / Gemini 上提回顶层 system（破坏 system 的唯一性）， 二是 Anthropic 拒绝连续的 user 消息——所以摘要被强制成 user，并在必要时并入首条 user。 这些不是风格选择，是协议约束。

第三条：内核不注入环境信息。除了 agent 提示词原文与插件贡献，没有第三段。 想要「当前目录是 X、今天是 Y」这类信息，得由插件通过 PromptContribution 或 TurnContextRequest 提供。

5. 裁剪：ContextWindow 的成组丢弃

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ContextWindow.java:59-79
for (int i = groups.size() - 1; i >= 0; i--) {
    List<LlmMessage> group = groups.get(i);
    int cost = TokenEstimator.estimateMessages(group);
    if (kept.isEmpty()) {
        if (cost > historyBudgetTokens) {
            kept.addAll(truncateGroup(group, historyBudgetTokens));
            used = TokenEstimator.estimateMessages(kept);
        } else {
            kept.addAll(group);
            used = cost;
        }
    } else if (used + cost <= historyBudgetTokens) {
        kept.addAll(0, group);
        used += cost;
    } else {
        truncated = true;
        break;
    }
}
规则说明
分组group()：把 tool 结果挂到它前面那条消息上（:88）， 保证 assistant(toolCalls) 与 tool 结果要么都在、要么都不在
方向从最新组向最旧组累加，装不下就整组丢
最新一组永远保留；单独就超预算时，组内截断正文、tool 结果换成带落盘路径的 stub（:107-160）
预算contextLength - maxOutputTokens - contextReserveTokens（缺省保留 1024）； 模型没有配窗口时返回 NO_CONTEXT_WINDOW（PromptAssembler.java:805）， 原样下发不裁剪（:822-823）
Token 估算不是「字符数 / 4」：CJK（汉字 / 平假名 / 片假名 / 谚文）按 1 token， 其余按 0.25，按 1/4 单位向上取整；每条消息 +4，每个 toolCall +2（TokenEstimator.java:14-24, 60-90）
超限不重试靠「裁剪 + 老化」解决，不做厂商侧重试
设计依据：为什么「只裁本次请求、历史一条不动」？

ContextWindow.java:14-16 给出了答案：裁剪是可逆的展示优化，会话一条不动。

反过来推演一下如果写回会发生什么：裁剪依据是这一次的模型配置（窗口大小、输出上限）。 如果你换了模型、或者把 maxOutputTokens 调小了，那么上一次裁剪掉的内容就永久丢了—— /resume 之后历史里没有，屏幕上也没有，你甚至不知道曾经有过。 而「不写回」的代价只是每次组装时多算一遍（有 ToolResultAger 与投影缓存兜着）。

压缩（compaction）也是同一个立场：/compact 非破坏式， 屏幕、落盘、/resume 之后的历史仍然是全文——它只推进 boundaryMessageId， 不删任何消息（配合 SessionCompaction.java:9 与 PromptAssembler 的 toLlmMessages 一起看）。 压缩只是「在组装时换一个起点」——boundary 往前走一格，历史一条不删。

坑点：孤儿 tool 与悬空 toolCalls 会被 400 拒掉

ToolPairing.java:30-40 专门处理这件事。裁剪与取消都可能破坏配对： 丢了 assistant(toolCalls) 却留下 tool 结果（孤儿）， 或者反过来（悬空）。而 OpenAI / Claude 都会直接 400 拒绝这种请求。

所以组装时有两处补丁：startIndexOf 跳过开头的孤儿 tool 结果（:914）， 以及 04 页里那个「取消/超预算时必须补 appendNotRunResults」。 改裁剪逻辑时，第一件要确认的事就是配对没被破坏。

摘要方式滚动摘要（旧摘要并入新摘要）；超预算时从最旧丢弃，并如实上报 droppedMessageCount
摘要长度compactMaxSummaryChars，缺省 4000
设计依据：「cache-safe fork」这个优化很值钱

压缩本身要发一次 LLM 调用（生成摘要）。如果这次调用的请求内容与正常请求完全不同， 那它就无法命中 prompt cache，要按全价重新读一遍全部历史——而历史通常有几万 token。 压缩因此可能比被压缩的那次对话还贵。

「复用父请求的字节前缀 + tool_choice: none」的做法，让摘要调用与正常调用共享同一个可缓存前缀， 于是只按缓存命中价读历史。这是一个把「缓存是前缀匹配」这条协议特性用到极致的优化， 也是判断一个 agent 实现是否成熟的分界线之一。

压缩是插件能力，而且不回退内置

没装压缩插件时行为

工具结果老化：ToolResultAger

  • 它只把「超限落盘过的信封」换成 stub，非信封的消息一个不动（ToolResultAger.java:30-40）。 也就是说：没被截断过的工具输出永远不会被老化。
  • 两种口径由 react.cache.agingPercent（缺省 70）选： 0 = 按尾部条数保留最近 keepRecentMessages（缺省 20）； > 0 = 按用量水位，且一个压缩周期内只推进一次（:123-124）。
  • AgingStrategy 扩展点可改 keepRecentMessages / agingPercent / stubText / stubTextsByTool 与占位符 （{tool}{chars}{lines}{firstLine}{recovery}），边界算法不出内核。
坑点：agingPercent = 0 不是「关闭老化」

0 是切换口径——回到「按尾部条数保留最近 N 条」的旧口径。 真正的「关闭老化」是 toolOutput.keepRecentMessages = 0（AgingStrategy.java:57, 63, 65）。 这两个键名字相近、语义相反，是最容易配错的一对。

缓存保活

provider.cache.keepAliveSeconds（缺省 0，关闭；上限 3600）控制 CacheKeepAlive：构造期起单线程调度，每 30 秒 tick() 一次， 到点发一个「复用父前缀 + 最小输出」的请求把 cache TTL 续上，每空闲期最多 3 次。 详细机制与成本分析见 05 页第 5 节。

配套的 CacheBreakWatcher（485 行）逐轮比对三层指纹： system prompt 散列 / 工具清单散列 / 逐条消息散列（问题清单在 :27，比对实现在 Report.between:351； 快照字段 systemPromptHash:168 / toolsHash:174）。 断裂时只 WARN 一次（持续期降为 DEBUG），并逐轮发 CachePrefixChangedEvent。 指纹存 32 位散列、LRU 64 条。 注意：命中率不在这里统计——由 SessionUsageSnapshot 的累计 cacheReadTokens / promptTokens 现算（SessionUsageSnapshot.java:9-12）。

问题答案
为什么是 500远大于典型会话的条数，因此几乎不会真的折叠； 同时给出了一个绝对上界，免去了实现虚拟滚动（可变行高 + 换行计算，复杂度高一个量级）

这三层「上限」经常被混淆——它们的口径完全不同，排查问题时要分清：

  • 消息区 500 条：只影响你看得到什么（TUI 投影）。
  • 裁剪（ContextWindow）：影响这一次发给模型什么，不写回会话。
  • 老化（ToolResultAger）：影响这一轮 tool 结果发全文还是 stub，同样不写回。
  • 压缩（ConversationCompactor）：影响后续所有请求从哪条开始，通过推进 boundary 实现，同样不删历史。

所以「我明明看到它在上下文里」和「它其实已经被裁掉了」可以同时为真。判断依据永远是 usage（token 使用率）与日志里的裁剪/老化记录，而不是屏幕。

设计依据：切点为什么必须按工具组对齐？

因为孤儿 tool 结果会被厂商 400 拒掉（第 4 节已讲过 ToolPairing）。 如果用户点在某条工具结果上分叉，而切点就落在那条结果上，新会话的历史会以一段「没有对应 assistant(toolCalls) 的 tool 结果」开头——那个会话开出来就是废的， 而且症状会在第一次提问时才出现，看起来像是新会话的 bug。

把「用户点哪」翻译成「安全切点」的责任放在 resolveCutIndex 里， 意味着调用方不需要理解工具配对规则。注释也点明了这个分工： 「『往哪边对齐』在 resolveCutIndex 上」（:405）。

设计依据：为什么 fork 不复制用量？

机械地看，「复制历史」似乎也该「复制成本」。但用量是计费口径而不是内容： 源会话里那些 token 已经花过了，新会话并没有为此再付一次钱。 如果复制，/usage 会出现两个会话报同一笔账，而账单只来一次——对账时无法解释。

所以方法名直接叫 copyMessagesWithoutUsage： 把「不复制用量」写进方法名，而不是靠注释提醒。 这跟 05 页「没写 vs 写了 0」用类型状态表达是同一类做法—— 让关键约束体现在名字/类型上，而不是文档里。

坑点：分母是「总输入」而不是「非缓存输入」

10.2 快照映射：为什么必须持锁

SessionSnapshots（197 行）负责「内核 Session → api 侧 SessionSnapshot」的映射， 反向是 toMessage / toSessionUsage / toCompaction（:88-131）。

  • capture(Session) 是包级可见（:62），唯一入口是 Session.captureSnapshot()，而那个方法是 public synchronized。 注释说明了原因（:48-58）：两次 getter 之间没有绑定， 不在同一把锁里读，就可能读到「消息是旧的、用量是新的」这种现实中不存在的组合。
  • Session.betweenSnapshotReads（SessionSnapshots.java:74，定义在 Session.java:387） 是测试接缝：插在「消息读完、用量未读」之间，专门用来复现上面那个竞态。
  • toUsage（:186-193）对五个可空字段用 orZero（:201-203）按 0 计—— 因为快照类型是给插件用的，让插件去处理 null 没有意义。
设计依据：为什么留一个「测试接缝」在正式代码里？

并发 bug 的麻烦在于无法稳定复现。留一个可注入的钩子（这里就是那个 Runnable 字段），测试就能把线程精确停在危险点上，把「偶尔出错」变成「每次必错」。

代价是多了一个生产代码里的字段。判断值不值，看它换来的是什么： 一个可重复的竞态测试比十次「我本地跑不出来」有价值。 这个仓库里还有同类做法（UiCache 的版本号、InflightTurn 的快照）， 可以当成一种可复用的模式。

10.3 压缩在会话里怎么存

SessionCompaction（105 行）只有四个字段（:28-37）： summary / boundaryMessageId / createdAt / droppedMessageCount。 summary 与 boundaryMessageId 都不可空白（:48-58）。

两条不变量写在类注释里（:9）：「会话里始终只有一块摘要、边界只能向后移（滚动摘要）」。 这就是第 6 节说的「压缩 = 把 boundary 往前推一格」在数据结构上的体现—— 不是往列表里追加摘要，而是替换那一块、并把边界指针往后推。 也因此「边界只能向后」不是约定而是结构事实：只有一个字段存边界，它只会被更大的值覆盖。

12. 本页坑点小结

会话与上下文的坑
  • fork 的 messageId 落在工具结果上会被自动向后对齐—— 你以为的切点与实际切点不一定是同一条。对齐是必须的（否则新会话开头就是孤儿 tool 结果，直接被 400）。
  • fork 不复制用量：新会话的 /usage 从零开始，这不是漏记也不是 bug。
  • plusTokens 不计调用次数，而 plus(LlmUsage) 计。 用错会让「调用次数」与「实际请求数」不一致（缓存保活就是前者的例子）。
  • 命中率的分母是「总输入」（含缓存命中与建缓存），不是「非缓存输入」； 且它是累计现算，不是逐次平均。
  • 工具输出的 _path 会被静默清理：超过 keepFiles = 200 或 maxBytes = 50 MiB 就从最旧的开始删，成功删除不打日志。 长会话里回读旧路径可能扑空——所以信封里同时带 preview。
  • 清理的 0 是「不清理」（ToolOutputStore.java:499, 120-121）， 不是「删光」。这一条与其他几个「0 语义反转」的坑同类（见 25 页速查表）。
  • create() 不落盘：空会话退出即消失，别指望文件存在。
  • 回合内只标脏：Ctrl+C 前必须走 flushAll()，且它要早于 pluginManager.close()。
  • flushQuietly 与 persist 失败语义不同（前者保脏标记只 WARN，后者上抛）。
  • 没装持久化插件时 persist 静默返回并照清脏标记——不报错，只是什么都没存。
  • 子代理会话不落盘、不进 all()，但仍在会话表里。
  • 工具输出落在主目录（~/.jellyfish/tool-outputs）而非项目目录；_path 是 ~ 缩写。
  • _partial = true 意味着文件本身也不完整，回读拿不到全部。
  • 别对可能是 JSON 的输出做 substring 封顶。
  • system prompt 必须逐字节恒定，否则整个历史按未命中价重发。
  • 摘要必须是 user 角色并合并连续 user（协议约束，不是风格）。
  • agingPercent = 0 ≠ 关闭老化；关闭要写 toolOutput.keepRecentMessages = 0。
  • 没有压缩插件时不是「回退内置策略」而是功能缺席，健康检查只降 WARN。
  • 四层上限口径不同：500 条是屏幕、裁剪/老化是本次请求、压缩是后续边界。都不删历史。
  • 孤儿 tool / 悬空 toolCalls 会被厂商 400；改裁剪逻辑先确认配对。

关键结论

  1. 整页最重要的纪律是：会话是唯一真源，其他一切都是投影或缓存。 ChatState、裁剪结果、老化 stub、压缩摘要，全部可以从会话重建。
  2. 「只裁本次请求、不写回」是一个反复出现的设计立场，它同时出现在裁剪、老化、压缩三处。 收益是任何配置变更都不会造成不可逆的信息丢失。
  3. 落盘的关键词是「宁可丢当前回合，不可留半截文件」：原子写 + 600 权限 + NOFOLLOW_LINKS + 回合内只标脏。
  4. 工具输出落盘信封是「用一个结构化 JSON 换取上下文空间」的典型做法，而 _hint 里写明回读方式是 让模型自己知道怎么取回细节——这套文档的 _path 提示与之同源。
  5. 压缩的「cache-safe fork」说明这一层已经不是「能跑就行」，而是开始按协议的计费特性做优化： 让摘要调用复用父请求的缓存前缀，否则压缩可能比被压缩的对话还贵。
