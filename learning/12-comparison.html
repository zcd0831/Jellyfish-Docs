12 与主流 AI Agent 工具对比

横向看一遍，才能判断哪些设计是「这个项目的选择」，哪些是「这个领域的共识」。 所有结论尽量给事实来源；查不到的明确标注 未核实，不猜。

学习目标

  • 用十个固定维度快速给任何 AI Agent 工具定位；
  • 说出 Jellyfish 在「权限模型」和「项目级配置信任」上相对激进的取舍；
  • 看清它的两个结构性劣势：能力生态薄、无 IDE 集成；
  • 知道哪些格子是「未核实」，不要拿它们当结论。
关于证据强度

本页表格里 [J] 标记表示依据来自本地仓库（Jellyfish/README.md、AGENTS.md、源码）； 其余依据来自各产品的官方文档或代码仓库（见文末来源清单）。 标「未核实」的格子表示未取得一手依据，我把它们留在表里是为了让你知道「这里不知道」， 而不是让你以为「这里没有」。

另外提醒一句：这类产品的细节变化很快。表里的版本相关描述（Node 版本要求、模型支持范围等） 以来源页为准，不要当成长期事实。

2. 三个维度上的深度对比

2.1 权限模型：谁最保守？

工具判定模型「无人在场」时项目级配置
Jellyfish 两段式：核心策略（三段名单）→ 插件拦截（三态，无 ALLOW） 拒绝（fail-closed） 默认不加载，路径 + 内容指纹信任
Claude Code allow / ask / deny 规则，判定序 deny → ask → allow 取决于 ask 规则与权限模式 默认生效（.claude/settings.json）
Codex CLI 沙箱 + 审批策略，默认只读、无网络 按所选沙箱模式 —
Aider 无逐调用审批 自动写盘 + auto-commit —
Cline 每次编辑 / 命令需批准，可开 auto-approve 可配置 —
这里的差异是「立场」而不是「好坏」

Aider 的「自动写盘 + auto-commit」不是安全漏洞，而是另一个产品假设： 它假设你在 git 仓库里工作，撤销靠 git checkout。Jellyfish 的 fail-closed 假设的是 你可能在没有版本控制的目录里跑它，而且终端前面可能没人。

两家都不是「更对」，而是对不同使用场景给出的一致的答案。 评估一个 agent 工具时，要问的是「它的假设和我的场景一致吗」—— 而不是「它的权限模型看起来够不够严」。

2.2 扩展机制：PF4J vs MCP vs 插件包

方案代表扩展粒度代价
进程内插件框架（PF4J） Jellyfish 最广：工具 / 命令 / 提示词 / 权限拦截 / 会话持久化 / UI / 模型厂商 / 压缩策略都能换 插件与内核同进程 → 类加载隔离必须自己管（PluginClasspathGuard）；jar 变更要重启
MCP Claude Code / Codex CLI / Continue / Cline 主要是工具（外部进程 / 服务） 进程边界天然隔离，但只能扩展「工具」这一维，改不了提示词组装、权限判定、UI
插件包（多文件打包） Claude Code（skills / agents / hooks / MCP 打包） 中：钩子 + 技能 + 子代理 + MCP 受宿主提供的钩子点限制，不能替换内部算法
配置文件 + hub Continue.dev 模型与 MCP server 配置 最轻，但扩展面也最窄
一个实用的判断法

问自己：我想换的是「能力」还是「行为」？

  • 只想加工具（连数据库、查 Jira）→ MCP 就够了，而且它跨产品通用。
  • 想改「权限怎么判」「提示词怎么拼」「上下文怎么压」→ 只有进程内扩展点能做到。

Jellyfish 选择后者，代价是插件不通用（不能拿去给别的 agent 用），收益是它能被改造成一个完全不同的产品—— 连「压缩策略」都是插件，这在这批产品里是很少见的粒度。

2.3 厂商适配：广度 vs 深度

AiderJellyfishContinue.dev
模型数量100+（含本地模型）只有 OpenAI 兼容 + Anthropic Messages 两类传输多厂商 + hub 清单
适配深度不同模型用不同的编辑格式（diff / whole）厂商特有字段靠 vendorBody 透传；中性参数由各客户端翻译配置驱动
缓存优化未核实显式 cache 断点 + keepAlive + cache-safe fork 压缩未核实

这里体现的是两种思路：Aider 追求「广」（覆盖尽可能多的模型），Jellyfish 追求「深」 （在支持的厂商上把缓存、思考文本、流式工具分片都做透）。 对用户的实际差别是：你用的模型在不在支持的短名单里。

3. Jellyfish 的相对优势

#优势依据
1 JVM 可嵌入：有 Jellyfish-Spring-Boot-Starter， 能把内核接进已有 Spring Boot 应用；上表其余工具都不是 JVM 系 [J]、workspace 下的 Jellyfish-Spring-Boot-Starter/、Jellyfish-Spring-Template/
2 装配可替换：Dagger2 与手工装配交付同一个 JellyfishRuntime 契约，容器无关 [J]，03 页
3 权限最保守：三段优先级 + 无审批者 / 超时 / 中断一律拒绝； -cli 无审批界面时按拒绝而非放行 [J]，对比 Aider 默认自动写盘提交、Cline 可 auto-approve
4 项目级配置信任闸：信任单位是「路径 + 内容指纹」，未信任即跳过并告警 [J]；.claude/settings.json 与 AGENTS.md 类项目配置在多数工具里默认生效
5 三外壳一内核：CLI / TUI / HTTP(SSE) 同一装配，server 提供 HTTP 化人工审批端点 [J]，10 页
6 厂商中立层较干净：与厂商无关的 LlmRequest、由各客户端翻译的中性采样参数、 vendorBody/Headers 兜底私有字段 [J]，05 页
7 扩展粒度最深：连压缩策略、提示词组装、权限拦截都能换插件 [J]，07 页的 28 个扩展点

4. Jellyfish 的相对劣势

#劣势依据
1 起步成本高：JDK 8 + Maven 多模块 + PF4J；插件须打包后重启进程才加载 （/reload 不能新增 jar） [J]，11 页 B1
2 能力生态薄：文件 / shell / MCP / 压缩 / 持久化全在独立仓库。 未装压缩插件则 /compact 不可用；未装持久化插件则不能恢复会话。 而 Aider / Cline 开箱即用 [J]，08 页、本页对比表
3 模型清单窄：只声明 OpenAI 兼容与 Anthropic Messages 两类传输， 没有 Aider 的「100+ 模型」或 Continue 的 hub 式现成清单 [J]，ProviderTypes.java、LlmModule.java:102-186
4 无 IDE 集成：只有 CLI / TUI / Server，没有 VS Code / JetBrains 插件，也没有桌面与移动端 [J]，仓库只有 7 个模块，无 IDE 相关模块
5 运行时约束硬：必须 Java 8（禁用 9+ API 与语法）；TUI 无可交互终端即退 3 [J]，pom.xml:54-56、AGENTS.md
6 缺公开验证数据：未检索到第三方 benchmark；而 Aider 有 polyglot 榜单、Cline / Continue 有公开活跃度 [J] + 未在公开渠道检索到（这条是「未找到」而非「确定没有」）
关于劣势 6 的说明

「未检索到第三方 benchmark」不等于「项目没有被评测过」。这条只是说：本次调研没有找到可引用的一手数据。 在这个领域，benchmark 结果对使用决策的影响其实有限——更重要的是「它的能力边界和你的场景匹配吗」。

5. 一句话总结各家哲学

工具一句话哲学
Jellyfish内核最小、能力全外置、默认不信任——面向「要被嵌进别人系统里」的场景
Claude Code单产品闭环、多面覆盖、hooks 保证确定性 [2][5]
OpenClaw自托管、数据在本地、一切皆插件 [8]
Codex CLI沙箱与审批分层，默认保守 [6]
Aider简单、代码库地图、自动提交——把 git 当作安全网 [9]
Continue.dev配置即代码、多 IDE 一致 [10]
ClinePlan / Act 分离 + 人工在环 [10]

关键结论

  1. Jellyfish 的差异点集中在四条：Java/JVM 可嵌入、插件化内核（含压缩与权限拦截）、fail-closed 权限、项目级配置信任闸。
  2. 主流工具的优势同样清楚：开箱即用、模型覆盖广、IDE 与多端形态。这三条恰好是 Jellyfish 的三条短板。
  3. 「扩展机制」这一维度上，MCP 是行业共识的「工具扩展」标准，而进程内插件框架是「行为扩展」的少数派路线。两者不冲突：Jellyfish 也有 MCP 插件（jellyfish-plugin-mcp）。
  4. 权限模型上的差异不是「严 vs 松」，而是产品假设的差异：Aider 假设你在 git 仓库里（撤销靠版本控制），Jellyfish 假设你可能在无版本控制的目录里且终端前没人。
  5. 评估这类工具的正确问题不是「哪个更强」，而是「它的假设和我的场景一致吗」—— 而这个假设，通常能从它的「默认行为」里读出来。
