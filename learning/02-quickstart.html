02 环境准备与快速上手

先让它跑起来，再理解它为什么这么跑。这一页同时是「配置体系」的源码导读——因为启动期做的大部分事情，就是把配置文件读成对象图。

学习目标

  • 能独立完成：构建 → 装插件 → 跑通 -cli / -tui / -server 三种模式；
  • 记住五份配置文件各自管什么、放哪里、哪些走双源、哪些不热更新；
  • 说清 ${VAR} 缺失时为什么是「整份配置加载失败」而不是「局部降级」；
  • 理解双源合并里「段声明标记」这个机制，以及它与「段非空」的区别（一个真实修过的 bug）。

坑点

新增 / 删除插件 jar 只在启动期确定，/reload 不会加载新 jar。 PF4JPluginManager.java:120 明确写着「不做 jar 热部署」。 /reload 只处理「插件已加载、配置段变了」以及启用/禁用名单变化这两件事 （详见 16 页）。换了 jar 必须重启进程。

4. 三种模式跑起来

# 不带参数 = 交互界面（-tui）
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar

# 单次问答
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "总结一下这个项目"

# 显式交互
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -tui

# HTTP 服务
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -server 9096

输出契约：stdout 与 stderr 分工

README（README.md:140-158）把它作为机器契约写死了： 回答与命令结果走 stdout，诊断、工具进度与日志走 stderr。因此这样是安全的： 

java -jar jellyfish-cli-0.1.1.jar -cli -p "总结这个项目" > answer.txt 2> diag.txt
echo "/help" | java -jar jellyfish-cli-0.1.1.jar -cli

退出码

码含义归类依据
0成功（含「未知命令」这类用户输入错误）—
2用法错误：参数缺失 / 未知 / 冲突，或没有输入解析阶段 StartupOptionsParser.build()
3启动失败：配置、插件或装配出错；TUI 需要可交互终端而没有bootstrap 期间任何运行时异常
4运行失败：回合抛异常，或命令执行失败内核起来之后的运行期故障
6回合未收敛：达到最大轮次仍未给出最终回复ReActResult.truncated
7回合被插件拦下：一句都没发给模型（stdout 保持为空）ReActResult.blocked
设计依据

「归类看的是失败发生在哪一步，不是异常属于哪个类」（README.md:161-162）： bootstrap 期间的任何运行时异常都算启动失败退 3，内核起来之后一律退 4——哪怕它不是 JellyfishException。 这条规则的价值在于：脚本里 if [ $? -eq 3 ] 就意味着「环境没配好，别重试」， -eq 4 才意味着「这次执行出问题了，可以重试」。如果按异常类型归类，这个判断就没法做。

常量定义在 jellyfish-cli/src/main/java/zcd/jellyfish/cli/ExitCodes.java:17-41。注意有两个不同的失败都返回 3（启动失败 / TUI 不可用）， 所以脚本里区分它们要看 stderr 文本。

注意这里是间接寻址：config.json 不写任何配置内容，只写「别的配置在哪」。 所以「改配置」永远是改另外三份文件，而 config.json 只在你想挪位置时才动。

设计依据

为什么 config.json 要放在 classpath 根、不参与双源？ 因为它决定了「去哪找项目级配置」。如果它本身也能被项目级覆盖， 那么一个 git clone 下来的目录就能通过「改写 projectPath 指向别处」 来绕过信任闸——闸门本身的钥匙不能挂在闸门上。同理 plugins.roots 也写在 config.json 里，并且不参与双源合并（RuntimeConfig.java:686-701）， 只有行首 ~ 展开。否则被克隆的仓库就能指向一个恶意插件目录。

另一个实际收益：config.json 在内核 jar 里， Jellyfish-Spring-Boot-Starter 这类嵌入形态可以自带一份而无需外部文件系统权限。

双源合并规则（细节最多的一块）

  • 同名 provider / agent / 插件配置段：项目级整对象覆盖全局级，不是逐字段合并。 想加一个模型就在项目级把整个 provider 写全。
  • react / permission / subAgent / ask 段：「写了才覆盖」， 靠「段声明标记」判断，而不是「段非空」（JellyfishSettings.java:46-58 的字段、:84-85 的赋值、 :173-217 的 isXxxDeclared()；字段与赋值在 :46-58、:84-85）。
  • 名单类字段（如 enabled/disabled）空数组 [] = 显式清空， 不是「未配置」（RuntimeConfig.java:663-683）。
  • plugins.roots 不合并（RuntimeConfig.java:686-700）。
坑点

「段声明标记」这条是 0.1.1 修过的真实 bug。 旧实现的合并层写成 project != null ? project : global，语义上看起来对， 但因为 project 是「读到的对象」而不是「这一段有没有被声明」，它永远走左支—— 于是你在项目级只改了别的段，全局级配的 ask.timeoutSeconds = 0 会悄悄回退到缺省的 120。 现在改成了按段声明标记判断（RuntimeConfig.java:510-524，判据是 isXxxDeclared()）。 这就是「用段非空当判据」会踩的坑：一个没有字段的段看起来是空的，但它被声明了。

6. 环境变量插值 ${VAR}

密钥不写进配置文件，而是用 ${VAR} 引用环境变量。支持三种写法 （infra/config/SettingsBinder.java:20-36 的类注释里列了三种写法）：

  • ${VAR} —— 必需，缺失即抛异常；
  • ${VAR:-默认值} —— 可选，缺失时用默认值；
  • \${VAR} —— 转义，保留字面量。

插值只作用于字符串值，不动 JSON 的 key。核心实现在 resolve()：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:160-173
private String resolve(String expression, String source) {
    int separatorIndex = expression.indexOf(DEFAULT_SEPARATOR);
    boolean optional = separatorIndex >= 0;
    String name = optional ? expression.substring(0, separatorIndex) : expression;
    String value = envProvider.apply(name);
    if (value != null) {
        return value;
    }
    if (optional) {
        return expression.substring(separatorIndex + DEFAULT_SEPARATOR.length());
    }
    throw new JellyfishException("environment variable is not set: " + name
            + (StringUtils.isBlank(source) ? "" : ", source: " + source));
}

逐行解释：

  • 先找 :-，决定这次是「必需」还是「可选」；
  • envProvider.apply(name) 是一个函数式接口——这样测试里可以注入假的环境变量， 不必真去改进程环境（SettingsBinder 的构造函数注入点）；
  • 环境变量存在但为空串时走的是「存在」分支（返回空串），不会用默认值。 这与 shell 的 ${VAR:-x} 语义一致；
  • 必需变量缺失 → JellyfishException，异常文本里带上 source（哪个文件）， 因为同一个变量名可能在多份配置里出现。
坑点

缺失的 ${VAR} 会让整份配置文件加载失败，不是局部降级。 异常从 resolve 经 ConfigLoader.read（ConfigLoader.java:40-51）一路向上抛， 最终在启动期失败退 3。所以现象是「进程起不来，报 environment variable is not set」， 而不是「那一个 provider 不能用了」。

这是刻意选的失败模式：配置错误如果降级成「部分生效」，最坏的结果是某个字段悄悄用着缺省值在跑， 而你完全不知道。表现为「配了但没生效」的 bug 比「起不来」难查得多。 想避免就在写配置时一律用 ${VAR:-默认值}。

7. 未知字段与数值校验

这里有两种方向相反的宽容策略，别搞混：

情形行为机制与位置
JSON 里有内核不认识的字段 静默忽略，但事后发一条配置告警 绑定层关闭 FAIL_ON_UNKNOWN_PROPERTIES（ObjectMapperWrapper.java:43）， 读取层把「绑不上的字段名」回调出来（ConfigLoader.java:71-84）， RuntimeConfig.read 对每个未知字段发 ConfigWarningEvent（RuntimeConfig.java:415-419）
字段名认识但数值越界 回退缺省值 + 收集告警 SettingsGuard 只做区间把关：positiveOrDefault / nonNegativeOrDefault / percentOrDefault（>100 按 100）
${VAR} 缺失 整份失败 见上一节

SettingsGuard（SettingsGuard.java:36-112）有个值得注意的细节： null 表示「没配」，不告警也不校验——只有「配了但非法」才回退并告警。 这保持了「没写 ≠ 写了 0」这条贯穿全项目的语义（在采样参数上它更关键，见 05 页）。

还有一点容易误解：SettingsGuard 没有「必填字段」校验。 必需性由两处承担——环境变量插值（缺失即抛），以及各个 Settings 构造器自己的 warnings （例如 PermissionApprovalSettings.java:113-124）。

告警最终怎么让人看到？由 ConfigWarningReporter 订阅事件后打一行 WARN 日志：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigWarningReporter.java:36-46, 96-113 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/AgentHarness.java:193-205 ← bootstrap() 里于 refresh() 之前 start
坑点

告警默认走日志，而日志默认级别是 WARN 且只写 stderr （log4j2.xml:12-16，级别是 ${sys:jellyfish.log.level:-WARN}）。 所以「字段名拼错，配了不生效」这种现象是真的没有任何界面提示的—— 它只在 stderr 上有一行。排查这类问题第一件事是 --verbose 或看 stderr。

8. 关键代码：双源加载的骨架

RuntimeConfig.load() 是整个配置体系的中心。它同时处理了「同一份文件只读一次」和「项目级先过信任闸」：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:216-233
<T> T load(ConfigPaths paths, Class<T> type, BinaryOperator<T> merger) {
    String globalPath = paths == null ? null : paths.getGlobalPath();
    String projectPath = paths == null ? null : paths.getProjectPath();
    T global = read(globalPath, type);
    T project;
    if (isSamePath(globalPath, projectPath)) {
        project = null;              // 同一份文件只读一次
    } else {
        project = readTrustedProject(projectPath, type);   // 先过信任闸
    }
    T merged = merger.apply(global, project);
    if (merged == null) {
        throw new JellyfishException("config merger returned null for type: " + type.getName());
    }
    return merged;
}
  • isSamePath 这一步不能省：用户完全可以把 globalPath 和 projectPath 配成同一个文件， 那时按「读两次 + 合并」会得到重复的名单项。
  • merged == null 时抛异常而不是返回 null：null 会一路传到注入点， 变成某个字段的 NPE，而那时的堆栈跟配置毫无关系。在这里炸掉，堆栈直接指向「哪个类型的合并器有问题」。
  • 注意 load 是包级可见的（不是 public）——外部只能用具体的 refresh() 等入口， 避免有人绕过配置类型直接读文件。

信任闸的两个状态与三条授予途径

状态行为
UNTRUSTED跳过该文件 + 发一条告警（提示解锁方式），但不失败
ABSENT文件不存在，不是错误，不告警

授予信任的三条途径（ProjectConfigTrust.java）：

  • trustEverythingInThisRun() —— 对应 --trust-project-config，仅本次进程有效、不落盘；
  • trustForSession() —— 只在当前会话内存里生效；
  • grant() —— 写入 ~/.jellyfish/trusted-project-configs.json（持久，TUI 确认框会问你要不要记住）。

信任的记录键是「文件绝对路径 + SHA-256 内容指纹」（ProjectConfigTrust.java:46 的注释、 :82 的字段、:171-178 的 grant()）， 内容一变即失效。classpath: 开头的路径不受此闸管辖（ProjectConfigTrust.java:118-122）。 CLI / TUI 的入口在 ProjectConfigTrustConsent.java:113-147。

9. 本页坑点小结

启动期最容易踩的六个坑
  • 项目级配置默认不加载：写了 ./.jellyfish/*.json 却发现不生效——先确认是否信任（01 页有完整解释）。
  • 未知字段静默忽略：键名拼错没有任何界面提示，只有 stderr 一行 WARN。
  • ${VAR} 缺失 → 整份配置加载失败退 3：不是局部降级。
  • 插件 jar 变更必须重启：/reload 不加载新 jar。
  • 装了新插件后插件不启动：插件自带 jellyfish-api 或 pf4j 会导致类加载冲突， 而护栏只记 loadError 不抛异常（PluginClasspathGuard.java:47-60）， 表现是「静默不启动」，必须看 WARN。详见 16 页。
  • 「配置写对了但仍按缺省值跑」的另一个来源：某些组件在 RuntimeConfig.refresh() 之前就被构造了 （RunScheduler 曾有此问题，见 CHANGELOG 的 Unreleased/0.1.1 Fixed）。这类参数改完要重启，不要指望 /reload。

关键结论

  1. Jellyfish 的配置是两级间接：config.json 只说文件在哪，另三份才装内容。因此 config.json 天然属于「用户不该随便改」的一层。
  2. 双源合并有三种不同的粒度——段级（声明标记）、对象级（整对象覆盖）、列表级（空数组即清空）。混淆它们是最容易配错也最难查的地方。
  3. 配置错误一律选择「要么立刻可见、要么不生效」：${VAR} 缺失直接炸，未知字段发告警，非法数值回退。没有「悄悄用了别的东西」的第三种结果。
  4. 构建与运行门槛很低（JRE 8+、一个 fat jar），但能力门槛不低：不装插件的话，跑起来只能执行系统命令。
