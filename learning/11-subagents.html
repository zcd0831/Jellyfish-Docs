11 子代理与多 Agent 协作

委派链路、父子之间唯一的通信机制、并发门控与上下文装载、多 Agent 协作的三种形态。 04 页讲了「边界在哪里」，这一页讲「机制怎么接起来的」。

学习目标

  • 说清一次 task 调用经过的五跳，以及每一跳「不通过就不产生任何副作用」的准入是怎么排的；
  • 解释父子代理之间只有一条下行输入与一条上行结果，以及完整记录为什么只能靠归档文件回读；
  • 拿到上下文与状态隔离的清单：子代理看不到什么、它的会话去哪了、用量算在谁头上；
  • 说清并发的两层门控分别是哪两层、为什么「让出许可」是结构性解法而不是优化；
  • 知道 RunContext / RunContextHolder / RunTree / RunPermit 各自管什么，以及 enter() / leave() 的配对为什么必须放在 finally；
  • 理解多 Agent 协作的三种形态为什么必须走不同的入口，以及插件为什么进不了 RunScheduler；
  • 知道 run 的观测走哪条通道、插件要观测得绕哪条道，以及嵌套回合里哪些能力被当场关掉。

1.1 工具层：只做三件事

TaskTool 的类注释把它的职责划得很死：「把模型给的参数翻成 SubAgentCall、 把子代理的进度转给外壳、把 SubAgentOutcome 渲染成回灌文本。所有准入判定与执行编排都在 SubAgentLauncher 里——工具层不重复它们，否则「为什么这次委派被拒绝」会有两份答案。」 这让「工具层薄、机制层厚」这条分工在代码上可以直接看出来：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/subagent/TaskTool.java:103-121
    public ToolCallResult handle(ToolCallRequest request) {
        Map<String, Object> arguments = request.getArguments();
        String agentId = text(arguments.get(ARG_SUBAGENT_TYPE));
        if (StringUtils.isBlank(agentId)) {
            // 参数缺失是 schema 层面的问题，说清楚缺哪个即可；类型写错时由委派器给出可用清单。
            // 但它是「这次工具没跑」而不是「跑完了什么都没做」——不补 terminal，界面会按缺省
            // （正常跑完）渲染，于是模型与用户都看不到该有的警示标记
            Map<String, Object> metadata = new LinkedHashMap<String, Object>();
            metadata.put(ToolMetadata.KEY_TERMINAL, ToolMetadata.TERMINAL_REJECTED);
            return new ToolCallResult(NAME, "[子代理未开始] 缺少参数 subagent_type，"
                    + "请指定一个可委派的子代理类型（见系统提示中的可委派类型列表）。",
                    Collections.unmodifiableMap(metadata));
        }
        ToolOutputSink sink = request.getOutputSink();
        announce(sink, agentId, text(arguments.get(ARG_DESCRIPTION)));
        SubAgentCall call = new SubAgentCall(request.getSessionId(), agentId, text(arguments.get(ARG_PROMPT)),
                request.getCancellationToken());
        SubAgentOutcome outcome = launcher.run(call, progress(sink));
        return render(outcome, agentId);
    }

三点值得注意。第一，唯一的本地判定是「参数缺失」：那属于 schema 层面的自纠错， 提示里还要指路「见系统提示中的可委派类型列表」——因为模型拿不到 agents.json， 不告诉它有哪些可选，它只能瞎猜。

第二，它给这个结果补了 terminal 标记：那个键的约定是「缺省 = 正常跑完」， 而「参数都没给」显然不是。不补的话界面会按缺省渲染，于是模型与用户都看不到该有的警示标记。

第三，它把 run 当成一次同步调用（launcher.run(call, progress(sink))）。 run 只是 await(spawn(...)) 的简写，语义上「派生 + 等结果」被合并成一行， 因为工具处理器本来就要等结果才能回灌给模型。并发的扇出入口是另外那一半（见第 6 节）。

设计依据：为什么同一次判定要查两遍（canDelegate 与 tryAcquireSpawn）

源码注释直接给了答案：「上面那次 canDelegate 只是尽早拒绝，真正占名额必须一次 CAS 完成， 否则并行派生时会集体超发」。RunTree.canDelegate（RunTree.java:66-67）是只读判定， 读的是 spawnCount.get()；真正占名额的 RunTree.tryAcquireSpawn （RunTree.java:76-88）把「读剩余额度」与「占用它」合成一次 compareAndSet。

为什么两遍而不是一遍：两处服务的对象不同。前一遍服务的是「快速失败」—— 被拒的委派连 sessionManager.require 都不该调；后一遍服务的是「不超发」—— 并行时多个父 run 会同时尝试派生兄弟，两步之间有一个窗口，窗口里每个线程都看到「还剩名额」， 于是集体超发，而上限的意义恰恰是不超发。

配套地，quota()（SubAgentLauncher.java:229-242）复用同一个 limitReason 组装拒绝理由——「同一份额度被两处描述（查询与 spawn 的拒绝理由）时， 各写一句话就等于给了两份会漂移的答案」。这也是插件侧 SubAgentPort.quota() 能拿来 「在派生任何子代理之前整份拒绝」的原因。

1.3 派生：把一次委派变成运行时里的一次 run

过了十道门之后，链路才第一次产生副作用：建一个瞬时子会话，然后把「跑一个嵌套回合」包成执行体交给 AgentRuntime.spawn。注意模型与 provider 两个参数明确传 null—— 它们由子代理自己的 agent 定义决定，不继承父会话：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/subagent/SubAgentLauncher.java:302-327
    private SubAgentRunHandle derive(SubAgentCall call, ReActListener listener, Session parent,
                                     SubAgentSettings settings) {
        Session child = null;
        String runId = null;
        try {
            // 模型与 provider 留空——它们由子代理自己的 agent 定义决定，不继承父会话。
            child = sessionManager.createEphemeral(parent.getSessionId(), call.getAgentId(),
                    null, null);
            // 执行体是「在 agent-run 线程上跑一次嵌套回合」：句柄同时是取消令牌，取消与超时都能掐断它的 LLM 流
            final Session childSession = child;
            AgentRunRequest request = new AgentRunRequest(parent.getSessionId(), call.getAgentId(),
                    childSession.getSessionId(), null);
            AgentRunHandle handle = runtime.spawn(request, call.getCancellationToken(), runHandle -> {
                ReActResult result = reActLooper.runNested(childSession, call.getPrompt(), listener, runHandle,
                        settings.getMaxRounds(), toolFilterOf(call, parent));
                return AgentRunResult.of(runStatusOf(result), result.getContent(), result.getRounds(),
                        childSession.getUsage(), null);
            });
            runId = handle.getRunId();
            return SubAgentRunHandle.of(call.getParentSessionId(), childSession, handle);
        } catch (RuntimeException e) {
            LOG.warn("子代理回合失败: parent={} agent={}", call.getParentSessionId(), call.getAgentId(), e);
            // 子会话可能已建、run 可能已登记：带着它们返回，交给 await 统一收尾
            return SubAgentRunHandle.failed(call.getParentSessionId(), child, runId,
                    SubAgentOutcome.failed(messageOf(e)));
        }
    }

这段代码里藏着一个很实用的设计：「早失败」的句柄也走同一条收尾出口。 建会话与登记 run 之间任何一步抛错，返回的都是 SubAgentRunHandle.failed(...)， 它带着已经建好的子会话与 runId，于是调用方只需要 spawn → await 两步， 不必为「派生到一半失败」另写一条清理分支（SubAgentRunHandle.java:74-101）。

另外注意执行体把 runHandle 直接当取消令牌传给了 runNested： 「取消这次 run」与「掐断这次 run 的 LLM 流」是同一件事，因此不设两个对象 （AgentRunHandle.java:11-25）。

2.1 下行：prompt 是唯一输入，所以它必须自足

「必须自足」不是一句提示语，而是写进工具名片的契约——它是模型判断「什么时候该委派、prompt 该写多细」 的主要依据，因此连不适用的场景也一并写清：

「不适用」那两句比「适用」更重要：「需要与用户来回确认的任务」这一条直接对应第 8 节 ——子代理回合里 ask_user 是当场拒绝的，派出去只会白花一轮。而「一两步就能做完的事」对应的是 成本：委派要建会话、跑一个完整回合、写归档，还有最小一份上下文开销。

还有一个容易忽略的下行细节：嵌套回合忽略插件的 replaceInput （ReActLooper.java:851-859），理由是 「它的输入是模型写出来的任务描述，改写会让『模型要什么』与『子代理收到什么』分叉，而模型无从得知」。 也就是说，这条下行通道连插件都不许改。

所以原因被挪到了正文开头，由 SubAgentLauncher.truncationReasonOf （SubAgentLauncher.java:518-526）从 run 结果的 error 与文本两处取： 墙钟到点时由调度器把原因写在 error 上（那时回合是被取消的，没有正文）， 轮数上限与 token 预算由循环器写在文本上。原因另存一份在 SubAgentOutcome.getError() 上， 「供调用方原样转述而不是去解析文本」。

2.3 归档：完整记录的唯一出口，而且是一个「可能缺席」的出口

文本是有损的：未收敛时只回灌最后一段；即使正常完成，父代理也看不到子代理中间读了哪些文件、 调了哪些工具。补上这条信息的东西是归档——把 run 身份、终态、用量与子会话完整快照 写成一份 JSON：

2.4 为什么不做双向通信

设计依据：不做双向通信，是有意把「自足」变成调用方的义务

一个很自然的想法是「让差旅中的子代理随时回来问一句」。项目明确不这么做，四个理由各自都能在源码里找到：

  • 子代理看不到父对话，因此「回来问一句」缺少上下文，问题本身也难问准。 定义在 SubAgentLauncher 类注释：「它只看得到自己的系统提示词与这次任务原文， 看不到父会话的消息、工具选择与模型——除了 agent_id 指向的那份 AgentDefinition 与项目约定（AGENTS.md）」 （SubAgentLauncher.java:57-60）。
  • 让 prompt 成为唯一输入，是「委派的价值来自把噪音留在主对话之外」这条前提的直接结果。 通道一多，隔离就不再成立。
  • 内核不在关键路径上同步回调上层（AgentRuntime.java:24-26）： 等待阻塞在调用方线程上（DelegationHandle.await() 的注释：「等待是『编排方等内核』， 不是『内核等插件』」），终态通过句柄交给调用方，没有反向调用的环。
  • 约束文档把这条路直接封死了：docs/constraints.md:665-666—— 「子代理与主会话除了传入的任务之外相互隔离（fresh-only，没有 fork，且不做）」。 与之一致的是 SubAgentSettings 里没有任何「继承父上下文」的开关， 因为「子代理与主会话相互隔离是这块能力的设计前提，不是可调参数」 （DelegationRequest.java:9-13）。

代价落在调用方身上：写不清 prompt 就得不到好结果，而这一点无法用机制补救。 换来的是机制极简——不需要协议、不需要消息路由、不需要处理「子代理问了但父又取消了」这类竞态。

坑点：以为「长结论会完整回灌」

现象：主模型读完子代理的回灌文本，以为已经拿到全部内容；实际末尾只有一句话， 或者中间被截了一段。

根因：三层有损叠加。① 未收敛时只回灌「原因 + 最后一段正文」； ② 回灌文本作为工具输出，还要过 ToolOutputLimiter 的硬截断，超限时按头 30% / 尾 70% 切分并把全文落盘（见 07 页）； ③ 长文本的档案是另一份文件（run 归档），与工具输出落盘不共用配额。

规避：给主模型的提示里要显式区分这两种缺失——「文本太长」由工具输出信封里的 _path 兜（见 07 页），「文本不长但进程没跑完」由归档路径兜； 两条合起来，主模型在两种情况下都能拿到回看线索。同时记住：归档路径只在 TRUNCATED 时才附，正常完成时附它「只会诱导主模型去读一份并不需要的文件」。

4.1 为什么「线程」与「许可」必须是两个东西

RunScheduler 的类注释把这条讲成了推理：「池只负责『提供线程』，真正的并发控制交给许可信号量。 理由同样是等待——一个 run 等孩子时会占着一条线程，但它不该占着并发许可；两者若合一， 深度大于 1 时就会被『正在等孩子的父』占满而自锁死。」

于是池的上界必须比许可大，公式就在建资源那三行里：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/runtime/RunScheduler.java:186-188

        int poolSize = concurrent * (Math.max(0, settings.getMaxDepth()) + 1);
        int capacity = Math.max(1, settings.getMaxQueuedRuns());

concurrent × (maxDepth + 1) 是「活跃 + 等待孩子的父」的运行上界。 注释还解释了为什么这个池一次建满并常驻而不是按需扩容：JDK 只在队列满时 才把线程数从 core 扩到 max，于是「队列里还有空位」反而会让并发退化成一两条线程，比没有队列更慢 （RunScheduler.java:37-41）。

另一个是 run 自己的执行结束（第 5 节的 runTask）。两处都走同一对方法， 因此「正在等孩子的父」与「已经跑完的 run」都不占许可， permit == null 那一支服务的是顶层回合——它的根上下文本来就没有许可。

设计依据：「让出许可」是结构性解法，不是优化

RunPermit 的类注释写的是「方案 A 下父 run 等孩子时会阻塞在自己的线程上。 若它一直占着并发许可，孩子就可能永远排不上号（全局许可被一群『正在等孩子的父』占满）」。 04 页把它点成「经典的线程池死锁」。

换个说法：这不是「减少等待时间」的优化，而是去掉一个死锁的必要条件。 如果只在测量到卡顿时才加它，那么加之前系统在深度大于 1 时是没有正确性保证的—— 它会偶尔成功，取决于许可与线程的分配顺序。这类问题的排查成本极高，因此必须在机制层解决。

同一条推理的另一面是不把嵌套回合排回 react 池： ReActLooper.runNested 的注释说「把任务再排回同一个池里，几条并发父回合就能把池占满并互相等死—— 只有 8 条线程，而队列里的嵌套回合永远不会被谁让出位置」（ReActLooper.java:334-341）。

现象：在缺省配置下把并发、超时、扇出都测了个遍，一切正常； 把 subAgent.maxDepth 调大之后开始偶发卡住，而且看不出来跟哪次委派有关。

根因：maxDepth = 1 时只有一层委派，等待方永远是顶层回合—— 它的根上下文没有 RunPermit（RunContextHolder.java:61-64 用 permit = null 建根上下文），AgentRuntime.await 里那一支直接 return handle.await()，suspend() 根本没被调用。 于是「让出许可」这条路径在缺省配置下没有被覆盖；一旦深度 ≥ 2， 深度 1 的 run 会带着许可去等深度 2 的 run，许可被一群「等孩子的父」占满， 才轮到真正的自锁。

规避：把「调大 maxDepth」当成一次并发配置变更来对待—— 同时验证并发许可、等待区、池上界（后者按 并发 × (深度+1) 在第一次提交时定型， 改了要重启进程才生效）。调大 maxSpawnsPerTurn 时要一起调大 treeTokenBudget，否则先被截断的是树预算而不是单 run 预算 （docs/constraints.md:673-678）。

上下文的使用点分布在调用链两端：循环器在回合一进一出时开闭它，而委派发生在工具处理器内部—— 那里只有一个 ToolCallRequest，而它「只携带会话标识，不能携带内核类型」。 显式传参则要穿过整条工具执行链，而中间每一层都不需要它。

还有一条容易误读的地方：保留 ThreadLocal 不等于保留「线程封闭语义」。 承载的 RunContext 里，共享的 RunTree 是跨线程按引用共享的， 并行时每个执行线程各持一个上下文，但它们指向同一棵树；真正随线程隔离的只有「当前这条路径的深度」。

6. 多 Agent 协作的三种形态

形态谁发起入口准入与限流在哪适用
① 父子委派 模型（在某个回合里调 task） 内核工具 task，owner=core 注册 SubAgentLauncher（与形态 ② 共用） 一件自足的窄活；结论型委派
② 插件驱动的委派 插件（在工具处理器里） PluginContext.delegations() → SubAgentPort 同上，同一条代码路径 插件要一次扇出多个子代理、或先查额度再决定
③ workflow 编排 模型提交一份 spec，由插件执行 workflow 插件内部调用 ②，自己管步骤与依赖 ② 的全部约束，加上插件自己的 ledger / 依赖判定 多步骤、有跨步骤依赖的编排（见 20 页）

6.3 形态 ③：编排是插件的事，内核只提供原语

workflow 插件走的就是形态 ②：启动时拿一次委派端口，然后把它交给自己的引擎。 它同时说明了「为什么编排不进内核」——WorkflowPlugin 的类注释： 「编排的『表达形式』（spec 长什么样、怎么聚合）会随着用法演化，把它放进内核意味着每次调整都要动内核的发布节奏； 而内核只需要提供稳定的原语。插件缺席时 task 薄工具照旧可用，这正是『卸载即回退』」 （Jellyfish-Plugins/jellyfish-plugin-workflow/src/main/java/zcd/jellyfish/plugin/workflow/WorkflowPlugin.java:23-29, 42）。

承上启下：步骤图、跨步骤依赖、失败补救、结果聚合这些都属于「表达形式」， 因此细节放在 20 workflow 插件； 本页只固定它的位置——它在形态 ② 之上，因此额度、并发、取消、用量、归档的行为 与 task 逐字段一致，插件不自己起线程池、不自己实现并发上限。

设计依据：为什么插件不能直接进 RunScheduler

三条硬约束各自独立成立。①api 边界：RunScheduler、 RunContext、AgentRunHandle 都是内核类型，插件看不到 （RunScheduler 的 submit 是包级可见，全类只被 AgentRuntime 调用）。②方向：让插件自己起线程池， 等于把「全局并发上限」拆成对插件数量的隐式依赖——3 个插件各开 3 条就变成 9 条。 ③可替换性：SubAgentPort 的注释明确「插件不应另建并发控制： 并发度由内核的 governor 决定，超出的 run 在内核侧排队」。

代价是插件侧多一层对象（DelegationRequest / DelegationResult / DelegationStatus），换来的是「内核改并发策略，所有插件自动跟着改」。

    }

终态映射是两套词表之间唯一的约定，因此被写成了显式的一张表 （RunObservationBridge.java:130-142）：DONE → COMPLETED、 TRUNCATED → TRUNCATED、CANCELLED → CANCELLED、 BLOCKED → REJECTED（「被拦下 = 从未开始，与委派侧的 REJECTED 是同一件事」）， 兜底走 FAILED。注意它和 SubAgentLauncher.toOutcome （SubAgentLauncher.java:460-476）口径不同：后者把 BLOCKED 与 DONE 同走「已完成」，这是既有的对外行为， 差异被源码注释明确标了出来（SubAgentLauncher.java:357-366）， 对齐留到结果类型统一那一步——读到这里时别以为是缺陷。

坑点：插件侧的 run 事件会丢，而且不会重试

现象：插件的任务列表里有一条 run 一直显示「进行中」，而它其实早就结束了。

根因：桥投递的是通知通道，队列满即丢；而桥不做重试、不做缓冲， 理由写在类注释里：「一份『看起来可靠、实际仍会丢』的重试逻辑只会让消费方误以为可以不做自愈」。

规避：插件消费方必须自愈——把 AgentRunProgressEvent 当作 「有变化了」的提醒，而不是「唯一的真相来源」；真正的状态要能通过查询重新对齐 （内核侧对应的查询面是 AgentRuntime.activeRuns() / snapshot(runId)）。 另外「内核 run 事件无 STEP」这条在这里也有个实际后果： 想看过程只能看面板与工具输出，事件里没有中间进度。

8. 嵌套回合里的限制：ask_user 当场拒绝

ask_user 工具在子代理回合里不会「等」，而是立刻回一条「问不到人」：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/AskUserTool.java:106-111
    private AskAnswer ask(ToolCallRequest request, String question, List<AskOption> options) {
        if (request.getRunId() != null) {
            return AskAnswer.unavailable("子代理回合里无法向用户提问");
        }
        return askPort.ask(AskRequest.of(NAME, request.getSessionId(), question, options));
    }

判据是 request.getRunId() != null。这个字段是内核在派发工具调用时塞进去的「调用者身份」， 来源正是第 5 节那个上下文：

        // 它本来就是线程作用域的，同一条线程上不会中途变。

所以「子代理回合」不是靠一个布尔标记判断的，而是靠「这次工具调用有没有 run 身份」—— 顶层回合的根上下文 runId 为 null（第 5.1 节的 RunContextHolder.open），子代理则在某个 run 上。

设计依据：为什么是「当场拒绝」而不是「静默等待」

AskUserTool.ask 的注释给了完整推理：「外层界面按当前会话取待答项， 而子代理有独立的会话，它的提问根本不会出现在任何一个界面上；若照旧进通道等待， 那个子代理回合只会静默卡到超时。」

也就是说，两种做法的后果完全不对等：静默等待会让一次委派耗掉整份超时预算， 最后以 TRUNCATED 或 CANCELLED 收场，而原因（「它想问用户」） 在整个链路上不可见；当场拒绝让子代理立刻拿到一条明确的答复， 它可以据此继续（比如把问题写进结论里带回去）或者收尾。 这与 04 页里「ask 是 fail-open、审批是 fail-closed」的区分是两件事—— 这里是「这个上下文里根本没有答复者」，属于能力缺席，不是安全判定。

实用推论：该问用户的事不要委派出去

子代理既看不到父对话、又不能提问，因此「需要与用户来回确认的任务」必须留在主回合里做—— 这正是 TaskTool.description() 明确写进「不适用」的那一类。 想让子代理的疑问到达用户，唯一可行的做法是让它把问题写进最终结论， 由主模型决定要不要在主回合里调 ask_user。

9. 本页坑点小结

子代理与多 Agent 协作相关的坑
  • 子代理 run 不得进 react 池：父回合等孩子时阻塞在自己的线程上， 排回同一个 8 线程池会让并发父回合互相等死；run 跑在独立的 agent-run 池。 改动时先看两池是否「不共享队列」。
  • 审批与提问阻塞的是 react 线程：两者都在工具调用里同步等待 （见 04 页与 16 页对事件内联降级的取舍）。 因此「在 react 线程上做会阻塞的事」是双倍危险——它同时拖慢回合数与子代理的唤醒。
  • maxDepth = 1 时「让出许可」是空操作：等待方是顶层回合，它没有许可。 调大 maxDepth 等于打开一条此前从未被覆盖的路径（见第 4.3 节）。
  • 长结论会被截断，归档路径只在未收敛时给：正常完成时回灌的就是完整结论； 未收敛时给的是「原因 + 最后一段正文」+ [完整记录见 path]。 把归档当成可依赖的产物还会踩第二个坑——它受配额清理，随时可能消失。
  • TRUNCATED 有三种来源：轮数上限、单 run token 预算、墙钟。 首行只写「未收敛」是刻意的；要知道该调哪个键，必须读正文开头那句原因 （或 SubAgentOutcome.getError()）。
  • 子代理的工具清单只按 agent 策略收窄：按模式收窄的工具（例如 plan 模式） 是插件在执行期用权限扩展点表达的，不在清单过滤的判据里——因此子代理的清单 不会因父会话开着某个模式而变化（SubAgentLauncher.java:387-393）。
  • 额度是快照：quota() 只适合支撑「该不该开始」； 同一回合里别的调用方（另一个编排、或 task 工具）也会占用它， 拿它做精确分配一定会算错。
  • 开关关掉时摘的是工具，重算是 best-effort：ConfigReloadedEvent 可能丢， 丢了的表现是「清单里还挂着 task」，但委派本身仍会被 SubAgentLauncher 拒掉——这是外观陈旧，不是放行。
  • 子会话不进 all()、不落盘，但会发 SessionCreatedEvent： 订阅会话事件的代码要能容忍一条指向「查不到的会话」的事件；判断是不是子代理会话 请用 getKind()，不要用 parentSessionId 猜。
  • 收尾阶段的一切失败都只记日志：用量归集、归档、关会话都是 WARN 级别的 best-effort。因此「账目不对」「没有归档」都不会表现为委派失败——排查时要主动去日志里找。

关键结论

  1. 委派链路是「工具层薄、机制层厚」：TaskTool 只翻参数与渲染文本， 十项准入全部在 SubAgentLauncher.spawn 的副作用之前完成；被拒的委派不建会话、不发事件。
  2. 父子之间只有一条下行输入（prompt）、一条上行结果（末条 assistant 文本）、 一个文件指针（归档路径）。不做双向通信是设计前提而非未实现的功能， 代价由调用方以「写自足的 prompt」承担。
  3. 隔离是四层叠加：会话历史 / 模型与工具选择 / 会话表与落盘 / 提问能力。 用量是唯一的例外——它必须归集到父会话，且归集失败只记日志，不改变委派结论。
  4. 并发是两层正交的门控：Semaphore 管「同时在跑」，RunTree 管「一共派了几个、烧了多少」。 「等待时让出许可」是去掉死锁必要条件的结构性解法——缺它时深度大于 1 的系统没有正确性保证。
  5. 多 Agent 协作有三种形态，但准入只有一份：内核 task 与插件委派端口走同一条代码路径， 编排（workflow）建在端口之上。插件进不了 RunScheduler， 因为并发上限必须由内核集中持有。
