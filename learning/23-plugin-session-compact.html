23 session-file 与 compact 插件

08 页讲了内核侧的会话机制——谁负责变更、什么时候落盘、压缩怎么推进边界。 这一页讲另一侧：这两件事具体由哪个插件、用什么文件、什么线程、什么失败语义做的。 两个插件加起来 1577 行主源码，但它们决定了「会话会不会丢」和「长会话还能不能继续」。

学习目标

  • 列出 session-file 注册的三个扩展点，并说清它刻意不注册哪两个生命周期钩子；
  • 说出会话目录的默认位置、文件命名规则、临时文件后缀，以及「为什么没有索引文件」；
  • 解释原子写的五步及其各自挡住的失败场景，说清写失败与 git 失败为什么语义不同；
  • 走通恢复链（SessionRestoreRequest → 目录列举 → 导入），并说明它为什么必须晚于插件启动；
  • 拿到 CompactionStrategy 的三个字段，以及它们各自在内核里的消费点与钳制规则；
  • 说清摘要提示词放在哪、为什么放那儿，以及「没装压缩插件 = 功能缺席」的三处表现；
  • 理解压缩插件化的收益与代价，能判断什么改动该写进插件、什么必须动内核。

1. 两个插件管的两件事：存得住、压得动

先把分工摆清楚。两个插件都不碰会话的内存状态——它们拿不到 SessionManager， 只在内核留出的扩展点上应答。

2. session-file 注册了哪三个扩展点

整个插件的装配就一个方法：读配置、造两个协作者、注册三个处理器。顺序上有一句注释值得注意—— 先装配再注册，因为处理器一旦注册就可能被调用 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionFilePlugin.java:54）。

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionFilePlugin.java:51-61（start：装配与注册）
    public void start(PluginContext context) {
        PluginConfig config = PluginConfig.from(context.configuration());
        Path directory = config.sessionDirectory();
        // 先装配再注册：处理器一旦注册就可能被调用，字段必须已经就绪
        this.store = new SessionStore(directory);
        this.git = new GitRepository(directory, config.gitEnabled());
        context.contribute(SessionPersistRequest.class, this::persist);
        context.contribute(SessionDeleteRequest.class, this::delete);
        context.contribute(SessionRestoreRequest.class, this::restore);
        LOG.info("会话文件插件已启动: dir={} git={}", directory, config.gitEnabled());
    }

它刻意不注册的两个钩子

内核另有一对可否决的生命周期钩子：关闭前的 SessionBeforeCloseRequest （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/SessionBeforeCloseRequest.java:28）与 fork 前的 SessionBeforeForkRequest （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/SessionBeforeForkRequest.java:26）。 session-file 一个都没注册——整个文件里只有那三处 context.contribute。 这不是漏掉，而是这两条链路本来就不需要它插手：

动作内核做的事为什么持久化插件不用参与
关闭会话 先跑 beforeClose 否决链，再 persist(session)，最后才从会话表移除 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:710-721） 「退出运行」和「删掉存储」是两件事。关闭会落最后一次快照， 文件必须留着，所以这里没有可拦的东西
fork 先跑 beforeFork（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:346-348）， 复制完历史后 persist(forked)（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:366） 新会话落盘走的就是普通的 SessionPersistRequest。 再挂一个钩子只会多一条等价路径
坑点：关闭 ≠ 删除，文件是「最后一份快照」不是「垃圾」

现象：关掉会话后去会话目录里找，文件还在，于是以为删除没生效。
根因：close() 的语义是「退出运行态」，它故意先落一次盘 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:716-717 的注释： 「落盘失败时宁可不关」）。只有 delete() （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:795-811）才会让插件删文件。
规避：把「会话文件」理解成「这个会话存在过的证据」。要它消失得走 /delete。

3. 目录布局与文件命名：一个会话一个 JSON，没有索引

存储模型简单到一句话：目录里每个 *.json 就是一个会话，文件名就是会话标识。 没有清单文件、没有索引、没有数据库。

路径来源说明
~/.jellyfish/sessions/ Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/PluginConfig.java:35（DEFAULT_SESSION_DIR） 配置键 sessionDir；注释说明它取「与内核全局级配置目录同一处」，因为会话是跨项目的运行态数据
<sessionId>.json fileOf（Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:68-71，拼 SUFFIX = ".json"） 一个会话一个文件；读取路径只认这个后缀
<sessionId>.json.tmp TEMP_SUFFIX = ".tmp"（Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:47，注释写明「刻意不匹配 SUFFIX」） 原子写的临时文件。不会被当会话读进来，所以崩溃残留只是垃圾不是坏数据
<会话目录>/.git/ GitRepository 类注释（Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/GitRepository.java:43-45） 只在 gitEnabled 为真时存在；要么已存在，要么由插件 git init

列举就是一次目录通配 + 排序，目录不存在时返回空列表（「还没落过盘」不是错误）：

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:120-137（files：会话文件列举）
    List<Path> files() {
        if (!Files.isDirectory(directory)) {
            // 还没落过盘：没有文件不是错误
            return Collections.emptyList();
        }
        List<Path> files = new ArrayList<Path>();
        try (DirectoryStream<Path> stream = Files.newDirectoryStream(directory, '*' + SUFFIX)) {
            for (Path file : stream) {
                if (Files.isRegularFile(file)) {
                    files.add(file);
                }
            }
        } catch (IOException e) {
            throw new JellyfishException("列举会话目录失败: " + directory + " (" + e.getMessage() + ')', e);
        }
        Collections.sort(files);
        return files;
    }

Files.isRegularFile(file) 那一行挡的是符号链接：目录里如果有人放了指向别处的链接， 它不会被当会话名单里的成员。排序是为了让恢复顺序稳定（错误信息、日志、界面列表都可复现）。

插件给会话加的「扩展条目」存在哪

插件要在会话上带自己的状态（待办清单、检查点、已扫过的文件……），走的是 SessionManager.putExtensionEntry （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:503-528）。 这些条目不另存文件——它们被 SessionSnapshots.capture 装进快照 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionSnapshots.java:64 把 session.getExtensionEntries() 交给构造器），于是随着会话 JSON 一起落盘， 恢复时再由 Session.restore 放回去 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/Session.java:181-182）。 快照里的对应字段是 Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/SessionSnapshot.java:73。

上限值位置
条目数 64 条（新增第 65 条直接抛；覆盖已有的同 key 不算新增） Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:106、 :516-518
单条值大小 64 KiB（按内核的规范编码量字节） Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:103、 :597-599、:523-524
key 长度 256 字符 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:109、 :511-514
设计依据：为什么一个会话一个文件，而不是一个大文件或一个数据库？

SessionStore 的类注释说得直白 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:24-25）： git 的 diff 与历史按文件走。全部会话塞进一个文件，每次提交都会变成「一大坨」改动， 既看不出改的是哪个会话，也容易冲突。而 git 恰好是这个插件附带的第二层能力（第 5 节）， 文件粒度就是它的工作单位。

代价也明摆着：列举会话要读一遍目录、想按标题搜索就得全量解析。但会话数量是「人的数量级」， 这两个代价都可以忽略；换来的好处是存储可以用 ls 和 cat 直接看懂， 备份就是复制目录。

坑点：插件配置段里的 ~ 由插件自己展开

现象：把 sessionDir 配成 ~/my-sessions， 结果在当前工作目录下多了一个名叫 ~ 的目录。
根因：内核对配置值只做「项目级覆盖全局级」与 ${ENV} 替换， ~ 只在配置文件的路径段上展开，插件配置段里的会被原样送进来 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/PluginConfig.java:15-19）。
规避：本插件的 PluginConfig.normalize （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/PluginConfig.java:135-147） 自己展开一次并规范化成绝对路径——所以落盘位置不会随进程工作目录漂移。 Jellyfish-Plugins/jellyfish-plugin-session-file/src/test/java/zcd/jellyfish/plugin/sessionfile/PluginConfigTest.java:20-21 专门锁住了这两条。

4. 文件长什么样、怎么写的

4.1 格式：缩进 JSON，读写用插件自带的 Jackson

插件只能依赖 jellyfish-api，而内核的 ObjectMapperWrapper 在 jellyfish-infra，所以这里自带一份映射器（由 shade 打进插件包）：

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SnapshotJson.java:83-90（映射器配置）
    private static ObjectMapper createMapper() {
        ObjectMapper mapper = new ObjectMapper();
        mapper.registerModule(new ParameterNamesModule());
        mapper.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
        // 缩进输出：文件是要被人读、被 git diff 的
        mapper.enable(SerializationFeature.INDENT_OUTPUT);
        return mapper;
    }
配置作用
ParameterNamesModule 快照类型是「全字段构造器 + 无 setter」的不可变对象，Jackson 没有默认构造器可用， 只能靠构造器参数名反序列化；参数名要在编译期用 -parameters 保留 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SnapshotJson.java:11-19 的类注释）
关掉 FAIL_ON_UNKNOWN_PROPERTIES 未知字段不报错：快照将来加字段时，旧文件仍然读得出来。 读不出来的代价是整段会话丢失，而少一个字段最多是某个新属性回到默认值
INDENT_OUTPUT 缩进输出——文件是给人看、给 git diff 的，不是给机器压行的

这条链路最怕的失败是「文件写出来了，重启后读不回来」（参数名没保留、编码不对）。 所以有一组专门的往返比对测试盯着它： Jellyfish-Plugins/jellyfish-plugin-session-file/src/test/java/zcd/jellyfish/plugin/sessionfile/SnapshotJsonTest.java:17-19。

4.2 内容没变就不写

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:81-93（writeIfChanged：先比内容再落盘）
    boolean writeIfChanged(String sessionId, String json) {
        Path file = fileOf(sessionId);
        try {
            createOwnerOnlyDirectories(directory);
            if (Files.exists(file) && json.equals(read(file))) {
                return false;
            }
            writeAtomically(file, json);
            return true;
        } catch (IOException e) {
            throw new JellyfishException("会话落盘失败: " + file + " (" + e.getMessage() + ')', e);
        }
    }

内核在每次状态变更后都会派发持久化，而「切换权限模式」这类变更常常没有实际改动。 先比内容再落盘，既省一次写，也避免 git 里出现一串空提交 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:27-28 的类注释）； 返回值就是给调用方判断「要不要排 git 提交」的 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionFilePlugin.java:109-112）。

4.3 原子写：五步挡住五种失败

Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:172-189（writeAtomically：临时文件 + 改名）
    private void writeAtomically(Path file, String json) throws IOException {
        Path temp = file.resolveSibling(file.getFileName() + TEMP_SUFFIX);
        try {
            Files.write(temp, json.getBytes(StandardCharsets.UTF_8),
                    StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING,
                    LinkOption.NOFOLLOW_LINKS);
            restrictToOwner(temp, false);
            try {
                Files.move(temp, file, StandardCopyOption.REPLACE_EXISTING, StandardCopyOption.ATOMIC_MOVE);
            } catch (AtomicMoveNotSupportedException e) {
                // 少数文件系统不支持原子替换，退化到普通替换：至少不会留下半截文件在目标路径上
                Files.move(temp, file, StandardCopyOption.REPLACE_EXISTING);
            }
        } catch (IOException | RuntimeException e) {
            deleteQuietly(temp);
            throw e;
        }
    }
步骤挡住的失败
写到 <id>.json.tmp 进程被杀在写的中途：目标文件一个字节都没动，读到的是上一份完整快照
LinkOption.NOFOLLOW_LINKS 临时文件名固定，而目录内容不完全由我们决定（同步盘、备份工具、有人手动放了同名符号链接）。 预置的链接会让普通的 open 老实跟过去写到别处——加上这个选项，最后一段是符号链接就直接失败 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:157-160）
restrictToOwner(temp, false)（文件收 600） 「先按 umask 可读、稍后才收紧」的窗口。rename 保留 inode，所以目标文件一出生就是 600 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:226-233）
ATOMIC_MOVE，不支持时退化普通替换 半截文件。同一文件系统上是原子的；跨设备时退化为「先删后移」，此时仍不会出现半截文件
异常时 deleteQuietly(temp) 残渣——而且清理失败也只记 DEBUG，不能把正在上抛的那个异常吃掉 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:240-246）

为什么临时名是固定的 <id>.json.tmp 而不是随机名？注释给了理由 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:162-163）： 同会话并发写本来就是「后写覆盖前写」（两次写的都是同一份快照的相邻版本）， 换随机名只会让崩溃残留的临时文件越积越多，并不换来正确性。

4.4 写失败怎么表达

有一条硬规矩：文件落盘失败必须上抛。理由写在契约里—— 「内核在『消息已追加』『会话已创建』之后同步派发本请求，处理器抛出的异常原样冒泡。 那一刻起『会话状态已变』与『状态已落盘』必须同生共死」 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/SessionPersistRequest.java:11-14）。 所以这里的三档语义是不同的：

设计依据：为什么 git 出错不让对话失败？

「文件是真相，git 是附加的版本化层」——这是插件类注释里的原话 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionFilePlugin.java:25-27）。 反过来做（git 出错就让对话失败）会把「机器上没装 git」「仓库权限不对」这类环境问题 直接升级成「Jellyfish 不能说话」，代价与收益完全不成比例。

但反过来也成立：文件写失败不能降级为 WARN。少一版历史只是不便， 少一段会话是数据丢失；两者不可能用同一个失败等级。

5. git：附加的版本化层

落盘链上不允许出现进程往返：persist 直接落在 ReAct 回合线程或启动线程上， 一次慢 git 会把「一轮对话的收尾」拖住好几秒。所以 commit 只做两件非阻塞的事： 把「这个文件该提交了」记进待提交表，叫醒提交线程。

    private SessionRestoreResult restore(SessionRestoreRequest request) {
        SessionStore current = requireStore();
        List<SessionSnapshot> sessions = new ArrayList<>();
        for (Path file : current.files()) {
            try {
                sessions.add(SnapshotJson.read(current.read(file), file.toString()));
            } catch (RuntimeException e) {
                // 单个坏文件不该让同目录其它会话也回不来
                LOG.warn("跳过无法解析的会话文件: file={} reason={}", file, e.getMessage());
            }

    }

7. 删除与清理

删除是破坏性操作，所以内核与插件的分工是「先派发删除、再移出会话表」， 任何一步失败都不留下不一致状态。插件这一侧只做两件事：删文件、留一次 git 提交。

三个动作的差别值得背下来，它们经常被混为一谈：

动作插件做什么文件内核的失败处理
落盘（persist） 内容变了才写 + 排一次 git 提交 写入 / 覆盖 失败上抛，本次变更失败 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/session/SessionManager.java:1268-1271）

但 keepRecentMessages = 0 是合法值：契约里它的含义是「一条原文都不留」。 把它当非法值会让用户没法表达这个意思 （Jellyfish-Plugins/jellyfish-plugin-compact/src/main/java/zcd/jellyfish/plugin/compact/PluginConfig.java:119-121）。 本插件允许的区间是保留条数 [0, 1000]、摘要上限 [1, 20000] （Jellyfish-Plugins/jellyfish-plugin-compact/src/main/java/zcd/jellyfish/plugin/compact/PluginConfig.java:41-48）； 内核允许的摘要上限区间是 [200, 20000] （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ReactSettings.java:67-70）。 两边都做不是重复而是分工：插件拒绝明显荒谬的值，内核拒绝任何越界值。

11. 为什么压缩要单独一个插件

这一条不是本页的推断，源码把它写在了插件类注释里：

Jellyfish-Plugins/jellyfish-plugin-compact/src/main/java/zcd/jellyfish/plugin/compact/CompactPlugin.java:12-17（类注释，逐字引用）
 * 为什么压缩要插件化：内核手里只有机制（读消息、选范围、发模型调用、校验摘要、推进边界、记用量、
 * 落盘），「这份历史压成什么样」是决定而非机制。放进插件有三个直接好处：摘要措辞可以自己改、保留条数可以
 * 按团队习惯调、不想用时直接不启用插件（压缩整体缺席，而不是有个半成品在内核里空转）。
 * 

 * 插件不做什么（内核的机制边界，不是本插件的自觉）：拿不到任何一条消息正文、不能发起模型调用、
 * 没有否决权。它只回答「这一次该怎么压」——见 {@link CompactionStrategyContribution}。

换句话说，划界标准是「机制 vs 决定」： 读哪些消息、什么时候压、怎么发调用、怎么校验摘要、边界怎么推进、用量怎么记——这些是机制，留在内核； 「压成什么样」是决定，交给插件。这条线让下面这张表的左列成为可能：

收益代价
摘要措辞、输出格式、长度约束全在那份资源文件里，改它不用碰内核 不装插件就没有压缩，而且不回退内置（第 10 节）
保留条数可以按团队习惯调（keepRecentMessages），不需要改内核配置语义 插件的资源打包错了（文件没进 jar、编码不对）就会让整功能不可用， 而且只在启动期或第一次 /compact 时才暴露 （Jellyfish-Plugins/jellyfish-plugin-compact/src/test/java/zcd/jellyfish/plugin/compact/SummaryPromptTest.java:15-16）
插件拿不到消息正文、不能发起调用、没有否决权——三条边界意味着一个坏插件 最多把摘要写差，不能丢数据、不能多花钱 插件崩掉时内核只会 WARN 跳过它 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/compact/ConversationCompactor.java:624-632）， 剩下的情况就是「没有可用指令」→ 整功能不可用
将来要写「自动压缩时更保守一些」这类策略，trigger 已经在请求里，不必改 api 想要「只压某几条」「按内容改范围」这类需求，插件这条路走不通—— 那属于机制，得改内核 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/CompactionStrategy.java:12-18）
设计依据：为什么宁可「功能缺席」也不做内置兜底？

一个内置兜底听起来更安全，但它会带来两个更麻烦的后果。 一是两套行为：装插件时用插件的措辞，没装时用内置的，那么「我到底在用哪套提示词」 就得靠回忆部署环境来回答，而摘要质量的差异本来就难以察觉。 二是把决定藏进内核：一旦内置兜底存在，内核就重新拥有了「压成什么样」的决定权， 前面那条机制/决定的边界也就名存实亡。

代价是被显式承认的：isAvailable() 为 false 就是功能缺席 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/compact/ConversationCompactor.java:202-205）， 而健康检查判 WARN 而不是 DOWN——因为「没装压缩插件」是合法配置， 长会话会因机械裁剪丢信息，但对话本身完全可用 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/compact/CompactionHealthIndicator.java:16-17）。

12. 本页坑点小结

session-file 与 compact 的坑
  • 关闭 ≠ 删除：close() 故意先落最后一次快照，文件会留着； 只有 /delete 才会让插件删文件。
  • restore() 早于插件 bootstrap 会静默恢复 0 个会话： extensions.bindings(...) 为空时循环一次都不进，没有报错。 凡走扩展点的能力都必须等插件启动（11 页 D7）。
  • 关停时 flushAll() 必须早于 pluginManager.close()， 否则 Ctrl+C 丢当前回合。
  • 插件配置段里的 ~ 不会由内核展开，插件自己展开；不展开会在工作目录建一个 名为 ~ 的目录。
  • 落盘目录默认在 ~/.jellyfish/sessions（主目录），不在项目目录； 它和工具输出目录 ~/.jellyfish/tool-outputs 不是一个地方（见 08 页）。
  • 会话标识会被拼进文件路径，所以 requireSafeFileName 拒绝 /、\ 与 ..——这些标识可能来自插件读回的 JSON，也就是外部输入 （Jellyfish-Plugins/jellyfish-plugin-session-file/src/main/java/zcd/jellyfish/plugin/sessionfile/SessionStore.java:257-264）。
  • 写失败上抛，git 失败只 WARN：两者的数据后果不同，不可能是同一个失败等级。
  • 强杀在途 git 可能留下 .git/index.lock，之后每次提交都告警； 删掉即可恢复，会话文件不受影响。
  • 临时文件是固定名 <id>.json.tmp：它不会被当会话读回来， 但崩溃残留需要自己清（插件不扫它）。
  • 600 权限挡不住同步盘与备份副本；把会话目录放进同步盘等于把完整对话上传。
  • 没装压缩插件不是「回退内置」而是功能缺席：自动压缩静默让路只播一次告警， /compact 直接报错，健康检查降 WARN。
  • 摘要指令缺占位符只告警不失败：内核对超长摘要仍有本地截断兜底，但模型会少一条自我约束 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/compact/ConversationCompactor.java:566-581）。
  • keepRecentMessages = 0 是合法值（一条原文都不留）， 与「没配」（缺省回落内核配置）是两件事。
  • 插件的扩展条目随会话文件一起落盘，受 64 条 / 64 KiB / key 256 字符三条上限约束。

关键结论

  1. 两个插件都只应答、不改状态：它们拿不到 SessionManager， 因此故障范围被限制在「存/取」与「摘要措辞」之内。这是「能力全在插件」这条主线的具体形态。
  2. 持久化的关键词是「宁可丢当前回合，不可留半截文件」：一文件一会话、 内容没变不写、临时文件 + NOFOLLOW_LINKS + 改名收 600 + ATOMIC_MOVE。 git 只是附加层，它失败不影响会话正确性。
  3. 恢复与删除的失败语义与落盘相反，且都是有意为之： 恢复「尽力而为」（坏文件跳过、不阻断启动），落盘与删除「不可丢」（失败上抛、宁可保留内存会话）。
  4. CompactionStrategy 只有三个字段，其中 null 与具体值是两种不同表态； 内核逐字段按优先级取第一，并且自己再钳制一遍—— 插件写出荒谬的值不该让压缩失控。
  5. 摘要提示词是插件 jar 里的资源文件（summary-prompt.md）， 这既是「换措辞不用改内核」的收益，也是「打包错了就整功能不可用」的代价； 健康检查因此把 compaction 降为 WARN，让这件事在运行期看得见。
