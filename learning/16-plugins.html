16 PF4J 插件化架构 重点

「工具即能力、能力全在插件」这条主线怎么落地的。这一页的扩展点清单可以直接当参考手册用。

学习目标

  • 说清 PF4J 的生命周期如何映射到 JellyfishPlugin.start/stop，以及启动失败时怎么回滚；
  • 拿到 28 个扩展点的完整对照表（api 类 → 内核消费点）；
  • 解释「无编译期依赖」靠什么实现，以及类加载冲突的表现与检测方式；
  • 知道 plugins.roots 的扫描顺序与路径来源；
  • 说清 /reload 的判定算法（Map.equals 整段比较），以及哪些变更必须重启进程；
  • 理解插件配置下发的层级与「安全边界键只认全局级」的原因。

「上下文每次 start 现造」这个细节很关键：它意味着插件重启后拿到的是新的 PluginContext，从而重启即读到新配置，不需要额外的刷新逻辑。

三个失败处理

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginManager.java:176-204
PluginState safeStart(String pluginId) {
    try { return startPlugin(pluginId); }
    catch (RuntimeException | LinkageError e) {
        LOG.error("插件启动失败: {}", pluginId, e);
        rollback(pluginId, e);
        return PluginState.FAILED;
    }
}

private void rollback(String pluginId, Throwable cause) {
    try { stopPlugin(pluginId); }
    catch (RuntimeException | LinkageError e) {
        LOG.warn("插件启动失败后的回滚停止也失败: {}", pluginId, e);
    } finally { contexts.release(pluginId); }
    markFailed(pluginId, cause);
}

回收注册的顺序有个反直觉但正确的细节：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/PluginContextFactory.java:193-209
public int release(String pluginId) {
    if (pluginId != null) {
        ContextLifecycle lifecycle = lifecycles.remove(pluginId);
        if (lifecycle != null) {
            lifecycle.close();
        }
        // 与注册同一条存活边界、同一时刻：插件停止后，它在途排队的动作再也无人排空，
        // 留在队列里只会镀成一个永不兑现的 QUEUED
        actions.dropByOwner(pluginId);
        // 与注册、动作队列同一条存活边界、同一时刻。顺序上必须先清空贡献：外壳随后可能收到一条
        // PluginStateChangedEvent 触发的失效重拉，那时该 owner 的贡献应当已经不在信箱里了
        shellIngress.reset(pluginId);
    }
    int removed = registry.removeAllUnder(pluginId, PluginOwnerNamespace.SEPARATOR);
    LOG.info("已回收插件注册: pluginId={} registrations={}", pluginId, removed);
    return removed;
}

源码注释比「先失效、再回收」这类概括更具体，逐条读能把顺序的理由讲清：

  • 为什么要清动作队列：「插件停止后，它在途排队的动作再也无人排空，留在队列里只会镀成一个永不兑现的 QUEUED」—— 留着它们不会报错，只会让面板上一直挂着一个假的「待执行」。
  • 为什么「先清贡献、再清注册」：「外壳随后可能收到一条 PluginStateChangedEvent 触发的失效重拉， 那时该 owner 的贡献应当已经不在信箱里了」。顺序反了，外壳会重拉到已死插件的贡献。
  • 为什么整体要早于 removeAllUnder：先关闸门（生命周期失效）、再清场（回收注册）， 中间不留窗口期——否则插件还能在窗口里注册新东西，而那些东西永远不会被回收。
  • 最后那行 LOG.info 把回收数量打出来：排查「插件停了但注册还在」时，这是第一手证据。
设计依据：注册窗口是「插件存活期」而不是「start() 期间」

JellyfishPlugin.java:11-16 明确写了这个语义：插件在 stop() 之前随时可以注册， 不必挤在 start() 里。这支持了「插件起一个后台线程，随后陆续注册工具」这类玩法。

代价是插件作者要自己负责生命周期：有注册线程的插件必须在 stop() 里先停掉那个线程， 否则线程可能在 release 之后继续注册，撞上 fail-closed 抛异常。 还有一条不太显眼但重要的：start() 抛错时 PF4J 不保证会调用 stop()， 所以插件在 start() 里自己申请的资源（文件句柄、线程、连接）必须在自己的 catch 里释放。

设计依据：为什么唯独 ShellContribution 不是 Request？

看第 25 行：其他扩展点都是 *Request，走 ExtensionRegistry 的「请求 → 处理器 → 返回值」模型。 ShellContribution 不一样——它是推而不是拉：插件主动 present() 一段内容，内核把它放进 ShellIngress 信箱，由三个外壳各自取件 （TUI 走 UiCache、Server 走 SseContributionListener、core 走 ShellStreams）。

为什么它要特殊？因为「外壳正在渲染 / 正在发 SSE」这件事与插件的调用栈无关。 如果做成同步 Request，插件就得在一个「外壳可以接受内容」的时机被调用—— 而那个时机内核自己都不知道。信件箱模型（有界、满了丢最新）把一个时序问题变成了一个队列问题。 容量 64，满即丢最新（ShellIngress.java:75）。

两个边界，一条判据

ExtensionRegistryEventChannel
同步 / 异步同步异步
能否丢弃不可丢（调用方要等返回值）可丢（通知而已）
失败后果功能缺陷（工具没执行 / 权限没判）少一条通知（界面晚刷新一次）
典型内容工具调用、权限判定、提示词贡献、命令回合进度、插件状态、配置告警、UI 失效
共用同一个 TypeRegistry（见 03 页的「同一实例」约束）

判据是「能否丢弃」，而不是「有没有返回值」——这条是 AGENTS.md 里反复强调的， 也是初学者最容易搞错的地方：一个「发出去了就不关心结果」的通知事件，即使它带着数据，也应该走异步通道。

3. 「无编译期依赖」是怎么做到的

这句话有三层含义，缺一层就不成立：

层机制位置
1. 插件依赖 provided 插件 pom 把 jellyfish-api（和 pf4j）标成 provided， 打包时不带进来；shade 的 includes 也排除 api / pf4j / slf4j Jellyfish-Plugins/jellyfish-plugin-node/pom.xml:22-31, 88、jellyfish-plugin-todo/pom.xml:22-31, 84
2. 运行时护栏 PluginClasspathGuard 只拦两个前缀：zcd/jellyfish/api/、org/pf4j/。 在 JellyfishPluginDescriptorFinder.find() 里调用， 只记 loadError 不抛异常（避免一个坏插件整批失败） PluginClasspathGuard.java:29-32, 47-60、JellyfishPluginDescriptorFinder.java:53-57
3. 类加载隔离 沿用 PF4J 默认的 PluginClassLoader，parent = 内核类加载器。 全仓没有覆写 createPluginLoader / classLoadingStrategy PF4JPluginManager.java、PluginClasspathGuard.java:16-21
坑点：插件自带 jellyfish-api 会导致「静默不启动」

PF4J 的插件类加载器默认是子优先（PDA）：插件自己的 jar 里若有 PluginContext 这个类， 它会先加载自己那份，导致类型同一性被破坏——插件眼里的 PluginContext 与内核的类型不是同一个，于是出现莫名的 ClassCastException、 「PluginContext 有两份」这类症状。

最麻烦的地方在于：护栏只记 loadError 不抛异常，所以表现是「插件静默不启动」， 而不是一条明确的报错。排查方式：把日志级别降到 WARN / DEBUG，搜 PluginClasspathGuard。 修法是插件 pom 里把这两个依赖改成 provided。

实例化的两个约束

  • 插件类必须实现 JellyfishPlugin，并且有公开无参构造器（JellyfishPluginFactory.java:44, 73-88）；
  • plugin.id 不能含 ::（JellyfishPluginDescriptorFinder.java:71-97）—— 那个分隔符留给了「子单元 owner」的概念（pluginId::unit）。 这也是 release() 里 registry.removeAllUnder(pluginId, SEPARATOR) 能按前缀一次清干净的原理。

5. /reload：只重启配置段变了的插件

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:133-147
for (Map.Entry<String, Map<String, Object>> entry : after.entrySet()) {
    if (!Objects.equals(before.get(entry.getKey()), entry.getValue())) {
        changed.add(entry.getKey());
    }
}
for (String pluginId : before.keySet()) {
    if (!after.containsKey(pluginId)) {
        changed.add(pluginId);
    }
}

判定算法朴素到极致：整段 Map.equals 比较，不是逐字段 diff。 两个循环覆盖了「新增 / 内容变化」与「消失」两种情形。

设计依据：为什么用整段比较而不是逐字段 diff？

因为插件看不到自己的字段级语义。一个插件可能这样写： if (config.get("mode").equals("x")) { 用 A 方案 } else { 用 B 方案 }。 如果内核只告诉它「mode 这个字段变了」，插件还是得自己判断整体状态； 而如果内核做逐字段 diff，就要理解每个字段的依赖关系——那是不可能的。

整段比较的语义更简单也更可靠：「这一段配置的可见内容变了，就重启这个插件」。 代价是「改一个无关字段也会重启插件」，但这个代价很小（重启一次 stop+start）， 而错误地「不重启」会导致插件按旧配置运行——后者难查得多。

注：既然 Map.equals 就能判等，说明配置段必须是有序且无副作用的数据， 这也解释了为什么插件配置用 Map<String, Object> 而不是任意对象。

坑点：重载失败不回滚

ConfigReloader.java:48 明确：重载是单向的，失败原样上抛， 内存状态与磁盘文件会不一致。所以改配置前先备份， 出现「配置改回去了但行为还是新的」时重启进程是最快的解法。

还有一个顺序陷阱：PluginRuntimeConfig.refresh 必须早于 bootstrap() （AgentHarness.java:208-209），否则插件会按空配置启动—— 现象是「插件装了、也启动了，但什么配置都没生效」。

设计依据：为什么「收紧安全边界的键」要单独留一份全局值？

因为项目级配置是可以被一个 git clone 的目录改写的（02 页）。 如果这类键接受项目级覆盖，那么克隆一个仓库就等于让对方能放宽你本地插件的安全边界—— 比如把「提示里内联文件内容的上限」调大，或者扩大允许读取的目录范围。

所以设计上把这些键单独留底（globalConfigurations）， 项目级写了也不生效。这是一个很细的层次：「可配置」与「可被谁配置」是两个不同的问题。

7. 插件驱动子代理

Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java:501-503 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/PluginContextImpl.java:216-219

插件通过 PluginContext.delegations() 拿到 SubAgentPort。 有个刻意的细节：这个入口不做 requireAlive 检查—— 因为准入判定由内核（SubAgentLauncher 的额度 / 深度 / 不得提权）负责， 插件上下文这一层不需要重复把关。两次把关不仅冗余，还会让「为什么被拒」的理由来源变得不明确。

它和 task 工具走同一条路径：SubAgentDelegationAdapter → SubAgentLauncher （SubAgentDelegationAdapter.java:32, 48）。装配在 di/PluginModule.java:104-108 与 PluginContextFactory.java:146-165。

8. 三块没被扩展点表覆盖的机制

扩展点表回答「插件能接哪」，但不回答「接上去之后内核靠什么保证一致性」。 这三块是支撑性机制，也是读源码时最容易跳过、出问题时最难查的部分。

8.1 TypeRegistry：键到底是什么、覆盖怎么还原

前面说「类型即地址」——但真到了表里，键并不是类型本身：

它记的历史 bug 类注释描述了一个曾经的真实缺陷：缓存命中之后新注册「永远不可见」，现象是「装过插件之后，某个内置命令就再也没了」 TypeRegistry.java:42, 74
设计依据：为什么覆盖要「压链」而不是「替换」？

因为插件是可以卸载的，卸载后必须回到原状。 如果就地替换，被替换掉的原注册项就丢了——插件一停，那个工具或命令就永久消失， 只能重启进程恢复。压链保留了完整历史：链尾一走，下一层自动显形。

这也解释了「跨 owner 重名为什么不报错」：它是一种受支持的、可回退的覆盖， 而不是配置错误。这是插件生态能长起来的前提——你想替换内核自带的某个命令，不需要改内核。 反过来说，DUPLICATE_HANDLER 只在同一层内冲突时抛，那才是真的写错了。

8.2 ActionQueue：插件唯一能「推动内核」的通道

前面所有扩展点都是「内核问插件」或「插件往里注册」。但插件有时需要反向： 主动让内核做一件事——插一条消息、压缩一次、切个模型、开个分支。 这条反向通道是 PluginAction + ActionQueue + ActionDispatcher。

DeliverAs：两种插入点的差别是可观察的

Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/action/DeliverAs.java:11-17（逐字引文，两行是原文的列表项）
两个取值的差别是**可观察的插入点**，不是措辞：
    · STEER     插在一轮工具批次**之后、下一次模型调用之前**，
    · FOLLOW_UP  插在模型**本来要收敛那一刻**，让它不收敛、继续跑一轮——

落到代码上：ActionDispatcher.drainTurnBoundary 取边界档（压缩 / 切模型 / 分支 / 重建清单 / STEER 消息）， 返回注入条数；drainConvergence 取收敛档（FOLLOW_UP）， 返回 >0 就意味着「不收敛」——这正是 04 页里 if (actionDispatcher.drainConvergence(...)) { continue; } 那一行的含义。 单条动作失败不连坐（execute :134），按 Kind 分派（run :156）。

设计依据：为什么「推动内核」要走队列，而不是让插件直接调服务？

因为插件的调用栈是同步的、可能很深的（权限拦截 → 工具执行 → 插件代码）。 如果在那个位置直接调 SessionManager 去插消息，会立刻破坏两条纪律： 「会话变更只在确定的回合位置发生」与「不在插件调用栈里改内核状态」。

队列把「我想让内核做 X」变成一条待执行的意图，真正的执行时机由内核在回合边界决定。 这也解释了 DeliverAs 为什么是枚举而不是两个方法： 它是「何时执行」的声明，属于数据而非行为——插件的职责是说清意图，不是决定时机。

类注释 :12-17 解释了「为什么不内联降级」：
  刻意不做「降级为调用线程内联执行」……
  内联降级会把订阅者拖回 ReAct 调用线程
设计依据：这条注释值一整节

事件通道满了，最「顺手」的处理是降级为在调用线程上直接执行订阅者—— 很多框架就是这么做的（各种 CallerRunsPolicy 的变体），看起来事件不会丢。

但这个项目明确拒绝了它，理由是「内联降级会把订阅者拖回 ReAct 调用线程」。 也就是说：一个本应异步处理的通知，会在事件风暴时跑到 react 线程上执行—— 而 react 池只有 8 条，且审批 / 提问就在这些线程上等待（04 页）。 结果会是「事件压力」转化为「回合卡顿」，而因果链在现象上完全看不出来。

两条路对比：丢事件 → 少一条通知，有计数、有告警、可诊断； 内联执行 → 界面卡住，没人知道为什么。 选择「可见的丢弃」而不是「隐蔽的降级」，是这个项目里最一致的一条成本观。 想知道丢了多少，读 EventChannelStats 的六个 LongAdder（:20-35）—— 它们正是 13 页里那六个 eventChannel.* 指标的数据源。

9. 本页坑点小结

插件相关的坑
  • 插件自带 jellyfish-api / pf4j → 类型同一性破坏，现象是莫名 ClassCastException； 护栏只记 loadError，表现为「静默不启动」，必须看 WARN 日志。
  • plugin.id 含 :: 被拒——分隔符留给子单元 owner。
  • plugin.class 缺失 → 会回退成 org.pf4j.Plugin 默认值，报错信息极具误导性 （JellyfishPluginDescriptorFinder.java:40-51：只有存在且非空时才校验）。
  • 注册窗口是「存活期」不是「start() 内」，但 stop() 之后注册会当场抛错； 有注册线程的插件必须自己在 stop() 里先停线程。
  • start() 抛错时 PF4J 不保证调用 stop()， 插件在 start() 里申请的资源要自己释放。
  • "enabled": [] = 一个都不启用；而 /reload 会清空运行期开关。
  • PluginRuntimeConfig.refresh 必须早于 bootstrap()， 否则插件按空配置启动。
  • 子上下文复用父的 ContextLifecycle（PluginContextImpl.java:51-52 的注释、:230 的 subContext()）， 回收按 pluginId::* 前缀一并清掉。
  • 插件作者写 PluginContextImpl 子类时的陷阱：覆写 create*() 时字段尚未赋值， statusProvider 不能写在字段初始化器里（JellyfishPluginManager.java:31-32 的说明、:63-67 的字段）。
  • 换了 jar 必须重启进程，/reload 只管配置与名单。

关键结论

  1. 插件化的核心机制是「类型即地址 + 两个方向不同的边界」：同步的 ExtensionRegistry（不可丢）与异步的 EventChannel（可丢），判据是「能否丢弃」。
  2. 「无编译期依赖」靠三层共同保证：插件侧 provided、运行期 PluginClasspathGuard 护栏、类加载器 parent 指向内核。少任何一层都会出现类型同一性问题。
  3. 插件故障一律 fail-closed：start() 失败转 FAILED 并回收注册；stop() 之后任何注册当场失败。 这让「插件坏了」不会变成「权限悄悄放宽了」。
  4. /reload 用整段 Map.equals 判定变化，语义是「这一段的可见内容变了就重启插件」—— 宁可多重启，不可漏重启。
  5. 「可配置」与「可被谁配置」是两件事：收紧安全边界的键只认全局级，因为项目级配置来自不可信目录。
