09 配置体系

一份配置从磁盘到「这一轮用哪个模型」要经过几道手？本页把 02 页 分散讲过的五份文件、插值、告警、信任闸串成一条完整链路，并补上「谁在什么时候读」 与「/reload 按什么顺序改」这两块内部机制。

学习目标

  • 说清四类配置（应用级 / 供应商与模型 / agent 定义 / 插件）各自的文件、根类与顶层结构；
  • 解释双源路径的优先级、三种合并粒度的判据来源，以及 config.json 为什么不参与双源；
  • 拿到「路径 → 文本 → JSON 树 → 类型对象」的读取链路，知道缺省值、:- 与类型不符各在哪层处理；
  • 理解 ${VAR} 缺失为什么是整份加载失败，未知字段为什么不能静默丢弃；
  • 说清项目级信任闸的信任单位、三种授予方式与「未信任时跳过 + 告警」的具体路径；
  • 拿到 refresh() 的发布方式与 /reload 的固定顺序，知道哪一步必须在插件之后；
  • 知道 provider / model / agent 三级解析的回落链与失败语义。

1. 四类配置：一个文件一个根类

类别文件（缺省位置）根类顶层结构
应用级 classpath:config.json，本仓库在 Jellyfish/jellyfish-cli/src/main/resources/config.json AppConfig processName + 四段：model / agent / jellyfish / plugins
供应商与模型 ~/.jellyfish/models.json、./.jellyfish/models.json ModelSettings defaultProvider / defaultModel / providers（provider 名 → Provider）
agent 定义 ~/.jellyfish/agents.json、./.jellyfish/agents.json AgentSettings agents（key 即 agentId）；刻意没有 defaultAgent
插件 jellyfish.json 的 plugins 段；扫描目录在 config.json PluginsSettings enabled / disabled / configurations（插件标识 → 自由映射）
（同文件其余段） jellyfish.json JellyfishSettings plugins / react / permission / subAgent / ask

命名约定是「类名 ↔ 文件名一一对应」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ModelSettings.java:14）， 所以看到一个 XxxSettings 就知道去翻哪份 json。四条容易记错的边界：

  • 插件这一类横跨两份文件——「去哪找插件 jar」是 config.json 的 plugins.roots， 「加载后怎么用」是 jellyfish.json 的 plugins 段；分工理由见 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/PluginPaths.java:13-19。
  • jellyfish.json 承载「除模型与 agent 之外的一切」：一个根类只装自己那份文件的内容 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/JellyfishSettings.java:13）。
  • provider 名与 agentId 都由 map 的 key 决定，条目内不重复声明，合并时再用 key 回填 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:460-467、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:483）。
  • 系统默认 agent 不可配置：它来自 classpath:default-agent.json，不走双源， refresh() 每轮重读一次——「是随构件发布的一份常量定义，会话创建时恒绑它」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:322）。
Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/AppConfig.java:68-77（应用级的全部字段）
    public AppConfig(@JsonProperty("processName") String processName,

缺省值在构造器里给：缺段得到的是「空路径对象 / 空列表对象」而不是 null， 于是下游只需判「路径是否为空串」，不必到处判空。

设计依据：插件扫描目录为什么不在 jellyfish.json？

「内核去哪找能力」与「内核去哪找配置」是同一类部署事实，放同一处才不用两处找。更实际的理由是安全： config.json 在 classpath 里、不参与双源合并，项目级目录改不了它；扫描目录一旦可被项目级改写， 一个 git clone 下来的仓库就能把「去哪加载插件 jar」指向别处，那个目录里的代码会以完整内核权限运行。

2. 双源路径：优先级与合并方向

三类双源配置（models / agents / jellyfish）的路径由 config.json 给出， 每段是一对 {globalPath, projectPath}；这个类型只描述路径、不做合并 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigPaths.java:7， 字段在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigPaths.java:15-18）。 合并方向固定为「先全局、后项目」，项目级是覆盖方； 某层路径为空串 = 该层未配置，对合并的贡献是 null。

绝对路径 + SHA-256 指纹"} GATE -->|"LOAD"| RD GATE -->|"UNTRUSTED"| WARN["跳过 + ConfigWarningEvent"] GATE -->|"ABSENT"| RD G --> RD["SettingsReader.read()：路径 → 原始文本"] RD --> LOADER["ConfigLoader.read()：比对未知字段"] LOADER --> BIND["SettingsBinder.bind()：解析树 → 替换 ${VAR} → 绑定类型"] BIND --> OBJ["ModelSettings / AgentSettings / JellyfishSettings"] WARN --> MERGE OBJ --> MERGE["合并器：段级 / 对象级 / 列表级"] MERGE --> SNAP["RuntimeSnapshot：volatile 单点发布"] SNAP --> USE["ModelManager / AgentManager / PluginRuntimeConfig / RunScheduler"]

三种合并粒度，判据来源不同，混起来最容易配错。调度的唯一入口是 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:519-525 的 mergeJellyfishSettings，它把五段各自交给一个专门的合并函数：

粒度适用判据
对象级（整对象覆盖） 同名 provider / agent / 插件配置段；react / permission / subAgent / ask 段 「项目级有没有值 / 这一段有没有被声明」——声明标记字段在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/JellyfishSettings.java:46-58， 赋值在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/JellyfishSettings.java:84-88， 取值方法在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/JellyfishSettings.java:173-217
列表级（声明即整体替换，含清空） plugins.enabled / plugins.disabled 「这个名单字段被写了吗」；写 [] = 本层一个都不要，判据 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/PluginsSettings.java:148-150
不合并 plugins.roots、processName 只有一处写它，天然一份真相 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:692-703）
Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:443-451（模型段：对象级覆盖 + 标量非空覆盖）
    private static ModelSettings mergeModelSettings(ModelSettings global, ModelSettings project) {
        Map<String, Provider> providers = new LinkedHashMap<>();
        putProviders(providers, global);
        // 同名 provider 整对象替换：项目级覆盖全局级，顺序保留全局级原有位置
        putProviders(providers, project);
        String defaultProvider = override(project, global, ModelSettings::getDefaultProvider);
        String defaultModel = override(project, global, ModelSettings::getDefaultModel);
        return new ModelSettings(defaultProvider, defaultModel, providers);
    }

两个细节：用 LinkedHashMap 且只 put，于是同名覆盖时保留全局级原有位置， 界面上的 provider 列表不会因为改一处而重排；标量走 override（项目级非空白才覆盖，javadoc 在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:724）， 与对象级的判据不是同一套。

坑点：项目级只改一处，却把全局级整段顶掉

现象：项目级文件只写了别的段，全局级的 ask.timeoutSeconds = 0 却回退成缺省的 120 秒。 根因：段落合并的判据必须是「这一段写没写」，不能是「取到的段非空」——构造器会把缺失的段填成缺省对象 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/JellyfishSettings.java:79-83）， 所以「段为空」永远不成立，旧写法 project != null ? project : global 于是永远走左支； 现在改按段声明标记判断（见上表第 1 行的行号）。 规避：把项目级的每一段当成「我全权接管」——同名 provider / agent / 插件段要么写全，要么别写。

3. 读取链路：Reader → Loader → Binder

从路径字符串到配置对象只有三个组件，串起来的是 ConfigLoader：读取职责集中在它一处， 配置类保持纯数据。它的 read 是整个体系的唯一漏斗。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigLoader.java:76-86
    public <T> T read(String path, Class<T> type, Consumer<String> unknownFieldReport) {
        Objects.requireNonNull(unknownFieldReport, "unknownFieldReport must not be null");
        if (StringUtils.isBlank(path)) {
            return null;
        }
        String json = settingsReader.read(path);
        for (String field : ObjectMapperWrapper.unknownFields(json, type)) {
            unknownFieldReport.accept(field);
        }
        return settingsBinder.bind(json, type, path);
    }

三步各自的边界：路径为空直接返回 null（那是「未配置」的正常表达，由合并器解释成「这一层没有」）； 未知字段比对在绑定之前（它只要 JSON 原文与目标类型，与插值无关）； 绑定与插值失败都抛异常，不在这里降级成 null。

SettingsReader 只做「路径 → 文本」，环境变量替换留给绑定器；唯一例外是行首 ~ 的展开， 因为那是文件系统语义而非内容加工 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsReader.java:19-24）。 本地文件那条路径上有一个刻意的取舍：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsReader.java:72-83（不预检存在性）
        Path filePath = Paths.get(HomePaths.expand(path));
        if (Files.isDirectory(filePath)) {
            throw new JellyfishException("settings path is a directory: " + path);
        }
        try {
            return new String(Files.readAllBytes(filePath), StandardCharsets.UTF_8);
        } catch (NoSuchFileException e) {
            return null;
        } catch (IOException e) {
            throw new JellyfishException("failed to read settings file: " + path, e);
        }
    }

不做 Files.exists 预检，直接读并捕获 NoSuchFileException，避免「检查后文件消失」的竞态 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsReader.java:64-65）。 文件不存在返回 null，不是错误；路径指向目录才是错误。

绑定层的规则（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:75-85）： JSON 文本为空或解析成 null 时返回 null；否则先 readTree 成树、 替换字符串值里的占位符、再 treeToValue 绑到目标类型。 类型不符在这里报错——readTree 与 treeToValue 都把 Jackson 异常包成 JellyfishException （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ObjectMapperWrapper.java:127-131、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ObjectMapperWrapper.java:143-147）， 因此现象是「整份配置加载失败」，而不是「那一个字段用了缺省值」。

4. ${VAR} 插值与未知字段

密钥不落盘，用 ${VAR} 引用环境变量。三种写法在类注释里列全了 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:27-32）： ${VAR} 必需、${VAR:-默认值} 可选、\${VAR} 转义。 替换只作用于字符串值，不动 JSON 的 key，所以实现是「先解析成树、再在树上替换」而不是对文本做正则 （理由在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:22-25）。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:136-149（替换循环：转义 / 空表达式 / 真正解析）
            String token = matcher.group();
            if (token.startsWith("\\")) {
                matcher.appendReplacement(buffer, Matcher.quoteReplacement(token.substring(1)));
                continue;
            }
            String expression = matcher.group(1);
            if (expression.isEmpty()) {
                matcher.appendReplacement(buffer, Matcher.quoteReplacement(token));
                continue;
            }
            matcher.appendReplacement(buffer, Matcher.quoteReplacement(resolve(expression, source)));
        }
        matcher.appendTail(buffer);
        return buffer.toString();

resolve 决定「必需还是可选」：先找 :-，取不到环境变量时可选分支返回默认值， 必需分支抛 JellyfishException，消息以 environment variable is not set: 开头， 并在末尾附上变量名与来源文件 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsBinder.java:160-173）。 带上来源是因为同一个变量名可能在多份配置里出现。

坑点：缺一个 ${VAR}，整份配置都加载不了

现象：进程起不来，报 environment variable is not set: XXX，退 3。 根因：异常从 resolve 经 ConfigLoader.read （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigLoader.java:76-86） 一路向上抛，没有局部降级。 规避：一律写 ${VAR:-默认值}；注意变量存在但为空串时不走默认值（与 shell 语义一致）。 这是刻意选的失败模式——配置错误降级成「部分生效」，最后会变成「配了但没生效」这种更难查的 bug。

未知字段走的是相反方向的宽容策略：绑定层关掉 FAIL_ON_UNKNOWN_PROPERTIES （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ObjectMapperWrapper.java:43）， 由 unknownFields （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ObjectMapperWrapper.java:172， 动机在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ObjectMapperWrapper.java:154） 事后比对字段名，ConfigLoader.read 把它们回调出去， RuntimeConfig.read 对每个未知字段发一条告警 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:416-423）。 数值越界是第三种口径：SettingsGuard 只做区间把关， null 表示「没配」既不告警也不算错，只有「配了但非法」才回退缺省并记一条告警 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/SettingsGuard.java:38-47 是 positiveOrDefault 的形态，另有非负整数、非负长整数、百分比三种口径）。

告警怎么让人看到？配置层只发事件，由 ConfigWarningReporter 订阅后打一行 WARN （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigWarningReporter.java:96-97）， 渲染时先过 ControlChars.singleLine——来源是文件路径、消息里带用户的 JSON 字段名， 一个带换行或终端控制符的键名能在终端里伪造诊断行 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigWarningReporter.java:111-118、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigWarningReporter.java:19-25）。

注意：告警默认只是一行 stderr

订阅者必须在 eventChannel.start() 之后、配置加载之前启动 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/AgentHarness.java:196-198）， 否则配置加载期的告警（正是绝大多数）订阅不上。而日志默认级别是 WARN、只写 stderr （Jellyfish/jellyfish-cli/src/main/resources/log4j2.xml:12、 Jellyfish/jellyfish-cli/src/main/resources/log4j2.xml:22-29）， 所以「字段名拼错，配了不生效」在界面上没有任何提示。

5. 项目级信任闸：信任单位是路径 + 指纹

项目级配置（./.jellyfish/*.json）按进程当前目录解析，内容随「在哪个仓库里启动」变化， 而它能改 provider 的 baseUrl / apiKey、新增 agent、改落盘目录—— 这些内容会因为一次 git clone / git pull 凭空出现在工作目录里，所以默认不加载。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:118-138（裁决：classpath 特例 → 存在性 → 已信任？→ 未信任）
    public Decision decide(String declaredPath) {
        if (isClasspathResource(declaredPath)) {
            // classpath 资源属于运行构件本身（由打包与部署的人决定），不是「当前目录里可能被塞进来的东西」，
            // 因此与全局级同性质，不在本闸的管辖范围内。这条不能少：Spring 接入方正是用它把配置放进
            // 自己的 src/main/resources，从而彻底不必依赖工作目录
            return Decision.LOAD;
        }
        Path file = absolute(declaredPath);
        if (file == null || !Files.isRegularFile(file)) {
            // 文件不存在：读出来也是 null，不必打扰用户，也不必告警
            return Decision.ABSENT;
        }
        if (trustEverything || sessionGranted.contains(file.toString())) {
            return Decision.LOAD;
        }
        String recorded = persisted.get(file.toString());
        if (recorded != null && recorded.equals(fingerprint(file))) {
            return Decision.LOAD;
        }
        return Decision.UNTRUSTED;
    }

信任的单位是「文件绝对路径 + 内容指纹」，不是目录 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:46-49）： 只记目录的话，一次 git pull 带来的新配置会静默沿用旧的信任，等于把「信任一次」变成 「永远信任这个仓库，无论它以后写什么」。指纹是 SHA-256 内容摘要 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:229）， 内容一变即失效。

  • 三种授予方式 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:50-58）： trustEverythingInThisRun()（对应 --trust-project-config，本次进程、不落盘， Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:155）、 trustForSession(path)（只让一个文件本次生效， Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:145）、 grant(path)（按当前内容记进信任仓库，缺省路径 ~/.jellyfish/trusted-project-configs.json 定义在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:74， 写入在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:178）。
  • 失败一律按「不信任」处理：仓库读不出来、内容非法、算不出指纹，都只会让配置不加载并记一条日志—— 闸门只会关得更紧，不会因为异常而自己打开 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ProjectConfigTrust.java:60-63）。
  • 未信任时的行为是「跳过 + 告警」，不失败： RuntimeConfig.readTrustedProject 只在 LOAD 时读文件，UNTRUSTED 时发一条 ConfigWarningEvent（源为 project-config），ABSENT 什么都不做 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:249-258、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:267-271）。
  • 外壳靠 AppConfig 才知道「有哪些项目级文件存在」：CLI 的确认流程遍历三段的 getProjectPath()，对每一段调 decide，收齐 UNTRUSTED 的路径再决定问不问 （Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/ProjectConfigTrustConsent.java:98-118， 交互入口在 Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:92）。
排查第一步：确认项目级到底有没有被加载

在项目里写了 ./.jellyfish/*.json 却不生效，先看 stderr 有没有 项目级配置未加载（未被信任）。有的话，加 --trust-project-config 重启即可本次生效； 想持久就在 TUI 确认框里选「加载并记住」（写进信任仓库）。classpath: 形式的项目级路径不受本闸管辖。

6. RuntimeConfig 与 refresh()

RuntimeConfig 是配置的唯一门面。它的构造器不读配置 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:52-56）， 真正加载由装配根在事件总线启动之后调用 refresh() 触发；配置内容整体重建后， 通过单个 volatile 字段一次性发布一份不可变快照 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:44-46， 字段在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:77， 初值是 RuntimeSnapshot.empty()）。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:112-122（唯一的加载入口）
    public synchronized void refresh() {
        AgentDefinition systemAgent = builtinAgentLoader.load();
        ModelSettings mergedModel = load(appConfig.getModel(), ModelSettings.class, RuntimeConfig::mergeModelSettings);
        AgentSettings mergedAgents = loadAgentSettings();
        JellyfishSettings mergedJellyfish = load(appConfig.getJellyfish(), JellyfishSettings.class,
                RuntimeConfig::mergeJellyfishSettings);
        notifyIfInvalid(mergedModel);
        notifyIfInvalid(mergedJellyfish);
        this.snapshot = RuntimeSnapshot.of(mergedModel, mergedAgents, mergedJellyfish,
                pluginRootsOf(appConfig.getPlugins()), systemAgent);
    }

注意顺序：先发告警、再换快照，告警因此一定与刚读到的内容对应； agent 段单独走 loadAgentSettings()，因为它还要在合并之前按各自源目录补上 {agentId}.md 提示词——提示词的基准目录由「这份配置写在哪个文件」决定，合并之后就丢了来源信息 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:125）。 快照本身是纯数据：RuntimeSnapshot.of 从模型段派生出 provider 列表，并对集合做不可变包装 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeSnapshot.java:83-93， 空快照在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeSnapshot.java:67）。

谁在什么时候读它？启动期由 bootstrap() 调一次 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/AgentHarness.java:204）， /reload 时由 ModelManager.refresh(true) 间接再调一次 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/ModelManager.java:115-121）。 读方的口径分两类：索引类（provider / agent / 插件段）在刷新时快照一次； 参数类刻意「每轮现读不缓存」——权限段、子代理段、提问段每次用到时取 （取值入口在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:355、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:366、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:377， 理由写在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:351、 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:373 的 javadoc 里）， 于是改完无需重启即可生效，与「不持有全局当前态」同口径。

坑点：有些配置在 refresh() 之前就被读了

现象：subAgent 的并发 / 墙钟预算明明配了，实际仍按缺省跑，而且没有任何日志。 根因：RunScheduler 由装配根构造 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:302）， 而那一步早于 AgentHarness.bootstrap() 里的 refresh() （装配顺序的注释在 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:248）， 此时快照还是空的，装配期读到的一切「配置」都只是缺省值。 规避：这类参数已改到「用到的那一刻」读——墙钟每次起看门狗时取 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/runtime/RunScheduler.java:206）， 并发 / 等待区在第一次提交时建一次（改它们仍需重启）。改动记录见 Jellyfish/CHANGELOG.md:356-361，口径见 Jellyfish/docs/constraints.md:555。

7. /reload：一条有顺序的路径

热更新不是「再调一次 refresh()」，而是一串有依赖关系的动作，编排在 ConfigReloader 里—— 每一处依赖关系都不该由调用点记住。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:101-120（顺序即语义）
    public synchronized ReloadOutcome reload() {
        long startedAt = System.currentTimeMillis();
        Map<String, Map<String, Object>> before = pluginRuntimeConfig.getPluginConfigurations();

        modelManager.refresh(true);
        agentManager.refresh(false);
        pluginRuntimeConfig.refresh(runtimeConfig.getPluginRoots(), runtimeConfig.getPluginsSettings());

        Set<String> reconfigured = changedPluginIds(before,
                pluginRuntimeConfig.getPluginConfigurations());
        PluginReloadReport pluginReport = pluginManager.reload(reconfigured);
        // 必须在插件重启之后：重启的插件是换了配置段的新实例，早问一次会拿到旧实例的目录，
        // 而目录要到下一次重载才修正
        modelManager.refreshCatalogs();

        long duration = System.currentTimeMillis() - startedAt;
        publishReloaded(pluginReport, duration);
        LOG.info("配置已重载: durationMillis={} reconfiguredPlugins={}", duration, reconfigured);
        return new ReloadOutcome(duration, pluginReport);
    }

五条顺序理由 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:27 起）： ① 只有 modelManager.refresh(true) 会重读文件，它同时清掉按旧 apiKey / baseUrl 建好的 LLM 客户端缓存； ② 紧接着的 agentManager.refresh(false) 复用同一份新快照——若也传 true， 文件会被读第二遍，并在两遍之间产生「模型用了新配置、agent 还在用旧配置」的窗口； ③ pluginRuntimeConfig.refresh 必须早于插件运行时重载，因为后者读的正是它那份快照； ④ 插件侧只重启「配置段真的变了」的插件，判据是整段相等比较而不是逐字段 diff—— 插件配置段是自由映射，内核不知道哪些键有语义 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:123）； ⑤ refreshCatalogs() 是最后一步，仍在广播事件之前。

flowchart LR R["/reload（SystemCommands）"] --> C1["ConfigReloader.reload()：synchronized 单飞"] C1 --> S1["① modelManager.refresh(true)：重读文件 + 清客户端缓存"] S1 --> S2["② agentManager.refresh(false)：复用同一份快照"] S2 --> S3["③ pluginRuntimeConfig.refresh：插件段快照"] S3 --> S4["④ 比对插件配置段：整段相等"] S4 --> S5["⑤ pluginManager.reload：只重启变了的插件"] S5 --> S6["⑥ modelManager.refreshCatalogs()：必须在插件之后"] S6 --> S7["⑦ 广播 ConfigReloadedEvent"]

另外两条纪律：整个重载 synchronized 单飞（并发重载会让插件被停两次、启动两次， 而配置重载本就是低频的人类动作）；重载单向、不回滚——配置的真相在文件里， 回滚只会制造「内存里的配置与文件不一致」这种更难排查的状态，失败原样上抛给命令层 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:39）。 命令层同步等结果、失败原样告知 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/command/SystemCommands.java:698-706）。 config.json 不参与热更新，新增 / 删除插件 jar 仍需重启进程（见 16 页）。

8. provider / model / agent 三级解析

配置读完了，最后一个问题是「这一轮用哪个模型」。它由 SessionModelResolver 一处回答， 回落链固定三级：会话显式选定（/model 改过）→ 该 agent 的偏好模型（agents.json 的 model 字段）→ 全局默认（models.json 的 defaultProvider / defaultModel）。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/SessionModelResolver.java:64-72（前两级：会话态 → agent/默认）
    public ResolvedModel resolve(Session session) {
        Objects.requireNonNull(session, "session must not be null");
        String provider = session.getProvider();
        String model = session.getModel();
        if (!StringUtils.isAnyBlank(provider, model)) {
            return modelManager.resolve(provider, model);
        }
        return resolveByAgentOrDefault(session.getAgentId());
    }

resolveByAgentOrDefault （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/SessionModelResolver.java:84-91） 先查 agent 的偏好模型，有就走 ModelManager.resolveReference，否则走 ModelManager.resolveDefault——后者的兜底规则是四条：默认 provider 与 model 都为空时取 「第一个有模型的 provider 的第一个模型」；只给 model 时取「第一个提供它的 provider」；只给 provider 时取它的第一个模型； 两者都有则精确匹配 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/ModelManager.java:342-357）。

  • 与配置的对应关系：第 ① 级是会话运行态（不写任何配置文件），第 ② 级来自 agents.json，第 ③ 级来自 models.json。
  • 解析不到时上抛，不返回 null：三个来源都是「用户明确表达过的意图」， 一个都落不到实处时静默降级会让问题在更远的地方以更难懂的形式出现 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/SessionModelResolver.java:31）。
  • 子代理会话自然落到第 ② 级：子会话的 provider / model 都是 null， 但 agentId 指向被委派的 agent；刻意不继承父会话的模型 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/SessionModelResolver.java:29）。
  • 这条链原本被写了两遍（ReActLooper 与 ConversationCompactor），靠注释声明「刻意保持镜像」； 收成一个类是因为压缩必须按同一个模型的窗口裁剪 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/SessionModelResolver.java:22-23）。

解析链与采样参数的交互见 05 页第 9 节。这里只强调它与配置体系的关系： 配置只提供「默认值」和「agent 偏好」，真正的选择权在会话上，而 ModelManager 不持有任何全局「当前模型」状态 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/ModelManager.java:33-34）， 注册 / 刷新阶段也不校验配置是否可用——配置问题只发告警，解析不到时由 resolve / resolveDefault 抛异常，即「真正用到时才报错」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/model/ModelManager.java:45-48）。

9. AppConfig 的两个职责

AppConfig 是纯数据类，不承担任何文件读取 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/AppConfig.java:30）； 「如何得到 AppConfig」放在最外层的 composition root，由 ConfigLoader 创建 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:16-23）， 最常用的那一份来源用 ConfigModule.loadDefault() 拿 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:44-46）。 固定路径常量是 classpath:config.json （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/AppConfig.java:38）。 它只有两个职责：

职责一：声明各配置段的双源路径（三个 ConfigPaths 字段）。这是「两级间接」的根： config.json 只说文件在哪，另三份才装内容，所以「改配置」永远是改另外三份。

职责二：声明插件扫描目录，并且它是外壳判断「有哪些项目级文件存在」的依据——CLI 的信任确认流程 不理解配置语义，只按 AppConfig 给出的三段项目级路径去问 ProjectConfigTrust （Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/ProjectConfigTrustConsent.java:98-118）。 扫描目录在快照里被转成路径列表：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:692-703（展开 ~ 并丢弃空白条目，不合并）
    private static List<Path> pluginRootsOf(PluginPaths plugins) {
        if (plugins == null || plugins.getRoots().isEmpty()) {
            return Collections.emptyList();
        }
        List<Path> roots = new ArrayList<>(plugins.getRoots().size());
        for (String root : plugins.getRoots()) {
            if (root != null && !root.trim().isEmpty()) {
                roots.add(Paths.get(HomePaths.expand(root.trim())));
            }
        }
        return roots.isEmpty() ? Collections.<Path>emptyList() : Collections.unmodifiableList(roots);
    }

「路径已配置但读不到内容」不会静默：RuntimeConfig.read 在绑定结果为 null 且路径非空白时 发一条「配置段文件缺失或为空，将按未配置处理」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:416-423）。 而扫描目录为空列表时，由插件运行时回退到默认目录 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:395 的 javadoc）。

设计依据：为什么 AppConfig 由组件构建者注入，而不是模块里的 @Provides？

「配置来源」是部署事实，两种装法（CLI 读 classpath、嵌入方自己给）都应当由各自的调用方决定， 所以模块里不再固定从 classpath 读，只留下 loadDefault() 这个静态方法给「只想要缺省行为」的调用方 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:21-42）。 与此配套的一条硬要求：ProjectConfigTrust 必须唯一——授予信任发生在启动期， 读取发生在 refresh()，两边看到的必须是同一份状态，否则「确认了却不生效」 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:51）。

10. 本页坑点小结

坑点 1：项目级配置默认不加载

现象：./.jellyfish/*.json 写了完全不生效，只有一行告警。 根因：未信任即 UNTRUSTED → 跳过 + 告警 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/RuntimeConfig.java:249-258）， 信任键是「绝对路径 + SHA-256 指纹」，内容一变即失效。 规避：本次生效用 --trust-project-config，持久用 TUI 确认框选「记住」； 参见 25 页 A5。

坑点 2：整对象覆盖，以及「只认全局级」的键

现象：项目级只改了别的段，全局级配好的整段却回退成缺省值。 根因：段落覆盖按声明标记判断，而 provider / agent / 插件段是整对象替换（见第 2 节）。 规避：项目级要写就写全。另外有一类「收紧安全边界」的插件配置键只能认全局级： 插件用 globalConfiguration() 读那一份、用 configScope() 判来源 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java:111-142）， 因为项目级一旦写了该插件段，configuration() 给的就是仓库里那份。

坑点 3：/reload 失败不回滚

现象：reload 报错之后，内存状态与磁盘文件不一致，「改回去了但行为还是新的」。 根因：重载单向，失败原样上抛 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ConfigReloader.java:39）。 规避：改配置前备份，出现不一致时重启进程最快。

坑点 4：三条「配了却没生效」的不同来源

现象：字段名拼错、数值非法、${VAR} 缺失，表现各不相同。 根因：三者走三条通道——未知字段发 ConfigWarningEvent、非法数值回退缺省并告警、 缺失的环境变量直接抛异常导致整份加载失败。 规避：先看 stderr（默认 WARN），再对照 02 页的配置章节。 总口径是：配置错误要么立刻可见、要么不生效，没有「悄悄用了别的东西」这第三种结果。

关键结论

  1. 配置是两级间接：config.json 只说文件在哪，另三份才装内容；因此它天然属于「不该随便改」的一层，也不参与双源与热更新。
  2. 读路径是单向漏斗：SettingsReader（路径 → 文本）→ ConfigLoader（比对未知字段）→ SettingsBinder（树上插值 + 绑定）→ 根类对象；失败一律上抛，不在此降级。
  3. 合并有三种粒度（段级声明标记 / 对象级整替换 / 列表级声明即替换），判据全部来自配置类的「声明标记」，不是「内容非空」。
  4. 项目级默认不加载，信任单位是「绝对路径 + SHA-256 指纹」，未信任只跳过并告警、不失败；classpath: 不受管辖。
  5. 配置整体重建后由单个 volatile 快照一次发布，读方看不到「新 provider + 旧默认值」的中间态；参数类配置刻意每轮现读，索引类在刷新时定型。
  6. /reload 的顺序本身就是语义，其中 refreshCatalogs() 必须在插件重启之后；装配期读到的配置永远是缺省值，改它们要重启。
