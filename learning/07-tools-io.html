07 工具系统与输入输出

工具是这套内核里唯一的「能力单元」，而它只有两个方向：进来的是参数，出去的是文本。 这一页讲清这两个方向的契约、执行链与全部限额，并把输出侧的落盘 / 信封 / 老化接到同一条线上。

学习目标

  • 说清一个工具由哪三样东西组成（名片、处理器、注册入口），以及为什么它们必须一起落表；
  • 拿到工具清单的完整算法：注册表 → 工具激活判定 → 过滤器 → 排序键，并知道清单为什么按会话冻结；
  • 解释跨边界值类型为什么必须是 api 侧快照，以及「恰好一个可见构造器」这条规矩的来由与豁免范围；
  • 说清 ToolExecutor 的七步执行链，特别是两个改写点为什么只能待在那两个位置；
  • 理解输入侧的三层防线：内核不校验 schema、参数改写链、工具自己的 max_bytes；
  • 拿到输出侧的完整体系：8 字段信封、两条截断入口、_partial / _path 的真实含义；
  • 知道失败怎么表达（terminal 的 FAILED / REJECTED），以及界面为什么不能去解析回灌文本。

1. 工具的契约：名片与处理器一起落表

一个工具在源码里就是三样东西： 名片（ToolDescriptor）、处理器 （ExtensionHandler<ToolCallRequest, ToolCallResult>）、 注册入口（PluginContext.handle，同键唯一）。 名片里的名字同时是路由键，所以「插件声明了一个工具」和「这个工具能被调用」是同一件事的两面。

名片放在 api 而不是 infra，理由写在类注释里： 插件作者必须能描述自己的工具，否则就没法注册工具。 而参数 schema 只需要 JSON Schema 的 properties 部分——type: object 与 required 由内核在转成厂商请求时自己包上 （Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ToolSchema.java:13-14）。

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/ReadFileTool.java:57-66（read_file 的名片：静态常量，一个实例服务全进程）
    /** 工具名片，无状态因此整个插件共用一个实例。 */
    private static final ToolDescriptor DESCRIPTOR = new ToolDescriptor(
            "read_file",
            "读取文本文件内容。大文件可用 offset 与 limit 分片读取，避免一次读入过多内容。",
            ToolSchema.properties(
                    "path", ToolSchema.string("文件路径，相对路径按进程工作目录解析"),
                    "offset", ToolSchema.integer("起始行号，从 1 开始；缺省从第一行开始"),
                    "limit", ToolSchema.integer("最多读取多少行；缺省读到文件末尾"),
                    "max_bytes", ToolSchema.integer("最多读取多少字节，缺省 " + DEFAULT_MAX_BYTES)),
            Arrays.asList("path"));

注意三个细节。第一，名片是 private static final——工具实例必须无状态， 它在 ReAct 执行线程上被内联调用，同一个实例会被反复使用，甚至可能被不同会话并发调用。 第二，max_bytes 的缺省值直接拼进描述文本（"缺省 " + DEFAULT_MAX_BYTES）： 模型看到的数字与代码里的常量因此不可能不一致。 第三，必填参数只有 path；required 是名片里的一个独立字段，不是 schema 里的 required 数组。

插件侧把「名片 + 处理器」这层绑定收进一个接口，注册就退化成一次遍历。 这样既不会「名字写两遍」，也让工具能声明一件内核需要知道的事实：

Jellyfish-Plugins/jellyfish-plugin-tools/src/main/java/zcd/jellyfish/plugin/tools/PluginTool.java:50-62（工具实例自己声明路径访问性质，并把自己注册进上下文）
    default PathAccess pathAccess() {
        return PathAccess.NONE;
    }

    /**
     * 把自己注册进插件上下文。
     *
     * @param context 插件上下文，不可为 {@code null}
     * @return 注册句柄，插件卸载时由框架统一回收，通常无需自行持有
     */
    default Subscription register(PluginContext context) {
        return context.handle(ToolCallRequest.class, name(), descriptor(), this);
    }

register 的四个实参就是契约本身：请求类型（决定结果类型校验）、路由键 （name()，即名片里的名字）、描述符、处理器。 Context.handle 的语义是同一「请求类型 + 路由键」至多一个 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java:175）， 重复注册当场抛 DUPLICATE_HANDLER——两个插件抢同一个工具名不会「谁后加载谁生效」， 而是启动时就炸掉。工具注册进的是 TypeRegistry， 而 descriptorBindings 与 handler 读的是同一张表的两个投影，因此 工具清单不需要第二份目录，插件下架时描述符随注册一起消失。

设计依据：描述符里没有「是否只读」字段

它曾经有：提供方在名片里自称只读。问题是那个设计让「只读」变成 由被判定的一方自己申报——提供方可以把任意工具塞进任何基于它构建的名单里， 用户没有手段拿出来；MCP 那一侧更极端，「提供方」是不受信的外部进程 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/ToolDescriptor.java:20）。 现在的口径是：只读与否完全由用户配置决定（例如 plan 插件的 readOnlyTools），描述符只回答「这个工具叫什么、怎么用、要什么参数」。

插件实现 JellyfishPlugin.start(context) 时只做一件事：遍历自己的工具清单逐个注册。 注册窗口是插件的整个存活期，框架按 pluginId 批量回收，因此插件不必持有注册句柄、 也不必实现 stop。

2. 工具清单是怎么算出来的

「模型这一轮能看到哪些工具」不是一个静态列表，而是三层作用的结果。先给结论，再逐层看依据：

层作用实现位置失败/缺省时的行为
注册表 全部已注册的名片，按 order + 名称排序 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:79-81 空注册表 → 清单为空
工具激活判定 按会话逐工具问一次「要不要隐藏」 Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:225-257 0 个处理器 → 全可见；处理器抛错 → 保持可见

排序键为什么是「order 升序 + 名称」而不是「order + 注册顺序」？ 因为注册顺序就是插件加载顺序，同序的两项谁先谁后会随加载时机变化； 而名称是内容的一部分。工具清单进的是缓存前缀里一个很靠前的位置（多数厂商把工具定义排在 messages 之前），因此「同序两项换个位置」等于整段请求连同全部历史作废。

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:79-81（清单的唯一排序键）
    private static final Comparator<DescriptorBinding<ToolDescriptor>> TOOL_ORDER =
            Comparator.comparingInt(DescriptorBinding<ToolDescriptor>::getOrder)
                    .thenComparing(binding -> nameOf(binding.getDescriptor()));

然后是激活判定。它的形状是「类型级扩展点 + 取第一个表态者」，与压缩策略、请求调优同一套做法：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:225-257（工具激活判定：失败保持可见、第一个表态者胜出）
    private boolean hidden(Session session, ToolDescriptor descriptor) {
        if (descriptor == null) {
            return false;
        }
        List<HandlerBinding<ToolActivationRequest, ToolActivation>> bindings =
                extensions.bindings(ToolActivationRequest.class, null);
        if (bindings.isEmpty()) {
            return false;
        }
        ToolActivationRequest request = new ToolActivationRequest(session.getSessionId(), session.getAgentId(),
                descriptor);
        for (HandlerBinding<ToolActivationRequest, ToolActivation> binding : bindings) {
            ToolActivation activation;
            try {
                activation = extensions.invoke(binding.getHandler(), request);
            } catch (RuntimeException e) {
                // 失败保持可见：隐藏会让模型「不知道有这个能力」而走进死路，保留只是多几个 token
                LOG.warn("插件 {} 的工具激活判定失败，{} 保持可见：{}",
                        binding.getOwner(), descriptor.getName(), e.getMessage());
                continue;
            }
            if (activation == null || !activation.isDecided()) {
                continue;
            }
            if (activation.isHidden()) {
                LOG.debug("工具已按插件判定隐藏: sessionId={} tool={} owner={} reason={}",
                        session.getSessionId(), descriptor.getName(), binding.getOwner(),
                        activation.getReason());
            }
            return activation.isHidden();
        }
        return false;
    }

「失败保持可见」不是随手选的保守方向：隐藏会让模型「不知道有这个能力」而走进死路， 保留只是多几个 token。代价不对称，所以往便宜的那一侧倒。 另外它只在冻结点求值一次——每轮问一次就等于把「清单逐轮可变」放回来了。

清单按会话冻结

会话首次取清单时拍一份快照，之后这个会话一直用它；注册表的变化只对新会话生效。 实现很短，但它是「单会话内工具清单逐字节不变」这条结构性保证的落点：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:175-185（冻结：命中就复用，未命中就现拍一份）
    private synchronized List<LlmTool> snapshotOf(Session session) {
        if (session == null) {
            return currentOf();
        }
        List<LlmTool> snapshot = snapshots.get(session.getSessionId());
        if (snapshot == null) {
            snapshot = activeOf(session);
            snapshots.put(session.getSessionId(), snapshot);
        }
        return snapshot;
    }

冻结的是未过滤的整份清单，过滤在之后做：同一会话里过滤器可能不同（子代理回合另传一份）， 但它们必须基于同一份底稿，否则「集合有没有变过」又说不清了。 想让已有会话跟上注册表变化只有一个显式入口 ToolCatalog.rebuild(sessionId) （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:158）， 而它一定会换来一次前缀断裂。快照表按访问顺序淘汰，上限 64 个会话 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolCatalog.java:72）。

坑点：清单里没有 ≠ 调用不了，「隐藏」和「禁用」是两件事

现象：某个工具被激活判定隐藏了，但模型如果用别的办法说出这个工具名，调用照样执行。

根因：被隐藏的工具不进这份清单，但仍在注册表里（描述符查得到）， ToolExecutor 直接调用它仍然会执行。 ToolFilter 与工具激活判定都只作用于清单， 执行期的准入仍然由权限判定把关——清单是「建议」，权限是「约束」。

规避：真要禁止调用，写权限策略（PermissionCheckRequest 扩展点）， 不要指望清单过滤。反过来，ToolCatalog.tools() / tools(filter) 这两个实时入口不冻结、也不做激活判定，只适合「现在装了什么」这类诊断，不要拿来拼请求。

3. 跨边界值类型：为什么必须在 api 侧

ToolCallRequest 是内核与插件之间的唯一输入载荷。它的构造期做了三件事，每件都在守一条边界：

Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/ToolCallRequest.java:88-104（构造期即快照：参数只读拷贝，三类「调用期设施」缺省有兜底）
    public ToolCallRequest(String toolName, Map<String, Object> arguments, String sessionId,
                          CancellationToken cancellationToken, ToolOutputSink outputSink,
                          String parentSessionId, String runId, String rootRunId) {
        super(ToolCallResult.class, sessionId);
        if (toolName == null || toolName.trim().isEmpty()) {
            throw new JellyfishException("tool name must not be blank");
        }
        this.toolName = toolName;
        this.arguments = arguments == null
                ? Collections.<String, Object>emptyMap()
                : Collections.unmodifiableMap(new LinkedHashMap<>(arguments));
        this.cancellationToken = cancellationToken == null ? CancellationToken.NONE : cancellationToken;
        this.outputSink = outputSink == null ? ToolOutputSink.NOOP : outputSink;
        this.parentSessionId = parentSessionId;
        this.runId = runId;
        this.rootRunId = rootRunId;
    }

三个要点：

  • 参数是只读拷贝。插件手里那份与内核手里那份从此是两个对象， 插件改不动内核的。这条不是洁癖：参数改写的「当前值」要靠链式传递维持， 任何一处偷偷共享可变映射都会让链式语义失效。
  • 「不参与」有缺省值。取消令牌退化为 NONE、输出通道退化为 NOOP，因此不使用它们的工具（绝大多数）行为与引入之前完全一致。
  • 调用者身份由内核填，插件与模型都碰不到。三个身份字段 （parentSessionId / runId / rootRunId）由内核从 当前执行路径推出，因此「协作键写偏」不可能被诱导发生。

为什么必须是 api 侧的值类型，而不是重用 infra 里的某个类？ 因为插件只依赖 jellyfish-api：跨这条边界的每一个类型都必须是插件能看见的、 且不与内核实现细节耦合的。同一条纪律也解释了 SessionToolCallSnapshot 为什么把参数保留成原始 JSON 文本： 这一层只负责把消息原样带出去再原样带回来，解析是模型调用侧的事； 在这里解析一次、回放时再拼一次，只会引入「序列化不一致」的可能 （Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/SessionToolCallSnapshot.java:5-8）。

「恰好一个可见构造器」这条规矩

快照类型必须恰好一个可见构造器，理由与代码风格无关，而是反序列化： Jackson 的「隐式属性构造器」只在唯一可见构造器时才认， 多一个重载会让整段快照反序列化失败；新增字段只能用新的静态工厂补， 不加兼容构造器（Jellyfish/docs/constraints.md:373-374）。 顺序也不能动：-parameters 是全局编译约定，去掉它同样会让「按参数名反序列化」失准。

注意：ToolCallRequest 是存量的豁免项，不是反例

它带着 4 个可见构造器（8 参 / 5 参 / 3 参 / 2 参），看起来违反了上面的规矩。 约束文档把这一档写得很清楚：api 里早于这条规矩落地的类型 （ToolCallRequest、CommandDescriptor 等）属存量豁免—— 它们都是已发布的公共契约，插件仓库对每一个重载都有调用点，删可见性是破坏性变更， 因此不要为了对齐规矩去删它们；要收敛就先补静态工厂 + 加守护测试。 真正没有豁免的是快照类型，所以写新类型时按「一个可见构造器」来。

4. 执行链：权限 → 路由 → 截断，只有这一个执行点

工具调用有两条发起方：模型（ReAct 循环，参数是 JSON 串）与 用户（输入指令，如 ! 标记，参数已是映射）。 ToolExecutor 把两者收在同一条路径上：只有一个执行点， 执行语义（权限判定、审批、事件埋点、输出捕获、截断落盘、异常转结果文本）因此只有一份实现。

先看链路的头部。这里最容易看漏的是「参数改写之前就把埋点发出去」这件事的顺序：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:174-193（链头：参数改写位次、拒绝短路、埋点顺序）
    private ToolCallResult execute(Session session, CancellationToken cancellation, String toolCallId,
                                   String toolName, Map<String, Object> arguments, ReActListener listener,
                                   ToolArgumentPreRequest.Source source) {
        Objects.requireNonNull(session, "session must not be null");
        ReActListener effective = listener == null ? ReActListener.NOOP : listener;
        String sessionId = session.getSessionId();
        String agentId = session.getAgentId();
        // 第 2 步：参数改写。本类里最不能挪的一处位置，两个理由：
        //   · 必须在权限判定之前，否则审批浮层显示参数 A、真正执行参数 B（TOCTOU）；
        //   · 必须在 onToolCallStarted 之前，否则轨迹行与 --show-tool-args 打出来的是旧参数，
        //     与审批记录、与会话里落库的 toolCalls 不是同一份（四个显示面共用一份文本是既有纪律）
        ToolArgumentDecision decision = transformArguments(agentId, toolName, arguments, source, sessionId);
        Map<String, Object> effectiveArguments = decision.isReplace() ? decision.getArguments() : arguments;
        events.publish(new ToolCallStartedEvent(toolCallId, toolName, sessionId));
        effective.onToolCallStarted(toolCallId, toolName, effectiveArguments);
        if (decision.isDenied()) {
            // 与「权限拒绝」同形：不建捕获通道、不调用工具，但照旧发齐「开始 + 结束」两个埋点，
            // 让外壳与指标看到的是一次配对的失败调用，而不是一条只有结果的孤儿记录
            return rejected(session, toolCallId, toolName, decision.getReason(), effective);
        }

参数改写必须在权限判定之前：否则用户批准的是参数 A、真正执行的是参数 B， 这是一处标准的 TOCTOU。它同样必须在 onToolCallStarted 之前： 轨迹行、--show-tool-args、审批记录、会话里落库的 toolCalls 这四个显示面共用同一份文本，任何一处拿旧参数，排查时就会出现无法对齐的现场。

权限判定与路由在 invokeTool 里，它是「插件只能声明意图、不能自己执行」这条边界的落点： 插件够不到 PermissionManager，而这个方法必然先调它。

为什么要从 ReActLooper 里抽出来

工具调用现在有两条发起方，而执行语义里有权限判定、审批、事件埋点、输出捕获与截断落盘、 异常转文本。复制一份到第二条路径上就等于把这些口径维护两遍，漂移只是时间问题。 抽取的副作用同样重要：ToolExecutor 不做异步、在调用线程上同步执行完整个调用， 因此 ReAct 循环在自己的 react 线程上调、输入指令在自己的执行器线程上调， 两者都不允许在界面线程上直接调。

5.2 参数改写链：三态、链式传递、失败按「不改」

参数改写是类型级扩展点（getRouteKey() 恒为 null）： 它针对的是「一次工具调用」这个整体，不按工具名分槽。 按工具名分槽会让两个插件都想处理同一个工具时撞「同键唯一」，与「横切对所有插件开放」的目标冲突； 需要按工具名分流时，处理器自己看 getToolName()。 链式语义写在调用点的 for 循环里——注册表不参与编排：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:259-289（改写链：每个处理器收到上一个的产出，DENY 立即短路）
    private ToolArgumentDecision transformArguments(String agentId, String toolName, Map<String, Object> arguments,
                                                    ToolArgumentPreRequest.Source source,
                                                    String sessionId) {
        List<ExtensionHandler<ToolArgumentPreRequest, ToolArgumentDecision>> handlers =
                extensions.handlers(ToolArgumentPreRequest.class, null);
        if (handlers.isEmpty()) {
            return ToolArgumentDecision.abstain();
        }
        Map<String, Object> current = arguments;
        boolean replaced = false;
        for (ExtensionHandler<ToolArgumentPreRequest, ToolArgumentDecision> handler : handlers) {
            ToolArgumentDecision decision;
            try {
                decision = extensions.invoke(handler, new ToolArgumentPreRequest(agentId, toolName, current,
                        source, sessionId));
            } catch (RuntimeException e) {
                LOG.warn("参数改写处理器抛错，按不改处理: sessionId={} tool={}", sessionId, toolName, e);
                continue;
            }
            if (decision == null) {
                continue;
            }
            if (decision.isDenied()) {
                return decision;
            }
            if (decision.isReplace()) {
                current = decision.getArguments();
                replaced = true;
            }
        }
        return replaced ? ToolArgumentDecision.replace(current) : ToolArgumentDecision.abstain();

ToolArgumentDecision 是三态而不是「返回一份新参数」：只有「返回新参数」一种表达能力时， 插件无法区分「我看过了、不改」与「我没看」——而这两者对后面的处理器是不同的。 三态是 ABSTAIN（不改，把当前值交给下一个）、REPLACE（替换后继续）、 DENY（短路，直接产出一条失败结果）。 没有「放行」这一态：本扩展点表达不了权限结论，改写之后照旧要过权限判定。

坑点：内核不校验工具参数，REPLACE 的形状由插件自己保证

现象：插件把参数替换成结构不对的东西，工具里抛出的是一句莫名其妙的参数错误。

根因：内核没有工具的参数 schema——schema 在名片里，是给模型看的， 内核只负责把它转成厂商请求。因此改写后的参数不重新校验， 这个扩展点刻意不做校验也不做兜底。

规避：写 REPLACE 的插件自己保证形状合法；而工具侧要把「不受信任的输入」 当成前提来读——ToolArguments 就是干这个的（见 5.3）。 另外这个扩展点也不是绕过权限的旁路：插件本来就是同进程的任意代码， 安全边界是「装不装这个插件」，不是「参数在第几步被看」。

    private String limitText(String sessionId, String toolCallId, String toolName, String text) {
        int maxChars = maxChars();
        if (text.length() <= maxChars) {
            return text;
        }
        String path = store.store(sessionId, toolCallId, toolName, text, false);
        String hint = ToolOutputEnvelope.hint(path);
        int totalLines = countLines(text);
        int budget = ToolOutputEnvelope.previewBudget(maxChars, toolName, path, hint);
        String rendered = "";
        for (int round = 0; round < ToolOutputEnvelope.MAX_FIT_ROUNDS; round++) {
            ToolOutputEnvelope envelope = ToolOutputEnvelope.text(toolName, text.length(), totalLines, path, hint,
                    ToolOutputPreview.text(text, budget));
            rendered = envelope.render();
            int excess = rendered.length() - maxChars;
            if (excess <= 0 || budget <= 1) {
                return rendered;
            }
            // 估算与转义长度有出入（例如正文里全是换行与引号）时按实际差额再收缩一次
            budget = Math.max(1, budget - excess - ToolOutputEnvelope.FIT_SLACK);
        }
        return rendered;
    }

信封自身的长度（工具名 + 路径 + 指引）参与计算，渲染后仍超预算就按实际差额再收缩一次， 因此「回灌文本不超过 maxToolOutputChars」在 Unicode 转义、超长路径等情况下依然成立。 截断策略是头 30% + 尾 70% （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/tooloutput/ToolOutputPreview.java:27）： 工具输出的结论往往在末尾（编译错误、测试失败、退出信息），只留头会让模型看到「一切正常的前 90%」。 结构化结果走另一条路：数组保留「前缀 + 哨兵元素 + 后缀」，对象只留能装下的前缀字段， 因此回灌的仍是合法 JSON。哨兵元素绝不能省——它是结构化路径上唯一能让「中间被省略」可见的东西。

为什么要那个纳秒时间戳？因为 toolCallId 与工具名都来自进程外部（模型 / 适配器）， 内核只保证「空 id 换 UUID」，不保证跨回合唯一；清洗还会把非法字符折叠成同一个名字， 超长时还会截断。于是两次不同的调用可能得到同一个文件名，而写入是带替换的原子改名—— 先写的那份被覆盖，可它那条信封里的 _path 还在，指向的却已经是别人的内容 （比「文件不存在」更难察觉）。清理只按文件数与总字节从最旧删起， 并且永不删刚落盘的那个：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/tooloutput/ToolOutputStore.java:498-534（清理只报告不阻断；保护刚落盘的文件）
    private static void cleanup(Path directory, Path justWritten, int keepFiles, long maxBytes) {
        if (keepFiles <= 0 && maxBytes <= 0) {
            return;
        }
        List<Path> files = listFiles(directory);
        if (files.size() <= 1) {
            return;
        }
        files.sort(Comparator.comparingLong(ToolOutputStore::lastModified));
        long totalBytes = 0L;
        for (Path file : files) {
            totalBytes += size(file);
        }
        int remaining = files.size();
        for (Path file : files) {
            if (remaining <= 1) {
                break;
            }
            boolean tooMany = keepFiles > 0 && remaining > keepFiles;
            boolean tooLarge = maxBytes > 0 && totalBytes > maxBytes;
            if (!tooMany && !tooLarge) {
                break;
            }
            // 保护刚落盘的那个：清理不该把本轮信封里写着路径的内容删掉；
            // 不靠 mtime 判断，是因为同一毫秒内写多个文件时它分不出先后
            if (file.equals(justWritten)) {
                continue;
            }
            long bytes = size(file);
            try {
                Files.deleteIfExists(file);
                remaining--;
                totalBytes -= bytes;
            } catch (IOException e) {
                LOG.warn("清理旧工具结果失败: file={} reason={}", file, e.toString());
            }
        }
注意：_path 只在保留窗口内有效，而且路径是 ~ 缩写

落盘目录有清理上限（缺省每会话 200 个文件 / 50 MiB），从最旧开始删， 因此 _path 只在保留窗口内有效——这是「不做引用计数式保留」的直接代价， 刻意接受（Jellyfish/docs/constraints.md:745）。 另外主目录内的落盘路径记成 ~ 形式（HomePaths.abbreviate）： 绝对路径会把真实用户名与主目录结构带进上下文（并随会话落盘、被导出、发给上游模型）， 而它对「回查这个文件」这件事没有任何用处。文件工具认 ~ （ToolPaths.expandHome），因此回灌的路径仍可直接交给 read_file。

6.5 为什么不做「让 LLM 自动摘要大输出」

这条路在别的系统里常见：输出太大就再调一次模型，让它吐一份摘要。 本内核刻意没有这么做，理由是从这条链路的形状推出来的 （源码里没有一条注释在讨论这个备选方案）：

  • 它会把一次工具调用变成一次额外的模型调用。截断发生在 ToolExecutor 的链尾，而这一步是同步、纯本地、零 token 成本的 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/tooloutput/ToolOutputLimiter.java:85）。 加一条模型调用就把「工具执行」的延迟与费用变成了不可预测的量，而且它发生在每一个大输出上。
  • 摘要也要模型读全文。几兆输出本身就可能超上下文，摘要调用要么先截断（那摘要只覆盖一部分）， 要么分块多次调用（那费用再乘一个量级）。相对之下，落盘 + 路径回查把 「要不要看全文、看哪一段」的决定权留给模型，按需付费。
  • 它会掩盖「被截断」这个事实。摘要是一段自然语言，没有 _truncated 与 _total_chars 这种机器可判定的字段；模型很容易把摘要当成完整内容。
  • 已有的两层已经够了：头尾预览保证「结论那一行」在，落盘与 _hint 保证 「完整内容找得回来」，_partial 保证「文件里也不全」这件事说得出口。
设计依据：落盘上限保护的是磁盘，不是 CPU

对「无界输出」的工具（典型是 yes），超出上限的部分 仍会继续被读取并丢弃（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ToolOutputSettings.java:25）—— 写到上限为止（不是整个放弃），并置信封字段 _partial （Jellyfish/docs/constraints.md:732）。 同样地，不做「输出体量杀命令」：无界输出由超时兜住。 因此「输出被截断」与「命令被停下来」是两件独立的事， 运行期的实时输出是旁路（可丢、抛错被隔离、绝不能阻塞）。

7. 结果老化：只把落盘过的信封换成 stub

机械裁剪只在总量超预算时才动手，而工具结果的特点是「单条就很大、还很早」。 几十轮前读过的一个大文件会一直占着上下文，直到某一次装不下被整组丢掉， 那时连「曾经读过它、内容在哪」都不知道了。老化就是提前把旧大结果换成一行 stub， 换回「最近几轮仍然完整 + 更早的仍可回查」。

它的实现里最值得看的是筛选条件——只动信封，非信封结果一个不动：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolResultAger.java:273-291（老化：role 必须是 tool，且正文必须能解析成信封）
    private static List<LlmMessage> stub(List<LlmMessage> messages, int frontier, AgingStrategy strategy) {
        List<LlmMessage> aged = null;
        for (int index = 0; index < frontier; index++) {
            LlmMessage message = messages.get(index);
            if (!LlmMessage.ROLE_TOOL.equals(message.getRole())) {
                continue;
            }
            ToolOutputEnvelope envelope = ToolOutputEnvelope.parse(message.getContent());
            if (envelope == null) {
                continue;
            }
            if (aged == null) {
                aged = new ArrayList<LlmMessage>(messages);
            }
            aged.set(index, new LlmMessage(message.getRole(), envelope.stub(stubTemplateOf(strategy, envelope)),
                    message.getToolCallId(), message.getName(), null));
        }
        return aged == null ? messages : Collections.unmodifiableList(aged);
    }

ToolOutputEnvelope.parse 对非信封内容一律返回 null（它不抛异常： 调用点都在「组装一轮请求」的路径上，一条普通工具结果不是信封是常态，抛异常会把常态做成故障， Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/tooloutput/ToolOutputEnvelope.java:281）。 于是小结果永远不会被老化：它们本来就不占地方，换成 stub 只会让模型无端失忆。

另外两条口径值得记住。第一，只改本次请求：返回的是新的消息列表， Session 里存的历史一条不动——屏幕投影、持久化、/resume 看到的仍是完整结果。 第二，两种触发口径由 react.cache.agingPercent 选择： 0 表示按「距尾部多少条消息」逐轮重算边界，> 0 表示按上下文用量水位、 且一个压缩周期内只推进一次（边界冻住），keepRecentMessages 写 0 是总开关 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolResultAger.java:108-127）。 水位口径为什么必须冻住？因为厂商的 prompt 缓存是前缀匹配， 「删掉前缀中的 N 个 token」省下的是 N，却让它后面的 M 个 token 全部从 0.1× 变回 1×—— 只要 M > 0.11N 就是净亏。

注意：缺省口径在两处写得不一样，以配置类为准

ToolResultAger 的类注释写的是「0（缺省）——按距尾部的条数」 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolResultAger.java:38-42）， 而配置里的缺省值是 70： ReactCacheSettings.DEFAULT_AGING_PERCENT = 70 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ReactCacheSettings.java:47）。 两处口径不一致，以配置类为准（真实生效的是水位口径）， 类注释那句看起来是上一版口径的残留。

8. 失败的表达：字段读成败，文案给人看

工具结果对模型是一段文本（首行写结论、正文写内容），而对界面与审计是数据。 没有约定时，界面只能去「解析那一行文本」才能知道命令成没成——把展示绑死在文案格式上， 改一个措辞就会让警告标记消失。约定只有三个键：

键回答的问题界面表现
exitCode它成没成（整数，非零即失败）红色警示后缀
terminal它成没成（终止原因，非 COMPLETED 即失败）红色警示后缀
summary刚才那一行轨迹到底是什么事工具名后面那句普通说明

判据只有一个实现，放在 api 里而不是各界面各写一遍，否则「超时算不算失败」迟早会有两种答案：

Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/ToolMetadata.java:123-137（界面渲染警告标记的唯一判据；宽容处理坏数据）
    public static boolean failed(Map<String, Object> metadata) {
        if (metadata == null || metadata.isEmpty()) {
            return false;
        }
        Object exitCode = metadata.get(KEY_EXIT_CODE);
        if (exitCode instanceof Number && ((Number) exitCode).intValue() != 0) {
            return true;
        }
        Object terminal = metadata.get(KEY_TERMINAL);
        if (terminal instanceof String) {
            String value = ((String) terminal).trim();
            return !value.isEmpty() && !TERMINAL_COMPLETED.equals(value);
        }
        return false;
    }

内核自己写入 terminal 的只有两处，而这两处的区分是刻意的： FAILED 是「工具自己没成」，REJECTED 是「工具压根没跑」。 后者发生在参数改写链上某个插件在权限判定之前就拦下这次调用时：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:363-374（参数被插件拒绝：与权限拒绝同形而不同因）

                                    ReActListener listener) {
        String sessionId = session.getSessionId();
        String text = "插件拒绝参数：" + messageOf(reason);
        String output = outputLimiter.limit(sessionId, toolCallId, toolName, text);
        Map<String, Object> metadata = new LinkedHashMap<String, Object>();

    }

两者对 failed() 都返回真（界面都警示），但对排查是两件事： 「工具失败率」这类指标因此不必去解析文案。另外它不进权限审计—— 权限事件回答的是「权限系统放没放行」，而这里是「插件拒了这条参数」， 合进同一个事件会让权限计数失真。

工具抛异常时，内核补的是 FAILED，并且把工具自己写的那一句原因 （仅限 JellyfishException 的消息首行）放进 summary：

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/tool/ToolExecutor.java:480-491（异常路径：只有约定的异常类型才贡献摘要文本）

        Map<String, Object> metadata = new LinkedHashMap<String, Object>();
        // 取值与 McpToolCaller 保持一致：这是对外约定的可见字符串，不自创词

为什么只取 JellyfishException？因为那条消息是工具自己写给 「为什么没成」的一句话（例如「文件不存在: /x/y」），内核只是转述； 其余 RuntimeException（NPE / 类型错）是实现细节，不该出现在界面上。 也因此，工具应当把消息写成一句给人看的原因，不要放密钥或大段内容。 落会话的是 metadata 而不是 success： 只有元数据才能在重投影 / -resume 之后仍显示标记。

坑点：前端绝不要解析 output 的首行文案

现象：改了一句工具的输出措辞，界面上的失败标记就消失了；或者换个工具就判断错。

根因：首行文案是给模型读的（它要据此判断这次调用成没成、要不要换个参数重来）， 而 metadata 才是给人与审计读的结构化事实。 两者受众不同，措辞可以各按各的需要写，不必强求一致。

规避：界面读 ToolMetadata.failed(metadata) 与 summaryOf(metadata)； summary 是展示用的事实，不得参与任何逻辑分支。 外壳永远不该按工具名分支，而是按「有没有摘要」——它只做「有就接在工具名后面」这一个判断。

9. 坑点清单

9.1 绝不对可能是 JSON 的输出做 substring

现象：对工具输出做 substring 封顶之后，模型拿到的 JSON 解析失败。 根因：脚本类工具返回的是 Map/List，序列化后是一段 JSON， 从中间切开会得到非法 JSON；而很多工具的输出恰好就是 JSON。 规避：用结构化的信封，而不是字符串截断—— 字符串结果按行做头尾切分，结构化结果按 JSON 子树截断， 两者都保证「回灌的仍是合法 JSON 信封」 （Jellyfish/docs/constraints.md:735-739，详版见 25 页 的 D3）。 配套的一条纪律是：output 在结果整形那一步保持原始类型， 不得提前序列化成文本——截断要知道类型才能选对算法。

9.2 四层「上限」口径不同

层管的是位置

9.3 孤儿 tool 结果 / 悬空 toolCalls 会被厂商 400

现象：一次请求失败之后，之后每一次请求都失败。 根因：裁剪 / 取消破坏了 assistant(toolCalls) 与 tool 消息的配对，厂商直接返回 400 （Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/prompt/ToolPairing.java:30-40）。 这正是为什么工具结果不能随便丢：它不是一个孤立的字符串，而是配对结构的一半。 规避：改裁剪或取消逻辑时，第一件要确认的事就是配对没被破坏 （详版见 25 页 的 D5）。

9.4 落盘目录在主目录，不是项目目录

_path 给的是 ~ 缩写，落盘目录缺省是 ~/.jellyfish/tool-outputs （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/config/ToolOutputSettings.java:39）， 因此「换个项目跑就找不到上次的输出」是正常的；交给需要绝对路径的工具时要先展开 （文件工具认 ~，其它工具不认）。 这一档的完整参数表见第 10 页 第 3 节与 25 页 的 D2。

关键结论

  1. 工具的契约是三件套：ToolDescriptor 名片 + 处理器 + Context.handle 注册； 名字即路由键，同键唯一在启动时就暴露冲突，工具因此不需要第二份目录。
  2. 工具清单 = 注册表 − 激活判定隐藏者，再按过滤器收窄，排序键是 order + 名称；整个清单按会话冻结一次， 因为它在缓存前缀里位置很靠前。清单是「建议」，权限才是「约束」。
  3. ToolExecutor 是唯一的执行点，七步顺序不可重排： 参数改写必须在权限判定之前（TOCTOU），结果整形必须在截断之前（否则信封与落盘文件永久分叉）。
  4. 输入侧的三层防线是「内核不校验 schema → 参数改写链 → 工具自我限流」； 输出侧两条截断入口共用一份信封与落盘实现，回灌的永远是 8 字段的规定 JSON。
  5. 成败只看 metadata 里的 terminal / exitCode （唯一判据 ToolMetadata.failed）；文案给人看，字段给机器读，两者不许互相替代。
