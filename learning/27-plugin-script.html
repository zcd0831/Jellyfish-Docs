27 跨语言脚本插件

让 Python / Node 写的插件在内核眼里与 Java 插件同构：这是全项目里跨语言程度最高、也最容易被误解的一块。 本页按源码把「三层架构 → 进程模型 → 线协议 → 扩展点编解码 → 声明式注册 → 事件 → 熔断」读一遍， 并说清每一个设计取舍的代价。

学习目标

  • 说清脚本插件要解决的核心矛盾——扩展点是 Java 接口，而脚本语言不认识它们——以及三层架构怎么把它拆开；
  • 拿到进程模型的确切事实：谁是谁的父进程、worker 怎么起、PID 文件管什么、僵尸与孤儿分别靠什么兜住；
  • 解释线协议的帧格式与那条「宿主单行上限必须严格大于脚本出帧上限」的硬关系，以及违反它的现场表现；
  • 理解 24 个扩展点编解码器的组织方式、类型映射规则与「热路径点」这一执行策略；
  • 知道注册为什么只依赖静态清单，以及 dump_manifest 与严格校验怎样把清单漂移变成启动期错误；
  • 说清熔断、台账、超时与取消这一层稳定性设计各自拒绝计入什么，以及为什么拒绝计入比计入更难；
  • 判断「加一门新语言」的真实成本，并理解为什么选「子进程 + 线协议」而不是嵌 JS 引擎或 JNI。

1. 问题与边界：扩展点在 Java 里，脚本在进程外

内核的扩展边界由三条硬性质定义，全部发生在 JVM 内：插件身份（注册表的 owner）来自 PF4J 描述符； 注册只能在插件存活期内发生（stop() 之后一切注册当场失败）；能力只能从 PluginContext 的几个方法拿到。脚本进程是 JVM 外的东西，既没有 PF4J 身份，也拿不到 PluginContext——那是 JVM 对象， 跨不过进程边界。

Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptBridgePlugin.java:26-45（类注释：为什么必须有一个 JVM 内的代理人）

于是矛盾变成这样一句话：扩展点是 Java 接口，而脚本语言不认识它们。 桥接方案必须同时满足两个看起来冲突的要求——内核侧完全不知道有脚本这回事（脚本与 Java 插件同构）， 脚本侧完全不需要写 Java（用户在 scripts/python/<id>/ 下放一个目录就能变成插件）。 解法是引入一个 JVM 内的代理人：它在 start() 里替脚本调用 handle / contribute / observe / emit， 而处理器背后不是本地代码，是一次进程往返。

能力边界：是一份「能力档」，不是全部扩展点

脚本不是「与 Java 插件同权」。具体支持哪些扩展点写在 jellyfish-script 的资源里，且被单测守着：内核新增扩展点而没有在这里分档，构建会失败。 三段语义不同，不能合并——in 是已打通，planned 是已决定要做但还没做， excluded 是明确不做。

坑点：脚本直接 print 会污染协议流，而且现象离原因很远

现象：某次调用返回了「别人的结果」，或者调用一直等到超时。日志里既没有异常也没有错误码。
根因：输出通道的分工是「stdout 只有协议、stderr 只有日志」。标准输出一旦多出一行， 它就是一行无法解析的协议帧——按设计被宽容丢弃，但如果这一行恰好长得像一条应答，更坏的事会发生： 网关侧有一条 id 检查专门挡这个（见第 12 节）。
规避：Python 侧用 sys.stderr，Node 侧 SDK 与协议都走同步写； 子进程的 fd 1/2 在 fork 后都指向日志管道，网关给每个 worker 的 stdout 加脚本前缀转进内核日志， 因此脚本的日志能看见，只是不能往协议流里写。

3. 进程模型：一个常驻网关 + 每脚本一个 worker

先给结论，六条，全部来自源码：

  1. 脚本侧有两个层级：每门语言一个常驻网关进程（控制面），每个脚本一个 worker 进程（数据面）。 网关只与宿主说话、只做路由，从不 import 任何业务脚本——因此「脚本把网关拖垮」这条路径不存在。
  2. 网关是单线程的，全部并发由一次 select 多路复用解决。Python 侧坚持单线程的 直接理由是 fork 在多线程进程里不安全：只要网关自己不存在线程，「worker 在没有任何线程时被 fork」这条约束就恒真。
  3. worker 由网关 fork（Node 侧是 spawn + 一帧 init）， 子进程不通过命令行接收参数。Node 没有 fork 的内存继承，所以用 init 帧把脚本目录、 入口与清单送过去——这样也不会让清单出现在进程列表里。
  4. 启动是懒的：initialize 之后还没有任何进程；第一次真正调用才抽取网关资源、起进程、下发清单。 因此内核启动不需要解释器、不需要写文件、不占内存。
  5. 进程退出后不自动重启：下一次调用会重新走一遍懒启动。自动重启只会把「脚本一启动就崩」 变成一段安静的无限重启循环，而调用方拿到的是超时——现场离原因更远。
  6. PID 文件只报告、不处置：正常路径上没有任何东西读它。它的全部价值在 「JVM 被 kill -9、网关也一起失联」之后，是唯一还留着的线索。

解读：worker 与网关之间是 socketpair（不是管道），日志走另一根管道。 子进程的 fd 整理在 _child_setup 里：0 指向 /dev/null， 1 / 2 指向日志管道，其余全部 close。 这里有两个非显然之处：一是必须手工关闭继承来的 fd——fork 不执行 exec， FD_CLOEXEC 毫无作用，残留的描述符会让「宿主死了」这件事在 worker 一侧永远等不到 EOF； 二是要摘掉继承来的信号唤醒管道（set_wakeup_fd(-1)），否则 worker 每收到一个信号 （孤儿看门狗的 SIGALRM、网关的 SIGTERM）都会往一个已关闭的 fd 写一次， 往 stderr 吐一段四行的 Exception ignored ...——每两秒一次，恰好把有用的那几行淹没。

def _die_now(script_id, which):
    """收到终止信号：立刻退出，不等主循环。

    **只置一个标志位是不够的**，这一点是实测出来的：脚本可能正卡在自己的代码里

    系统调用。于是主循环永远轮不到，「父进程没了」也永远查不到——现场是
    gateway 早已退出、这个 worker 却要等到用户代码自己醒来才消失（十分钟量级），
    而日志里没有任何一条指向它。

    发出信号的一方（网关：超时隔离 / 空闲自毁 / 关闭 / 拒绝服务）已经判定不需要
    这个 worker 的任何输出，因此这里直接退出；半行协议帧由网关的脏行容忍吃掉。
    """

这段注释里「这一点是实测出来的」是值得照着学的一句：卡住的脚本正是最该被清理的情形（它已经让宿主超时过一次）， 而它恰恰是「只翻标志」方案收不掉的那一种。代价是可能留下半行协议帧——由网关的脏行容忍吃掉，这也是那条 「脏行只丢不失败」的宽容口径为什么是必需的。

设计依据：为什么帧格式是「一行一个 JSON」而不是长度前缀？

脚本语言的调试手段几乎都是「打印一行看看」。长度前缀会让任何一次误打印把后续所有帧错位、恢复无从下手； 行分隔则是「错一行、丢一行、继续」，与解析函数的宽容口径一致。代价是 JSON 里不能有裸换行—— 由 JSON 转义保证，协议层不存在多行帧。与之配套的三条： 脏行返回 null 而不是抛异常（Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/protocol/ScriptProtocol.java:297-326）、 脏行不进任何失败账目（否则「脚本里多打了一行日志」会演变成「工具被隔离」）、 告警要限流（一个循环打印的脚本会把内核日志刷满，让真正的错误淹没其中）。

四个值得单独记住的点：

  • 写帧不阻塞调用线程：子进程的 stdin 是一根有界的管道，网关执行一次 invoke 期间不读 stdin，管道写满时 write 会阻塞到网关回到读循环为止； 那个阻塞发生在 ScriptRpc 进入等待之前，调用超时对它完全无效。 FrameWriter 存在的全部理由就是让「写不进去」退化成「这次调用超时失败」。
  • 超时处置链是「宿主只发指令，杀的动作由网关做」：worker 是网关的子进程， 回收（waitpid）与 PID 表都在网关一侧；宿主越过去杀，就得自己维护一张必然漂移的 PID 表， 而漂移的表现是「某个进程谁也杀不掉」。
  • 每个 worker 同时只有一个在途请求，因此 worker 内部可以完全是同步的， 脚本作者不必考虑并发；代价是同一脚本的并发调用排队，而排队比「脚本里到处是竞态」便宜得多。
  • 截止时间从「派发」起算，而不是「到达」起算：排队等待不是脚本的错， 而超时的语义是「脚本执行太久」。真要排太久的队，前一个请求的超时会把整个 worker 杀掉， 队列里的人也一起拿到明确失败。

备选方案是「反射 + 通用 POJO ↔ JSON 映射」。它被否掉的理由是语义而不是性能： 每个扩展点的结果都有一层不属于「数据搬运」的规则，通用映射表达不了。三个例子： ToolCodec 的 output 必须把节点还原成「字符串就是字符串、对象就是 Map」的形态 （与内核 ReActLooper.serializeOutput 对齐），否则脚本返回结构化数据时会被二次转义； PermissionCodec 遇到的未知取值要报错而不是静默当 ABSTAIN （多写一个字母就让一道本该有人看的调用直接放行）； PromptCodec 的缺省是「本轮没有说话」而不是空字符串。 这些规则各自属于那个扩展点的领域，收在 codec 里，就能整页离线单测。

9. 稳定性：熔断、台账、超时与取消

熔断：拒绝派发，但不摘注册

四个状态：CLOSED（正常）、OPEN（熔断中，冷却后自动转半开）、 HALF_OPEN（放行探测，成功即恢复、失败则重新打开）、PERMANENT （拒绝且不再自动恢复，只能靠 /reload 重建）。admit() 有副作用—— 冷却到期时把自己推进到半开，因为「要不要探测」与「探测什么时候开始」本来就是同一件事。 半开期不限制并发探测数：限制「只放一个」需要排队或计数，代价是把调用线程挂住； 而多放几次探测的代价只是多几次失败，状态由最后到达的那个结果决定，是自纠正的。

设计依据：为什么熔断是「拒绝派发」而不是「摘掉注册」？

注册与进程生命周期解耦（清单驱动、懒启动）是这套设计的核心价值。摘注册会把这个价值丢掉—— 工具会从清单里消失（模型看到的不是「它坏了」，而是「它不存在」）， 而恢复就得走 /reload 重新装配插件。熔断保住的是自动半开恢复： 工具仍然在清单里，模型可能反复调用，但它拿到的是一个明确的、带剩余时间的错误，看到一次就会避开。 拒绝文案因此必须给出「还要等多久」——Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/CircuitBreakingScriptCaller.java:170-179 的 refusalMessage 就是这么写的：「已因连续 N 次失败熔断，将在 M 秒后自动重试」。 一句「脚本不可用」只会让模型换个参数再试一次。

实测的熔断参数（Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/CircuitBreakerSettings.java:21-31）： failuresToOpen = 2（缺省 2 次就开始熔断，因为每一次都很贵——一个完整超时或一次进程重建）、 cooldownSeconds = 60、roundsToPermanent = 3。 三个参数零都有确定含义：0 分别表示「不熔断」「立即重试」「永不转永久」， 因此构建器只拒绝负数、不拒绝零——把零当默认值会让「显式关闭熔断」这条唯一手段失效。

坑点：哪些失败不计入熔断，比哪些计入更重要

现象：网关挂过一次之后，所有脚本还要再等一个冷却期；或者用户按了几次 Esc，某个脚本被熔断冷却了； 或者一个坏脚本看起来「已经好了」。
根因：账记错了。判据收在唯一一个方法里 （Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/CircuitBreakingScriptCaller.java:148-165）， 四类失败明确不计：ScriptConnectionException（L3：整门语言不可用，不是这个脚本的问题； 网关是懒启动的，下次调用会重新拉起来）、错误码 -32001（熔断自己产生的拒绝——记进去会让冷却被自己的拒绝无限延长）、 ScriptCancelledException（取消是用户主权）、ScriptNotHandledException（「不表态」既不是成功也不是失败）。 其余都计：超时、脚本回报的错误、协议错误码，判据是「这次调用没有拿到结果」。
规避：给「不表态」专门一个异常类型，而不是复用 null 或抛通用异常—— 把「这次没去办」与「办砸了」在类型上分开，是这一整套记账能正确的前提。

台账与状态命令：注册是快照，运行态是视图

脚本插件在 Java 侧没有自己的 PF4J 身份（注册全挂在桥接插件命名空间下），因此 /plugins 与插件状态页看不到它们。差一本台账，「我明明写了脚本」就只能靠翻日志判断——而清单漂移是本方案唯一的高危点， 它的可观测性不该依赖日志。于是每个桥接插件自带一条 /<语言> 命令，输出 ScriptLedger.render() 的结果：脚本数、已登记能力数、运行时自述、熔断状态、 事件通道计数、逐脚本注册项、以及逐条列出的启动期问题。

设计依据：为什么台账里「注册」用快照，而「运行态」必须现看？

ScriptLedger 的类注释把这条区分讲得很清楚：注册结果与启动期问题是 start() 那一刻的事实， 不随后续变化；但运行态（进程在不在、哪些脚本被熔断了）必然是活的， 因此这两部分不是存下来的副本，而是转发到运行时去看一眼。 区分方式是：报告「注册了什么」用快照，报告「现在怎么样」用视图——把后者也快照下来， 会得到一份「已经过时的真相」，而它比没有更具误导性。 渲染顺序也有讲究：运行态、熔断、事件各占单独一行，因为注册数与运行态本来就是解耦的 （进程没起，注册照样有效），这正是这套设计最需要被看见的一点。

    public void close(long graceMillis, long killMillis) {
        Process current = process;
        if (current == null) {
            stopped.set(true);
            return;
        }
        if (!stopped.compareAndSet(false, true)) {
            return;
        }
        // 先关 stdin：解释器读到 EOF 就走正常退出路径，比信号温和，
        // 也让「网关正在收信号、worker 来不及回收」的概率最低

            LOG.warn("脚本进程未在 {} ms 内退出，发送终止信号: {}", Long.valueOf(graceMillis), describeCommand());
            current.destroy();
        }
        // 第二段等待用 killMillis 而不是再等一遍 graceMillis：从这一刻起已经进入「动手收尾」，
        // 剩下的每一段等待都该受同一个上限约束（否则最坏情况是 grace + grace + kill，
        // 而那个多出来的 grace 只是把强杀推后）
        if (!awaitExit(killMillis)) {
            LOG.warn("脚本进程未响应终止信号，强杀: {}", describeCommand());
            current.destroyForcibly();
            if (!awaitExit(killMillis)) {
                LOG.error("脚本进程强杀后仍未退出，可能出现残留进程: {}", describeCommand());
            }
        }
    }

超时的处置链有三层，缺一层都收不干净：宿主侧 ScriptGateway.call 捕获 ScriptTimeoutException 后发 kill_worker 指令 （Jellyfish-Plugins/jellyfish-script/src/main/java/zcd/jellyfish/script/ScriptGateway.java:249-267）； 网关侧自己的 _expire 有同一个截止时间做兜底（宿主失联时仍然会清理），失败在途的那一个并保留排队的请求； worker 侧收到 SIGTERM 就立刻 os._exit。两条路径都指向同一个 worker， 而网关那侧的 kill 是幂等的——因此「两边同时动手」是正常情况，不是错误，killWorker 把「没杀到」当成一个可接受的返回值而不是异常。

取消（CancellationToken）的接法有一处很关键的工程细节：取消回调可能在渲染线程上执行 （TUI 的 Esc 路径），因此它只做两件非阻塞的事——翻标志、起一条短命守护线程去杀 worker； 杀 worker 是一次阻塞 RPC，绝不能放在回调里。另外取消令牌是回合级的， 而一次调用只属于其中一次：回调晚到时不能杀掉别的调用正在用的 worker，所以有一个 active 标志在 finally 里被清掉。只有工具调用会传真实令牌， 其余扩展点一律传 CancellationToken.NONE（ExtensionCodec.handlerTo 的默认实现）， 这是 ToolCodec 唯一覆盖 handlerTo 的原因。

            JsonNode response = created.call(ScriptProtocol.METHOD_INITIALIZE, ScriptJson.treeOf(params),
                    initializeTimeoutMillis());
            reportInitialization(response);
            LOG.info("{} 脚本网关已启动: {} 个脚本，{}", language.displayName(),
                    Integer.valueOf(scripts.size()), settings);
        } catch (RuntimeException e) {
            discard(created, started, createdWriter);
            throw e;
        }
    }

这段代码里三处顺序都是有代价的：会话先于进程（否则退出回调不知道该通知哪一代）、 写出行先于初始化（否则 initialize 那一帧自己发不出去）、 workers.clear()（否则台账会把上一代退出时的样子当成现在的样子）。 另有两个超时值也需要记住：调用超时就是配置里那一个数字， 因为「Java 比网关先放弃」会让网关来不及杀掉卡死的 worker，下一次调用撞上同一个卡住的 worker， 表现为「连续超时」；而初始化的等待上限刻意更宽（max(30s, 调用超时 + 10s)）， 因为网关自己有一个更短的初始化宽限，正常情况下「网关的精确错误」总是先到—— 哪个脚本、差在哪个扩展点都在里面。

初始化结果的记账方式同样值得抄：单脚本初始化失败只告警不失败 （网关已经起来了，成功的脚本还能正常工作，而「因为一个脚本的入口文件写错，整门语言都不可用」 正是本方案要避免的连坐）；但一个脚本都没起来就显式失败，否则后面的每次调用都只会超时， 现场离原因（清单与实现对不上）隔了整整一个超时周期。而且每个脚本都要出现在结果里 （gateway.py._expire_init 的注释）：只在失败时上报的话，「worker 一起来就崩」的脚本会静默消失， 而宿主看到的是「清单里有它、初始化结果里没有它」——那正是最难判断的一种不一致。

为什么必须有 ScriptScheduler：脚本的 worker 是「收请求 → 跑处理器 → 收事件」的单线程循环， 进程只在被调用时活着、空闲还会自毁，因此脚本无法自行计时。发起方只能落在桥接层—— 它是唯一常驻、且手里有调用通路的一侧。三条实测语义：间隔是「上一次跑完 + 间隔」 （scheduleWithFixedDelay，本身就是 single-flight 的；取数一次可能十几秒，用固定频率会把 「还没返回就又发一次」变成常态）；成功之后代发一次 UiInvalidatedEvent （脚本发布不了这个事件，而周期任务的语义就是「我后台更新了自己贡献的内容」—— 没有它，定时抓到的新数据只会写进文件，而屏上那块面板永远不会自己重画）； 失败只记日志、绝不让定时器停（任务体抛异常会让 scheduleWithFixedDelay 的后续触发静默停止，表现是「跑了几次就不动了」而日志里什么都没有。 连「代发失效」这一步都单独包了 try/catch，因为那恰好是关闭那一刻最容易抛的一步）。

设计依据：为什么「清单是注册的唯一来源」值得付出漂移的代价？

替代做法是让脚本运行时上报注册。它的直接后果是：注册必须在 start() 里阻塞等待进程就绪， 而进程一旦起不来，插件就只能整个失败——也就是「内核启动依赖解释器」。 静态清单换来三件事：Python 环境缺失不阻塞内核启动（清单在磁盘上，与解释器无关）、 没有请求时脚本侧进程数为零（注册不需要进程）、worker 崩溃后直接重启即可（清单是权威，无需重注册）。 代价是清单可能与实现漂移，因此配套了三重防线：清单由 dump_manifest 从代码生成、 --check 供 CI 比对、worker 启动时 compare_with 严格校验。 这套「用一个静态事实换掉一条启动期依赖，再花力气守住它」的账，是本页最值得记住的取舍之一。

12. 坑点清单

前文散落的坑，这里按「现象 → 根因 → 规避」收成一张表。多数坑的共同特征是 现场离原因很远——这正是跨进程方案必须额外花钱买可观测性的原因。

现象根因规避
调用一直等到超时，两侧日志里没有任何线索 宿主单行上限 小于脚本侧出帧上限：落在中间的帧被就地切成两条非法行丢掉，脚本侧那条「结果超过传输上限」永远不会触发 两个数字必须满足严格不等式（宿主 10 MB + 64 KiB > 脚本 10 MB），端到端测试各有一条守卫用例从脚本侧源码读数比对

脚本里声明的工具/事件从来没有被调用过 重复声明被后一个静默盖掉（事件到处理器是一对一映射）；或清单与实现不一致而 manifestStrict=false 重复声明当场抛 ScriptError（jellyfish_sdk.py:442-470 的 subscribe）；保持 manifestStrict=true，让不一致变成启动期拒绝服务

关键结论

  1. 桥接的本质是「一个 JVM 内的代理人 + 一次进程往返」：内核侧只看到普通的扩展点注册 （脚本与 Java 插件同构），脚本侧一行 Java 都不用写，而 ScriptBridgePlugin 就是那个代理人。
  2. 注册与进程生命周期彻底解耦：静态 manifest.json 是注册的唯一来源， 于是内核启动不依赖解释器、空闲时脚本侧零进程、worker 崩溃后无需重注册。代价（清单漂移） 由「代码生成清单 + --check + 启动时严格校验」三重防线守住。
  3. 线协议是 stdio 上的 JSON-RPC 2.0，一行一个 JSON；帧格式选行分隔而不是长度前缀， 换来的是「错一行、丢一行、继续」。而宿主单行上限必须严格大于脚本侧出帧上限—— 这是一条被端到端测试钉死的硬不等式，违反它的现象（调用等到超时、无任何线索）离原因最远。
  4. 扩展点的跨语言能力由 24 个纯函数 codec 承担，名单只在 ExtensionCodecs.defaults() 里出现一次，同时服务于注册、清单校验与调用路由；哪些扩展点支持、哪些明确不做，写在 extension-points.json 并由单测逼着内核作者分档。
  5. 稳定性靠三条边界划分清楚：熔断拒绝派发但不摘注册（保住自动半开恢复）、 四类失败明确不计入熔断、「不表态」用独立异常与「空结果」区分开——记账正确比记账严格更难，也更值钱。
  6. 进程模型选「子进程 + 行分隔 JSON」而不是嵌 JS 引擎或 JNI， 换来的是语言无关与崩溃隔离；主要代价是进程往返、类型映射、错误传播与调试体验， 这四样各自有一处具体工程答案（懒启动 / codec / 协议错误对象 / stderr 与台账）。
