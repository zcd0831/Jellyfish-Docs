06 权限与审批系统 重点

这是「默认不信任」主线的落地页。整套机制的默认方向只有一个：更严。 每一种「说不清楚」的情形都被收敛成一条有理由的拒绝。

学习目标

  • 准确说出 allowedTools / deniedTools / askTools 的判定优先级与匹配规则 （以及为什么 shell* 这种写法无效）；
  • 指出权限判定插在工具执行链的哪一步，以及为什么它必须在那一步；
  • 说清插件拦截为什么「三态里没有 ALLOW」，以及插件抛异常时的处理；
  • 画出审批请求从 TUI 弹框 / Server SSE 到用户裁决的完整路径，并说出 fail-closed 的五个触发条件；
  • 解释 !命令 如何复用与模型调用完全相同的工具执行链。

1. 三段权限的语义

agents.json 里每个 agent 的 permissions 有三个集合。匹配规则是集合精确相等 （Set.contains），没有任何通配符或前缀逻辑：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/permission/PermissionPolicy.java:118, 128, 141-142
/** 判断工具是否被显式拒绝。 */
public boolean denies(String toolName) {
    return toolName != null && deniedTools.contains(toolName);
}

/** 判断工具是否需要人工审批。 */
public boolean requiresApproval(String toolName) {
    return toolName != null && askTools.contains(toolName);
}

/** 判断工具是否在允许范围内。
 *  允许名单未声明（null）表示「不限制」，此时一律返回 true；已声明时只放行命中项，
 *  因此声明为空集合就是「一个都不允许」。 */
public boolean allows(String toolName) {
    return allowedTools == null || (toolName != null && allowedTools.contains(toolName));
}
集合语义没写时写空数组 [] 时
deniedTools显式拒绝（优先级最高）无操作无操作
askTools需要人工审批（优先级居中）无操作无操作
allowedTools允许范围（收窄用）不限制（null）一个都不允许（全拦）

「没写」与「写空数组」的区别靠配置层的 allowListDeclared 标记实现（AgentPermissions.java:56）—— 这是02 页讲过的「段声明标记」思路在权限上的同一份应用。

坑点：没有通配符

allowedTools: ["shell*"] 不等于放行 shell—— shell* 只是一个普通的字符串，永远命中不了任何真实工具名。 同理 mcp__* 也无效。工具名的唯一化由插件侧负责（MCP 工具名形如 mcp__<server>__<tool>），内核不解析前缀。 想放行一批工具只能逐个列名。

第二个坑：allowedTools: [] 是「全部拦下」，不是「未配置」。 如果你的意图是「不限制」，就把这个键整段删掉。

默认 agent 与 agentId 解析

内置默认 agent 的定义只有 4 行（jellyfish-infra/src/main/resources/default-agent.json）： 

{"agentId": "jellyfish", "description": "系统默认 agent", "permissions": {}}

三个集合都是 null → 不受限（AgentRegistry.java:250-256）。 注意这个 JSON 不接受 systemPrompt——提示词来自同目录的 {agentId}.md （AgentDefinition.java:13-16 的说明、:67 的构造器注释）；默认 agent 绑的是 classpath 根的 jellyfish.md。

解析失败时的行为分两种，方向相反，必须分清：

情形结果位置
agentId == null（没有 agent 概念） fail-open：返回 unrestricted() AgentRegistry.java:175-177
声明了 agentId 但查不到（拼错） fail-closed：denyAll() + 发一条 ConfigWarningEvent AgentRegistry.java:181-184、PermissionPolicy.java:72, 86
设计依据：为什么「agentId 拼错」要全拦而不是放行？

因为这两种情形不是同一件事。agentId == null 表示「这个进程/这个调用点根本没有 agent 维度的授权概念」（例如内核被嵌入为一个库），那时没有可收窄的依据，只能不限制。

而「声明了一个 agentId 但系统里没有这个 agent」是配置错误。 如果这时 fail-open，一个拼写错误就会让原本被收窄了权限的 agent 静默变成无限制—— 用户以为自己还受保护，实际上那道限制已经消失了，而且没有任何迹象。 这正是 PermissionManager.intercept() javadoc 里反复强调的那句话： 「拒绝是可见、可诊断、可重试的」。

设计依据：为什么「参数改写」必须在「权限判定」之前？

源码注释（ToolExecutor.java:180-184）给的理由是 TOCTOU（检查后使用的时间差）： 「必须在权限判定之前，否则审批浮层显示参数 A、真正执行参数 B」。

设想一个插件会把 command 参数从 "ls" 改写成 "rm -rf /"。 如果权限判定在改写之前，用户看到并批准的是 ls，实际执行的是 rm -rf /—— 审批就变成了形式主义。所以顺序只能是：先让参数定型，再拿定型后的参数去问人。

第二个理由同样重要：它必须早于 onToolCallStarted，否则工具轨迹行与 --show-tool-args 打出来的参数，与审批记录、与会话里落库的 toolCalls 不是同一份。 注释里那句「四个显示面共用一份文本是既有纪律」就是这个意思。

decide() 的完整流程

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/permission/PermissionManager.java:107-139
public PermissionDecision decide(PermissionCheckRequest request) {
    Objects.requireNonNull(request, "request must not be null");
    PermissionDecision decision = evaluatePolicy(request);
    String source = CORE_SOURCE;
    if (!decision.isDenied()) {
        // 核心策略已经拒绝时不必再问插件：结果不可能更宽，问了也只是白跑一遍插件代码
        for (HandlerBinding<PermissionCheckRequest, PermissionVerdict> binding
                : extensions.bindings(PermissionCheckRequest.class, null)) {
            PermissionVerdict verdict = intercept(binding, request);
            if (verdict.isAbstain()) {
                continue;
            }
            if (verdict.isDenied()) {
                // DENY 一定是最严的结论，不必再问后面的插件
                decision = PermissionDecision.deny(verdict.getReason());
                source = binding.getOwner();
                break;
            }
            if (!decision.isAsk()) {
                // 同为 ASK 时保留先到者的理由：两个插件都要求审批时，原因属于「先说出来的那个」，
                // 覆盖它只会让审计里的理由随插件顺序变化，没有信息增益
                decision = PermissionDecision.ask(verdict.getReason());
                source = binding.getOwner();
            }
        }
    }
    if (decision.isAsk()) {
        decision = resolveApproval(request, decision);
        source = APPROVAL_SOURCE;
    }
    publishAudit(request, decision, source);
    return decision;
}

这段有三处值得学的设计：

  • 已 DENY 就跳过插件：因为插件的判定只能收紧、不能放宽（三态里没有 ALLOW）， 所以「已经拒绝了」意味着结论不会变，再跑一遍插件纯粹是浪费——而且会让审计里的「谁拒的」变得模糊。
  • DENY 短路：遇到第一个 DENY 立刻 break，后面的插件不再问。 理由是「DENY 一定是最严的结论」。这带来一个可观察的语义：插件的注册顺序会影响「谁的拒绝理由被记下来」。
  • 同为 ASK 时保留先到者的理由：注释专门解释了——两个插件都要求审批时，原因属于「先说出来的那个」； 覆盖它只会让审计里的理由随插件顺序变化，没有信息增益。这是一个很成熟的细节判断： 在多来源信息等价时，选择保持稳定而不是选择「最新」。
坑点：decide() 永远不返回 ASK

javadoc 明确写了：「本方法不会返回 ASK」——Ask 在 decide 内部就被 resolveApproval 变成了 ALLOW 或 DENY。所以调用方写 if (decision.isAsk()) 是死代码。 这个设计的好处是：调用点不可能「忘记处理 ASK」导致悬空状态。

另一个坑：usableTools（工具清单过滤）只走核心策略，不跑插件拦截、也不问人 （PermissionManager.java:159）。而且 ASK 不算被拒—— 所以「清单里有这个工具，执行时却被拦下」是完全正常的，不是 bug。

3. 插件拦截：三态，且没有 ALLOW

Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/extension/PermissionVerdict.java:29-38
态含义对最终判定的影响
ABSTAIN无异议（不是「放行」，是「不表态」）继续问后面的插件；不影响核心策略结论
ASK要求人工审批若当前不是 ASK，则升级为 ASK
DENY拒绝（最严）短路，立刻落定为拒绝
没有 ALLOW——插件在类型上就无法表达「我允许它」

插件抛异常或返回 null 时：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/permission/PermissionManager.java:205-223 及该方法 javadoc
private PermissionVerdict intercept(HandlerBinding<PermissionCheckRequest, PermissionVerdict> binding,
                                 PermissionCheckRequest request) {
    PermissionVerdict verdict;
    try {
        verdict = extensions.invoke(binding.getHandler(), request);
    } catch (RuntimeException e) {
        LOG.warn("权限拦截处理器执行失败，按拒绝处理: owner={} tool={}", binding.getOwner(),
                request.getToolName(), e);
        return PermissionVerdict.deny("权限拦截处理器执行失败（来源：" + binding.getOwner()
                + "），无法确认本次调用是否被放行，按拒绝处理");
    }
设计依据：为什么「没表态」不能等于「无异议」？

javadoc 把这个问题讲得比任何文档都清楚，值得整段读（PermissionManager.java:188-204）：

「拦截只能把判定收紧，它『没能表态』因此不能等价于『无异议』——那样一来，一条按模式或按参数收窄的授权 会在插件出故障时静默消失，而现场没有任何痕迹：模型只看到这次调用照常放行， 用户也不知道自己开着的那道限制已经失效。拒绝是可见、可诊断、可重试的： 模型收到一条写明『哪条拦截没跑成』的失败理由，日志里有 owner 与堆栈。」

第二段回答了「为什么不把异常抛出去」：「本方法在判定链上被同步调用，异常逃出去会让整次工具调用以未定义的方式失败 （外壳拿到 500 而不是『工具被拒』）。内核的立场是故障收敛成一条有理由的拒绝， 而不是把故障本身当成『没意见』。」

第三段是最好的一句：「与『插件不能放宽权限』一致：PermissionVerdict 里没有 ALLOW， 插件连表达放行都做不到；那么它无法表态时也就只可能落在『更严』这一侧。」 ——类型系统层面的收紧，让运行期的失败处理有了唯一正确答案。

坑点：插件作者最容易犯的错

想「放行」时返回了 null 或抛异常，结果工具被拒。 正确的写法是返回 PermissionVerdict.abstain()——「我没有异议」，让判定回到核心策略。 另外：插件 stop() 之后再注册 / 发布会当场失败（fail-closed）， 有注册线程的插件必须在 stop() 里先停线程（见 16 页）。

4. 审批：fail-closed 的完整实现

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/permission/ApprovalChannel.java:304-331
private PermissionDecision await(Pending request, Duration timeout) {
    if (!attached) {
        return PermissionDecision.deny(NO_APPROVER);
    }
    Waiter waiter = new Waiter();
    if (!enqueue(request, waiter)) {
        // 入队失败的原因在锁内定下，但这里重读一次 attached 就足够区分：关闭是一次性事件
        return PermissionDecision.deny(attached ? QUEUE_FULL : DETACHED);
    }
    String unanswered = null;
    try {
        if (timeout == null) {
            // 永不超时：等到有人裁决，或通道关闭 / 回合取消把它放开
            waiter.latch.await();
        } else if (!waiter.latch.await(Math.max(1L, timeout.toMillis()), TimeUnit.MILLISECONDS)) {
            unanswered = timeoutReason(timeout);
        }
    } catch (InterruptedException e) {
        // 中断在此处只有一种来源：回合被取消 / 进程在退出。恢复中断位让上层也能看到
        Thread.currentThread().interrupt();
        unanswered = INTERRUPTED;
    }
    if (unanswered != null) {
        // 落定失败说明裁决方抢先给出了结论，此时按它的结论返回
        finish(request.getId(), PermissionDecision.deny(unanswered));
    }
    return waiter.decision;
}

坑点：0 不是「立即拒绝」，是「永不超时」

语义再次与直觉相反。permission.approvalTimeoutSeconds = 0 表示 永久等待用户裁决。因为等待发生在 react 线程上（池子只有 8 条）， 攒够 8 个这样的回合，内核的智能入口就彻底堵塞了。 想放宽就写一个很大的秒数，不要写 0。

坑点：Server 的真实路由与你猜的不一样

不是 POST /approval，而是三条件：GET /approvals（全局待裁决）、 GET /sessions/{id}/approvals、POST /sessions/{id}/approvals/{requestId} （JellyfishServer.java:372-374、ApprovalHandlers.java:97-111）。

还有一个反直觉的行为：resolve 只对「头槽位」生效—— 对排队中的请求调用 resolve 等于什么也没发生。 HTTP 层据此区分「已裁决」和「还没轮到」，所以客户端不能只发一次请求就认为裁决成功了。

第三点：SSE 断连会主动拒绝（ChatHandler.java:249）， 这也是 fail-closed 的一部分——客户端跑了不该等于「用户默认同意了」。

为什么 AskChannel 与 ApprovalChannel 不共享基类

两个通道的队列语义几乎一样（每会话一个头槽位、FIFO、只对头生效、上限 8）， 但 docs/constraints.md:491-517 明确说明它们各自独立实现、不抽公共基类。 理由是它们的默认行为相反：审批 fail-closed（拒绝），提问 fail-open（返回「无人应答」让模型自己继续）。 强行共享基类会逼着两个「默认相反」的东西去凑一个抽象——而抽象一旦成立， 未来任何一方的默认语义想变，都要先说服另一方。

超时键也是各自独立的：ask.timeoutSeconds 与 permission.approvalTimeoutSeconds， 不复用（AskSettings.java:37）。两者完整对比见 04 页第 3 节。

设计依据：为什么不让 ! 走一条「用户自己敲的，不用判权限」的捷径？

因为「用户自己敲的」这个判断本身不可靠。三种情况下它不是真的：

  • 用户可能只是复制粘贴了一段来自模型输出的内容（提示注入的最常见载体）；
  • 会话可能运行在 Server 模式，敲命令的不是坐在终端前的人；
  • 即使真是本人在敲，「我看到的是什么」与「实际执行的是什么」也可能不同—— 所以参数改写必须在权限判定之前（TOCTOU，见第 2 节）。

走同一条链路的收益很实际：! 命令也会弹审批框、也走截断与落盘、也留下同样的审计事件。 你不需要为「手动执行」单独想一遍所有安全规则。

附带的一个事实：! 这个指令标记由插件声明（InputDirectives.java:45-55）—— 卸掉官方 shell 插件，! 就不存在了。指令的结果作为 user 消息落会话（appendResult）， 所以它会进上下文，模型下一轮能看到。

6. 拒绝之后，模型看到什么

拒绝来源回灌给模型的文本位置
权限判定 "权限拒绝：" + 理由（理由空白时补「未提供理由」） ToolExecutor.java:392-395、:550-552
审批拒绝 理由 = 策略原文 + ； + 审批原文 PermissionManager.java:250
参数改写被插件拒绝 "插件拒绝参数：" + 理由，元数据 terminal=REJECTED； 不进权限审计 ToolExecutor.java:346-374（:366 是文本构造处）
拦截处理器自己出错 "权限拦截处理器执行失败（来源：owner）…按拒绝处理" PermissionManager.java:212-216

两个要点：（1）拒绝不抛异常，只转成文本。工具调用仍然是一次「成功的调用」， 只是结果是拒绝文本——所以它照旧落进会话，模型下一轮能看到并在下一轮换策略。 （2）审计事件放行也发。PermissionDecidedEvent 无论 ALLOW 还是 DENY 都发 （PermissionManager.java:137 调用、:271 定义；来源常量在 :59 与 :62），来源字段会区分 core / 插件 owner / approval。

7. 本页坑点小结

权限系统的坑
  • 没有通配符：shell* / mcp__* 永不命中，必须逐个列名。
  • allowedTools: [] 是「全拦」，不是「未配置」。
  • approvalTimeoutSeconds: 0 是「永不超时」，会挂死 react 线程（池仅 8 条）。
  • decide() 永不返回 ASK，调用方判 isAsk() 是死代码。
  • usableTools 只走核心策略，ASK 不算被拒 →「清单里有、执行时被拦」是正常现象。
  • 参数改写必须在权限之前，否则审批看到参数 A、执行参数 B（TOCTOU）。
  • Server 的裁决路由是 /sessions/{id}/approvals/{requestId}，且 resolve 只对头槽位生效。
  • agentId 拼错不是「变宽松」而是「全拦」，且只告警一次。
  • -cli 从不 attach 审批者，所以 askTools 在 CLI 下命中即拒。 挂接审批的有两处：-tui（TuiRunMode.java:198）与 -server（JellyfishServer.java:166 的 approvals.attach()）。
  • 拒绝不抛异常，只回灌文本；上层别指望看到异常。
  • 插件想「放行」要返回 abstain()，返回 null 或抛异常都会被判拒绝。

关键结论

  1. 整套权限模型的默认方向只有一个字：严。「说不清楚」的每一种情形都有唯一的收敛方向——拒绝。
  2. 「插件三态无 ALLOW」是这个设计里最巧妙的一处：把「插件不能放宽权限」这条规则做进类型系统， 于是「插件出故障怎么办」这个运行期问题自动有了唯一正确答案。
  3. 判定优先级固定为「显式拒绝 > 需审批 > 允许收窄」，且核心策略先于插件——插件只能在这个基础上收紧。
  4. ! 命令与模型调用共用 ToolExecutor 的私有 execute，唯一差异是 source 参数。 这是「安全规则只写一遍」的典型做法。
  5. fail-closed 的五个触发条件（无审批者 / 队列满 / 通道已关闭 / 超时 / 中断）覆盖了「审批不可能完成」的全部情形， 再加上「SSE 断连主动拒绝」，任何异常路径都不会意外放行。
