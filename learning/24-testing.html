24 测试体系与构建

一个项目「敢不敢改」取决于测试。这一页把 Jellyfish 的测试规模、技术栈、覆盖率、端到端策略与打包方式 全部量化——数字都是本次实测的，不是估计。

学习目标

  • 知道测试与主源码的规模比例，以及哪些模块测得最厚、哪些最薄；
  • 说清测试技术栈的三个事实（版本、没有覆盖率门禁、规范提到但未引入 AssertJ）；
  • 理解为什么单测与端到端测试要用四个独立 profile 隔开；
  • 读懂 JellyfishAssemblerTest——它是全仓最重要的一个测试，因为它守的是「两套装法等价」；
  • 能自己算出一个新模块该写多少测试（对照现有比例）；
  • 看懂 fat jar 是怎么拼出来的，以及构建里最脆的一环在哪。
数字口径说明

本页所有数量（测试类数、主类数、jar 体积）都是本次在工作区用 find / grep -c / ls 实测的结果。覆盖率数字来自各模块 target/site/jacoco/index.html， 也就是说它是上一次构建的快照，不等于你当前代码的即时覆盖率。 重新跑一次 mvn test 再 mvn jacoco:report 才能得到当次结果。

一个可复用的经验值

测试类/主源类 ≈ 0.6（内核），复杂模块（infra / tui / cli）会到 0.8–1.0。 这个比例背后其实是「一个类至少有一种值得独立验证的行为」： 纯数据类（DTO、事件、枚举）贡献了分母却不产生测试，所以被动测（DTO）多的模块比例天然低 （server 只有 0.38，正是因为它有 33 个 DTO）。

反过来说：看到某个模块比例异常低，先看它是不是 DTO 多，再看是不是漏测。 直接拿比例当质量指标会误判。

2. 技术栈：三个必须知道的事实

事实一：JaCoCo 没有覆盖率门禁

Jellyfish/pom.xml:273-294
<!-- 排除生成代码：Dagger 的产物不该算进覆盖率分母 -->
<excludes>
  <exclude>**/Dagger*</exclude>
  <exclude>**/*_Factory.*</exclude>
  <exclude>**/*_MembersInjector.*</exclude>
  <exclude>**/package-info.*</exclude>
</excludes>
<!-- :283-286 prepare-agent / :290-294 report（绑 test 阶段） -->

只有 prepare-agent 与 report 两个 goal，没有 check。 也就是说：覆盖率会被计算并生成报告，但不设阈值、不会让构建失败。

设计依据：没有门禁是疏漏还是选择？

从 AGENTS.md 的规范看（下面第 6 节），它的单元测试纪律写得相当细——所以「没有门禁」 更像是刻意不设而不是忘了。理由通常有两个：

  • 覆盖率门禁会制造坏激励。一旦设了 80%，最省事的达法就是给 getter 写无意义断言。 对「契约类多」的项目（api 144 个类）尤其容易跑偏。
  • 它用另一种门禁替代了覆盖率：不变量清单（AGENTS.md 的「关键不变量」一节， 12 条）+ 强制双跑的 JellyfishAssemblerTest。这比一个百分比更贴近「改坏了会静默出错」的地方。

代价也很实在：贡献者无法靠「跑一下」发现漏测，只能靠评审。 如果你要在自己的分支上加门禁，建议按模块设差异化的阈值（api 可以低、infra 应该高）。

事实二：规范提到 AssertJ，但全仓没有这个依赖

AGENTS.md 的测试规范里写着「断言用 JUnit5 Assertions 或 AssertJ，异常用 assertThrows」。 但全仓搜 assertj 只命中规范正文本身，没有任何 pom 声明这个依赖。

坑点：照着规范写会编译失败

如果你看到那条规范就去写 assertThat(x).isEqualTo(y)，会得到一个「找不到符号」的编译错误—— 因为既没引入 assertj-core 依赖，也没 import。

实际可用的只有 JUnit5 的 Assertions（assertEquals / assertTrue / assertThrows 等）。想用 AssertJ 得先加依赖——但那属于改构建配置，按 AGENTS.md 要先跟维护者确认。 这属于「规范与依赖不一致」的文档缺陷，本页如实记录。

事实三：TamboUI 是 SNAPSHOT 依赖

dev.tamboui:tamboui-bom 0.5.0-SNAPSHOT（Jellyfish/pom.xml:142-144，import 方式）， 实际构件 tamboui-toolkit / tamboui-jline3-backend 不带版本（jellyfish-tui/pom.xml:38-49）。

坑点：SNAPSHOT 依赖会让「同一个 commit 构建出不同结果」

SNAPSHOT 意味着该版本的内容可以被远程仓库覆盖。 所以两个人在同一份代码上跑 mvn package，可能拿到行为不同的 TUI 实现； 而 mvn -o（离线）在本地没有该快照时会直接失败。

这是本页所有事实里对构建可复现性影响最大的一条。要做生产构建， 建议先把该快照落到本地仓库并固定，或等它发正式版。 另外 jellyfish-tui/pom.xml:48-55 排除了 TamboUI 传递来的 jline 3.25.1， 自己显式声明 jline 3.30.17（:58-60）——这种「排除传递版本、自己钉一个」的做法值得学， 因为它把版本冲突的处理显式化了。

4. 单测与端到端：四个 profile

mvn test 不会跑任何端到端测试。端到端被收在四个独立 profile 里， 靠 surefire 的 include 模式隔离：

profile在哪跑什么依赖什么真实资源
server-it jellyfish-cli/pom.xml:142（<id>server-it</id>；surefire 在 :147，include 在 :149） ServerEndToEndIT（308 行，2 个测试） 真 Undertow + 真内核（Dagger 装配），走本机回环，端口用 0 让系统分配
shell-it jellyfish-plugin-shell/pom.xml:116 ShellIT 真的 /bin/sh
mcp-it jellyfish-plugin-mcp/pom.xml:118 McpStdioTransportIT 真 fork 一个 echo server
script-it jellyfish-plugin-python/pom.xml:126、jellyfish-plugin-node/pom.xml:127 PythonScriptIT / NodeScriptIT 真的 python3 / node

Jellyfish-Plugins/AGENTS.md:26-28 说明了这三个插件 profile 的性质， :46 明确「mvn test / package 不跑 *IT」。

设计依据：为什么端到端不进默认构建？

因为它们依赖真实外部资源：真实 shell、真实 python3/node、真实端口、真 fork 子进程。 而 AGENTS.md 的测试规范里有两条硬要求——「测试独立、可重复、无外部依赖」 与「单测不访问数据库、网络等真实外部资源」。

于是一个测试要么无外部依赖（进默认 mvn test）要么有（进 -P<x>-it）， 两者不能混。这个划分让「日常开发跑得动、发布前单独验」两件事都成立。 相比之下把端到端塞进默认构建，最常见的后果是开发者开始习惯性加 -DskipTests—— 那时连单测也不跑了，得不偿失。

ServerEndToEndIT 的类注释（:26-37）还解释了一个设计：它放在 jellyfish-cli 而不是 jellyfish-server，因为只有这里有 composition root （能装配出完整内核）。两个测试方法的名字本身就是验收标准： server_should_expose_sessions_commands_health_and_stream_over_http 与 server_should_require_api_key_when_configured。

5. 最重要的一个测试：JellyfishAssemblerTest

jellyfish-di/src/test/java/zcd/jellyfish/di/JellyfishAssemblerTest.java（283 行，9 个测试）。 它存在的唯一理由，是守住 03 页讲过的那条约束： 两种装法必须交付行为等价的对象图。

JellyfishAssemblerTest.java:37-50（类注释）与 :245-255（双跑机制）
// 类注释 :37-50 的要点（原文摘意）：
//   测手工装配（JellyfishAssembler）与 Dagger 装配（JellyfishComponent）的「行为等价性」，
//   防「本该唯一的实例被建第二份」；用行为断言，而不是比较对象引用。

// 实现思路（:245 起）：把两种装配放进同一个列表，然后逐一遍历断言
private void forEachRuntime(Consumer<JellyfishRuntime> assertion) {
    List<JellyfishRuntime> runtimes = Arrays.asList(
            DaggerJellyfishComponent.builder().appConfig(appConfig).build(),
            JellyfishAssembler.create(appConfig));
    for (JellyfishRuntime runtime : runtimes) {
        assertion.accept(runtime);   // :249-255  同一段断言，对两种装配各跑一遍
    }
}
  • 断言写在回调里、由 forEachRuntime 双跑——这是「一处断言、两种实现」的最省写法。 新增一个断言不需要写两遍，也就不会出现「只在一种装配上验过」的漏洞。
  • 用行为断言而不是引用比较：因为它的目标是「两个 runtime 的行为一样」， 而不是「两个 runtime 内部是同一个对象」。后者其实是实现细节—— 虽然「同一实例」约束（如 EventPublisher 必须是那个 EventChannel） 确实可以靠引用比较表达，但作者选择验证可观察行为，这样重构内部结构时测试不会失效。
  • 它守的是「静默故障」：03 页讲过， 漏一行 EventPublisher publisher = eventChannel; 的后果是「配置告警发进没人订阅的通道」—— 没有任何异常，只是什么都不会发生。这类 bug 只能靠专门的测试抓。
可复用的做法：为「两套实现」写一个双跑 harness

凡是同一契约有多个实现的场景（多厂商客户端、两种装配、新旧算法），都可以照这个模式： 把实现放进一个集合 + 一条断言双跑。它比「写两份测试」更不容易漏， 也比「运行时二选一」更能发现差异。

6. 测试规范（原文）

以下逐字引自 Jellyfish/AGENTS.md:113-123，这是写测试前该对齐的唯一标准：

Jellyfish/AGENTS.md:113-123
## 单元测试规范

- JUnit5 + Mockito，JaCoCo 收集覆盖率。
- 测试类包路径与被测类一致；命名 `{被测试类名}Test`。
- 方法名 `{被测试方法}_should_{预期结果}_when_{条件}`；一个方法只验一个行为；测试独立、可重复、无外部依赖。
- 结构遵循 Given/When/Then 或 Arrange/Act/Assert。
- 只 mock 外部依赖或协作者，不 mock 被测类、POJO、DTO。
- 用 `@ExtendWith(MockitoExtension.class)`，统一 JUnit5 API，不混用 JUnit4。
- 断言用 JUnit5 `Assertions` 或 AssertJ，异常用 `assertThrows`。
- 多组输入用 `@ParameterizedTest`，覆盖正常、边界、异常场景。
- 单测不启动 Spring 容器，不访问数据库、网络等真实外部资源。

这套规范的辨识度很高，三个点值得单独看：

  • 方法名模板带条件后缀（..._should_..._when_...）：好处是测试名本身长成一个句子， 失败时报告直接可读（decide_should_deny_when_no_approver）。 这比 testDecide2() 的信息密度高得多，也是 ShellIT 命名（ server_should_require_api_key_when_configured）的来源。
  • 「不 mock 被测类、POJO、DTO」：mock DTO 会让断言变成「我 mock 的东西等于我 mock 的东西」， 测不出任何东西。这条规范把常见的「为了凑覆盖率而 mock」堵掉了。
  • 「不启动 Spring 容器」：这条在 Jellyfish-Spring-Boot-Starter 存在的前提下尤其重要—— 内核的测试不该依赖 Spring，否则内核就被间接绑上了 Spring 的启动开销与配置。

7. 构建与产物

fat jar 怎么拼出来

Jellyfish/jellyfish-cli/pom.xml:100-124（shade 配置要点）
<createDependencyReducedPom>true</createDependencyReducedPom>   <!-- :100 -->
<transformer implementation="...ManifestResourceTransformer">   <!-- :104 -->
  <mainClass>zcd.jellyfish.cli.JellyfishApplication</mainClass> <!-- :105 -->
  ...
  <manifestEntries>
    <Implementation-Version>...</Implementation-Version>       <!-- :109 版本号写进 manifest -->
<transformer implementation="...ServicesResourceTransformer"/>     <!-- :113 合并 META-INF/services -->
<filters>
  <filter><excludes>
    <exclude>META-INF/*.SF</exclude><exclude>META-INF/*.DSA</exclude><exclude>META-INF/*.RSA</exclude>
  </excludes></filter>                                              <!-- :116-124 去掉签名文件 -->
配置为什么必须有
ServicesResourceTransformer 合并 META-INF/services/ 而不是覆盖。PF4J、Jackson、SLF4J 都靠 SPI 文件发现实现； 如果 shade 只保留其中一个 jar 的 services 目录，运行时会「少掉一些实现」且没有报错
排除 *.SF / *.DSA / *.RSA 依赖 jar 的签名文件在合并后会失效，留着会让 JVM 抛 SecurityException（签名不匹配）
ManifestResourceTransformer + Implementation-Version 让 fat jar 的 manifest 带回版本号，-V / --version 与日志才能报出正确版本 （否则合并后 manifest 的版本信息会丢失或错乱）
createDependencyReducedPom 生成一份「去掉已打进去的依赖」的 POM，避免下游引用时重复拉依赖

8. 本页坑点小结

测试与构建的坑
  • 没有覆盖率门禁：漏测不会被构建拦住，只能靠评审。别以为 mvn test 绿了就安全。
  • 规范说可以用 AssertJ，但仓库没有这个依赖：照抄规范会编译失败，只能用 JUnit5 的 Assertions。
  • 覆盖率数字要看构建时间：target/site/jacoco/ 是上一次构建的快照，改了代码不会自动更新。
  • TamboUI 是 0.5.0-SNAPSHOT：同一 commit 可能构建出不同结果；mvn -o 在本地无该快照时直接失败。 这是构建可复现性上最脆的一环。
  • mvn test 不跑任何端到端：要跑得加 -Pserver-it / -Pshell-it / -Pmcp-it / -Pscript-it，且它们需要真实的 shell、python3、node、端口与子进程能力。
  • ServicesResourceTransformer 不能省：少了它，SPI 文件会被覆盖而不是合并， 现象是「插件/实现莫名少了几个」且无报错。
  • 签名文件必须排除：不排会让运行时抛 SecurityException。
  • server-it 用端口 0（系统分配）正是为了「可重复、不抢端口」—— 自己写端到端测试时照这个来。
  • Dagger 生成物被排除在覆盖率之外：所以 di 的 92% 指的是「人写的装配代码」， 不要把它与别的模块的原始数字直接对比。

关键结论

  1. 测试规模是内核 294 类测 475 个主类（≈0.62），插件另有 183 个； infra 与 tui 测得最厚，server（DTO 多）比例最低但合理。
  2. 技术栈是 JUnit5 5.10.2 + Mockito 4.11.0 + JaCoCo 0.8.12； 没有覆盖率门禁、没有 AssertJ 依赖——前者是选择，后者是文档与依赖的不一致。
  3. 端到端被刻意隔离在四个 profile 里，判据是「是否需要真实外部资源」。 这条分界线让 mvn test 永远可重复，也让端到端测试能放心用真环境。
  4. JellyfishAssemblerTest 是这套测试体系里最有代表性的一环： 它不为覆盖率存在，只为守住「两套装法行为等价」这条错了不会报错的约束。 它示范的「一份断言双跑多种实现」值得直接搬去别处用。
  5. 构建上最值得警惕的是 TamboUI 的 SNAPSHOT 依赖； 除此之外 shade 的四个配置项（合并 services、排签名、写版本、减依赖 POM）每一项都对应一个具体故障，不可省。
