14 终端界面（TamboUI）

TuiApp.java 有 2239 行，是整个仓库最大的单个类。理解它的关键在于一条纪律： 界面状态只归渲染线程。

学习目标

  • 说出 ChatShell 的六个区域与它们的固定顺序；
  • 知道主事件循环在哪里（不在本仓库），以及 TuiApp 实现了哪些回调；
  • 解释「不能直接跨线程改组件」的两个具体原因，以及 UiInvalidatedEvent 的作用；
  • 列出几个反直觉的键盘映射，并说出它们为什么被改成这样；
  • 知道渲染层面的硬性性能约束，以及日志为什么必须与终端隔离。

高度分配是一套「账本」：ChatLayout.compute()（:140）算各区域行数， messageWidth()（:206）算消息区可用宽度。 之所以要单独一个 ChatLayout（447 行），是因为终端宽度可变、各区域又有最小高度要求—— 这套算术放在渲染代码里会立刻变成一团乱麻。

设计依据：消息区为什么必须是「单个 richText」？

这是全页最实用的一条性能约束，来自 docs/constraints.md： 消息区的子元素数到 120–180 就出现性能断崖。

原因是 TamboUI（以及大多数 TUI 框架）的布局与按键路由都是按元素树做的： N 个元素意味着 N 次布局计算、N 次命中判定、N 次重绘比较。 一个会话里几百条消息，如果每条（甚至每个 markdown 块）都是一个元素，布局成本会随消息数线性增长， 而每一帧都要重算。

做法是：把整个消息区渲染成一个 richText 元素， 内部由 TranscriptProjector（1077 行）预计算成「视觉行」列表 （text/VisualLine.java、text/LineWrapper.java、text/DisplayWidth.java 都是为这件事服务的）。 再加上 500 条投影上限，每帧的渲染成本就被钉死在一个常数上。

代价：没有「按消息级别的元素交互」——点击某条消息、单独给某条消息加 hover 效果都做不到。 对终端界面来说这不是损失，但对想扩展的人来说是一道硬墙。

2. 主事件循环不在本仓库

读代码时容易迷路的一点

TuiApp extends ToolkitApp，而 ToolkitApp 来自外部依赖 dev.tamboui:tamboui-toolkit（jellyfish-tui/pom.xml:38）。 主事件循环由 ToolkitApp.run() 驱动，本仓库里找不到它。 TuiRunMode.java:213 的注释指明了这一点。

所以 TuiApp 的角色是实现回调，不是「写一个 while 循环」。 这也解释了为什么这个类有 2000+ 行——它把「所有回调的内容」都收在了一起。

第 4 步排在第 5 步之前是有原因的：ChatLayout.compute 需要知道浮层占多少行， 才能把剩余高度分给消息区。所以顺序是「先建浮层、再算账本」，而不是反过来。

第 1 步的 drainShell 是「每帧一次」而不是「每来一条就刷」—— 这是 16 页里 ShellIngress 信件箱模型能成立的前提： 投递与消费解耦，消费时机由渲染节奏决定。

3. 跨线程刷新：为什么只能发「失效」信号

这是这一页最重要的机制。先看不能做什么：直接在其他线程上改界面组件。 两个具体原因：

  1. 界面状态没有同步保护。UiCache.java:27-28（类注释）与 :38-60（字段）里只有一个 AtomicLong 版本号是原子的，其余字段没有任何同步。 这是有意的——渲染线程是唯一的写者，加锁纯属浪费。 但这也意味着别的线程写它就是数据竞争。
  2. TamboUI 的元素树是渲染期注册并按键路由的。 ChatInputView.java:47-49 说明了这点：元素在渲染期注册， 键位路由依赖树的结构。跨线程改元素树会与「渲染中遍历树」和「按键查找元素」竞争， 而且改完不会触发重绘（没人知道要重画）。

正确的做法是一条单向链路：

sequenceDiagram autonumber participant RT as react 线程 participant IT as InflightTurn participant EC as EventChannel participant UC as UiContributions participant CA as UiCache participant RD as 渲染线程 RT->>IT: 写流式文本 / 工具进度 Note over IT: 上限：正文 256K / 思考 64K
工具输出末 20 行 × 200 字符 RT->>EC: publish(UiInvalidatedEvent) EC->>UC: onInvalidated（异步，可能丢） UC->>CA: uiCache.invalidate() Note over CA: 只动版本号（AtomicLong）——这是唯一被允许跨线程写的字段 RD->>IT: snapshot() 取走最新状态 RD->>CA: snapshot() 取走贡献快照 RD->>RD: 重绘

环节实现要点位置
承载「进行中」的数据 InflightTurn：react 线程写、渲染线程 snapshot() 读； 有硬上限防止流式内容无界增长 InflightTurn.java:27-28, 58-67, 345

设计依据：为什么要绕这么大一圈，而不是直接刷？

因为走的是EventChannel（异步、可丢）而不是 ExtensionRegistry（同步、不可丢）——这个选择本身就是判据的应用： 「界面晚刷新一次」是可以丢弃的损失（下一帧或下一次事件就补上了）， 而「同步等渲染线程」会造成 react 线程与渲染线程相互等待： react 线程在等渲染完成，渲染线程可能正在等某个锁，而那个锁的持有者又在等 react 线程。

另外，丢事件在这里是安全的，因为「失效」是一个幂等信号： 收到 1 次和收到 10 次的效果一样。这正是「可丢」判据能成立的前提—— 如果事件内容是「新增了第 5 条消息」，丢了就会错位；但「内容可能变了」丢了无所谓。 设计可丢事件时，让它幂等，是一条很值得学的经验。

坑点：TUI 里 submit 之后不得 await()

TuiApp.java:99 明确写了这条。原因是界面线程一旦阻塞在「等回合结束」上， tamboui 的事件循环就停了——Esc 收不到、审批弹框画不出来、状态栏不再更新。 回合进行中要拒绝新输入（由 SubmissionPolicy 负责），而不是用阻塞来解决。

这是 TUI 与 CLI 最大的结构差异：CLI（15 页）就是要 awaitTurn 阻塞等终态，因为它的输出契约是「stdout 只等于最终回答」。

坑点：粘贴有上限，而且超限是「一个字都不插入」

7.2 DisplayWidth：中文为什么占两列

Jellyfish/jellyfish-tui/src/main/java/zcd/jellyfish/tui/text/DisplayWidth.java:76-81, 14, 10-12, 114
public static int ofCodePoint(int codePoint) {
    if (isZeroWidth(codePoint)) {
        return 0;
    }
    return isWide(codePoint) ? 2 : 1;

  • 零宽（:96-110）：组合符 U+0300-036F、U+1AB0-1DFF、 U+200B-200F、变体选择符 U+FE00-FE0F、U+FEFF。
  • 宽（:114）：区间表——Hangul Jamo、CJK、全角、Emoji（1F300、1F900）、CJK 扩展 B……
  • 依据在注释里（:14）：「判定依据是 Unicode 的 East Asian Width 属性（W 与 F 两类计 2 列），此处按区间近似实现」—— 作者明确承认这是近似，不是规范实现。
  • 为什么不放内核（:10-12）：列宽是终端概念，内核不该知道。
坑点：宽度算错是终端 UI 里最难查的一类 bug

错一个字符，整行后续对齐全错——现象是边框错位、文字重叠、光标位置漂移， 而且只在含特定字符时出现（某个 emoji、某个 CJK 扩展区汉字）。 所以「按区间近似」这件事值得记住：遇到对齐问题，先怀疑某个字符落在近似区间之外。

7.3 StyledSegment：终端注入的唯一收口点

Jellyfish/jellyfish-tui/src/main/java/zcd/jellyfish/tui/text/StyledSegment.java:47-50 与类注释 :19
public StyledSegment(String text, Style style) {
    this.text = ControlChars.strip(Objects.requireNonNull(text, "text must not be null"));
    this.style = Objects.requireNonNull(style, "style must not be null");
}

类注释（:19）原话：「构造即过滤控制字符，这是屏幕文本的唯一收口」。 理由也写在注释里：进屏幕的文本有两个来源——模型与工具输出（不可信）、 插件贡献与文件名候选（同样不可信）——所以把过滤放在所有渲染路径的汇合点上， 而且过滤是幂等的，新增渲染路径会自动被覆盖。

ControlChars.strip 丢弃 C0/C1 控制字符与双向控制符（U+202A-202E / U+2066-2069）， \t 转空格，保留 \n。

设计依据：为什么收在构造器，而不是「输出前统一过滤一次」？

「统一过滤一次」听起来更简单，但它要求找出所有输出点——而这个项目里输出点至少有三处： TUI 屏幕、CLI 的 SystemConsoleIO 三个写出方法、日志是第四条出口。 任何一个新增输出点忘了过滤，就开了一个洞。

收在构造器是另一种思路：让数据在诞生时就不可能带着危险字符。 于是「有没有过滤」不再取决于每个输出点是否记得，而取决于「你有没有用这个类型」—— 而类型是编译期能约束的。靠「不可能构造出坏数据」比靠「每个出口都记得检查」更可靠。 详见 25 页 G3。

  • 「按实例比对」代替深比较：提示表只在失效时重建，所以「同一实例 = 内容没变」成立。 用构建时机换掉深比较开销。

7.6 外壳事件协议：两条 lane 与 10 种 Kind

第 3 节讲的「跨线程发失效信号」之上还有一个更基础的约定：内核往外壳送的事件是什么形状、哪些可以不送。

通道语义（ShellStreams.java:60-65）丢了会怎样
可靠 lane（subscribe / subscribeAll） 内核回合事件。没有队列，同步扇出，不丢不乱序 不该发生——它是「屏幕上发生了什么」的真源
尽力 lane（subscribeShell） 插件贡献。队列在 ShellIngress 里，每 owner 有界、同 key 可合并、满即丢 少一段插件输出，下次事件或下一帧补上

注释里那句关键判断是：「可丢性在通道级就确定」——不是由发送方临时决定。

Jellyfish/jellyfish-core/src/main/java/zcd/jellyfish/core/conversation/ShellTurnEvent.java:37-67（Kind）与 :12, :22-24
Kind 十种：STARTED  TEXT  THINKING  TOOL_STARTED  TOOL_OUTPUT（可丢，只服务进展）
         TOOL_COMPLETED  BLOCKED（开始前被插件拦下，用户消息未进会话）
         COMPLETED（正常收敛，含达最大轮次）  CANCELLED  ERROR

:12  为什么用判别式 kind：
     外壳要对其做 switch，而新增一种事件不应要求每个外壳都改一遍接口实现
     （那正是 ReActListener 的痛点）

:22-24  不承载审批：
      审批是拉取式的（外壳每帧读 ApprovalChannel.pending(sessionId)，
      Server 在 SSE 循环里同步头槽位）。理由是审批需要「当前是否还挂着一件」
      这样的状态语义，而事件是过去式的，用它表达状态会引入两套真源
设计依据：为什么从「一组回调方法」改成「一个方法 + Kind」？

注释里点了 ReActListener 的痛点：那是按事件类型分的一组方法 （onText / onThinking / onToolStarted …）。 每加一种事件，每个实现者都必须改——而外壳有三个，加一个接口方法就是三处编译错误。

改成「onTurnEvent(ShellTurnEvent) + Kind」之后， 新增事件只影响关心它的那个外壳（switch 里加个 case）。 代价是编译期不再强制处理所有类型（switch 可能漏 case）， 换来的是内核加事件不必动外壳。这条取舍在「内核会持续演进、外壳可能由别人写」的项目里几乎必选前者。

终态约束也值得记：回合四选一（COMPLETED / CANCELLED / BLOCKED / ERROR）， 指令二选一，且恰好一次——外壳可以放心地在收到任一个终态时收尾。

8. 本页坑点小结

TUI 相关的坑
  • 发送键是 Ctrl+S 不是 Enter——按 Enter 只换行。这是终端不解码修饰键逼出来的反转设计。
  • End 归消息区，编辑器里用不了「光标到行尾」。
  • 粘贴 CRLF 文本可能出现额外空行（文档记载，源码未坐实）。
  • 粘贴上限 1 MiB（码点），超限一个字都不插入。
  • 消息区只投影最近 500 条——这是屏幕的上限，不代表上下文里没有。
  • 消息区必须是单个 richText：子元素数到 120–180 就有性能断崖。
  • 不要在非渲染线程改界面状态：UiCache 里除版本号外都没有同步，改了也不会触发重绘。
  • 日志配置必须早于第一个 Logger，否则配置不生效、日志撕坏备用屏。
  • 界面线程不得 await() 回合，否则 Esc 与审批弹框全失效。
  • 主事件循环不在本仓库（在 tamboui-toolkit 里），别在 TuiApp 里找 while。

关键结论

  1. TUI 的全部复杂度集中在两件事上：把「随手可变的界面状态」限制在一条线程里， 以及把「每帧成本」压成一个常数（单 richText + 500 条上限 + 布局账本）。
  2. 跨线程刷新走的是「写数据 + 发幂等失效信号」，而不是「跨线程改 UI」。这个模式能成立的关键是 失效信号是幂等的、可丢的——所以它走 EventChannel 而非 ExtensionRegistry。
  3. 多个键盘映射看起来反直觉，根因是同一个：终端协议里可用的按键空间比 GUI 小得多， 而且修饰键常常拿不到。这类约束在 TUI 项目里是硬约束，改设计不如改习惯。
  4. 「弹框只画、通道负责等」是一个干净的分工：UI 层永远不会因为等待而阻塞事件循环。
