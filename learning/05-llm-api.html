05 多厂商 LLM API 抽象层 重点

这一层的设计目标可以一句话概括：让内核只认识一种请求形状，同时让用户能用到厂商的私有能力。 两件事是矛盾的，看它怎么调和。

学习目标

  • 画出 LlmClient 的继承树，并说出每个子类覆写了什么；
  • 理解 type 与传输实现的关系，以及「内置优先、插件兜底」的路由顺序；
  • 说清 vendorBody / vendorHeaders 的来源、合并方向与保留键保护；
  • 解释「没写 vs 写了 0」在类型系统上是怎么表达的，以及为什么这很重要；
  • 说清「这一轮用哪个模型」的三级回落，以及子代理为什么不继承父会话的模型；
  • 知道 LlmUsage 只对齐五个口径，思考 token 不在其中；
  • 知道 prompt cache 的两个断点分别打在哪里、keepAliveSeconds 在做什么；
  • 说清流式侧工具调用分片的累积算法。

设计依据：为什么 Claude / Gemini 不继承 OpenAiCompatible？

因为它们不是「另一种 OpenAI」。差异不只是 URL 和字段名，而是消息模型的形状本身不同：

  • OpenAI 把 system 当一条普通 message；Claude 把它当顶层字段，Gemini 叫 systemInstruction； 内核因此在 AbstractHttpLlmClient.java:493 做「消息区 system 上提顶层」。
  • OpenAI 的 tool 结果是 role: tool 的消息；Claude 要求包成 user 里的 tool_result 块， 而且连续 user 必须合并（ClaudeLlmClient.java:370-408）。
  • 缓存标注（cache_control）只有 Claude 需要显式标；OpenAI 系与 Gemini 是隐式缓存。

把这些差异塞进一个 if (isClaude()) 里，会让 AbstractOpenAiCompatibleLlmClient 变成一个「名字骗人」的类。当前做法是：只有真正相同的部分（HTTP 与 SSE 读流）才在基类， 消息形状各写各的。代价是三个大客户端类（857 / 593 / 461 行）里有重复的样板—— 这是刻意接受的重复，因为「错误的抽象比重复更贵」。

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/llm/LlmClientFactory.java:140-172
public LlmClient getClient(Provider provider) {
    if (provider == null) {
        throw new JellyfishException("provider must not be null");
    }
    String type = normalize(provider.getType());
    if (type == null) {
        throw new JellyfishException("provider type must not be blank");
    }
    // 内核自带类型先行；只有它不认识该类型时才去问注册表
    ProviderContribution contribution = null;
    if (!creators.containsKey(type)) {
        contribution = findPluginTransport(type);
        if (contribution == null) {
            throw unknownType(type, provider);
        }
    }
    String cacheKey = cacheKey(provider, type);
    // 锁内完成「查缓存 + 创建 + 回填」：既保证 LRU 访问顺序的线程安全，也避免并发重复创建客户端
    synchronized (clientCache) {
        LlmClient cached = clientCache.get(cacheKey);
        if (cached != null) {
            return cached;
        }
        LlmClient created;
        if (contribution != null) {
            LOG.info("provider 类型由插件接管: type={} plugin={} provider={}",
                    type, contribution.getDisplayName(), provider.getName());
            created = new PluginLlmClientAdapter(provider, contribution, streamExecutor);
        } else {
            created = creators.get(type).create(provider);
            if (created == null) {
                throw new JellyfishException("failed to create LlmClient for provider: " + provider.getName());
            }
        }
        clientCache.put(cacheKey, created);
        return created;
    }
}

逐段解释：

  • normalize()（:263）做小写归一，这就是 google / anthropic 别名能生效的地方。
  • 「内核自带类型先行」是关键的优先级选择：if (!creators.containsKey(type)) 只在内核不认识时才问插件。 这意味着插件无法覆盖 openai / claude 这类内置类型。
  • 缓存键是 type|name|apiKey|baseUrl（:269），LRU 上限 128（:54）， 整个「查 → 建 → 回填」在锁内完成，避免并发重复创建客户端（每个客户端都持有 HTTP 连接池）。
  • 插件接管时打一条 INFO 日志（provider 类型由插件接管）——这是排查「为什么流量走了别的实现」的第一手线索。
设计依据：为什么内置优先，而不是后注册的赢？

如果允许插件覆盖内置类型，那么「同一个 models.json 在两台机器上跑出不同行为」就变得极其容易—— 只要插件目录里多了一个 jar。而 type: claude 这种写法，用户预期的是内核实现在干活。 让插件用新 type 名接管（例如 type: my-vendor），语义清晰且不会意外改行为。

另外一个实际考虑：内置类型是经过测试的那条路径。允许覆盖意味着任意插件都能让内核的核心功能（对话）失效， 而这个故障会表现为「所有请求都 400」，排查时很难联想到插件。

3. vendorBody / vendorHeaders：给私有字段留的透传口

中性抽象解决不了「厂商出了个新参数」这件事。做法是留一个透传口，让用户直接把原始字段塞进请求。

来源合并方向写入位置
vendorBody 只来自 models.json（Provider 段 + Model 段），与 agents.json 无关 深合并，且 model 覆盖 provider（VendorBody.merge:141，由 ModelTuning.of:88 组装） 请求体构建的最后一步：VendorBody.applyTo（OpenAI :203、Claude :211、Gemini :220）
vendorHeaders 同上，但只有 provider 级 在鉴权头之后后应用，同名头用户优先（:91 / :111 / :176） 构造请求时（authorizedRequest）

两条保护措施值得单独记：

  • 保留键被挡住：RESERVED_KEYS（VendorBody.java:74）拦下 temperature / max_tokens / cache_control / messages 这类内核自己要写的键，任意嵌套深度都拦。被拦的字段静默丢弃。
  • 头部的保护范围小得多：只有 6 个协议头被挡，其余同名头用户优先。 这是刻意的——厂商私有头（如某些网关的租户头）本来就该让用户覆盖。
坑点：改 vendorBody 不在缓存签名里

客户端缓存键是 type|name|apiKey|baseUrl（LlmClientFactory.java:269）， 不含 vendor 相关配置。所以改了 models.json 里的 vendorBody 之后， 已经缓存的客户端不会重建——必须 clearCache() 或 /reload。 源码注释专门标了这一点。

相关的第二个坑：保留键是静默丢弃的。你在 vendorBody 里写 "temperature": 0.3 想覆盖采样参数，结果什么也没发生、也没有任何提示—— 因为采样参数应该写在 sampling 段里。

第三个坑在 Gemini：它的请求体是嵌套结构（generationConfig / toolConfig）， 必须深合并，浅合并会把整个 generationConfig 挤掉， 表现是「配了 vendorBody 之后模型完全不听参数」。

4. 采样参数：「没写」与「写了 0」

这是这一层最容易被忽视、但影响面最大的一条约定。先看结论：

设计依据：用包装类型的 null 表达「未表态」

LlmRequest 里 temperature / maxTokens / topP / topK / stop 全部用包装类型（LlmRequest.java:22 起）。判定在各客户端的 if (request.getTemperature() != null) （Claude :171、OpenAI :158、Gemini :352）。

为什么不能统一用 double 加一个「-1 表示没配」的哨兵值？ 因为 -1 本身对 topK 非法但语义上可解释，一旦哪天厂商支持了它， 这个哨兵就变成歧义。更重要的是：哨兵值需要每个使用点都记得判断， 而 null 检查是 Java 的默认习惯。用一个「根本不能出现在合法值域里」的类型状态来表达「没表态」， 比用一个「碰巧非法」的数值稳健。

写法结果依据
不写 temperature请求体里没有这个字段，厂商用自己缺省null → 不下发
写 "temperature": 0请求体里确实是 0（确定性输出）0 合法且保留
写 "stop": []不下发（空列表 = 没表态）SamplingSettings 的空列表处理
写 NaN / 负数丢弃 + 发告警，回退缺省SamplingSettings.cleanTemperature（只拒 NaN / Inf / 负数）
坑点：没有任何「思考模式 vs 采样参数」的互斥校验

很多厂商在思考 / 推理模式下会忽略采样参数且不报错。 Jellyfish 不做这个校验——SamplingSettings 的类注释直接说明了这一点： 思考类参数一律走 vendorBody 透传，而思考模式下厂商会忽略采样参数。

所以现象是「配了 temperature 没生效」。别去找内核的 bug，先确认这个模型当前是否开着思考模式。 同类坑还有：model 级无法单独关掉 provider 级已经配好的项（merge 的语义是覆盖不是删除）， 所以要控制某个模型的采样参数，就在 model 级配全。

DeepSeek 是典型例子：思考模式下采样参数厂商侧无效；Claude 4.7+ 收到 temperature / top_p / top_k 会直接 400（ClaudeLlmClient.java:180）；另外 Claude 的 thinking.budget_tokens 必须小于本次 max_tokens， 没配 maxOutputTokens 时它取 4096（:62）——这两条一组合，配了大的 thinking 预算但没配 maxOutputTokens 就会 400。

工具调用分片怎么拼

流式协议下，一个工具调用的 id / name / arguments 是分片到达的， 只能靠 index 关联。累积算法在 StreamToolCallAccumulator.merge:36：

  • 按 index 合并 id / name / arguments；
  • 没有 index 时用一个伪造的 key（100000+）（:19）—— 宁可把这一片单独放，也不要错误地把它拼到第 0 个调用上（那会让 arguments 变成非法 JSON）；
  • arguments 是字符串拼接，拼完才做 JSON 解析——所以任何一片丢了，最终就是解析失败。
坑点：流式的错误不是异常，是回调

非 2xx 在流式路径上走 onError(LlmHttpException)，不抛异常； 同步路径才抛。而且 onError 与 onComplete / onCancelled 互斥， 实现监听器时不能重复收尾——否则会出现「重复落库 / 重复计数」这类问题。

另一个容易踩的：max_tokens: 0 只有 Claude 合法，且它与 stream 互斥（内部退回 1）； OpenAI / Gemini 的下限是 1（由 MIN_OUTPUT_TENS 换算）。 最后：maxTokensField 只有模型级配置且缺省 max_tokens—— 字段名猜错就直接 400，而且报错信息来自厂商，不一定指向配置。

插件也能提供模型厂商，走 ProviderContribution 这个扩展点。适配器是 PluginLlmClientAdapter（538 行）， 它的核心动作是把内部请求一次性转成不可变快照：

设计依据：为什么必须做「快照」而不是直接给内部对象？

因为插件是别人写的代码，跑在同一个 JVM 里。如果直接把内核的 LlmRequest 交给它， 它就拿到了一堆可变对象：能改 messages、能在里面塞字段、能持有引用延迟改。 而那份请求之后还要被缓存前缀比对（10 页的 CacheBreakWatcher）， 一旦被改，缓存结论就失真了。

更根本的理由在 AGENTS.md 的关键不变量里：「跨边界载荷必须是 api 侧快照值类型」， 而且这类快照恰好只能有一个可见构造器。这是个聪明的约束——如果只有一个构造器， 就没人能绕过它构造出一个「内容不同但类型相同」的对象，插件也就无法伪造内核载荷。 另外 -parameters 编译参数因此不允许去掉（构造器参数名被用于反射绑定）。

设计依据：从「靠注释镜像」改成「一次调用」

类注释（:22-26）把这段历史写得很直白：「这条三级回落原本被写了两遍—— ReActLooper 一份、ConversationCompactor 一份，靠注释声明「刻意保持镜像」。 而两者的判据必须相同：压缩要按同一个模型的窗口裁剪、花同一个模型的额度，一旦两边漂移， 摘要就会以另一个模型的上下文长度去衡量对话。与其靠约定，不如让它变成一次调用。」

这是「重复代码 + 注释约定」失效的典型案例：两处逻辑在各自看起来都对的情况下缓慢漂移， 而症状（摘要按错的窗口裁剪）出现在离改动点很远的地方。 「刻意保持镜像」这个注释本身就是代码坏味道的信号—— 写这句话的时候，作者已经知道这里有风险了，只是还没付出重构成本。

顺带一提：这个仓库里「靠注释约定」的地方还有一处（AGENTS.md 说「不要照抄 shutdown 顺序清单」）， 但那条是刻意的——因为顺序的理由是依赖关系而非序号，抽不出一个可复用的函数。 区分「该抽」与「该用注释说清」的标准，是这份知识能不能表达成一次调用。

设计依据：为什么「解析不到」不能静默用缺省？

这个项目的立场在这里又一次体现：配置错误要么立刻可见，要么别生效（ 02 页的 ${VAR} 缺失也是同一个取向）。

如果解析不到就「随便用一个默认模型」，现象会是「我配了模型但对话走的是别家」—— 而且你只有在看账单或对比输出质量时才会察觉。上抛异常则把问题钉在第一次请求上。

子代理那条「不继承父模型」则相反方向地避免了另一个坑： 如果继承，一次 task 委派就会让子代理用父会话的模型跑—— 而父会话可能是用户为了省钱临时切的便宜模型，子代理的任务却需要更强的推理。 显式绑定（agent 的偏好模型）比隐式继承更容易预测。

设计依据：为什么「两个字段都看一眼」比「按厂商分支」好？

OpenAI 与 DeepSeek 的缓存命中字段名不同（prompt_tokens_details.cached_tokens vs prompt_cache_hit_tokens）。直觉做法是在子类里各写一份解析， 但作者选择在基类里「两个都读、取有值的那个」，注释给了理由：

「比为每家在子类里各写一份解析便宜，也不会因为某家换字段而静默漏读」。

第二条是关键：如果按厂商分支，某家改了字段名之后，那一支拿到的永远是 0—— 而 0 在业务上没有异常，只会让命中率看起来突然变差。 「都读一遍」把这个故障从「静默漏读」变成了「照样读到」，代价是多一次 JsonNode.path()。

这是个可复用的模式：面对同一语义的多个字段名，读全部再取有效值，比按来源分支更抗协议演进。

Claude 的输入是三项之和，别直接拿一个字段

Anthropic 把输入拆成互斥的三部分：普通输入 / cache_read_input_tokens / cache_creation_input_tokens。缓存命中率的分母必须是三者之和， 否则算出来的命中率会大于 100%（cacheRead 可以接近甚至超过基础输入）。 这也是 10 页那条「分母是总输入」在 Claude 上的具体含义。

另外 ClaudeLlmClient.java:46 记了一条实测行为： 短对话下 cache_creation_input_tokens 为 0， 「因此短对话打断点是无害的空操作，不是错误」——看到 0 不用担心配置错了。

10.3 三家都不记思考 token——这是一个真实的记账缺口

坑点：思考 token 花了钱，但不在 /usage 里

LlmUsage 里没有 reasoning / thinking 字段， 而三家的解析里也都没有读这类字段：

  • OpenAI / DeepSeek：只读 prompt_tokens / completion_tokens / total_tokens / 缓存两项（:357-371），不读 completion_tokens_details.reasoning_tokens。
  • Claude：只读 cache_read_input_tokens 与 cache_creation_input_tokens（:634-635），不单独统计思考。
  • Gemini：不读 thoughtsTokenCount（:498-499 的五个参数里没有它）。

所以准确的说法是：开启思考 / 推理模式后，思考部分产生的 token 不会出现在 Jellyfish 的用量统计里。 它们的费用通常被厂商计入 completion_tokens（或另有单独计费规则）， 但你无法从 /usage 分辨「这笔账单里有多少是思考」。

做成本分析时的实际影响：如果开了思考且预算给得很大，/usage 的输出会明显低于 厂商账单。这不是 bug，而是当前实现只对齐了「输入 / 输出 / 缓存」这五个口径。 想精确分摊思考成本，只能去厂商后台看明细。

11. 本页坑点小结

LLM 适配层的坑
  • 「0 vs 未写」全靠包装类型的 null：把内部字段改成 int 就会把「未表态」当「配了 0」下发。
  • 改 vendorBody 不在客户端缓存签名里 → 必须 /reload 或 clearCache()。
  • vendorBody 写保留键会被静默丢弃：temperature / max_tokens / cache_control / messages，任意嵌套深度都拦。
  • Gemini 必须深合并，浅合并会把 generationConfig 整体挤掉。
  • 用户 vendorHeaders 会覆盖内核同名头（只有 6 个协议头被挡）。
  • 流式非 2xx 走 onError 不抛异常；onError 与 onComplete / onCancelled 互斥，别重复收尾。
  • 没有思考模式与采样参数的互斥校验，配错只会「配了不生效」。
  • Claude 代际差异：4.7+ 收到 temperature / top_p / top_k 直接 400； thinking.budget_tokens 必须 < 本次 max_tokens（未配则 4096）。
  • maxTokensField 猜错直接 400，且报错来自厂商不一定指向配置。
  • Anthropic 不标 cache_control 命中率恒为 0；命中率分子分母都在 SessionUsageSnapshot，别自己算。
  • keepAliveSeconds 缺省关闭：开了就是花钱买命中率，且与 thinking.budget_tokens 互斥。
  • 插件不能覆盖内置 type：openai / claude 这类名字永远走内核实现。
  • 思考 token 不记账：LlmUsage 只有五字段，三家都不读 reasoning / thinking 数量。 开了思考模式后 /usage 会明显低于厂商账单。
  • Claude 的输入是三项之和（普通 + cache_read + cache_creation）， 只取其中一个字段去算命中率会得到大于 100% 的结果。
  • Gemini 的 cacheWriteTokens 恒为 0（隐式缓存没有「建缓存」），不是漏读。
  • 模型解析不到时是抛异常，不是用默认：第一次请求就会失败，别以为是「配了不生效」。
  • 子代理不继承父会话的模型：它用被委派 agent 的偏好模型（或全局默认）； 想让子代理用特定模型，得在那个 agent 上配 model。

关键结论

  1. 这一层用「薄通用 + 厚专用」的分层：只有 HTTP 与 SSE 读流是真正共享的，消息形状各写各的。因为消息形状的差异不是字段名差异，是模型差异。
  2. type 不是「协议」的同义词，而是注册表 key；路由顺序「内置优先、插件兜底」保证了同一个配置文件在两台机器上行为一致。
  3. vendorBody 是给「厂商出参数的速度快于内核发版」这个现实留的口子，代价是保留键必须被静默拦掉——所以配错了没有任何提示。
  4. 「没写 vs 写了 0」用类型状态（null）而不是哨兵值表达，是这一层定义得最干净的一条约定，也是排查采样问题时第一个要确认的假设。
  5. PluginLlmClientAdapter 的「快照 + 唯一可见构造器」是插件隔离边界在数据层面的实现——插件能读，不能改，也不能伪造。
  6. 模型解析链的教训值得单拎出来：「两处逻辑 + 注释声明保持镜像」是坏味道。 压缩与循环器各自实现过一遍三级回落，一旦漂移，症状（摘要按错误的窗口裁剪）会出现在离改动点很远的地方—— 所以它被抽成了 SessionModelResolver 一次调用。
  7. 用量统计目前只对齐五个口径（输入 / 输出 / 总量 / 缓存读 / 缓存写）。 思考模式的 token 不在其中，这是做成本分析时必须知道的边界。
