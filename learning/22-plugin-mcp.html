22 MCP 插件 重点

26 页把 MCP 当成一种「外部能力来源」横向比过；这一页讲它的 接入实现：一个进程内插件怎么把一个不受信的第三方子进程，伪装成内核里的普通工具， 而且不让它绕开审批、不让它拖死内核。

学习目标

  • 说清 MCP 在 Jellyfish 里被定位成什么，以及它为什么必须是插件而不是内核内置；
  • 知道传输方式是什么（stdio 子进程 + 换行分帧），以及 stderr、行长上限、环境变量、进程树各自怎么处理；
  • 掌握协议层的三个动作：握手与能力协商、按 id 的请求-应答配对、通知的处理位置；
  • 拿到 servers[].* 与五个全局键的逐个字段说明（含缺省值与上界）；
  • 解释 tools/list 的工具怎么变成内核工具（命名展开、重名两类冲突、清单整体替换）；
  • 说清 tools/call 的 content 数组如何映射成 Jellyfish 的工具结果，二进制为什么要落盘；
  • 理解为什么 MCP 工具与内核工具在同一张扩展点表里，以及权限闸门到底守住了什么、没守住什么。

1. MCP 是什么，这里怎么用

MCP（Model Context Protocol）是一套「客户端 ↔ 外部能力提供方」的协议：server 以子进程或服务的形态 存在，通过 JSON-RPC 暴露它自己的能力（主要是工具），客户端负责拉起它、握手、拉清单、转发调用。 它与 Jellyfish 的 PF4J 插件机制不是同一层东西： PF4J 是进程内的行为扩展（改权限判定、改提示词组装、换压缩策略都能做）， MCP 只能加「工具」这一维，但换来的是进程边界天然隔离与跨产品通用。

本插件的自述写得很直白——插件仓库的描述符里把工具命名规则直接写进了 plugin.description：

plugin.id=jellyfish-plugin-mcp
plugin.class=zcd.jellyfish.plugin.mcp.McpPlugin
plugin.version=0.1.1
plugin.provider=zcd
plugin.description=MCP 客户端：stdio 连接 MCP server，工具以 mcp__<server>__<tool> 形式接入

# 内核未向 PF4J 声明系统版本（缺省 "0.0.0" 会让这条校验直接放行），写 * 是显式声明「不限版本」。

注意 plugin.id 的注释（plugin.properties:3）：「plugin.id 同时是注册表的 owner：插件卸载时按它批量回收工具、权限拦截与命令」。这句话是后面所有「谁负责收干净」问题的答案—— 回收不是这里手写的，而是 16 页讲的 PluginOwnerNamespace 前缀回收。

设计依据：为什么 MCP 是插件，不是内核内置的一个「工具来源」

McpPlugin.java:39-45 的类注释给了一条与所有既有插件不同的性质： 工具是运行期注册的——「这是本插件依赖「注册窗口是插件存活期」那条契约的地方， 也是它与所有既有插件的根本差别——那些插件的能力在 start() 里就是已知的」。

换句话说，如果内核把 MCP 写死成一种工具来源，内核就必须自己知道「进程怎么起、清单什么时候变、 断了怎么办」；而这套知识对一个「只想要工具」的场景毫无复用价值。做成插件之后， 内核只看到「有人在存活期里陆续注册工具」，这条它本来就会。

2. 传输：一个子进程 + 换行分帧

传输方式是 stdio：插件起一个子进程，父进程写它的 stdin、读它的 stdout， 一条消息一行 JSON。这不是「顺手选的」，而是由协议约束推出的最短实现—— 消息内部不允许出现换行，那么「按行读」就是完整的分帧实现，不需要长度头，也不需要自己维护缓冲区。

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpStdioTransport.java:141-158（起进程：不合并 stderr，环境交给 applyEnvironment）
    static McpStdioTransport start(McpServerConfig config) throws IOException {
        List<String> commandLine = new ArrayList<String>();
        commandLine.add(config.command());
        commandLine.addAll(config.args());
        ProcessBuilder builder = new ProcessBuilder(commandLine);
        // 刻意不合并两条流：stderr 里是服务端日志，混进 stdout 会破坏分帧
        builder.redirectErrorStream(false);
        applyEnvironment(builder, config);
        Process process = builder.start();
        BufferedWriter writer = new BufferedWriter(
                new OutputStreamWriter(process.getOutputStream(), StandardCharsets.UTF_8));
        BufferedReader reader = new BufferedReader(
                new InputStreamReader(process.getInputStream(), StandardCharsets.UTF_8));
        Thread drainer = drainStderr(config.id(), process);
        LOG.info("MCP server 进程已启动: id={} command={} args={}", config.id(), config.command(),
                maskArgs(config.args()));
        return new McpStdioTransport(config.id(), process, writer, reader, drainer);
    }

这里有三处不能省的细节：

  • redirectErrorStream(false)：server 的日志走 stderr。把它并进 stdout， JSON 流里就会混进「连不上数据库」这类人类文本，表现为「偶尔收到一帧解析不了」。这里的取舍是 宁可自己排空 stderr——drainStderr（McpStdioTransport.java:533 起） 起一条守护线程持续读，因为不读的话，日志写满管道缓冲区会把 server 自己卡死。
  • 命令与参数分开：command 是可执行文件、args 是列表。 McpServerConfig.java:21-24 说明了理由：把整条命令行写成一个字符串就得自己处理引号与空格， 而「带空格的参数」是最常见的用法。原文还点了与 shell 插件的对比—— 「那里要的是用户怎么敲就怎么跑，这里要的是「哪个可执行文件、哪些参数」这件事不能被再解释一次」。
  • 启动日志走 maskArgs：它记的是「起了哪个 server、怎么起的」， 是排查起不来的第一眼线索，但参数里常见 --token sk-***、 --api-key=...，所以要按旗标名遮蔽（McpStdioTransport.java:226-257）。 它只认旗标名，不认值的样子，因此 --header "Authorization: Bearer x" 这种「密钥藏在普通旗标值里」的写法认不出来。

2.1 子进程的环境是白名单，不是「继承 + 剔除」

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpStdioTransport.java:183-206
    static Map<String, String> resolveEnvironment(Map<String, String> parent, Map<String, String> overrides) {
        Map<String, String> resolved = new LinkedHashMap<String, String>();
        if (parent != null) {
            for (Map.Entry<String, String> entry : parent.entrySet()) {
                if (entry.getKey() != null && entry.getValue() != null && isInheritable(entry.getKey())) {
                    resolved.put(entry.getKey(), entry.getValue());
                }
            }
        }
        if (overrides != null) {
            for (Map.Entry<String, String> entry : overrides.entrySet()) {
                if (entry.getKey() != null && entry.getValue() != null) {
                    resolved.put(entry.getKey(), entry.getValue());
                }
            }
        }
        return resolved;
    }

白名单本身在 McpStdioTransport.java:76-78：PATH、HOME、 LANG、TMPDIR、TEMP、TMP、USER、 LOGNAME、SHELL，加 Windows 的 SystemRoot、 PATHEXT、ComSpec、windir；再加一个前缀 LC_ （McpStdioTransport.java:81，因为区域设置有多套键，逐个列会漏）。

这段逻辑为什么要单独抽成一个纯函数，源码注释也讲了：它让「哪些变量过不去」可以被断言， 而不必真起一个进程去读它的环境——那样测试就会依赖跑测试那台机器上刚好设了什么变量。 测试正是这么用的（McpStdioTransportTest.java:82-83「父进程里的凭据不应跟过去」）。

坑点：白名单是「破坏性」的安全修复，老配置可能因此起不来

现象：同一个 server，升级之后忽然起不来，或者起来之后连不上数据库—— 而命令、参数、版本都没动。根因：子进程环境从「继承父进程全部 + 叠加配置」 改成了白名单（McpStdioTransport.java:76-78 与 :183-206）， 宿主 JVM 里那些 provider 凭据（ANTHROPIC_API_KEY 之类）不再跟过去。 规避：需要什么就写进该 server 的 env 段——显式即允许， 这与脚本插件的 ${ENV} 插值同一条口径。

顺带记住这条改动的理由：对面是个不受信的第三方进程（用户从 npm/pip 拉下来的 server）， 「继承」意味着 JVM 里的一切都会跟过去。方向反过来之后，漏一个变量只是「少给了一点便利」， 而不是「多给了一份凭据」。

2.2 行长上限与关停四步

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpStdioTransport.java:312-334
    static String readLineWithinLimit(BufferedReader reader, String serverId) throws IOException {        StringBuilder line = new StringBuilder();
        while (true) {
            int next = reader.read();
            if (next == -1) {
                return line.length() == 0 ? null : line.toString();
            }
            if (next == '\n') {
                return line.toString();
            }
            if (next == '\r') {
                reader.mark(1);
                int afterCr = reader.read();
                if (afterCr != '\n' && afterCr != -1) {
                    reader.reset();
                }
                return line.toString();
            }
            line.append((char) next);
            if (line.length() > MAX_LINE_CHARS) {
                throw new IOException("MCP server 输出的一行超过上限 " + MAX_LINE_CHARS + " 字符: id=" + serverId);
            }
        }
    }

为什么不用 BufferedReader.readLine()：它没有长度上限，而这里读的是子进程的输出 ——MAX_LINE_CHARS 是 4 MiB（McpStdioTransport.java:61）， 一个不换行、一直吐的 server 能直接把宿主 JVM 撑爆，而它连「恶意」都不需要， 一句「把整个数据库 dump 到 stderr」的日志就够了。分帧语义保持 \n、\r、 \r\n 三种都算，因为「对面是第三方程序，不该要求它只用一种换行」。

关停是四步而不是一步（McpStdioTransport.java:347-367）： 关 stdin（多数 server 看到 EOF 会自行收尾，代价最小）→ destroy() 并等 2 秒 （GRACE_MILLIS，McpStdioTransport.java:48）→ killDescendants 尽力杀进程树 → destroyForcibly()。

坑点：只杀直接子进程，npx 拉起的 node 会活下来

现象：插件已经停了、进程也退出了，但那个 server 还占着端口与文件句柄。 根因：最常见的 MCP server 用法是 npx -y <package>， 真正干活的是 npx 拉起的 node 孙进程，而 Process.destroy() 只作用于直接子进程。 规避：源码里用 killDescendants（McpStdioTransport.java:409-431） 递归找子进程再发 TERM。

但它刻意是「尽力」的：取 PID 要先用反射试 Process.pid() （Java 9+），失败再退到 JDK 8 的 UNIXProcess 打印格式 （McpStdioTransport.java:434-450），再不行就靠 pgrep -P 递归 （McpStdioTransport.java:458）——pgrep 不存在或没权限时， 就只能杀到直接子进程为止。这是已知边界，日志里有痕迹。

3. 协议层：JSON-RPC 的分派与配对

方法名与错误码全部收在一个不可实例化的常量类里。理由源码写得很具体： 「方法名会同时出现在「发请求」与「识别来的是什么」两侧，各写一遍字面量的结果是一侧改了、 另一侧静默不匹配，而现场表现是「某个功能就是不生效」」。

3.1 握手：声明 roots，然后发一条 notifications/initialized

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpServerConnection.java:320-337
    private void initialize(long timeoutMillis) {
        ObjectNode params = McpJson.object();
        params.put("protocolVersion", McpProtocol.PROTOCOL_VERSION);
        ObjectNode capabilities = params.putObject("capabilities");
        capabilities.putObject("roots").put("listChanged", false);
        ObjectNode clientInfo = params.putObject("clientInfo");
        clientInfo.put("name", CLIENT_NAME);
        clientInfo.put("version", "0.0.1");
        JsonNode result = request(McpProtocol.METHOD_INITIALIZE, params, timeoutMillis,
                CancellationToken.NONE);
        String serverVersion = McpJson.text(result, "protocolVersion", null);
        if (serverVersion != null && !McpProtocol.PROTOCOL_VERSION.equals(serverVersion)) {
            // 规范允许 server 回一个它支持的版本；不相等不是错误，但它决定了对面按哪套规则说话
            LOG.info("MCP server 协商到不同协议版本: id={} ours={} theirs={}", config.id(),
                    McpProtocol.PROTOCOL_VERSION, serverVersion);
        }
        notify(McpProtocol.METHOD_INITIALIZED, null);
    }

握手的顺序是 initialize（请求，等到应答）→ notifications/initialized （通知，不等应答）。上报的 clientInfo.name 是常量 "jellyfish" （McpServerConnection.java:56），version 写死 "0.0.1"—— 它只是一个自报名片，不参与任何判定。

更值得琢磨的是能力协商里只声明了 roots，而且 listChanged 是 false。源码给的理由是「声明了就得能应答」：roots/list 我们确实答得上来 （McpServerConnection.java:483-491 把进程工作目录作为唯一的根返回）， 而 sampling / elicitation 做不到——「声明了却办不到比不声明更糟： server 会按「客户端支持」去规划它的行为」。这条见第 8 节。

3.2 读线程是唯一的分发点

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpServerConnection.java:387-410
    private void dispatch(String line) {
        ObjectNode message;
        try {
            message = McpJson.parseObject(line);
        } catch (JellyfishException e) {
            // 解析不了的那一行只可能是服务端日志混了进来或对面不是 MCP server；
            // 丢掉它是安全的：协议没有「半条消息」这种状态，而留着它会毒化后续所有处理
            LOG.warn("忽略无法解析的 MCP 消息: id={} reason={}", config.id(), e.getMessage());
            return;
        }
        JsonNode id = message.get("id");
        String method = McpJson.text(message, "method", null);
        if (id == null || id.isNull()) {
            if (method != null) {
                handleNotification(method, message);
            }
            return;
        }
        if (method != null) {
            handleServerRequest(id, method);
            return;
        }
        completePending(id, message);
    }

这个 if 链就是 JSON-RPC 的全部路由规则（McpServerConnection.java:23-29 的类注释）： 带 id 带 method 的是 server 主动发来的请求； 带 id 不带 method 的是我们某次请求的应答； 不带 id 的是通知。不需要额外的状态机。

应答配对靠 id，不靠顺序：每个请求发出前登记一个等待位（pending， McpServerConnection.java:90），超时后摘掉等待位 （McpServerConnection.java:770-789 的 request 尾部）， 迟到的应答按 id 找不到人，于是被计数并丢弃 （McpServerConnection.java:666-687 的 completePending → McpRegistry.noteLateResponse），而不是错误地唤醒一个已经在等别的东西的调用。 这个计数会显示在 /mcp 台账上（McpLedger.java:61-63）。

请求 id 用 AtomicLong 递增（McpServerConnection.java:77）， 组装格式在 requestMessage（McpServerConnection.java:811-822）： jsonrpc / id / method / params 四个字段， 序列化出来是单行（McpJson.write，McpJson.java:110-118）。

3.3 通知为什么必须换一条线程

notifications/tools/list_changed 是在读线程上收到的， 而重扫要发一个 tools/list 请求并等应答——应答只能由同一条读线程投递。 直接在读线程上做，就是一条线程等它自己。因此通知处理必须转到另一条线程 （McpServerConnection.java:79-87 的 notificationWorker， 单线程守护池），失败只记告警不外抛（McpServerConnection.java:437-449）。

设计依据：pendingLock 保护的到底是什么

关连接时要先叫醒在途请求（failAllPending），而调用方是「先入表、再等应答」。 两件事分头做，就会出现「入表落在叫醒之后」——那条等待位再没有人来唤醒； 而 callTimeoutSeconds 可以配成 0（不超时），那就是永远等下去： 表现是 react 线程永久挂住。

因此 McpServerConnection.java:92-100 的注释把这条写成纪律： 「立关闭旗」与「请求入表」必须在同一把锁内（与 16 页那处 「检查与入表同一把锁」是同一条），于是关停之后才到达的调用是显式失败， 而不是「等一个永远不会来的应答」（McpServerConnection.java:744-751）。

5.2 先入表再连接：一个原子性细节

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpPlugin.java:430-462
    private boolean connectOne(McpConfig parsed, McpRegistry parsedRegistry, McpServerConfig server) {
        // 工具接收方需要「它所属的那个连接」，而连接又要先有接收方才能构造：
        // 用一个一元素数组把这两件事的顺序解开。数组是 final 的，每个 server 一份
        final McpServerConnection[] holder = new McpServerConnection[1];
        Consumer<List<McpToolDefinition>> sink = tools -> {
            McpServerConnection connection = holder[0];
            if (connection == null || stopping || !isCurrent(server.id(), connection)) {
                return;
            }
            try {
                registrar.apply(connection, server, tools);
            } catch (RuntimeException e) {
                LOG.warn("注册 MCP 工具失败: id={}", server.id(), e);
                parsedRegistry.noteWarning(server.id(), "工具注册失败：" + e.getMessage());
            }
        };
        McpServerConnection connection =
                new McpServerConnection(server, parsed, parsedRegistry, sink, spill, transportFactory);
        holder[0] = connection;
        connection.onDisconnected(() -> handleDisconnected(server, connection));
        if (!adopt(server.id(), connection)) {
            return false;
        }
        try {
            connection.connect();
            return true;
        } catch (RuntimeException e) {
            // 单个 server 连不上不该让插件 FAILED：其余 server 与「没有 MCP」都还能用。
            // 失败状态由连接对象自己记（它才知道握手停在哪一步），这里只负责收尾资源
            discard(server.id(), connection);
            closeQuietly(connection);
            return false;
        }
    }

三处关键决定：

  • 一元素数组解顺序：工具接收方（sink）需要「它所属的那个连接」， 而连接构造时又需要接收方。用一个 final 数组把这两件事的顺序解开，比引入一个 setter 或可空字段更不容易出错。
  • 接收方自己确认「我这条还作数吗」：isCurrent （McpPlugin.java:514-519）。一次清单拉取是「发请求、等应答」， 期间连接可能已经断开、被重连换掉、或插件已经停了；不确认的后果是把一批工具重新注册回 一条已经死掉的连接上（McpPlugin.java:505-511）。
  • 先 adopt 再 connect：adopt 拿着 connectionLock 问一句「停了没」（McpPlugin.java:527-545）。 连接线程顶部的停止检查挡不住这段窗口——「它检查完到这里之间隔着构造与整个 connect()， 而 connect() 是要起子进程的」。

单个 server 连不上不会让插件变成 FAILED：其余 server 与「没有 MCP」都还能用。 失败状态由连接对象自己记（它才知道握手停在哪一步，McpServerConnection.java:190-200）， 调用点只负责收尾资源。

5.3 断开与重连：退避封顶，用尽就停

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpPlugin.java:375-399
    private void reconnect(McpConfig parsed, McpRegistry parsedRegistry, McpServerConfig server) {
        long backoff = reconnectInitialMillis;
        for (int attempt = 1; attempt <= reconnectMaxAttempts; attempt++) {
            if (stopping) {
                return;
            }
            parsedRegistry.noteState(server.id(), McpRegistry.State.RECONNECTING,
                    "连接已断开，第 " + attempt + " 次重连尝试");
            if (connectOne(parsed, parsedRegistry, server)) {
                LOG.info("mcp server 已重连: id={} 第 {} 次尝试", server.id(), Integer.valueOf(attempt));
                return;
            }
            if (stopping || attempt == reconnectMaxAttempts) {
                break;
            }
            if (!sleepQuietly(backoff)) {
                return;
            }
            backoff = Math.min(backoff * 2L, reconnectMaxMillis);
        }
        if (!stopping) {
            parsedRegistry.noteState(server.id(), McpRegistry.State.FAILED,
                    "重连 " + reconnectMaxAttempts + " 次仍失败，已放弃（/reload 可重试）");
        }
    }

参数写死在常量里、不可配（McpPlugin.java:66-74）： 初始 1 秒（RECONNECT_INITIAL_MILLIS）、每次翻倍、封顶 60 秒 （RECONNECT_MAX_MILLIS）、一次断开最多再试 6 次（RECONNECT_MAX_ATTEMPTS）， 合计约一分钟。源码给的理由是「每次尝试都可能真的起一遍进程（npx 还会拉网）， 一个装坏了的 server 不该让用户一直为此付费」。

注意失败现场的处理：每轮失败的原因由连接对象自己写进「最近错误」，最后放弃时只改状态的说明文字， 不去覆盖 lastError（McpPlugin.java:365-372）。 「用户最需要看到的恰恰是「上次到底是为什么起不来」（命令写错、缺解释器、握手被拒）， 而不是「重试了 6 次」」。

「断开」这个事实只上报一次（McpServerConnection.java:175-180 的 disconnectNotified），而且只报「不是我们关的」那种： 主动 close() 的路径有自己的收尾。收到断开通知后要做的三件事在 McpPlugin.java:479-500：收旧连接的资源 → 注销该 server 的工具 → 排队重连。

坑点：断开时不摘工具，模型会拿着「撒谎的清单」规划下一步

现象：server 进程挂了，但模型还在调用它的工具，每次都以「MCP server 未连接」收场。 根因：注册表里那批工具还挂着。源码在 McpPlugin.java:474-478 写得很直白： 「留着它们，模型会继续调用一批每次都以「未连接」收场的工具——那份清单等于在撒谎， 而模型据此规划出来的下一步全都白费」。 规避：handleDisconnected 里第一步就是 registrar.close(server.id())，重连成功后再由新连接把工具装回去。 测试用例正对着这条：「server 进程退出后，它的工具必须从注册表摘掉：不能留一批必然失败的工具」 （McpPluginTest.java:214-215）。

  • 关连接排在 awaitConnector 之前：连接线程此刻可能正卡在握手等应答上， 而叫醒在途请求的正是 close()——先等就会白等到超时。
  • 等连接线程本身：16 页讲的 AGENTS.md 约定是 「产生注册的后台线程必须在 stop() 返回前停下来」，而等待是有界的 （2 秒，McpPlugin.java:242-257），因为一个卡在进程启动或读管道上的线程无法被强杀 ——那种情况只能如实告警。
  • 最后清落盘目录：二进制内容写到临时目录，停插件时整棵删掉 （McpMediaSpill.java:124 起）。

还有一处「两侧各查一次」的收口：close() 是「先立旗再收资源」， 而它读 transport 的那一刻这份资源可能还不存在（进程刚要起）。 因此 connectInternal 起完进程要复查一次 closed，把那之后出生的资源自己收掉 （McpServerConnection.java:204-215）。测试用「挡住传输出生再 stop()」 精确验证了这条路径（McpPluginTest.java:152-153）。

四件事发生在这里：

  1. 按上限截断：超过 maxToolsPerServer 的其余工具不注册，只记一条告警； 没有 name 的工具直接跳过。
  2. 名字展开：McpToolName.qualify(serverId, original, toolPrefix, maxLength)。
  3. 同一个 server 内撞车就消歧：加哈希后缀（见下）。
  4. 参数与描述取 inputSchema.properties / required， 描述缺失时退到 title（McpServerConnection.java:594-605）—— 「一段空白描述等于一个永远不会被调用的工具」。

6.3 名字展开：为什么要加前缀、清洗字符、超长加哈希

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpToolName.java:52-60 Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpToolName.java:81-93
    static String qualify(String serverId, String toolName, boolean prefixed, int maxLength) {
        String body = sanitize(toolName);
        String candidate = prefixed ? PREFIX + sanitize(serverId) + SERVER_SEPARATOR + body : body;
        if (candidate.length() <= maxLength) {
            return candidate;
        }
        String hash = shortHash(candidate);
        return candidate.substring(0, maxLength - HASH_LENGTH - 1) + "_" + hash;
    }

    static String sanitize(String raw) {
        if (raw == null || raw.trim().isEmpty()) {
            return "tool";
        }
        StringBuilder sanitized = new StringBuilder(raw.length());
        for (int index = 0; index < raw.length(); index++) {
            char current = raw.charAt(index);
            boolean allowed = (current >= 'a' && current <= 'z') || (current >= 'A' && current <= 'Z')
                    || (current >= '0' && current <= '9') || current == '_' || current == '-';
            sanitized.append(allowed ? current : '_');
        }
        return sanitized.toString();
    }

前缀常量是 mcp__（McpToolName.java:29），server 与工具之间的分隔符是 __（McpToolName.java:32），哈希取 8 位十六进制 （McpToolName.java:35、McpToolName.java:101-115，用 SHA-256 片段）。 三条理由都在类注释里（McpToolName.java:9-25）：

做法不这么做会怎样
加 mcp__<server>__ 前缀 「不加前缀等于让「谁先连上谁占坑」成为事实，而那种冲突的表现是「某个工具忽然变成了别人的」 ——最难排查的一类问题」
清洗字符（只留字母、数字、下划线、连字符） 「带点号的工具名会被厂商在整次请求上拒绝——不是「这个工具不可用」，是「这一轮对话发不出去」」
超长时保留可读前缀 + 8 位哈希 「直接截断会让 ..._create_issue 与 ..._create_issue_v2 变成同一个名字（后注册的那个变成幽灵）」

重名有两类，处理方式不同：

  • 同一个 server 内（清洗或截断之后撞车）→ 就地消歧，加哈希后缀： McpServerConnection.java:651-658 的 disambiguate （"_" + McpToolName.shortHash(original + "@" + index)，必要时先把头部截短）。
  • 与内置工具、或与别的插件撞车→ 内核注册时会失败， 这时只跳过那一个工具并记告警（McpToolRegistrar.java:109-115）。 关掉 toolPrefix 之后最容易撞上内置工具（read_file 就是典型）。

6.4 落进内核：每个 server 一个子上下文，整体替换

Jellyfish-Plugins/jellyfish-plugin-mcp/src/main/java/zcd/jellyfish/plugin/mcp/McpToolRegistrar.java:95-122

        synchronized (lock) {
            closeHandlers(server.id());
            registry.replaceTools(server.id(), tools);
            List<Subscription> created = new ArrayList<Subscription>(tools.size());

            PluginContext serverContext = context.subContext(server.id());

                            tool.descriptor(), new McpToolCaller(tool, invoker, timeoutMillis)));
                    registeredNames.add(tool.qualifiedName());
                } catch (RuntimeException e) {
                    // 名字被占了（关掉前缀时最容易撞上内置工具）：跳过它，让其余工具照常可用
                    LOG.warn("MCP 工具注册失败，已跳过: server={} tool={} reason={}", server.id(),
                            tool.qualifiedName(), e.getMessage());
                    registry.noteWarning(server.id(),
                            "工具 " + tool.qualifiedName() + " 注册失败：" + e.getMessage());
                }
            }

        }

这段的四步顺序本身就是防线（McpToolRegistrar.java:71-93 的注释逐条给了理由）： 关旧处理器 → 装新标记 → 注册新处理器 → 摘掉没注册成的名字。

  • 第 1 步只关处理器、标记留到第 2 步一起换——「若反过来先摘标记，那几步里旧处理器还在， 写类工具就是不需要审批的」。
  • 第 2 步装的是整份清单，替换是原子的：新视图（LinkedHashMap）建好后 一条 put 顶掉旧的，因此不存在「旧名字已删、新名字未进」的空窗 （McpRegistry.java:128-134、McpRegistry.java:167-176）。
  • 第 3 步里每注册成一个名字，它已经在标记表里了；代价是注定注册不上的名字 在第 4 步之前也带着标记，最长一次刷新窗口，「最坏结果是给那个名字多弹一次审批，方向偏严」。
  • 第 4 步 retainTools 摘掉注册不成的名字，否则权限处理器会把占了那个名字的内置工具 认成「我们的写类工具」，让它白多一道审批。

这一段还有一个并发前提：整个 apply 被一把互斥锁串行化 （McpToolRegistrar.java:57-70 的 lock）。两条线程会同时调它—— 连接线程的首轮 refreshTools 与通知线程的 tools/list_changed 重扫， 「后者在读线程收到通知后立刻可能发生，而读线程在握手之前就起了」。不串行化的话 registered.put 会互相覆盖，先注册的那批 Subscription 再没人关， 于是「一批已经不在清单上的工具留在注册表里——模型看得见、调得到，而 server 已经不认识它们了」。 换到的不变量是：「任何时刻，某个 server 的注册恰好对应某一份清单」， 测试标题就叫「两条线程同时换清单：最后留在注册表里的必须恰好是其中一份，不能是混合」 （McpToolRegistrarTest.java:240-241）。

设计依据：为什么整体替换，而不是增量增删

tools/list 返回的是「当前全部」，而工具的名片 （描述、参数 Schema、只读标记）都可能变。增量增删要判断「这个工具是新的还是改过的」， 「而那条判断一旦漏了「改过」这一档，模型就会拿着旧 Schema 去调新工具」 （McpToolRegistrar.java:21-24）。

整体替换的代价是注册表在极短窗口内少了几个名字——而那个窗口里最坏的结果只是 「模型看不到这个工具」。16 页讲的 TypeRegistry 还有一层好处：跨 owner 重名是「压链」而不是报错，所以这里整体关掉再整体装回， 被覆盖的注册项不会丢。

子上下文用 context.subContext(server.id())（PluginContext.java:95）， 落在 jellyfish-plugin-mcp::<serverId> 下（分隔符 ::， PluginOwnerNamespace.java:37）。诊断输出因此能指出「这个工具是哪个 server 提供的」， 卸载时按命名空间一次性收干净。测试断言了这一点： 「应把工具注册到 <插件>::<server> 的子命名空间下」 （McpToolRegistrarTest.java:84-85）。

设计依据：为什么是 ASK 而不是 DENY

MCP 工具的参数 Schema 由对面决定，「而它到底会不会改东西，用户在看到工具之前无法回答。 默认全部可信，等于让「装了一个 server」与「给了它这台机器上的写权限」变成同一件事」 （McpPermissionContribution.java:11-14）。而权限裁定里没有「放行」这一态， 插件只能收紧，因此要的是「让人看一眼再决定」：只读工具免打扰、其余弹一次批准框。

它与 18 页里 shell 插件的分类器是同一种便利机制 ——区分只读与写入，而不是替用户下结论。裁决的构造入口是 PermissionVerdict.ask（PermissionVerdict.java:77）与 PermissionVerdict.abstain（PermissionVerdict.java:67）。

注意：这道闸门不是安全边界

源码把话说得很死（McpPermissionContribution.java:27-30）： 「它不是安全边界：只读与否只由用户写的 readOnlyTools 决定， 用户写错了这里就会放行。真正的边界是「装了什么 server」以及 askTools / allowedTools 那套核心策略——本处理器只是让默认姿势偏保守一点」。

两条推论：一，MCP 工具的参数内容、路径、网络目标，这个插件一概不管， 它只转发——想按路径或命令收紧，那是 06 页的核心策略 与 18 页路径闸门的地盘； 二，在 -cli / -server 下没有审批者， ASK 等于拒绝，因此这两个模式里写类 MCP 工具实际不可用 （Jellyfish-Plugins/README.md:658）。

8.3 为什么外部工具与内核工具在同一张表里

这是本页最该记住的一条设计取舍。MCP 工具不是「另一类工具」，它注册的就是 ToolCallRequest 这一族扩展点（McpToolRegistrar.java:105-107）， 因此它自动获得了内核已经建好的全部机制：

机制MCP 工具是否复用依据
权限判定（含插件拦截链） 复用：调用前统一过 PermissionCheckRequest ToolExecutor.java:392-396
工具清单（模型看到的那份） 复用：注册进同一张表就自动进清单 ToolCatalog.java:193、ToolCatalog.java:204
结果截断与落盘信封 复用：处理器只返回文本，截断由内核统一做 ToolExecutor.java:230
取消（Esc） 复用：request.getCancellationToken() 一路传到底 McpToolCaller.java:51-52、McpServerConnection.java:759-762
轨迹行与埋点 复用：摘要在 KEY_SUMMARY，失败标记在 KEY_TERMINAL McpToolCaller.java:84-97、ToolMetadata.java:56、ToolMetadata.java:96
「未知工具 / 注册冲突」的统一措辞 由内核给出，插件不参与 ToolExecutor.java:397-405

如果不这样设计——比如把 MCP 工具放在一个平行的「外部工具表」里——那么权限、清单、 截断、取消、埋点这五套机制都要再实现一遍（并且要保证两套的行为一致）。这也是 16 页那条主线「工具即能力、能力全在插件」的必然结论： 既然是同一张表，就不该有「外部工具」这个概念。

9. 坑点清单

MCP 的现场表现几乎全是「工具没出现」或「工具一会儿有一会儿没有」。下面每一条都按 「现象 → 根因 → 规避」写。

现象根因规避
工具一个都不出现，日志里也没异常 server 压根没起来（命令写错、缺解释器、没网），而失败原因只在运行期 敲 /mcp：状态里的「最近错误」就是上一次起不来的原因 （McpLedger.java:59、McpRegistry.java:276-283）
工具跑到一半全没了，过一会儿又自己回来 server 进程退出 → 工具被摘掉（这是有意的）→ 退避重连成功后重新注册 看 /mcp 的「重连中（第 N 次尝试）」；这正是设计行为 （McpPlugin.java:375-399、McpPluginTest.java:232-233）
某个工具忽然「不再是我们的」 两个 server 提供了同名工具，而 toolPrefix 被关掉 保持 toolPrefix: true（缺省）；它会以告警形式记进台账
升级之后 server 起不来或连不上数据库 子进程环境改成白名单，凭据不再继承 写到该 server 的 env 段（McpStdioTransport.java:76-78）
写类工具莫名其妙要审批（或内置工具要审批） 工具名与内置工具撞车，注册被跳过；若标记没摘干净，权限处理器会把内置工具认成我们的 这是被修掉的缺陷，现在由 retainTools 收口 （McpToolRegistrar.java:117-119、McpToolRegistrarTest.java:128-129）
插件已经停了，server 还占着端口 npx 拉起的 node 是孙进程，只杀直接子进程够不到 尽力杀进程树（McpStdioTransport.java:409-431）；取不到 PID 时是已知边界
react 线程永久挂住 callTimeoutSeconds: 0（不超时）+ 请求入表落在「叫醒在途请求」之后 已由 pendingLock 消除；自定超时值时可保留一个非零值作为额外保险 （McpServerConnection.java:92-100）
「偶尔收到一帧解析不了」 stderr 与 stdout 被合并，服务端日志混进了 JSON 流 源码已分开处理：redirectErrorStream(false) + 独立排空线程 （McpStdioTransport.java:146-147、:533）
整次对话发不出去 工具名里有厂商不接受的字符，被厂商在整次请求上拒绝 字符清洗 + 长度上限 64（McpToolName.java:81-93、McpConfig.java:60）
模型拿到一整屏 base64 把 image / audio 的 data 当文本回灌 落盘并只回灌路径（McpMediaSpill.java:92-117）
坑点：把「缺 tools 数组」当成「没有工具」

现象：server 的工具在某次刷新之后全部消失，且再也不回来。 根因：重扫时对面回了一个非法应答（没有 tools 数组、或 result 为 null），若按 0 个工具处理，就等于用一份空清单替换了完整清单； 而重扫只由 tools/list_changed 触发，对面已经出问题了，不会再来一次。 规避：源码把「没有数组」当协议违规抛异常，调用点保留现有清单并记一条告警 （McpServerConnection.java:534-537、:437-449）， 测试断言 assertTrue(received.isEmpty(), "没拿到清单就不该动注册表") （McpServerConnectionTest.java:316）。 合法的空清单 {"tools":[]} 则照常替换——「确实没有工具」与「它没给我们清单」是两件事。

注意：重连期间工具是真的不可用，不是「迟早会好」

断开后工具会被注销，重连成功后由新连接装回来。这意味着两件事： 模型在重连窗口里看不到这些工具（这是有意的——留着它们等于让清单撒谎）； 而重连一共只有 6 次、约一分钟，用尽之后停在 FAILED 并写明 「/reload 可重试」（McpPlugin.java:395-398）。

换 server 的 jar / 配置后的行为差异也要记住：配置段的改动由 /reload 触发插件重启， 而任何「改完就生效」的期待都要落到 /reload 上—— 16 页讲了这套重载的判定算法与它不覆盖的范围。

10. 测试怎么覆盖这条链路

本插件的测试分三层，边界划得很清楚——按类注释的说法，测的是「协议逻辑」而不是「管道能不能用」。

层用什么东西驱动测什么入口
协议逻辑（单测） FakeTransport——内存传输，不起任何真进程 握手与能力声明、清单替换、迟到应答、调用往返、断开上报 McpServerConnectionTest.java:32-33

端到端为什么单独一个 profile，理由写在 jellyfish-plugin-mcp/pom.xml:110-117： 「它会 fork 一个子进程（用例自带的极简 MCP server），因此不进 mvn test （AGENTS.md 规定单测不访问外部资源）」。而为什么不用一个真的第三方 server， EchoMcpServer.java:17-22 讲得很清楚：「那要求用户的机器上装了它（npx、 python、网络……），而端到端用例的价值恰恰在于「换一台机器也能跑」」。

EchoMcpServer 本身也刻意造了两个「反例工具」：一个只读的 echo、 一个总是报告失败的 boom（EchoMcpServer.java:108-124）—— 后者正是「isError 不是异常」那条约定的现场， 端到端用例断言 assertTrue(failed.error()) 与 failed.text().contains("工具自己说失败了") （McpStdioTransportIT.java:88-95）。它还会故意往 stderr 写一行 （EchoMcpServer.java:49），因为「真实的 server 都会这么做，而它绝不能混进 stdout 的 JSON 流」。

关键结论

  1. MCP 插件的本质是「把外部能力来源伪装成内核的普通工具」： 传输是 stdio 子进程 + 换行分帧，协议是 JSON-RPC 2.0， 工具注册进 ToolCallRequest 这一族扩展点，因此权限、清单、截断落盘、取消、埋点五套机制全部复用。
  2. 抖动都藏在「一个不受信的第三方进程」这个前提里：环境白名单、单行 4 MiB 上限、stderr 单独排空、 关停杀进程树、二进制落盘到带 PID 的临时目录——每一条都是「对面可能不守规矩」的兜底。
  3. 连接发生在 start() 之后、由 mcp-connector 线程做， 只在 startupWaitSeconds（缺省 5 秒）内有界地等一等： server 装错不会让内核起不来，断开按 1/2/4/8/16/32 秒退避重连 6 次， 用尽停在 FAILED 并写明 /reload 可重试。
  4. 工具名必须是 mcp__<server>__<tool>（前缀让「谁占谁的位置」不成为事实）， 字符清洗与长度上限是厂商约束的硬要求——撞了不是「这个工具不可用」， 而是「这一轮对话发不出去」。
  5. 清单的三条纪律：整体替换而不是增量增删；缺 tools 数组是协议违规、要保留旧清单； 标记与注册同生同死（先装标记再注册，注册不成的名字从标记表摘掉）， 因此刷新窗口里挤不出「写类工具免审批」的一瞬。
  6. 权限上只有一个补丁式闸门：MCP 工具未在用户写的 readOnlyTools 里就 ASK。 它不是安全边界——真正的边界是「装了什么 server」和内核的 askTools / allowedTools 策略；-cli / -server 下 ASK 即拒绝。
