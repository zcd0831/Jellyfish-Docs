15 可观测性与运行观测

前面十四页讲的是「它怎么工作」。这一页讲「你怎么知道它正在怎么工作」—— 以及一个必须说清的结论：内核里这套东西做得挺完整，但几乎没有出口。

学习目标

  • 说清三条可观测通道的分工：指标、健康检查、run 事件；
  • 背下 33 个指标名的命名规律，以及两处容易被误读的统计口径；
  • 画出健康检查的聚合规则（最差优先）与四个指示器各自的降级条件；
  • 知道 GET /health 的契约（状态码恒 200）与它为何是唯一免鉴权路由；
  • 说清 run 观测与「外壳回合事件」的关系，以及 RunEventBus 为什么和 ShellStreams 用同一套契约；
  • 指出这套可观测性当前的真实空白（无 /metrics、指标只在关停时落日志）。

设计依据：健康检查为什么是「拉取」而不是「订阅」？

指标的模型是事件驱动：来了 ToolCallCompletedEvent，就把 tool.completed 加一。 它需要「持续累计」，所以必须订阅。

健康检查的模型是状态判定：「现在插件起来了吗」「现在配了 provider 吗」。 这类问题用事件表达会很别扭——你没法用「某事件发生过」来回答「现在是否正常」， 因为中间可能又被改回去了。现算（拉取）永远反映当下，而且不需要维护一份可能与现实脱节的状态副本。

同一条推理在审批上出现过一次：ShellTurnEvent 的类注释（:22-24）明确说 「不承载审批：审批是拉取式的……理由是审批需要『当前是否还挂着一件』这样的状态语义， 而事件是过去式的，用它表达状态会引入两套真源」。 同一份判断，两处独立应用。

两处必须注意的统计口径

坑点：这两条会把数字读错
  • tool.failed 包含「权限拒绝」（MetricsSubscriber.java:31-33）。 所以「工具失败率高」不一定是工具坏了，可能只是权限拦得多。
  • permission.denied 把「非 ALLOW」全算作拒绝（:169-171）—— 这与 06 页里 decide() 永不返回 ASK 的实现是一致的： 走到最后只有放行或拒绝两种结果，中间态在内部就被收敛掉了。

这类「指标名看起来自明、口径其实有约定」的地方，是看板最容易骗人的一类。写看板前先读 MetricsSubscriber。

MetricsRegistry：只有两种指标

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/metrics/MetricsRegistry.java
// 类文档 :33  「线程安全，可安全被多个 react / 渲染 / 事件线程并发写入」
// 只有两种指标（:7-16）：
//   counters —— 计数，用 LongAdder（高并发自增，比 AtomicLong 更快）
//   gauges   —— 仪表，用 Supplier<Number>（拉取时现算，不缓存）
private final Map<String, LongAdder> counters = new ConcurrentHashMap<>();   // :41
private final Map<String, Supplier<Number>> gauges = new ConcurrentHashMap<>(); // :44
  • 计数用 LongAdder 而不是 AtomicLong：这是高并发自增的标准选择—— AtomicLong 在多核上所有线程争同一个 CAS，LongAdder 用分散的 cell 把竞争打散。 这里的写入端来自事件通道的广播线程，属于典型的多写场景。
  • 仪表是 Supplier 而不是数值：所以「队列长度」这类指标不需要有人定时去更新， 取快照时现读一次即可。副作用是仪表可能抛异常，代码对此的处理是「坏仪表只丢自己」 （:109-121），不让一个坏指标毁掉整份快照。
  • 重复注册按最后一次生效（:96）——没有冲突告警。如果你见到仪表值莫名变化，先怀疑这里。
  • requireName 对空名抛 JellyfishException("metric name must not be blank")（:149）： 宁可早期炸掉，也不要出现一个空名字的指标混进快照。

三档 HealthLevel 是 UP / WARN / DOWN（:13-20）， 其中 WARN 的定义是「功能受限但内核可用」。装配顺序固定为 model、plugin、eventChannel、compaction （di/MetricsModule.java:53-56、JellyfishAssembler.java:447-450）。

设计依据：「有插件但一个都没起来」为什么只是 WARN 而不是 DOWN？

因为内核仍然可用——你能跑 /help、能切换模型、能退出。缺的是能力，不是内核本身。 而「没配 provider」判 DOWN，因为那意味着连一次对话都发不出去，内核的核心功能确实不可用。

这个区分对运维很重要：WARN 是「去装插件」，DOWN 是「去配配置」。 如果两者都判 DOWN，运维会去查一个本来没问题的配置文件。 这也解释了 11 页里那条「没装压缩插件只降 WARN」—— 它是同一个判断标准的一致应用。

GET /health 的契约

Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/handler/HealthHandler.java:44-45
public void handle(HttpServerExchange exchange, PathParams params) {
    Responses.writeJson(exchange, Responses.OK, HealthDto.of(healthCheck.check()));
}
  • HTTP 状态码恒为 200，健康状态在响应体的 status 字段里 （HealthHandler.java:15-17 的注释说明了这点）。所以监控系统不能只看状态码， 必须解析 JSON 里的 status。
  • 响应体 HealthDto 三个字段：status（UP/WARN/DOWN）、 healthy（boolean）、results（List<HealthItemDto>）。 每个 HealthItemDto 有 name / level / detail。
  • 它是唯一免鉴权的路由：ApiKeyGuard 里 if (isHealthProbe(exchange) || isAuthorized(exchange))（:76）， 而 isHealthProbe 要求 GET + 路径归一化后等于 /health（:107-113）。 路径先归一化很关键——否则 /health/../sessions 这类写法可能绕过（10 页）。
坑点：HealthCheck 会把「指示器抛异常」收敛成一条 DOWN

HealthCheck.checkOne（:57-68）把指标抛错或返回 null 都收敛成一条 DOWN 结果。 这是合理的容错，但意味着你看到的 DOWN 可能不是真 DOWN，而是指示器自己坏了。 排查时看 detail 字段——它会带上异常信息。

与 06 页那条「插件拦截抛异常一律按拒绝」是同一个思路： 故障收敛成一个可见的、更严的结果，而不是把故障本身当成「没问题」。

4. run 观测：与外壳事件并列的第二条可靠通道

子代理的 run 是内核里唯一会并发存在多个实例的执行单位，所以它有一套独立的登记与观测：

类职责关键点
RunRegistry（356 行） run 登记表：Map<String, RunState>，ConcurrentHashMap（:57） register 生成 UUID.randomUUID()，root 缺省即自身（:72-77）； 终态 CAS 幂等（finish :161-186）；active() 只返未终结（:194）； remove 才真正回收（:206）

RunPermit（56 行） 并发许可的持有句柄 持 Semaphore 与 held，构造即「已持有」（:26-34）； suspend() 幂等让出（:39-45）、resume() 幂等取回（:50-56）

设计依据：RunEventBus 为什么不复用 ShellStreams？

两者的契约一模一样（同步扇出、不丢、异常隔离），但服务对象不同： ShellStreams 送的是「回合」（外壳的当前会话），RunEventBus 送的是「run」（可能有很多个，跨会话）。

为什么不合并成一条？因为两者的订阅者与生命周期不同：回合事件是「一个会话同一时刻最多一个」， 而 run 事件是「一棵树在跑」。混在一起会让订阅者需要自己过滤「这条事件属于哪个 run」—— 而那正是分类的意义所在。做法是复制契约、分离通道：语义清晰，代价是一份重复的扇出实现。

上报频率：只报两端

AgentRunProgressEvent 只有两个 Kind：STARTED 与 FINISHED （:38-44），没有 STEP。字段有 kind / outcome / runId / parentRunId / rootRunId / agentId / rounds / totalTokens（:47-63），且 STARTED 时 rounds 与 totalTokens 恒为 0（:59-63）。

原因是 RunObservationBridge.republish 里主动丢弃 STEP（:114-116）， 注释写的理由是「量级远高于生命周期事件」。也就是说： 中间进度不走事件，而是走拉取——TUI 的子代理面板每秒补一次失效去读登记表 （TuiApp.java:300 的 LIVE_REFRESH_MILLIS = 1000L，注释说明「无事件，回合中每秒补一次，空闲零调用」）。

设计依据：高频进度为什么用「轮询」而不是「事件」？

一个子代理跑 8 轮、每轮几十条流式片段，如果用事件推每一次变化，事件量会压过所有其他事件之和—— 而订阅者（面板）每秒最多画一帧，99% 的事件是白推的。

「低频状态用拉取（面板每秒读一次）、高频过程用推送（文本增量走事件）」是一条很实用的分界线。 判据是「消费速率上限」而不是「变化频率」：变化再快，若消费者处理不过来，就该改成拉取。 注意这跟 07 页的「能否丢弃」是两条不同的判据。

三个可直接拿去用的观察：

  • MetricsSubscriber 只订阅、不发布（类注释 :25-27）。 这一点很重要：它避免了「指标更新又触发事件、事件又更新指标」的回路。 在事件驱动系统里，明确谁是叶子订阅者是一条值得写进规范的纪律。
  • 它注册在 bootstrap() 里、且在 eventChannel.start() 之后 （AgentHarness.java:196）。顺序反了的话，早期事件就没人统计——而「启动期丢了几个事件」 恰恰是排查启动问题时最想知道的。
  • 外壳贡献的三个指标不走事件，由 ShellIngress 直接自增 （:140, 145, 156, 174）。因为这三次计数发生在「投递」这个动作里， 而投递本身需要知道结果（入队成功 / 被合并 / 被丢弃），用事件表达反而绕。

聚合规则

Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/dto/HealthDto.java:74（聚合表达式）
status = report.isHealthy() ? (warn ? STATUS_WARN : STATUS_UP) : STATUS_DOWN;

读法是：只要不是「有任何 DOWN」，就健康（HealthReport.isHealthy() :39-46）； 在健康的前提下，有任意 WARN 就报 WARN，否则报 UP。也就是最差优先，且 DOWN 吸收一切。

6. 消费点：这里有一个真实的空白

这套东西做得完整，但出口很少。审计过的消费点只有这几处：

消费者做了什么位置
MetricsSubscriber唯一的指标写入端装配于 MetricsModule:50、JellyfishAssembler:444
ShellIngress外壳贡献的三个指标自增:140, 145, 156, 174
AgentHarness关停时把指标渲染成日志；启动时打一行健康检查:324（snapshot().render()）、:298、:259、:309
HealthHandlerServer 模式的 GET /health:44-45
坑点（也是这个子系统的真实局限）
  • 没有 /metrics 命令，也没有 /health 命令。 内核命令只有 status / usage / delete / compact / reload （core/command/SystemCommands.java:190 附近）。 也就是说在 TUI 与 CLI 里你根本取不到指标。
  • 指标只在关停时落一行日志（AgentHarness:324）。 想看运行中的指标，只能靠 --verbose + 事件日志，或者用 Server 模式。
  • TUI 不消费健康检查与指标（全仓无引用；ChatShell.java:45 把状态栏称为「一行扫读指标」， 那只是措辞，不是指标系统）。
  • CLI 只是把 healthCheck() 透传给 Server（Launcher.java:159）， 自己不显示。

所以「Jellyfish 有没有可观测性」的准确回答是：内核有完整实现，Server 模式有 /health 与 run 事件； 但交互式使用（TUI / CLI）取不到指标。这属于可以提议改进的地方，而不是缺陷—— 毕竟它的设计目标不是「运维监控面板」。若你要做生产部署，优先考虑用 Server 模式 + /health 探活， 指标则需自己订阅 EventChannel 或读 MetricsRegistry。

7. 本页坑点小结

可观测性相关的坑
  • GET /health 状态码恒 200，健康与否看响应体 status 字段。只看状态码会永远认为健康。
  • tool.failed 含权限拒绝；permission.denied 把非 ALLOW 全算拒绝。
  • 仪表重复注册静默按最后一次生效（MetricsRegistry:96），没有告警。
  • 坏仪表只丢自己（:109-121）——快照少一项不代表没有这项，可能只是它抛错了。
  • 指示器抛异常会被收敛成 DOWN（HealthCheck:57-68）：看到 DOWN 先看 detail 是真故障还是指示器故障。
  • run 事件只报 STARTED / FINISHED，STEP 被主动丢弃；中间进度靠面板每秒轮询（1000ms）。
  • RunContextHolder 必须 remove()：执行池线程会复用，漏掉会把上一个 run 的上下文带到下一个。
  • AgentRunSnapshot.startedAt 是「登记时刻」而不是「开始跑的时刻」 （:53-56, 178-181）——在等待区里排队的 run，这个字段会很早。别用它算执行时长。
  • 插件不能走 RunEventBus（:27-29）：要观测子代理得走 EventChannel 的通知事件。
  • TUI / CLI 取不到指标，没有 /metrics 命令。

关键结论

  1. 三条通道各有明确语义：指标是累计（事件驱动）、健康是当下（拉取现算）、run 事件是生命周期（同步扇出）。 「状态用拉取、过程用推送」这条判据在审批、健康、面板进度三处独立出现，是这个项目里最一致的一条设计直觉。
  2. 33 个指标名的命名规律（域.动作）本身就是契约；但两处口径（tool.failed 含权限拒绝、 permission.denied 含全部非 ALLOW）必须先读代码再建看板。
  3. 健康检查的「最差优先 + WARN 表示功能受限但内核可用」把运维动作区分开了： WARN 去装插件，DOWN 去改配置。这个区分比等级本身更有价值。
  4. RunEventBus 与 ShellStreams 用同一套契约但分成两条通道—— 复制契约、分离语义，代价是一份重复实现，收益是订阅者不需要自己做过滤。
  5. 最诚实的一条：这套可观测性在 Server 模式下有出口，在 TUI / CLI 下没有。 知道「哪里有、哪里没有」，比知道「它有可观测性」更有用。
