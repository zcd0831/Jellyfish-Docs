01 项目概览与设计哲学

把「这个项目解决什么问题、为什么长成现在这样」先立住。后面每一页的细节，都是这一页三条主线的展开。

学习目标

  • 能用三句话说清 Jellyfish 是什么、和普通「LLM 调用封装」的区别在哪；
  • 记住三条设计主线：三外壳一内核、工具即插件、默认不信任，并知道每条落在哪些代码上；
  • 能画出 7 个模块的职责表，并说出每个模块「不做什么」；
  • 理解 Java 1.8 这个硬约束带来了哪些具体写法限制，以及它的收益假设是什么。

1. 它是什么

README 的第一句话已经把定位说完了（Jellyfish/README.md:3）： 「用 Java 1.8 编写的轻量级 AI Agent 工具：单次问答、交互式终端界面、HTTP 服务三种形态共享同一个内核」。 拆开看有三层意思：

  1. 它是 Agent，不是 SDK。它自己驱动「模型 → 调工具 → 看结果 → 再调模型」这个循环（见 04 页）， 而不是把循环交给调用方写。你的代码不参与决策，只负责给它一个入口和一个界面。
  2. 它是内核，不是产品。仓库里没有一行「读文件」「跑命令」的实现——jellyfish-core 里的 ToolExecutor 只做权限判定、路由和结果截断，真正干活的东西全在 Jellyfish-Plugins 那 13 个独立 jar 里。
  3. 它有三个门，一个屋子。-cli / -tui / -server 是三个不同的入口， 但装配出来的对象图（JellyfishRuntime）是同一套。

2. 三条设计主线

这个仓库的所有代码几乎都能被这三条线解释。如果你只记三件事，记这三件。

主线一：三外壳一内核

三种运行形态不是三份代码，而是同一份装配 + 三个不同的投影层。 「谁依赖谁」这件事被单独抽成一个模块 jellyfish-di（composition root）， 它对外只暴露一个接口 JellyfishRuntime，共 23 个访问器 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishRuntime.java:54-213）。

设计依据

为什么要单独一个 di 模块？因为「哪些实例必须唯一」这件事是关键知识： ExtensionRegistry 与 EventChannel 必须共享同一个 TypeRegistry， EventPublisher 必须就是那个 EventChannel 本身——否则配置告警会发进一个没人订阅的通道，然后静默消失。 把这些绑定关系写两份（Dagger 一份、手写一份）就等于把这类错误写进去两次的机会。 Jellyfish/AGENTS.md 明说了这个取舍：「代价是新增绑定时两处都要改」， 兜底手段是 JellyfishAssemblerTest——同一段行为对两种装配各跑一遍。

替代方案与为什么没选：让三个外壳各自 new 一套依赖（省一个模块）→ 会出现三份逐渐漂移的装配， 且无法用测试锁住一致性；只用 Dagger（省掉手写装配）→ 把内核绑死在 DI 框架上， Jellyfish-Spring-Boot-Starter 之类的容器接入就得绕一圈。当前方案是「两套都要，用手工那套证明没有 Dagger 也能立起来」。

主线二：工具即能力，能力全在插件

内核只提供机制，不提供任何能力。这句话有非常直接的推论，而且作者把它写进了 AGENTS.md 的关键不变量里：

  • 压缩是插件能力、内核只提供机制；没有策略插件即整体不可用，不回退内置。 （实测：没装 jellyfish-plugin-compact 时 /compact 直接抛异常，自动压缩静默让路并只发一条配置告警）
  • !命令 这个输入指令由插件声明，卸了 shell 插件就没有 ! （core/input/InputDirectives.java:45-55）。
  • 会话落盘也是插件（jellyfish-plugin-session-file），没装持久化插件时会话退出即消失。
  • ToolExecutor 排在执行链上的位置是「权限 → 路由 → 截断」，它自己不实现任何工具。

设计依据

为什么把工具全部推出去？因为工具是「会随着场景爆炸」的那一维：文件、shell、MCP、Python、Node、浏览器…… 而循环和权限是「必须收敛、必须唯一」的那一维。把易变的一维放进插件，把必须唯一的一维锁进内核， 这样加一个工具不需要动内核一行代码，也不需要重新发版内核。

代价（很重要）：内核单独跑起来是「哑」的——模型一个工具都调不了。 这对使用者是坏消息（必须装插件），对内核维护者是好消息（不用为每个新工具做兼容）。 横向对比里这是 Jellyfish 与 Aider/Cline「开箱即用」最大的差距，详见 26 页。

主线三：默认不信任

这是这个项目最有辨识度的一条。它体现在三个层次，每一层都选择了「更严」而不是「更方便」：

层次默认行为代码位置
工具权限 判定优先级「显式拒绝 > 需审批 > 允许收窄」；插件拦截三态里没有 ALLOW，插件连「放行」都表达不了；插件抛异常或返回 null 一律按拒绝 infra/permission/PermissionManager.java:170-216
人工审批 fail-closed：无审批者、超时、线程中断，三者一律判拒绝。-cli 从不挂接审批者，所以 CLI 下 askTools 命中即拒 infra/permission/ApprovalChannel.java:304-330
项目级配置 默认不加载。信任单位是「文件绝对路径 + SHA-256 内容指纹」，内容一变即失效；未信任即跳过 + 告警 infra/config/ProjectConfigTrust.java:46, 128, 137, 171-178
设计依据

项目级配置为什么要过信任闸？因为它按进程当前目录解析。 你要是在一个刚 git clone 下来的目录里敲了 jellyfish， 那个仓库里的 ./.jellyfish/models.json 就能改写模型端点（把你的对话发到别的服务器）、 换掉密钥、新增一个权限宽松的 agent、甚至改掉工具输出的落盘目录。 而这一切不需要你做任何操作，clone 下来就已经发生了。

为什么信任单位要细到内容指纹？如果只信「这个路径」，那么攻击者只要往那个路径塞新内容，旧授权就继续有效。 绑上内容指纹后，「路径 + 内容」一变，授予自动失效，必须重新确认。对比一下：.claude/settings.json 与 AGENTS.md 这类项目配置在多数同类工具里是默认生效的。

坑点

在 ./.jellyfish/models.json 里配好模型却发现不生效——这是最常见的第一次踩坑。 原因就是这条信任闸在跳过该文件，并且只在日志里留一条告警。 解锁方式只有两条：本次生效的 --trust-project-config（不落盘），或 TUI 里的确认框（可记住）。 注意 classpath: 路径不受此闸管辖，因为那部分内容跟着内核 jar 走，用户改不了。

核心 vs 辅助

按「改动风险」而不是「行数」来分，核心模块是这五个——它们承载了 AGENTS.md 里那份不变量清单： jellyfish-api（契约）、jellyfish-core（循环与管线）、 infra/session（状态真源）、infra/permission（安全边界）、infra/plugin（外部代码入口）。 其余更像「翻译层」：模型客户端把中性请求翻译成厂商格式，TUI/Server 把内核状态翻译成界面。

读代码的启发式

这个仓库里类注释的质量高于方法注释，而类注释里往往写着「为什么不能那样做」。 遇到一个类看不懂定位，先读它类注释的前两段——很多设计依据直接写在那儿，例如 PermissionManager.intercept() 的 javadoc 用四段解释「为什么插件抛异常要按拒绝处理」。

4. 设计依据追溯：为什么是 Java 1.8

先分清事实与推断。可核实的事实：Jellyfish/pom.xml:54-56 把 java.version 定为 1.8； Jellyfish/README.md:27 写明「JDK 8（源码与目标版本都是 1.8）；运行只需 JRE 8+」； AGENTS.md 用加粗写着「不要使用 Java 9+ 的 API 或语法」。

从这些事实能推出的工程假设：

  • 目标宿主是企业内网的 Java 8 存量环境。「运行只需 JRE 8+」意味着部署方不需要升级 JDK 就能用—— 这是把工具塞进已有 JVM 生态（尤其 Jellyfish-Spring-Boot-Starter 这种形态）的前提条件。 一个要求 JDK 17 的 agent 工具，在很多公司里连试用都进不去。
  • 插件要能编译进老环境。插件的 provided 依赖是 jellyfish-api， 如果内核升到 11+，插件作者也被迫升——这会直接扼杀「第三方写插件」这件事。
  • 代价是显式的：没有 var、没有 List.of()、没有 record、 没有 CompletableFuture.orTimeout、没有模块系统。代码里因此到处是 new ArrayList<String>()、Collections.unmodifiableList、 手写的 builder（如 LlmRequest 的 665 行）与显式泛型。
  • 替代方案：升到 Java 11/17 能显著精简代码（大量 BOILERPLATE 消失）。 没有选，是因为收益（对内核维护者的舒适度）不足以抵消成本（丢掉整个 Java 8 存量市场， 以及破坏插件作者的最低门槛）。这是一个典型的「技术更好 ≠ 商业上更对」的取舍。

引用了哪些 Agent 设计范式

范式在 Jellyfish 里的对应实现偏离之处
ReAct（Reason + Act 交替） ReActLooper.loop()：一轮 = 一次模型调用，有工具就调工具、回灌结果后进下一轮 不做「Thought 文本解析」——思考文本直接由厂商侧返回（thinking/reasoning_content）， 不用让模型把思考写进正文再正则抠出来
Plan-and-Execute 不在内核里。由 jellyfish-plugin-plan 与 jellyfish-plugin-workflow 提供 内核刻意不内置规划器，避免把「一种工作方式」写死
Sub-Agent / 编排 TaskTool + SubAgentLauncher + RunScheduler：可把子任务委派给独立上下文的子代理，并发由许可门控 关键约束：委派不得提权（子 agent 授权必须是父授权子集）
Human-in-the-loop 权限两层 + 审批通道（TUI 弹框 / Server SSE + HTTP 回调），fail-closed 比多数实现更严：没人在场时不是「默认放行」而是「默认拒绝」
Context Engineering 提示词组装（PromptAssembler）+ 成组裁剪（ContextWindow）+ 摘要压缩（ConversationCompactor）+ 工具结果老化（ToolResultAger）+ prompt cache 断点与保活 裁剪只裁本次请求，历史一条不动；压缩非破坏式，屏幕与落盘仍是全文
设计依据

为什么内核不内置 Plan 模式？因为「怎么规划」是使用习惯，不是机制。 把它内置进循环意味着：想换一种工作方式就得改 ReActLooper，而那是整个项目最不该被动的地方。 推给插件后，规划能力可以和其他插件（比如 workflow、skills）自由组合，也可以被完全不用—— 内核的 loop() 一个字都不用改。

5. 关键代码：三条主线落在同一处

下面这段是 AGENTS.md 里那条最重要的不变量的实现—— 「ExtensionRegistry（同步、不可丢）与 EventChannel（异步、可丢）是内核与插件之间唯一边界」。 它同时体现了主线一（装配唯一）和主线二（边界收敛）：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:239-247
TypeRegistry registry = new TypeRegistry();
extensionRegistry = new ExtensionRegistry(registry);
EventChannelOptions channelOptions = EventChannelOptions.defaults();
eventChannel = new EventChannel(channelOptions, registry);
// 窄接口视图与通道是同一个对象：配置 / 模型 / agent 的告警都从这里出去，
// 只有 bootstrap() 启动的那一个通道才有人订阅
EventPublisher publisher = eventChannel;

逐行解释：

  • TypeRegistry 是「类型即地址」的注册表——扩展点没有 ID 清单，请求的 Class 对象本身就是地址 （api/extension/ExtensionRequest.java:9-15）。
  • ExtensionRegistry 包着它，提供注册与派发（同步，不可丢）：调用方要等返回值，丢了就是功能缺陷。
  • EventChannel 也包着同一个 registry——这就是「必须同源」的那条约束。 两边的判据不是「有没有返回值」，而是「能否丢弃」。
  • 最后一行 EventPublisher publisher = eventChannel; 是这段注释存在的理由： 内核早期就要发配置告警，但那时只有 EventChannel；如果没有这一步， 在别处 new 一个 publisher 就会发进一个没人订阅的通道， 表现是「配置写错了但什么提示都没有」。
坑点

新增一个内核绑定时，必须在 @Module 的 @Provides 与 JellyfishAssembler 里各写一行（JellyfishAssembler.java:109-110 自己承认了这点）。 分叉的表现不是编译错误，而是上面那类静默故障——所以改装配之后一定要跑 JellyfishAssemblerTest（同一段行为对两种装配各跑一遍）。

6. 坑点速览

这一页相关的坑
  • 不带参数 = TUI，但带了任何参数就必须显式给模式。裸跑兜底只认「参数个数为零」这一种情形 （StartupOptionsParser.java:154），所以 jellyfish --verbose 会报「请指定启动模式」退 2， 而不是「默认 TUI + 详细日志」。这是刻意的：避免「敲了没反应」和「悄悄挂在等 stdin」。详见 15 页。
  • 项目级配置默认不加载——最常见的第一次踩坑。
  • 内核不带工具：不装插件时只能跑系统命令（/help 等），模型什么都干不了。
  • Java 8 不是「建议」是「不允许」：改代码时用了 List.of() 之类会在 mvn compile 直接失败 （-source 1.8 会拒绝 9+ 的 API），这是好事——错误立刻可见。

关键结论

  1. Jellyfish 不是「LLM 调用封装」，而是一个把能力全部外置的 Agent 内核：内核给机制，插件给能力，外壳给界面。
  2. 三条主线互为因果：因为要给三种外壳共用内核，所以要有装配层；因为要能不断加能力，所以工具必须是插件；因为插件是外部代码，所以默认必须不信任。
  3. 「默认不信任」不是安全团队的附加要求，而是架构选择带来的必然结果——你把执行权交给外部代码，就必须在每次调用上留下否决点。
  4. Java 1.8 是一个明确的市场取舍，不是技术落后：换来「JRE 8+ 就能跑」和「插件作者不必升级 JDK」。
