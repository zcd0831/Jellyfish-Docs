12 装配与依赖注入 重点

「装配」在这个仓库里是两件事叠在一起：一张对象图（谁依赖谁、哪些实例必须唯一）和一份 交付契约（外壳拿到哪 23 个入口）。这一页讲 Dagger2 具体怎么把这张图声明出来、 JellyfishRuntime 为什么是这样一份契约、以及「同一段行为两种装法」是怎么被钉住的。

学习目标

  • 知道 jellyfish-di 的 13 个源文件各是什么，以及它们合起来只有一个职责；
  • 能用一句话说清 JellyfishComponent 为什么继承 JellyfishRuntime 而不是各写一份；
  • 解释 @Component.Builder + @BindsInstance 存在的理由，以及它修掉的 N-07 是什么；
  • 拿到 10 个模块 / 22 条 @Provides 的完整分工表，并能说清每条为什么落在这个模块；
  • 说清 @IntoMap + @StringKey 的 Map 多绑定为什么比 if-else / 工厂里的 switch 好；
  • 知道 Dagger 的编译期校验兜住了什么，以及 Dagger* 生成物在覆盖率与调用点上的位置；
  • 列出「同一实例」这类不体现在方法签名上的约束，以及两套装法各自怎么落实、测试怎么抓分叉。

1. 两种装法，一个契约

先给结论：这个仓库里装配知识只有一份，但它有两种落地实现，二者交付同一个 JellyfishRuntime。为什么要有专门的装配层、为什么不只用 Dagger， 03 页第 2 节已经从「模块边界」的角度讲过一遍，这里不再重复； 本页补的是机制细节：Dagger 到底怎么用、门面接口怎么维护、两套装法怎么保持一致。

先把范围说清楚。装配层是 jellyfish-di，主源码恰好 13 个文件： JellyfishComponent.java（298 行）、JellyfishRuntime.java（214 行）、 JellyfishAssembler.java（569 行），加上 10 个 @Module。 这个模块不带任何资源（配置与提示词分别归 infra 与 cli）， 它只装东西（Jellyfish/docs/constraints.md:183-184）。

2. Dagger2 在这个项目里到底怎么用

全站此前没有一页讲过 Dagger2 的用法，所以这一节从注解开始。先说清一件事： 项目用的 Dagger 版本是 2.16，注解处理器由父 POM 统一配置 （Jellyfish/pom.xml:61 定义版本，Jellyfish/pom.xml:253-255 在 maven-compiler-plugin 的 annotationProcessorPaths 里挂上 dagger-compiler），因此子模块的 pom.xml 里只声明 dagger 依赖、 不重复声明处理器（Jellyfish/jellyfish-di/pom.xml 的依赖清单里没有 dagger-compiler）。

2.1 @Component：一个接口声明 10 个模块，并继承交付契约

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishComponent.java:31-49（类注释 + @Component + 继承 JellyfishRuntime）
/**
 * 应用级 Dagger2 组件：在最外层（composition root）装配共享的 {@code OkHttpClient}、
 * LLM 客户端注册表、配置门面、扩展层（注册表 / 同步策略 / 事件通道）、插件运行时、agent 定义与权限判定。
 * <p>
 * <b>它继承 {@link JellyfishRuntime}</b>：那 23 个访问器是「装配完成后对外交付什么」的契约，
 * 与具体装法无关；本组件是 Dagger 侧的实现，{@link JellyfishAssembler} 是手工装配侧的实现。
 * 继承而非各写一份，是为了让「两边少交付一个入口」在编译期就暴露，而不是等某个外壳用到时才发现。
 * <p>
 * <b>{@link AppConfig} 由构建者注入，不由模块提供</b>：配置来源是部署事实，两种装法都该由调用方决定
 * （见 {@link ConfigModule} 的类注释）。只想要最常用的那份来源（classpath）时用
 * {@link ConfigModule#loadDefault()}。
 *
 * @author zcd
 */
@Singleton
@Component(modules = {ConfigModule.class, LlmModule.class, ExtensionModule.class, EventModule.class,
        PluginModule.class, AgentModule.class, PermissionModule.class, AskModule.class, CommandModule.class,
        MetricsModule.class})
public interface JellyfishComponent extends JellyfishRuntime {

三个要点。第一，@Singleton 写在组件接口上，含义是「这个组件的作用域」—— 组件内部的单例。凡是标了 @Singleton 的 @Provides （或带 @Singleton 的 @Inject 构造器）在整个组件里只会被创建一次， 这正是「全局共享的 OkHttpClient」这类约束的落地方式。

第二，@Component(modules = {...}) 一次列了 10 个模块， 顺序按「先基础设施、后域服务」排：ConfigModule、LlmModule、 ExtensionModule、EventModule、PluginModule、AgentModule、 PermissionModule、AskModule、CommandModule、MetricsModule。 这个顺序不影响语义（Dagger 自己算依赖顺序），列出来只是为了读起来顺。

第三，也是这一小节真正要说的一点：JellyfishComponent extends JellyfishRuntime。 接口继承带来的是编译期的完整性检查：Dagger 生成的实现类必须把 23 个访问器全部实现， 少一个就是编译错误。如果两套装配各自声明一份入口清单（而不是共享一个接口）， 「Dagger 侧漏了 healthCheck()」这种问题就要等到 -server 外壳真的去调 GET /health 时才发现，而手工装配侧可能早就补上了——两边的不一致没人能提前发现。

设计依据：继承比「各写一份」多买到的是「编译期」

一个更松的做法是在 JellyfishComponent 里手抄 23 个方法签名。它能跑， 但抄写这件事没有任何机制保证两边同步：手工侧加了访问器，Dagger 侧不会编译失败， 只是外壳用不了。继承把这件事交给 javac——漏交付从「运行时某个外壳报错」 提前成「编译不过」，代价为零。

顺带一个可读性上的事实：JellyfishComponent 里那 23 个访问器是重复声明的 （继承已经给了签名）。它们存在的价值是每一条都带一段「调用点是谁」的 javadoc—— 例如 approvalChannel() 那条写明「只有 -tui 会 attach()， -cli 与 -server 不挂审批者，因此需要审批的工具一律按拒绝处理」。 这类「谁在调」的信息在 JellyfishRuntime 里只写「保证非 null」， 分开放是有意的：契约给实现者看，调用点说明给使用者看。

2.2 @Component.Builder + @BindsInstance：AppConfig 为什么由调用方给

这是整套装配里唯一一处「必须由外部喂进来」的绑定，也是最近才修掉的一个等价性缺口。 先看源码：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishComponent.java:51-71（构建者与实例绑定）
    /**
     * 组件构建者：把 {@link AppConfig} 作为实例绑定交给组件。
     * <p>
     * <b>为什么要有它</b>：此前 {@code AppConfig} 由 {@code ConfigModule} 固定从
     * {@code classpath:config.json} 读，而手工装配侧（{@link JellyfishAssembler}）是调用方传入——
     * 「两种装法交付同一契约」这句话在配置来源上并不成立。现在两侧都由调用方给，
     * 差异只剩各自的调用方想给什么。
     *
     * @author zcd
     */
    @Component.Builder
    interface Builder {

        /**
         * 绑定应用级配置（配置来源由调用方决定）。
         *
         * @param appConfig 应用级配置，不可为 {@code null}
         * @return 本构建者，便于链式调用
         */
        @BindsInstance
        Builder appConfig(AppConfig appConfig);

先说这两个注解各自做什么。@Component.Builder 让 Dagger 为组件生成一个构建者类 （生成物就是 DaggerJellyfishComponent.builder()）；@BindsInstance 表示「把调用者手里这一份现成实例直接绑进图里」，而不是让 Dagger 去构造它。 没有 @BindsInstance 的话，AppConfig 就必须由某个模块的 @Provides（或带 @Inject 的构造器）提供——而 AppConfig 是纯数据类，构造它需要先决定「去哪读」，那正是个部署事实。

注释里的那段历史值得单独讲，因为它是本页最实在的一个教训。修之前的状态是： Dagger 侧固定读 classpath:config.json，手工装配侧由调用方传入。 于是「两种装法交付同一契约」这句写在注释里的话，在配置来源这一件事上并不成立 （报告编号 N-07）。现在的口径是「两侧都由调用方给」， 这条规矩同时也写进了约束清单（Jellyfish/docs/constraints.md:187-190）， 还配了一条测试专门钉住它（第 4 节会看到）。

那「最常用的那一份来源（classpath）」放哪？放在 ConfigModule 的 普通静态方法里，而不是 @Provides：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:44-46（缺省来源的唯一落点）
    public static AppConfig loadDefault() {
        return new ConfigLoader(new SettingsReader(), new SettingsBinder()).loadAppConfig();
    }

为什么不是 @Provides？因为它与 @BindsInstance 会形成同类型双绑定， Dagger 在编译期就报错。而「最常用的那一份来源」仍然需要一个落点，否则每个只想要缺省行为的调用方 （CLI、测试）都要自己把 SettingsReader 与 SettingsBinder 拼一遍， 那种重复必然漂移——这段理由逐字写在 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/ConfigModule.java:36 起的注释里。

CLI 侧就三行，一眼能看完「谁决定配置来源」：

Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/JellyfishApplication.java:84-98（CLI 的组件创建点）
        if (options.isVersion()) {
            console.writeOut(PROGRAM_NAME + " " + version() + "\n");
            return ExitCodes.OK;
        }
        try {
            // 配置来源由本外壳决定：CLI 用的就是最常用的那一份（classpath:config.json）
            return new Launcher(DaggerJellyfishComponent.builder()
                    .appConfig(ConfigModule.loadDefault())
                    .build(), console).launch(options);
        } catch (RuntimeException e) {
            // 走到这里说明失败发生在能归类之前：DI 装配 / 组件创建，或启动最早的那几步
            // （项目级配置的信任表态、选模式）。此刻还没有 harness 可收敛，也没有「运行期」可言，
            // 因此一律归启动失败。launch() 内部的失败由它自己分成 3 / 2 / 4，不会到这里
            console.writeErrLine("初始化失败：" + e.getMessage());
            return ExitCodes.STARTUP_ERROR;
        }

三点留意。第一，DaggerJellyfishComponent 是注解处理器的产物， 它不在源码仓库里，构建时出现在 target/generated-sources/annotations/ 下—— 本项目里能看到 DaggerJellyfishComponent.java 与 22 个 *_Factory.java（每条 @Provides 一个）。 本页不描述生成物的内部实现：那是 Dagger 的版本相关细节，读它没有收益， 知道「它是编译期生成的、CLI 直接用它的 builder」就够了。

第二，ConfigModule.loadDefault() 是静态调用，不依赖任何注入对象； 这正是「只想用缺省来源」的调用方唯一需要写的一行。 第三，注意 try 的位置：组件创建被包在「初始化失败」这一档里， 与 launch() 内部的 3 / 2 / 4 分类刻意分开——装配期炸了就是「内核没起成」。

2.3 10 个模块、22 条 @Provides：谁提供什么，为什么这么切

这一节的数字是自己数出来的（命令写在括号里，可复现）： 10 个 @Module（grep -rl '^@Module'，10 个文件）、 22 条 @Provides（grep -rn '@Provides$'，22 处）。 另一个独立佐证是生成物目录下恰好有 22 个 *_Factory.java——每条 @Provides 恰好一个。

模块提供什么@Provides为什么这样切分
ConfigModule ProjectConfigTrust；另有静态方法 loadDefault() 1 配置来源是部署事实，不由模块决定；模块里只留「信任裁决必须唯一」这一条绑定
LlmModule OkHttpClient、流式线程池 ExecutorService、7 个厂商 LlmClientCreator 9 共享连接池与线程池是全局资源；厂商客户端做成 Map 多绑定，按 provider type 路由
ExtensionModule TypeRegistry、ExtensionRegistry 2 同步侧与异步侧共用同一份表的唯一落点，两个派发策略都只是这张表上的视图
EventModule EventChannelOptions、EventChannel、EventPublisher 3 异步通道 + 一个窄接口视图，让配置层只依赖接口
PluginModule PluginRuntimeConfig、PluginContextFactory、SubAgentPort、PF4JPluginManager 4 插件运行时那四件套；顺序敏感（装配输入 → 上下文工厂 → 门面），放进同一个模块便于对照
AgentModule PermissionPolicyProvider（绑到 AgentManager 本身） 1 策略来源本就来自 agent 定义，依赖方向是 agent → permission

这张表解释了一个容易误解的现象：10 个模块里有 2 个是「空的」 （PermissionModule、CommandModule 只有 @Module 与私有构造器）。 它们不是占位垃圾。PermissionModule 的类注释解释了为什么空还留着： 它曾经放着一个「一律返回 unrestricted」的占位实现，后来 PermissionPolicyProvider 挪到 AgentModule（依赖方向 agent → permission）， 占位实现被删掉——保留它会形成同类型双绑定，Dagger 编译期即失败 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/PermissionModule.java:8 起）。 换句话说，「空模块」本身是「这一层不许有别的绑定」的一份声明。

另一个值得注意的边界：模块里只提供「怎么造」，不提供「造出来的东西怎么用」。 例如 PluginModule 只提供四个插件运行时构件， 但命令、工具、扩展点这些注册都不在这里发生——它们在 AgentHarness.bootstrap() 与插件自己的 start() 里完成。装配层只负责「谁依赖谁、哪些实例必须唯一」。

2.4 模块里反复出现的三种写法：static、@Singleton、窄接口视图

看几个有代表性的 @Provides，就能把模块的写法归纳完。 第一个是全局共享的 HTTP 客户端：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/LlmModule.java:50-62（static 的 @Provides：共享连接池）
    /**
     * 提供全局共享的 HTTP 客户端。
     * <p>
     * 构造细节（含「关掉重定向」的理由）在 {@code LlmClients.newHttpClient()}：
     * 手写装配侧（{@code JellyfishAssembler}）也要交付同一份，因此只留一个落点。
     *
     * @return OkHttpClient
     */
    @Provides
    @Singleton
    static OkHttpClient provideOkHttpClient() {
        return LlmClients.newHttpClient();
    }

为什么 @Provides 方法都是 static：模块类本身没有任何状态 （每个模块都是 final + 私有构造器），因此不需要先 new 一个模块实例再调方法。 声明成 static 之后 Dagger 直接静态调用它，省掉一个没有意义的对象； 同时这也是一个约束信号——模块不许持有状态，否则它就会成为「同一实例」约束的第四个落点。

注意 @Singleton 与 LlmClients.newHttpClient() 的组合：真正的构造细节 （含 followRedirects(false) 这类安全取舍）只在 Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/LlmClients.java:55 一处， Dagger 侧与手工侧都调它。「两边交付同一份」的落实办法是把构造收敛成一个静态工厂， 而不是在两条装配路径上各写一遍构造参数。

第二个例子是流式线程池，它演示了「有界优于无界」这条判断，同时也说明 同一份代码路径在两套装法里逐字相同（对照 JellyfishAssembler 里的同名私有方法）：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/LlmModule.java:74-91（有界线程池：并发上限与等待队列都是常量）
    @Provides
    @Singleton
    static ExecutorService provideStreamExecutor() {
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
                STREAM_MAX_THREADS,
                STREAM_MAX_THREADS,
                STREAM_KEEP_ALIVE_SECONDS,
                TimeUnit.SECONDS,

                    Thread thread = new Thread(runnable, "llm-stream");
                    thread.setDaemon(true);

        executor.allowCoreThreadTimeOut(true);
        return executor;
    }

常量在模块顶部定义（STREAM_MAX_THREADS = 32、STREAM_QUEUE_CAPACITY = 128、 STREAM_KEEP_ALIVE_SECONDS = 60L，Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/LlmModule.java:38-45）。 线程工厂把线程设为守护线程，这样空闲线程不会阻止 JVM 退出；AbortPolicy 表示「线程 + 队列都满就当场拒绝」，而不是无限排队。 这些运行参数与配置无关——它们是装配期定型的常量，改它们要重启进程。

2.5 @IntoMap + @StringKey：厂商客户端注册表

这是全站唯一一处「Map 多绑定」，也是 Dagger 用法上最值得学的一处。 先说它解决什么问题：内核认识 7 个 provider 键，每个键对应一个「怎么造客户端」的函数。 朴素做法是在工厂里写一长串 switch，或者在装配处 if-else 拼一张表—— 两种做法都把「厂商清单」写进了消费方。

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/LlmModule.java:100-119（每个厂商一条 @Provides @IntoMap @StringKey）
    @Provides
    @IntoMap
    @StringKey(ProviderTypes.OPENAI)
    static LlmClientCreator openAiClientCreator(OkHttpClient httpClient, ExecutorService streamExecutor) {
        return provider -> new OpenAiLlmClient(provider, httpClient, streamExecutor);
    }

    /**
     * 注册 DeepSeek 客户端创建器。
     *
     * @param httpClient     HTTP 客户端
     * @param streamExecutor 流式线程池
     * @return 客户端创建器

    @Provides

    @StringKey(ProviderTypes.DEEPSEEK)
    static LlmClientCreator deepSeekClientCreator(OkHttpClient httpClient, ExecutorService streamExecutor) {
        return provider -> new DeepSeekLlmClient(provider, httpClient, streamExecutor);

这段长这样读：@IntoMap 表示「这条绑定不贡献单个对象，而贡献一个 map 条目」， @StringKey(ProviderTypes.OPENAI) 表示「键是字符串 "openai"」。 7 条这样的 @Provides 合起来就是一张 Map<String, LlmClientCreator> 绑定， 消费者是注入它的工厂：

Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/llm/LlmClientFactory.java:69-84（消费整张 map 的 @Inject 构造器）
    /**
     * 构造工厂。
     *
     * @param creators       Dagger2 注入的 provider type 到创建器的映射，可为 {@code null}
     * @param extensions     扩展注册表，用于查询插件提供的 provider 类型
     * @param streamExecutor 流式线程池，插件适配器要在它上面跑阻塞式传输
     */

    public LlmClientFactory(Map<String, LlmClientCreator> creators, ExtensionRegistry extensions,
                            ExecutorService streamExecutor) {
        if (creators != null) {
            this.creators.putAll(creators);
        }
        this.extensions = extensions;
        this.streamExecutor = streamExecutor;
    }

调用方一个字都不用改：LlmClientFactory 拿到整张表，按 provider.getType() 查表创建客户端（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/llm/LlmClientFactory.java:169-171）。 于是关键的性质是：新增一个厂商 = 在 LlmModule 里加一条 @Provides， 不动工厂、不动任何调用方。

键的取值来自常量类 ProviderTypes（Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/support/ProviderTypes.java:14-22）， 7 个键是 openai / deepseek / minimax / gemini / google / claude / anthropic。 其中后两组是别名：google 与 gemini 都造 GeminiLlmClient，anthropic 与 claude 都造 ClaudeLlmClient。 别名键的存在是一处真实风险：漏掉一个别名键不会编译失败， 表现为「配了那个 provider 却静默不可用」（这条写在 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:409-410）。 而 LlmClientCreator 本身只是个单方法接口，一眼能看完： 「由一个 Provider 配置创建对应 LlmClient 的工厂函数」 （Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/llm/LlmClientCreator.java:8-9）。

设计依据：为什么是 Map 多绑定，而不是 if-else 或工厂里的 switch

三种做法的差别不在「能不能跑」，在新增一个厂商要碰几个文件、漏了会不会被发现：

  • if-else / switch：厂商清单写在消费方， 新增厂商要改工厂；漏改的后果是运行到那一条时报「未知 provider」——错误点离改动点很远。
  • 手拼一张 Map：清单离开消费方了，但落在一处普通代码里， 与其它绑定的写法不一致，装配层要同时维护两种风格（手工侧确实就是手拼一张 LinkedHashMap，见第 4 节）。
  • @IntoMap 多绑定：每条绑定自带键，清单由绑定本身构成， 消费方只声明「我要一张 Map<String, LlmClientCreator>」。 键重复会在编译期报错，键缺失（比如别名忘了加）则由测试或运行期暴露—— 这是 Dagger 在这里能提供的最大帮助。

还有一个附带收益：多绑定让「插件也能注册 provider」变得顺手。 LlmClientFactory 的 getRegisteredTypes() 只返回内核自带的 Map 快照，插件接管的类型另走扩展注册表查询——两条来源被清晰分开。

2.6 编译期校验：Dagger 在这里到底帮了什么

Dagger 最实际的收益不是「少写 new」，而是把一批错误从运行期提到编译期：

  • 缺绑定：某个构造器需要一个 Foo，而没有任何地方能提供它 → 编译失败。运行时容器（反射式 DI）对应的是启动或首次解析时抛 NoSuchBeanDefinitionException 一类的错误，而且往往带着一份难读的候选链。
  • 同类型双绑定：PermissionModule 里那个历史占位实现就是活例子—— 它的类注释写明「保留它会与 AgentModule 形成同类型双绑定，Dagger 编译期即失败」 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/PermissionModule.java:8 起）。 这条规矩的两面都要记住：多一条绑定编译不过，少一条绑定也编译不过， 所以「两种装法交付同一契约」这件事，在 Dagger 侧是被编译器持续检查的。
  • 接口没有绑定到实现：api 侧的接口（AskPort、SubAgentPort） Dagger 无从构造，必须显式绑定到实现——这正是 AskModule 必须存在一条 @Provides 的原因（Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/AskModule.java:40-44）， 缺了它同样是编译期报错。

对照一下覆盖率这一侧：Dagger* 生成物与 *_Factory.* 被排除在 JaCoCo 统计之外 （Jellyfish/pom.xml:272-278，其中 Jellyfish/pom.xml:274 就是 **/Dagger*）， 所以 jellyfish-di 报出来的覆盖率只反映人写的装配代码 （24 页第 3 节列了这股覆盖率实测）。这两件事是配套的： 生成物不进分母，人写的那部分就必须由测试兜住。

3.2 刻意不声明生命周期

接口上一个 start() / stop() 都没有。理由在注释里：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishRuntime.java:35-38（为什么不放一对 start/stop）
 * <b>本接口刻意不声明生命周期</b>：启动与收敛是 {@link AgentHarness#bootstrap()} /
 * {@link AgentHarness#shutdown()} 的事，外壳按自己的时机调（CLI 在 {@code Launcher} 里，
 * Spring 外壳在 {@code SmartLifecycle} 里）。接口里再放一对 start/stop 只会多出「谁先谁后」的
 * 第二处说法，而启动顺序是内核的硬约束，只能有一处。

这段话有可验证的落点：CLI 侧启动与收敛确实都写在 Launcher 里—— 先写运行时信息（Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:87-88）， 再做项目级配置的信任表态（Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:92-93）， 然后 bootstrap()（Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:104）， 最后在 finally 里 shutdown()（Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/Launcher.java:135）。 这几步的相对顺序不是外壳的心血来潮：运行时信息必须在 bootstrap() 之前写入 （插件在 start() 里就会读它，这条写在 Jellyfish/docs/constraints.md:898-899），信任表态也必须在装载配置之前。

所以接口上不放 start/stop 不是「懒得加」，而是避免出现第二处顺序的说法。 外壳拿到的 JellyfishRuntime 只是一个「已经装好的对象图」， 什么时候让它转起来由外壳按自己的容器时机决定。

3.3 「同一实例」约束：不体现在签名上，只能靠实现自己守住

这是这套设计真实的弱点，作者在类注释里直接承认了：

Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishRuntime.java:40-43（逐字）
 * <b>实现者必须保证「同一实例」约束</b>：例如 {@code EventPublisher} 与 {@link #eventChannel()}
 * 必须是同一个对象、{@link ExtensionRegistry} 与 {@link EventChannel} 必须共用同一份
 * {@code TypeRegistry}。这些约束不体现在方法签名上，只能靠各实现自己守住；两套实现的一致性
 * 由 {@code JellyfishAssemblerTest} 断言。

换句话说：接口能保证「你交给我一个 eventChannel()」，但保证不了 「别的组件内部用的也是这一份」。这类约束一共有四处，全部得靠两条装配路径各自落实：

这张图里每一条边都代表一次「两处必须看到同一份状态」。它们的失败模式在 25 页与本节第 5 小节会再展开，这里先把四处点清楚：

  • 注册表唯一：同步扩展点与异步事件通道共用同一份 TypeRegistry。 分叉的代价很具体——插件停止时按 owner 回收只走过通道那一张表， 于是该插件的事件订阅全部残留（插件已经停了、监听器还在被回调的幽灵订阅）。
  • EventPublisher 就是那个通道：配置、模型、agent 的告警都从它出去。 如果它指向另一个没人订阅的通道，现象是「我配错了但一点提示都没有」。
  • ProjectConfigTrust 唯一：授予信任发生在启动期（启动参数或交互确认）， 而读取它发生在 RuntimeConfig.refresh()；两份状态就会「确认了却不生效」。
  • 键一个都不能少：厂商别名键（google / anthropic）漏了不会编译失败， 只会让配置里那个 provider 静默不可用。

Dagger 侧讲完了，现在看手工侧。它存在的理由写在 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:96-123 的类注释里，最关键的两句是：

两条非直觉顺序里，第一条（插件运行时排在 ReAct / 压缩链之后）是依赖关系决定的： PluginContextFactory 要拿到 SubAgentPort，而那条实现链要穿过 子代理启动器、ReAct 循环器、动作分发器、压缩器，最后到子代理委派适配器。 对应的落点在第十四层：

这里还有一处与模块写法不同的细节值得记下来：手工侧在装配时就调了一次 pluginRuntimeConfig.refresh(...)，而 Dagger 侧在 providePluginRuntimeConfig 里也调了一次 （Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/PluginModule.java:57-63）。 两次都是在「合法的默认对象」上刷一份构造期快照， 真正生效的刷新发生在 AgentHarness.bootstrap() 里、插件启动之前。 对象是「引用稳定、快照可换」的，所以装配期刷一次不生效但无害，忘掉真正的刷新才是故障。

第二条非直觉顺序（PluginRuntimeConfig 只建一次）在两边是同一个道理： 刷新要刷在管理器手里的那一个对象上，不能另建一个。

坑点：顺序不能靠「照抄清单」

装配顺序是硬约束，但它不是一份可以背下来的清单。原因有二：

  • 清单会随依赖图变化而失效，而依赖图是活的（每次新增绑定都可能插入一层）；
  • 同一个「先后」在不同位置有不同理由——assemble() 的顺序理由是「谁依赖谁」， 而 AgentHarness.shutdown() 的收敛顺序理由是「先静默所有写者、再兜底落盘」， 两者不是一回事。

要改装配顺序时，正确的做法是读这两处的注释： Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:221-235 的 assemble() 注释，以及 AgentHarness.shutdown() 里那条「flushAll() 必须早于 pluginManager.close()」的硬约束（Jellyfish/AGENTS.md 的「关键不变量」一节有摘要）。

4.4 JellyfishAssemblerTest 怎么锁一致性

这个测试有 283 行、9 个方法，类注释把「防什么」和「怎么防」都写清楚了 （Jellyfish/jellyfish-di/src/test/java/zcd/jellyfish/di/JellyfishAssemblerTest.java:33-49）： 「谁依赖谁」写错会编译不过（类型互不相同）， 真正会静默出事的只有一类——本该唯一的实例被建了第二份。 而它用行为断言而不是比对象引用：约束的落点全在私有字段里，反射读字段会把测试绑死在实现细节上。

首先是那条专治 N-07 的断言——它给两次不同的输入，要求两次都命中调用方给的那一份：

Jellyfish/jellyfish-di/src/test/java/zcd/jellyfish/di/JellyfishAssemblerTest.java:62-78（配置来源必须由调用方决定）

        // 它最多只能命中其中一份，而这里要求两次都命中调用方给的那一份
        AppConfig first = appConfigNamed("jellyfish-di-test-a");
        AppConfig second = appConfigNamed("jellyfish-di-test-b");

        // When / Then：两种装法读到的都是**那一次**给的那一份（配置来源是部署事实，由调用方决定）。

        assertEquals("jellyfish-di-test-a",

        assertEquals("jellyfish-di-test-b",
                DaggerJellyfishComponent.builder().appConfig(second).build().appConfig().getProcessName());

这条测试的设计值得单独学：它没有断言「AppConfig 非 null」，而是喂了两份可辨认的配置。 因为「非 null」证明不了「是调用方给的那一份」——一个固定从 classpath 读的实现照样能让断言通过，只要它构造出了一份非 null 的配置。 给两次不同的输入，就把「固定从某个来源读」那种实现彻底排掉了：它最多只能命中其中一份。

5. 装配错了会怎样

这一节把上面散落的坑点收在一起，因为它们的共同特征很鲜明：装配错误几乎都不会抛异常。

5.1 静默分叉：不报错，只是什么都不发生

少写一行 EventPublisher publisher = eventChannel;（手工侧那一行在 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:246）的后果不是异常， 而是「配置 / 模型 / agent 的告警发进一个没人订阅的通道」——现象是 「我配错了但一点提示都没有」。同类的还有：

  • 插件拿到的出向端口被装成占位实现（AskPort.unavailable()）：插件照常启动， 功能只在运行时悄悄不生效——测试里为此专门断言了「不是占位」「就是装配出来的那一个通道」 （Jellyfish/jellyfish-di/src/test/java/zcd/jellyfish/di/JellyfishAssemblerTest.java:221-234）。
  • 两个派发策略各拿一张 TypeRegistry：幽灵订阅（插件停了，监听器还在被回调）。
  • 厂商别名键漏一个：配了 google 却「provider 不认识」。
坑点：这类问题只能靠专门的测试抓

它们没有编译错误、没有启动期异常、日志里也不会有痕迹——因为「发到一个没人订阅的通道」 在实现上完全合法。判断这类问题的办法只有一个：改完装配先跑 mvn -q -Dtest=JellyfishAssemblerTest test。 这也是为什么这个测试用的是「从一个入口写、从另一个入口读」的行为断言—— 它抓的正是可观察行为上的分叉，而不是实现上的写法。

5.2 顺序类分叉：别照抄清单

顺序错误的表现比静默分叉好一点（通常是 NullPointerException， 因为你拿到了一个还没赋值的字段），但定位起来依然费劲。要改顺序时，以 Jellyfish/jellyfish-di/src/main/java/zcd/jellyfish/di/JellyfishAssembler.java:221-235 的注释与 AgentHarness.shutdown() 为准，不要照抄一份「哪一步必须第几个」的清单—— 理由见上面的坑点框（顺序的「为什么」在不同位置并不相同）。

5.3 配置来源不统一：两种装法在起跑线上就不同

如果 AppConfig 回到「由模块固定提供」的做法， 就会出现「CLI 与其它容器外壳的配置来源不同」——一个用 classpath:config.json， 另一个用它自己的来源，而两边都认为自己装的是同一个契约。 这正是加 Builder 要解决的问题，也是 Jellyfish/docs/constraints.md:190 那条「不要把它改回模块提供」的原因。

5.4 覆盖率上的错觉

Dagger* 与 *_Factory.* 被排除在 JaCoCo 之外 （Jellyfish/pom.xml:272-278），所以 jellyfish-di 报出来的覆盖率 只反映人写的装配代码：JellyfishRuntime、JellyfishAssembler 与 10 个模块。反过来说，生成物没人测（也不该测）， 而人写的那部分——尤其「哪些实例必须唯一」这类约束——就得靠 JellyfishAssemblerTest 与几个模块级测试 （AgentModuleTest、AskModuleTest、ExtensionModuleTest、 PluginModuleTest，都在同一目录下）来覆盖。

关键结论

  1. 10 个模块、22 条 @Provides、23 个访问器、13 个源文件—— 这四个数字是这一页的骨架，也都是可以自己数一遍的（数法见第 2.3 节与第 3.1 节的说明）。
  2. JellyfishComponent extends JellyfishRuntime：继承买的是编译期—— 漏交付一个入口变成编译错误，而不是某个外壳用到时才发现。两套装法因此不可能在入口集合上漂移。
  3. @Component.Builder + @BindsInstance 把 AppConfig 交回调用方：配置来源是部署事实，不该由「用哪种装法」决定。 缺省来源（classpath）留在 ConfigModule.loadDefault()，不能做成 @Provides（会双绑定）。
  4. @IntoMap + @StringKey 让「新增厂商只加一条 @Provides」成立： 清单由绑定本身构成，消费方只声明「我要一张 map」。唯一的空隙是别名键——它漏了不报错。
  5. JellyfishRuntime 是不含 DI 注解、不声明生命周期的普通接口： 前者让外壳不必依赖 Dagger 代码生成，后者让「启动顺序」全站只有一处说法 （AgentHarness.bootstrap() / shutdown()，外壳决定时机）。
  6. 「同一实例」约束不体现在签名上——注册表唯一、EventPublisher 就是那个通道、 信任裁决唯一、别名键齐全。四条都只能靠实现自己守住，靠 JellyfishAssemblerTest（同一段行为对两种装配各跑一遍）抓分叉。
  7. 装配分叉是静默的：没有异常、没有日志，只有「某个功能悄悄不生效」。 这是这一层最贵的一课，也是「两处都要改」这个代价被接受的前提。
