14 整合到 Spring Boot

如果你的服务已经是 Spring Boot 应用，而你想在里面用上 agent（读文件、跑命令、查库、做多轮工具调用）， 那就不必再包一层进程。本页讲的就是这件事：jellyfish-spring-boot-starter 把内核装进你的容器， 再用一层带归属校验的门面把「用户」这一维补上。接口由你自己写——starter 一个 HTTP 端点都不提供。

学习目标

  • 说清 starter 「是什么」与「不是什么」——尤其是「不提供 HTTP 接口、不依赖 spring-boot-starter-web、不改内核、不支持同进程多套内核」四条；
  • 照着抄出可用的 application.yml，并说清每个 jellyfish.* 字段的类型、默认值与生效方式；
  • 明白「配置的分工」：yml 只回答「文件在哪」，模型 / agent / 插件的内容仍是内核格式的 JSON；
  • 理解自动装配的三步链与 @ConditionalOnProperty 的「整条不装」语义；
  • 注入 JellyfishUserFacade 跑通一次对话，并记住四条必须遵守的纪律；
  • 把对话、审批、提问接成 REST + SSE 接口，知道 SseEmitter 为什么要设 0L；
  • 知道多用户护栏补了内核哪几个缺口、唯一可替换的 SPI 是什么，以及生产环境的硬红线。
读这一页之前需要什么
  • 三个仓库的版本都是 0.1.1，但没有任何文档声明三者之间的版本兼容矩阵； 凡涉及「哪个内核版本配哪个 Starter 版本」，一律按 【版本对应关系需查阅各自 README】 处理。
  • 本页假定你已经知道内核的四份配置文件与插件怎么装：没读过的话先看 05 配置体系总览 与 11 安装与使用官方插件—— starter 里的 models.json / agents.json / jellyfish.json 与 CLI 版完全同一份格式。

1. 它是什么、不是什么

jellyfish-spring-boot-starter 做的事情只有两件：把内核装进你的 Spring 容器， 以及在内核外面补一层「用户」。前者复用内核自己的装配模块，后者是本 starter 的主要价值。 除此之外它什么都不做——这一节先把边界钉死，后面的所有内容都在这个边界里。

它是什么它不是什么
一个自动配置 + 一层带归属校验的多用户门面。 业务代码注入 JellyfishUserFacade 就能建会话、提问、裁决审批， 并通过插件系统扩展内核的能力（文件工具、shell、持久化、MCP、编排……）。 不提供任何 HTTP 接口。接口由接入方自己定义（@RestController + SseEmitter 等）， starter 只交付编程式 API。因此它不依赖 spring-boot-starter-web， 不会替你决定 Web 技术选型（也不会带进 Tomcat / Netty）。
内核的另一种装配方式。它只依赖内核的装配模块 jellyfish-di， 用它的 JellyfishAssembler.create(...) 装配——装配知识只有一处， 内核新增绑定不需要本模块跟着改。 不改内核。内核的组件一个都没有在 Spring 里重建；也没有引入 Dagger 生成的组件 （那会把 Dagger 的运行期依赖带进接入方的技术栈）。 两个数字都对，只是口径不同：55 是内核里「带 @Inject 的类」的个数， 63 是装配完成后对象图上的节点数——两句话出自同一处 javadoc， 原文是「整张图（63 个节点）由 JellyfishAssembler 一次装配完成， 这里不逐个注册内核的 55 个带 @Inject 的类」。README 那句「内核那 55 个组件」说的是前者。
面向服务端场景的装配。外壳种类恒为「服务化外壳」（hasUI=false）， 有终端时用 jellyfish.runtime.interactive=true 让插件据此降级。 不支持同进程多套内核。内核是进程级单例语义（「当前会话」是一个进程级指针、 模型索引进程级一份），两套内核在同一个 JVM 里会互相污染。
为什么门面「一个 HTTP 端点都不提供」是对的

会话 id 怎么生成、鉴权放在哪一层、SSE 还是 WebSocket、返回体长什么样——这些是你的业务的决定， 而不是一个 starter 的。starter 能替你决定的只有一件事：哪些能力可以被业务代码拿到。 所以它给的是「带归属校验的门面」而不是「控制器」。

3. application.yml：完整示例与逐字段表

最小可用配置：路径 + 开关

是什么
整套配置只有路径与开关两类。真正的「内容」（有哪些模型、哪个 agent 能调哪些工具、 启用哪些插件）仍然写在内核格式的 JSON 里，由 application.yml 指向它们。
怎么用
把下面这份抄进 src/main/resources/application.yml，再把 models.json / agents.json / jellyfish.json 放进 src/main/resources/jellyfish/ 下（用 classpath: 前缀指过来是最省事的做法）。

完整示例（照抄 README 的那一份）

jellyfish:
  enabled: true
  process-name: my-app

  # 路径：yml 只回答「那些文件在哪」
  models:   { global-path: '~/.jellyfish/models.json',    project-path: 'classpath:jellyfish/models.json' }
  agents:   { global-path: '~/.jellyfish/agents.json',    project-path: 'classpath:jellyfish/agents.json' }
  settings: { global-path: '~/.jellyfish/jellyfish.json', project-path: 'classpath:jellyfish/jellyfish.json' }

  plugins:
    roots: [ '~/.jellyfish/plugins/' ]     # 插件 jar 放哪；平铺 jar 或「一插件一子目录」都支持

  runtime:
    interactive: false                      # 有终端时置 true（插件据此降级）

  approval:
    enabled: false                          # 见第 8 节「审批」

  ask:
    enabled: false                          # 见第 9 节「提问」

  lifecycle:
    bootstrap-on-start: true                # false = 只装配不启动；自己挑时机就注入 JellyfishLifecycle 调 bootstrap()

配置：starter 自己的字段（前缀 jellyfish）

字段类型必填默认值含义示例
jellyfish.enabled boolean 选填 true false 时一个 Bean 都不装配（连内核对象图都不构造）。条件在类级别，见第 5 节 false
jellyfish.process-name string 选填 Jellyfish 进程名，进内核的 AppConfig，仅用于展示与日志 my-app
jellyfish.models.global-path string 选填 ~/.jellyfish/models.json 模型配置段（ModelSettings）的全局级路径，支持 classpath: 前缀；空串表示该层级未配置（内核视为「未配置」而非「配错」，不发告警） ~/.jellyfish/models.json
jellyfish.models.project-path string 选填 ./.jellyfish/models.json 模型配置段的项目级路径。项目级优先于全局级，但是否加载由 trust-project-config 决定 classpath:jellyfish/models.json
jellyfish.agents.global-path string 选填 ~/.jellyfish/agents.json agent 配置段（AgentSettings）的全局级路径，同上语义 ~/.jellyfish/agents.json
jellyfish.agents.project-path string 选填 ./.jellyfish/agents.json agent 配置段的项目级路径 classpath:jellyfish/agents.json
jellyfish.settings.global-path string 选填 ~/.jellyfish/jellyfish.json 运行期设置段（JellyfishSettings）的全局级路径：插件启用名单、逐插件配置段、react / permission / subAgent ~/.jellyfish/jellyfish.json
jellyfish.settings.project-path string 选填 ./.jellyfish/jellyfish.json 运行期设置段的项目级路径 classpath:jellyfish/jellyfish.json
jellyfish.plugins.roots list<string> 选填 ['~/.jellyfish/plugins/'] 插件扫描目录，顺序即扫描顺序；平铺 jar 与「一插件一子目录 + plugin.properties」都支持。 只含扫描目录——启用名单在 jellyfish.json 里 ['~/.jellyfish/plugins/']
jellyfish.trust-project-config boolean 选填 false 是否信任并加载项目级配置。缺省不加载：它按进程当前目录读取，能改模型端点与密钥、新增 agent、改落盘目录， 因此内容会随「在哪个目录里启动」而变。用 classpath: 指到自己的 resources 时不受此开关约束（那是构件的一部分） true
jellyfish.runtime.interactive boolean 选填 false 是否有终端，插件据此降级。外壳种类不可配，恒为「服务化外壳」（hasUI=false、Shell.SERVER） true
jellyfish.approval.enabled boolean 选填 false 是否挂载人工审批通道。关闭时需审批的调用立即按拒绝处理（fail-closed）；打开后阻塞最多 120 秒。见第 8 节 true
jellyfish.ask.enabled boolean 选填 false 是否挂载提问通道。关闭时提问立即返回一条「问不到人」的成功结果（不阻塞、不失败）；打开后阻塞最多 120 秒。见第 9 节 true
jellyfish.lifecycle.bootstrap-on-start boolean 选填 true false = 只装配不启动内核，由接入方挑时机。 挑时机的方式是注入 JellyfishLifecycle 调它的 bootstrap()；两条路径的关闭动作相同 false

配置：多用户护栏的字段（前缀 jellyfish.user，独立配置类）

字段类型必填默认值含义示例
jellyfish.user.enabled boolean 选填 true 是否启用多用户门面。关掉则只装配内核，不提供任何护栏入口 true
jellyfish.user.max-inflight-turns-per-user int 选填 2 每用户并发回合上限；<= 0 表示不限。占不到额度立刻拒绝，不排队（排队会把容器线程一起堵住） 4
jellyfish.user.max-sessions-per-user int 选填 20 每用户会话数上限；<= 0 表示不限。「查数 + 建 + 绑定」在同一把锁里完成 50
jellyfish.user.reaper-enabled boolean 选填 true 是否开启闲置会话回收 false
jellyfish.user.idle-timeout Duration 选填 30m 多久没用算「可以回收了」。<= 0（或不配）表示不回收，此时回收器不启动，会话表只增不减 1h
jellyfish.user.sweep-interval Duration 选填 5m 回收扫描间隔（钳到 >= 1 秒） 30s
jellyfish.user.denied-commands list<string> 选填 [new, resume, delete, rm, session, sessions, reload] 命令闸门拦下的命令名（不含前缀，别名各写一条）。这些命令要么改写进程级状态、要么按参数操作任意会话、要么列出全进程会话 [new, resume, delete, rm, session, sessions, reload, mcp]
jellyfish.user.session-required-commands list<string> 选填 [model, agent, a] 这些命令必须带会话才准执行：不带会话时它们写的是「下次新建会话的默认值」，那是进程级状态 [model, agent, a, plan]

yml 里用短横线小写（max-inflight-turns-per-user），对应的 Java 字段是驼峰 （maxInflightTurnsPerUser），由 Spring 的宽松绑定对应起来。

生效方式：application.yml 的任何改动都建议直接重启 需重启——本 starter 不提供 /reload 的入口， 内核那套热更新没有暴露出来。同理，models.json / agents.json / jellyfish.json 的内容改动也建议重启（在 CLI 模式下它们是可以 /reload 的， 见 13 插件进阶与发布）。

常见问题

  • 一份配置都不给能起来吗？能。配置缺失只告警、不中断启动——这是内核的既有纪律， 代价是模型与 agent 都是空的。默认路径与内核 CLI 的缺省一致（~/.jellyfish/ + ./.jellyfish/）， 因此同一个进程里跑 CLI 与本应用看到的是同一份配置。
  • 为什么我写在项目级 ./.jellyfish/ 的配置不生效？因为 trust-project-config 缺省 false。用 classpath: 指向自己的 resources 时不受这个开关约束。
  • jellyfish.user.idle-timeout 写 0 是「立刻回收」吗？不是，是「不回收」。 越界值不会被折算成一个很小的门槛——1 毫秒的语义是「每轮扫描关掉所有空闲会话并解绑归属」， 而配的人以为自己写的是「不限」。

4. 配置的分工：yml 给路径，内容仍是内核格式

配置在哪为什么
四份配置文件在哪、插件扫描目录 application.yml 「文件在哪」是部署事实，与 Spring 的配置习惯一致
providers / models / agent 定义 models.json / agents.json 内核已有格式，classpath: 前缀可用
插件启用名单、逐插件配置段、react / permission / subAgent 段 jellyfish.json 同上

为什么不把 JSON 格式翻译成 yml？那需要给内核加第二个配置写入口， 而内核的配置快照语义正是靠「只有 refresh() 一个写入口」成立的。收益只是「少一个文件」。

classpath: 前缀怎么用：把 JSON 放进你的 src/main/resources/jellyfish/ 下，然后在 yml 里写 classpath:jellyfish/models.json。这样配置是构件的一部分， 因此不受 trust-project-config 约束（那个开关管的是「按进程当前目录读到的项目级文件」）。 空串则表示该层级未配置。

AppConfig 由 yml 直接构造、不走 ConfigLoader.loadAppConfig()： 后者读的是写死的 classpath:config.json，而 classpath 上的同名资源谁生效取决于顺序。 本 starter 若自带一份就会与接入方项目里的同名资源争夺优先级，因此让 application.yml 成为唯一入口。

同一个进程里同时跑 CLI 与本应用时注意

因为默认路径一致，两者看到的是同一份 ~/.jellyfish/*.json 与同一批插件。 这不是 bug，而是有意的：换机器只用改一处。但如果你希望它们互不干扰，就得在 yml 里显式给出不同的路径。

5. 自动装配入口

spring.factories 的两个条目

是什么
本 starter 用 Boot 2.7 的自动配置注册入口 META-INF/spring.factories： org.springframework.boot.autoconfigure.EnableAutoConfiguration 下挂两个类—— zcd.jellyfish.spring.boot.JellyfishAutoConfiguration 与 zcd.jellyfish.spring.boot.user.JellyfishUserAutoConfiguration。
怎么用
你不需要做任何事（Boot 会读它）。但要知道两件事：两者的顺序不靠这里的排列， 而是由 JellyfishUserAutoConfiguration 上的 @AutoConfigureAfter 声明 （它需要内核的持有者 Bean 先装配好，@ConditionalOnBean 才能求对值）； 以及多用户护栏的 Bean 声明不在 spring.factories 里， 而由 JellyfishAutoConfiguration 直接 @Import——它需要内核门面的包私有访问器， 因此必须与持有者同包。

为什么用 spring.factories 而不是 AutoConfiguration.imports： 前者在 Boot 2.7 上必定生效，后者要到 Boot 3.0 才成为唯一入口。 迁移到 Boot 3 时把本文件换成那一份 imports 文件即可（内容只有类名），代码不用动。

配置　这里没有可配字段；开关是下面那一条 @ConditionalOnProperty， 以及 jellyfish.user.enabled（护栏层单独一层开关，同样必须显式写成 false 才关）。

完整示例：本 starter 的自动配置类（顺序与条件都在这几个注解上）

// 组件声明（节选自 JellyfishAutoConfiguration，注释为说明）
@AutoConfiguration
@ConditionalOnProperty(prefix = "jellyfish", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(JellyfishProperties.class)
@Import({JellyfishRuntimeConfiguration.class, JellyfishFacadeConfiguration.class})
public class JellyfishAutoConfiguration {

    /** 注册内核生命周期宿主：把「内核什么时候起停」接到容器生命周期上。 */
    @Bean
    public JellyfishLifecycle jellyfishLifecycle(JellyfishKernel jellyfishKernel,
                                                 JellyfishProperties jellyfishProperties) {
        return new JellyfishLifecycle(jellyfishKernel, jellyfishProperties);
    }
}

常见问题

  • jellyfish.enabled=false 与「装好了但不用」有什么区别？ 区别很大：条件是类级别的，因此关掉时不但不启动内核， 连对象图都不会构造——构造本身就有副作用（例如缓存保活器在构造期就排了扫描任务）。 「不启用」应当是零成本。
  • 改了 spring.factories 怎么验证？仓库里有一条专门的用例 JellyfishStarterRegistrationTest 走完整 SpringApplication， 是唯一会读这个文件的测试（其它用例显式点名配置类，把类名写错也照样绿）。

四条必须遵守的纪律

  1. 交互一律走 JellyfishUserFacade。 内核没有归属校验——SessionManager 按 id 操作任意会话、ApprovalChannel / AskChannel 只认「某会话的头槽位」不认调用方是谁、ShellStreams 能按 id 订阅任意会话的事件流。 因此 starter 默认不把这些门面注册成 Bean：容器里拿不到的，就用不着记住「不要用它」。
  2. 不要调 switchTo / createDefault。 那是进程级的「当前会话」指针，多用户下会让一个用户的会话变成所有人的。门面内部一律用 create(agentId, provider, model)。
  3. 不要调 /new、/resume、/delete、/session、/reload。 门面的 executeCommand 已经拦住了它们（名单可配，见第 3 节）；直接调 CommandManager 就绕过了闸门。
  4. chat 的 listener 在内核线程上被调用（react / llm-stream / 工具输出泵，后两者会并发）：必须快且线程安全。写 SSE 这类 I/O 建议自己缓冲或转投线程池； listener 抛出的异常会被记日志后吞掉，不会影响内核的事件派发。
最容易被绕过的是第 4 条

「listener 抛异常会被吞掉」听起来很宽容，但它同时意味着：你在 listener 里写的东西失败时不会有任何反馈。 所以不要在 listener 里做数据库写入、发 MQ、调外部接口——那些必须只做「入队 / 转投」，真正的处理在别的线程上做。

完整示例：不进 Web 层，纯 Java 调一次 chat

是什么
最短的一条路：建会话 → 提交一次对话 → 在 listener 里收到终态事件后收工。 这里用 CommandLineRunner 只是为了让代码可直接运行，真实场景通常是你的服务方法。
怎么用
直接注入 JellyfishUserFacade，不要注入任何内核门面。 
package com.example.app;

import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;
import zcd.jellyfish.core.conversation.ShellTurnEvent;
import zcd.jellyfish.core.conversation.Submission;
import zcd.jellyfish.spring.boot.user.JellyfishUserFacade;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

/**
 * 纯 Java 调一次对话：不经过任何 Web 层。
 *
 * @author you
 */
@Component
public class DemoRunner implements CommandLineRunner {

    /** 业务侧唯一入口。 */
    private final JellyfishUserFacade jellyfish;

    /**
     * 构造注入。
     *
     * @param jellyfish 用户门面，由 starter 装配
     */
    public DemoRunner(JellyfishUserFacade jellyfish) {
        this.jellyfish = jellyfish;
    }

    @Override
    public void run(String... args) throws Exception {
        String userId = "u-1001";

        // 1) 建会话：归属已经记在门面内部，不需要你操心
        String sessionId = jellyfish.createSession(userId);

        // 2) 提交一次对话。回合是异步的，用闩锁等终态
        final CountDownLatch done = new CountDownLatch(1);
        Submission submission = jellyfish.chat(userId, sessionId, "用一句话解释什么是 ReAct 循环",
                event -> {
                    // 这个回调在内核线程上，必须快且线程安全：这里只打印与计数
                    System.out.println("[" + event.getKind() + "] " + line(event));
                    if (event.isTerminal()) {
                        // 终态有四条互斥事件：COMPLETED / CANCELLED / ERROR / BLOCKED
                        done.countDown();
                    }
                });
        System.out.println("提交结果：" + submission.getKind());

        if (!done.await(5, TimeUnit.MINUTES)) {
            // 超时：先把在途回合取消掉，别让它一直占着这个用户的额度
            jellyfish.cancel(userId, sessionId);
        }
    }

    /**
     * 把一条事件压成一行可读文本。
     *
     * @param event 回合事件
     * @return 一行文本
     */
    private static String line(ShellTurnEvent event) {
        if (event.getText() != null && !event.getText().isEmpty()) {
            return event.getText();
        }
        if (event.getToolName() != null) {
            return event.getToolName();
        }
        return event.getKind().name();
    }
}

配置：这段代码本身没有配置字段。它依赖 jellyfish.models.* 指向的 models.json（要有可用的 provider 与模型，见 06 models.json 详解）， 以及 jellyfish.plugins.roots + jellyfish.json 里装好的插件—— 不装插件的话模型手里没有任何工具。

常见问题

  • chat 返回了 REJECTED 是什么情况？会话不存在、插件拦下了这轮输入等。 它不会产生终态事件，因此额度在门面内部已经被还掉了（你不需要自己处理）。
  • 为什么 listener 收到终态之后就不用管了？门面内部在收到终态时关闭了订阅，所以不要期待更多事件。
  • 能不能在 listener 里调 jellyfish.chat 再发一轮？不要。那是在内核线程上发起新的回合， 而且这个用户的并发额度还没归还（额度是随终态归还的）。要串第二轮，就在你自己的线程上等终态之后再发。

7. 暴露为 REST 接口：照抄一份能用的控制器

会话 / 对话（SSE）/ 审批

是什么
接口由你自己写。下面这份是 README 给的示例：建会话、SSE 对话、裁决审批三个方法。 SSE 的帧格式由你决定，starter 只给你内核事件。
怎么用
直接抄进你的工程。注意三处：SseEmitter 用 0L（不超时）、 listener 里只做「转帧 + 发送」、真正的慢处理转投线程池。 
package com.example.app;

import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;
import zcd.jellyfish.spring.boot.user.JellyfishUserFacade;

/**
 * 把内核能力暴露成 REST + SSE。接口形态完全由你决定。
 *
 * @author you
 */
@RestController
public class ChatController {

    /** 业务侧唯一入口。 */
    private final JellyfishUserFacade jellyfish;

    /**
     * 构造注入。
     *
     * @param jellyfish 用户门面
     */
    public ChatController(JellyfishUserFacade jellyfish) {
        this.jellyfish = jellyfish;
    }

    /** 建会话。 */
    @PostMapping("/sessions")
    public String create(@RequestParam String userId) {
        return jellyfish.createSession(userId);
    }

    /** 对话。SSE 由你自己写，starter 只给你内核事件。 */
    @GetMapping(value = "/sessions/{sid}/chat", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter chat(@RequestParam String userId, @PathVariable String sid,
                           @RequestParam String message) {
        SseEmitter emitter = new SseEmitter(0L);   // 不超时：回合可能持续几分钟
        jellyfish.chat(userId, sid, message, event -> {   // 注意：这个回调在内核线程上
            try {
                emitter.send(toFrame(event));
                if (event.isTerminal()) {
                    emitter.complete();
                }
            } catch (Exception e) {
                // listener 里的异常会被门面吞掉，因此这里必须自己收尾，否则连接会一直挂着
                emitter.completeWithError(e);
            }
        });
        return emitter;
    }

    /** 裁决审批。 */
    @PostMapping("/sessions/{sid}/approvals/{rid}")
    public void approve(@RequestParam String userId, @PathVariable String sid,
                        @PathVariable String rid, @RequestParam boolean ok) {
        if (!jellyfish.approve(userId, sid, rid, ok)) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "没有这条待审批项");
        }
    }
}

SSE 的 event 怎么转帧：用 SseEmitter.event() 构帧， 事件名用 Kind（小写），数据用一个简单的 Map。注意 SseEmitter.send 会抛 IOException，而 onTurnEvent 没有 throws 子句，所以必须自己 try/catch。

import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;
import zcd.jellyfish.core.conversation.ShellTurnEvent;

import java.util.LinkedHashMap;
import java.util.Locale;
import java.util.Map;

/**
 * 内核事件 → SSE 一帧。
 *
 * @param event 回合事件
 * @return 可交给 SseEmitter.send 的帧
 */
private static SseEmitter.SseEventBuilder toFrame(ShellTurnEvent event) {
    return SseEmitter.event()
            .name(event.getKind().name().toLowerCase(Locale.ROOT))
            .data(payloadOf(event));
}

/**
 * 只放前端真正要用的字段；不要整个事件对象直接序列化（里面可能有工具参数与输出）。
 *
 * @param event 回合事件
 * @return 载荷
 */
private static Map<String, Object> payloadOf(ShellTurnEvent event) {
    Map<String, Object> payload = new LinkedHashMap<String, Object>();
    payload.put("kind", event.getKind().name());
    payload.put("turnId", event.getTurnId());
    payload.put("text", event.getText());
    payload.put("toolName", event.getToolName());
    payload.put("rounds", event.getRounds());
    return payload;
}

向用户提问的通道开关（代价与审批不同）

10. 多用户护栏：本 starter 的主要价值

内核没有「用户」，这一层把它补上

是什么
内核是为「本地单用户、多会话」设计的，它的 HTTP 外壳也是（默认只绑回环、 GET /sessions 返回全量会话）。它没有「用户」这一维——Session 上没有 owner 字段。 下面这些事内核都不做，由本 starter 补齐。
怎么用
默认全部开启，你只需要调 jellyfish.user.* 的数值（见第 3 节）。 唯一的「接线动作」是在需要时替换 SessionOwnerStore。

配置：护栏补的缺口与做法

护栏内核的缺口本 starter 的做法
会话归属 无 owner 字段；all() 是全量的 SessionOwnerStore（SPI，默认内存实现）+ 每个入口先校验； 「不存在」与「不属于你」对外是同一个答复，避免用错误信息枚举会话 id
每用户并发配额 react 池 8 线程 + 128 队列是全进程共享，一个用户能占满 每用户信号量，占不到立刻拒绝（不排队，否则连容器线程一起堵）
每用户会话数上限 会话表只增不减、无上限 建会话时检查；「查数 + 建 + 绑定」在同一把锁里完成
闲置回收 无 TTL、无淘汰，消息全量驻留内存 定时 close()；跳过有在途回合的会话（长调用不刷新时间戳，只看时间会误杀）， 也跳过没有归属者的会话
审批归属 resolve 只校验「是不是它自己会话的头槽位」，不校验调用方说的会话对不对 网关额外要求 requestId 属于本会话且是头槽位
提问归属 resolve 同上；而答案会作为工具结果原文进模型上下文 同一条要求，且更要紧——少了它既是越权，也是内容注入路径
命令入口 /new / /resume 改进程级指针；/delete <别人的 id> 的参数不受归属保护；/session 列出全进程会话 命令闸门（名单可配：denied-commands / session-required-commands）

这 7 条在 starter 里都有对应实现（会话归属、并发配额、会话数上限、闲置回收、审批归属、提问归属、命令入口）： 七个 @Bean 集中在 JellyfishUserWiringConfiguration（会话归属存储、配额闸门、命令闸门、审批网关、提问网关、多用户门面、闲置回收器）， 其中「会话数上限」的检查落在建会话的同锁临界区里（JellyfishUserFacade.createSession）。 （README 正文早期版本写「下面六件事」，与同节表格的 7 行对不上，现已改为「七件事」。）

完整示例：替换 SessionOwnerStore（唯一的可替换点）

SessionOwnerStore 是一条SPI，不是内核组件的视图：归属存在内存还是关系库， 只有接入方知道，因此实现它并注册成 Bean，默认实现会自动让位（它是唯一的 @ConditionalOnMissingBean 例外之一）。实现要求： 线程安全（回合在 react 线程上跑、HTTP 请求在容器线程上跑，两边都会读它）、 bind / unbind 幂等、只回答归属而不做别的权限判定。 

package com.example.app;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import zcd.jellyfish.spring.boot.user.SessionOwnerStore;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;

/**
 * 把会话归属换成自己的存储（这里用一张并发表示意，真实场景换成你的库表访问）。
 *
 * @author you
 */
@Configuration
public class OwnerStoreConfig {

    /**
     * 注册自定义归属存储：默认的 InMemorySessionOwnerStore 会自动让位。
     *
     * @return 归属存储
     */
    @Bean
    public SessionOwnerStore sessionOwnerStore() {
        return new MySessionOwnerStore();
    }

    /** 一个线程安全的示例实现。 */
    static final class MySessionOwnerStore implements SessionOwnerStore {

        /** userId 到 sessionId 集合的索引。 */
        private final ConcurrentMap<String, List<String>> byUser =
                new ConcurrentHashMap<String, List<String>>();

        /** sessionId 到 userId 的反向索引。 */
        private final ConcurrentMap<String, String> bySession =
                new ConcurrentHashMap<String, String>();

        @Override
        public synchronized void bind(String userId, String sessionId) {
            // 幂等：重复绑定同一对 (userId, sessionId) 不报错
            bySession.put(sessionId, userId);
            List<String> owned = byUser.get(userId);
            if (owned == null) {
                owned = new ArrayList<String>();
                byUser.put(userId, owned);
            }
            if (!owned.contains(sessionId)) {
                owned.add(sessionId);
            }
        }

        @Override
        public synchronized void unbind(String sessionId) {
            // 幂等：解绑一个不存在的会话也不报错
            String userId = bySession.remove(sessionId);
            if (userId != null) {
                List<String> owned = byUser.get(userId);
                if (owned != null) {
                    owned.remove(sessionId);
                }
            }
        }

        @Override
        public boolean owns(String userId, String sessionId) {
            return userId != null && userId.equals(bySession.get(sessionId));
        }

        @Override
        public synchronized List<String> sessionsOf(String userId) {
            List<String> owned = byUser.get(userId);
            return owned == null ? new ArrayList<String>() : new ArrayList<String>(owned);
        }

        @Override
        public int countOf(String userId) {
            // 存储支持更快的计数时应当覆盖它（默认实现按 sessionsOf 的长度算）
            return sessionsOf(userId).size();
        }

        @Override
        public String ownerOf(String sessionId) {
            // 没有记录时返回空串
            String userId = bySession.get(sessionId);
            return userId == null ? "" : userId;
        }
    }
}
会话持久化与归属必须一起持久化

默认的 InMemorySessionOwnerStore 与会话同生命周期（内核的会话默认也在内存里）。 一旦你给会话加了持久化（自己写插件或换存储），归属也必须一起持久化—— 否则重启后会话还在、归属没了，那些会话就变成谁也访问不到的孤儿。

常见问题

  • 为什么「不存在」与「不属于你」回同一个异常？告诉请求者「这个 id 存在但不是你的」 等于给了他一个枚举会话 id 的工具。
  • 配额超了会排队吗？不会，立刻拒绝。排队会把容器线程也堵住—— 那比让一个请求快速失败要糟得多。
  • 闲置回收会关掉正在跑的会话吗？不会。shouldReap 必须同时满足 「有归属者」与「没有在途回合」：一次长 LLM 调用在第一条新消息落库前不刷新时间戳， 只看时间会把它关掉。
  • 命令闸门拦的是命令名还是整行？拦命令名（denied-commands 里写的是不带前缀的名字， 别名各写一条）。之所以必须有这道闸门：命令的参数部分不受归属校验保护 （/delete <别人的会话 id> 里的 id 从不经过本层检查）。

11. 门面 Bean：只暴露「观测面」

哪七个进容器，哪些故意不进

是什么
starter 只把内核里「不按会话操作、也读不到别人数据」的那几个门面注册成 Bean，按类型即可注入。 其余一律不进容器——这是一道编译期边界，不是约定。
怎么用
需要读模型 / agent 清单、读配置、看健康状态时，直接按类型注入下面那七个。 要操作会话，走门面；要扩内核，写插件。

配置：进容器的七个门面 Bean（判据是「拿到它做不了跨用户的事」）

故意不进容器的（全部）：内核门面 JellyfishRuntime 不进，因此下面这些也都不在容器里：

SessionManager、ConversationService、ShellStreams、 TurnRegistry、CommandManager、ApprovalChannel、 AskChannel、PermissionManager、AgentHarness、 EventChannel、RunEventBus、ExtensionRegistry、 InputDirectives、ConversationCompactor。

为什么不给：这些能力都是「按 id 操作某个会话」，而它们都不校验调用方是谁。 做成 Bean 之后，容器里任何一个 Bean（你写的、或某个第三方库的自动配置）注入进来就能 读别人的对话正文、批准别人的工具调用、改掉进程级的「当前会话」指针——本 starter 那整套归属校验就只剩一句约定。 这道边界是编译期的：内核门面由 JellyfishKernel 持有， 它的访问器是包私有的，别的包里的 Bean 即使注入了那个 Bean 也调不到。

为什么不做 @ConditionalOnMissingBean： 登记进来的这几个不是可以随你替换的组件，而是同一张对象图上的视图： 让接入方「再注册一个 ModelManager」等于在同一个 JVM 里造出第二套内核状态， 而坏掉的方式是静默的（配置刷了一份、另一份永远是空的）。 需要不同行为时应当用内核的扩展点（插件），不是在 Spring 容器里替换内核组件。

加新的 @ConditionalOnMissingBean 之前先问一句

「这是内核组件的第二个视图，还是一条 SPI？」 SessionOwnerStore 是 SPI（归属存哪只有接入方知道），所以可以被替换； 门面 Bean 是视图，所以不能。

本 starter 源码里没有 CurrentUser 这个类：…/spring/boot/user/ 下 15 个文件里没有它， 全仓库检索只命中 README 的那一行——那是上游 README 的串味（把示例仓库的东西写进来了）。 真正的可替换点只有一个：SPI SessionOwnerStore，它是 JellyfishUserWiringConfiguration 里 唯一带 @ConditionalOnMissingBean 的 Bean，本仓库 AGENTS.md 的措辞也据此写成 「SessionOwnerStore 是仅有的例外之一」。CurrentUser 确实存在，但在示例仓库 Jellyfish-Spring-Template（template/CurrentUser.java:16 的接口 + template/CurrentUserConfiguration.java:26 的 @Bean）， 与本 starter 无关。

12. 生命周期：JellyfishLifecycle

SmartLifecycle，phase 取 Integer.MIN_VALUE

是什么
内核的起停挂在 Spring 的生命周期上：JellyfishLifecycle 实现 SmartLifecycle， phase 取最小值，也就是「启动最先、停止最后」。
怎么用
缺省什么都不用做（bootstrap-on-start=true）。要自己挑启动时机时， 置 false 并注入 JellyfishLifecycle 调 bootstrap()。

配置

字段类型必填默认值含义示例
jellyfish.lifecycle.bootstrap-on-start boolean 选填 true 上下文启动时是否自动拉起内核。false = 只装配不启动； 两条路径的关闭动作完全相同（stop() 认的是「内核起没起」，不是「谁起的」） false
JellyfishLifecycle.PHASE int（常量） 必填（常量，不可配） Integer.MIN_VALUE 生命周期阶段。公开常量，本 starter 里别的生命周期组件靠它推导 （例如闲置会话回收用 PHASE + 1） Integer.MIN_VALUE

bootstrap-on-start 影响的是启动行为，改了必须重启 需重启。

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/**
 * 等某个外部依赖就绪之后再起内核：把 jellyfish.lifecycle.bootstrap-on-start 置 false，
 * 然后在你的时机调 bootstrap()。这是「自己挑时机」的唯一入口。
 *
 * @author you
 */
@Configuration
public class DelayedBootstrapConfig {

    /**
     * 等到外部依赖 ok 之后再拉起内核。
     *
     * @param lifecycle starter 的生命周期宿主
     * @return 一个在上下文启动后执行的任务
     */
    @Bean
    public ApplicationRunner warmUpJellyfish(JellyfishLifecycle lifecycle) {
        return args -> {
            waitForMyDependency();
            // 幂等，且与 stop() 互斥：重复调用不会拉起第二遍
            lifecycle.bootstrap();
        };
    }

    /** 你自己的等待逻辑。 */
    private static void waitForMyDependency() {
        // 例如探测配置中心 / 数据库 / 网关
    }

常见问题

  • 为什么 phase 不取「比 Web 容器小一点」？需要保证的只有一条——内核早于 Web 容器就绪、 晚于它停止（否则请求会打进一个已经关掉的线程池）。但 Web 容器的 phase 是 Boot 的内部实现 （2.x 是 Integer.MAX_VALUE - 1，较新版本已改成 Integer.MAX_VALUE - 1024）， 跟着它减一个魔数会在某次升级 Boot 时静默失效——而失效的表现是「偶发地打不通」，排查成本极高。 取最小值就与那个数字无关。副作用是内核会在其它 SmartLifecycle 之前启动，这是可接受的： start() 发生在所有单例都已实例化之后。
  • 为什么不注册 JVM shutdown hook？Spring 关上下文时就会走 SmartLifecycle.stop()； 再叠一个 hook 只会让「谁先关」取决于 JVM 并不保证的 hook 执行顺序。
  • 启动失败会怎样？bootstrap() 会先收敛再抛： 尽力关掉已经起来的资源（事件通道、指标订阅、插件运行时），再原样抛出，并让本次启动不算数 （isRunning() 仍为 false）。一个「内核半死、接口照常对外服务」的进程， 表现是每个请求都失败，而根因早埋在启动日志里。
  • 关停时审批 / 提问会怎样？stop() 先摘审批与提问、再关内核： 让卡在等待上的回合以「通道已关闭」收敛，而不是被 shutdown 打断。

13. 与原生 -server 模式的差异与选择建议

内核自己也有一个 HTTP 外壳（-server）。它和本 starter 解决的不是同一个问题： -server 是「给别人用的一个服务」，starter 是「给你自己的应用加一个能力」。

维度原生 -server 模式本 starter
接口由谁定义 内核外壳已经定义好（会话、命令、事件流等一批端点） 你自己定义，starter 只给编程式 API（门面）
部署形态 一个独立的 JVM 进程，你启动它 装进你已有的 Spring Boot 进程，与你的业务代码同一个 JVM
鉴权 缺省只绑 127.0.0.1 时等于「本机可用」：没配密钥就不鉴权； 但绑非回环却未配密钥会拒绝启动（退 3）。配了密钥后，除 GET /health 外 所有接口都要 Authorization: Bearer <密钥>（否则 401）；写请求 （POST/PUT/PATCH/DELETE）还要 Origin （缺席时退到 Referer）与本服务同源，否则 403。密钥来自 --api-key 或 环境变量 JELLYFISH_SERVER_API_KEY，不接受 query 传参 鉴权完全由你自己实现：starter 不依赖 spring-boot-starter-web、 不提供任何接口，因此它不管认证；它补的是归属校验（护栏）

热更新 可敲 /reload（三份内容类配置生效，jar 增删仍需重启） 没有暴露 /reload 入口，配置改动建议直接重启
选型建议 你要的是一个「独立的 agent 服务」、或者本地 / 内网自己用：直接用 -server（或 -cli / -tui）， 少一层自研接口 你的业务已经在 Spring Boot 里、agent 只是其中一个功能（比如工单系统里加一个「让模型读日志」的能力）： 用 starter，省掉一个进程与一套 IPC

使用限制（六条，如实抄出）

是什么
这些是设计边界，不是待修的 bug。知道它们能避免「为什么做不到」的反复试错。
怎么用

17. 常见问题

我把内核门面注入到自己写的 Bean 里，为什么编译不过？

因为 JellyfishKernel 的访问器是包私有的，而它对外有意不提供任何公开方法。 这不是疏漏——包可见性就是这道边界本身。你要内核能力有三条正路： 用 JellyfishUserFacade（带归属校验）、写插件（内核的扩展点）、 或者自己 JellyfishAssembler.create(...) 造一套自己的（那时你同时接管了它的生命周期）。

为什么拿不到 SessionManager / CommandManager？

因为它们都是「按 id 操作某个会话」且不校验调用方是谁。做成 Bean 之后， 容器里任何一个 Bean 注入进来就能读别人的对话正文、批准别人的工具调用。 完整清单见第 11 节（故意不进容器的 14 个）。

怎么让内核晚一点启动？

置 jellyfish.lifecycle.bootstrap-on-start=false，注入 JellyfishLifecycle， 在你的时机调 bootstrap()。这是唯一入口——内核门面不在容器里，你拿不到 AgentHarness。 两条路径（自动 / 手动）的关闭动作相同。

为什么 chat 的 listener 里不能写阻塞 IO？

它在 react / llm-stream / 工具输出泵线程上被调用，后两者会并发； listener 抛出的异常会被门面记一条日志后吞掉，所以你也不会收到失败通知。 正确做法是 listener 只做「转投」（放进队列或线程池），真正的 I/O 在别的线程上做。

可以在同一个应用里跑两套内核吗？

不行。内核是进程级单例语义：「当前会话」是一个进程级指针、模型索引进程级一份，两套内核在一个 JVM 里会互相污染。

投入生产前最该先确认哪几件事？

  1. jellyfish.plugins.roots 指向的目录里装了哪些插件——涉密插件一律不装进多租户进程；
  2. 审批与提问通道到底开不开：要开就先把接口接好， approval.enabled / ask.enabled 与两个超时值一起定；
  3. 每用户配额（max-inflight-turns-per-user / max-sessions-per-user）与 react 池的 8 条线程对得上；
  4. 闲置回收的 idle-timeout / sweep-interval 与「客户端手里的 sessionId 会不会变 404」一起考虑；
  5. 会话要不要持久化——要的话，归属也必须一起持久化；
  6. 密钥走环境变量插值（${OPENAI_API_KEY}），不要写进配置文件。

关键结论

  1. starter 只做两件事：把内核装进你的容器（用 JellyfishAssembler.create(...)，走 jellyfish-di）， 以及补上一层带归属校验的多用户门面。它不提供任何 HTTP 接口、不依赖 spring-boot-starter-web、 不改内核、不支持同进程多套内核。
  2. 配置只有路径与开关：application.yml 回答「那些文件在哪」， 模型 / agent / 插件的内容仍是内核格式的 JSON；classpath: 前缀让配置成为构件的一部分 （因此不受 trust-project-config 约束）。
  3. 自动装配是一条三步链：造对象图 → 暴露只读门面 → 注册 JellyfishLifecycle； jellyfish.enabled=false 是类级别条件，因此关掉时连对象图都不构造（零成本）。
  4. 业务侧只注入 JellyfishUserFacade，它的 16 个方法都以 userId 开头； 四条纪律里最容易违反的是「chat 的 listener 在内核线程上、必须快且线程安全」。
  5. 接口由你自己写：SseEmitter 用 0L 不超时，SSE 帧自己转， 待审批 / 待答都有「只有头槽位能被处理」的语义（对排队中的那一条调用返回 false）。
  6. 审批缺省关闭是fail-closed（立即拒绝）；提问缺省关闭是立即返回成功结果（不阻塞）—— 两者口径不同。打开后各自最多阻塞 react 线程 120 秒，而那个池只有 8 条线程。
  7. 护栏补的缺口都在 user/ 包：会话归属、每用户并发配额、会话数上限、闲置回收、审批归属、提问归属、命令入口； SessionOwnerStore 是唯一的可替换点，而会话持久化与归属必须一起持久化。
  8. 内核门面（含 SessionManager / ApprovalChannel / AskChannel 等 14 个） 故意不进容器，靠 JellyfishKernel 的包私有访问器守住——这是编译期的边界，不是约定。
  9. JellyfishLifecycle.PHASE = Integer.MIN_VALUE（启动最先、停止最后）， 不要改成「比 Web 容器小一点」；也不注册 JVM shutdown hook。自己挑时机只有 bootstrap() 一条入口。
  10. 与原生 -server 的分工：-server 是「给别人用的服务」，starter 是「给自己应用加的能力」； 多用户护栏只存在于 starter 这一侧。
