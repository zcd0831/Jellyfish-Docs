09 会话与上下文

会话是「这一串对话」的身份证，上下文是「这一轮真正发给模型的那段历史」。两者不是一回事—— 这一页把命令、落盘位置、压缩与老化机制、@ 引用、用量记账一次讲清。读完之后， 你应该能回答「我的会话去哪了」「为什么模型好像忘了前面说过的话」「那条几十轮前的输出路径为什么打不开」。

学习目标

  • 列出会话相关命令，说出每个命令的别名与一句作用；
  • 说清会话文件存在哪、里面有什么、是怎么被 git 管起来的，以及没有 session-file 插件时会发生什么；
  • 会用 --session 恢复一次会话，并知道 --agent / --model 只归 -cli；
  • 会用 /compact 与 /compact preview，并一眼分辨「不可用 / 未压缩 / 已压缩 N 条」三种状态；
  • 能解释「历史一条不删」为什么成立，以及压缩后模型看不到的是哪一段；
  • 会配 react.toolOutput 的五个字段，能读懂回灌信封 _truncated / _path / _partial 的含义；
  • 会用 @ 引用文件，并说明它为什么不把文件内容内联进消息。

会话是什么

一个会话（session）就是一段对话的容器：它持有 agentId、模型、消息列表、累计 token 用量、压缩摘要、 扩展条目。会话状态一律归会话对象自己——进程里不另存一份全局副本，内核也没有 session 配置段。唯一的进程级「会话状态」是新建会话用的待生效默认值 （SessionDefaults），它只在创建那一刻被消费。

会话种类（SessionKind）是什么进 /session 列表吗落盘吗能 /resume 吗
NORMAL 你自己建的普通会话 是 是 是
EPHEMERAL 子代理的临时会话 否 否 否
FORKED 从某个会话切出来的分支会话 是 是 是
  • 判定「是不是子代理会话」只能看 kind，parentSessionId 只是追溯信息。
  • 「这份数据归哪个会话」由内核统一回答（ownerSessionId）：沿父链只穿 EPHEMERAL， 遇到用户会话就停。因此嵌套委派时孙代理的活算在你所在的会话上，而分支会话归它自己。

命令的两条行为口径

  • 命令可以不把话说完（命令「接力」）：有一类命令想做的事是「让模型接着干」， 它返回 CommandResult.handoff(text)，内核不呈现命令输出，而是把 text 当成你这一次敲下的输入接着走——那句文本会成为会话里的一条用户消息（因此也会落盘、也会被压缩）， 模型据此发起的读写工具调用照旧过权限与审批，命令没有借此取得任何新权限。 /init 就是这么实现的。Server 只走半程：POST /sessions/{id}/commands 是纯 JSON， 客户端需要拿 handoff 文本再 POST /chat 一次。
  • -tui 另有五个由外壳处理的命令，不在 /help 列表里： /exit、/ui、/thinking、/toolargs、/mouse。
/status 逐行输出：一行会话标识 + 六个字段

README 只写它是「显示当前会话概要」。内核命令实现里实际逐行输出的是下面这些 （字段名与顺序都写死，六个字段各自缩进两格）：

  • 会话：<sessionId>
  • model：<provider>/<model>——会话没绑模型（provider 或 model 为空）时显示 默认
  • agent：<agentId>——没绑 agent 时显示 -
  • 消息数：<当前消息条数>
  • 压缩：四态之一——不可用（没有插件提供压缩策略）、未压缩、 压缩记录已失效（边界消息不在会话里，本次按未压缩发送）、 已压缩 N 条更早消息（摘要 X 字，其中 M 条未收录）
  • token：<累计总量>（输入 <prompt token 数> / 输出 <completion token 数>）
  • 缓存：命中 <命中数> / 输入 <输入数>（<百分比，保留一位小数>%）

TUI 的状态栏另有一份口径：agent · provider/模型 · token 用量， 会话被压缩过时追加 已压缩 N 条（丢弃 M 条）。 当前没有会话时 /status 只回一行 当前没有会话，可用 /new 新建。

会话存在哪：session-file 插件

会话持久化（jellyfish-plugin-session-file）

是什么
把会话落到本地磁盘：一个会话一个 JSON 文件，并用 git 管理历史。 装了它，--session / /resume / /session 才有内容可恢复——启动时内核向所有注册了恢复处理器的插件要回会话， 因此上次退出前的会话在下次启动时立即可见。
怎么用
装 jar 到扫描目录（缺省 ~/.jellyfish/plugins/）后重启进程， 然后什么都不用做：首轮对话结束就会落盘。 
mkdir -p ~/.jellyfish/plugins
# 把 jellyfish-plugin-session-file-0.1.1.jar 放进去，然后重新启动 jellyfish

配置

字段类型必填默认值含义示例
sessionDir 路径字符串 选填 ~/.jellyfish/sessions 会话文件目录。会话是跨项目的运行态数据，因此默认放全局级目录 "~/my-jellyfish/sessions"
gitEnabled boolean 选填 true 首次落盘时在 sessionDir 里 git init，此后每次内容变化的落盘留一次提交（内容没变则不写文件、也不提交）。机器上没有 git 时只告警，文件照常落盘 false

完整示例

{
  "plugins": {
    "enabled": ["jellyfish-plugin-tools", "jellyfish-plugin-shell", "jellyfish-plugin-session-file"],
    "configurations": {
      "jellyfish-plugin-session-file": {
        "sessionDir": "~/.jellyfish/sessions",
        "gitEnabled": true
      }
    }
  }
}

插件配置段写在 jellyfish.json，改完敲 /reload 即可生效 （新增 / 删除插件 jar 才需要重启）。

常见问题

  • 会话文件里是什么？一份会话快照 SessionSnapshot，字段见下一节。
  • git 提交会拖慢对话吗？不会。提交在专属线程上做、按文件合并待提交记录；插件停止时会把在途的那一次做完或强杀（强杀可能留下 .git/index.lock，那时提交告警并跳过，会话文件本身不受影响）。

会话文件的结构

文件名是 <sessionId>.json，写在 sessionDir 下；写入走 临时文件 <id>.json.tmp + 原子改名，因此读路径永远不会读到半份文件。 新建的会话文件权限是 600、新建的目录层级是 700（已存在的层级不动——那是用户的盘）。 文件里装的是一份 API 侧契约类型 SessionSnapshot——它是会话的投影而不是第二份真相： 内核在变更会话时生成快照交给插件，插件原样存下；恢复时内核把快照还原成会话。

快照字段含义
sessionId会话标识，不可为空白
createdAt / updatedAt创建时间戳与最后一次变更时间戳（epoch millis）
title会话标题，可为 null
agentId会话绑定的 agentId，可为 null（未绑定）
provider / model会话当前的 provider 名与模型名，null 表示跟随默认
messages消息列表（每条是 SessionMessageSnapshot），可为 null（等价空列表）
usage累计 token 用量（SessionUsageSnapshot），可为 null（按零用量处理）
compaction压缩摘要（SessionCompactionSnapshot），从未压缩过时为 null
kind会话种类 SessionKind——它就是「是不是子代理会话」的判定来源
parentSessionId派生该会话的父会话标识，根会话为 null（只是追溯信息）
forkPointMessageId分支点消息标识（含），非分支会话为 null
extensionEntries插件挂在会话上的扩展条目，无条目时为空列表
为什么快照类型只有一个构造器

快照靠 Jackson 的「隐式属性构造器」反序列化，而 Jackson 只在恰好一个可见构造器时才认它。 多出一个重载会让整个快照类型直接反序列化失败——代价是整段会话读不回来。 因此新增字段走静态工厂，不加兼容构造器。这也解释了「往返测试」（capture → restore → capture 必须相等） 为什么是这套机制唯一的护栏。

什么时候落盘

场景语义
创建会话不落盘（空会话无文件、无提交）；失败从「创建时暴露」变为「第一次变更时暴露」
回合内消息追加只标脏，由回合的 finally 统一 flush 落一次——回合收敛 = 已落盘
命令 / recordUsage / applyCompaction / 关闭会话仍即时落盘（挂起的只有消息追加）
延迟落盘 flush 失败只记 WARN 并保留脏标记等下次重试，不得升级为回合失败
变更时的落盘失败异常原样上抛：那一刻起「状态已变」与「状态已落盘」必须同生共死
恢复单个插件读不出只告警跳过；恢复必须排在插件启动（bootstrap）之后
关闭前钩子调用点在最后一次落盘之前；USER_REQUEST 的否决被采纳（fail-loud），SHUTDOWN / RELOAD / INTERNAL 的否决被忽略

没有装持久化插件时会怎样

会话只活在内存里，退出即丢
  • 会话不会落盘，进程退出后没有任何文件留下，下次启动也没有会话可恢复。
  • /session 列表里只有当前进程里活着的会话（EPHEMERAL 子代理会话连列表都不进）。
  • --session <会话> 要「切换到已有会话」，而没有持久化插件时没有可恢复的会话， 因此会按用法错误退出 2（--session 指向不存在的东西就是 2）。
  • /resume <sessionId> 切不到上次的会话，当场回一行错误 会话不存在：<sessionId>（不带参数时弹会话选择页；参数多于一个时回报 用法：/resume <sessionId>）。

「没有持久化插件就一定退 2」在源码里能逐字对上：启动期由 SessionBootstrap 把「切不到」抛成异常，消息形如 会话不存在：<sessionId>（本次进程里没有这个会话；历史会话由会话持久化插件在启动时恢复，未装它则每次进程都是全新的）； Launcher 把这一步的失败归为「参数不可满足」，stderr 打印 错误：…， 并返回 ExitCodes.USAGE_ERROR（2）。

上下文与压缩（本页重点）

为什么需要压缩

长会话的每一轮都要把整段历史重新发给模型，token 花得越来越多，最后撞上上下文窗口。 压缩的思路是：多花一次调用把更早的对话压成一份摘要，之后每次请求只带 摘要 + 最近若干条原文。

flowchart LR A["会话里的完整历史
（一条不删）"] --> B["老化：保留窗口之外的工具结果
换成带路径的 stub"] B --> C["压缩边界：边界之前换成摘要"] C --> D["最近 N 条原文
（compactKeepRecentMessages）"] D --> E["这一轮真正发给模型的链路"]

图 9-1　「历史」与「发给模型的链路」不是一回事：老化与压缩都只改后者

压缩后的请求链路

压缩是非破坏式、滚动摘要：消息一条不删，只记下 Session.compaction = {boundaryMessageId, summary, droppedMessageCount}， 失败无副作用。每次只压「上次边界之后、再留 keepRecent 条」的那一段， 并把上一份摘要一起喂回模型，边界只向后移。

  • 摘要是一条每次现算的出站合成消息，不落盘：排在压缩边界之后、被保留历史之前；角色用 user。
  • 边界必须落在工具调用组的边界上：起点若落在 tool 消息上，就向前退到组开头 ——所以 keepRecent 是「至少保留最近多少条」。
  • 单次压缩、装不下就丢最旧：待压范围超预算时从最旧侧丢弃，被丢弃条数如实上报并落盘；至少进摘要 1 条。
  • 摘要调用复用当前上下文（cache-safe fork）：发出去的是「父请求的真前缀 + 一条追加指令」——切的是父请求自己的字节、工具原样带上、用 tool_choice: none 关掉工具调用。
「历史一条不删」——这句话要用在正确的地方

屏幕上的会话、恢复出来的会话、落盘的文件，都还是完整历史。变的只是「发给模型的那条链路从哪里开始」。 因此：

  • 压缩之后你往回翻，早先的消息一条都没少；/session、会话 JSON 文件也是完整的。
  • 但模型看不到被压掉的那一段原文——它只拿到摘要。所以「压完之后模型好像忘了细节」不是 bug。
  • 更严重的一种情况是被丢弃：单次压缩装不下时，最旧的那段既不在摘要里、也不会再发给模型， 完成结果会写明条数（写在命令输出面板里，同时状态栏的 已压缩 N 条（丢弃 M 条） 一直带着它）。

/compact 与 /compact preview

`/compact` 会话压缩

是什么
把更早的对话压成一份摘要，之后每次请求只带摘要 + 最近若干条原文，从而把 token 花销压下来。
怎么用
/compact                 按默认档位压一次（保留条数取 react.compactKeepRecentMessages，缺省 20）
/compact preview         只回报「将压缩 X 条、保留 Y 条、丢弃 Z 条、摘要输入约 T token」，不发起压缩
/compact 只起头不等结果：它跑在自持的 compact 线程池上， 外壳每帧轮询状态；完成 / 失败的结果显示在底部的命令输出面板里（不进消息区）， 形如 压缩完成：已压缩 3 条更早的消息；而「已压缩 N 条（丢弃 M 条）」这个持续有效的事实 由状态栏那行标记一直带着。 不做用户可见档位——「没什么可压」时报 ERROR，而 preview 在同一种情况下返回正常 且连模型都不解析。

看什么

  • 可压条数不足时不要浪费钱：先用 /compact preview 看「将压缩 X 条、保留 Y 条、丢弃 Z 条、摘要输入约 T token」， 再决定压不压。

常见问题

  • 压完之后能再压吗？能，可以反复压：每次只压上次边界之后新增的那段，边界只向后移。
  • 压缩会变慢对话吗？自动压缩跑在当前那一轮模型调用的旁边，不拖慢对话，结果在下一轮生效。

压缩需要插件：不装就没有

压缩是插件能力，内核只提供机制

内核手里只有机制——读消息、选范围、发模型调用、校验摘要、推进边界、记用量、落盘； 「这次该压成什么样」由插件回答：一份摘要指令（插件 jar 里的 summary-prompt.md） + 两个可选数量参数。没有插件提供摘要指令，就没有可以发给模型的摘要请求。

  • 自动压缩不生效（上下文满了只会走机械裁剪，历史在请求里变少）；
  • /compact 与 /compact preview 直接回答「压缩不可用：没有插件提供压缩策略」；
  • /status 的压缩一行显示「不可用（没有插件提供压缩策略）」。

不回退内置是刻意的：可用性只查注册表（isAvailable()）。

状态屏幕上长什么样说明
不可用 「压缩不可用：没有插件提供压缩策略」/ /status 显示「不可用」 没装 jellyfish-plugin-compact（或同类插件）
未压缩 状态栏与 /status 都不显示压缩标记 插件可用，但这个会话还没压过（compaction 为 null）
已压缩 N 条 已压缩 N 条；有丢弃时追加 （丢弃 M 条） 条数按压缩边界在消息列表里的位置现算，不另存一份可能撒谎的数字；边界失效时按「未压缩」显示

插件 jar 在 ~/.jellyfish/plugins/ 里、但没列进 jellyfish.json 的 plugins.enabled 时，算没装。启动日志里会有一条：

是什么

怎么用

配置

字段类型必填默认值含义示例

工具输出落盘（react.toolOutput）

工具结果太长时自动落盘，回灌一份「信封」

是什么
一个工具输出过长时，完整内容写到磁盘，回灌给模型的是一份结构化报文 ——里面写明「被截断了、原来多大、完整内容在哪、怎么回查」，正文只留头尾预览。 这样既不让一条日志把上下文撑爆，也不让模型拿到半截 JSON 或半截文本。
怎么用
无需操作：超限自动发生。短输出不产生任何文件。你要做的是按需调这几个字段， 并在模型要回查时用 read_file / grep_files 打开信封里的路径。

配置

字段类型必填默认值含义示例
react.toolOutput.dir 路径字符串 选填 ~/.jellyfish/tool-outputs 完整内容的落盘根目录（运行产物写在这里而不是项目目录） /path/to/tool-outputs
react.toolOutput.keepFiles int 选填 200 每个会话在该目录下的文件数上限，超了从最旧开始删（写 0 关闭清理） 500
react.toolOutput.maxBytes long（字节） 选填 52428800（50 MiB） 每个会话在该目录下的字节数上限，超了从最旧开始删（写 0 关闭清理） 104857600
react.toolOutput.keepRecentMessages int 选填 20 组装请求时最近多少条消息里的工具结果保留完整内容（写 0 同时关掉裁剪与老化） 40
react.toolOutput.spillMaxBytes long（字节） 选填 33554432（32 MiB） 单个工具结果的落盘上限，运行期钳制为不超过 maxBytes；触及上限时后续内容不再保存、信封会带 _partial 说明它不完整 16777216

/reload 生效 react 段属于「项目级写了这一段才覆盖，没写就整段回退全局级」的那类配置，改完敲 /reload 即可。

完整示例

{
  "react": {
    "maxToolOutputChars": 20000,
    "toolOutput": {
      "dir": "~/.jellyfish/tool-outputs",
      "keepFiles": 200,
      "maxBytes": 52428800,
      "keepRecentMessages": 20,
      "spillMaxBytes": 33554432
    }
  }
}

  • 落盘失败会怎样？不是回合失败：只记 WARN，信封里 _path 为 null 并说明内容不可恢复。

回灌信封长什么样

信封是唯一格式，字段名由 ToolOutputEnvelope 一处定义，渲染与解析共用—— 禁止两处各写一遍键名。

字段类型含义
_truncatedboolean恒为 true，用于识别「这是一份截断信封」
_toolstring工具名
_total_charsint原始输出的字符数
_total_linesint原始输出的行数；结构化结果记为 0
_pathstring \| null完整内容的落盘路径；落盘失败时为 null。主目录内的路径记成 ~ 形式
_hintstring给模型的恢复指引（正常 / 不完整 / 落盘失败三种措辞）
_partialboolean落盘内容是否不完整：只在「捕获期溢出且触及落盘上限」时为 true——此时路径下只有前一段内容
preview字符串 \| 子树预览：纯文本结果是字符串节点，结构化结果是结构截断后的子树（这样「信封就是一段合法 JSON」对两类输出都成立）

一份纯文本结果的信封（示意，值为示例）

{
  "_truncated": true,
  "_tool": "shell",
  "_total_chars": 128430,
  "_total_lines": 2410,
  "_path": "~/.jellyfish/tool-outputs/a1b2c3d4/call_1-shell-1837465123456789.txt",
  "_hint": "本轮只保留预览（开头与结尾）。完整内容已落盘：~/.jellyfish/tool-outputs/a1b2c3d4/call_1-shell-1837465123456789.txt；用 read_file（支持 offset/limit）或 grep_files 回查。",
  "_partial": false,
  "preview": "…（开头约 30%）…\n…（中略，详见落盘文件）…\n…（结尾约 70%，结论通常在这里）…"
}
  • 预览是头 30% + 尾 70%（比例与省略标记都是常量、不开放配置）——因为结论往往在末尾。
  • 绝不按字符切：字符串按行截断，Map / List 先序列化再按 JSON 子树截断，不对可能是 JSON 的输出做 substring。
  • 回灌给模型、写入会话、通知外壳用的是同一份文本，只有一个硬截断点。
  • 主目录内的落盘路径记成 ~ 形式（不把真实用户名与主目录结构带进上下文，因为它会随会话落盘、被导出、发给上游模型）；文件工具认 ~，所以信封里那条路径可以直接交给 read_file / grep_files / list_dir。

「几十轮之前的路径会失效」

清理会从最旧开始删，_path 只在保留窗口内有效

落盘目录有清理上限（缺省每会话 200 个文件 / 50 MiB），从最旧开始删。 因此_path 只在保留窗口内有效——这是「不做引用计数式保留」的直接代价，是刻意接受的。 另外还有两种更难发现的失效：

  • 被后来者覆盖：文件名里带一段唯一片段（调用 id + 工具名 + 纳秒时间戳）， 因为调用 id 由外部给、清洗又会把不同的 id 折叠成同一个名字，所以是「同一次调用独占一个路径」； 旧文件被覆盖时，先那条信封里的 _path 还在、内容却已经不是它的。
  • 内容不完整：_partial: true 时路径只有前一段内容，超出部分未捕获、不可恢复。

应对：要长期留用的内容请在它还在时另存一份；需要更长保留窗口就把 keepFiles / maxBytes 调大；要立即可查就用信封里的路径交给 read_file / grep_files。

工具结果老化（react.cache.agingPercent）

把窗口之外的旧工具结果换成 stub

是什么
组装请求时，把「保留窗口之外」的旧工具结果信封换成短短一行 stub（带路径与预览首行）， 只改本次请求，会话一条不动。它直接决定提示词缓存的命中率——厂商的缓存是前缀匹配， 改掉历史上的一个字节，后面整段就从约 0.1× 的命中价变回 1× 全价。
怎么用
无需操作。要调节就改下面这一个字段；要彻底关掉老化就把 react.toolOutput.keepRecentMessages 写 0。

配置

字段类型必填默认值含义示例
react.cache.agingPercent int 选填 70 0 = 按「距尾部多少条消息」老化，边界每轮重算（复原升级前行为的逃生门）；> 0 = 只在上下文用量达到该百分比时老化，且一个压缩周期内只推进一次 0

/reload 生效

完整示例

{
  "react": {
    "autoCompactPercent": 80,
    "toolOutput": { "keepRecentMessages": 20 },
    "cache": { "agingPercent": 70 }
  }
}

为什么默认是 70，与压缩什么关系

  • 缺省落在 70 是因为它必须略低于 autoCompactPercent（80），相差约 10 个点、低了才会真正泄压——高于它就变成压缩先发生、老化永远轮不到。
  • 改了 autoCompactPercent 就应一并重看这一项。
  • 水位口径必须把边界冻住（一个压缩周期内只推进一次）：否则每轮追加 2～3 条消息就让边界前移，移过「最近、最贵、刚被缓存」的那一段。
  • 老化排在机械裁剪之前；stub 必须保留预览首行（工具把退出码 / 终止原因 / cwd 放在正文首行），首行长度上限 400 字符，结构化预览不取首行。

常见问题

  • 想彻底关掉老化？把 react.toolOutput.keepRecentMessages 写 0（0 同时关掉裁剪与老化）。
  • 改了 agingPercent 但命中率没改善？先确认它不是被压缩抢先——两者相差只有约 10 个点。

@ 文件引用

输入框的 @ 路径引用

是什么
输入框里敲 @ 引用当前工作目录下的文件：弹补全面板（目录在前、可逐层往下钻）， 接受后路径写进输入框。它不是工具，也不会把文件内容贴进来。
怎么用
@src/main/java/App.java 帮我看看这个类的空指针风险
路径里的空白用 \ 转义：含空格的文件名会补全成 @my\ file.txt。 这层转义会随消息一起发给模型，所以如果你在自己的提示词里解释 @ 引用， 记得也写明「\ 是空格」。规则只有一处（InputReferenceEscapes）：插件插入时转义、 比较时还原、外壳切片段时认转义——判据是「前面紧邻的反斜杠个数为奇数」，因此 \\ 是 「一个反斜杠 + 一个真边界」。

配置

字段类型必填默认值含义示例
—（无配置项） — — — 语法由插件提供（jellyfish-plugin-tools），没有可调字段；没有装该插件时，@ 只是一段普通文本 —

关键口径

引用不内联文件内容
  • @ 不内联、不展开：引用只是把路径写进消息，真正的读取由模型调用 read_file 完成 ——因此大文件不会撑爆上下文，权限与 max_bytes 照旧生效。
  • 输入框的特殊语法归插件、不归外壳：外壳不维护「哪些标记需要哪个插件」的名单。
  • 插件只能声明映射，执行权始终在内核：插件拿不到权限管理器，任何在 handler 里直接执行命令的实现都是错的。
  • 补全查询与执行是两个请求类型：补全（InputReferenceRequest）是渲染线程上每帧可能问一次的纯只读路径，与提交时解析的指令（InputDirectiveRequest）分开。

常见问题

  • 敲 @ 没反应？先确认 jellyfish-plugin-tools 已启用——没有它，@ 就是一段普通文本。
  • 模型把 \ 也当成文件名的一部分？约定里已明说「\ 是空格」；自己写提示词时补上这句。

上下文投影上限：500 条消息

TUI 的消息区只投影最近 500 条消息，更早的以占位行显示： 

⎿ N 条更早的消息已折叠
这只是「屏幕上的投影」，不是会话被截断

500 是界面渲染的上限，与会话里真正保存了多少条消息、发给模型多少条历史无关： 会话照旧是完整历史（见上面的「历史一条不删」），发给模型的链路由压缩与老化决定。 这条限制写在 README 的 TUI「已知限制」里。

同一节里还有两条相关的界面限制：滚动到内容末尾时自动跟随，用户上翻后不再打扰（生成中状态栏显示 ↓ 正在生成…）；编辑器的「光标到行尾」不可用（End 归消息区）。

/usage 与 token 记账

`/usage`（别名 `/cost`）

是什么
显示当前会话的 token 用量与缓存命中率，用来回答「这段活花了多少钱、缓存有没有起作用」。
怎么用
/usage
/cost
TUI 的状态栏也常驻一行用量：agent · provider/模型 · token 用量（有缓存活动时追加命中率）。

记账口径

  • 缓存命中率 = 累计命中 / 累计输入（两个累计量相除），不是把每次调用的命中率取平均——后者会被分母很小的短调用带偏。
  • 调用次数只认 assistant 消息：用户输入与工具结果只累加 token，不算一次调用。
  • 子代理花掉的 token 计入父会话（/usage 看得到），但子代理的会话不留痕（不落盘、不进 /session 列表）。
  • 用量归集失败只记 WARN，不影响回合。

常见问题

  • 子代理花了多少看得见吗？看得见总量（计入父会话），但看不到「哪个子代理花了多少」这一层拆分——那需要看轨迹行里的 ⎿ task · 子代理 scout · 3 轮 · 123456 tok。
  • 命中率很低怎么办？先看是不是老化（agingPercent）或压缩太频繁；厂商缓存是前缀匹配，历史被改动的那一瞬命中率就会掉。

常见问题

退出再进来，会话没了？
先确认 jellyfish-plugin-session-file 已启用（plugins.enabled 里有没有它）， 并且插件 jar 是在启动前就放好的——新增 / 删除插件 jar 只在启动期确定，需要重启进程。 另外，子代理会话（EPHEMERAL）本来就不落盘，不参与恢复。
/compact 说「压缩不可用」？
没有插件提供压缩策略。装 jellyfish-plugin-compact（或同类插件）并确认它在 plugins.enabled 里；启动日志里出现 插件被禁用或版本不满足，未启动: pluginId=jellyfish-plugin-compact 就说明是「在目录里但没启用」。
/compact 报「没什么可压」？
这是 /compact 的正常报错（ERROR），说明可压范围不足（边界对齐后可能退到可压范围下界）。 先用 /compact preview 看会压几条、保留几条、丢弃几条——它在同一种情况下返回正常，并且连模型都不解析。
压完之后模型好像忘了更早的约定？
被压缩的那段原文不再发给模型（只给摘要）。若状态栏显示 已压缩 N 条（丢弃 M 条）， 被丢弃的 M 条既不在摘要里、也不会再发给模型。要长期生效的约定请写进 AGENTS.md 或 agent 的提示词文件，而不是只靠对话。
几十轮之前的工具输出路径打不开了？
落盘目录按「每会话 200 个文件 / 50 MiB」从最旧删起，_path 只在保留窗口内有效。 要长期留用的内容请在它还在时另存一份；路径若在主目录内会记成 ~/... 形式，文件工具认 ~。
落盘的文件会不会被别人看到？
工具输出目录与新建层级只给本人权限，文件是 600；会话文件同样收到 600 / 新目录 700。 已知边界：这挡的是「同机其他用户读」，挡不住同用户的其它进程，也挡不住已经落地的副本（备份、同步盘）。
会话文件能手工改吗？
能改，但后果自负：压缩边界若因此失效，内核会按「从未压缩过」处理（不误伤）；快照反序列化失败会让这段会话读不回来。 要备份就在会话没在用的时候整目录拷走。

关键结论

  1. 会话命令只有九个是本页要记的：/new、/session(/sessions)、/resume、 /status、/usage(/cost)、/delete(/rm)、/model、 /agent(/a)、/compact；-tui 另有五个外壳命令不在 /help 里。
  2. 会话持久化是插件给的：session-file 一个会话一个 <sessionId>.json、 默认写在 ~/.jellyfish/sessions、默认用 git 管历史；不装它，会话只活在内存里，--session 会退 2。
  3. --agent / --model 只归 -cli，且只在新建会话时生效； 模型解析是「会话显式 → agent.model → 全局默认」三级回落。
  4. 压缩是插件能力：不启用 jellyfish-plugin-compact 就整体不可用、且不回退内置； 自动压缩在上下文用到 80%（react.autoCompactPercent）或本次已被机械裁剪时触发。
  5. 历史一条不删：屏幕、恢复出来的会话、落盘文件都是完整历史，变的只是「发给模型的那条链路从哪里开始」； 但被丢弃的那段既不在摘要里、也不再发给模型。
  6. 工具输出落盘与老化都只改请求：落盘信封以 _truncated / _tool / _total_chars / _total_lines / _path / _hint / _partial / preview 八个字段为唯一格式；agingPercent 缺省 70，必须略低于 autoCompactPercent（80）。
  7. @ 引用不内联文件内容：它只把路径写进消息，读取由模型调 read_file 完成， 因此大文件不会撑爆上下文，权限与 max_bytes 照旧生效。
