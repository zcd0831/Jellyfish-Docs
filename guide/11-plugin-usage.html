11 安装与使用官方插件

内核是「最小内核」——文件读写、跑命令、会话持久化、上下文压缩全都在插件里。这一页回答两件事： 这 13 个插件各是什么、该怎么装，以及每个插件的配置段怎么写。 每个插件的字段表都给了类型、必填、默认值与示例，可以直接拼进 jellyfish.json。

学习目标

  • 说出 13 个官方插件各自的 plugin.id 与它提供的能力，并知道 jellyfish-script 不是插件而是库；
  • 用三种方式之一把插件装进扫描目录，并知道为什么「新增 / 删除 jar 必须重启」；
  • 写对 plugins.enabled / plugins.disabled，并分清「未声明」与「声明为空」；
  • 为任意一个插件写出它自己的配置段（plugins.configurations.<pluginId>）；
  • 知道改动哪个配置由 /reload 生效、哪个必须重启进程；
  • 按「最小可用 / 日常开发 / 全功能」三档挑出该装的插件；
  • 遇到「装了但命令没出现」时能自己定位到扫描目录、禁用名单或配置段这三处。

13 个插件一览

官方插件仓库 Jellyfish-Plugins 里 15 个 Maven 模块，其中 13 个产出插件 jar，另外两个是 库与示例。plugin.id 与模块名在官方插件里恰好同名，但你写配置时用的必须是 plugin.id（它同时是注册表的 owner 与配置段的键）。

模块plugin.id提供什么能力
jellyfish-plugin-tools 同名 五个文件工具 read_file / write_file / edit_file / list_dir / grep_files；提问工具 ask_user；输入框的 @ 文件引用；按路径收口的闸门 pathPolicy
jellyfish-plugin-shell 同名 shell 工具（/bin/sh -c 执行命令原文）+ 命令策略（分段判定、白名单准入、可信表免审批、只读表不打扰、灾难形状拒绝、命令替换与重定向升级审批）+ !命令 输入指令。没有沙箱
jellyfish-plugin-session-file 同名 会话持久化：一个会话一个 JSON 文件，并用 git 管理历史
jellyfish-plugin-todo 同名 会话待办：todo_write / todo_claim / todo_done / todo_release / todo_block 五个工具 + 只读 /todo 命令 + 随本轮消息送达的待办块 + 状态栏进度 + 左栏清单面板
jellyfish-plugin-project 同名 项目约定：探测工作目录下的 AGENTS.md，小文件内联原文、大文件只给路径；/init [--force] 让模型读仓库后写出它
jellyfish-plugin-compact 同名 会话压缩策略：摘要指令 + 保留条数 / 摘要上限。不装它就没有压缩
jellyfish-plugin-skills 同名 skills：按目录发现 SKILL.md，元信息常驻 system prompt、正文由模型用 skill 工具按需加载
jellyfish-plugin-mcp 同名 MCP 客户端：stdio 连外部 MCP server，把它的工具以 mcp__<server>__<tool> 接入
jellyfish-plugin-workflow 同名 编排：workflow 工具接受一份声明式 spec，按依赖并发派生子代理并聚合结果
jellyfish-plugin-plan 同名 plan 模式：/plan [on|off] 在会话内开关，开启时只有白名单里的工具可用
jellyfish-plugin-resmon 同名 资源监控：JVM 与 ~/.jellyfish 占用采样，只读 /resmon [jvm|disk|auto] 命令 + 右栏常驻面板。只报告、不清理
jellyfish-plugin-python 同名 Python 脚本插件运行时：把 scripts/python/<id>/ 下的脚本目录变成标准插件
jellyfish-plugin-node 同名 Node 脚本插件运行时：与 Python 同构（同一套协议与进程模型），零第三方依赖
另外两个模块不是插件
  • jellyfish-script 是库：Python / Node 桥接共用的机制层（探测解释器、扫清单、按脚本注册、事件与熔断、按序关闭）。 它不产出到 plugins/，而是被两个桥接插件以 shade 的方式打进各自的 jar。 因此你在 plugins/ 目录里永远不该看到它的 jar。
  • examples/scripts 是示例脚本目录：{python,node}/{hello,jira} 是可直接拷贝运行的示例 （被端到端用例直接加载），另有仅 Python 的 web、stock、stockpanel。

安装：三种装法

插件是独立打包的 PF4J jar，安装这件事本身就是「把 jar 放进扫描目录」。扫描目录来自 config.json 的 plugins.roots（缺省 ["~/.jellyfish/plugins/"]）， PF4J 只在目录下一层找 plugin.properties——因此把 jar 塞进子目录是找不到的。

方法一：全量装（cpPlugins.sh）

是什么
仓库根目录的脚本把 13 个插件的 target/*.jar 一次性拷进 ~/.jellyfish/plugins，并把几个示例脚本拷进 ~/.jellyfish/scripts/。
怎么用
cd /path/to/Jellyfish-Plugins
mvn -q package -DskipTests      # 打包全部插件
./cpPlugins.sh                  # 拷进 ~/.jellyfish/plugins/

完整示例：脚本里对每个 jar 就是一行 cp（下面是节选，不是全文）

cp Jellyfish-Plugins/jellyfish-plugin-compact/target/jellyfish-plugin-compact-0.1.1.jar ~/.jellyfish/plugins
cp Jellyfish-Plugins/jellyfish-plugin-tools/target/jellyfish-plugin-tools-0.1.1.jar ~/.jellyfish/plugins
# …13 个 jar 各一行…
rm -rf ~/.jellyfish/scripts/python/web
cp -r Jellyfish-Plugins/examples/scripts/python/web ~/.jellyfish/scripts/python/web

常见问题

  • 脚本报 No such file or directory？脚本里的路径写成 Jellyfish-Plugins/...，也就是从工作目录的相对路径出发的——本套文档的工作目录同时下辖两个仓库，所以能直接用；如果你的目录结构不同，按实际路径改或直接手抄 cp 一行。
  • 拷完就生效了吗？没有。需重启 扫描目录与插件集合只在启动期确定。

方法二：只装用得到的几个

是什么
不跑脚本，自己把某几个模块的 jar 拷进扫描目录——少一个插件就少一份启动期开销与一份配置面。
怎么用
cd /path/to/Jellyfish-Plugins
mvn -q package -DskipTests
mkdir -p ~/.jellyfish/plugins
cp jellyfish-plugin-tools/target/jellyfish-plugin-tools-*.jar ~/.jellyfish/plugins/

常见问题

  • 只拷一个模块能构建吗？能。mvn -q package -DskipTests 在聚合 POM 上是全量打包，但每个插件模块也可以单独构建（-pl jellyfish-plugin-tools）。
  • 桥接插件要不要连脚本一起拷？要。jellyfish-plugin-python / -node 只是运行时，脚本目录在 scripts/python/<id>/ 下另行放置（见本页 python / node 桥接 一节）。
Jellyfish-Plugins/README.md:38-46（「也可以只装用得到的几个」）

方法三：从源码 mvn package（改代码的人走这条）

是什么
插件仓库是独立的 Maven reactor：jellyfish-api 不来自内核源码树，而是本地 Maven 仓库里那一份。所以改插件之前，先把内核装进本地仓库。
怎么用
# 0. 先把内核 install 到本地仓库（不能省）
(cd ../Jellyfish && mvn -q install -DskipTests)
# 1. 再构建插件
cd ../Jellyfish-Plugins
mvn -q clean package -DskipTests
./cpPlugins.sh

常见问题

  • 为什么编译看不到内核刚改的字段？漏了第 0 步。表现正是「内核明明改了，插件这边编译却看不到」。
  • 需要 clean 吗？内核升级后必须 clean：增量编译会复用按旧 jellyfish-api 编出的 target/，把编译问题伪装成运行期问题（仓库里记录的实例是 11 条 NoSuchMethodError）。
Jellyfish-Plugins/README.md:14-28（环境要求与「本仓库是独立的 reactor」）、Jellyfish-Plugins/AGENTS.md「内核升级后要做的检查」、Jellyfish-Plugins/README.md:1061-1081
一条钉子：新增 / 删除插件 jar 必须重启

扫描目录与插件集合只在启动期确定。往 plugins/ 里加一个 jar 或删一个 jar，都要重启进程才认。 与之相对，改配置不用重启：启用 / 禁用名单与逐插件配置段写在 jellyfish.json，改动由 /reload 生效。

Jellyfish-Plugins/README.md:33-35、Jellyfish/README.md:517-519（/reload 与「只重启配置段变了的插件」）、Jellyfish/docs/constraints.md「插件扫描与配置」

启用与禁用

三件事写在 jellyfish.json 的 plugins 段里：

字段类型必填默认值含义示例
plugins.enabled string[] 选填 未声明（＝不额外限定，全部加载） 启用名单。「未声明」与「声明为空」是两回事：不声明表示「不额外限定」，显式写 [] 表示「一个都不启用」 ["jellyfish-plugin-tools"]
plugins.disabled string[] 选填 [] 禁用名单。不声明与写 [] 等价，都不禁用任何插件。同一 pluginId 同时出现在两份名单里时按禁用处理，并发一条配置告警 ["jellyfish-plugin-todo"]
plugins.configurations.<pluginId> object 选填 未配置（插件拿到空映射） 单个插件的配置段，逐插件的键值见插件自己的文档。两级合并时同名插件段是整对象替换，项目级一写就整段盖掉全局级 {"jellyfish-plugin-tools": {"pathPolicy": {…}}}

生效方式：/reload 生效 上面三个字段全部由 /reload 生效（内核只重启配置段变了的插件）；需重启 config.json 的 plugins.roots 与 jar 的增删。

完整示例——只想装文件工具、并临时禁用待办插件：

{
  "plugins": {
    "enabled": ["jellyfish-plugin-tools"],
    "disabled": ["jellyfish-plugin-todo"],
    "configurations": {
      "jellyfish-plugin-tools": {
        "pathPolicy": {
          "write": { "allow": ["."], "outside": "ask" },
          "read":  { "allow": [".", "~/.jellyfish"], "outside": "deny" }
        }
      }
    }
  }
}

常见问题

  • 我把 enabled 写成 [] 想「不限制」，结果一个插件都没了？语义反了：不限制就是不写这个键；[] 是「一个都不启用」。
  • 写错了 pluginId 会怎样？禁用名单里写错只会「什么也没禁」；configurations 里写错 pluginId 时插件拿到的是空映射，因此配置看起来「被忽略了」——先核对拼写与大小写。
  • 项目级配置为什么不生效？项目级 .jellyfish/jellyfish.json 的插件段是整对象替换：项目级一写某个插件段，全局级那一份就整段被盖掉。想同时保留两处，就把完整内容写在生效的那一级。

tools —— 文件工具与 @ 引用

是什么
给模型五把文件操作的手（三个只读、两个可写）、一个提问工具，以及输入框里的 @ 文件补全。
装了之后多出什么
  • 工具：read_file（按行分片读）、write_file（整文件覆盖写）、edit_file（字面量替换；匹配到多处且未声明 replace_all 时报错而不改文件）、list_dir（只列一层）、grep_files（逐行正则，跳过 .git / target / node_modules 与二进制文件）；
  • 工具：ask_user（把一个问题连同 2~6 个候选项摆到用户面前，答案以工具结果回灌给模型；它不是审批）；
  • 输入引用：@路径 弹出补全面板。它不内联文件内容，读取仍由模型调 read_file 完成；
  • 一个权限拦截贡献：pathPolicy 闸门（见下）。

配置字段

字段类型必填默认值含义示例
pathPolicy object 选填 未配置（read 不设限、write 走缺省） 路径闸门总开关。文件工具在允许的路径之外时升级为人工审批或直接拒绝；粒度是「工具名 + 路径」 { "write": {…}, "read": {…} }
pathPolicy.read object 选填 不设限 读方向的规则，管 read_file / list_dir / grep_files。不配就不设限 { "allow": [".", "~/.jellyfish"], "outside": "deny" }
pathPolicy.write object 选填 { "allow": ["."], "outside": "ask" } 写方向的规则，管 write_file / edit_file。不配按缺省：只允许工作目录、范围外要审批 { "allow": ["."], "outside": "ask" }
pathPolicy.read.allow string[] 选填 ["."] 读方向允许的目录。相对路径按进程工作目录解析、行首 ~ 按用户主目录，因此 "." 就是工作目录 [".", "~/.jellyfish"]
pathPolicy.read.outside string（allow / ask / deny） 选填 ask 读方向范围之外的裁定。allow 等于把该方向的门关掉（恒无异议） deny
pathPolicy.write.allow string[] 选填 ["."] 写方向允许的目录，解析规则与读方向的同名键逐字一致（相对路径按进程工作目录、行首 ~ 按用户主目录） ["."]
pathPolicy.write.outside string（allow / ask / deny） 选填 ask 写方向范围之外的裁定，取值与语义和读方向的同名键一致（allow 即关掉该方向的闸门） "ask"

完整示例

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-tools": {
        "pathPolicy": {
          "write": { "allow": ["."], "outside": "ask" },
          "read":  { "allow": [".", "~/.jellyfish"], "outside": "deny" }
        }
      }
    }
  }
}

常见问题

  • ask 在 -cli 下等于拒绝？是。-cli 不挂审批通道，「需要审批」一律按拒绝处理——工作目录外的写在那里会直接失败。要放开就把该方向配成 outside: "allow"，或把目录加进 allow。
  • 它是文件系统沙箱吗？不是。它管不了 shell 命令里出现的路径，也管不了 MCP 工具；它管的是本插件这几个文件工具的 path 参数。符号链接会先解开再比，因此工作目录里放一个指向 /etc 的链接不会成为后门。
  • 配置写错会把插件弄挂吗？不会，只回退并告警（走 ConfigWarningEvent，TUI 上看得见）。

shell —— 执行命令与 !命令

是什么
让模型在本机执行命令，外加一套「先拒绝、再免打扰、最后才问人」的命令分类策略。它没有沙箱：命令以本进程的权限运行，能读写你这个用户的任意文件。
装了之后多出什么
  • 工具 shell（参数 command / cwd / timeout_seconds）；
  • 输入指令 !命令：手动执行一条命令、不进模型，执行完把「命令回显 + 输出」作为一条用户消息落进会话；它复用与模型调用完全相同的执行链路，照旧过权限与审批；
  • 一个权限拦截贡献：命令策略（白名单、可信表、只读表、拒绝形状、重定向与命令替换升级）。

配置字段

字段类型必填默认值含义示例
timeoutSeconds int 选填 120 命令最多允许跑多久；单次调用可用 timeout_seconds 参数覆盖，并被 maxTimeoutSeconds 钳制。不支持「不超时」 300
maxTimeoutSeconds int 选填 1800 单次调用能声明的超时上限 1800
idleTimeoutSeconds int 选填 0（关闭） 连续多久没有任何输出就判定卡住。模型不能设置它，它是用户的环境策略 600
environment object（string → string） 选填 {} 额外注入或覆盖的环境变量。子进程继承父进程环境，但名字匹配 *KEY* / *TOKEN* / *SECRET* / *PASSWORD* 等的变量不会传下去；这里写的值可以盖掉防挂死默认值 { "HTTP_PROXY": "http://127.0.0.1:7890" }
sensitivePatterns string[] 选填 []（只追加，不替换内置表） 在内置剔除模式之外追加要剔除的环境变量名模式 ["*_PWD"]
allowedCommands string[] 选填 [] 非空即默认拒绝的准入白名单，支持 git status 这种两 token 形式、也支持整条 *（匹配全部命令）。它只管准入，不管审批，也不受 commandPolicy.enabled 影响 ["git status", "mvn test"]
commandPolicy object 选填 未配置（等价全缺省） 命令分类策略容器 { "enabled": true, "trustedCommands": ["mvn test"] }
commandPolicy.enabled boolean 选填 true 只关分类器这个便利机制。false 时只读表、重定向 / 命令替换检查与「其余命令问人」都不再表态，但白名单、可信表、拒绝形状照旧生效 false
commandPolicy.trustedCommands string[] 选填 [] 可信命令表，命中即免审批。粒度与白名单一致（两 token 形式可用）。判定要求「所有分段都命中」 ["mvn test", "npm run build"]
commandPolicy.readOnlyCommands string[] 选填 [] 追加在内置只读表之后。内置表不可替换，只能追加 ["terraform plan"]
commandPolicy.deniedPatterns string[] 选填 [] 追加在内置拒绝形状（rm -rf /、mkfs、of=/dev/、:(){）之后，同样不可撤销 ["docker system prune -a"]

完整示例——「mvn test 静默执行，其余非只读命令问人」：

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-shell": {
        "timeoutSeconds": 300,
        "idleTimeoutSeconds": 600,
        "commandPolicy": {
          "enabled": true,
          "trustedCommands": ["mvn test"]
        }
      }
    }
  }
}

常见问题

  • 写进 allowedCommands 了，为什么还弹批准框？白名单只回答「能不能跑」，不解除审批。要它静默执行，就把同一条前缀也写进 trustedCommands。
  • 想一次放行全部命令怎么写？整条 *：allowedCommands: ["*"] 表示准入不再拦任何命令，再把 trustedCommands 也写成 ["*"] 就是一律免审批（只读表里的 * 则是「一律按只读放行」）。它只解除自己所在的那一道门，拒绝形状照旧拒绝；半个通配（如 git *）按字面量匹配、永不命中，解析时会有告警。
  • 把 rm 写进可信表会不会把 rm -rf / 也放行？不会。拒绝形状判定排在可信表之前。
  • -cli / -server 下命令总是被拒？那两个外壳没有审批者，ASK 就是拒绝。免审批的放行口只剩两个：被分类器判为只读的命令，以及 trustedCommands 里的命令（白名单非空时还要先过白名单）。

结论
敲 /mcp 看连接状态、工具数与失败原因——那是唯一的线索。连不上不会让内核起不来。 断开会按退避自动重连（1 秒起、每次翻倍、封顶 60 秒、共 6 次），重连期间该 server 的工具先被摘掉； 约一分钟后仍连不上就停在「失败」，/reload 可重试。

三个常见原因：command 写的可执行文件不在 PATH 上；需要密钥但没写进 env 段（子进程只继承白名单里那几个环境变量）；用了 sampling / elicitation 这类能力（本客户端不声明也不支持，会回一条明确错误）。

脚本插件报「环境变量未设置」

结论
配置段里写了 ${SOME_KEY} 而环境变量没设，是硬失败（整个进程启动即失败，报错形如 environment variable is not set: SOME_KEY）。确实要用的密钥才写 ${...}，并保证它总是已设。

推论：不用某个后端时把对应的 apiKey 留成 ""，不要写占位符——写上去就是一个定时炸弹，换个人或换个 shell 拉不到那个变量就起不来。 （这条口径在示例脚本 web 的配置段上体现得最清楚。）

同一个工具被两个插件抢了怎么办

结论
不用自己处理：重复注册默认直接失败，冲突在插件启动时以 DUPLICATE_HANDLER 当场暴露， 而不是「谁后注册谁生效」。

要顶替别人（含内核自带的 task 与系统命令）必须显式声明覆盖（RegisterOptions.override(true)）， 且覆盖是压在链顶之上——旧登记仍在表里只是不生效，覆盖者一被回收（插件停止、/reload 重启插件）旧的就自动重新生效。 MCP 工具名带 mcp__<server>__ 前缀，正是为了让「重名」不成为事实。

关键结论

  1. 官方插件共 13 个（11 个 Java + 2 个脚本桥接），jellyfish-script 是被 shade 进桥接插件的库，不产到 plugins/。
  2. 安装就是「把 jar 放进 plugins.roots 指向的目录」；新增 / 删除 jar 必须重启，改配置只需 /reload（且只重启配置段变了的插件）。
  3. plugins.enabled 不写＝不限制，写 []＝一个都不启用；两个名单里都有同一个 id 时按禁用处理。
  4. 每个插件的配置都在 plugins.configurations.<pluginId>；项目级一写某个插件段就是整对象替换全局级那一份。
  5. 三个「不装就没有」：不装 tools 模型读不了文件、不装 compact 就没有压缩、不装 session-file 就没有可恢复的会话。
  6. 两个「没有沙箱」：shell 以你的权限运行命令；tools 的 pathPolicy 只管这几个文件工具的 path，管不了 shell 与 MCP。
  7. 插件起不来不会拖垮内核：失败只影响它自己，原因在启动日志的 WARN / ERROR 行里。
