12 从零开发一个插件

一个插件就是一个 jar：一份 plugin.properties + 一个 JellyfishPlugin 实现 + 若干扩展点处理器。 内核负责发现、装载、回收它，你只需要回答两件事：注册什么与怎么处理。 这一页按「选形态 → 建工程 → 写 POM → 实现 SPI → 选扩展点 → 抄最小插件 → 打包 → 安装验证 → 调试」的顺序走一遍， 代码块都对着 jellyfish-api 源码核过签名，可以直接编译。

学习目标

  • 在 Java 插件与 Python / Node 脚本插件之间做出选择，并知道脚本插件覆盖的是一份「能力档」而非全部扩展点；
  • 写出最小的插件工程（目录树、plugin.properties、pom.xml）并说清每个字段的含义；
  • 实现 JellyfishPlugin 的 start(PluginContext) / stop()，并说清注册窗口、失败语义与 fail-closed；
  • 会用 PluginContext 的每一个方法，知道哪些事它刻意不给（会话、工作目录、起回合）；
  • 在 24 个可用扩展点里选对「带路由键的 handle」还是「类型级 contribute」；
  • 写出一个能被模型调用的工具（hello）和一条用户能敲的命令（/hello）；
  • 按 plugins.configurations.<pluginId> 读自己的配置，并在配置可疑时告警而不阻断启动；
  • 打包、安装、用三种方式验证插件真的生效了，并在加载失败时按清单定位原因。

第一步：先选形态 —— Java 插件还是脚本插件

两条路都产出「内核眼里的标准 PF4J 插件」：同样的注册、owner、回收与生命周期。区别在于能力覆盖面与 运行期模型。选错了不会报错，只会在某个扩展点上发现「脚本这边没有这个点」。

对照项Java 插件Python / Node 脚本插件
扩展点覆盖 全部（jellyfish-api 里所有扩展点） 只覆盖一份「能力档」：extension-points.json 里 "in" 那 24 项，另外 4 项明确 "excluded"（见 扩展点清单）
挡在哪一类点之外 — 两类：要返回 Java 对象的（结构上做不到）、跑在渲染线程或启动期的（一次进程往返不可接受）
进程模型 与内核同进程、同一 JVM 独立子进程：一个脚本一个 worker，首次调用才拉起、空闲自毁；网关懒启动
热路径表现 直接函数调用 对 request_tuning / aging_strategy 不冷启动：worker 没热着就返回「不表态」，热着也只给 2 秒截止（超时不杀 worker）
失败隔离 插件抛错会影响调用点（同步派发无超时、无异常隔离，调用点自行捕获） 脚本崩溃只影响它自己（每脚本一 worker）；连续失败按熔断冷却、冷却后自动半开恢复
依赖与语言 JDK 1.8（不得用 Java 9+ API 或语法）；私有依赖自带并 shade 脚本可以用自己的生态（Python 包、node_modules），依赖装在脚本自己那边
编排、渲染、启动期行为 能写（能拿到内核类型、能读写文件、能起线程，但要自己遵守 stop() 纪律） 不能写（excluded 的四项就是这类）；只做「数据进出」
什么时候选它 要用到全部扩展点、要在渲染线程上直接返回、要把旧版内核工具的注册顶替掉、要接入内核的 ExtensionRegistry 做单测 只是「多一个取数工具 / 一条命令 / 一段提示词 / 一个面板」，且希望用 Python / Node 生态快速迭代；或者要一个会联网、会依赖第三方库的隔离边界
「能力档」不是一句形容词，而是一份被测试守着的清单

脚本能用的扩展点唯一真源是 Jellyfish-Plugins/jellyfish-script/src/main/resources/script/extension-points.json， 它把每个扩展点分成三段：in（已打通）、planned（已决定要做但还没做，当前为空）、 excluded（明确不做，且写明理由）。

内核新增扩展点时，本仓库会构建失败：ExtensionPointCoverageTest 枚举 jellyfish-api 里全部 ExtensionRequest 子类，未分档即失败。这条纪律的用意是 「先做分档决策，再决定要不要实现」——而不是让新扩展点在脚本侧静默不存在。

最小插件工程结构

一个插件的最小形态是「一个实现类 + 一份描述符」。官方插件的源码结构范式是 plugin.properties + PluginConfig（配置段解析）+ JellyfishPlugin 实现 + 各扩展点 handler。

my-plugin/
├── pom.xml
└── src/main/
    ├── java/com/example/myplugin/MyPlugin.java
    └── resources/plugin.properties

若你把它放进 Jellyfish-Plugins 仓库里当子模块（而不是建一个独立工程），它长这样：

Jellyfish-Plugins/
├── pom.xml                      ← 父 POM：新增模块要在 <modules> 里登记
├── cpPlugins.sh                 ← 新增插件要在这里加一行 cp
└── my-plugin/
    ├── pom.xml                  ← <parent> 指向 io.github.zcd0831:jellyfish-plugins:0.1.1
    └── src/
        ├── main/java/com/example/myplugin/MyPlugin.java
        ├── main/resources/plugin.properties
        └── test/java/com/example/myplugin/MyPluginTest.java

plugin.properties 完整内容与逐字段说明

它必须位于 jar 根目录——PF4J 按名查找。

# Jellyfish 插件描述符（PF4J），必须位于插件 jar 根目录
#
# plugin.id 同时是注册表的 owner：插件卸载时按它批量回收注册。
plugin.id=my-plugin
plugin.class=com.example.myplugin.MyPlugin
plugin.version=0.1.0
plugin.provider=com.example
plugin.description=一句话说明这个插件做什么
plugin.requires=*
jellyfish.tags=example
字段类型必填默认值含义示例
plugin.id string 必填 — 插件身份，同时是注册表的 owner 与 plugins.configurations.<pluginId> 的键。它不得包含 ::（那是「插件内子单元」的 owner 命名空间分隔符，自带会误伤其它插件的注册），命中即在描述符体检阶段被拒 my-plugin
plugin.class string 必填 —（缺失记一条描述符错误，插件不启动） 实现类全限定名。该类必须有一个公开无参构造器：插件由 PF4J 的插件类加载器实例化，无法走 Dagger 装配 com.example.myplugin.MyPlugin
plugin.version string 选填 0.0.0（缺省兜底版本号，避免下游依赖解析拿到 null） 插件版本，供依赖解析与展示 0.1.0
plugin.provider string 选填 未提供时为 null（PF4J 把该键的原始值直接塞进描述符，不做任何兜底；内核既不读也不校验它） 提供者标识，仅展示用 com.example
plugin.description string 选填 未提供（或写成空串）时为 ""：PF4J 对空值显式写入空串而不是 null；内核里没有任何 getPluginDescription() 读取点 一句话说明这个插件做什么，展示用 按名字打招呼
plugin.requires string（semver 约束） 选填 未提供时不校验（描述符保持 PF4J 初值 *；内核 normalizeRequires 见空白直接返回、连错误都不记）；示例统一写 * 内核兼容约束。内核目前不声明系统版本，PF4J 的缺省值 0.0.0 会让这条校验直接跳过，因此写 * 是显式声明「不限版本」；写成非法表达式（如带 -SNAPSHOT）会被预检归一为 * 并记一条描述符错误，插件起不来 *
jellyfish.tags string（逗号分隔的 CSV） 选填 空集合 标签。语义在仓库里有两种说法：内核描述符的 javadoc 写「供按标签授权使用」， 而官方插件的 plugin.properties 注释写「标签仅作诊断与展示；agent 授权只按工具名，不按标签」。 内核 main 代码里除了解析与测试没有其它读取点，因此现在它实际只被解析、不被使用。 已查实：它现在没有任何运行期效果——getTags() 的全部调用点都在单测里， 生产代码里唯一的读写分别是解析器的一行 addTags 与本题的 getTags() 本身， 既没有授权判定、也没有任何展示/序列化读取点，因此它是「预留的授权维度」，javadoc 的措辞是意图声明而非现状。 example

生效方式：需重启 描述符在启动期解析，改它必须重新打包并重启进程。

两处能被拦在加载期的写法
  • 漏写 plugin.class：解析器校验的是「键存在」而不是「值非空」。若按后者，漏写会被放过，最终报出 「org.pf4j.Plugin 未实现 JellyfishPlugin」这种指错方向的错误——所以它干脆在描述符层拦下。
  • jar 里带了内核契约或 PF4J 的类：加载期的 classpath 护栏会拒绝这种插件包，理由是「该类由父加载器提供，自带会破坏类型同一性（请改为 provided 依赖）」。 这就是下一条规矩为什么是硬性的。

pom.xml：先看仓库原文，再看不依赖父 POM 的那份

仓库原文（README 的写法，<parent> 指向插件聚合 POM）：

<parent>
    <groupId>io.github.zcd0831</groupId>
    <artifactId>jellyfish-plugins</artifactId>
    <version>0.1.1</version>
</parent>

<artifactId>my-plugin</artifactId>

<dependencies>
    <!-- 内核契约必须 provided：PF4J 的插件类加载器是子优先的，自带 api 会遮蔽父加载器里的同名类 -->
    <dependency>
        <groupId>io.github.zcd0831</groupId>
        <artifactId>jellyfish-api</artifactId>
        <version>${project.version}</version>
        <scope>provided</scope>
    </dependency>
</dependencies>
这份父 POM 不在中央仓库

拿不到。内核仓库明确说明它发布了父 POM 与 jellyfish-api / -infra / -core / -di 四个构件（坐标 io.github.zcd0831:jellyfish），而 Jellyfish-Plugins 没有 release profile（整份 pom.xml 里没有任何用于发布 Central 的 <profiles>； 各插件模块自己的 <profiles> 只用来跑端到端测试，如 shell-it、mcp-it、script-it）。 因此 io.github.zcd0831:jellyfish-plugins:0.1.1 不在中央仓库——repo1.maven.org 上 io/github/zcd0831/ 整个路径 404，Central 检索该 groupId 命中 0 条。

只在本仓库内部开发时不构成问题（父 POM 就在聚合层级上）；在仓库之外开发时请直接用下面那份 不依赖父 POM 的等价 POM。要说清楚的第二件事：本机 ~/.m2 里那份之所以能用，是因为本仓库 mvn install 装过（~/.m2/repository/io/github/zcd0831/jellyfish-plugins/ 下只有 maven-metadata-local.xml，没有任何从中央仓库下载的痕迹），换一台机器就解析不到——仓库之外开发请直接用下面那份。

替代方案：不依赖父 POM、可直接用的等价 POM（<parent> 换成 jellyfish-api 坐标）：

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         http://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <!-- 不再继承 jellyfish-plugins 父 POM：那份父 POM 不在中央仓库，仓库之外解析不到（见上） -->
    <groupId>com.example</groupId>
    <artifactId>my-plugin</artifactId>
    <version>0.1.0</version>
    <packaging>jar</packaging>
    <name>My Jellyfish Plugin</name>

    <properties>
        <!-- 内核契约的版本：与你要装的那个内核一致（本套文档写的是 0.1.1） -->
        <jellyfish.version>0.1.1</jellyfish.version>
        <java.version>1.8</java.version>
        <maven.compiler.source>${java.version}</maven.compiler.source>
        <maven.compiler.target>${java.version}</maven.compiler.target>
        <jackson.version>2.21.6</jackson.version>
        <slf4j.version>1.7.36</slf4j.version>
        <maven-compiler-plugin.version>3.11.0</maven-compiler-plugin.version>
        <maven-shade-plugin.version>3.5.1</maven-shade-plugin.version>
        <junit.version>5.10.2</junit.version>
    </properties>

    <dependencies>
        <!-- 内核契约：永远 provided。插件 jar 里不含它的类，因此插件拿到的值类型
             永远是运行期内核那一份——内核给值类型加字段时插件什么都不用做 -->
        <dependency>
            <groupId>io.github.zcd0831</groupId>
            <artifactId>jellyfish-api</artifactId>
            <version>${jellyfish.version}</version>
            <scope>provided</scope>
        </dependency>

        <!-- 日志：宿主已有 slf4j，同样由父加载器提供 -->
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>${slf4j.version}</version>
            <scope>provided</scope>
        </dependency>

        <!-- 私有依赖示例：需要把配置段或 JSON 转成对象时必须自带 Jackson 并 shade 进 jar
             （内核的序列化封装在 jellyfish-infra 里，插件看不到）。
             不需要就删掉这一条与下面的 shade 执行 -->
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>${jackson.version}</version>
        </dependency>

        <!-- 测试期可以引 jellyfish-infra（test scope）：注册与派发走的就是内核那条路径 -->
        <dependency>
            <groupId>io.github.zcd0831</groupId>
            <artifactId>jellyfish-infra</artifactId>
            <version>${jellyfish.version}</version>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <version>${junit.version}</version>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <!-- 编译：-parameters 必须开。这不是「为了调试方便」：
                 jellyfish-api 的扩展点载荷（会话快照等）是「全字段构造器 + 无 setter」
                 的不可变类型，插件侧用 Jackson 反序列化时只能靠构造器参数名把 JSON 字段对上。
                 去掉它，会「写得出、读不回」，而编译与大部分单测依然全绿 -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>${maven-compiler-plugin.version}</version>
                <configuration>
                    <parameters>true</parameters>
                </configuration>
            </plugin>

            <!-- 打包：只把私有依赖打进插件包。
                 includes 里绝不能出现 jellyfish-api —— 那会让插件带着旧版本的值类型跑，
                 新字段静默丢失；内核的 classpath 护栏也会在加载期直接拒绝这种插件包 -->
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-shade-plugin</artifactId>
                <version>${maven-shade-plugin.version}</version>
                <executions>
                    <execution>
                        <id>shade-private-deps</id>
                        <phase>package</phase>
                        <goals>
                            <goal>shade</goal>
                        </goals>
                        <configuration>
                            <createDependencyReducedPom>true</createDependencyReducedPom>
                            <artifactSet>
                                <includes>
                                    <include>com.fasterxml.jackson.core:jackson-databind</include>
                                    <!-- 需要时按坐标继续加；jellyfish-api / pf4j / slf4j 由父加载器提供 -->
                                </includes>
                            </artifactSet>
                            <filters>
                                <filter>
                                    <artifact>*:*</artifact>
                                    <excludes>
                                        <exclude>META-INF/*.SF</exclude>
                                        <exclude>META-INF/*.DSA</exclude>
                                        <exclude>META-INF/*.RSA</exclude>
                                        <exclude>module-info.class</exclude>
                                    </excludes>
                                </filter>
                            </filters>
                        </configuration>
                    </execution>
                </executions>
            </plugin>
        </plugins>
    </build>
</project>
三条规矩，全是硬性的
  1. jellyfish-api 永远是 provided。插件 jar 里不含它的类，因此插件拿到的值类型永远是运行期内核那一份——内核给值类型加字段时插件什么都不用做。
  2. shade 的 includes 里绝不能出现 jellyfish-api。那会让插件带着旧版本的值类型跑，新字段静默丢失；而且加载期的 classpath 护栏会拒绝整个插件包（连带理由都写好了：「自带会破坏类型同一性（请改为 provided 依赖）」）。
  3. 在插件仓库里新增插件，要同时登记两处：父 pom.xml 的 <modules> 里加一行，往 cpPlugins.sh 加一行 cp。只做一处的结果是「构建过了但没拷进扫描目录」或「构建里根本没有这个模块」。

SPI 契约：JellyfishPlugin

实现类必须提供公开无参构造器。接口只有两个方法，其中 start 是唯一必需方法：

public interface JellyfishPlugin {

    /** 启动插件：注册处理器、订阅事件、申请资源。 */
    void start(PluginContext context);

    /** 停止插件：释放自己申请的资源（连接、线程、子进程）。默认空实现。 */
    default void stop() {
    }
}
方法语义边界与失败行为（逐条来自源码注释）
start(PluginContext) 注册处理器、订阅事件、申请资源。「有什么能力是启动期就能确定的、就先挂上」的那个常用落点
  • 它不是唯一的注册时机：注册窗口是插件的整个存活期，start() 返回到 stop() 之前都可以注册、订阅、发布（运行期才知道自己能提供哪些能力的插件——例如 MCP 客户端在握手后才知道工具集——必须如此）；
  • start() 抛错 → 插件转 FAILED，框架回收本次已完成的注册、发布状态变更通知，并继续处理其它插件，因此不必自行回滚；
  • 框架不保证会调用 stop()（PF4J 对未进入 STARTED 的插件会跳过停止），因此 start 内部自己申请到一半的资源要在 catch 里自行释放
stop() 释放自己申请的资源
  • 处理器注册与事件订阅由框架按 owner 回收，插件无需为了回收而自行反注册（Subscription.close() 是主动注销的正式手段，属可选优化）；
  • stop() 返回（或抛错）之后，上下文即失效：此后任何注册、订阅、发布、投递都当场抛 JellyfishException（fail-closed），而不是静默落表变成「插件已停、工具还能调」的幽灵注册；
  • 因此先停下会产生注册的后台线程与定时器，再返回是插件这边的责任；
  • 本方法抛错只被记录，不影响其它插件的停止与内核关闭
为什么注册窗口是「整个存活期」而不是「start() 之内」

因为有一类插件在启动时根本不知道自己能提供什么：MCP 客户端要握完手才知道对端有哪些工具， 脚本桥接要等脚本被拉起才知道它声明了什么。把它们逼进 start() 只会让它们要么阻塞启动、要么写一堆占位工具。 而回收仍然只按 owner 一次收干净（含命名空间前缀 pluginId::子标识），因此运行期注册不会留下没人收的登记。

扩展点清单：24 个可用 + 4 个明确不做

扩展点分两类，选错类的后果是「能编译但注册不上去」或「重复注册失败」。 判据很简单：这个东西有没有名字？有名字（工具名、命令名、标记字符、provider 名）→ handle，同键唯一； 只有类型没有名字（提示词、面板、权限拦截……）→ contribute，0..N 个。

带路由键的（handle，同一「类型 + 路由键」至多一个）

SPI 请求类路由键作用返回值类型
ToolCallRequest 工具名 模型（或外壳）请求执行一次工具调用。请求里带三类调用期设施：取消令牌、输出捕获通道、调用者身份（parentSessionId / runId / rootRunId） ToolCallResult
CommandRequest 命令名 执行一条 /xxx 命令。参数已被归一化成 CommandArguments（tokens 与 raw 两种视图并存），处理器不需要自己拆字符串 CommandResult
CommandOptionRequest 命令名 「这条命令在不带参数时，有哪些取值可以让用户挑」。与执行分开，因为执行可能有副作用，而候选查询必须只读、必须快 CommandOptions
ModelCatalogRequest provider 名 这个 provider 现在有哪些模型。非空时整体替换 models.json 里写的 models，且发现结果不落盘 ModelCatalogResult
InputDirectiveRequest 标记字符（如 !） 用户提交一行输入时问「这行输入有没有插件要接管」——把输入变成一次工具调用。注册表里查不到就按普通文本处理。一次 handle 调用必须是一次纯解析（它在渲染线程上同步执行） InputDirectiveResult

类型级贡献（contribute，0..N 个，按 order 升序）

SPI 请求类路由键作用返回值类型
PromptContributionRequest无（类型级）组装某次请求的 system prompt 前问「这个会话还有没有要追加的上下文」。插件唯一能影响模型行为的贡献点（它不进消息历史）PromptContribution
StatusLineContributionRequest无状态栏尾部的一小段文本（例如待办插件的 待办 2/5）。内容走拉取，不是推送StatusLineContribution
PanelContributionRequest无一块常驻面板的内容。位置、宽度、行数全部由外壳决定PanelContribution
PermissionCheckRequest无本次工具调用要不要拦（权限拦截）。插件只能收紧、不能放宽：核心策略的 ASK 无法被插件的「无异议」降级PermissionVerdict
ToolArgumentPreRequest无工具参数要不要改写（在权限判定之前）。可以「不改」「替换」「直接拒绝」三态，但表达不了权限结论ToolArgumentDecision
ToolResultPostRequest无工具结果要不要整形（在截断与落盘之前）。事后改文本会与落盘文件内容永久分叉，因此顺序是刻意的ToolResultAdjustment
ToolActivationRequest无某个工具该不该进本次工具清单（三态：ABSTAIN / 可见 / 隐藏）。「隐藏」不是「禁用」：它不进下发给模型的那份清单，但仍在注册表里ToolActivation
InputTransformRequest无用户按回车后的原文要不要改写（也可以声明「这次输入我接过去了、不进对话」）InputTransformResult
TurnContextRequest无本轮要随用户消息一起送达的即时状态（会话内会变的状态走这里，而不是提示词贡献）TurnContext
TurnBeforeRequest无这个回合要不要起（可以拦下，也可以改写本轮输入）TurnDirective
SessionPersistRequest无会话快照要落盘（持久化）。落盘失败要上抛——那一刻起「状态已变」与「状态已落盘」必须同生共死Void
SessionRestoreRequest无启动时把会话要回来。内核向所有注册了该处理器的插件要回会话SessionRestoreResult
SessionDeleteRequest无会话被删除，插件清理自己的外存Void
SessionBeforeCloseRequest无会话关闭前能不能关（放行 / 拦下并给出原因）LifecycleVerdict
SessionBeforeForkRequest无会话分支前能不能分（同上）LifecycleVerdict

合并规则只有两类，且都写在调用点而不是注册表里：链式（逐环传递，最后一环天然生效， 不存在「谁胜」）与合并（order 最小且声明了该字段的那一个胜出）。

  1. 请求与结果类型放 api，恰好一个可见构造器 + 静态工厂；新增字段只能用新静态工厂补，不加兼容构造器（Jackson 反序列化要求）。

最小可运行插件：一个工具 + 一条命令

下面这份代码可以直接编译：一个工具 hello（模型调用）+ 一条命令 /hello（用户敲）， 外加可选的 stop()。签名都以 jellyfish-api 源码为准——注意 ToolDescriptor 的构造器是 (name, description, parameters, required) 四个参数， 没有 order 参数（顺序只在 contribute / RegisterOptions 上声明）。 

package com.example.myplugin;

import java.util.ArrayList;
import java.util.Collections;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

import zcd.jellyfish.api.JellyfishException;
import zcd.jellyfish.api.extension.CommandDescriptor;
import zcd.jellyfish.api.extension.CommandRequest;
import zcd.jellyfish.api.extension.CommandResult;
import zcd.jellyfish.api.extension.ToolCallRequest;
import zcd.jellyfish.api.extension.ToolCallResult;
import zcd.jellyfish.api.extension.ToolDescriptor;
import zcd.jellyfish.api.plugin.JellyfishPlugin;
import zcd.jellyfish.api.plugin.PluginContext;

/**
 * 最小可运行插件：一个工具 + 一条命令。
 * <p>
 * 生命周期契约见 {@link JellyfishPlugin}：注册窗口是插件的整个存活期，
 * 而 {@code stop()} 之后一切注册与发布当场失败（fail-closed）。
 *
 * @author 你的名字
 */
public final class MyPlugin implements JellyfishPlugin {

    /** 工具名，同时是工具调用的路由键。 */
    private static final String TOOL_NAME = "hello";

    /** 命令名，同时是 {@link CommandRequest} 的路由键（注册时用小写，外壳负责去掉 {@code /}）。 */
    private static final String COMMAND_NAME = "hello";

    /**
     * 启动插件：把能力挂上去。
     *
     * @param context 框架创建的能力上下文，不可为 {@code null}
     */
    @Override
    public void start(PluginContext context) {
        // ① 工具：带路由键的唯一处理器。descriptor 与 handler 一起落表，
        //    因此不需要再维护第二份「工具清单」。
        context.handle(ToolCallRequest.class, TOOL_NAME, descriptor(), request -> {
            Object raw = request.getArguments().get("name");
            if (raw == null || String.valueOf(raw).trim().isEmpty()) {
                // 参数非法当场抛错（JellyfishException 是运行时异常），
                // 内核会把它转成一条可读的工具结果回灌给模型让它自己改
                throw new JellyfishException("hello 需要参数 name");
            }
            // 结果对象只承载成功语义；output 用字符串（模型看到的就是它）
            return new ToolCallResult(TOOL_NAME, "你好，" + String.valueOf(raw).trim() + "！");
        });

        // ② 命令：同样是「类型 + 路由键」的处理器，路由键是命令名。
        //    名片的 summary 会出现在 /help，usage 是命令名之后的片段，aliases 不含命令名本身。
        context.handle(CommandRequest.class, COMMAND_NAME,
                new CommandDescriptor("按名字打招呼", "<名字>",
                        Collections.singletonList("hi"), true),
                request -> {
                    // tokens 是按空白切好的词，raw 是命令名之后的原文；
                    // 只读命令用 getTokens()，要原样记录用 getRaw()
                    List<String> tokens = request.getArguments().getTokens();
                    if (tokens.isEmpty()) {
                        return CommandResult.ok("用法：/hello <名字>");
                    }
                    return CommandResult.ok("你好，" + tokens.get(0) + "！");
                });
    }

    /**
     * 停止插件：释放自己申请的资源。
     * <p>
     * 本插件没有申请任何资源，因此这里什么都不用做——处理器注册与事件订阅由框架按 owner 回收。
     * 一旦你起了线程、连接或子进程，<b>必须在这里停掉它们并且必须在 return 之前停完</b>：
     * 本方法返回之后上下文即失效，那时还在跑的注册路径会当场报错。
     */
    @Override
    public void stop() {
        // 没有资源需要释放
    }

    /**
     * 构造工具名片：名称、用途描述、参数的 JSON Schema properties、必填参数名。
     *
     * @return 工具描述符
     */
    private static ToolDescriptor descriptor() {
        // parameters 是 JSON Schema 的 properties 部分，key 为参数名
        Map<String, Object> name = new LinkedHashMap<String, Object>();
        name.put("type", "string");
        name.put("description", "要打招呼的人");

        Map<String, Object> parameters = new LinkedHashMap<String, Object>();
        parameters.put("name", name);

        List<String> required = new ArrayList<String>();
        required.add("name");

        return new ToolDescriptor(TOOL_NAME, "按名字打招呼", parameters, required);
    }
}

读自己的配置

用户在 jellyfish.json 的 plugins.configurations.<pluginId> 下写你的配置，你在插件里这样读： 

public void start(PluginContext context) {
    Map<String, Object> configuration = context.configuration();   // 未配置时是空映射，不是 null
    MyConfig config = MyConfig.from(configuration);
    // …用 config 注册工具 / 命令…
}

final class MyConfig {

    private static final String DEFAULT_DIR = "~/.jellyfish/my-plugin";

    /** 本插件的目录，缺省落在用户主目录下。 */
    private final String myDir;

    private MyConfig(String myDir) {
        this.myDir = myDir;
    }

    /**
     * 从配置段构造：键写错 / 值类型不对 / 缺省值兜底都在这里处理。
     *
     * @param configuration 内核合并好的配置段，不可为 {@code null}
     * @return 配置对象
     */
    static MyConfig from(Map<String, Object> configuration) {
        Object raw = configuration.get("myDir");
        String dir = raw instanceof String ? ((String) raw).trim() : "";
        return new MyConfig(dir.isEmpty() ? DEFAULT_DIR : dir);
    }

    /**
     * 获取本插件目录。
     *
     * @return 目录字符串（<b>可能含未展开的 {@code ~}</b>）
     */
    String myDir() {
        return myDir;
    }
}

五条口径：

口径说明
配置从哪来 plugins.configurations.<pluginId>。${ENV} 插值与双源（全局级 + 项目级）合并已由内核完成，你拿到的就是最终值；插件不允许自行读配置文件
惯例写法 「值对象 + 静态工厂 from(Map)」：键写错、值类型不对、缺省值兜底都在这里处理，插件其余部分只面对强类型字段
~ 不展开 内核只在配置文件自身的路径段上展开 ~（如 config.json 里的 plugins.roots），插件配置值里的 ~ 需要插件自己展开
要 Jackson 就自己带 需要把配置段或 JSON 转成对象时，插件必须自带 Jackson 并以 shade 打进 jar——内核的序列化封装在 jellyfish-infra 里，插件看不到
配置可疑时告警，不阻断 启动时发现配置可疑，用 context.emit(new ConfigWarningEvent(source, message)) 告诉用户，不要阻断启动（TUI 上看得见）。ConfigWarningEvent 有两个构造器：(source, message) 与 (source, message, sessionId)

context.emit(new ConfigWarningEvent(
        "plugins.configurations." + context.pluginId(),

日志：先看「谁没有启动」，再看「为什么」

怎么用
启动日志里与插件有关的有四类行，按严重度从低到高：
  1. 插件被禁用或版本不满足，未启动: pluginId=… requires=…（被 plugins.disabled 或 enabled 名单筛掉）；

加载失败的常见原因清单

逐条对照
  • jar 路径不对：不在 config.json 的 plugins.roots 指向的目录里； 或放在了子目录里（PF4J 只在目录下一层找 plugin.properties）；或忘了重启。
  • plugin.id 冲突：与已装的另一个插件同名，于是注册与回收范围打架； id 里带 :: 时则在描述符体检阶段直接被拒。
  • plugin.class 找不到：类名写错、包名与目录不一致（src/main/java 下的路径与 package 不匹配）， 或漏写这个键（描述符体检会记一条 缺少必需的 plugin.class）。类还需有公开无参构造器。
  • plugin.requires 不是合法 semver 约束：例如带 -SNAPSHOT。 它会被归一为 * 并记一条描述符错误，插件起不来。
  • 被 disabled 排掉：或 plugins.enabled 显式列了名单而你的插件不在其中。 这一条会以 WARN 明说，不要凭猜。
  • DUPLICATE_HANDLER：与内置工具或别的插件抢了同一个「类型 + 路由键」， 在插件启动时当场暴露。要顶替就显式声明 RegisterOptions.override(true)。
  • jar 包里带了 zcd/jellyfish/api 或 org/pf4j 的类： classpath 护栏拒绝，理由会写成「该类由父加载器提供，自带会破坏类型同一性（请改为 provided 依赖）」。
  • 整批加载被带停：不太可能发生（框架刻意不在解析里抛异常）， 真发生时的兜底日志是「插件加载中断，可能有插件未被加载」。

start() 里起了个后台线程，停止时为什么报错

结论
stop() 返回之后上下文即失效，此后任何注册、订阅、发布、投递都当场抛 JellyfishException（fail-closed）。所以「先停下会产生注册的线程与定时器，再 return」是插件这边的责任。

正确的写法：在字段里持有线程 / 执行器 / 连接 / 子进程，stop() 里先置一个停止标志、再 shutdown、再（必要时）awaitTermination，最后才返回；start() 里已经申请到一半的资源要在 catch 里自行释放——因为 start 抛错时框架不保证会调用 stop()。 不要把这条留给下一个插件去做：它没有这个义务，后果只是噪声日志，而噪声会把人引向错误的方向。

我能不能让插件去改会话、起一个新回合

结论
不能，而且这是结构性约束而不是权限问题：PluginContext 里没有那样的入口， subContext 也无法越界。能做的是：submit(PluginAction) 往正在跑的顶层回合投递一个有界动作（没有在途回合就回报 FAILED，不新开回合）， 以及用 present(...) 在回合之外显示点东西（那是唯一被允许的回合外形态）。

为什么要这么严：内核不自己起回合——那会弄坏外壳的在途状态、取消入口、输入互斥与并发写历史四件事。 「插件在回合之外想说话」（定时检查点、长任务完成后汇报、自动提交反思结论）明确不做，需要这类能力的场景请换个设计 （例如把状态写进会话扩展条目，让下一轮的工具去读）。

Jellyfish/docs/constraints.md「插件动作只在顶层回合内」「两个注册式能力面 + 四条插件出边」、Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/plugin/PluginContext.java（submit / present 注释）

插件的配置改了就生效吗？产物拷进去要重启吗

结论
分两件事：改配置段 /reload 生效——/reload 会重读配置并只重启配置段变了的插件； 新增 / 删除 jar、改 plugin.properties 需重启——描述符与插件集合只在启动期确定 （config.json 同样需要重启）。另外：PluginContext 在每次 start 时重建， 描述符里的配置段那一刻才读，因此「重启插件」就等于「拿到新配置」。
Jellyfish/README.md:516-518（/reload 只重启配置段变了的插件）、Jellyfish/README.md:1133-1137（改了配置不生效怎么办）、Jellyfish/jellyfish-infra/src/main/java/zcd/jellyfish/infra/plugin/JellyfishPluginFactory.java（「上下文在每次 start 时重建：描述符里的配置段那一刻才读，因此重启即拿到新配置」）

我想顶替内核自带的 task 工具或某个系统命令

结论
内核自带的系统命令与 task 工具以 owner=core 注册，且先于插件启动。 要顶替它们必须显式声明覆盖： 
context.handle(ToolCallRequest.class, "task", myDescriptor, myHandler,
        RegisterOptions.override(true));
覆盖不是就地替换，而是压在链顶之上：旧登记仍在表里、只是不生效，你的注册一被回收（插件停止、/reload 重启插件） 它就自动重新生效。因此不存在「插件走了，被它顶掉的内核工具永久消失」这种事故。
Jellyfish-Plugins/README.md:1034-1045（显式声明 override）、Jellyfish/docs/constraints.md「覆盖是一条链，不是就地替换」、Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/event/RegisterOptions.java（默认不覆盖）

脚本插件和 Java 插件能不能混着用、互相替换

结论
能共存，但不是同权：机制上同构（同样的注册、owner、回收、生命周期），脚本覆盖的是一份 能力档而不是全部扩展点。因此「先用脚本写、以后想接渲染线程上的扩展点再改成 Java」是可行的演进路径—— 注册与生命周期的写法在两边是同一套概念，需要重写的只是处理器实现。

两个具体差异：脚本侧的工具不能自称只读（read_only / readOnly 参数已移除，清单里写 readOnly 会被判未知键并拒绝加载）；脚本侧的热路径扩展点（request_tuning / aging_strategy）不冷启动， 只声明这两个贡献的脚本永远不会被拉起。

Jellyfish-Plugins/README.md:744-771（脚本与 Java 同构但只覆盖能力档）、Jellyfish-Plugins/examples/scripts/README.md（「没有只读声明这回事」、「热路径点」两节）、Jellyfish-Plugins/jellyfish-script/src/main/resources/script/extension-points.json（hotPath 标记）

关键结论

  1. 插件 = 一份 plugin.properties（jar 根目录）+ 一个 公开无参构造器的 JellyfishPlugin 实现，其余全是可选的。
  2. jellyfish-api 永远 provided，且 shade 的 includes 里绝不能出现它——否则类型同一性被破坏，加载期护栏会直接拒绝整个插件包。
  3. start(PluginContext) 是唯一必需方法；注册窗口是整个存活期，stop() 之后一切注册与发布 fail-closed。
  4. PluginContext 是唯一入口，它刻意不给会话、工作目录、新会话与起回合的能力；回合之外只能「显示」。
  5. 扩展点只有两类：带路由键的 handle（同键唯一）与类型级 contribute（0..N）；24 个可用，脚本侧另有 4 个明确不做。
  6. 工具与命令的代码只写三件东西：描述符（名片）、路由键、处理器；写描述符前先 grep 一遍源码签名——README 的示例在某些构造器上与源码已经不一致。
  7. 配置从 plugins.configurations.<pluginId> 读（合并与插值内核已做）；~ 要自己展开、要 Jackson 就自己 shade、配置可疑就 emit(ConfigWarningEvent) 而不阻断启动。
  8. 改内核后跑那五条命令，第 0 步不能省、必须 clean、三个 -P*-it 一个都不能漏。
