01 Jellyfish 是什么

这一页不教你敲命令，而是先把「它由哪些部件组成、能力从哪来、什么时候别用它」讲清楚。 搞明白了这三件事，后面 15 页里那些「为什么没装插件就不能用」「为什么插件要重启」的疑问会自己消失。

学习目标

  • 用一句话说出 Jellyfish 的定位，并说出它提供的三种形态；
  • 说清三个仓库各自负责什么，以及依赖方向为什么是单向的；
  • 判断「我需要装哪些插件」——并知道不装插件会具体缺什么；
  • 在 -cli / -tui / -server 之间按使用场景选出合适的那个；
  • 说出内核与集成分支的技术栈选型与版本号，并知道去哪一行核对；
  • 认清内核的四条边界（单主体、无 GUI、无沙箱、Windows 未验证），知道哪种场景该换方案。

Jellyfish 是什么

一句话定位：Jellyfish 是一个用 Java 1.8 编写的轻量级 AI Agent 工具—— 单次问答、交互式终端界面、HTTP 服务三种形态共享同一个内核，能力通过 PF4J 插件扩展。

它要解决的其实是三件不同的事，而这三件事在命令行工具里经常被硬塞进同一个入口。Jellyfish 的做法是 做成三种形态，但三种形态共享同一个入口与同一份装配，只靠启动参数区分； 一个参数都不带直接运行时等价于 -tui。

你想做的事形态启动方式结果落在哪
问一次、拿一次结果，不需要来回聊（脚本、管道、CI） -cli 单次调用 -cli -p "总结这个项目" 回答与命令结果走 stdout，诊断与工具进度走 stderr，进程结束即退出
想跟它来回聊、看工具轨迹、在现场点鼠标审批 -tui 交互式终端界面（TamboUI） -tui（裸跑 jellyfish 等价） 终端里的消息区 + 输入框 + 状态栏
想让它当服务，被别的程序（你的前端、你的后端）调用 -server HTTP 服务（Undertow） -server 9096 REST + SSE 接口，会话按 id 寻址

兜底只此一处

只有「一个参数都不带」才默认 -tui。一旦带了任何参数，模式就必须显式给： jellyfish --verbose 一样报「请指定启动模式」并退 2。 这样「敲了没反应」和「悄悄挂在等 stdin」都不会发生。

三个仓库各是什么、怎么配合

这套工具被拆成三个 Git 仓库，它们在同一个工作目录并列存在。分工不是「核心 / 周边」，而是 内核只保留机制与契约，能力全部另外交付——所以「我该不该拉插件仓库」这个问题， 答案几乎总是「要」。

仓库角色你要不要它坐标 / 形态
Jellyfish 内核：三种外壳（-cli / -tui / -server）、装配、扩展点与插件运行时、插件 SPI。工具、命令、权限模式等能力都不在内核里 必然要。它产出唯一的可执行入口 jellyfish-cli-0.1.1.jar 父 POM 与 jellyfish-api / -infra / -core / -di 发中央仓库，坐标 io.github.zcd0831:jellyfish:0.1.1
Jellyfish-Plugins 官方插件集（13 个：11 个 Java 插件 + 2 个脚本桥接插件）+ 插件开发教程。每个插件是独立打包的 PF4J jar 想读文件 / 跑命令 / 存会话就必须装，否则内核近乎空转 独立 Maven reactor；插件本身不发布到中央仓库，按 cpPlugins.sh 装进内核的插件目录
Jellyfish-Spring-Boot-Starter 把内核搬进已有的 Spring Boot 容器，并补上内核没有的「用户」维度（带归属校验的多用户门面） 只有当你要在自己的 Java 服务里用 agent 才需要 io.github.zcd0831:jellyfish-spring-boot-starter:0.1.1，依赖内核装配模块 jellyfish-di:0.1.1

图 1-2　依赖方向单向：插件只认 jellyfish-api 且是 provided，Starter 只认 jellyfish-di，两者都不反向依赖内核实现

为什么依赖是单向的（这不是洁癖，是交付方式）
  • 插件对 jellyfish-api 是 provided：因此插件可以在内核之外单独构建、单独发版，换内核版本不用重编插件，插件也可以来自第三方。
  • Starter 只依赖 jellyfish-di：它用内核的 JellyfishAssembler 装配，没有在 Spring 里重建内核组件——所以它「不改内核」，只换一种装配方式，也不提供任何 HTTP 接口（接口由你写）。
  • 装配知识只写一份：CLI 用 Dagger 组件，不用 Dagger 的容器用 JellyfishAssembler，两种装法交付同一个 JellyfishRuntime 契约。
版本号都是 0.1.1，但没有兼容矩阵

三个仓库当前都停在 0.1.1，但没有任何文档声明三者之间的版本兼容矩阵。 凡涉及「哪个内核版本配哪个插件 / Starter 版本」，一律按 【版本对应关系需查阅各自 README】 处理， 本套文档不做推测。

能力从哪来：内核只有机制，能力全在插件

这是整套设计里最需要先接受的一条：内核提供的是「怎么把能力接进来」，不是能力本身。 内核交付工具调用框架（权限判定 → 路由 → 截断）、ReAct 循环、提示词组装、压缩机制、 子代理调度、命令域与三种外壳；而文件读写、跑命令、会话持久化、待办、MCP、编排、plan 模式 这些「能干活」的东西，全在插件仓库里。

内核自带的唯一工具：task（子代理委派）

是什么
把一段自足的子任务委派给另一个 agent 去做，只拿回它的最终结论——噪音（读了多少文件、 试了多少次）留在那边。这是内核唯一自带的工具，其余工具都由插件注册。
怎么用
不需要写代码：在 agents.json 里给目标 agent 标上 delegatable: true， 它才会出现在模型看到的可用类型清单里；然后正常提问，由模型决定要不要委派。

配置

字段类型必填默认值含义示例
agents.<agentId>.delegatable boolean 选填 false 这个 agent 能不能被 task 当作委派目标；不配就不出现在模型看到的可用类型清单里 true
agents.<agentId>.model string 选填 未配即回落全局默认模型：models.json 的 defaultProvider / defaultModel 子代理自己的偏好模型，不继承主会话的模型；写法与 /model 参数一致 openai/gpt-4o-mini
agents.<agentId>.permissions.allowedTools string[] 选填 未写 = 不限制 同时决定子代理能看到哪些工具（只随委派生效，主会话不受影响） ["read_file", "list_dir", "grep_files"]

完整示例

{
  "agents": {
    "scout": {
      "description": "只读摸清相关代码，只回传结论",
      "delegatable": true,
      "model": "openai/gpt-4o-mini",
      "permissions": {
        "allowedTools": ["read_file", "list_dir", "grep_files"]
      }
    }
  }
}

常见问题

  • 为什么模型从不用它？目标 agent 没写 delegatable: true——它不会出现在模型看到的清单里。
  • 为什么子代理答得答非所问？子代理与主会话除了那段任务之外相互隔离（看不到对话历史、你看过哪些文件），任务描述必须自足。
  • 子代理花掉的 token 算谁的？计入父会话（/usage 看得到），但子代理的会话不留痕（不落盘、不进 /session 列表）。

/reload 生效——题目里说的是 agents.json 的内容改动； 插件 jar 的增删另说（见 02 安装）。

不装插件会缺什么：别把「设计」当成「装坏了」
  • 工具几乎全无：内核只注册 task，而 task 还要求你对某个 agent 配了 delegatable: true。因此「只装内核」时，模型既读不了文件也跑不了命令——你看到的是配置现场，不是故障。
  • 会话不落盘：会话持久化在 jellyfish-plugin-session-file。 装了它，--session / /resume / /session 才有内容可恢复。
  • 压缩整体不可用：压缩是插件能力、内核只提供机制，没有策略插件即整体不可用，不回退内置； /compact 会直接告诉你缺什么。
  • 命令仍然能用：11 个系统命令来自内核，不需要模型也不需要插件； /compact 是唯一的例外（依赖压缩策略插件）。

三种形态分别适合谁

选形态看两件事：有没有人在场（决定审批和提问能不能成立）和结果要交给谁 （人看屏幕，还是程序拿走）。参数细节、按键、退出码在 04 三种运行模式 一页里， 这里只给选择依据。

形态适合谁 / 什么场景适合的表现不适合的后果
-cli 脚本、管道、CI、一次性问答；想把它塞进别的自动化流程 输入走 -p 或 stdin，结果在 stdout，退出码可判；> 重定向安全 没有审批者：askTools 里的工具一律按拒绝处理；ask_user 也不挂答复者，立刻返回一句「当前外壳没有交互界面」
-tui 你本人坐在终端前，要来回聊、要现场看工具轨迹、要人工审批 审批弹框（↑/↓ 选、Enter 确认、Esc 拒绝并中断回合）；Ctrl+T 看思考、Ctrl+E 看工具参数 需要可交互终端；管道 / CI / 被重定向的 shell / IDE 的非真终端控制台都会退 3
-server 让别的程序驱动 agent：自己的前端、内部平台、需要把会话按 id 寻址的服务端程序 REST + SSE；审批走 POST /sessions/{id}/approvals/{requestId}，提问走 POST /sessions/{id}/asks/{requestId} 是单主体模型：一个 API key 就是一个信任域，别拿它做多租户（见下文红线）
选不出来时的默认答案

有人在场、要动手改文件：-tui。无人值守、只要一个答案：-cli -p。 要给别的程序调：-server；但如果那个程序本身就是个 Spring Boot 应用， 先看 14 整合到 Spring Boot——starter 直接给编程式 API， 比你自己起一个 HTTP 外壳再调它更短。

什么场景不该用它

下面这些不是「配置一下就能解决」的问题，而是内核的边界。踩上去会拿到错误的安全感， 所以放在入门页就说明白。

红线一：不要拿 -server 当多租户服务

服务端是单主体模型：一个 API key 就是一个信任域，内核不认识「哪个调用方」。 更具体地说，内核没有「用户」概念——Session 无 owner 字段、 SessionManager.all() 返回全进程会话、插件也不做用户隔离。 按调用方区分的会话归属与审批归属只存在于 Spring starter 的 user 包里 （SessionOwnerStore / ApprovalGateway，那里有 userId 概念）。

而且命令域与对话域同权：POST /sessions/{id}/commands 能执行 /reload 等系统命令， 因此密钥泄露等于整机权限泄露。要做按用户隔离，请改用 14 整合到 Spring Boot 的护栏，不要在本服务前面自己加一层代理。

红线二：涉密或多用户环境里不要随手装 shell / mcp / 脚本桥接

shell 插件没有沙箱：命令以本进程的权限运行，能读写你这个用户的任意文件； 它不做目录围栏（围栏可被 cd /、绝对路径、sh -c 嵌套绕过， 真正的边界是审批加白名单），而且Windows 未验证（非 POSIX 平台映射成 cmd.exe /c， 但没有在真机上跑过）。shell、mcp、python / node 桥接 都不做用户隔离，装进多租户进程等于把所有用户放进同一个权限面。

边界三：它是终端工具，不是 GUI，也不是文件系统沙箱
  • 没有桌面 / 图形界面：内核仓库的 7 个模块里只有终端与 HTTP 两种呈现方式 （jellyfish-tui / jellyfish-server / jellyfish-cli）， 最接近「客户端」的 -tui 需要可交互终端——stdin 或 stdout 被重定向也算没有， 此时退 3（这是有意的：否则 TamboUI 会永久挂住）。要图形界面得自己接 -server 或 starter。
  • 文件工具的路径闸门不是沙箱：pathPolicy 管的是本插件那几个文件工具的 path 参数，管不了 shell 命令里出现的路径，也管不了 MCP 工具。
  • 权限按 agentId 全局共享：同一个 agent 对不同用户只能有同一套权限； 要区分角色就为每个角色定义一个 agentId，建会话时按角色选。
那什么时候该用它

反过来看就清楚了：单主体、你已经信任这台机器和你自己的密钥的场景—— 本机开发助手、代码库探索、把一段重复的问答流程写进脚本、给内部工具加一个「能读文件能跑命令」的 agent。 这些正是它设计时瞄的目标。

关键结论

  1. Jellyfish 的定位是「Java 1.8 的轻量级 AI Agent 工具」：三种形态（-cli / -tui / -server）共享同一个入口、同一份装配、同一个内核，只靠启动参数区分；只有「一个参数都不带」才默认 -tui。
  2. 三个仓库是单向依赖：插件对 jellyfish-api 是 provided（可独立构建发版），Starter 只依赖 jellyfish-di（复用内核装配，不在 Spring 里重建组件）。
  3. 内核只有机制，能力全在插件：内核自带的工具只有 task（还需 delegatable: true 的 agent 才用得上），文件工具、shell、会话持久化、压缩策略全在 Jellyfish-Plugins；不装插件不是故障，是设计。
  4. 选形态看「有没有人在场」：-cli 无审批者（askTools 一律按拒绝处理），-tui 需要真终端，-server 给自己写客户端用。
  5. 技术栈的硬前提是 JDK 1.8（不要用 Java 9+ 的 API 或语法），插件运行时 PF4J 3.14.1，TUI 是 TamboUI SNAPSHOT，HTTP 外壳是 undertow-core 2.2.40.Final，三个仓库版本号都是 0.1.1——但没有兼容矩阵，涉版本问题一律 【版本对应关系需查阅各自 README】。
  6. 四条边界要记住：单主体（一个 key 一个信任域、Session 无 owner 字段，别做多租户）、shell 无沙箱、Windows 未验证、无 GUI（只有终端与 HTTP 两种呈现）。
  7. 本页所有命令、字段、类名都标了 文件:行号 出处；查不到的会写成 【待确认】，读到时请先去仓库核对再动手。
