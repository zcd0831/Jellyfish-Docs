15 故障排查

这一页是「卡住了就来翻」的手册：每条都按现象 → 原因 → 解决写，共 46 条， 覆盖启动与退出码、模型与配置、插件、审批与权限、上下文与会话、TUI 显示、Server 接口、Spring Boot 整合八类。 每条的原因都指出「内核为什么这样设计」，解决都给出可照抄的命令或配置。

学习目标

  • 看到报错时先按退出码（2 / 3 / 4 / 6 / 7）判断故障出在哪一步；
  • 能解释「命令能用但一发对话就没模型」「-cli 下写类工具一律被拒」这两类最高频的现象；
  • 会区分「配置改了没反应」的四种情形：改错文件、改的是不热更新的文件、项目级没被信任、键名拼错被静默忽略；
  • 能用 /mcp、/usage、TUI 文件日志这三个入口拿到排错所需的一手线索；
  • 知道 Server 外壳上 401 / 403 / 409 / 415 各自代表什么，以及它们分别该改什么；
  • 在 Spring Boot 整合里避开重复构造内核对象图、Jackson 版本、启动顺序三类冲突；
  • 知道 0.1.1 有几处会改变既有行为的变更，升级前先对照一遍。

A. 安装与启动

A1　-tui 一启动就退出 3

现象
敲下 -tui，界面没出来，进程立刻以退出码 3 结束（stdin 或 stdout 被重定向也算）。
原因
TUI 需要可交互终端（备用屏 + raw 模式）。在管道、CI、被重定向的 shell 或 IDE 的非真终端控制台里 一律立即报错退出——这是有意的，否则 TamboUI 会永久挂住。
解决
  • 在真实终端里运行：java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -tui；
  • 要在 IDEA 里调试，在真实终端启动、用远程调试挂接（IDEA 内置 Terminal 标签页是真 PTY，也可以直接在那里跑）：
mvn -o package -DskipTests
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 \
     -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -tui
  • 确认终端明明可用却被拦下时，用 -Djellyfish.tui.skipTerminalCheck=true 跳过检查；
  • 只是要跑一次问答，就别用 TUI：-cli -p "…" 不需要终端。

A2　裸跑 jellyfish 没有交互却挂住或退 3

现象
不带任何参数运行，脚本 / CI 里看起来「挂住」或直接退 3。
原因
一个参数都不带 = -tui（交互界面是最常用的入口）。因此它同样需要可交互终端， 在管道 / CI 里一样退 3。
解决
  • 要单次问答就显式写 -cli：-cli -p "总结一下这个项目"；
  • 要从管道喂输入，-cli 缺省从 stdin 读到 EOF：
echo "/help" | java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli

A3　带了参数却报「请指定启动模式」并退 2

现象
例如 jellyfish --verbose，报用法错误并退 2。
原因
兜底只认「一个参数都不带」这一处。只要带了任何参数，模式就必须显式给—— 这样「敲了没反应」和「悄悄挂在等 stdin」都不会发生。
解决
  • 补上模式旗标：-cli / -tui / -server 三选一；
  • 注意 --agent / --model / -p / --show-thinking / --show-tool-args 只归 -cli：-tui / -server 带上它们会判用法错误退 2（拒绝而不是静默忽略）。

A4　找不到构建产物 / 命令里的路径写错

现象
java -jar …jar 报 Unable to access jarfile，或提示找不到 jellyfish-cli/target/…。
原因
构建产物只有一个可执行 fat jar： jellyfish-cli/target/jellyfish-cli-0.1.1.jar。三种模式都用它启动； 相对路径是按当前工作目录解析的，所以在别的目录里敲同一条命令就会失败。
解决
  • 从仓库根跑构建：mvn -o clean package（-DskipTests 可跳测）；
  • 嫌路径长就设别名，用绝对路径：
alias jellyfish='java -jar /绝对路径/jellyfish-cli/target/jellyfish-cli-0.1.1.jar'
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "/help"   # 在仓库根执行
  • 没有「安装目录」这回事：内核就那一个 fat jar，只有插件需要拷进扫描目录。

A5　Maven 构建失败，或插件编译看不到内核改动

现象
插件仓库构建报找不到新版 jellyfish-api 的符号；或内核明明改了，插件这边编译却看不见。
原因
Jellyfish-Plugins 是一个独立 Maven reactor，它的 jellyfish-api 来自 本地 Maven 仓库，而不是相邻目录的源码。此外增量编译会复用按旧 jellyfish-api 编出的 target/，把编译问题伪装成运行期问题 （实例：内核给 SessionSnapshot 加字段之后，不带 clean 报的是 11 条 NoSuchMethodError）。
解决
  • 按顺序跑，第 0 步不能省：
(cd ../Jellyfish && mvn -q install -DskipTests)   # 0. 先把内核装进本地仓库
mvn -q clean package                              # 1. 必须 clean
mvn -q -Pshell-it test                             # 2. 三个端到端 profile
mvn -q -Pmcp-it test
mvn -q -Pscript-it test
  • 内核自身常用命令：mvn -q compile（只编译）、mvn -q package -DskipTests（只打包）、mvn -q test（全量单测）；
  • mvn test / mvn package 不跑 *IT，坏掉的端到端不会被它们发现，所以三个 -P*-it 一个都不能漏。

B. 模型与配置

B1　一发对话就提示没有可用模型

现象
/help、/status 都能用，但一问它就提示没有可用模型。
原因
这是正常现象而不是故障：命令域不经过模型，而对话必须有一个 models.json 里配好的 provider / 模型。另外 apiKey 写成 ${OPENAI_API_KEY} 时， 环境变量没设会让整份配置加载失败（见 B2），表现也是「没有可用模型」。
解决
  • 先建一份最小 models.json（放全局级 ~/.jellyfish/，或项目根 .jellyfish/ 并显式信任）：
{
  "defaultProvider": "openai",
  "defaultModel": "gpt-4o",
  "providers": {
    "openai": {
      "type": "openai",
      "apiKey": "${OPENAI_API_KEY}",
      "models": [{ "id": "gpt-4o", "name": "gpt-4o", "contextLength": 128000, "maxOutputTokens": 4096 }]
    }
  }
}
  • 再把密钥放进环境变量（不要写进配置文件）：export OPENAI_API_KEY=sk-***；
  • 验证顺序：-cli -p "/help" 先确认 jar 起得来（不需要模型），再加配置。

B2　${VAR} 缺失导致整份配置加载失败

现象
配了 apiKey 之后启动失败（退 3），或原本能用的配置忽然整份失效。
原因
配置里的字符串值支持 ${VAR} 插值，但缺失是硬失败——不是「留空」而是整份配置加载不了。 插件配置段里的 ${ENV} 同理，甚至更早：整个进程启动即失败（见 C5）。
解决
  • 确认变量真的存在且被导出：printenv OPENAI_API_KEY；
  • 想容错就写默认值："apiKey": "${OPENAI_API_KEY:-sk-placeholder}"；
  • 要字面量 ${...} 就转义：\${VAR}；注意 JSON 的 key 不参与插值，只有字符串值参与。

B3　vendorBody / vendorHeaders 里键名拼错，静默无效

现象
配了一段厂商私有字段（例如思考开关），运行时什么变化都没有，也没有任何报错。
原因
vendorBody 的键由厂商定义，内核只搬运、不解释、不校验：未知键静默忽略， 键名大小写敏感，厂商多半直接忽略它不认识的字段。所以「拼错」与「厂商不支持」在表面上完全一样。
解决
  • 把日志级别调低（--verbose 或 -Djellyfish.log.level=DEBUG）， vendorBody 生效时会打一行实际下发的键名（不打值，值可能含凭据）；
  • 键名逐字抄厂商文档、注意大小写；
  • 顺带记住 vendorHeaders 里有六个头会被丢弃并告警：Content-Type Accept Host Content-Length Accept-Encoding Range；不合规条目的日志只记头名。

B4　配了思考强度却没反应

现象
vendorBody 里写了思考强度，模型行为没变化，或者界面上一片空白看不到思考文本。
原因
四类高频原因，逐个排查：
  • ① 键名写错，或用了这个模型不认的档位：前者多半静默无效，后者可能直接 400；
  • ② 配置其实生效了，是采样参数被思考模式吃掉：DeepSeek 思考模式下 temperature 与两个惩罚项完全无效， 而 top_p 反过来只在思考模式下生效、且被夹到 0.95–1.0；
  • ③ 配置生效了但界面看不到思考文本：要厂商侧与外壳侧两边都开——Claude 要 display: "summarized"、 Gemini 要 includeThoughts: true；外壳侧 -cli 要 --show-thinking、TUI 要 Ctrl+T / /thinking；
  • ④ Claude 代际不匹配：老代际的 thinking.budget_tokens 用在已升级的新代际模型上会直接 400。
解决
{
  "vendorBody": { "thinking": { "type": "adaptive" }, "output_config": { "effort": "high" } }
}
  • 各家的键名与取值：DeepSeek 用 thinking.type + reasoning_effort； Claude 用 thinking.type + output_config.effort； Gemini 用 generationConfig.thinkingConfig.thinkingLevel；
  • 先按 B3 的办法确认键真的发出去了，再按 ②③④ 逐条排除。

B5　maxTokensField 用错，报 400 Unsupported parameter

现象
用 gpt-5 或 o 系模型对话，直接 400，错误里提到 max_tokens 不被支持。
原因
maxTokensField 决定「输出上限写在请求体的哪个字段名里」： OpenAI 的推理模型（o 系）与 gpt-5 及之后只认 max_completion_tokens， 用 max_tokens 就是一次 Unsupported parameter； DeepSeek / MiniMax / OpenRouter 这类兼容端点只认 max_tokens。它只有模型级， 因为同一个端点下两个模型认的字段名就不一样。
解决
{
  "models": [{
    "id": "gpt-5", "name": "gpt-5", "contextLength": 400000, "maxOutputTokens": 8192,
    "maxTokensField": "max_completion_tokens"
  }]
}
  • 写别的值会在加载时告警并回退到 max_tokens——所以「写错」的表现可能不是 400 而是「默认字段」；
  • Claude 老代际另有一坑：thinking.budget_tokens 必须小于当次下发的 max_tokens （未配 maxOutputTokens 时内核发的是 4096），而报错只提 max_tokens，不会提 maxOutputTokens。

B6　温度写了没反应

现象
把 sampling.temperature 从 0.2 改成 1.0，输出风格没变化。
原因
采样参数与思考模式互相挑食：DeepSeek 思考模式下 temperature 与两个惩罚项完全无效（不报错）； OpenAI 旧 GPT-5 系对非缺省温度直接 400，gpt-5.1 之后只在 reasoning_effort 为 none 时才接受； Claude 新代际不再接受 temperature / top_p / top_k（设非缺省值 400）。 另外「没写」与「写了 0」是两回事：没写就不下发，写了 0 就发 0。
解决
  • 先看模型是不是在思考模式下运行，是就换别的调参手段（改提示词 / 换档位），别指望温度；
  • Claude 这类新代际要按 model 级 sampling 分开配，不要指望 provider 级基线对所有模型都成立；
  • 温度上限各家不同（OpenAI 系 0–2、Anthropic 0–1），内核只校验它确定的那部分，越界由厂商拒。

B7　改了配置却不生效

现象
改了 models.json / agents.json / jellyfish.json，行为没变。
原因
「不生效」有四种完全不同的成因，先分清是哪一种：
  • 改的文件不参与热更新：config.json 只在 classpath 根、不参与双源、也不热更新；
  • 没敲 /reload：三份内容类配置的改动由 /reload 生效（重读配置、重建模型 / agent 索引， 并只重启配置段变了的插件）；
  • 项目级配置根本没加载：<工作目录>/.jellyfish/*.json 默认不加载， 而且日志里会有一条配置告警（「项目级配置未信任」）；
  • 键名拼错了：0.1.1 起读取配置时会比对字段名，发现内核不认识的字段会发一条 ConfigWarningEvent 并打 WARN （带文件路径与字段名）。但它只比字段名、只认内核自己那几段——vendorBody 与逐插件配置段这类自由格式一概不看； 数值写错（react 段、provider 的 sampling 段）也会进这个事件面。
解决
  • 内容类改动：敲 /reload；
  • 改 config.json、新增 / 删除插件 jar：重启进程（扫描目录与插件集合只在启动期确定）；
  • 项目级配置：-cli / -server 启动时加 --trust-project-config（仅本次进程有效、不落盘）； -tui 在启动确认框里选 y（加载并记住）或 o（仅本次）。 注意信任的单位是文件绝对路径 + 内容指纹，文件内容一变（比如 pull 下来一份新配置）信任立即失效；
  • 还想连 Spring 接入方那种「不依赖工作目录」的写法，就用 classpath: 前缀把配置放进自己的 resources—— 它不受这道闸管辖。

B8　baseUrl 配了却被上游 301 / 302

现象
请求失败，错误信息里写着「重定向被禁止」，并给出目标主机与路径。
原因
出站请求不跟随重定向，而且这是刻意的：Claude 的密钥走 x-api-key、 Gemini 走 x-goog-api-key，而 OkHttp 在跨主机重定向时只剥 Authorization—— 跟随重定向就等于允许上游把我们某个密钥头送到任意主机去。
解决
  • 把 baseUrl 填成最终地址（不要写会跳转的旧域名或短链）；
  • 错误信息里只给目标主机与路径，不复制 Location 的 query（那里可能挂着一次性凭据）， 所以要去厂商控制台自己确认最终端点；
  • 改完敲 /reload 即可生效。

C. 插件

C1　装了插件但 /help 里没有它的命令

现象
jar 已经拷进去了，重启后 /help 里看不到该插件的命令或工具。
原因
四种常见成因：
  • jar 不在 config.json 的 plugins.roots 指向的目录里（缺省 ~/.jellyfish/plugins/）；
  • 目录层级不对：PF4J 只在目录下一层找 plugin.properties（平铺 jar，或「一插件一子目录 + plugin.properties」）；
  • 被 jellyfish.json 的 plugins.disabled 排掉了（同一个 pluginId 同时在启用与禁用名单里时按禁用处理，并发一条配置告警）；
  • 只是没重启：新增 / 删除 jar 必须重启（扫描目录与插件集合只在启动期确定）。
解决
ls -l ~/.jellyfish/plugins/          # 确认 jar 在扫描目录、且布局是「平铺」或「一层子目录」
# 装官方插件：在 Jellyfish-Plugins 里构建后
./cpPlugins.sh                        # 把 target/*.jar 拷进扫描目录（缺省 ~/.jellyfish/plugins/）

C2　插件加载失败，但内核起来了

现象
进程正常启动、命令能用，可就是少了某个插件的能力，屏幕上没有任何明确报错。
原因
插件加载失败不会让内核起不来，所以原因只出现在启动日志里。常见成因： plugin.class 找不到（必须有一个公开无参构造器）、plugin.properties 缺失或位置不对、 plugin.id 冲突（plugin.id 是插件身份、同时也是注册表的 owner）、 两个插件抢同一个注册键导致插件启动时以 DUPLICATE_HANDLER 当场暴露、 或 plugin.id 里含命名空间分隔符（plugin.id 含分隔符的插件在描述符体检阶段被拒）。
解决
  • 在启动日志里找该插件的加载行（TUI 看 F3 说的日志文件，-cli 看 stderr）；
  • plugin.properties 必须放在 jar 根目录，PF4J 按名查找：
plugin.id=my-plugin
plugin.class=com.example.MyPlugin
plugin.version=1.0.0
plugin.requires=*
  • 确认 plugin.id 全局唯一、且不含命名空间分隔符；
  • 一次只有一个插件出问题就先把别的 jar 挪走复现，DUPLICATE_HANDLER 这类冲突只有两个插件同时在才出现。
  • plugin.requires 这一档分两半看：内核目前不声明系统版本（PF4J 的缺省值会让它直接跳过这条校验）， 所以合法约束（含 *）一律放行；而非法表达式（例如带 -SNAPSHOT）不会被静默忽略—— 描述符解析期先把它归一为 * 并记一条描述符错误（plugin.requires 不是合法的 semver 约束: …）， 随后在描述符体检阶段该插件不启动、标记为 FAILED，启动日志里是 插件未通过描述符体检，将不启动: pluginId=… reason=描述符存在问题: …。

C3　类冲突 / NoSuchMethodError

现象
插件跑起来后报 NoSuchMethodError、ClassCastException，或某个新字段静默丢失。
原因
PF4J 的插件类加载器是子优先的：插件自带 jellyfish-api 的类会遮蔽父加载器里的同名类， 于是插件拿到的值类型不是运行期内核那一份。这也是「jellyfish-api 必须 provided、 shade 的 includes 里绝不能出现 jellyfish-api」的原因。
解决
<!-- 内核契约必须 provided -->
<dependency>
  <groupId>io.github.zcd0831</groupId>
  <artifactId>jellyfish-api</artifactId>
  <version>0.1.1</version>
  <scope>provided</scope>
</dependency>
  • 有私有依赖（Jackson、commons-exec 之类）时才配 shade，把它们打进插件包，且 includes 里不要写 jellyfish-api；
  • 升级内核后必须 clean，见 A5；
  • 插件不可能自己造 TamboUI 组件——子优先类加载器会让 Element 不是同一个 Class，这是已知边界而不是配置问题。

C4　改了插件配置段要重启吗

现象
改了 jellyfish.json 里某个插件的配置（例如 pathPolicy、readOnlyTools），不确定要不要重启。
原因
插件配置段的变化由 /reload 按差异重启对应插件——只重启配置段变了的那几个，而不是全部。
解决
  • 只改配置段：敲 /reload 即可，不用重启进程；
  • 改 config.json（含 plugins.roots）、新增 / 删除插件 jar：必须重启；
  • 在 Spring Boot 接入方那边更简单：starter 不提供 /reload 的入口，一律重启最省心；
  • 注意 /reload 会终止正在跑的命令（热部署与内核关闭都会杀掉在途子进程），别在长命令跑到一半时敲它。

C5　脚本插件报「环境变量未设置」

现象
配了 Python / Node 脚本插件后，整个进程启动即失败，提示环境变量未设置。
原因
配置段里写了 ${SOME_KEY} 而环境变量没设，是硬失败——整个进程启动即失败， 不是「这一项留空」。而且脚本进程的环境变量是严格白名单（只透传解释器运行与依赖解析必需的那几个）， 因此 API key 不能靠环境变量直接传给脚本。
解决
  • 确实要用的密钥才写 ${...}，并保证它总是已设；不需要就干脆不写；
  • 密钥要走脚本自己的配置段（桥接层只按脚本 id 切片转发、不解释里面的键，字符串值里的 ${ENV} 照常插值， 与 Java 插件是同一条密钥通道）：
{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-python": {
        "scripts": { "<脚本目录名>": { "apiKey": "${SOME_KEY}" } }
      }
    }
  }
}
  • 写错脚本 id（拼写 / 大小写）会在启动时告警；scripts 段写成非对象会当场报错。

C6　MCP server 连不上

现象
配好的 MCP server 的工具用不了，或干脆看不到 mcp__… 工具。
原因
连不上不会让内核起不来，所以要看状态而不是看启动失败。断开会按固定退避自动重连： 1 秒起、每次翻倍、封顶 60 秒、共 6 次（合计约一分钟）；重连期间该 server 的工具先被摘掉 （留着它们，模型会继续调用一批每次都以「未连接」收场的工具）；约一分钟后仍连不上就停在「失败」。
解决
  • 敲 /mcp 看每个 server 的连接状态、工具数与失败原因——那是唯一的线索， 上面能看到「重连中（第 N 次尝试）」；
  • 重连退避用尽后，它写明 /reload 可重试（每次尝试都可能真的起一遍进程，npx 还会拉网， 所以不能一直重试）；
  • 先在终端里手动跑一遍该 server 的启动命令，确认可执行文件与参数没问题；
  • 启动日志里的参数值会遮蔽（--token sk-*** 打成 ***），但 --path /tmp 这类会照旧打印，排查起不来时正是要看它；
  • 写类 MCP 工具在 -cli / -server 下实际不可用（askWriteTools 缺省 true，而 ASK 等于拒绝）。

D. 审批与权限

D1　-cli / -server 下写类工具总被拒

现象
同一份配置在 -tui 里能写文件、能跑命令，切到 -cli 或 -server 后一律失败。
原因
那两个外壳没有审批者，而审批是 fail-closed 的：ASK 就是拒绝（绝不静默放行）。 -tui / -server 会挂审批者，-cli 不挂； -server 只是把审批显式搬到了 HTTP 层（有人接才是有人）。
解决
  • 无人值守下跑：把该工具移出 askTools，或为 shell 配 commandPolicy.trustedCommands；
  • 要人工确认：用 -tui，或在 -server 上把 POST /sessions/{id}/approvals/{requestId} 接起来；
  • 记住免审批的放行口只有两个——被分类器判为只读的命令，以及 trustedCommands 里的命令（白名单非空时还得先过白名单）。

D2　审批框一直不出来 / 卡住

现象
回合停在某一步不动，界面上没有审批框，也没有报错。
原因
先排除一个误判：TUI 里的审批浮层优先级最高，不会被别的浮层压住——所以「框不出来」 不是浮层互相遮挡的问题。真正会「永远回不来」的是另外两种情形：你其实在 -cli 下 （那里没有审批者，需要审批的调用按拒绝处理，但表现可能只是静默失败）；或者 permission.approvalTimeoutSeconds 被写成了 0——那表示永不超时， 于是「等不到人就拒绝」变成「等不到人就一直卡住」，而且占住一条 react 线程。
解决
  • 确认外壳：-cli 下永远不会弹审批框，请在 -tui 里复现；
  • 检查 jellyfish.json：
{ "permission": { "approvalTimeoutSeconds": 120 } }
  • 写 0 是刻意的「无限等」，代价是那条 react 线程在有人裁决前不会自愈 （react 池只有 8 条线程 = 并发顶层回合上限）；配 0 时启动会有一条 ConfigWarningEvent（来源 permission）说明这件事。负数按非法回退 120 秒并告警， 超过 3600 秒的值照旧生效但也会告警；
  • 卡住时按 Esc：它是「拒绝 + 中断回合」，不是只拒绝。外壳退出（通道关闭）也会把等待放开；
  • 接入方在客户端断开时应当主动拒绝待审项，而不是放着等满 120 秒。

D3　把命令加进 allowedCommands 却还是要审批

现象
allowedCommands 里写了 mvn test，每次调用仍然弹批准框。
原因
这是最容易踩的一处：allowedCommands 是准入白名单， 只回答「能不能跑」，不解除审批。免审批是另一张表 commandPolicy.trustedCommands。
解决
{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-shell": {
        "allowedCommands": ["mvn test"],
        "commandPolicy": { "trustedCommands": ["mvn test"] }
      }
    }
  }
}
  • 粒度一致（支持 git status 这种两 token 形式；单 token 覆盖该命令的全部子命令）， 且要求所有段都命中才免审批：trustedCommands: ["mvn test"] 不该把 mvn test; rm -rf ~/x 一并免审批；
  • 拒绝形状（rm -rf /、mkfs、dd of=/dev/）排在可信表之前， 把 rm 写进可信表也拦得住；
  • 「允许跑但每次都要我批准」是能写出来的姿态：只配白名单、不配可信表即可；
  • 不想再一条条维护名单时，可以写整条 *：allowedCommands: ["*"] 表示准入不再拦任何命令， 再配 trustedCommands: ["*"] 就是一律免审批（readOnlyCommands: ["*"] 则是「一律按只读放行」）。 它只解除自己所在的那一道门（拒绝形状照旧拒），写作半个通配（如 git *）没有这个效果——那会被当成字面量、永不命中，解析时会发告警；
  • 注意 commandPolicy.enabled=false 只关掉分类器这个便利机制，白名单、可信表、拒绝形状照旧生效。

D4　工作目录外写文件失败

现象
write_file / edit_file 写到工作目录之外时失败，或提示需要审批。
原因
jellyfish-plugin-tools 有一道路径闸门 pathPolicy：文件工具在允许的路径之外会被升级为人工审批或直接拒绝， 粒度是「工具名 + 路径」而不只是工具名。而 write 方向不配就按缺省（只允许工作目录、范围外要审批）； ask 在没有审批界面的外壳里等于拒绝——-cli 不挂审批通道，工作目录外的写在那里会直接失败。
解决
{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-tools": {
        "pathPolicy": {
          "write": { "allow": ["."], "outside": "ask" },
          "read":  { "allow": [".", "~/.jellyfish"], "outside": "deny" }
        }
      }
    }
  }
}
  • 要放开就把该方向配成 outside: "allow"（等于把该方向的门关掉），或把目录加进 allow；
  • 相对路径按进程工作目录解析、行首 ~ 按用户主目录，因此 "." 就是工作目录；
  • 它不是文件系统沙箱：管不了 shell 命令里出现的路径（那是命令策略的事），也管不了 MCP 工具；
  • 配置写错只回退并告警（ConfigWarningEvent，TUI 上看得见），不会让插件起不来。

D5　plan 模式下所有工具都被拒

现象
/plan on 之后，连 read_file 都用不了。
原因
plan 模式是白名单语义：「用户没表态」与「用户不准」是同一件事。 readOnlyTools 不写就等于开启时一个工具都用不了。
解决
{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-plan": {
        "readOnlyTools": ["read_file", "list_dir", "grep_files", "todo_write", "skill"]
      }
    }
  }
}
  • 改完敲 /reload；/plan off 可即时恢复；
  • 白名单为空时插件会补一条 ConfigWarningEvent，但它是挂在「因白名单为空而拒绝」上的，不挂在启动上—— 所以不看拒绝理由就不会知道；
  • 开关按会话存（随会话落盘与恢复），同一个进程里可以一个会话开着、另一个关着；子代理按会话树继承—— 父会话开着 plan 时，它派生的子代理会话同样只看不写；
  • 另外注意 subAgent.enabled: false 会让 task 工具直接不再注册，模型看不到它—— 这也是一种「工具忽然没了」。

D6　ask_user 在子代理里被拒 / 在 CLI 里不生效

现象
模型在子代理回合里调 ask_user 直接失败；在 -cli 下则立刻返回一句「无法送达用户」。
原因
两种情形是不同设计，不是同一个 bug：
  • 子代理里提问：外层界面按当前会话取待答项，而子代理有独立的会话，它的提问不会出现在任何一个界面上， ask_user 因此在 run 上当场拒绝、绝不进通道等待（那只会静默卡到超时）；
  • -cli 下提问：那里不挂答复者，工具不失败也不挂住， 立刻返回一条「当前外壳没有交互界面，无法把提问送达用户」的成功结果，模型据此照自己的判断继续。 提问刻意不是 fail-closed：审批者缺席时放行等于静默放宽权限，而提问缺席时让模型继续，代价只是它可能猜错。
解决
  • 要人回答就用 -tui 或 -server（-server 推 ask_required， 客户端拿 requestId 调 POST /sessions/{id}/asks/{requestId}）；
  • 模型总问它自己能查到的问题时，用 agent 的 deniedTools 把 ask_user 拦掉—— 那是硬结论而不是建议（ask_user 只把问题摆到你面前，选任何一项都不放行任何工具）；
  • 超时来自 ask.timeoutSeconds（缺省 120、每次提问现读），它与审批刻意分开； 同样可以写 0 表示永不超时，代价同样是占住一条 react 线程。

E. 上下文与会话

E1　上下文超限 / 历史被静默丢弃

现象
长会话里模型开始「忘记」早先的事；或日志里出现历史被裁剪的痕迹，而屏幕上什么都看不出来。
原因
长会话的每一轮都要把整段历史重新发给模型，所以内核有三层泄压机制，机制不同、副作用也不同： ① 自动压缩（react.autoCompactPercent 缺省 80，上下文用到该百分比就自动压一次）； ② 机械裁剪（只要某一次请求已经触发裁剪，就立刻压一次；被丢弃的那段既不在摘要里、也不会再发给模型）； ③ 工具结果老化（react.cache.agingPercent，把保留窗口之外的信封换成带路径的 stub）。
解决
  • 先看 /usage（token 用量与缓存命中率）确认确实接近窗口上限；
  • 要知道会压多少，用 /compact preview——只回报「将压缩 X 条、保留 Y 条、丢弃 Z 条、摘要输入约 T token」， 不发起压缩；
  • 关键结论：历史一条不删。屏幕上的会话、恢复出来的会话、落盘的文件都还是完整历史， 变的只是「发给模型的那条链路从哪里开始」；可以反复压，每次只压上次边界之后新增的那段；
  • 越界前先调预算：contextReserveTokens（为系统提示词 / 插件注入预留）、 compactKeepRecentMessages、maxToolOutputChars。

E2　/compact 说「压缩不可用」

现象
敲 /compact（或自动压缩该触发时），得到的是一句「压缩不可用」。
原因
压缩依赖插件提供策略：没有启用 jellyfish-plugin-compact（或同类插件）时压缩整体不可用， 而且不回退内置策略（刻意如此）。
解决
  • 把插件装进扫描目录（新增 jar 要重启），并在 jellyfish.json 里放进启用名单：
{
  "plugins": { "enabled": ["jellyfish-plugin-tools", "jellyfish-plugin-session-file", "jellyfish-plugin-compact"] }
}
  • 检查 plugins.disabled 有没有把它排掉（同时出现在两份名单里按禁用处理）；
  • plugins.enabled 显式写 [] 表示「一个都不启用」，那也会让它的命令消失。

E3　几十轮之前的工具输出路径失效

现象
信封里给的 _path 过一段时间就打不开，或者内容已经不是当初那条了。
原因
落盘目录有清理上限（缺省每会话 200 个文件 / 50 MiB），超了从最旧开始删， 所以 _path 只在保留窗口内有效——这是「不做引用计数式保留」的直接代价，刻意接受。 另外文件名带一段唯一片段（调用 id + 工具名 + 纳秒时间戳），而清洗会把不同的调用 id 折叠成同一个名字， 旧文件被后来者覆盖时，先那条信封里的 _path 还在、内容却已经不是它的（比「文件不存在」更难发现）。
解决
  • 要长期留用的内容，趁它还在时另存一份（从信封或落盘目录里拷走）；
  • 放大窗口：react.toolOutput.keepFiles / maxBytes（写 0 关闭清理）、 spillMaxBytes（单条结果的落盘上限，运行期钳制为不超过 maxBytes， 触及上限时信封带 _partial 说明它不完整）；
  • 主目录内的落盘路径会记成 ~/... 形式（不把真实用户名带进上下文），而文件工具认 ~， 所以信封里那条路径可以直接交给 read_file / grep_files / list_dir；
  • 预算泄漏排查用 /resmon（只报告、不清理）。

E4　read_file 报「单行超过上限」

现象
读一个压缩过的大文件（单行很长）时报错，而不是返回内容。
原因
这是刻意的：切短会产出一行看起来完整、实际残缺的内容。工具层先自我限流， 而「单行就超过 max_bytes」与「多行累加超预算」两条路径的语义要分清——后者仍照旧分页。
解决
  • 按错误信息给的三条出路办：缩小 limit、调大 max_bytes， 或改用 grep_files 定位；
  • 不要指望内核自动截断那一行——那是它明确不做的行为；
  • 内核侧还有 react.maxToolOutputChars（缺省 20000）作为硬上限兜底。

E5　提示词缓存命中率低

现象
/usage 里缓存命中率很低，token 花得比预期多。
原因
厂商的缓存是前缀匹配：改掉历史上的一个字节，后面的整段都会从约 0.1× 的命中价变回 1× 全价。 agingPercent 决定「工具结果什么时候换成 stub」，因此它直接决定命中率。 缺省落在 70 是因为它必须略低于 autoCompactPercent（80），相差约 10 个点—— 低了才会真正泄压，高了就让压缩先发生、老化永远轮不到。
解决
  • 改了 react.autoCompactPercent 就一并重看 agingPercent；
  • 想彻底关掉老化：把 react.toolOutput.keepRecentMessages 写 0 （它同时关掉裁剪与老化）；
  • providers.<name>.cache.keepAliveSeconds 是要花钱的，而且有两个坑： 保活请求按「最省输出」只发极小输出（Claude 发 max_tokens: 0），因此与 Claude 的 thinking.budget_tokens 互斥（会被 400 拒）；部分新模型对输出上限有最小值要求（如 GPT-5 是 16）。 保活失败只记 DEBUG 日志，症状就是「配了保活但命中率没改善」——怀疑时先关掉它；
  • 另外 Anthropic 不标 cache_control 就一个字节都不缓存，内核默认替它标两个断点。

F. TUI 显示

F1　滚动看着不对 / 复制文本选不中

现象
滚轮能用，但用鼠标拖选复制不了文本；或上翻之后又自动被拉回底部。
原因
滚轮要求应用捕获鼠标（默认开启），而一旦捕获，终端的鼠标选择就归应用， 所以本地拖选失效。自动跟随也是设计：滚动到内容末尾时自动跟随，用户上翻后不再打扰，状态栏会出现 ↓ N 行。
解决
  • 要复制时按 Ctrl+O（或敲 /mouse）把鼠标交还终端：拖选 + ⌘C 立刻可用； 期间滚轮停用，消息区滚动改用 PageUp / PageDown / End，复制完再按一下收回；
  • 整体不要鼠标捕获：-Djellyfish.tui.mouseCapture=false——代价是滚轮在多数终端下根本到不了应用；
  • 别忘了 TUI 没有 stdout 契约：它独占备用屏，> answer.txt 不适用，退出后也不回显会话内容。

F2　界面字符错乱 / 表线不对齐

现象
边框与表格线断裂、中文错位，或侧栏 / 插件面板突然不见了。
原因
界面用的是备用屏 + 制表符绘制，依赖等宽字体与正确的 TERM 设置。 面板消失则是布局预算：界面窄于 80 列时左右侧栏自动隐藏，窄到放不下时面板会让位给消息区，而不是反过来； 浮层（审批框、提问框、补全面板）出现时面板不会消失、只会变矮。
解决
  • 换成等宽字体、确认 TERM 是终端实际支持的取值，把窗口拉宽到 80 列以上；
  • 整体不要插件 UI：-Djellyfish.tui.pluginPanels=false；
  • 助手正文的表格画成网格（按显示列量宽对齐），列数多到分不下时会退回等宽代码块—— 这是刻意的降级，不是渲染错误；
  • 快捷键诊断（「我绑的键为什么没反应」）只在 /ui list 里。

F3　TUI 的日志在哪

现象
界面上出过一条提示 / 告警（例如配置告警），想回去看原文。
原因
TUI 独占备用屏、绝不写 stderr，日志改写到文件： <用户主目录>/.jellyfish/jellyfish-tui.log。它会自动滚动：单文件涨到 10 MB 就轮换一次， 历史是 jellyfish-tui.log.1、.2……最多留 5 个历史档（再加当前文件，磁盘上限约 60 MB）。
解决
  • 默认路径：~/.jellyfish/jellyfish-tui.log；
  • 改路径用 -Djellyfish.log.file=/path/to/jellyfish-tui.log（占位符，请写你自己的路径）；
  • 两个容量参数：-Djellyfish.log.maxSize=20MB（写法 20MB / 20 MB / 1048576 都认，单位 KB/MB/GB） 与 -Djellyfish.log.maxFiles=10（历史档数）；
  • 注意 -cli / -server 没有文件日志，它们只写 stderr——排查写类工具被拒、401/403 这类问题要看 stderr。

F4　看不到思考文本

G. Server

G1　端口被占用 / 想换端口

现象
-server 起不来，报端口被占用。
原因
缺省端口是 9096；换端口有两条等价写法（位置参数与 --port）。
解决
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -server 9097
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -server --port 9097
curl -s localhost:9097/health
  • 先用 curl localhost:<端口>/health 确认起没起来（它返回 UP / WARN / DOWN， 也是唯一一个不需要鉴权的接口）；
  • 绑定地址用 --host（缺省 127.0.0.1），想换地址先看 G2。

G2　绑非回环地址却启动失败退 3

现象
加了 --host 0.0.0.0，进程直接以 3 退出。
原因
绑非回环地址却不配密钥会拒绝启动（退 3），不是只留一条 WARN—— 那等于把「建会话、跑命令、读全部会话正文」交给同网段的任何人。判据用 InetAddress.isLoopbackAddress() （localhost / ::1 / 127.0.0.2 都算回环），解析不出来按非回环处理。 回环 + 无密钥仍然允许，那是「本机跑一次」的刻意缺省。
解决
# 推荐：密钥走环境变量（不会出现在 ps 输出里）
JELLYFISH_SERVER_API_KEY=$(openssl rand -hex 32) java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -server --host 0.0.0.0
# 也可以：命令行参数（argv 会出现在 ps 里，同机其他用户看得见）
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -server --host 0.0.0.0 --api-key <你的密钥>
  • 不接受用 query 参数传密钥（URL 会进访问日志、浏览器历史与 Referer）；
  • 密钥短于 16 位会在启动日志里告警，但不拒绝启动；密钥比较是常时比较；
  • 命令域与对话域同权：POST /sessions/{id}/commands 能执行 /reload 等系统命令， 因此密钥泄露等于整机权限泄露；
  • 要按调用方区分权限，别指望本服务——它是单主体模型（见 G3 与 H5）。

G3　所有接口都返回 401

现象
配了密钥之后，curl 每个接口都是 401 + {"error":"UNAUTHORIZED"}。
原因
配了密钥后，除 GET /health 外所有接口都要带 Authorization: Bearer <密钥>，并带 WWW-Authenticate: Bearer realm="jellyfish"。
解决
curl -s localhost:9096/health                                    # 唯一不需要鉴权的接口
SID=$(curl -s -X POST localhost:9096/sessions \
      -H "Authorization: Bearer <你的密钥>" | jq -r .sessionId)
curl -sN -X POST localhost:9096/sessions/$SID/chat \
     -H "Authorization: Bearer <你的密钥>" \
     -H 'Content-Type: application/json' -d '{"message":"总结这个项目"}'
  • /health 的不校验是刻意的：探活必须能在「还没有密钥」的场景下工作，且它不含会话正文与路径； 路径按归一化后比对（尾斜杠等价）；
  • 没配密钥 = 不鉴权：任何能访问该端口的人都能建会话、跑命令、读全部会话正文，只对仅绑回环的本地场景够用。

G4　写请求回 403

现象
从浏览器页面（或带 Origin 头的客户端）发 POST / PUT / PATCH / DELETE 回 403。
原因
写请求会额外校验来源：带 Origin（缺省时退到 Referer）时， 其主机必须与本服务一致，否则回 403；两个头都不带则放行。 这挡的是浏览器被恶意页面指使来驱动你本机的 agent——浏览器对 text/plain 这类「简单请求」会照常发出并执行副作用， 只是响应不可读，因此只绑回环挡不住（请求确实来自本机）。Origin 为字面量 null 一律拒绝。
解决
  • 要明确由自己发起：别带 Origin / Referer——curl 与 SDK 本来就不带， 只有浏览器会自动加上；curl 里显式写了 -H 'Origin: …' 反而会把自己挡掉；
  • 从网页发请求时，让页面与本服务同源（同主机同端口），或走自己的后端代理；
  • 顺手检查是不是同时踩了 G5（415）：两个错误的成因完全不同。

G5　带体请求回 415

现象
POST /sessions 或 /chat 回 415。
原因
带体的请求要声明 application/json。回 415 的正是 text/plain 这类浏览器能跨站发出的内容类型——这与 G4 是同一道防线的一部分。
解决
curl -s -X POST localhost:9096/sessions -H 'Content-Type: application/json' -d '{"agentId":"coder"}'
  • POST /sessions 的 body 可选 agentId / provider / model； POST /sessions/{id}/chat 的 body 是 {"message":"…"}，且恒为 SSE；
  • 向用户提问作答的 body 给 {"optionId":"…"} 或 {"text":"…"}， 两种都不给（或 text 全空白）回 400。

G6　同一会话的第二个请求回 409

现象
一个会话的 /chat 还在流式输出，再发一条就回 409。
原因
同会话同时只允许一个回合——这是刻意的并发口径，不是偶发故障。
解决
  • 要打断在途回合：POST /sessions/{id}/cancel，或直接断开 SSE 连接（服务端据此取消回合）；
  • 要并行干活：新建会话（POST /sessions），而不是在同一个会话里排队；
  • 顺带记住 input_handled 与其他终态的区别：它不带 turnId，也不占一个在途回合槽位；
  • 权威结果只看 tool_done 的 output：tool_output 是可丢的过程信息， 客户端不要拿它当状态真源。

G7　命令端点回 403 COMMAND_NOT_ALLOWED

现象
POST /sessions/{id}/commands 执行 /new、/reload 之类的命令时被拒。
原因
命令端点有一道闸门：/new、/resume、/reload、/session、/delete 这类「改进程级状态或按参数操作别的会话」的命令回 403 COMMAND_NOT_ALLOWED—— 本外壳按会话 id 寻址，不需要这些命令。
解决
  • 建会话用 POST /sessions，删会话用 DELETE /sessions/{id}；
  • GET /commands 仍会如实列出全部命令——过滤器与闸门是两件事，别拿清单当「能不能调」的依据；
  • 还要知道两个 404 的差别：/sessions/{id}/commands 会先校验会话存在 （不存在回 404，与 /chat、GET /sessions/{id} 同口径）， 命令自身不认识则回 404 + kind=UNKNOWN，两者靠 kind 与状态码并存可区分；
  • Spring 接入方那边还有一份命令闸门（jellyfish.user.denied-commands），默认同样拦下这些命令。

H. Spring Boot 整合

H1　内核对象图被重复构造 / Bean 冲突

现象
容器里出现两个模型 / 会话相关的视图，行为诡异；或启动时 Bean 冲突。
原因
starter 的设计是只暴露观测面的门面，内核门面默认不进容器； 而「插件是唯一正确的扩展方式」——不要在 Spring 容器里替换内核组件。
解决
  • 不要再注册 ModelManager / SessionManager / ApprovalChannel / AskChannel 这类内核组件的第二个视图；容器里拿不到它们是刻意的（拿不到就用不着记住「不要用它」）；
  • 真要拿到内核门面，只能自己 JellyfishAssembler.create(...)——那时多用户护栏就都在你手上了；
  • 四条纪律照抄：交互一律走 JellyfishUserFacade； 不要调 switchTo / createDefault（那是进程级的「当前会话」指针，多用户下会让一个用户的会话变成所有人的）； 不要调 /new、/resume、/delete、/session、/reload （门面的 executeCommand 已拦住，直接调 CommandManager 就绕过了闸门）； chat 的 listener 在内核线程上被调用，必须快且线程安全，抛出的异常会被记日志后吞掉。

H2　Jackson 版本冲突

现象
宿主的 Jackson 版本比内核低（例如 Boot 管理的 2.13.5），担心解析 models.json / agents.json 出问题。
原因
内核的构建与测试用 jackson-databind 2.21.6，Boot 2.7.18 管理的是 2.13.5； starter 的 pom 覆盖了 Boot 的 jackson-bom.version 属性，让自己按内核那一份构建。 但宿主应用的最终 classpath 由宿主自己的 BOM 决定。
解决
  • 不必为了 starter 去动手改宿主的 Jackson：实测两个版本下全部用例（含真解析 models.json / agents.json 的那条链路）通过：
mvn test                                # 2.21.6
mvn test -Djackson-bom.version=2.13.5   # Boot 管理版本
  • 想让宿主也用内核那一份，就在宿主的 pom 里设同一个属性；
  • 同类问题（依赖版本被宿主统一管理）先确认最终 classpath，而不是先怀疑 starter。

H3　审批 / 提问开关没打开，工具全被拒或提问立刻返回

现象
接进来之后 askTools 里的工具全部失败；ask_user 立刻返回一句「无法送达用户」。
原因
starter 不实现审批界面、也不实现提问界面，因此两个开关都缺省 false。 关闭时：需要审批的调用立即按拒绝处理（fail-closed，问题当场暴露）； 提问则立即返回一条成功结果（既不失败也不阻塞任何线程）。
解决
jellyfish:
  approval:
    enabled: true    # 缺省 false
  ask:
    enabled: true    # 缺省 false
  • 接好接口之后再打开：打开时调用会阻塞 react 线程最多 120 秒再按拒绝（审批）或返回「用户没有回答」（提问）； 这个 120 秒来自 jellyfish.json 的 permission.approvalTimeoutSeconds / ask.timeoutSeconds；
  • 审批队列与提问队列都是每会话上限 8 条：第 9 条起审批直接按拒绝处理、提问直接返回「问不到人」； 且只有头槽位能被裁决 / 作答，对排队中的那一条调用返回 false；
  • 客户端断开时应当调 cancelAsk / 拒绝待审项，而不是放着等满 120 秒； 把超时写成 0（永不超时）时这条纪律就是唯一的护栏。

H4　启动顺序不对 / 偶发打不通

现象
服务起来了但第一次调用偶发失败；或改了 phase 之后某次升级 Boot 就静默失效。
原因
JellyfishLifecycle 是 SmartLifecycle，phase 取 Integer.MIN_VALUE（启动最先、停止最后）， 保证内核早于 Web 容器就绪、晚于它停止。Web 容器的 phase 是 Boot 的内部实现（2.x 是 Integer.MAX_VALUE - 1， 较新版本已改成 Integer.MAX_VALUE - 1024），跟它减一个魔数会在某次升级 Boot 时静默失效。
解决
  • 不要把 phase 改成「比 Web 容器小一点」；
  • starter 不注册 JVM shutdown hook：Spring 自己会在上下文关闭时走 SmartLifecycle.stop()， 再叠一个 hook 只会让「谁先关」取决于 JVM 不保证的 hook 执行顺序；
  • 想自己挑启动时机：jellyfish.lifecycle.bootstrap-on-start: false（只装配不启动内核）， 再注入 JellyfishLifecycle 调它的 bootstrap()——两条路径的关闭动作相同。

H5　想按用户区分权限做不到

现象
同一个 agent 对不同用户想要不同权限，发现怎么写都只有一套。
原因
这是明确的使用限制：内核的权限策略按 agentId 全局共享， 因此同一个 agent 对不同用户只能有同一套权限。内核没有「用户」这一维—— Session 上没有 owner 字段、SessionManager.all() 返回全进程会话、插件也不做用户隔离。
解决
  • 要区分角色，就给每个角色定义一个 agentId，建会话时按角色选；
  • 会话归属、审批归属在 starter 的 user 包里（SessionOwnerStore / ApprovalGateway）， 那里才有 userId 概念；
  • 涉密能力不要装进多租户进程：shell（无沙箱、可起任意子进程）、 mcp（fork 外部进程）、python / node 桥接（要解释器、每脚本一个进程）都不做用户隔离， 装进来等于把所有用户放在同一个权限面里；
  • 反过来也成立：绕过门面就是绕过全部护栏。

I. 升级到 0.1.1 后要留意的行为变更

下面几条不是「怎么修」而是「为什么你原来的预期会变」——如果你从更早的版本升上来， 现象会看起来像 bug，其实是刻意的行为变更。

变更升级后会看到什么该做什么
未声明的 agentId 由「放行 + 告警」改为「全拒 + 告警」 绑了一个配置里查不到的 agent（改名、删除、从别处恢复出来的会话、/reload 之后 agent 被改名）的旧会话， 从「不受限」变成「全部工具被拒」，并带一条每个标识一次的 ConfigWarningEvent 把 agent 名字改回去，或给这些会话重新绑一个存在的 agent。「一个 agent 都没配」那支的口径没动（仍是 fail-open）
审批 / 提问超时写 0 的语义变了 0 与负数过去一律被静默换成 120 秒；现在 0 表示永不超时、负数按非法回退 120 秒并告警 想「多等一会儿」别再写大数（超过 3600 秒会给告警）：要么写 0，要么写一个明确的值
拼错字段名不再无声 读取配置时会比对字段名，内核不认识的字段会发 ConfigWarningEvent 并打 WARN（带文件路径与字段名）； 数值写错（react 段、provider 的 sampling 段）也进同一个事件面；而呈现这条告警的 ConfigWarningReporter 也是这一版才有的 升级后把启动日志里的配置告警当回事——它可能就是「我调了配置却没变化」的答案。vendorBody 与逐插件配置段这类自由格式不参与比对，别指望它替你发现拼错的厂商键名
subAgent 的并发 / 等待区 / 墙钟不再「永远按缺省值跑」 过去它们由 RunScheduler 在构造器里读一次，而那时配置快照还是空的， 于是 runTimeoutMillis 写 20 分钟照样按 300 秒掐断、maxConcurrentRuns 写 6 照样只并发 3，没有任何日志 现在墙钟在每次起看门狗时按当时配置取（/reload 之后下一个 run 就按新值计时）； 并发 / 等待区 / 池上界在第一次提交时定型（此后不重建，语义仍是「改它们需重启」）
取消（Esc）能穿过等待区 过去一个在等待区里等许可的 run 收不到取消，句柄长时间不落终态，界面上与「没按上」无法区分 升级后排队中的 run 被取消会当场落「已取消」，面板上有「取消中」这一档；子代理面板另外分开了「已等待」与「已运行」

排错时最容易扩大事故的三件事
  • 把 permission.approvalTimeoutSeconds / ask.timeoutSeconds 写成 0 来「让它多等一会儿」： 那会把「等不到人就拒绝」换成「等不到人就一直卡住」，并占住一条 react 线程（池子只有 8 条）。
  • 为了排错把密钥写进配置文件：配置会随 git、随日志、随会话落盘外流。 密钥一律走环境变量或 ${VAR}，Server 用 JELLYFISH_SERVER_API_KEY 而不是 --api-key（argv 会进 ps）。
  • 为了排错把 pathPolicy 的 outside 全改成 allow、把 shell 加进可信表： 那是把安全边界关掉，而不是排错。先定位，再最小化放开。

关键结论

  1. 先看退出码属于哪一步：2 是用法、3 是启动（bootstrap 期任何运行时异常都算）、4 是运行期、6 是没收敛、7 是被插件拦下。它比报错文案更能定位问题。
  2. 「命令能用、对话不能用」几乎总是 B1（没 models.json）或 B2（${VAR} 缺失导致整份配置没加载），不是内核坏了。
  3. 「工具总被拒」在有审批者的外壳（-tui、接好接口的 -server）里是配置问题； 在 -cli 里是能力缺失——那里没有审批者，ASK 就是拒绝，只能靠免审批的两个放行口。
  4. 「改了配置不生效」有四种成因：改错文件（config.json 不热更新）、没敲 /reload、 项目级配置没被信任（信任单位是路径 + 内容指纹）、键名拼错被静默忽略（只能靠 ConfigWarningEvent 与 DEBUG 日志发现）。
  5. 插件相关的三类问题各有专属入口：/help 没命令看 plugins.roots / 目录层级 / 重启； 加载失败看启动日志；NoSuchMethodError 看 provided、shade includes 与 clean。
  6. Server 的 401 / 403 / 409 / 415 分别对应「没带 Bearer」「不是同源 / 带了 Origin」「同会话已有在途回合」「没声明 application/json」， 它们都是刻意的防线而不是服务故障。
  7. 整合进 Spring Boot 时最该记住两条：不要重复构造内核对象图、不要改 JellyfishLifecycle 的 phase； 而「按用户分权」不是配置问题，是内核不提供的维度——给每个角色定义一个 agentId。
