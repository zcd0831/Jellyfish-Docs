05 配置体系总览

Jellyfish 的配置不是「一份文件配完」，而是五份文件各管一段 + 全局级与项目级双源合并。 这一页把「谁管什么」「两级怎么合并」「环境变量怎么插值」「项目级为什么默认不加载」 「改了要不要重启」一次讲清，最后给五条可以直接抄的常见配置任务。 字段级细节分别落在 06 models.json 详解 与 07 agents.json 与工具权限。

学习目标

  • 说出五份配置文件各自的配置类、管什么、放在哪，以及哪几份参与「全局级 + 项目级」双源；
  • 看懂并会改 config.json：进程名、三份内容文件的双源路径、插件扫描目录；
  • 记住双源合并的四种单位：整对象覆盖、整段回退、名单整体替换、非空值回退；
  • 正确使用 ${VAR} / ${VAR:-default} / \${VAR}，并知道 ${VAR} 缺失会让整份配置加载失败；
  • 解释项目级配置为什么默认不加载，并用 --trust-project-config 或 TUI 确认框把它放进来；
  • 判断一次改动是敲 /reload 就行，还是必须重启进程；
  • 照着抄五条常见配置任务：全域统一模型、单项目覆盖、关自动压缩、临时禁插件、关子代理。

五份配置文件，各管什么

README 的口径是五份文件：一份管「其它文件在哪」，三份管内容（模型 / agent / 运行期设置）， 还有一份是随构件发布、用户改不了的内置默认 agent。用户日常真正要维护的通常只有前四份， 其中 config.json 多数时候一行都不用改。

配置文件 对应配置类 内容 缺省寻找位置 是否参与双源
config.json AppConfig 进程名 + 各配置文件路径 + 插件扫描目录 classpath 根（本仓库 jellyfish-cli/src/main/resources/config.json） 不参与，也不热更新
models.json ModelSettings defaultProvider / defaultModel / providers ~/.jellyfish/ → ./.jellyfish/ 参与，项目级优先
agents.json AgentSettings 用户自定义 agent 同上 参与，项目级优先
jellyfish.json JellyfishSettings 插件名单与配置段、react / permission / subAgent（另有 ask 段） 同上 参与，项目级优先
default-agent.json AgentDefinition 内置系统默认 agent classpath 根，不走双源、用户改不了 不参与
为什么「文件在哪」要单独一份文件

config.json 里只有路径与目录，没有内容；models.json / agents.json / jellyfish.json 里只有内容，没有路径。这么分的好处是：换机器、换目录布局只改一处， 而内容类配置可以自由地在「全局级」与「项目级」各放一份。

另一半理由在源码里写得很直白：plugins.roots（插件扫描目录）属于「内核去哪找能力」的部署事实， 与「去哪个文件读配置」同一性质，放在一起才不用两处找；而 jellyfish.json 的 plugins 段只保留「加载后怎么用」的运行期设置（enabled / disabled / configurations）。

config.json：唯一管「其它文件在哪」的那份

config.json

是什么
应用级配置，绑定到 AppConfig，固定从 classpath:config.json 读取。 它声明三份内容类配置的「全局级 / 项目级」路径，以及插件扫描根目录—— 它自己不是内容，只回答「去哪读」。
怎么用
它是一份 classpath 资源，因此改它的方式是改源码里的 jellyfish-cli/src/main/resources/config.json 后重新构建； 也可以在 classpath 上放一份同名资源（注意 classpath 上同名资源谁生效取决于顺序）。 Spring Boot 接入方不走这份文件，而是用 application.yml 里的 jellyfish.* 属性（见 14 整合到 Spring Boot）。

配置（仓库自带的原文如下）

{
  "processName": "Jellyfish",
  "model": {
    "globalPath": "~/.jellyfish/models.json",
    "projectPath": "./.jellyfish/models.json"
  },
  "agent": {
    "globalPath": "~/.jellyfish/agents.json",
    "projectPath": "./.jellyfish/agents.json"
  },
  "jellyfish": {
    "globalPath": "~/.jellyfish/jellyfish.json",
    "projectPath": "./.jellyfish/jellyfish.json"
  },
  "plugins": {
    "roots": ["~/.jellyfish/plugins/"]
  }
}
字段类型必填默认值含义示例
processName string 选填 Jellyfish 进程名；写空白按缺省值处理 "Jellyfish"
model.globalPath string 选填 ""（空串＝该层级未配置） 模型配置的全局级文件路径；支持 ~ 与 classpath: 前缀 "~/.jellyfish/models.json"
model.projectPath string 选填 ""（空串＝该层级未配置） 模型配置的项目级文件路径；相对进程工作目录解析 "./.jellyfish/models.json"
agent.globalPath string 选填 "" agent 配置的全局级文件路径 "~/.jellyfish/agents.json"
agent.projectPath string 选填 "" agent 配置的项目级文件路径 "./.jellyfish/agents.json"
jellyfish.globalPath string 选填 "" 运行期设置（插件段 / react / permission / ask / subAgent）的全局级文件路径 "~/.jellyfish/jellyfish.json"
jellyfish.projectPath string 选填 "" 运行期设置的项目级文件路径 "./.jellyfish/jellyfish.json"
plugins.roots string[] 选填 空列表 → 回退默认目录 plugins 插件扫描根目录，顺序即扫描顺序；展开行首 ~、丢弃空白条目， 相对路径相对进程工作目录解析 ["~/.jellyfish/plugins/"]

需重启 config.json 与 plugins.roots 不参与双源合并、也不参与热更新： 改完要重启进程；新增 / 删除插件 jar 同样只在启动期确定。

完整示例（把插件扫描目录指到两个位置，其余保持约定）

{
  "processName": "Jellyfish",
  "model":     { "globalPath": "~/.jellyfish/models.json",    "projectPath": "./.jellyfish/models.json" },
  "agent":     { "globalPath": "~/.jellyfish/agents.json",    "projectPath": "./.jellyfish/agents.json" },
  "jellyfish": { "globalPath": "~/.jellyfish/jellyfish.json", "projectPath": "./.jellyfish/jellyfish.json" },
  "plugins":   { "roots": ["~/.jellyfish/plugins/", "/opt/jellyfish/plugins"] }
}

常见问题

  • 把 plugins.roots 写成 [] 会怎样？空列表回退默认目录 plugins（相对进程工作目录），不是「一个目录都不扫」。
  • 两份路径写成同一个文件？内核识别到 global 与 project 指向同一路径时只读一次，此时「项目级覆盖」等价于单源。
  • 我只想改模型配置的存放位置？改 model.globalPath / model.projectPath 即可，内容格式完全不变。

双源：全局级 vs 项目级

三份内容类配置都是双源：先读全局级（~/.jellyfish/），再读项目级 （<工作目录>/.jellyfish/），项目级优先。但「优先」的单位并不统一—— 记住下面四种单位，就不会出现「我明明覆盖了却没生效」。

合并单位规则典型后果
同名 provider / agent / 插件配置段 项目级整对象覆盖全局级（不是逐字段合并）；agent 的提示词 md 也随来源一起覆盖 项目级写 provider 时，必须把 type / apiKey / models 一整套写全，否则那些字段等于没配
defaultProvider / defaultModel 取项目级非空值，否则回退全局级 项目级写 "" 或省略 = 继续用全局级
react / permission / ask / subAgent 段 项目级写了这一段才整对象覆盖，没写就整段回退全局级；判据是段级「声明标记」，不是「取到的段非空」 写 "ask": {} 也算「写过」，此时该段按缺省值生效（不是继承全局级）
plugins.enabled / plugins.disabled 名单 项目级已声明则整体替换（写 [] 即清空该名单），不做并集 项目级写 "disabled": ["a"] 会把全局级的禁用名单整份顶掉
plugins.roots 只在 config.json 一处，不参与双源合并 —
default-agent.json 内置只读定义，不走双源、用户改不了；用户 agents.json 里写同名 jellyfish 会被忽略并告警 想用自定义 agent 只能 /agent <agentId> 切换

容错口径：配置可疑不拦启动
  • 配置缺失或可疑只发配置告警事件（ConfigWarningEvent），不中断启动，真正用到时才报错。
  • 项目级被跳过时必发一条告警（源为 project-config）：静默跳过会让用户以为配置生效了。
  • 插件还能问出「我这个配置段是哪一级给的」：PluginContext.configScope() 给来源层级，PluginContext.globalConfiguration() 给只由全局级决定的那一份（见 13 插件进阶）。

环境变量插值

${VAR} 环境变量占位符

是什么
让配置里不出现明文密钥：值写成 ${OPENAI_API_KEY}，真实密钥放环境变量， 由绑定器在解析 JSON 之后替换。它解决的是「配置文件会被提交、会被共享，而密钥不该」。
怎么用
在配置文件的字符串值里写占位符，然后导出环境变量： 
export OPENAI_API_KEY=sk-***
export DEEPSEEK_API_KEY=sk-***
java -jar /path/to/jellyfish-cli-0.1.1.jar -cli -p "/model"

配置：三种写法

写法类型必填默认值含义示例
${VAR} 字符串占位符 选填 无（缺失即报错） 必需：环境变量缺失就抛 JellyfishException， 整份配置加载失败；它不会退化成「这一项为空」 "apiKey": "${OPENAI_API_KEY}"
${VAR:-default} 字符串占位符 选填 分隔符后的 default 可选：环境变量缺失时用 default（可为空），配置照常加载 "baseUrl": "${LLM_BASE_URL:-https://gateway.example.com/v1/chat/completions}"
\${VAR} 转义写法 选填 无 输出字面量 ${VAR}，不做替换（值本身就长这样时用） JSON 里要写成 "note": "\\${NOT_A_VAR}"——JSON 文本里是两个反斜杠，解析后字符串里只剩一个反斜杠，绑定器见到的正是 \${NOT_A_VAR}，于是原样输出 ${NOT_A_VAR}

两条边界（源码口径）：只替换字符串值——JSON 的 key 不替换，数组元素里的字符串同样替换； {agentId}.md 提示词是原文，不做模板插值。

缺一个 ${VAR}，整份配置都加载不了

${VAR}（不带默认值）是硬要求。环境变量没设时绑定阶段直接抛 JellyfishException，报 environment variable is not set: <名字>, source: <配置文件路径>， 整份配置加载失败；启动期属于「配置出错」，按退出码表的归类是启动失败（退 3）。 它不会变成「这一项为空、其余照常」。

两种容错写法：

  • 给默认值："apiKey": "${OPENAI_API_KEY:-}"——默认值可以是空串：变量没设时该字段得到空串，配置照常加载；
  • 对不需要替换的 ${...} 文本加反斜杠转义 \${VAR}，让它原样留在配置里。

注意 ${VAR:-} 只是不再让加载失败，它把该字段变成空串—— 空串在具体字段上意味着什么，要按该字段的语义判断。

完整示例（密钥走环境变量，网关地址可被环境变量覆盖）

{
  "providers": {
    "openai": {
      "type": "openai",
      "apiKey": "${OPENAI_API_KEY}",
      "baseUrl": "${LLM_BASE_URL:-https://gateway.example.com/v1/chat/completions}",
      "models": [{ "id": "gpt-4o", "name": "gpt-4o", "contextLength": 128000, "maxOutputTokens": 4096 }]
    }
  }
}

常见问题

  • 启动时报 environment variable is not set？照着报错里的名字导出环境变量；报错里还带上了是哪份配置文件（source）。
  • 能不能把密钥直接写进配置文件？能跑，但不要这么做——配置文件会被提交、会被复制，而密钥不该。README 的「坑」第 7 条就是这一条。
  • export 了却不生效？确认导出发生在启动进程的同一个 shell / 同一份环境里（容器、systemd、IDE 的运行配置各有各的环境变量）。

路径规则

所有路径字段（三份内容文件的 globalPath / projectPath、plugins.roots） 走同一套规则：

规则行为依据
行首 ~ / ~/ 展开为用户主目录 HomePaths.expand 在读取前展开；这是唯一的内容加工，其余一律原样
相对路径 相对进程工作目录解析，不是相对 jar 位置 因此「在哪个目录里启动」决定 ./.jellyfish/ 指向哪里
classpath: 前缀 读 classpath 资源，而不是文件系统文件 Spring 接入方靠它把配置放进自己的 resources
文件不存在 视为「该源未配置」，跳过、不阻断启动 「这个目录没有项目级配置」是常态
路径指向目录 抛 JellyfishException（settings path is a directory） SettingsReader 先判目录再看内容
文件存在但读不到内容 发一条告警：「配置段文件缺失或为空，将按未配置处理」 RuntimeConfig.read：路径已配置而结果为 null 时发事件
「文件不存在」与「文件存在但没被信任」是两件事

文件不存在：不发告警（常态）。文件存在但未被信任：不加载，并发一条告警说明怎么才能加载。 另外，「内容为空」与「路径已配置但文件确实缺失」都会命中那条「配置段文件缺失或为空」的告警—— README 把这组情况概括为「静默跳过」，指的是不中断、不要求确认。 这条告警在源码里是明文：RuntimeConfig.read（RuntimeConfig.java:416-421）在 path 非空白而读到的结果是 null 时发一条 ConfigWarningEvent， 消息就是「配置段文件缺失或为空，将按未配置处理」（RuntimeConfig.java:420）；0.1.1 起由 ConfigWarningReporter 渲染成一行 WARN 落到终端与日志文件。

项目级配置的信任

项目级配置的信任闸门

是什么
项目级配置（<工作目录>/.jellyfish/*.json）默认不加载， 只有被显式信任过才参与合并。它挡的不是「格式错误」，而是「这份内容会不会随着 git clone / git pull 凭空出现在你的工作目录里」。
怎么用
-cli / -server 加启动参数；-tui 在启动时回答确认框： 
# 命令行：本次进程内信任并加载 ./.jellyfish/*.json（不落盘）
java -jar /path/to/jellyfish-cli-0.1.1.jar -cli --trust-project-config -p "读一下这个项目"

# TUI：启动时弹确认框，y = 加载并记住，o = 仅本次加载
java -jar /path/to/jellyfish-cli-0.1.1.jar -tui

配置：三种授予方式

场景做法必填是否落盘含义示例
-cli / -server 启动参数 选填 否，仅本次进程 信任并加载项目级配置 --trust-project-config
-tui 确认框选 y（加载并记住） 选填 是，写入 ~/.jellyfish/trusted-project-configs.json 按当前内容记进信任仓库，后续进程直接生效 —
-tui 同一确认框里选 o（仅本次加载） 选填 否 只让这一个文件在本次进程内生效 —

信任的单位是「文件绝对路径 + 内容指纹」，不是目录：内容一变（指纹用 SHA-256）信任立即失效， 需要重新确认。这是刻意的——只记目录的话，「信任一次」会变成「永远信任这个仓库，无论它以后写什么」。 classpath: 形式的项目级路径（如 classpath:jellyfish/models.json） 不受这道闸管辖：它属于运行构件本身，由打包与部署的人决定，与全局级同性质。

完整示例（项目根建一份只覆盖模型的配置，然后带信任参数启动）

mkdir -p ./.jellyfish
# 写入 ./.jellyfish/models.json（内容见 06 页的多厂商示例）
java -jar /path/to/jellyfish-cli-0.1.1.jar -cli --trust-project-config -p "/model"

常见问题

  • 为什么默认不加载？它的读取基准是进程当前目录，内容取决于「在哪个目录里启动」；而它能决定的东西很重：models.json 里同名 provider 是整对象替换，改掉 baseUrl / apiKey 就等于把密钥与全部对话正文送到别处；agents.json 可以新增 agent（未声明权限的 agent 不受限）；jellyfish.json 可以改落盘目录与插件配置。
  • 没有终端可问时会怎样？-cli / -server 只会打印一行提示告诉你怎么才能加载，绝不擅自加载；确认框的缺省答案、无法识别的输入、读不到应答，一律按不加载处理。
  • 改了文件内容还要重新确认吗？要。指纹对不上就重新征求确认。
  • 信任仓库本身读不出来？失败一律按不信任处理：闸门只会关得更紧，不会因为异常而自己打开。

未知字段怎么处理

这一节要分清三件事：会不会报错、会不会有告警、写错的字段会不会生效。 答案是：不报错、字段不生效；而「有没有告警」在 0.1.1 起变了。

两处明文口径不一致，以 CHANGELOG 与源码为准
  • README（models.json 一节，Jellyfish/README.md:552）：本文件关掉了「未知字段」的报错，多写一个键既不会有提示、也不会有任何效果；表里没列出的字段就是不支持的。
  • CHANGELOG 0.1.1（Jellyfish/CHANGELOG.md:43-47）：配置里拼错字段名不再无声——读取配置时会比对字段名，发现内核不认识的字段就发一条 ConfigWarningEvent 并打出 WARN 行，带上文件路径与字段名；只比字段名、不做类型转换；自由格式的位置一概不看（vendorBody、逐插件配置段这类键名由使用方决定），宁可漏报也不报假警。

两句说的不是同一件事，但要一起读：「不报错、不阻断启动、字段照样不生效」在 0.1.1 前后都成立， 变的只是「完全无声」这一条——0.1.1 起会多一条 WARN。

该信哪个：以 CHANGELOG 为准，源码也站在 CHANGELOG 这一边。 README 那句「既不会有提示」是 0.1.1 之前的措辞（两份文件分头维护，这类旧句子会滞后）。 源码里有三处互相印证的事实：

  • 绑定确实容忍未知字段：ObjectMapperWrapper.java:43 里 FAIL_ON_UNKNOWN_PROPERTIES=false，所以「不报错、不阻断启动」成立；
  • 读取这一层另有一条「比对字段名」的流程：ConfigLoader.read(path, type, unknownFieldReport) （ConfigLoader.java:76-84）比对后把每个未知字段名交给调用方；
  • RuntimeConfig.read（RuntimeConfig.java:416-421）把它包成 ConfigWarningEvent 发出去，消息形如「配置里有内核不认识的字段：<路径.字段名>（拼错了？它会被静默忽略）」 （RuntimeConfig.java:417-418），再由 ConfigWarningReporter 渲染成一行 WARN。

三份内容文件口径一致：models.json（RuntimeConfig.java:114）、 jellyfish.json（RuntimeConfig.java:116）、agents.json（RuntimeConfig.java:169）都走同一个 read(path, type)，全局级与项目级都一样，因此三者都报未知字段、且报的范围相同。 不报的只有两份非内容文件：config.json（ConfigLoader.loadAppConfig， ConfigLoader.java:44-46，用的是两参重载）与 default-agent.json （BuiltinAgentLoader.java:78，同样是两参重载）。

哪些改动要重启、哪些热生效

一句话记法：「文件在哪」与「有哪些插件 jar」要重启，「文件里写了什么」敲 /reload。 但有三个例外必须单独记住（见下表最后几行）。

你改了什么生效方式说明
config.json 的内容（三份文件路径、plugins.roots、进程名） 需重启 config.json 不参与热更新
新增 / 删除插件 jar 需重启 插件在启动期扫描加载
models.json / agents.json / jellyfish.json 的内容 /reload 生效 重读配置、重建模型 / agent 索引，并只重启配置段变了的插件，同步等结果
项目级配置的信任（--trust-project-config / TUI 确认框） 需重启 启动期决定要不要读；内容指纹一变信任立即失效，需重新确认
subAgent.maxDepth / maxConcurrentRuns / maxQueuedRuns 需重启 在本次进程第一次派子代理时定型，此后不再变（runTimeoutMillis 例外，/reload 后下一个 run 就按新值计时）
/reload 做了什么、没做什么
  • 顺序固定：modelManager.refresh(true) → agentManager.refresh(false) → pluginRuntimeConfig.refresh → 比对插件配置段 → pluginManager.reload → modelManager.refreshCatalogs → 广播 ConfigReloadedEvent。
  • 单飞、不回滚：synchronized 串行执行，触发只有 /reload 一条路；出错不会退回旧配置。
  • 「重启插件」= stop + start：PF4J 插件实例在装载期缓存，stop 不会重置它。

常见配置任务

1. 让这台机器上的所有项目都用同一套模型配置

把同一份文件放到 ~/.jellyfish/。项目级若有同名条目，会整对象覆盖全局级。

{
  "defaultProvider": "openai",
  "defaultModel": "gpt-4o",
  "providers": {
    "openai": {
      "type": "openai",
      "apiKey": "${OPENAI_API_KEY}",
      "models": [{ "id": "gpt-4o", "name": "gpt-4o", "contextLength": 128000, "maxOutputTokens": 4096 }]
    }
  }
}

写完之后确认生效：java -jar /path/to/jellyfish-cli-0.1.1.jar -cli -p "/model"（/model 离线可用，不需要模型也能看出当前选的是哪个）。

2. 只给某个项目换模型

在项目根建 .jellyfish/models.json，只写要覆盖的 provider； 然后启动时加 --trust-project-config（-tui 则在确认框里选加载）。 注意同名 provider 是整对象替换，所以 type / apiKey / models 要写全。 

{
  "providers": {
    "openai": {
      "type": "openai",
      "apiKey": "${CORP_GATEWAY_KEY}",
      "baseUrl": "https://gateway.example.com/v1/chat/completions",
      "models": [{ "id": "gpt-4o", "name": "gpt-4o", "contextLength": 128000, "maxOutputTokens": 4096 }]
    }
  }
}

3. 关掉自动压缩

写 0 关闭自动压缩，只留手动 /compact；建议先 /compact preview 看会压多少再压。

{
  "react": { "autoCompactPercent": 0 }
}

4. 临时禁用某个插件

写进 jellyfish.json 的 plugins.disabled，然后 /reload。同一 pluginId 同时出现在启用与禁用名单里时按禁用处理，并发一条配置告警。

{
  "plugins": { "disabled": ["jellyfish-plugin-todo"] }
}

5. 关掉子代理委派

/reload 后 task 工具直接不再注册，模型看不到它。

{
  "subAgent": { "enabled": false }
}

关键结论

  1. 配置分五份：config.json 管「其它文件在哪」，models.json / agents.json / jellyfish.json 管内容（三份走双源），default-agent.json 是内置只读兜底。
  2. 双源合并有四种单位，别混：同名 provider / agent / 插件段整对象覆盖、默认模型非空才覆盖、段级「写了才覆盖」、启禁名单整体替换（写 [] 即清空）。
  3. ${VAR} 缺失会让整份配置加载失败（不退化成空值），要容错就写 ${VAR:-默认值}；密钥一律走环境变量，不进配置文件。
  4. 项目级配置默认不加载，信任单位是「文件绝对路径 + 内容指纹」，内容一变即失效；classpath: 形式的项目级路径不受这道闸管辖。
  5. 未列出的字段永远不会生效；0.1.1 起拼错字段名会多一条 WARN + ConfigWarningEvent，但 vendorBody 与逐插件配置段这些自由格式位置不看。
  6. 生效方式只有两种：内容类改完敲 /reload；config.json、插件 jar 增删、项目级信任、subAgent 的三个并发键要重启进程。
