08 内置工具速查

工具是模型唯一能「动手」的地方。这一页按「工具从哪来」分组，把每个工具的名字、参数、限制与调用示例列全。 最重要的一个认识是：绝大多数工具不在内核里，而在插件里——不装插件，内核只给你一个 task。 本页的每个工具名与参数名都逐字来自仓库 README 与源码，可以直接拿去写 07 页的权限名单。

学习目标

  • 说清一个工具来自哪里（内核 / 哪个插件 / MCP），并知道「只读」不是工具自己声明的；
  • 查到一个工具的参数名、类型、必填与默认值，并写出一次正确的调用；
  • 知道每个工具各自的硬性限制（单行超限、匹配多处、耗时上限、UTF-8 限制……），避免撞上报错才去找原因；
  • 理解 shell 的四个反直觉行为：全新 shell、stdin 关闭、合并输出、非零退出码不算错误；
  • 会用 todo_* 五个工具与它们的状态取值；
  • 会配 pathPolicy 路径闸门，知道它「是什么、不是什么」；
  • 知道怎么让某个工具不出现、怎么让某个工具必须审批。

「只读」不是工具自己声明的

ToolDescriptor（工具描述符）里没有「是否只读」这个字段，它曾经有、现已移除。 原因是那个设计让「只读」变成了由被判定的一方自己申报：提供方可以把自己的工具塞进任何基于它构建的名单里， 用户没有任何手段拿出来（MCP 那一侧更极端，「提供方」是不受信的外部进程）。

现在的口径是：只读与否完全由用户配置决定（例如 plan 模式插件的 plugins.configurations.jellyfish-plugin-plan.readOnlyTools，以及 MCP 插件配置里那个同名的 readOnlyTools）。描述符只回答「这个工具叫什么、怎么用、要什么参数」。 因此上表「是否只读」一列只写 README 的归类，真正的判定永远看你写的名单。

不装插件，就只有 task

内核只保留插件机制与 SPI，全部文件、命令、待办、技能、编排工具都在 Jellyfish-Plugins 仓库里。 拿到 jellyfish-cli-0.1.1.jar 直接跑，会看到一个近乎空转的 agent。 装哪些、怎么装见 11 安装与使用官方插件；插件 jar 的增删只在启动期确定，必须重启进程。

内核自带：task

task：把一段子任务委派给子代理

是什么
把一段自足的子任务交给一个 delegatable: true 的 agent 去做，只拿回它的最终结论。 它是内核自带的能力：把模型给的参数翻成一次委派、把子代理的进度转给外壳、把结果渲染成回灌文本。
怎么用
通常由模型自己决定何时调用。手动验证： 
{
  "subagent_type": "scout",
  "description": "摸清鉴权链路",
  "prompt": "读 src/main/java 下所有与鉴权相关的文件，回答三个问题：1) 入口类叫什么；2) token 在哪校验；3) 有哪些失败分支。结论里给「文件:行号」依据。"
}

配置

字段类型必填默认值含义示例
subagent_type string 必填 — 子代理类型，可取系统提示中列出的可委派类型之一 "scout"
description string 选填 null（不写即缺省；此时开场行只写「开始」） 一句话说明这次委派要做什么，供人阅读与日志排查 "摸清鉴权链路"
prompt string 必填 — 给子代理的完整任务说明。它看不到本次对话，因此必须自足 "读 src/auth 下所有文件，列出……"

subagent_type 缺失时工具一次都不跑，回一条 「[子代理未开始] 缺少参数 subagent_type……」，并带上终态标记（界面显示警示，而不是「正常跑完」）。 参数类型写错时由内核的委派器给出可用清单。

它与 07 页讲的 subAgent 配置段是一套东西： maxDepth / maxSpawnsPerTurn / maxConcurrentRuns 都作用在它上面， subAgent.enabled: false 会让这个工具直接不再注册，模型根本看不到它。

生效方式：/reload 生效（subAgent.enabled 关掉后 task 不再注册；maxDepth 等三个键需重启，见 07 页）。

常见问题

  • 模型看不到这个工具？先查 subAgent.enabled 是不是 false，或没有任何 agent 标 delegatable: true。
  • 子代理改动了我的文件？给它配只读的 allowedTools。

tools 插件：六个文件与提问工具

插件 id 与配置段名都是 jellyfish-plugin-tools。它提供五个文件工具、一个提问工具、 输入框的 @ 文件引用，以及按路径收口的闸门 pathPolicy。

read_file：按行分片读取文本文件

是什么
读取一个文本文件的内容；大文件可用 offset 与 limit 分片读取，避免一次读入过多内容。
怎么用
{ "path": "src/main/java/App.java", "offset": 1, "limit": 120 }

配置

字段类型必填默认值含义示例
pathstring必填—文件路径，相对路径按进程工作目录解析"src/main/java/App.java"
offsetinteger选填从第一行开始起始行号，从 1 开始200
limitinteger选填读到文件末尾最多读取多少行120
max_bytesinteger选填65536（64 KiB）最多读取多少字节；命中 limit 或 max_bytes 会提示续读131072
单行就超过 max_bytes 时它会报错，不切短

切短会输出一行「看起来完整、实际残缺」的内容，模型无从判断自己拿到的是不是全文。 错误文案给出三条出路：缩小 limit、调大 max_bytes、或改用 grep_files 定位。

多行累加超预算仍照旧分页（内容还在文件里，可按 offset 续读）。 另外 read_file 反过来必须能读任意文件：非法字节处停下并明确说「这不是合法 UTF-8」， 而不是把每个字节都换成问号。

常见问题

  • 报「单行超过 max_bytes」？按上面三条出路改参数。
  • 读到一半停了？可能是被 Esc 取消。三个读工具取消时都会说清是哪一种停——它不会把「已取消」说成「没有匹配」。

write_file：整文件覆盖写

是什么
把内容整体写入文件（UTF-8，会覆盖原内容）。父目录不存在时自动创建；输出区分「新建」与「覆盖」。
怎么用
{ "path": "notes/plan.md", "content": "# 计划\n\n1. 先跑起来\n" }
只改一处请用 edit_file，不要整份重写。

配置

字段类型必填默认值含义示例
pathstring必填—文件路径，相对路径按进程工作目录解析"notes/plan.md"
contentstring必填—要写入的完整文件内容"# 计划\n"

常见问题

  • 把原文件冲掉了？它本来就是整文件覆盖。想保留原文只改一处，用 edit_file。
  • 写到工作目录外面去了？那是 pathPolicy 的 write 方向管的事，见本页最后的路径闸门一节。

edit_file：字面量精确替换

是什么
在文件中精确替换一段原文（字面量匹配，按 UTF-8 读写）。匹配到多处且未声明 replace_all 时会报错而不改文件。
怎么用
{
  "path": "src/main/java/App.java",
  "old_text": "return null;",
  "new_text": "return Optional.empty();"
}

配置

字段类型必填默认值含义示例
pathstring必填—文件路径，相对路径按进程工作目录解析"src/main/java/App.java"
old_textstring必填—要被替换的原文，必须与文件中完全一致（含缩进）"return null;"
new_textstring必填—替换后的新文本，可以是空串（等于删除）"return Optional.empty();"
replace_allboolean选填false原文匹配到多处时是否全部替换true
它只改 UTF-8 文本

文件里出现非法 UTF-8 字节时直接拒绝：它整份读出、整份写回，一次替换会把 GBK 文件整体变成乱码， 那是不可逆的损毁。写入走同目录临时文件 + 原子替换，并且读之后、写之前会再看一眼文件有没有被别人改过。

常见问题

  • 报「匹配到多处」？把 old_text 写到唯一（带上上下文缩进），或显式声明 replace_all: true。
  • 报「不是合法 UTF-8」？目标文件不是 UTF-8 编码。它不会替你转码，请先用别的工具转成 UTF-8。

list_dir：列举一层目录

是什么
列举一个目录的直接子项（不递归）。目录名以 / 结尾，文件带字节数；不过滤 target 之类；大目录可分页。
怎么用
{ "path": "src/main/java", "offset": 1, "limit": 100 }

配置

字段类型必填默认值含义示例
pathstring选填当前工作目录目录路径，相对路径按进程工作目录解析"src/main/java"
offsetinteger选填从第一项开始起始条目序号，从 1 开始201
limitinteger选填200每页最多返回多少项100

一条只管耗时的上限：枚举本身最多 50000 项，撞上会说明「总数不是全量」。 这个上限不改变结果语义、只在真撞上时兜底（正常项目的源码树远小于它）。

常见问题

  • 看到一堆 target/ 之类的目录？它不过滤，自己往下钻或改用 grep_files（那个会跳过 .git/target/node_modules）。
  • 提示「列举被中止，以上不是完整内容」？被 Esc 取消了。它不会把这个说成「空目录」。

grep_files：逐行正则搜索

是什么
在文件或目录树中按正则表达式逐行搜索，返回「文件:行号:该行内容」。会跳过 .git/target/node_modules 等目录与二进制文件。
怎么用
{ "pattern": "class .*Manager", "path": "src/main/java", "max_results": 30 }

配置

字段类型必填默认值含义示例
patternstring必填—Java 正则表达式，对每一行做查找（不是整文件匹配）"class .*Manager"
pathstring选填当前工作目录搜索起点，可以是文件或目录，相对路径按进程工作目录解析"src/main/java"
max_resultsinteger选填100最多返回多少处匹配30
max_line_charsinteger选填500单行最多显示多少字符，超出部分截尾200
max_bytesinteger选填65536（64 KiB）结果总字节上限131072

另一条只管耗时的上限：最多访问 20000 个文件。为什么需要它： 上面那三个结果上限都要「先有匹配」才生效，而搜一个不存在的词时一处匹配都不会有、遍历却要走完整棵树—— 在网络挂载上就是几分钟。

常见问题

  • 它说「未扫完整棵树」？撞上 20000 个文件的兜底上限，或搜索被中止。两种情况它都会明说，不会含糊成「没有匹配」。
  • 搜不到却走得很久？正是上面那条上限要解决的情况。

ask_user：向用户提问

是什么
把一个问题连同 2~6 个候选项摆到用户面前，等他选一个或自己填，答案以工具结果回灌给模型。 它是这个插件里唯一持有外部依赖的工具（经内核的提问端口拿到），其余工具都是无状态的纯函数。
怎么用
{
  "question": "这次改动要保留向后兼容吗？",
  "options": [
    { "id": "keep", "label": "要兼容", "description": "老接口继续可用，代价是多一层适配" },
    { "id": "break", "label": "可以破坏", "description": "直接改，版本号升一位" }
  ]
}

配置

字段类型必填默认值含义示例
questionstring必填—你要问的问题，一句话说清在纠结什么"要保留向后兼容吗？"
optionsarray<object>必填—候选答案，2~6 个[{ "label": "要兼容" }, { "label": "可以破坏" }]
options[].idstring选填按序号 1、2、3…选项标识，回传时用它"keep"
options[].labelstring必填—给用户看的选项文案"要兼容"
options[].descriptionstring选填null（不写就没有说明；界面只显示 label）补充说明，帮用户分辨这个选项"老接口继续可用"

四条必须知道的口径

  • 它不是审批：用户选任何一项都不会放行任何工具，只是把答案告诉模型。权限仍然只由内核的 PermissionManager 收口。
  • 拿不到答复不算失败：没有交互界面的外壳（-cli）、子代理回合、等待超时，三种都返回成功的工具结果，内容说明原因并让模型自行判断。做成失败会让模型以为环境出错、反复重试同一个提问。
  • 子代理回合里当场拒绝：外层界面按当前会话取待答项，而子代理有独立的会话，它的提问不会出现在任何界面上。
  • 超时来自 jellyfish.json 的 ask.timeoutSeconds（缺省 120 秒），不是本插件的配置段。

生效方式：提问超时键 ask.timeoutSeconds 属配置内容，/reload 生效。

常见问题

  • -cli 里提问没人答？正常，它会回一条「用户没有回答」让模型继续。
  • 选项数量报错？只能 2~6 个（超出一个模态框能读完的量，用户会开始随便选）。

输入框的 @ 文件引用（不是工具）

是什么
输入框敲 @ 弹补全面板（目录在前、可逐层往下钻），接受后路径写进输入框。 它不内联文件内容——读取由模型调用 read_file 完成。
怎么用
@src/main/java/App.java 帮我看看这个类的空指针风险
路径里的空白用 \ 转义：含空格的文件名会补全成 @my\ file.txt （插入时转义、匹配前还原、外壳切片段时认转义，三处共用同一条规则）。

为什么这么设计：不内联意味着大文件不会撑爆上下文，权限与 max_bytes 照旧生效。

常见问题

  • 模型把 \ 也当成文件名的一部分？约定里已明说「\ 是空格」；如果你在自己写的提示词里解释 @ 引用，记得也写这一句。

shell 插件：shell

shell：在本机执行命令

是什么
让模型在本机执行一条 shell 命令并返回输出。命令原文交给 /bin/sh -c 执行，因此管道、重定向、 通配符都按 shell 语义工作。它没有沙箱：命令以本进程的权限运行，能读写你这个用户的任意文件。
怎么用
{ "command": "mvn -q -DskipTests package", "cwd": "/path/to/repo", "timeout_seconds": 600 }
也可以直接手敲一条，不进模型： 
!git status

配置（工具自身的参数）

字段类型必填默认值含义示例
commandstring必填—命令行原文，交给 /bin/sh -c 执行——管道、重定向、通配符都按 shell 语义工作"git status"
cwdstring选填进程工作目录工作目录，相对路径按进程工作目录解析"/path/to/repo"
timeout_secondsinteger选填120（跟随插件配置 timeoutSeconds）本次调用的超时秒数，被 maxTimeoutSeconds（1800）钳制600

五个反直觉但必须记住的行为

  • 每次调用都是一个全新的 shell，cd 不跨调用保留：需要换目录就用 cd 目录 && 命令 或传 cwd。
  • stdin 在启动后立即关闭：vi / ssh / sudo 这类交互式命令会立刻失败（TUI 处于 raw 模式，子进程直接写终端会把界面画烂）。
  • stdout 与 stderr 合并成一条流（到达顺序，像终端）。
  • 非零退出码是结果而不是错误：grep 没匹配到返回 1，这在输出里如实报告；工具调用本身不算失败。
  • 输出边产生边捕获：内存占用与输出体积无关，超限部分落盘，回灌给模型的是头尾预览加路径。每个落盘文件名都带一段唯一片段（调用 id + 工具名 + 纳秒时间戳），因此同一次调用独占一个路径。

被终止时会说清是哪一种：墙钟超时、静默判定、取消，还是插件被停掉（热部署 / 内核关闭）， 并附上已捕获的部分输出。静默超时报的是「真的静默了多久」，不是总耗时——一条先跑了十分钟、再卡住的命令， 说成「连续 600 秒无输出」会把有输出的那十分钟也算进去。

执行期输出实时可见：-cli 写到 stderr，-tui 在消息区显示「运行中的工具轨迹」块。

!命令 输入指令：手动执行一条命令，不进模型；执行完把「命令回显 + 输出」作为一条用户消息落进会话， 因此下一次提问时模型看得到结果。它复用与模型调用完全相同的执行链路，照旧过权限与审批；Esc 可以中断正在跑的命令。

插件配置（plugins.configurations.jellyfish-plugin-shell）

字段类型必填默认值含义示例
timeoutSecondsint选填120命令最多允许跑多久；单次调用可用 timeout_seconds 参数覆盖。不支持「不超时」300
maxTimeoutSecondsint选填1800单次调用能声明的超时上限3600
idleTimeoutSecondsint选填0（关闭）连续多久没有任何输出就判定卡住。模型不能设置它，它是用户的环境策略600
environmentobject选填{}额外注入或覆盖的环境变量；另有一组防挂死默认值可被这里盖掉{ "MAVEN_OPTS": "-Xmx1g" }

commandPolicy.readOnlyCommandsarray<string>选填[]追加在内置只读表之后。内置表不可替换，只能追加；也支持整条 *（一律按只读放行，等于把审批整体关掉）["gh pr view"]
commandPolicy.deniedPatternsarray<string>选填[]追加在内置拒绝形状（rm -rf /、mkfs、of=/dev/、:(){）之后，同样不可撤销["curl .* \\| sh"]

权限判定的六道（每次调用依次过，先拒绝后免打扰、最后才问人）：

  1. 按未引用状态下的 ;、|、&、换行切成子命令，每一段各自过一遍下面的表（取最严的结果）；
  2. allowedCommands 非空且任一段没命中 → 直接拒绝（默认拒绝的硬门）；
  3. 命令原文命中拒绝形状（rm -rf /、mkfs、dd of=/dev/）→ 直接拒绝；
  4. 所有段都命中 commandPolicy.trustedCommands → 免审批，直接执行；
  5. 含命令替换（$(...)、反引号）或重定向（>、<）→ 升级为人工审批；
  6. 所有段都命中只读表（ls、git status、cat……）→ 免审批；否则 → 升级为人工审批。

「全部」只有一种写法：整条 *。三个表都认它，含义随表而定——allowedCommands 里是 「准入不再拦任何命令」（等于白名单不表态），trustedCommands 里是「一律免审批」， readOnlyCommands 里是「一律按只读放行」（等于把审批整体关掉）。它只解除自己所在的那一道门： 拒绝形状、命令替换 / 重定向升级问人照旧生效。条目里带别的字符时仍按 1 / 2 token 的前缀规则匹配， 因此 git * 这类半个通配按字面量匹配、永不命中（单 token 的 git 本来就覆盖 它的全部子命令），配置解析时会为这种条目发一条告警，不让它静默失效。

allowedCommands 是免审批表之外的独立机制，白名单不解除审批

allowedCommands 里的 mvn test 每次仍然弹批准框，因为白名单只回答「能不能跑」。 要它静默执行，就把同一条前缀也写进 commandPolicy.trustedCommands。 「允许跑但每次都要我批准」这种姿态仍然写得出来——只配白名单、不配可信表即可。

同理，commandPolicy.enabled=false 会连第 5 步一起关掉；白名单、可信表、拒绝形状照旧生效。

分类器不是安全边界

FOO=bar cmd、别名、sh -c 嵌套照旧能绕过前缀判定。它也不做目录围栏（可绕过： cd /、绝对路径、sh -c 嵌套），与文件工具没有围栏也不自洽。 真正的边界是审批加白名单。

另外两点边界：-cli / -server 下没有人在场，askTools 等于禁用， 免审批的放行口只剩「被分类器判为只读的命令」与「trustedCommands 里的命令」（白名单非空时还得先过白名单）； 进程树只能尽力杀（sh -c 的直接子进程是 shell，杀掉它不一定带走孙进程），杀不干净是已知边界。

生效方式：插件配置段改动 /reload 生效（/reload 会只重启配置段变了的插件）。

常见问题

  • 想在无人值守下跑 mvn test？必须把它写进 trustedCommands（-cli/-server 里 ASK 等于拒绝）。
  • 每次 git status 也要批准？你把 shell 整个写进了 askTools：核心策略的 ASK 无法被插件的「无异议」降级，插件的裁定只能收紧、不能放宽。
  • 命令卡住了？用 idleTimeoutSeconds（「多久没动静就当死了」），它是用户的环境策略，模型改不了。
  • Windows 能用吗？非 POSIX 平台映射成 cmd.exe /c，但 README 明说没有在真机上跑过。

todo 插件：五个待办工具

待办是模型的计划草稿，由插件自己持有（内核没有会话待办字段、也没有 /todo 系统命令）。 五个工具的分工是「父回合写计划、子代理认领并推进」。

工具参数（必填加粗）语义
todo_write todos（数组，元素含 content、status、选填 reason） 模型写待办的唯一入口。整表覆盖：传完整的新列表，上次列过而这次没列出的项视为删除，空数组表示清空
todo_claim 无参数（认领「下一条」） 子代理认领一条还没人做的待办：原子地标成 in_progress 并记下自己的 run 标识。一个 run 只认领一条。顶层回合不在任何 run 上，会被拒绝
todo_done content 把一条待办标成完成（content 传原文）。别人正认领着的条目只有认领者能完成；无主的条目谁都可以完成
todo_release content 把一条待办放回去（清认领、回未开始，谁都能接）：用于「我没做它」
todo_block content、reason 把一条待办记成卡住：用于「它做不了」。卡住之后不会再被任何子代理认领，直到有人放回或父回合重写清单

配置——状态取值与插件配置段：

字段类型必填默认值含义示例
todos[].content string 必填 — 待办内容。要简短、可执行 "补齐 UserService 单测"
todos[].status string（枚举） 必填 参数 Schema 里必填（required 含 content 与 status）；解析层则对缺失兜底：取不到时按 pending 处理 取 pending / in_progress / completed / blocked。读的时候忽略大小写与连字符（In-Progress 也认），写出去的一律是小写下划线 "in_progress"
todos[].reason string 选填 无 blocked 才带 reason，写在别的状态上会被丢掉 "缺权限，连不上测试库"
todoDir string（路径） 选填 ~/.jellyfish/todos 待办文件目录，一个会话一个 JSON 文件，空表会删掉文件 "~/.jellyfish/todos"

四态与标记的对应：pending = [ ]、in_progress = [~]、 completed = [x]、blocked = [!]。

完整示例

{
  "todos": [
    { "content": "读一遍鉴权入口", "status": "completed" },
    { "content": "补齐 UserService 单测", "status": "in_progress" },
    { "content": "跑通集成测试", "status": "pending" },
    { "content": "接上真实支付网关", "status": "blocked", "reason": "缺沙箱环境凭据" }
  ]
}

三条协作口径

  • 父子共享同一份清单，而「父」是内核沿父链算出来的归属会话（嵌套委派下孙代理读写的仍是用户那一份；分支会话归自己）。
  • 谁可以动哪一条：认领者可以完成、放回、卡住自己那条；父回合可以放回或卡住任何一条，但不能替别人说「做完了」；已完成的条目不接受退回。
  • 参数非法当场报错（todos 不是数组、content 为空、status 不在取值内），并带上实际收到的值，作为工具结果回灌给模型让它自己改。

为什么「做不了」必须是一个状态：没有它，一条做不了的活只能一直停在 pending， 于是一批一批的子代理反复把它领走、反复失败——抢单式协作最容易烧钱的地方就是这个。

生效方式：/reload 生效。

常见问题

  • 顶层回合调 todo_claim 被拒？正常：只有子代理能认领，父回合负责写计划。
  • 面板上某条显示「认领者已结束」？那是「子代理没把活标完成就走了」的信号；卡住的条目要显式 todo_block 或放回。
  • 待办会进 system prompt 吗？不会。每轮把待办块拼在本轮用户消息前面送达——system prompt 是缓存前缀的第 0 个 token，待办每勾掉一项都会作废整个请求。

workflow 插件：workflow

workflow：按 spec 编排多个子代理

是什么
让模型一次说清「几件事、什么顺序、怎么合起来」，由插件把它们变成一批并行跑的子代理。 没有 needs 的步骤立刻开始，因此它们并行执行。
怎么用
只派一个子代理做一件事时用内置的 task；「几件事可以同时做、再把结果合起来」才用 workflow。

配置——工具只接受一个参数 spec：

字段类型必填默认值含义示例
specobject必填—编排定义{ "spec": { "steps": [ … ] } }
spec.namestring选填面板退回显示 id人类可读名字，只用于编排面板展示，不进任何机器可读的位置；面板上按显示宽度截到 20 列（中日韩算两列）"调研并写方案"
spec.stepsarray<object>必填—步骤列表，最多 12 步[ { "id": "probe-a", … } ]
spec.steps[].idstring必填—被 needs 引用的键"probe-a"
spec.steps[].namestring选填面板退回显示 id人类可读名字，只用于面板展示；超过 20 字会被截短"调研 A 方向"
spec.steps[].agentstring必填—这一步派给哪个 agent（必须是可委派的）"scout"
spec.steps[].promptstring必填—这一步的任务说明"调研 A 方向……"
spec.steps[].needsarray<string>选填无（立刻开始，因此并行）依赖的步骤 id；等这几步结束，并把它们的结论拼进本步任务["probe-a", "probe-b"]
spec.steps[].whenstring（枚举）选填always只有三个取值：always / on_success / on_failure（后者必须声明 needs）"on_failure"
spec.aggregate.modestring（枚举）选填collect（不写就按顺序拼接各步正文）collect 按顺序拼接各步结论；summarize 再派一个子代理把它们汇成一段结论。取值只能是这两个"summarize"
spec.aggregate.agentstring选填null（不写即缺省）；但 mode: "summarize" 时必须给，否则整份 spec 被拒汇总那一步派给哪个 agent；collect 下它没有意义"planner"

完整示例（README 原文）：

{"spec": {
  "name": "调研并写方案",
  "steps": [
    {"id": "probe-a", "name": "调研 A 方向", "agent": "scout", "prompt": "调研 A 方向……"},
    {"id": "probe-b", "name": "调研 B 方向", "agent": "scout", "prompt": "调研 B 方向……"},
    {"id": "plan", "name": "写方案", "agent": "planner", "prompt": "结合 A 与 B 的结论给出方案",
     "needs": ["probe-a", "probe-b"]}
  ],
  "aggregate": {"mode": "summarize", "agent": "planner"}
}}

五条必须知道的边界

  • 结论是有损转交的：每个依赖各有字符额度（合计上限 20000 字符，对齐 react.maxToolOutputChars），超出部分只给头部，并在材料块首标注被截了多少字、完整记录在哪个归档文件里。
  • 没有循环、变量、表达式，也没有重试——要改主意就重新提交一份 spec。
  • 校验全部发生在派生任何子代理之前：写错的 spec 不会先烧掉几个子代理再报错；装不下时整份拒绝。
  • 受本回合的派生额度限制（subAgent.maxSpawnsPerTurn，缺省 12），与 task 等别的调用方共享。一次编排最多能派的子代理数 = 步骤数 +（声明 summarize 时那一次汇总）。
  • 一次 workflow 会占住一条工具执行线程直到整批跑完（与 task 同口径）；按 Esc 取消回合会掐断全部在途 run。

子代理来自内核的委派端口，与内置的 task 工具走同一条代码路径：并发上限、深度、墙钟与 token 预算、 取消、用量归集与归档的行为完全一致。插件不自己起线程池。不装它也能用：只需要「派一个子代理做一件事」时用内置的 task。

跑的时候看得见：消息区上方有一块「编排」面板。标题行给「进度（已了结/总 步数）· 整条编排已跑多久 · 几个在跑」， 正文把步骤画成一张图：链压一行（L1 [x] 调研 A（scout） ───> L2 [~] 写方案（planner））、 汇合（多上游用 ┬/┤/┘ 的竖线汇到第一个上游那一行）、 分叉（第一个下游接在行内，其余从同一列往下引）。同一层 = 可以并行，一眼能数出哪几步在一起跑。

MCP 插件：mcp__<server>__<tool>

把外部 MCP server 的工具接进来

是什么
用 stdio 连上外部的 MCP server，把它的工具当作本机工具使用。
怎么用
工具名带前缀：mcp__<server>__<tool>。server 给的工具名可能与内置工具或 另一个 server 重名，前缀让「谁占谁的位置」不成为事实；字符会被清洗成厂商允许的集合，超长时保留前缀并追加哈希。 
mcp__filesystem__read_file
mcp__filesystem__list_directory

配置（plugins.configurations.jellyfish-plugin-mcp）

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-mcp": {
        "servers": [
          {
            "id": "filesystem",
            "command": "npx",
            "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
            "env": { "SOME_TOKEN": "${SOME_TOKEN}" },
            "callTimeoutSeconds": 60,
            "readOnlyTools": ["read_file", "list_directory"]
          }
        ],
        "askWriteTools": true,
        "startupWaitSeconds": 5
      }
    }
  }
}
字段类型必填默认值含义示例
servers[].idstring必填—server 标识，工具名前缀用它"filesystem"
servers[].commandstring必填—起 server 子进程的可执行文件"npx"
servers[].argsarray<string>选填[]（空数组，不是 null）启动参数["-y", "@modelcontextprotocol/server-filesystem", "/tmp"]
servers[].envobject选填{}（空对象，不是 null）env 是拿到环境变量的唯一通道：子进程只继承 PATH / HOME / LANG / LC_* / TMPDIR / TEMP / TMP / USER / LOGNAME / SHELL（Windows 另加 SystemRoot / PATHEXT / ComSpec / windir）{ "SOME_TOKEN": "${SOME_TOKEN}" }
servers[].callTimeoutSecondsint选填60单次工具调用的超时；0 表示不超时（上限 3600 秒）120
servers[].readOnlyToolsarray<string>选填[]本插件审批策略用的只读名单（与 plan 插件的同名键无关）["read_file", "list_directory"]
askWriteToolsboolean选填true写类工具是否要人工审批false
startupWaitSecondsint选填5启动期等多久让第一轮就能看到工具；超时就转异步10
重连退避——1s → 60s不可配：初始 1 秒、每次翻倍、封顶 60 秒，共 6 次（合计约一分钟）【不可配】

六条口径

  • 连接发生在启动之后：某个 server 装错了不会让内核起不来。
  • 断开会按退避自动重连，用尽就停；重连期间该 server 的工具先被摘掉（留着它们，模型会继续调用一批每次都以「未连接」收场的工具）。约一分钟后仍连不上，就停在「失败」并写明 /reload 可重试。
  • 只读只认你写的 readOnlyTools（server 自填的 readOnlyHint 不再采纳）；缺省一律按可写。
  • 清单拿不到时保留旧清单：「确实没有工具」（"tools":[]）与「它没给我们清单」是两件事。
  • 协议能力：声明 roots（把进程工作目录告诉 server）；不声明也不支持 sampling / elicitation，被请求时回一条明确的错误而不是挂在那里等。
  • 二进制内容落盘：server 返回的图片 / 音频写到系统临时目录下的 jellyfish-plugin-mcp/<pid>/，回灌给模型的只是一个路径；插件停止时整个目录会被删掉。
子进程的环境是白名单，反过来也要小心

宿主 JVM 里有各 provider 的 API key，而对面是个不受信的第三方进程——「继承」意味着它们会一起过去。 要传别的东西（含密钥）就写在 env 段里：显式即允许。 另外，启动日志里的参数值会按旗标名遮蔽（--token sk-xxx、--api-key=... 打成 ***）， 但识别只按旗标名、不按值的样子猜——把密钥塞进 --header "Authorization: Bearer x" 这种普通旗标的值里，这里认不出来。

-cli / -server 下没有审批者：ASK 等于拒绝，因此这两个模式里写类 MCP 工具实际不可用（与 shell 同理）。

生效方式：/reload 生效（配置段变了才重启这个插件；/mcp 看连接状态）。

常见问题

  • 工具名和内置的撞了？注册不成的名字不会被当成我们的工具，因此不会连累被撞的那个工具多一道审批；两个 server 提供同名工具时按最严算。
  • server 挂了怎么办？看 /mcp——每个 server 的连接状态、工具数与失败原因，连不上时的唯一线索。

tools 插件的路径闸门：pathPolicy

文件工具在允许的路径之外时会升级为人工审批或直接拒绝。粒度是「工具名 + 路径」， 而不只是工具名——否则「允许 write_file」就等于「允许往任何地方写」。 配置位置：plugins.configurations.jellyfish-plugin-tools.pathPolicy。 

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-tools": {
        "pathPolicy": {
          "write": { "allow": ["."], "outside": "ask" },
          "read":  { "allow": [".", "~/.jellyfish"], "outside": "deny" }
        }
      }
    }
  }
}

配置

字段类型必填默认值含义示例
write object 选填 按缺省（只允许工作目录、范围外要审批） 写方向的规则。不配就按缺省 { "allow": ["."], "outside": "ask" }
read object 选填 不配就不设限 读方向的规则 { "allow": [".", "~/.jellyfish"], "outside": "deny" }
….allow array<string>（路径数组） 选填 ["."] 允许的目录。相对路径按进程工作目录解析、行首 ~ 按用户主目录；因此 "." 就是工作目录 [".", "~/.jellyfish"]
….outside string（枚举） 选填 ask 范围之外的裁定，取 allow / ask / deny。allow 等于把该方向的门关掉（恒无异议） "deny"

五条口径

  • 哪些工具受管由工具自己声明：read_file / list_dir / grep_files 归读， write_file / edit_file 归写，ask_user 不碰路径因此不受管。 闸门不认识别家的工具——shell、MCP 工具送到它面前时一律「无异议」。
  • 判据看的是真实位置：符号链接会先解开再比。工作目录里放一个指向 /etc 的链接不会成为后门。 对「准备新建的文件」这类还不存在的路径，解开它最近一个已存在的祖先、尾段原样保留。
  • ask 在没有审批界面的外壳里等于拒绝：-cli 不挂审批通道，因此工作目录外的写在那里会直接失败。 要放开就把该方向配成 outside: "allow"，或把目录加进 allow。
  • 它不是文件系统沙箱：管不了 shell 命令里出现的路径（那是命令策略的事），也管不了 MCP 工具。 它管的是本插件这几个文件工具的 path 参数。
  • 配置写错只回退并告警，不会让插件起不来：告警走 ConfigWarningEvent（TUI 上看得见）。

生效方式：/reload 生效。

常见问题

  • -cli 里往工作目录外写直接失败？因为 write.outside 缺省是 ask，而 -cli 没有审批者，ask 就等于拒绝。
  • 读也被拦了？说明你配了 read 方向（不配就不设限）。

怎么让某个工具不出现 / 必须审批

想要的效果写哪里实际行为
某个工具调用被拒 agents.json 的 deniedTools 模型仍看得到工具，但每次调用都被拒（页面见 07）
某个 agent 只放行少数工具 agents.json 的 allowedTools 白名单之外的调用被拒；同时决定子代理能看到哪些工具（只随委派生效）
某个工具每次都要我批准 agents.json 的 askTools -tui 弹框、-server 走 SSE、-cli 一律拒绝
整类工具彻底消失 jellyfish.json 的 plugins.enabled / plugins.disabled，或把插件 jar 拿掉 插件不加载，它注册的工具一个都不存在。增删 jar 必须重启进程
只让 task 不再注册 jellyfish.json 的 subAgent.enabled: false task 工具直接不再注册，模型看不到它；/reload 生效
会话级「先看别改」 plan 插件的 readOnlyTools 白名单 + /plan on 不换工具清单，只拦执行：模型看到的清单不变，写操作在执行时被拒
文件工具只在特定目录里能用 tools 插件的 pathPolicy 按「工具名 + 路径」裁定：allow 内放行，outside 决定越界时是 allow / ask / deny
MCP 写类工具要批准 MCP 插件的 askWriteTools 与 servers[].readOnlyTools 只读只认你写的名单；缺省一律按可写
shell 里「允许跑但每次批准」 shell 的 allowedCommands（只配白名单、不配可信表） 白名单只回答「能不能跑」，不解除审批；要静默执行须写进 trustedCommands
shell 的命令「一次全放开」 allowedCommands: ["*"]；连审批也不弹就再把 commandPolicy.trustedCommands 写成 ["*"] 整条 * 表示匹配全部命令，含义随表而定（白名单 = 不拦、可信表 = 免审批、只读表 = 按只读放行）；只适合你自己完全掌控的机器，因为前缀判定这一层整个交出去了

常见问题

工具清单里没有 read_file / shell？
大概率是插件没装或没加载。先确认 jellyfish-plugin-tools / jellyfish-plugin-shell 的 jar 在扫描目录（缺省 ~/.jellyfish/plugins/）里，然后重启进程——插件 jar 的新增 / 删除只在启动期确定。再看一眼 plugins.enabled / plugins.disabled 有没有把它排除掉。
read_file 报「单行就超过 max_bytes」？
三条出路：缩小 limit、调大 max_bytes、或改用 grep_files 定位。它刻意不切短——切短会输出一行「看起来完整、实际残缺」的内容。
edit_file 报「匹配到多处」？
把 old_text 写到唯一（带上下文缩进），或显式声明 replace_all: true。这是刻意的：默认不猜你想改哪一处。
在 -cli 里写工作目录外的文件直接失败？
pathPolicy.write.outside 缺省是 ask，而 -cli 没有审批界面，ask 就等于拒绝。放开就把该方向配成 outside: "allow"，或把目录加进 allow。
ask_user 没弹框，模型却继续干了？
「拿不到答复不算失败」是刻意的：-cli、子代理回合、等待超时三种情况都返回成功的工具结果，让模型按自己的判断继续。超时值在 jellyfish.json 的 ask.timeoutSeconds（缺省 120 秒）。
shell 返回了非零退出码，是出错了吗？
不是。非零退出码是结果而不是错误（grep 没匹配到就是 1），它在输出里如实报告，工具调用本身不算失败。
想知道某个工具「算不算只读」？
没有这个概念。工具无法自称只读（描述符里已无该字段），只看你把它写进了哪份名单：plan 的 readOnlyTools、MCP 的 servers[].readOnlyTools。

关键结论

  1. 工具来自三处：内核只有 task，其余全在插件里（tools / shell / todo / skills / workflow / MCP），因此「不装插件几乎什么都干不了」是设计而不是缺陷。
  2. 「只读」不是工具自己声明的：ToolDescriptor 里没有该字段，只读与否完全由你写的名单决定（plan 的 readOnlyTools、MCP 的 servers[].readOnlyTools）。
  3. 三个读工具（read_file / list_dir / grep_files）都响应 Esc，并且都会说清「停下来时是哪一种停」——绝不把「已取消」说成「没有匹配」「空目录」。
  4. read_file 单行超限报错不切短；edit_file 匹配多处报错不改文件、且只改 UTF-8；list_dir / grep_files 各有一条只管耗时的兜底上限（50000 项 / 20000 文件）。
  5. shell 的四个反直觉点：每次调用全新 shell、stdin 启动即关闭、stdout 与 stderr 合并、非零退出码是结果不是错误；它没有沙箱，真正的边界是审批加白名单。
  6. pathPolicy 管的是 tools 插件这几个文件工具的 path 参数，判据看真实位置（会解符号链接），它不是文件系统沙箱——管不了 shell 命令里的路径，也管不了 MCP 工具；ask 在没有审批界面的外壳里等于拒绝。
  7. 「让工具不出现」有两条不同的路：改 agents.json 的名单（工具还在，调用被拦）与关掉提供它的插件（工具彻底不存在，需重启）；想让某个工具每次批准就写进 askTools。
