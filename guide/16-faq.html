一、入门与概念

Q1　Jellyfish 是什么？

一个用 Java 1.8 写的轻量级 AI Agent 工具：单次问答（-cli）、交互式终端界面（-tui）、 HTTP 服务（-server）三种形态共享同一个内核。它的结构是「最小内核 + 能力全在插件 + 三外壳共用一份装配」—— 不装插件它几乎做不了事，这是设计而不是缺陷。详见 01 Jellyfish 是什么。

Q2　和 Claude Code / Cursor 有什么不同？

三个代码仓库未提供对比材料：已在 Jellyfish / Jellyfish-Plugins / Jellyfish-Spring-Boot-Starter 三仓检索「对比 / 竞品 / 选型 / 横向对比 / 同类工具 / Claude Code / Cursor」， 唯一的命中是 ContributionCache 的 javadoc 借「Codex 每次运行构建一次指令链、Claude Code 在对话开始时加载 CLAUDE.md」说明自己为什么按会话缓存约定文件——那是设计参考，不是产品对比。 本页因此不做评价也不推测。可以确定的事实只有这些：内核是 Java 1.8 写的、用 PF4J 做插件扩展、与插件之间没有编译期依赖； 工具、命令、会话持久化、压缩等能力全在插件仓库；对外只有 TUI 与 Server 两条界面路径（没有 Web UI）； 权限按 agentId 全局共享、内核没有「用户」这一维。要做选型对比请自行评估 （本套文档的 Jellyfish-Docs/learning/26-comparison.html 另有一页横向对比，但那是文档按各产品官方文档整理、 逐格附来源链接的，不是仓库自带的材料）。

Q3　不装插件能做什么？

只有系统命令：/help、/new、/session、/resume、 /model、/agent、/status、/usage、/delete、 /compact、/reload，其中 -tui 另有 /exit、/ui、 /thinking、/toolargs、/mouse。要发一次对话还得有 models.json； 读文件、跑命令、存会话、压缩都要装插件。内核自带的能力只有 task 子代理工具与 ReAct 循环。

Q4　一个参数都不带会怎样？

等价于 -tui——交互界面是最常用的入口，不必先背旗标。因此它需要可交互终端，在管道 / CI 里会退 3。 兜底只此一处：只要带了任何参数，模式就必须显式给（jellyfish --verbose 一样报「请指定启动模式」并退 2）。 详见 04 三种运行模式。

Q5　-cli / -tui / -server 怎么选？

偶发的一次性问答、脚本或 CI 里跑一次：-cli（-p 给输入，或从 stdin 读到 EOF；有明确的退出码）； 人长期坐在终端前干活：-tui（消息区 + 输入框 + 命令输出面板 + 审批框）； 要让别的程序驱动它：-server（REST + SSE）。注意 --agent / --model / -p / --show-thinking / --show-tool-args 只归 -cli，另两种外壳带上它们判用法错误退 2。

Q6　支持哪些模型厂商？能不能接本地 llama.cpp / 自建网关？

内核自带这些传输类型（providers.<name>.type）：openai、claude、 deepseek、gemini、minimax 及其别名，写错会报错并列出内核认识的类型。 type 也可以由插件提供（自建网关、私有协议、本地 llama.cpp）：插件注册一个新类型，配置里写一个指向它的 provider 即可。 两条硬规则：内核自带的 type 不能被插件顶替（传输请求里带的是已解析好的 apiKey， 能顶替 openai 的插件等于把密钥转发出去）；models 可以由插件动态发现， 且发现结果不落盘——配置文件始终是模型的唯一持久事实。 若你的自建网关本身就是 OpenAI 兼容端点，用 type: openai 加 baseUrl 指过去是通的： baseUrl 的语义就是「服务地址，缺省用该 type 的官方地址」，而 type: openai 走的是 Chat Completions——请求地址由 <baseUrl>/v1/chat/completions 拼出（baseUrl 已含 /v1 时不重复拼）， 鉴权头是 Authorization: Bearer <apiKey>。两个配套点：baseUrl 要填最终地址（客户端不跟随重定向）； 网关要求额外鉴权 / 租户头时用 vendorHeaders，否则会在「发现模型」那一步先失败。 仓库为「自建网关 / 私有协议 / 本地 llama.cpp」另给的路径是让插件注册一个新 type， 两条都成立，按你的网关协议选（仓库没有为前者单开一节，但它落在上面的字段表里）。 详见 06 models.json 详解。

Q7　一个会话的完整历史在哪、会不会丢？

由 jellyfish-plugin-session-file 负责持久化：一个会话一个 JSON 文件，并用 git 管理历史； 装了它，--session / /resume / /session 才有内容可恢复——启动时内核向所有注册了恢复处理器的插件要回会话， 因此上次退出前的会话在下次启动时立即可见。而且历史一条不删：屏幕上的会话、恢复出来的会话、落盘的文件都是完整历史， 压缩与裁剪改变的只是「发给模型的那条链路从哪里开始」。 详见 09 会话与上下文。

Q8　能不能多用户？

内核不行：它是单主体模型——Session 上没有 owner 字段、SessionManager.all() 返回全进程会话、 插件也不做用户隔离，一个 API key 就是一个信任域。要按用户隔离的是 Spring Boot Starter， 它在 user 包里补上了 userId 维度（SessionOwnerStore / ApprovalGateway）， 并给出「不存在」与「不属于你」对外同一个答复这类护栏。详见 14 整合到 Spring Boot。

二、配置与模型

Q9　密钥放哪？为什么不能写进配置文件？

一律走环境变量："apiKey": "${OPENAI_API_KEY}"，然后 export OPENAI_API_KEY=sk-***。 理由是这份文件会外流的地方太多：它会随 git 提交、随配置告警进日志、随项目级配置被 clone / pull 凭空带进工作目录（这也是项目级配置默认不被信任的原因之一，见 Q12）。Server 外壳同理， 优先用 JELLYFISH_SERVER_API_KEY 而不是 --api-key——argv 会出现在 ps 里。 脚本插件的密钥不能靠环境变量传（脚本进程的环境是严格白名单），要走 scripts.<脚本 id> 配置段。

Q10　配置字段写错了会怎样？

models.json 的规则是「表里没列出的字段就是不支持的」：多写一个键不会生效。 读取配置时会比对字段名：内核不认识的字段会发一条 ConfigWarningEvent 并打 WARN （带文件路径与字段名）；react 段、react.toolOutput、每个 provider 的 sampling 段的非法值同样进这个事件面， 并说明「哪个键、原值多少、为什么非法、按什么处理」。 但有一类永远不参与比对：vendorBody 与逐插件配置段这类自由格式的键名由使用方决定，宁可漏报也不报假警。 所以厂商私有键名拼错仍然只能靠 DEBUG 日志里那行「实际下发的键名」发现。

Q11　改了配置要重启吗？

看改的是哪一份：models.json / agents.json / jellyfish.json 的内容改动敲 /reload （重读配置、重建模型 / agent 索引，并只重启配置段变了的插件，同步等结果）； config.json（它只管「其它文件在哪」与插件扫描目录）不参与热更新， 新增 / 删除插件 jar 也必须重启进程。在 Spring Boot 接入方那边 starter 不提供 /reload 的入口，一律重启最省心。 四个高频坑见 15 页 B7。

Q12　项目级 .jellyfish/ 为什么不生效？

因为它默认不加载，只有被显式信任过才参与合并。理由是它的读取基准是进程当前目录， 内容取决于「在哪个目录里启动」，而它能决定的东西很重：models.json 里同名 provider 是整对象替换， 其中的 baseUrl / apiKey 一改，该 provider 的密钥与全部对话正文就送到别处；agents.json 可以新增 agent； jellyfish.json 可以改落盘目录与插件配置。授予方式：-cli / -server 加 --trust-project-config（仅本次进程、不落盘）； -tui 在启动确认框里选 y（记住）或 o（仅本次）。 信任的单位是文件绝对路径 + 内容指纹，不是目录——内容一变信任立即失效。 classpath: 形式的项目级路径不受这道闸管辖。

Q13　上下文满了会怎样？

三层机制依次兜住：① 自动压缩——上下文用到 react.autoCompactPercent（缺省 80）就自动压一次， 跑在当轮模型调用旁边、不拖慢对话，结果下一轮生效；② 机械裁剪——只要某一次请求已触发裁剪（历史正在被静默丢弃），也会立刻压一次； ③ 工具结果老化——把保留窗口之外的信封换成带路径的 stub。 要注意的是压缩本身不是内核能力：只有启用 jellyfish-plugin-compact（或同类插件）才可用，不启用时整体不可用且不回退内置。 详见 09 会话与上下文。

Q14　怎么彻底关掉某个能力？

按能力选开关，全都只改 jellyfish.json 再 /reload：停某个插件用 plugins.disabled: ["jellyfish-plugin-todo"]；关掉子代理委派用 subAgent.enabled: false （task 工具直接不再注册，模型看不到它）；关掉自动压缩用 react.autoCompactPercent: 0 （只留手动 /compact）；彻底关掉工具结果老化用 react.toolOutput.keepRecentMessages: 0 （它同时关掉裁剪与老化）；一个插件都不启用用 plugins.enabled: []。 注意「未声明」与「声明为空」是两回事：不声明表示不额外限定，显式写 [] 表示一个都不启用。

Q15　提示词缓存命中率怎么提高？

厂商的缓存是前缀匹配，改掉历史上的一个字节，后面的整段都会从约 0.1× 的命中价变回 1× 全价。 所以关键在 react.cache.agingPercent（缺省 70）：它必须略低于 autoCompactPercent（80）， 相差约 10 个点——低了才会真正泄压，高了就让压缩先发生、老化永远轮不到；改了自动压缩就应一并重看它。 cache.keepAliveSeconds 能保活但要花钱，且有两个坑（与 Claude 的 thinking.budget_tokens 互斥、 部分新模型对输出上限有最小值要求）。查看当前命中率用 /usage。

Q16　思考强度在哪配？

内核没有 reasoningEffort / thinkLevel 这类字段——四家的形状与取值全不通约， 因此都从 vendorBody 走（provider 级与 model 级深合并）：DeepSeek 用 thinking.type + reasoning_effort； Claude 用 thinking.type + output_config.effort；Gemini 用 generationConfig.thinkingConfig.thinkingLevel。 键名要逐字抄厂商文档、大小写敏感，拼错就是静默无效；排查靠把日志级别调低看实际下发的键名（不打值）。 另外「看不到思考文本」通常是外壳侧没开，见 15 页 F4。

Q17　token 用量在哪看？子代理花的分开算吗？

用 /usage（别名 /cost）看当前会话的 token 用量与缓存命中率。 子代理花掉的 token 计入父会话，因此 /usage 上看得到；但子代理的会话不留痕—— 不落盘、不进 /session 列表。run 的归档另有 subAgent.archiveKeepFiles（缺省 200）与 archiveMaxBytes（缺省 100 MiB）两道配额，与工具输出分开算。

三、使用与权限

Q18　有没有 Web UI？

没有。界面只有两条路：-tui（终端界面），或 -server 暴露 REST + SSE 让你自己写前端。 -server 明确不做自带 Web 前端与 TLS——要上公网请自己在前置代理上做 TLS，并务必配上 API key。 详见 04 三种运行模式。

Q19　能不能在 Windows 上跑？

内核本身是 Java 1.8，没有平台绑定的声明。仓库里对 Windows 的明文只有下面几条，都能直接对上： shell 插件明确「Windows 未验证」（非 POSIX 平台会把命令映射成 cmd.exe /c， 但没有在真机上跑过）；session-file 插件与 tools 插件的 UTF-8 落盘在不支持 POSIX 权限位的平台（Windows） 跳过权限设置，行为保持原样；mcp 插件的子进程环境白名单在 Windows 下另加 SystemRoot / PATHEXT / ComSpec / windir。 除此之外没有别的地方对 Windows 表态。所以「能不能在 Windows 上干活」这件事要在目标环境里验证： 唯一明确未验证的是 shell 那条路，跑一遍 -cli -p "/help" 与一次读写工具调用即可下结论。

Q20　能不能自定义主题 / 界面配色？

仓库没有主题 / 配色配置项——已在三个仓库的源码与配置类里检索 theme / palette / 主题 / 配色：没有任何读取这类键的配置代码（仅有的两处颜色相关代码是 TUI 把颜色语义收在 UiRender 里、并注明「插件换不了主题」，以及 resmon 按阈值给读数行换档位——那是读数表达，不是可配外观）。 而且这件事是明确不做的一类：UI 深度明确不做自定义组件 / overlay、替换 editor / footer / header、 主题与自定义颜色、消息与条目的自定义渲染器、富文本表格。可以调的是显示行为、不是外观，且只有三个系统属性： -Djellyfish.tui.mouseCapture=false、-Djellyfish.tui.pluginPanels=false、-Djellyfish.tui.skipTerminalCheck=true。

Q21　为什么 -cli 下工具总被拒？

因为 -cli 没有审批界面，而审批是 fail-closed 的：askTools 里的工具一律按拒绝处理（绝不静默放行）。 无人值守下能放行的只剩两个口子：被分类器判为只读的命令，以及写进 commandPolicy.trustedCommands 的命令 （白名单非空时还得先过 allowedCommands）。要一次全放开就把两张表都写成整条 *（见 10 权限与审批）。 要人工确认就用 -tui 或接好审批接口的 -server。详见 10 权限与审批。

Q22　一个回合最多跑多少轮？超了会怎样？

由 react.maxRounds 控制，缺省 16。达到上限仍未收敛时，回合以「未收敛」收尾而不是报错： -cli 退 6，SSE 的 done 事件里 truncated=true，此时 content 是一句可读提示 而不是模型回答。另外两种「形状正常、内容不对」的回复由内核兜底：空回复会在同一回合内自动重试 1 次 （重试不产生会话消息，但 token 照常计费）；被输出上限截断只提示、不自动续写，提示走各外壳自己的提示通道 （TUI 提示行 / -cli 的 stderr / SSE 的 notice），不会被拼进正文。

Q23　子代理和主会话共享什么？

除了任务描述本身，几乎什么都不共享：子代理不继承主会话的模型（用自己在 agents.json 里配的 model， 没配则落到全局默认）；它看不到主会话的消息；它的会话是临时的，不落盘、不进 /session 列表。 它花掉的 token 计入父会话。而「上下文 fork」是永久不做（不是推后）——对话条件型委派只能靠调用方 把背景写进 task.prompt。workflow 插件的 needs 能把前几步的结论拼进下游任务， 但那是有损转交（每个依赖各有字符额度、合计上限 20000 字符，超出只给头部并附归档路径）。

Q24　ask_user 和审批有什么区别？

机制与语义都不同。机制：通道 AskChannel 在内核，工具 ask_user 在官方 tools 插件。 语义：提问不是审批、不涉及权限——在这里选任何一项都不会放行任何工具； 审批是 fail-closed（无审批者 / 超时 / 溢出 / 通道关闭 / 中断一律拒绝），而提问不是—— 无答复者（-cli 不挂）、无人回答（超时）、用户放弃，三种都返回成功的工具结果并让模型自行判断。 Esc 对审批是「拒绝 + 中断回合」，对提问则不中断。详见 10 权限与审批。

Q25　怎么让某条命令不弹审批框？

写进 plugins.configurations.jellyfish-plugin-shell.commandPolicy.trustedCommands——那是免审批表， 命中即免。别和 allowedCommands 搞混：后者是准入白名单，只回答「能不能跑」， 里面的命令每次仍然弹批准框。另外第 3 步的拒绝形状排在可信表之前：把 rm 写进可信表， rm -rf / 依旧被拒。要「允许跑但每次都要我批准」，就只配白名单、不配可信表。 不想一条条维护名单时，两个表都可以写整条 *（匹配全部命令；写作 git * 没有这个效果）。

四、插件与集成

Q26　插件能拿到会话吗、能拿到工作目录（cwd）吗？

都不能，这是结构性约束而不是暂时缺口。PluginContext.runtimeInfo() 只有进程级事实 （外壳种类、有无交互界面、是否具备审批通道、有无终端），快照里刻意没有 sessionId、 agentId、cwd、上下文用量、系统提示词与模型注册表。工具的相对路径按进程工作目录解析， 而 ShellIngress 刻意不注入 SessionManager 与 AgentHarness—— 「插件不能新建会话、不能起回合」是结构性的。

Q27　插件里怎么知道自己在哪种外壳里？

读 PluginContext.runtimeInfo()（类型是 zcd.jellyfish.api.RuntimeInfo），四个字段： getShell()（CLI / TUI / SERVER）、hasUI()、 supportsApproval()、isInteractive()。 关键一点：supportsApproval() 是静态语义——它回答「本外壳具备审批通道吗」， 不表示此刻有人在线（字段名不叫 hasApprover 就是为了让这种误读在编译期就不可能发生）。 因此它应当用于降级决策，而不是判断一次调用会不会被批准：安全边界在审批通道自身的 fail-closed。 详见 13 插件进阶与发布。

Q28　插件能不能自称某个工具是只读的？

不能。ToolDescriptor 里已没有该字段，内核也不持有「模式」概念（无字段、无枚举、无 /mode、无 --mode）。 只读与否由用户配置决定：plan 模式看 plugins.configurations.jellyfish-plugin-plan.readOnlyTools， MCP 只认你写的 readOnlyTools（server 自填的 readOnlyHint 不再采纳，缺省一律按可写）。 这样设计是因为「被约束者自己定边界」等于没有边界；白名单语义下「用户没表态」与「用户不准」是同一件事。

Q29　会话文件会无限增长吗？

会。~/.jellyfish/sessions 是整套运行时里唯一没有自我约束的增长点： 工具输出有 50 MiB / 200 文件上限、子代理归档有 100 MiB 上限、MCP 落盘的文件在进程退出时删掉， 而会话文件连同目录里那个 git 仓库（每次落盘一次提交、从不 gc）只会越写越多， 磁盘占用也跟着 git 历史一起长。用 /resmon 观察占用， 它只报告、不清理（删除文件涉及用户的真实数据，得由你和模型决定）。详见 11 安装与使用官方插件。

Q30　插件热重载的边界在哪？

三条：只改配置段——/reload 只重启配置段变了的那几个插件； 新增 / 删除 jar——必须重启进程（扫描目录与插件集合只在启动期确定）； 覆盖是压链不是替换——RegisterOptions.override(true) 的新登记压在旧登记之上， 旧登记仍在表里，插件一停（或 Subscription.close()）它就自动重新生效， 因此不存在「插件走了，被它顶掉的内核工具永久消失」这种事故。 另外热部署与内核关闭都会终止正在跑的命令，别在长任务跑到一半时敲 /reload。

Q31　脚本插件（Python / Node）能做什么、不能做什么？

它把脚本目录暴露成标准插件，但只覆盖一部分扩展点（能力档写在插件仓库的 script/extension-points.json，分 in / planned / excluded 三档）。 明确不做的：返回 Java 对象的扩展点（脚本给不了）、跑在渲染线程 / 启动期的（脚本调用是一次可能冷启动的进程往返，付不起这个代价）。 已知边界：脚本进程的环境变量是严格白名单（密钥要走上一条配置段）；取消令牌能中止在途调用，但脚本侧看不到取消标志； 输出捕获明确不做；脚本没有出向边（submit / present / 扩展条目 / delegations / askUser）—— 那是「脚本只处理请求」这个立场的代价。

Q32　怎么把内核接进已有的 Spring Boot 应用？

加依赖 io.github.zcd0831:jellyfish-spring-boot-starter（版本与内核保持一致；它传递依赖内核 jellyfish-di，两者都在中央仓库）， 用 application.yml 指定四份配置文件在哪与插件扫描目录，内容仍是内核的 JSON 格式 （starter 刻意不把 JSON 翻译成 yml）；然后交互一律走 JellyfishUserFacade。 三条最容易踩的：审批与提问通道缺省关闭（接好接口再打开）、不要重复注册内核组件的第二个视图、 不要改 JellyfishLifecycle 的 phase。详见 14 整合到 Spring Boot。

Q33　装了插件但 /help 里没有它的命令，怎么办？

按这个顺序查：jar 是否在 config.json 的 plugins.roots 指向的目录里（缺省 ~/.jellyfish/plugins/）； 目录布局是否是「平铺 jar」或「一插件一子目录 + plugin.properties」——PF4J 只在目录下一层找 plugin.properties； 是否被 jellyfish.json 的 plugins.disabled 排掉；以及是否重启过进程（新增 jar 不热加载）。 完整清单见 15 页 C1 与 C2。

术语表

排序方式：英文条目按首字母，中文条目按拼音；中英混排的条目（如「plan 模式」）归到首字母那一组。 每条一句话解释，括号里是出处或交叉链接。

按英文首字母

agent（代理身份）
agents.json 里定义的一套装扮：系统提示词（同目录 {agentId}.md）、模型、工具权限三段、是否可委派； 会话建起来时绑定它，权限策略随后按 agentId 决定（07 agents.json 与工具权限）。
aging（老化）
把保留窗口之外的工具结果信封换成一条带落盘路径的 stub，只改本次请求、Session 一条不动； 由 react.cache.agingPercent 控制触发口径（缺省 70，见 09 会话与上下文）。
approval（审批）
「这个工具能不能执行」的逐次人工裁决，唯一的放行出口；fail-closed——无审批者、超时、溢出、通道关闭、中断一律拒绝 （Jellyfish/docs/constraints.md:464-479）。
ask（提问）
「问你一件事」的通道，与审批刻意分开：机制在内核（AskChannel）、工具在官方 tools 插件（ask_user）； 不涉及权限，且不是 fail-closed（Jellyfish/docs/constraints.md:495-521）。
compact（压缩）
把更早的对话压成一份摘要，之后每轮只带摘要 + 最近若干条原文；依赖插件提供策略， 不启用压缩插件时整体不可用且不回退内置（09 会话与上下文）。
context window（上下文窗口）
模型单次请求能容纳的 token 上限，在 models[].contextLength 里声明，内核用它算压缩预算（Jellyfish/README.md:586-596）。
extension point（扩展点）
内核允许插件介入的位置，分两个能力面：ExtensionRegistry（同步、不可丢，如工具、参数改写、权限拦截、会话持久化、输入改写） 与 EventChannel（异步、有界队列、可丢，如轮次通知、指标、审计）（Jellyfish/docs/constraints.md:196-201）。
fail-closed（失败即拒绝）
「没能表态」不等于「无异议」：审批通道、插件权限拦截、stop() 之后的注册，一律按最严的结果处理 （Jellyfish/docs/constraints.md:452-461）。
handler
注册在「类型 + 路由键」上的处理器。handle 是同键唯一（0 个 → NO_HANDLER， 多个 → AMBIGUOUS_HANDLER），contribute 是 0..N 个（Jellyfish/docs/constraints.md:205-211）。
handoff（命令接力）
命令返回 CommandResult.handoff(text) 时，内核不呈现命令输出，而是把 text 当成你这次敲下的输入继续走 （输入改写 → 指令 → 建会话 → 起回合）；它只声明、不执行，回合仍由外壳那一次提交拥有（04 三种运行模式）。
MCP
Model Context Protocol，官方 jellyfish-plugin-mcp 作为客户端用 stdio 连外部 server， 把它的工具以 mcp__<server>__<tool> 接入（Jellyfish-Plugins/README.md:622-702）。
owner
每一份注册、贡献、动作的归属者，通常就是 plugin.id；也可以是命名空间 （pluginId + 分隔符 + 子标识），内核按命名空间做前缀回收（Jellyfish/docs/constraints.md:283-292）。
PF4J
Java 的插件框架，Jellyfish 用它扫描并加载插件 jar：只在目录下一层找 plugin.properties， 插件类加载器是子优先的（Jellyfish-Plugins/README.md:865-921）。
plan 模式
官方 jellyfish-plugin-plan 提供的一套「先看，别改」的工作方式：/plan on 后只有 readOnlyTools 白名单里的工具可用，开关按会话存、子代理按会话树继承（Jellyfish-Plugins/README.md:706-742）。
plugin（插件）
独立打包的 PF4J jar：一份 plugin.properties + 一个 JellyfishPlugin 实现 + 若干扩展点处理器； 与内核之间没有编译期依赖（对 jellyfish-api 是 provided）（12 从零开发一个插件）。
prompt cache（提示词缓存）
厂商侧按前缀匹配做的输入缓存：改掉历史上的一个字节，后面的整段都会从约 0.1× 的命中价 变回 1× 全价；内核用 aging 与 cache 段治理它（Jellyfish/README.md:882-890）。
Reactor
Maven 的多模块构建单元。Jellyfish 与 Jellyfish-Plugins 是两个独立 reactor， 因此插件仓库要用 jellyfish-api 必须先在内核仓库 mvn install（15 页 A5）。
ReAct
「推理 → 调用工具 → 看结果 → 再推理」的循环，内核的实现是 ReActLooper， 跑在 react 线程池上（上限 8 条线程 = 并发顶层回合数）（Jellyfish/docs/constraints.md:524-561）。
round（轮次）
回合内部的一次模型调用；单回合轮数上限是 react.maxRounds（缺省 16）， 达到上限仍未收敛 → -cli 退 6、SSE truncated=true（Jellyfish/README.md:850-871）。
run
子代理的一次执行（一个 task 或 workflow 步骤 = 一个 run）。run 跑在独立的 agent-run 线程池上， 受 subAgent 的并发、墙钟与 token 预算约束，归档到 <toolOutput.dir>/subagent-runs（Jellyfish/README.md:919-956）。
RuntimeInfo
插件能看到的「我正跑在哪种外壳里」的只读快照：Shell / hasUI / supportsApproval / interactive； 只有进程级事实，不含会话与工作目录（Jellyfish/jellyfish-api/src/main/java/zcd/jellyfish/api/RuntimeInfo.java）。
session（会话）
agentId、模型与消息历史的持有者；状态一律归 Session，进程内不另存全局副本 （唯一的例外是 SessionDefaults，只在 create 那一刻被消费）（Jellyfish/docs/constraints.md:305-310）。
ShellContribution
插件向外壳「贡献一段显示」的载荷：Kind 只有 NOTICE / INVALIDATED， 不产生 LlmMessage、不进提示词、不落盘；Scope.SESSION 必须指向已存在的会话 （Jellyfish/docs/constraints.md:234-250）。
skills
官方 jellyfish-plugin-skills 提供的能力：按目录发现 SKILL.md， 元信息常驻系统提示词、正文由模型用 skill 工具按需加载（Jellyfish-Plugins/README.md:44-66）。
spill（落盘）
工具输出溢出时把完整内容写进文件、只回灌头尾预览 + 信封；落盘只在溢出时发生，短输出不产生文件； 单条上限是 react.toolOutput.spillMaxBytes（缺省 32 MiB，Jellyfish/docs/constraints.md:719-747）。
SPI
插件对内核的编程接口面，集中在 jellyfish-api：JellyfishPlugin 的 start(PluginContext) / stop()，加上扩展点的请求与结果类型；插件只能依赖它，不能碰 infra / core（12 从零开发一个插件）。
subagent（子代理）
主会话按 task 或 workflow 派出去的一次委派执行：不继承主会话模型、会话是临时的、 除了任务描述几乎什么都不共享；它的 token 计入父会话，「归谁所有」沿父链只穿临时会话 （Jellyfish/README.md:432-462）。
token
模型计费与预算的单位。内核记录用量（/usage 可看），并给子代理设了 runTokenBudget / treeTokenBudget 两道上限（Jellyfish/README.md:939-951）。
tool（工具）
模型可以调用的一个动作，由插件注册（内核只自带 task）；执行统一走 ToolExecutor： 权限 → 路由 → 截断的唯一执行点（Jellyfish/docs/constraints.md:714-718）。
tool call（工具调用）
assistant 消息里的一次调用请求（带 toolCallId 与参数），与随后的 tool 结果消息成对出现； 参数在执行之前就已落库，因此轨迹行在运行期、回合结束后、恢复会话后看到的是同一份文本（Jellyfish/README.md:230-236）。
turn（回合）
一次 chat 调用 = 一个回合，边界由外壳决定；回合内可以有很多轮、很多次工具调用。 插件动作只落进正在跑的顶层回合，子代理回合不开窗，且内核不自己起回合（Jellyfish/docs/constraints.md:212-224）。
workflow spec
官方 jellyfish-plugin-workflow 接受的一份声明式编排说明： steps[]（含 id / agent / prompt / needs / when）加可选的 aggregate； 没有 needs 的步骤立刻并行开始，没有循环、变量、表达式，也没有重试，步骤最多 12 步 （Jellyfish-Plugins/README.md:557-621）。

按拼音

插件运行时
内核里负责扫描、加载、启动、停止插件并维护「owner → 注册」对应关系的部分（PF4J + infra/plugin）； 注册窗口是插件的整个存活期，回收按 owner 一次收干净，注销是可选优化而不是必须动作（Jellyfish/docs/constraints.md:268-282）。
待办（todo）
官方 jellyfish-plugin-todo 提供的会话级任务清单：五个工具 todo_write / todo_claim / todo_done / todo_release / todo_block 加只读 /todo，让多个子代理认领同一份清单（Jellyfish-Plugins/README.md:44-66）。
工具轨迹
界面上按工具调用逐行显示的记录：TUI 里是 ⎿ 工具名 · 结果摘要 · 调用参数； 失败标记来自结果信封里的 metadata（exitCode / terminal），界面按字段渲染、不解析文本 （Jellyfish/README.md:1105-1107）。
门面（facade）
JellyfishUserFacade：Spring Boot 接入方唯一应当使用的交互入口。它替内核补上归属校验 （会话、审批、提问都按 userId 收口）；内核门面默认不进容器，「拿不到就用不着记住不要用」 （Jellyfish-Spring-Boot-Starter/README.md:192-213）。
命令域
输入以 / 开头就走的那条路：CommandManager 按命令名路由，别名与用法来自 CommandDescriptor； 候选查询是与执行平行的只读路径，不执行命令（Jellyfish/docs/constraints.md:840-864）。
输入改写
InputTransformRequest 链：排在命令判定之后、指令解析之前、建会话之前，可 continueAsIs / replace / handled 短路。它跑在调用线程上（TUI 路径上是渲染线程），因此只能纯计算、不得阻塞 （Jellyfish/docs/constraints.md:791-802）。
输入指令（! 与 @）
输入框里的特殊语法，归插件不归外壳（没有插件就没有这个语法）：!命令 手动执行一条命令、 不进模型，结果落成一条 user 消息；@路径 只做引用、不内联不展开， 真正读取由模型调用 read_file（Jellyfish/docs/constraints.md:808-838）。
头槽位（head slot）
审批与提问队列的裁决口：每会话一个，会话内是 FIFO 队列且只有头槽位能被裁决 / 作答， 首次结论胜出，排队中调用等于无事发生，队列上限 8 条；会话之间互不排队（Jellyfish/docs/constraints.md:472-479）。
投影（projection）
把内部状态按某个视图整理成一份只读结果：会话快照是「一次一致的投影」（整份读取在同一段临界区，见 Session.captureSnapshot()）； TUI 的视图 = 会话投影 + 在途回合暂存区，消息区不持有第二份消息列表 （Jellyfish/docs/constraints.md:331、905-930）。
信封（落盘信封）
工具输出超限时回灌给模型的唯一格式：{_truncated, _tool, _total_chars, _total_lines, _path, _hint, _partial, preview}； 完整内容落盘，预览是头 30% + 尾 70%（顺序在末尾），渲染与解析共用 ToolOutputEnvelope 的字段常量 （Jellyfish/docs/constraints.md:728-736）。

这几类问题为什么不在这里回答

1. 某家厂商今天支持哪些参数 / 某个模型认哪些字段

原因
内核刻意不认识厂商语义：它不做按字段名的分支、不校验字段名是否被端点认识，也不替厂商维护「哪些模型认哪些字段」。 vendorBody 打错就是静默无效，正是这个立场的直接后果。
去哪找
厂商自己的文档 + 内核的 DEBUG 日志（它会打出实际下发的键名，不打值）。

2. 性能 / 容量（每秒能跑多少请求、最多支持多少会话）

原因
三个仓库没有压测数据，也没有「每秒能跑多少请求 / 最多支持多少会话」这类容量指标； 会话目录会随 git 历史一起长（resmon 面板能看磁盘占用），这与吞吐、并发能力无关。 能确定的只有结构性的数字：react 池 8 条线程（= 并发顶层回合上限）、队列 128、空闲回收 60 秒； 子代理并发由 subAgent.maxConcurrentRuns 门控；Server 侧同会话同时只允许一个回合。
去哪找
要容量结论请自己在目标环境压一遍；结构上限见 Jellyfish/docs/constraints.md「ReAct 循环」一节。

3. 能不能商用 / 能不能进内网 / 合规怎么算

原因
这是法律与合规判断，本指南不替代专业意见。仓库里能查到的只是许可证文件本身 （各仓库根目录的 LICENSE）与技术侧的安全口径（密钥走环境变量、Server 对外开放必须配密钥、 shell / mcp / 脚本桥接不做用户隔离）。
去哪找
许可证原文 + 你们的安全与法务同事。

4. Jellyfish 与其它 Agent 工具的选型对比

原因
三个代码仓库未提供对比材料（检索词与唯一命中见 Q2）。 本套文档只描述 Jellyfish 自己的行为与边界（例如它明确不做 Web 前端、TLS、UI 深度定制、 后台子代理、上下文 fork、模型厂商 OAuth），不做跨产品评价。
去哪找
Jellyfish/docs/constraints.md 的「边界与明确不做」清单，用来自行判断它是否适合你的场景。
两种「查不到」标记的含义，别混用
  • 【待确认】：在三个仓库的 README / 示例配置 / 源码 / 文档里找不到出处。本套文档宁可标出来，也不编造。
  • 【需核实】：属于合理推断、仓库有相邻明文但没有正面写，需要你在自己环境里验证一次（例如 Windows 上的 shell）。
Jellyfish/docs/constraints.md:1148-1257（边界与明确不做）、Jellyfish/README.md:1-22（三个仓库与角色）、Jellyfish-Plugins/README.md:1063-1077（内核升级后的检查清单）、三个仓库的 AGENTS.md（各仓库的开发约定与分工）

关键结论

  1. 判断「这件事 Jellyfish 做不做」最快的办法是翻「边界与明确不做」：Web 前端与 TLS、UI 深度定制、后台子代理、 上下文 fork（永久不做）、回合之外由插件发起动作、工具延迟激活、ask_user 的一屏多题与子代理提问，都在这一档。
  2. 能力几乎全在插件里：不装插件只有系统命令；压缩、会话持久化、文件工具、shell、MCP、plan、skills、workflow 都要装。
  3. 三条「默认更严」的纪律要背下来：项目级配置默认不加载（信任单位是路径 + 内容指纹）、 审批无人裁决即拒绝（-cli 下 ASK 就是拒绝）、插件无法自称只读（只读与否由用户配置决定）。
  4. 密钥一律环境变量：配置文件会随 git、日志与会话外流；Server 用 JELLYFISH_SERVER_API_KEY 而不是 --api-key。
  5. 「改了配置不生效」先问三句：改的是哪一份（config.json 不热更新）？敲了 /reload 吗？项目级被信任了吗？
  6. 多用户不是内核能力，是 Spring Boot Starter 补上的维度；内核是单主体模型， 按角色隔离的正确办法是给每个角色定义一个 agentId。
  7. 本页的每条结论都标了出处；【待确认】 与 【需核实】 是刻意留下的诚实标记， 动手前请按「去哪找更权威的答案」核对原文。
