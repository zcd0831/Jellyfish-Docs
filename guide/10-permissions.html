10 权限与审批

这一页不重复 07 页「怎么写名单」，而是讲运行时到底按什么顺序判定、 三种外壳下的审批各长什么样、写 0 表示永不超时的代价是什么、以及 !命令、shell 白名单、plan 模式、MCP 这几处各自的边界。 一句话记住方向：插件只能收紧、不能放宽；没人裁决 = 拒绝。

学习目标

  • 画出「核心策略 → 插件拦截 → 审批通道」的判定顺序，并说明为什么没有 ALLOW 这一态；
  • 说清三段权限在运行时各产生什么结论，以及哪一段的否定是硬结论；
  • 说出审批在 -tui / -server / -cli 下分别发生什么，并能读懂审批框上的每一行；
  • 会配 permission.approvalTimeoutSeconds，并解释写 0 为什么可能「卡住整个 TUI」；
  • 会区分「审批」与「提问」：一个卡住执行、一个不卡住，Esc 的含义也不同；
  • 能用 !命令 手动跑一条命令，并知道它照旧过权限；
  • 按六道判定顺序配好 shell 的五个字段，知道「白名单只管准入、可信表才免审批」；
  • 在无人值守（-cli / -server）下说清还有哪两个放行口，并会用 plan 模式兜住写操作。

两道闸门：判定顺序总览

权限由两层组成：核心策略（内核按 agentId 取三段名单）与 插件拦截（插件对这一次调用表态）。两者汇合后统一处理 ASK 与审计。

为什么判定里没有 ALLOW

插件拦截的结论类型是三态 ABSTAIN / ASK / DENY， 合并取最严（DENY > ASK > ABSTAIN）且 DENY 短路。 类型里根本没有 ALLOW，因此「插件不能放宽核心策略」是编译期约束， 不是靠约定或代码评审守住的。核心策略的 ASK 也因此无法被插件的「无异议」降级 ——插件的裁定只能收紧、不能放宽。

两个容易被忽略的次序细节
  • 参数改写排在权限判定之前（防 TOCTOU）：排在之后就会出现「审批浮层显示参数 A、 真正执行参数 B」。排在之前则审批记录、界面轨迹行、-cli --show-tool-args、 会话里落库的 toolCalls 是同一份文本。 它不是放宽权限的入口：改写之后照旧走核心策略与插件拦截。 改写链上的 DENY 不进权限审计——那表现为一条 terminal=REJECTED 的工具失败结果。
  • 工具清单的过滤复用执行期判定：因此 ASK 不算被拒（工具仍出现在清单里）， 而插件拦截不参与过滤（它要看参数、可能问人）——所以「模式类收窄」在工具清单里看不到。

三段权限在运行时怎么被判定

语义本身（「字段缺失 = 不限制，显式写 [] = 该方向上一个都不放行」、优先级 deniedTools > askTools > allowedTools）见 07 agents.json 与工具权限。 这里只讲运行时它产生什么结论、能不能被别处改写。

名单命中后的结论还能不能被插件改写典型误配
deniedTools 硬拒绝：工具调用直接失败，不进审批 不能。优先级最高，插件只能表示「无异议」或更严 用它把 ask_user 拦掉来「不想让模型问」——有效，但那不是建议而是硬结论
askTools ASK：每次调用都要人工审批 不能降级。插件的「无异议」不会把它变成免审批 把它写成整个 shell、-cli 下等于禁用；连 git status 都要批准
allowedTools 「允许」：不产生硬结论，仍要过插件拦截 能被插件收紧；还决定子代理能看到哪些工具（只随委派生效） 写 "allowedTools": [] 想表达「只拒绝两个工具」——那是全拦；要表达仅两次拒绝就直接省略该字段

「取不到策略」与「查不到身份」是两件事

改名 / 删配置之后，旧会话会被「全拦」
  • fail-open 只覆盖「取不到策略」这一种情况（会话没绑 agentId）； 策略一旦生效，它的否定就是硬结论。
  • 「绑了一个查不到的身份」不是「取不到」：它在配置里查不到（改名、删除、 从别处恢复出来的会话），因此内核返回「全拦」并附一条 ConfigWarningEvent （每个标识只发一次）。继续放行等于「配置里改个名字就悄悄把一批旧会话提权」。
  • 看到工具突然全部被拒时，先去 agents.json 核对那个 agentId 还在不在。

审批在三种外壳下的行为

外壳有审批者吗发生什么怎么裁决
-tui 有 弹出审批选择框，优先于补全面板与二级选择页；批准才执行 ↑/↓ 选、Enter 确认、Esc 拒绝并中断回合
-server 有 把待审批项推进 SSE 流（事件名 approval_required） POST /sessions/{id}/approvals/{requestId}；发现入口是 GET /approvals（跨会话最早一条，带 sessionId）
-cli 没有 没有审批界面、也没有审批者，需要审批的调用一律按拒绝处理 不存在。绝不静默放行

TUI 的审批框长什么样

╭ ⏸ 需要审批 ────────────────────────╮
│ 工具 bash                          │
│ 参数 {"command": "rm -rf build"}   │
│ 理由 agent 策略要求人工审批该工具   │
│ 会话 a1b2c3d4… · 模式 normal       │
│                                    │
│  ❯ 允许一次   本次调用放行…        │
│    拒绝       本次调用按拒绝处理…  │
│    ↑/↓ 选择 · Enter 确认 · Esc 拒绝并中断 │
╰────────────────────────────────────╯
  • 参数原样显示（含 apiKey 这类键的值）：审批要回答的是「放不放行这次调用」，而能回答它的只有原文。
  • 超长参数折行显示并在截断处写明省略了几行。
  • Esc 是「拒绝并中断回合」——只拒绝的话模型往往会换个方式接着试。
  • 框里的「理由」一行由发起方给出（例如「agent 策略要求人工审批该工具」）。

Server 侧的裁决契约

  • 必须按会话寻址：POST /sessions/{id}/approvals/{requestId} 要求 requestId 属于路径里那个会话、且是它的头槽位，否则 404。
  • 头槽位是每会话一个：同会话内是「一个头槽位 + FIFO 队列 + 只对头生效 + 首次结论胜出」， 队列上限 8 条，超出只拒新请求、已排队的不受影响；会话之间互不排队。
  • 排队中的请求裁决它等于无事发生——能裁决的始终只有头槽位那一条。
  • 子代理的审批落在它自己的会话上：按主会话订阅的流看不到它，所以要用 GET /approvals 这个只读发现入口，否则只能等超时被拒。

permission 段：审批超时

`permission.approvalTimeoutSeconds`

是什么
决定 askTools 里的工具在 TUI 上弹出审批框之后最多等多久；等不到人一律按拒绝处理。
怎么用
写在 jellyfish.json 的 permission 段，每轮现读；改完 /reload 生效。 
{
  "permission": { "approvalTimeoutSeconds": 120 }
}

配置

字段类型必填默认值含义示例
permission.approvalTimeoutSeconds int（秒） 选填 120 askTools 里的工具在 TUI 上弹审批框后最多等这么久，超时按拒绝处理；写 0 表示永不超时（一直等到有人裁决）。负数按非法处理：回退 120 并告警；超过 3600 的值照旧生效但也会告警 300

/reload 生效（该键每轮现读）

写 0 的代价（务必先读）

永不超时 = 一直卡住，不是「更安全」
  • 配 0 时启动会有一条 ConfigWarningEvent（来源 permission）说明代价。
  • fail-closed 的形状从「等不到人就拒绝」变成「等不到人就一直卡住」： 那一条 react 线程在有人裁决之前不会自愈。
  • 而 react 线程池只有 8 条（= 并发顶层回合上限）——几条这样的等待就能把并发占满， 表现为「TUI 里点哪个会话都不动」。
  • 仍然会放开的两条出口：外壳退出（通道关闭）或回合被取消。
  • 永不超时只改变「等多久」，不改变 fail-closed 这条口径。

常见问题

  • 写了个负数会怎样？按非法处理：回退 120 秒并告警（同样在事件面，来源 permission）。
  • 写了 7200 呢？照旧生效，但会告警——多半是笔误；真要不设上限应当写 0。

ask_user：向用户提问

`ask_user` 提问

是什么
让模型把一个问题连同若干选项摆到你面前，你挑一个即可，不必自己敲答案。 它不是审批：在这里选任何一项都不会放行任何工具，只是把答案告诉模型。
怎么用
由模型发起（工具在官方 tools 插件里，机制在内核的 AskChannel）。 -tui 下弹出提问浮层，末项固定是「其它（自己输入）」： 选中后按键交给常驻输入框，写下答案按 Enter 提交，Esc 退回选项。

配置

字段类型必填默认值含义示例
ask.timeoutSeconds int（秒） 选填 120 ask_user 弹出的提问框最多等这么久，超时后工具回一条「用户没有回答」让模型继续；写 0 表示永不超时。负数按非法处理：回退 120 并告警 60

/reload 生效（每次提问现读）

它与审批的三处刻意区别

维度审批（askTools）提问（ask_user）
作用 「能不能执行」卡在半路等人放行 「问你一件事」，不放行任何工具
等不到人的结果 按拒绝处理（fail-closed） 返回成功的工具结果，文本说明原因（「用户没有回答」），让模型自行判断
TUI 里 Esc 的含义 拒绝并中断回合 放弃作答，回合继续（模型收到「用户取消了这次提问」后自己接着判断）
超时键 permission.approvalTimeoutSeconds ask.timeoutSeconds（刻意分开，改一个不会顺带改另一个）

为什么提问不是 fail-closed

审批者缺席时放行等于静默放宽权限；而提问缺席时让模型照自己的判断继续，代价只是它可能猜错并说出来。 做成失败会让模型以为环境出错、反复重试。因此「无答复者 / 超时 / 用户放弃」三种都返回成功的工具结果。

三种外壳下的行为

  • -tui：提问浮层，优先级低于审批、高于二级选择页与补全；选项很长时光标停在哪一项，那一项就完整折行展开（标签与说明都显示，最多 6 行，超出写明省略了几行），其余各项单行截断——保证「你准备按 Enter 的那一项一定是完整的」。
  • -server：推 ask_required，由 POST /sessions/{id}/asks/{requestId} 作答，请求体给 {"optionId":"…"} 或 {"text":"…"}；两种都不给回 400（「用户自己填的答案」与「客户端写错了请求」必须能分开）；连接断开时收敛未决项。发现入口是 GET /asks。
  • -cli：不挂答复者，工具立刻返回一条「当前外壳没有交互界面，无法把提问送达用户」，模型据此照自己的判断继续——不会失败、也不会挂住。
  • 子代理回合里当场拒绝：外层界面按当前会话取待答项，而子代理有独立的会话，它的提问不会出现在任何一个界面上；因此工具直接返回「子代理回合里无法向用户提问」，绝不进通道等待（那只会静默卡到超时）。

头槽位与审批同口径

每会话一个 + FIFO 队列 + 只对头槽位生效 + 首次结论胜出 + 排队上限 8；会话之间互不排队。 裁决、超时、关闭三方都在同一把锁内落定，后到者当作无事发生。

常见问题

  • 写 ask.timeoutSeconds: 0 与审批写 0 一样有代价吗？同源：提问发生在 react 线程上并被同步等待，而那个池只有 8 条线程，每一次这样的等待都占住其中一条；配 0 时启动有一条告警（来源 ask）——不报的话，「故意配的」与「手滑写了个 0」在日志里长得一样。
  • 不想让模型问怎么办？用 agent 的 deniedTools 把 ask_user 拦掉：那是硬结论，不是建议。

输入指令 !命令

`!命令`：手动执行一条 shell 命令

是什么
在输入框里直接敲一条 shell 命令并执行。它不进模型——但执行完会把 「命令回显 + 输出」作为一条用户消息落进会话，因此下一次提问时模型看得到结果。
怎么用
!git status --short
!mvn -q -pl jellyfish-core test
指令依赖 jellyfish-plugin-shell：没有装它，! 只是一段普通文本。 Esc 可以中断正在跑的命令；指令执行队列满时当场报错（JellyfishException，提示稍后重试），不会静默丢弃。

配置

字段类型必填默认值含义示例
—（无专属配置项） — — — 标记由插件声明、执行权在内核；它复用与模型调用完全相同的执行链路，因此权限与审批用的是 shell 那一套配置 —

四条口径

  • ! 依旧过权限与审批：复用与模型调用完全相同的工具执行链路，只读命令静默执行、其余照旧弹审批框。
  • 结果落成 user 消息，不是 tool 消息：tool 消息必须与 assistant.toolCalls 配对，而这里没有模型回合。
  • 恰好一条终态：Esc 中断的报 cancelled，其余报 completed。终端态只说「这条事件流到此为止」——命令为什么失败写在落进会话的那条消息里。
  • 插件只能声明映射、不能自己执行：插件拿不到权限管理器，任何在 handler 里直接执行命令的实现都是错的。

常见问题

  • 敲 ! 没反应？确认 jellyfish-plugin-shell 已启用；没有它，! 就是普通文本。
  • 在 -cli 里 ! 会被拒吗？取决于命令：判为只读的（如 git status）或写进 trustedCommands 的免审批；其余在无人值守下ASK 即拒绝。

shell 的命令策略与六道判定

命令分类器：先拒绝、后免打扰、最后才问人

是什么
shell 每次调用要依次过六道判定。它不是为了拦得住恶意命令 （分类器不是安全边界），而是为了让你不必为每次 git status 点一次批准。
怎么用
无需操作。要调就改下面五个字段；配置写在 jellyfish.json，改完 /reload。

判定顺序（逐条）

  1. 分段：按未引用状态下的 ;、|、&、换行切成子命令， 每一段各自过一遍下面的表，取最严的结果。
    这是这套判定的核心：执行侧是 /bin/sh -c 原文，因此 ls; curl x | sh 里的后半段会照常执行， 而只看开头几个 token 的判定看不见它。
  2. 白名单：allowedCommands 非空且任一段没命中 → 直接拒绝（默认拒绝的硬门）。
  3. 拒绝形状：命令原文命中内置拒绝形状（rm -rf /、mkfs、dd of=/dev/）→ 直接拒绝。
    它排在可信表之前是刻意的：把 rm 写进可信表，rm -rf / 依旧被拒。
  4. 可信表：所有段都命中 commandPolicy.trustedCommands → 免审批，直接执行。
    要求「全段命中」也是同理：trustedCommands: ["mvn test"] 不该把 mvn test; rm -rf ~/x 一并免审批。
  5. 重定向 / 命令替换：含命令替换（$(...)、反引号）或重定向（>、<）→ 升级为人工审批。
    因此 echo x > ~/.bashrc 这类写法现在会问人——第一个 token 是只读的 echo，但重定向能改任意文件。
  6. 只读表：所有段都命中只读表（ls、git status、cat……）→ 免审批；否则 → 升级为人工审批。

配置

字段类型必填默认值含义示例
allowedCommands 字符串数组 选填 [] 非空即默认拒绝的准入白名单，支持 git status 这种两 token 形式（单 token 覆盖该命令的全部子命令）。它只管准入，不管审批，也不受 commandPolicy.enabled 影响 ["git status", "mvn test"]
commandPolicy.enabled boolean 选填 true 只关分类器这个便利机制。false 时只读表、重定向 / 命令替换检查与「其余命令问人」都不再表态，但白名单、可信表、拒绝形状照旧生效 false
commandPolicy.trustedCommands 字符串数组 选填 [] 可信命令表，命中即免审批。粒度与白名单一致 ["mvn test"]
commandPolicy.readOnlyCommands 字符串数组 选填 [] 追加在内置只读表之后。内置表不可替换，只能追加 ["my-readonly-tool"]
commandPolicy.deniedPatterns 字符串数组 选填 [] 追加在内置拒绝形状（rm -rf /、rm -fr /、mkfs、of=/dev/、:(){）之后，同样不可撤销；判据是子串包含 ["shutdown -h"]

完整的配置键是 plugins.configurations.jellyfish-plugin-shell.*； /reload 生效（逐插件配置段写在 jellyfish.json）。

deniedPatterns 是子串匹配，不是正则

README 只把它描述为「拒绝形状」，没说匹配方式；命令策略的实现里判据是 command.contains(pattern)——对命令原文做子串包含判断，正则元字符一律按字面量处理。 因此 "shutdown -h" 只要出现在命令里的任何位置就命中；写 "^rm" 也不会得到 「只匹配行首」的效果，它找的字面量就是 ^rm。

两个连带口径：判据作用在整条命令原文上（含引号与空格，不区分「命令名」与「参数」， 也不按段分别判断）；内置形状实际是五条——rm -rf /、rm -fr /、mkfs、 of=/dev/、:(){，插件 README 的字段表里只列了其中四条（漏了 rm -fr /），以源码为准。

完整示例：允许跑但每次都要我批准

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-shell": {
        "allowedCommands": ["git status", "git diff", "mvn test"],
        "commandPolicy": {
          "enabled": true,
          "trustedCommands": ["git status", "git diff"],
          "readOnlyCommands": [],
          "deniedPatterns": []
        }
      }
    }
  }
}

这份配置下：git status / git diff 免审批（可信表命中）； mvn test 每次都要批准——白名单只回答「能不能跑」。

三条最容易踩的口径

  • 白名单只管准入，不管审批：allowedCommands 里的 mvn test 每次仍然弹批准框。要它静默执行，就把同一条前缀也写进 trustedCommands。
  • 可信表才是免审批：「允许跑但每次都要我批准」这种姿态仍然写得出来——只配白名单、不配可信表即可。
  • commandPolicy.enabled=false 会连第 5 步一起关掉：它关的是「分类器」这个便利机制，只读表、重定向 / 命令替换检查与「其余命令问人」都不再表态；白名单、可信表、拒绝形状照旧生效。
shell 没有沙箱

命令以本进程的权限运行，能读写你这个用户的任意文件。

  • 分类器不是安全边界：FOO=bar cmd、别名、sh -c 嵌套照旧能绕过前缀判定。
  • 不做目录围栏：它可绕过（cd /、绝对路径、sh -c 嵌套），与文件工具没有围栏也不自洽。真正的边界是审批加白名单。
  • 真正的最强姿态是把 shell 写进 askTools（每条命令都要批准，连 git status 也要），代价是噪音。
  • 子进程继承父进程环境，但名字匹配 *KEY* / *TOKEN* / *SECRET* / *PASSWORD* / *CREDENTIAL* / *_PAT* / *AUTH* / *NETRC* / *PROXY* / *PASSPHRASE* / *_PWD 的变量不会传下去（工具输出会送到远端 LLM）。

其它边界

  • 引号内的分隔符与重定向是字面量：echo "a;b"、echo 'a > b' 仍是一条只读命令；引号没闭合时不给结论，一律问人。
  • find / git fetch / git branch / git remote / npm test 刻意不算只读（find -delete 会删东西、git fetch 改 ref、npm test 执行仓库里的任意代码），它们免审批的唯一正当路径是可信表。
  • 进程树只能尽力杀：杀 sh -c 不一定带走孙进程，工具用 pgrep -P 递归尽力而为，杀不干净是已知边界。
  • 插件停止时在途命令会被连根拔掉：/reload 与内核关闭都会终止正在跑的命令；停止之后新来的调用回「插件已停止，进程已终止」，这与「已取消」分开说。
  • Windows 未验证：非 POSIX 平台映射成 cmd.exe /c，但没有在真机上跑过。

常见问题

  • 配了白名单怎么还每次问批准？因为白名单只管准入。把同一条前缀也写进 trustedCommands。
  • echo x > file 为什么突然要审批？第 5 步：有重定向就升级为人工审批（重定向能改任意文件）。要静默执行就把整条命令（含重定向）写进 trustedCommands——可信表优先于这一步。

无人值守模式下的放行口

-cli / -server 没有审批者：ASK 就是拒绝
  • 这两个模式不挂审批通道，因此 askTools 等于禁用，「等不到人」的结果就是拒绝。
  • 免审批的放行口只剩两个：被分类器判为只读的命令，以及 commandPolicy.trustedCommands 里的命令（白名单非空时还得先过白名单）。
  • 想在无人值守下跑 mvn test 这类非只读命令，必须把它写进 trustedCommands。
  • MCP 同理：-cli / -server 下写类 MCP 工具实际不可用（ASK 等于拒绝）。
  • 文件工具也同理：pathPolicy 的 outside: "ask" 在没有审批界面的外壳里等于拒绝。
无人值守的三条实用做法
  • 用plan 模式兜住写操作：/plan on 之后只有白名单里的工具可用，它不依赖审批者，因此在没有人在场的模式里同样有效。
  • 把要跑的构建 / 测试命令写进 trustedCommands，别把整个 shell 放进 askTools。
  • 需要审批的活改到 -tui 或 -server（Server 侧由客户端订阅 approval_required 后裁决）。

plan 模式：一套「先看，别改」的工作方式

`/plan on` / `/plan off`

是什么
开启后只有你列在 readOnlyTools 里的工具可用，其余一律被拒。 拒绝理由会告诉模型「plan 模式下只能使用只读工具：……」，它就不会反复去试一个注定失败的写操作。
怎么用
/plan            查看当前状态（并给出 on / off 候选）
/plan on         开启：只有白名单里的工具可用
/plan off        关闭：恢复正常
装了这个插件才有 /plan；不带它的内核里没有「模式」这个概念，也没有 --mode 参数。

配置

字段类型必填默认值含义示例
readOnlyTools 字符串数组（工具名） 选填 [] plan 模式的工具白名单。不写就等于开启时一个工具都用不了（白名单语义：「用户没表态」与「用户不准」是同一件事） ["read_file", "list_dir", "grep_files", "todo_write", "skill"]

完整键是 plugins.configurations.jellyfish-plugin-plan.readOnlyTools；/reload 生效。

完整示例

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-plan": {
        "readOnlyTools": ["read_file", "list_dir", "grep_files", "todo_write", "skill"]
      }
    }
  }
}

五条口径

  • 开关按会话存：存在会话扩展条目里，随会话一起落盘与恢复；同一个进程里可以一个会话开着、另一个关着。
  • 子代理按会话树继承：判定沿父链——父会话开着 plan 时，它派生出来的子代理会话同样只看不写。子代理是模型自己派出来的，只看本会话的话，「把被禁的写操作交给子代理」就能绕开这道限制。
    注意 内核的约束只要求「插件自己决定要不要传播」（开关存在会话上、子代理是另一个会话），官方 plan 插件选择的传播方式就是按会话树继承。
  • 开关读不出来时按「开着」处理（fail-closed）：判不出开没开就按最严的一侧倒，否则限制会在出故障的那一刻静默消失。代价是被拒的工具会给出「开关读不出来」的理由，/plan off 可重置。
  • 不换工具清单，只拦执行：模型看到的工具清单不变，写操作在执行时被拒——清单进的是请求前缀里很靠前的位置，换集合会让那一轮之后的前缀（连同全部历史）全部作废。
  • -cli / -server 下同样有效：它不依赖审批者，因此没有人在场的模式里也能用它兜住写操作。

常见问题

  • 开了 plan 连 read_file 都用不了？readOnlyTools 没写（或写成了空数组）：白名单为空 = 一个都不许。补上名单再 /reload。
  • 工具无法自称只读吗？对。工具描述符里没有「是否只读」字段，谁能进名单完全由你说了算。

路径闸门与 MCP 审批

tools 插件的 pathPolicy（要点回顾）

是什么
文件工具在允许的路径之外时会升级为人工审批或直接拒绝。粒度是「工具名 + 路径」—— 否则「允许 write_file」就等于「允许往任何地方写」。
怎么用
详见 08 内置工具速查的 pathPolicy 一节（含完整 JSON 与五条口径）。 这里只强调与权限判定相关的三条：
  • 只有 tools 插件自己的几个文件工具受管：read_file / list_dir / grep_files 归读， write_file / edit_file 归写；ask_user 不碰路径因此不受管。 闸门不认识别家的工具——shell、MCP 工具送到它面前时一律「无异议」。
  • 判据看真实位置：符号链接会先解开再比；ask 在没有审批界面的外壳里等于拒绝。
  • 它不是文件系统沙箱：管不了 shell 命令里出现的路径（那是命令策略的事），也管不了 MCP 工具。

常见问题

  • pathPolicy 配错了会不会让插件起不来？不会：只回退并告警，告警走 ConfigWarningEvent（TUI 上看得见）。

MCP 工具的只读名单与写类审批

是什么
MCP server 提供的工具也过本机这套权限：只读与否只认你写的名单， 写类工具是否要人工审批由一个开关决定。
怎么用
写在 jellyfish.json 的 plugins.configurations.jellyfish-plugin-mcp 段， 改完 /reload。工具名带前缀：mcp__<server>__<tool>， 因此权限名单里也要带这个前缀。

配置

字段类型必填默认值含义示例
servers[].readOnlyTools 字符串数组（工具名） 选填 [] 本插件审批策略用的只读名单（与 plan 插件的同名键无关）。只读只认你写的这一份——server 自填的 readOnlyHint 不再采纳；缺省一律按可写 ["read_file", "list_directory"]
askWriteTools boolean 选填 true 写类工具是否要人工审批 false

/reload 生效

完整示例

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-mcp": {
        "servers": [
          {
            "id": "filesystem",
            "command": "npx",
            "args": ["-y", "@modelcontextprotocol/server-filesystem", "/tmp"],
            "env": { "SOME_TOKEN": "${MCP_TOKEN}" },
            "callTimeoutSeconds": 60,
            "readOnlyTools": ["read_file", "list_directory"]
          }
        ],
        "askWriteTools": true,
        "startupWaitSeconds": 5
      }
    }
  }
}

四条要记住的口径

  • 缺省一律按可写：不写 readOnlyTools 就等于所有 MCP 工具都算写类；askWriteTools 为 true 时每个都要审批。
  • 不采纳 server 自填的只读标记：这是「工具不能自称只读」这条原则在 MCP 上的落点。
  • 刷新期没有「免审批」空窗：一次 tools/list 就是一次整体替换，任何时刻「能调用的名字」都已经带着审批用的标记；两个 server 提供同名工具时按最严算。
  • 无人值守下写类工具实际不可用：-cli / -server 里 ASK 等于拒绝（与 shell 同理）。

  • 把只读工具写进 plan 的 readOnlyTools 会影响 MCP 吗？不会，两者是同一名字的两处独立配置。
  • MCP 工具的调用超时怎么配？servers[].callTimeoutSeconds（缺省 60，0 表示不超时，上限 3600 秒），见 08 页。

常见问题

配了 askTools，工具调用却直接失败、连框都不弹？
看外壳。-cli 不挂审批者，需要审批的调用一律按拒绝处理；要在无人值守下跑， 就别把该工具放进 askTools，要人工确认就用 -tui 或 -server。
配了 approvalTimeoutSeconds: 0 之后，TUI 里点哪个会话都不动？
这是写 0 的已知代价：永不超时会在一条 react 线程上一直等，而线程池只有 8 条（= 并发顶层回合上限）。外壳退出或回合被取消仍会放开它。生产上更推荐给一个 合理的秒数（如 300），而不是不设上限。
把 shell 放进 askTools 之后连 git status 也要批准？
是的，而且这是刻意的最强姿态：核心策略的 ASK 无法被插件的「无异议」降级。 想两头都要，就不要把 shell 放进 askTools，改用白名单 + 可信表。
-cli 下 ask_user 会挂住吗？
不会。它立刻返回一条「当前外壳没有交互界面，无法把提问送达用户」，模型据此照自己的判断继续。 真要人回答就用 -tui 或 -server。
子代理能替我批准或替我回答吗？
不能。子代理回合里的提问当场被拒（判据是这次调用带着 run 标识），绝不进通道等待。 而子代理的审批落在它自己的会话上：Server 侧要用 GET /approvals 才看得到 （按主会话订阅的流看不到，那就只能等超时被拒）。
改了 agent 名字以后，旧会话里的工具全被拒了？
这是「绑了一个查不到的身份」的情况：内核返回全拦并发一条 ConfigWarningEvent。 把 agentId 改回来，或用 /agent 切到一个配置里存在的 agent。
怎么让我自己写的插件也不能偷偷放宽权限？
不用做什么——插件拦截返回值的类型里没有 ALLOW，这是编译期就堵死的； 而且插件抛错或返回 null 一律按 DENY 处理。细节见 12 从零开发一个插件。

关键结论

  1. 权限是两道闸门：核心策略（deniedTools 是硬否定）→ 插件拦截（三态取最严、DENY 短路、抛错按 DENY）， 最后 ASK 统一收口到审批通道。没有 ALLOW 这一态，所以插件永远只能收紧。
  2. 三段名单里 deniedTools 与 askTools 的结论都不能被插件放宽； allowedTools 才是「允许」并仍受插件收紧；字段缺失 = 不限制，显式 [] = 全拦。
  3. 审批的每一条失败出口都通向拒绝：无审批者、超时、溢出、通道关闭、中断一律拒绝； Esc 是「拒绝并中断回合」。-cli 没有审批者，所以需要审批的调用在那里一律被拒。
  4. permission.approvalTimeoutSeconds 缺省 120；写 0 表示永不超时， 代价是那一条 react 线程一直卡住，而池子只有 8 条；负数回退 120 并告警，超过 3600 也告警。
  5. ask_user 不是审批：选任何一项都不放行工具，超时/放弃都返回成功的结果让模型继续， Esc 只是放弃作答。超时键 ask.timeoutSeconds（缺省 120）与审批刻意分开。
  6. !命令 不进模型但照旧过权限与审批，结果以用户消息落进会话（不是 tool 消息）， 依赖 jellyfish-plugin-shell；没有它，! 只是普通文本。
  7. shell 的六道判定是「分段 → 白名单 → 拒绝形状 → 可信表 → 重定向 / 命令替换 → 只读表」； 白名单只管准入、可信表才免审批，commandPolicy.enabled=false 会连重定向检查和「其余命令问人」一起关掉。 shell 没有沙箱，真正的边界是审批加白名单。
  8. 无人值守（-cli / -server）下 ASK 就是拒绝，免审批只剩「判为只读的命令」与 trustedCommands 两个口； 要兜住写操作就用 plan 模式（readOnlyTools 白名单，不写等于全禁）。
