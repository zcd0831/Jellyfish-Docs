13 插件进阶与发布

12 页把插件「写出来、装进去、跑起来」这条线走完了。这一页回答后面更常遇到的几个问题： 改完东西到底要不要重启？插件在运行期还能注册吗？怎么顶掉内核自带的工具？以及把插件做进官方仓库要做什么。 最后两节是脚本插件的高级配置（熔断、周期任务、能力档）与插件调试手段。

学习目标

  • 记住「四类改动 × 两种操作」的对照表：哪些改完敲 /reload、哪些必须重启进程；
  • 说清 /reload 的固定顺序、它做到哪一步为止、以及它为什么「不回滚」；
  • 写对带后台线程的插件：把线程的终止放进 stop()，并在 catch 里自己释放半途申请的资源；
  • 用 RegisterOptions.override(true) 覆盖内核自带的工具或命令，并解释「插件走了内核工具不会永久消失」；
  • 分清带路由键的扩展点与类型级贡献，知道两种合并规则分别是什么；
  • 能判断一个插件有没有加载成功、加载失败时去哪里找原因，并用真实的内核注册表写单测；
  • 照抄内核升级后的五条检查命令，并解释第 0 步、clean、三个 -P*-it 各自防的是什么；
  • 会给官方插件仓库加一个插件（三件登记事），并知道那个仓库没有正式的贡献流程文档。

1. 什么时候生效：四类改动 × 两种操作

插件的改动分四类，每类的生效方式不同。先把这张表记住，它能省掉大量「我明明改了却没反应」的排查时间。

改动内容典型例子生效方式为什么
config.json 的任何字段 插件扫描目录 plugins.roots、进程名、三份配置文件的路径 需重启 config.json 不参与热更新：它决定的正是「其它文件在哪」，只有重启才重读
插件 jar 的增删（含用同名的 jar 覆盖旧文件） 新装一个插件、删掉一个插件、重新打包后拷进扫描目录 需重启 扫描目录与插件集合只在启动期确定
models.json / agents.json / jellyfish.json 的内容 加一个模型、改 agent 的 allowedTools、改 react.maxRounds /reload 生效 重读配置、重建模型与 agent 索引，并只重启配置段变了的插件，同步等结果
jellyfish.json 里逐插件的两段 plugins.enabled / plugins.disabled 名单、plugins.configurations.<pluginId> 配置段 /reload 生效 内核比对插件配置段的差异，只重启配置段变了的插件（stop + start）
一句话版本

「文件在哪」和「哪些 jar 在」要重启；「文件里的内容」敲 /reload。 前者是部署事实，后者是运行期设置——内核自己也是这么分的（config.json 的 plugins.roots 对 jellyfish.json 的 plugins 段）。

2. 热重载：/reload 到底做了什么

/reload：一次固定顺序的配置重载

是什么
一条把「配置文件的新内容」搬进运行中内核的命令。它不是「重新读取所有东西」——config.json 与插件 jar 集合都不在它的职责里。顺序是固定的，也是同步的： 命令返回时重载已经做完（毫秒级）。
怎么用
# 在 CLI 里直接敲（TUI 的输入框同理）
/reload

# 非交互环境（-cli -p）下同样可以：
java -jar /path/to/jellyfish-cli-0.1.1.jar -cli -p "/reload"

它内部做的七件事（顺序不可换）

  1. modelManager.refresh(true) —— 重读 models.json；
  2. agentManager.refresh(false) —— 重读 agents.json；
  3. pluginRuntimeConfig.refresh —— 重读 jellyfish.json 里给插件用的那部分；
  4. 比对插件配置段 —— 算出哪些插件的那一段变了；
  5. pluginManager.reload —— 只重启配置段变了的插件（stop + start）；
  6. modelManager.refreshCatalogs —— 让模型目录（含插件贡献的目录）重新收敛；
  7. 广播 ConfigReloadedEvent —— 订阅了它的插件 / 组件收到通知。

配置　/reload 自己没有配置字段（它是一条命令）。它影响的是三份内容类配置文件： models.json（模型）、agents.json（agent）、jellyfish.json （插件名单 / 逐插件配置段 / react / permission / subAgent）。 这三份文件在哪由 config.json 决定，而那不在热更新范围内。

三条必须知道的边界

  • synchronized 单飞、不回滚：整个流程串行执行，触发入口只有 /reload。 中途某一步失败不会退回旧配置——你会得到一个「前一半新、后一半旧」的进程，正确做法是修好文件再敲一次 /reload。
  • /reload 与插件运行时的关闭共用同一把锁：close() 也是 synchronized， 并在拿锁前先立旗（关停开始后 reload 空跑返回、bootstrap 直接拒绝）。 没有这一条时，关停期并发到达的 /reload 会在即将卸载的类加载器上启停插件，留下的注册无人回收， 现场表现是「插件已经卸了、工具还能调」。
  • 「重启插件」= stop + start，前提是能力上下文在每次 start() 现造。 PF4J 的插件实例在装载期就被缓存，stop() 不会重置它——所以你把状态存在插件对象的字段上时， 一次 /reload 重启不会把它清干净。要「每次都从零开始」，就在 start() 里显式重置。

什么情况下 /reload 不够

  • 改了 config.json（扫描目录、进程名、三份文件的位置）；
  • 新增 / 删除 / 覆盖插件 jar；
  • 改了插件的代码——即使你把新 jar 拷进扫描目录，jar 集合也只在启动期确定，必须重启；
  • 升级了内核的 jar（换掉 jellyfish-cli-0.1.1.jar）——那是进程的 classpath，只能重启；
  • 你以为「重启插件会清掉插件对象里的字段状态」——这一条恰恰是 /reload 做不到的（见上）。

常见问题

  • 敲了 /reload，模型列表没变？先确认改的是哪一份文件：项目级（./.jellyfish/） 缺省不参与加载，你在项目级改了内容而进程用的是全局级，表现就是「怎么 reload 都没反应」。
  • 插件配置段改了，插件却像没重启？先确认你改的是 plugins.configurations.<pluginId> 这一层（键名写错会落到一个没人读的段里）；再确认改的不只是空白或注释——比对的是解析后的配置段差异。
  • 能在 -server 模式下触发热重载吗？内核的命令域里确实有 /reload， 但 Spring Boot Starter 那条路没有暴露这个入口，建议直接重启——见 14 整合到 Spring Boot。

3. 插件生命周期：start / stop 的契约

生命周期是插件里最容易写错、又最难在本地发现的一处。12 页给过最小骨架， 这一节把几件容易踩坏的事写清楚，并给一个带后台线程的插件的正确写法。

事项契约违反了会怎样
注册窗口 是插件的整个存活期，不是 start() 之内；start() 只是「启动期就能确定的能力」的常用落点 把运行期才发现的能力（如 MCP 握手后才拿到的工具集）硬塞进 start()，只能靠阻塞启动来规避
start() 抛错 插件转 FAILED，框架回收本次已完成的注册、发布状态变更通知、继续处理其它插件 不必自行回滚注册；但框架不保证再调 stop()，所以 start() 里半途申请到的资源要在你自己的 catch 里释放
stop() 返回（或抛错）之后 上下文即失效：一切注册 / 订阅 / 发布当场抛 JellyfishException（fail-closed） 产生注册的后台线程若还在跑，日志里全是异常噪声，而噪声会把排查引向错误方向
注册与订阅的回收 框架按 owner（即 pluginId）一次收干净，插件不需要为了回收而反注册 —（这条是给你省事的：Subscription.close() 是「提前解除」的正式手段，属可选优化）
插件自己的资源 连接、线程、子进程——框架不管，必须覆写 stop() 释放 用户看到的是「jellyfish 都退出了，那条命令还在跑」
stop() 自己抛错 只被记录，不影响其它插件的停止与内核关闭 —
start() 抛错时不保证调 stop()——这是唯一需要你手动兜底的地方

PF4J 对「没有进入 STARTED 的插件」会跳过停止，因此 stop() 里那段「关连接、停线程」的代码 不会被执行到。正确姿势是把那一段抽成一个幂等的私有方法，start() 的 catch 与 stop() 各调一次。

完整示例：一个有后台线程的插件怎么写

是什么
下面这个插件模拟「握手之后才发现远端有哪些工具」的形态：半个能力在 start() 里注册， 另一半在后台线程里、握手成功之后注册。
怎么用
注意 stop() 的先后顺序：先立旗、再打断、最后 join 等它真的退出。 三步都不能省：只立旗，卡在 sleep 上的线程要等满一个周期；只打断，可能醒在一次注册途中。 
package com.example.slowplugin;

import zcd.jellyfish.api.extension.ToolCallRequest;
import zcd.jellyfish.api.extension.ToolCallResult;
import zcd.jellyfish.api.extension.ToolDescriptor;
import zcd.jellyfish.api.plugin.JellyfishPlugin;
import zcd.jellyfish.api.plugin.PluginContext;

import java.util.List;
import java.util.Map;

/**
 * 演示「有后台线程的插件」的正确写法：线程在 start 里起，在 stop 返回前必须停干净。
 *
 * @author you
 */
public final class SlowPlugin implements JellyfishPlugin {

    /** 后台线程的退出旗。volatile：它在别的线程上被读。 */
    private volatile boolean running;

    /** 后台线程句柄。 */
    private Thread worker;

    @Override
    public void start(PluginContext context) {
        this.running = true;
        this.worker = new Thread(() -> {
            try {
                // 这一段可能很慢（例如与远端握手），所以放在后台线程里：
                // 插件被允许阻塞自己的线程，但不该阻塞内核启动
                List<String> discovered = handshakeAndDiscover();
                for (String tool : discovered) {
                    // 运行期注册是合法的：注册窗口是插件的整个存活期
                    context.handle(ToolCallRequest.class, tool,
                            new ToolDescriptor(tool, "由远端发现的工具：" + tool),
                            request -> new ToolCallResult(tool, callRemote(tool, request.getArguments())));
                }
                while (running) {
                    sleepQuietly(1000L);
                }
            } catch (RuntimeException e) {
                // 后台线程里抛异常没人接，只会打一条栈；这里自己记日志并退出
                System.err.println("slow-plugin 后台线程退出：" + e.getMessage());
            }
        }, "slow-plugin-worker");
        worker.setDaemon(true);
        worker.start();
    }

    @Override
    public void stop() {
        // 1) 先立旗：让循环自己决定退出，避免「打断之后继续跑、再注册」的竞态
        running = false;
        Thread thread = this.worker;
        if (thread != null) {
            // 2) 再打断：sleep / wait 会被唤醒，从而尽快看到旗子
            thread.interrupt();
            try {
                // 3) 最后必须等它真的退出：stop() 返回之后上下文就失效了，
                //    此时还在跑的注册路径会当场抛 JellyfishException
                thread.join(2000L);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }
    }

    /** 一次慢握手：返回远端声明的工具名。 */
    private List<String> handshakeAndDiscover() {
        return java.util.Collections.emptyList();
    }

    /** 调用远端工具。 */
    private String callRemote(String tool, Map<String, Object> arguments) {
        return "（此处是你的实现）";
    }

    /** 可被打断的睡眠：打断即返回，由调用方的 while 重新判断旗子。 */
    private static void sleepQuietly(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

配置　生命周期本身没有配置字段：plugin.properties 里的 plugin.id / plugin.class / plugin.version / plugin.requires 是描述符而不是运行期配置；插件能读到的配置只有 plugins.configurations.<pluginId> 那一段（12 页有全字段表）。 start() / stop() 的调用时机由框架决定，不可配。

常见问题

  • 能不能不起后台线程，直接在 start() 里阻塞等握手？技术上可以，但它会把启动拖住； 内核不会因为一个插件慢而超时放弃你，用户看到的是「启动卡住了」。
  • 线程用 daemon 是不是就不用管了？不是。daemon 只保证「不阻止 JVM 退出」， 不保证「不会在 stop() 之后再注册」——后者才是这条契约要防的。
  • 后台线程里注册失败（比如插件已经停了）怎么处理？捕获 JellyfishException 并退出循环， 不要重试：上下文失效是终端状态，重试只会刷日志。
为什么这条契约是「同步返回」而不是「异步通知」

stop() 返回的那一刻，框架就认为这个插件不再产生任何东西——回收是紧接着做的。 异步通知意味着「框架要求插件停」与「插件真的停了」之间有窗口，而这个窗口里产生的登记会落在正在被回收的表上。 所以契约选的是「你告诉我停完了，我才继续」。

4. 覆盖内核自带的工具或命令

RegisterOptions.override(true)：压链顶，而不是就地替换

是什么
内核自带的系统命令与 task 工具以 owner=core 注册，且先于插件启动。 默认注册语义是「同键唯一，撞车即失败」，所以你直接注册同名工具会撞上已有登记。 显式声明 override(true) 才能顶替它。
怎么用
在 context.handle(...) 的最后一个参数上声明 RegisterOptions.override(true)。

配置

字段类型必填默认值含义示例
override boolean 选填 false（RegisterOptions.DEFAULT） 是否允许覆盖同键的既有注册。命中已占用的键时，新登记压在旧登记之上；不声明则注册直接失败 RegisterOptions.override(true)
order int 选填 0 调用顺序，仅对类型级贡献有意义（contribute）。是唯一向插件开放的通道参数，同序按注册顺序 RegisterOptions.order(-10)

RegisterOptions.order(int) 与 RegisterOptions.override(boolean) 都返回不带覆盖 / 不带顺序的选项， 需要两个一起用就派生：RegisterOptions.override(true).withOrder(-10)。 注册选项在 注册那一刻生效，之后改任何文件都不影响已完成的登记 需重启或重启插件。

完整示例

package com.example.taskplugin;

import zcd.jellyfish.api.extension.ToolCallRequest;
import zcd.jellyfish.api.extension.ToolCallResult;
import zcd.jellyfish.api.extension.ToolDescriptor;
import zcd.jellyfish.api.event.RegisterOptions;
import zcd.jellyfish.api.plugin.JellyfishPlugin;
import zcd.jellyfish.api.plugin.PluginContext;

/**
 * 顶替内核自带的 task 工具。
 *
 * @author you
 */
public final class MyTaskPlugin implements JellyfishPlugin {

    @Override
    public void start(PluginContext context) {
        ToolDescriptor descriptor = new ToolDescriptor("task", "task 工具的替代实现（本插件接管）");
        // 第 5 个参数是注册选项：只有显式声明 override，才允许命中已有的同键登记
        context.handle(ToolCallRequest.class, "task", descriptor,
                request -> new ToolCallResult("task", "已被 my-plugin 接管"),
                RegisterOptions.override(true));
    }
}

语义：压在链顶，旧登记仍在表里

  • registerUnique 遇到已占用的键且声明了 override(true) 时， 新登记压在旧登记之上，旧登记仍在表里、只是不生效；对外的「同键唯一」语义逐字段不变（只看链顶）。
  • 解除链顶就是一次回退：Subscription.close()、 或插件停止时的 removeAllUnder(pluginId, PluginOwnerNamespace.SEPARATOR)， 都让被压住的那层自动重新生效。
  • 回收按 owner 判定，与是否生效无关：收的是槽位里的全部登记， 否则被压住的层会在覆盖者离开后悄悄复活。
所以不存在「插件走了，被它顶掉的内核工具永久消失」这种事

如果实现成「就地替换并丢弃旧登记」，插件一卸载，被顶掉的内核工具就会永久消失——而且没有任何日志说明它去哪了。 现在的实现把覆盖做成一条链，于是两种回收路径都自然回退： 插件自己 close() 一个句柄、或者插件整个停掉。

常见问题

  • 不写 override(true) 会怎样？注册直接失败（DUPLICATE_HANDLER）， 并且是在插件启动期就暴露——这正是「默认不覆盖」的用意：避免「工具被静默替换」这类难排查的问题。
  • 能不能覆盖别的插件注册的键？机制上可行（同一条链），但语义上要谨慎： 两个插件抢同一个键会在插件启动时以 DUPLICATE_HANDLER 当场暴露， 而你一旦 override 就等于把对方的实现压住了，用户很难看出是谁干的。
  • 覆盖之后模型看到的工具描述变了吗？变的是链顶那个描述符。 要让模型看到新描述，就给出你自己的 ToolDescriptor（示例里就是这么做的）。

5. 扩展点的两类与两种合并规则

内核的同步扩展面只有两个注册入口——PluginContext.handle(...) 与 PluginContext.contribute(...)。每个扩展点归哪一类是定死的，选错了不是「效果差一点」， 而是根本注册不上或者拿不到你要的结果。完整的扩展点清单与逐项说明在 12 从零开发一个插件，这里只讲两类的判据与合并规则。

维度带路由键（handle）类型级贡献（contribute）
数量同一「类型 + 路由键」至多一个同一类型 0..N 个
判据「一个名字对应一个实现」「同一件事，多方各说一句」
典型扩展点ToolCallRequest（工具名）、CommandRequest（命令名）、CommandOptionRequest（命令名）、InputDirectiveRequest / InputReferenceRequest（标记字符 ! / @）、ModelCatalogRequest（provider 名）提示词、状态栏、面板、回合上下文、权限拦截、工具参数改写与结果整形、工具激活、输入改写、会话持久化、压缩策略、老化策略等
冲突时的表现两个插件抢同一个键 → 插件启动时报 DUPLICATE_HANDLER不冲突：多个实现按 order 升序被依次问一遍
缺实现时的表现NO_HANDLER调用点走「0 个 handler」的保守缺省

合并规则只有两类，而且都写在调用点（注册表只做有序查找与单处理器执行，不做编排）：

规则语义典型扩展点
链式 逐环传递，最后一环天然生效，不存在「谁胜」 输入改写、工具参数改写等
合并 order 最小、且声明了该字段的那一个胜出 按字段合并的类型级贡献
两条硬规矩
  • 禁止「取最后一个非缺省」。这类实现看着更宽容，实际让「谁生效」取决于注册顺序， 而注册顺序又取决于插件扫描顺序——一个没人能预期的量。
  • order 是唯一向插件开放的通道参数，默认 0，同序按注册顺序。 其余通道参数（谁是唯一处理器、无处理器怎么办、在内核哪个线程执行）都由注册入口与调用点决定，不暴露。

如果你在给内核新增扩展点：请求类型必须显式定义「0 个 handler 时是什么行为」并写测试 （老插件不注册它时，调用点必须走与改造前逐字段一致的路径），还必须写明失败语义 （handler 抛错时按 ABSTAIN / 保留原值 / 继续 中的哪一个处理）。 请求与结果类型放 api，恰好一个可见构造器 + 静态工厂，新增字段只能用新静态工厂补、不加兼容构造器。 最后一步不能忘：在脚本桥接的能力档里登记（见本页第 8 节），否则插件仓库会构建失败。

6. 调试：怎么确认插件真的加载了

/help 与启动日志：两个观测点

是什么
插件的成败有两处可观测量：启动日志（有没有被扫描到、有没有启动起来）与 能力面（/help 里有没有它的命令、模型能不能看到它的工具）。 插件加载失败不会让内核起不来，因此「启动失败」这个形态根本不会出现——只能自己去看这两处。
怎么用
按这个顺序查，前面的都通过再看后面：
  1. jar 在不在扫描目录里：PF4J 只在目录下一层找 plugin.properties，不递归。 平铺 jar 与「一个插件一个子目录」两种形态都支持，但再深一层就找不到。
  2. 有没有被名单排掉：jellyfish.json 的 plugins.disabled。 顺带确认 plugins.roots 指向的目录就是你以为的那个（相对路径按进程工作目录解析，行首 ~ 展开为主目录）。
  3. 描述符体检过没过：plugin.id 含命名空间分隔符、plugin.requires 写成非法表达式之类的问题在这一步被拒，插件起不来。
  4. 启动有没有抛错：start() 抛错 → 插件转 FAILED，只在日志里可见。
  5. 能力面：/help 里看不到你的命令，就是前四步里有一步没过。

7. 内核升级后要做的检查

Jellyfish-Plugins 是一个独立的 Maven reactor，jellyfish-api 取自本地仓库， 因此「内核改了」与「插件看到了新内核」之间有一道需要手动跨过的缝。内核一侧改了 jellyfish-api 之后， 按顺序跑下面这几条，只有全绿才算真的没问题： 

(cd ../Jellyfish && mvn -q install -DskipTests)   # 0. 不能省
mvn -q clean package                              # 1. 必须 clean
mvn -q -Pshell-it test                            # 2. 三个端到端 profile
mvn -q -Pmcp-it test
mvn -q -Pscript-it test

三条注意事项，以及它们各自防的是什么

注意防的是症状
第 0 步不能省 插件仓库不依赖内核源码树，jellyfish-api / jellyfish-infra 来自本地 Maven 仓库 「内核明明改了，插件这边编译却看不到」——你编的是本地仓库里的旧构件
必须 clean 增量编译会复用按旧 jellyfish-api 编出的 target/ 编译问题被伪装成运行期问题。仓库里记了一个实例：内核给 SessionSnapshot 加字段之后，不带 clean 报的是 11 条 NoSuchMethodError
三个 -P*-it 一个都不能漏 mvn test / mvn package 不跑 *IT 坏掉的端到端不会被它们发现。三个 profile 分别覆盖真 /bin/sh、真 fork 进程的 MCP echo server、真 python3 / node
同一节里还有两条与值类型有关的纪律
  • 引用 api 的值类型优先用静态工厂；
  • 测试夹具反过来，必须用全字段构造器——夹具要填满全部字段， 否则「后加字段读不回来」的失真会被静默吞掉（往返测试照样全绿，而现场是「文件写出来了，重启后那个属性悄悄回到默认值」）。
只在内核一侧改了 api 才需要这一套

日常改插件代码只需 mvn -q package -DskipTests（加上 clean 更稳）+ 把 jar 拷进扫描目录 + 重启进程。上面这套是「内核动了跨边界契约」时的完整回归。

8. 脚本插件进阶：熔断、周期任务与能力档

脚本插件的写法（manifest.json 字段表、两门语言的 API 逐条对照、可直接拷贝的示例）在 Jellyfish-Plugins/examples/scripts/README.md，12 页给过入口。 这里只讲三类「用起来才会碰到」的东西：熔断与超时、周期任务、能力档。

熔断：连续失败 → 冷却 → 自动半开 → 永久

是什么
脚本插件有三层隔离：进程隔离 + 静态清单 + 熔断。熔断解决的是「这个脚本一直坏」—— 每次调用都等满超时再失败，会把用户的耐心和 react 线程一起耗掉。 熔断不摘注册：熔断只是一种「暂时拒绝」，工具定义仍然在清单里， 因此熔断期间的调用会立刻被拒（而不是等满一个超时）。
怎么用
直接配在桥接插件的配置段里；熔断态在 /python（或 /node）台账里看—— 那是它唯一的观测窗口。

配置

字段类型必填默认值含义示例
scriptsRoot string 选填 scripts/python（python 桥）/ scripts/node（node 桥） 脚本根目录，相对进程工作目录解析；其下每个含 manifest.json 的子目录是一个脚本插件。目录不存在等于「还没建脚本」 ~/.jellyfish/scripts/python
pythonPath / nodePath string 选填 python3 / node 解释器路径。没装解释器也不影响内核启动（启动期零进程），工具清单依然完整 /usr/local/bin/python3
invokeTimeoutSeconds int 选填 30 单次调用超时；写 0 表示没有截止时间（不是「立刻超时」）。超时会隔离该脚本的 worker 并计入熔断 90
workerIdleSeconds int 选填 300 worker 的空闲自毁秒数（写 0 关闭） 600
gatewayIdleSeconds int 选填 600 网关的空闲自毁秒数（写 0 关闭） 900
manifestStrict boolean 选填 true 脚本首次拉起时逐项比对清单与实现，任何漂移都报错并熔断该脚本 false
events.allow array<string> 选填 []（不写即「不收窄」：空清单不做任何事件名过滤） 可订阅事件的收窄清单。只收窄、不扩展——可订阅事件清单硬编码在运行时里，写不存在的事件名不会扩大任何能力 ["PluginNotificationEvent"]
circuitBreaker.failuresToOpen int 选填 2 连续失败几次后熔断。写 0 是显式关闭熔断（不会被当成「没配」退回默认值） 3

circuitBreaker.roundsToPermanent int 选填 3 半开探测失败几轮之后转为永久熔断 5

常见问题

  • 熔断期间的调用会不会被当成「工具不存在」？不会。工具定义仍在清单里，调用被立刻拒绝， 理由里带「熔断」。不摘注册是有意的：模型看到的是稳定的工具面，变的是可调用性。
  • 为什么熔断段写成非对象会报错？整个 circuitBreaker 段缺失、段内单字段缺失都走默认值， 但类型不对则当场报错——熔断参数写错的表现是「阈值悄悄变了」，而现场要等到某次故障才出现。
  • 超时与取消都算失败吗？超时会隔离 worker 并计入熔断； 用户按 Esc 造成的取消不计入熔断——它是用户主权，不是脚本的毛病。
  • 热路径点为什么老显示「未启动」？request_tuning / aging_strategy 每次组装请求都会被问到， 桥接层对它们不冷启动、只给 2 秒截止。推论：只提供这两个贡献的脚本永远不会被拉起， 要让它跑起来至少还得提供一个会被真正调用的点（工具、命令、turn_context、turn_before……）。

周期任务（schedules）：让脚本「到点做一件事」

是什么
脚本没有自己的主循环（worker 只在被调用时活着，空闲还会自毁）， 因此「到点做一件事」这个发起方只能落在桥接层：清单里声明一条 schedules， 桥接插件就按它的间隔调用脚本里同名的处理函数。
怎么用
清单里声明，脚本里用装饰器 / 声明函数实现同名处理函数： 
# manifest.json: "schedules": [ { "name": "refresh", "intervalSeconds": 60 } ]
@periodic(name="refresh", interval_seconds=60)   # Node: periodic({name: 'refresh', intervalSeconds: 60}, fn)
def refresh_watch(ctx):
    reload_cache()          # 返回值被忽略

配置

字段类型必填默认值含义示例
schedules array<object> 选填 不写即「没有周期任务」 清单里声明的周期任务列表；写在 manifest.json 里，因此启动期就定了 [{"name": "refresh", "intervalSeconds": 60}]
schedules[].name string 必填 —（没有缺省值：清单解析时缺 name 直接抛错，同名重复也报错） 周期任务名；桥接按这个名字调用脚本里同名的处理函数 "refresh"
schedules[].intervalSeconds int 选填 5（下限 1） 间隔秒数。语义是「上一次跑完 + 间隔」，因此天然不会重入。只支持固定间隔，不做 cron 60
scripts.<脚本 id>.schedules.<任务名>.intervalSeconds int 选填 清单里的声明值 覆盖清单里的间隔；越界会回落声明值并发一条配置告警 30

schedules 写在清单里，改它等于改插件内容 需重启； 覆盖间隔写在插件配置段里，改完 /reload 会重启插件 /reload 生效。

完整示例

{
  "plugins": {
    "configurations": {
      "jellyfish-plugin-python": {
        "scripts": {
          "stock": {
            "dataDir": "~/.jellyfish/stock",
            "schedules": { "refresh": { "intervalSeconds": 30 } }
          }
        }
      }
    }
  }
}

常见问题

  • 定时抓到的新数据为什么屏上的面板不重画？周期任务成功之后由桥接层代发一次界面失效事件 （脚本的可发布事件白名单里没有 UiInvalidatedEvent）。没有这一步，新数据只会写进文件。 失败时则不发失效事件——数据没变，重画面板只是白跑。
  • 任务抛异常会怎样？失败只记一条日志，任务照常继续。因此任务体该做的容错要自己做； 「跳过这一次」必须是正常 return，不能抛异常（抛了会被记一条 WARN， 甚至让后续触发静默停止）。
  • 定时任务会不会让进程常驻？会多占一份资源：定时调用让该脚本的 worker 不再空闲自毁 （缺省空闲 300 秒回收）。一个脚本一条守护线程；关闭插件时先停定时器、再关网关。
  • 把自动刷新开关关掉，进程就没了吗？没有。关掉用户开关只让它不联网，周期任务本身不会停 （清单里的 schedules 在启动期就定了）。要连进程一起不要，得去掉 schedules 或关掉整个桥接插件。

能力档：脚本能用哪些扩展点

是什么
脚本插件与 Java 插件在机制上同构（同样的注册、owner、回收、生命周期）， 但扩展点覆盖的是一份「能力档」而不是全部。真源是 jellyfish-script/src/main/resources/script/extension-points.json，由单测守着。
怎么用
写脚本的人不用操作——但给内核加扩展点的人必须在这里做一次决策， 否则插件仓库会构建失败（这是有意的：先做分档决策，再决定要不要实现）。

新增一个插件要做的三件登记事

是什么
一个插件是「一个 jar 一个 plugin.properties」，因此一个插件一个子模块。 除了写代码，还要在三处「登记」它，否则它不会被构建、不会被拷进扫描目录、也不会出现在插件一览里。
怎么用
前两处是构建与安装链路，第三处是文档。三处都在仓库根，改动都在各自的顺序位置上。

配置（三处登记点）

10. 常见问题

加了插件但 /help 里没有它的命令

最常见的一类「装了但没生效」。按顺序查三处：

  1. jar 在不在 config.json 的 plugins.roots 指向的目录里 （PF4J 只在目录下一层找 plugin.properties）；
  2. 有没有被 jellyfish.json 的 plugins.disabled 排掉；
  3. 新增 jar 必须重启——/reload 管不了 jar 集合。

-cli / -server 下写类工具总是被拒

那两个外壳没有审批者，而 ASK 就是拒绝——fail-closed。两条路可选： 别把工具放进 askTools；或者为 shell 配 commandPolicy.trustedCommands （白名单只管准入、不解除审批）。细节见 10 权限与审批。

MCP server 连不上

连接失败不会让内核起不来，因此只在它自己的状态里看得见。敲 /mcp 看连接状态、工具数与失败原因——那是唯一的线索。

脚本插件报「环境变量未设置」

配置段里写了 ${SOME_KEY} 而环境变量没设，是硬失败：整个进程启动即失败 （environment variable is not set: SOME_KEY），不是「取不到就留空」。确实要用的密钥才写 ${...}， 并保证它总是已设；不用某个后端时把那个键留成 ""，不要写占位符。 另外：密钥不能靠环境变量直接传给脚本进程（脚本进程的环境是严格白名单）， 与 Java 插件同一条通道是配置段里的 ${ENV} 插值。

改完 SKILL.md / AGENTS.md 要不要重启

  • SKILL.md：不用重启——目录缓存按文件修改时间失效。
  • AGENTS.md：会话中途修改一个已经存在的 AGENTS.md 不生效 （project 插件对「已经读到的内容」每个会话只缓存一次），开个新会话即可。
  • 反过来，新出现的 AGENTS.md 立刻生效：/init 写完之后， 同一会话的下一轮模型就能看到它。

插件 A 把插件 B 的工具顶掉了，怎么恢复

覆盖是一条链，链顶被回收就回退——这是设计而不是巧合。三种恢复办法任选一个： 让 A 自己 Subscription.close() 那个句柄；在 jellyfish.json 的 plugins.disabled 里禁掉 A 并 /reload；或者删掉 A 的 jar 并重启进程。 不需要为了恢复 B 去动 B。

通用排查路线：现象 → 先确认「改动属于哪一类」（第 1 节的表）→ 再看第 6 节的两处观测点 （启动日志、/help）→ 都不对就开 DEBUG 日志。跨页的场景清单在 15 故障排查。

关键结论

  1. 「文件在哪」和「哪些 jar 在」要重启，「文件里的内容」敲 /reload。 config.json 的任何改动、插件 jar 的增删、插件代码改动、内核 jar 升级，都只能重启。
  2. /reload 是固定七步、单飞、不回滚、同步：重读三份内容类配置、重建模型与 agent 索引、 只重启配置段变了的插件、广播 ConfigReloadedEvent。中途失败不会退回旧配置。
  3. 注册窗口是整个存活期，不是 start() 之内；stop() 返回之后一切注册当场失败（fail-closed）， 所以产生注册的后台线程必须在 stop() 返回前停下来。而 start() 抛错时框架不保证调 stop()—— 半途申请到的资源要在自己的 catch 里释放。
  4. RegisterOptions.override(true) 是压在链顶而不是就地替换：旧登记仍在表里， 链顶一被回收就自动重新生效。因此不存在「插件走了，被它顶掉的内核工具永久消失」这种事故。
  5. 扩展点两类：带路由键的 handle（同键唯一，撞车即 DUPLICATE_HANDLER）与 类型级 contribute（0..N，按 order 升序）； 合并规则只有「链式」与「order 最小且声明了该字段者胜出」两种，禁止「取最后一个非缺省」。
  6. 插件加载失败不会让内核起不来，所以排查入口只有两处：启动日志与 /help； 单测要引 jellyfish-infra（test scope）拿真实的注册表与事件通道。
  7. 内核改了 jellyfish-api 之后：先 install、必须 clean、三个 -P*-it 一个都不能漏。 三条防的分别是「编的是本地仓库旧构件」「编译问题伪装成运行期问题」「坏掉的端到端没被发现」。
  8. 脚本插件的三层隔离里，熔断不摘注册（只是暂时拒绝）；周期任务的间隔语义是「上一次跑完 + 间隔」， 失败只记日志但不发失效事件；能力档分 in / planned / excluded 三段， 内核新增扩展点未分档会让插件仓库构建失败。
  9. 官方插件仓库没有正式的贡献流程 / 评审清单 / 发版步骤文档（聚合工作目录根与五个仓库的 .github/、CONTRIBUTING*、RELEASE*、docs/ 及各 AGENTS.md 都逐一检查过，全都没有——是「确实没有」而不是「没查」）， 只有 AGENTS.md 的 Git 约定；新增插件要做的三件登记事是：父 pom.xml 的 <modules>、cpPlugins.sh、README.md 的插件一览表。
