04 三种运行模式

三种模式共享同一个入口与同一份装配，只靠启动参数区分。这一页把三种外壳的对照、 完整参数表、退出码、CLI 的输出契约、TUI 的按键与浮层、Server 的鉴权与接口契约一次讲清， 最后给一张「怎么选」的决策图。所有条目都标了仓库出处。

学习目标

  • 说出 -cli / -tui / -server 各自的形态、是否需要终端、什么时候用它；
  • 背下「一个参数都不带 = -tui」的兜底规则，以及「哪些参数只归 -cli，其余模式带上退 2」；
  • 会读退出码 0/2/3/4/3(TUI)/6/7，并知道归类看的是「失败发生在哪一步」；
  • 在 TUI 里敲对键：Ctrl+S 发送、Enter 换行，并会用 Ctrl+T / Ctrl+E / Ctrl+O / /ui；
  • 把 Server 安全地跑起来：绑非回环地址必须配密钥，写请求要过来源校验，除 GET /health 外都要 Bearer；
  • 用一张表决定「要接进自己的程序 / 要脚本化 / 要人机交互 / 要给别人调」分别该用哪种模式。

一个内核，三种外壳

三种启动模式、一个内核：共用 main、DI、AgentHarness、 CommandManager，差异收在 RunMode 里。三种外壳的命令一致（输入以 / 开头即走命令域），能力也都来自同一批插件。

模式形态交互性需要可交互终端典型命令适用场景
-cli 单次调用、不交互：进一个输入，出一次结果后退出 无 不需要（可以是被重定向的 shell、管道、CI） jellyfish -cli -p "今天天气怎么样？" 脚本、CI、批处理、把回答重定向到文件；退出码是机器契约
-tui 交互式终端界面（TamboUI）：消息区 + 输入框 + 状态栏 有（浮层式审批与提问） 需要（备用屏 + raw 模式），否则启动即报错退 3 jellyfish -tui（等价于裸跑 jellyfish） 自己在终端里干活：多轮对话、看工具轨迹、逐次审批
-server HTTP 服务（Undertow），对外暴露 REST + SSE 接口 无界面，审批与提问搬到 HTTP 层 不需要 jellyfish -server 9096 给别人调（前端 / 其它服务）、常驻提供 agent 能力

外壳种类是插件可见的进程级事实：Launcher 在 bootstrap() 之前把 RuntimeInfo 写进 RuntimeInfoHolder（插件在 start() 里就会读它），因此插件能在启动期就按外壳收窄自己的行为：

启动参数（完整表）

下面是全部启动参数，一条不多、一条不少：

参数说明
-cli / -tui / -server模式旗标，三选一；一个参数都不带时默认 -tui，否则必填；-server 可带位置端口
-p, --print <输入>单次模式的输入；缺省时从 stdin 读到 EOF（管道可用）
--session <会话>切换到已有会话（需安装 jellyfish-plugin-session-file 等持久化插件；会话不存在时按用法错误退出 2）
--agent <agentId>新建会话时绑定 agent
--model <provider/模型>新建会话时指定模型，必须含 /
--port <端口>服务器端口（等价于 -server 的位置参数，缺省 9096）
--host <地址>服务器绑定地址（缺省 127.0.0.1）
--show-thinking在 -cli 的工具轨迹之外单独打出思考过程（TUI 用 Ctrl+T / /thinking）
--show-tool-args-cli 的工具轨迹行上打出调用参数（单行，过长截断；TUI 用 Ctrl+E / /toolargs）
--verbose日志级别降到 DEBUG（也可用 -Djellyfish.log.level=DEBUG）
--trust-project-config信任并加载项目级配置（./.jellyfish/*.json），仅本次进程有效、不落盘。缺省不加载，理由见 05 配置体系总览
-h, --help / -V, --version帮助 / 版本号
只归 -cli 的五个参数——带错模式会直接退 2

--agent / --model / -p / --show-thinking / --show-tool-args 只归 -cli：-tui / -server 带上它们一律判用法错误退 2——拒绝而不是静默忽略。

为什么是拒绝：静默忽略会让「我明明写了 --model」变成一次跑在别的模型上、却没有任何提示的调用。 模式与参数不匹配属于配置错误，越早暴露越好。

兜底规则：判据只有「参数个数为零」
  • args 为空（含 null）→ StartupOptionsParser 把模式定为 -tui，等价于显式 jellyfish -tui。交互界面是最常用的入口，不必先把旗标背下来。
  • 带了任何参数却没给模式→ 报「请指定启动模式」退 2。 jellyfish --verbose 一样如此。兜底不许扩成内容推断，这样 「敲了没反应」与「悄悄挂在等 stdin」两头都不会发生。
  • 兜底收在解析器里，因此 Launcher 与各 RunMode 只面对「模式已定」的世界。
--api-key 为什么不在上面的表里？

README 的主参数表里没有 --api-key；它只出现在「Server 模式」一节的示例中 （--api-key <密钥>），并与环境变量 JELLYFISH_SERVER_API_KEY 二选一。 因此本页把它放在下面的 Server 小节里讲，不混进通用参数表。

上游两处口径不一致：--agent / --model 在 Server 下
  • 说「拒绝」的有两处：Jellyfish/README.md 写「--agent / --model / -p / --show-thinking / --show-tool-args 只归 -cli：-tui / -server 带上它们 一律判用法错误退 2」 （Jellyfish/README.md:137，参数表另见 Jellyfish/README.md:127-128）； constraints.md 的「Server」一节写的是同一件事：「启动期不建会话。 --agent / --model / -p / --show-thinking 只归 CLI， 其余模式带上这些参数一律判用法错误退 2——拒绝而不是静默忽略」 （Jellyfish/docs/constraints.md:1032-1033）。
  • 说「降级」的有一处：constraints.md 的「会话语义」一节写 「--agent / --model 降级为『新建会话的默认值』」 （Jellyfish/docs/constraints.md:1191）。
  • 该信哪一个：以「拒绝」为准——这一条在实现里没有含糊的余地： StartupOptionsParser 在解析阶段对 -p / --agent / --model / --show-tool-args / --show-thinking 逐个调 requireCliOnly，只要模式不是 -cli 就抛异常 （Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/StartupOptionsParser.java:257-266， 判定本体见 Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/StartupOptionsParser.java:314）；该异常在进程入口被翻成退出码 2 （Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/JellyfishApplication.java:73-77 配 Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/ExitCodes.java:20）。 ServerRunMode 的类注释重申了同一结论并给出理由：「--agent / --model 在解析阶段就被判为用法错误退 2——新建会话的 agent 与模型由调用方在 POST /sessions 的请求体里给定，服务端不另存一份启动参数默认值」 （Jellyfish/jellyfish-cli/src/main/java/zcd/jellyfish/cli/mode/ServerRunMode.java:37-40， 不另存默认值的理由另见 Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/ServerConfig.java:11-12）。
  • 「降级」那句要能成立，只能这样读：它说的是 POST /sessions 请求体里的 agentId / provider / model——这三个字段确实存在、且全可空 （不填就按内核默认解析）：Jellyfish/jellyfish-server/src/main/java/zcd/jellyfish/server/dto/CreateSessionRequest.java:9-29。 也就是说「建会话时可以由请求指定」，而不是「Server 下启动参数会被降级收下」。本页全篇按前者写。

退出码

退出码是机器契约（-cli 与裸跑的 -tui 都在此口径内； -server 是常驻进程，没有单次退出码语义）：

退出码含义典型触发
0 成功（含「未知命令」这类用户输入错误） 正常回答、/help 打出清单
2 用法错误：参数缺失 / 未知 / 冲突，--session --agent --model 指向不存在的东西，或没有输入 jellyfish --verbose；-tui 带上 --model
3 启动失败：配置、插件或装配出错 配置解析失败、插件加载失败、-server 绑定失败
4 运行失败：回合抛异常，或命令执行失败 模型调用报错、工具执行抛错
3（TUI） TUI 需要可交互终端而当前没有（stdin 或 stdout 被重定向也算） 在管道、CI、被重定向的 shell、IDE 的非真终端控制台里跑 -tui
6 回合未收敛：达到最大轮次仍未给出最终回复 模型反复调工具不收尾
7 回合被插件拦下：一句都没发给模型（stdout 保持为空，原因在 stderr） agent 策略或权限插件在回合开始前拦下
归类看的是「失败发生在哪一步」，不是异常属于哪个类
  • bootstrap 期间的任何运行时异常都算「内核没起成」，退 3；
  • 内核起来之后的运行期故障一律是 4（哪怕它不是 JellyfishException）；
  • mode.run 与「参数没问题却仍然出错」的会话准备也算运行期故障（4）。

只认 JellyfishException 会让别的运行时异常穿到进程入口、被打成「初始化失败」退 3—— 而那时内核往往已经起来了，脚本会据此去改一份本来没问题的配置。这就是为什么判据必须按「哪一步」而不是「哪个类」。

Jellyfish/README.md「输出与退出码」（退出码表与归类说明）、Jellyfish/docs/constraints.md「三个外壳的共同约定」（退出码是机器契约、按步骤归类）

CLI（-cli）

stdout / stderr 分离：重定向是安全的

是什么
回答与命令结果走 stdout，诊断、工具进度与日志走 stderr。因此你可以放心把回答重定向进文件， 而不会被进度噪音污染。
怎么用
# 回答进 answer.txt，诊断进 diag.txt
java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -cli -p "总结这个项目" > answer.txt 2> diag.txt

# 不写 -p 时从 stdin 读到 EOF，管道可用
echo "/help" | java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -cli

回答是按轮缓冲、收敛时整体写出的，所以不会出现「写了一半的 JSON」这种中间态。

写出前一律过 ControlChars，连重定向到文件也不例外

写出去的几乎都是不可信文本（模型回答、工具输出正文、异常消息、命令回显），因此 writeOut / writeErr 走 strip（保留换行——增量诊断靠它断行）， writeErrLine 走 singleLine（整行语义下换行是注入手段）。

判据取「文本从哪里来」而不是「写到哪里去」：JDK 1.8 没有可靠的「这是不是终端」判定，而 「有时过滤有时不过滤」会让行为随运行环境变化。代价是重定向到文件时回答里的控制字符也会被剔掉—— 这是刻意的取舍，不是遗漏。

TUI 没有 stdout 契约

-tui 独占备用屏，> answer.txt 不适用，退出后也不回显会话内容。 要把结果存下来就用 -cli。

工具轨迹：默认两行，--show-tool-args 加打参数

是什么
单次模式的工具轨迹默认只给「开始」与「结束」两行；加旗标后才补上调用参数，且单行、最多 200 字。
怎么用
java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -cli -p "跑一下单测并总结失败原因"
java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -cli --show-tool-args -p "跑一下单测并总结失败原因"

默认两行的形状（README 的原例）：

→ shell
← shell 完成（N 字符）

加 --show-tool-args 之后（README 的原例）：

→ shell {"command": "mvn -q test", "cwd": "/x"}
参数不脱敏——别把带密钥的输出贴出去

参数不脱敏：外壳按参数名猜不出哪个是密钥，遮不住命令原文与写入正文这些真正会出事的地方。 --show-tool-args 与 TUI 的 Ctrl+E 同此口径。

常见问题

  • 参数被截断了？单行 200 码点封顶是刻意的；要看完整参数就去看会话里那次调用的记录。
  • -cli 下审批怎么办？没有审批界面，askTools 里的工具一律按拒绝处理， 要人工确认请用 -tui 或 -server（见 10 权限与审批）。
Jellyfish/README.md「输出与退出码」「快速开始」、Jellyfish/docs/constraints.md「三个外壳的共同约定」（CLI 输出契约、ControlChars 收口点、200 码点封顶）

TUI（-tui）

-tui 需要可交互终端（备用屏 + raw 模式）。在管道、CI 或没有终端的环境里启动会 立刻报错并退出 3，不会挂住。 

java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -tui

命令输出面板：命令结果不进消息区

是什么
/help、/session、/status、插件命令这些结果都显示在输入框上方那块 DOCK 面板里，不进消息区。压缩的完成 / 失败结果也走这块面板—— 它是外壳对刚发生那件事的回应，同样不是会话消息。
怎么用
  • 它只留最近一次——再敲一条就替换；
  • 内容超长时用 PageUp / PageDown（或滚轮）翻，Esc 关掉；
  • 开始新一轮对话或新敲一条命令时自动让位；
  • 面板占用的行数由外壳在纵向预算里分配（最多 8 行内容，超出靠滚动），矮终端上它会变矮，而不是把消息区挤没；
  • DOCK 这一格与插件的 DOCK 面板共用：有命令输出时它优先，关掉面板后插件面板立刻回来。
为什么命令输出不进消息流

首页上那样会让字标被逐条命令输出顶走，会话页上会让命令输出插进对话中间。 插件通知仍然按时间戳插进消息流（它是异步推送的状态，不是用户敲出来的反馈），两者刻意走不同的路。

为什么发送不是 Enter

终端 raw 模式下所有「带修饰的 Enter」都无法与普通 Enter 区分，因此 「Enter 发送 + 修饰键换行」在任何终端上都不可实现——反转之后 Enter 稳定换行、 Ctrl+S 稳定发送。

另外：这五个外壳自有命令在回合进行中也生效（它们不写会话，与 Ctrl+T / Ctrl+E / Ctrl+O 是同一个动作）；普通文本仍要等回合结束，草稿留在输入框。

是什么

│                                    │

浮层优先级超时Esc 的语义
审批框 最高，优先于补全面板与二级选择页，可见时吞掉其余按键 缺省 120 秒（permission.approvalTimeoutSeconds；写 0 表示永不超时），等不到答复按拒绝处理 拒绝并中断回合（只拒绝的话模型往往会换个方式接着试）
提问框 低于审批、高于二级选择页与补全 缺省 120 秒（ask.timeoutSeconds；写 0 则永不超时），等不到答复时工具回一条「用户没有回答」让模型继续 放弃作答（不是中断回合）——模型收到「用户取消了这次提问」后自己接着判断
审批参数按原文显示，不脱敏

参数原样显示（含 apiKey 这类键的值）：审批要回答的是「放不放行这次调用」， 而能回答它的只有原文。超长参数折行显示并在截断处写明省略了几行。

提问框则是选任何一项都不会放行任何工具，只是把答案告诉模型；选项很长时光标停在哪一项、 哪一项就完整折行展开（最多 6 行）——你准备按 Enter 的那一项一定是完整的。

插件面板与 /ui

是什么
插件可以往界面上放两类东西：状态栏尾部的一小段文本（例如待办插件的 待办 2/5） 与一块常驻面板（例如完整的待办清单）。位置、宽度、行数全部由外壳决定， 插件无权把消息区挤没；插件不可能自己造 TamboUI 组件。
怎么用
/ui                        选区域（二级页）：每行标出该区域显示的是谁、还有几个候选
/ui right                  选插件（三级页）：该区域的候选插件 + on / off，当前那个标「（当前）」
/ui right jellyfish-plugin-todo   直接指定：由某个插件占用该区域
/ui right cycle            在该区域轮换到下一个候选
/ui right off              关掉该区域（/ui right on 恢复）
/ui list                   不弹页面，直接列出所有贡献：区域 | 插件 | 标题 | 是否可见 | 还有哪些候选 | 没生效的插件快捷键

打开它有两种方式：把 /ui 敲到输入框里、在补全面板里按 Enter 选中， 或者直接把 /ui 发出去——两者打开的是同一个区域选择页。

情形行为
两个插件抢同一区域默认只显示 order 最小的那个，其余进入候选
界面窄于 80 列左右侧栏自动隐藏；窄到放不下时面板让位给消息区
浮层出现时面板不会消失，只会变矮：DOCK / TOP 在剩余预算里分配行数（DOCK 优先），矮到放不下就暂时不显示；浮层关掉后自动恢复
想整体关掉插件 UI-Djellyfish.tui.pluginPanels=false
「我绑的键为什么没反应」快捷键诊断只在 /ui list 里显示

日志：只写文件，且必须滚动

是什么
TUI 是唯一写文件的日志目标（长时间驻留，一次开几天），因此单文件涨到上限就轮换，历史档数也有上限。 日志绝不写 stderr——它独占备用屏。
怎么用
默认路径    <用户主目录>/.jellyfish/jellyfish-tui.log
单文件上限  -Djellyfish.log.maxSize=20MB     （缺省 10 MB；20MB / 20 MB / 1048576 三种写法都认，单位 KB/MB/GB）
历史档数    -Djellyfish.log.maxFiles=10      （缺省 5，因此磁盘上限约 60 MB）
改路径      -Djellyfish.log.file=/path/to/your.log

历史档是 jellyfish-tui.log.1、.2……更早的自动删掉。 当前日志始终写在 jellyfish.log.file 那个名字上，历史是它的 .%i 后缀。

-cli / -server 没有文件日志

这两种模式只写 stderr（你自己把 stderr 重定向到文件，那是你的事，不归这条管）。 因此排查「日志去哪了」时先确认自己在哪个模式里。

Server（-server）

启动与绑定

是什么
HTTP 服务（Undertow），对外暴露 REST + SSE 接口。默认只绑 127.0.0.1， 且没配密钥时不鉴权——对只绑回环的本地场景够用。
怎么用
# 只在本机可用（缺省行为）
java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -server 9096

# 对外暴露：必须同时配密钥
JELLYFISH_SERVER_API_KEY=$(openssl rand -hex 32) java -jar jellyfish-cli/target/jellyfish-cli-0.1.2.jar -server --host 0.0.0.0
绑非回环地址却未配密钥 → 拒绝启动，退 3

那等于把「建会话、跑命令、读全部会话正文」交给同网段的任何人，而一行 WARN 是拦不住这种配置的。 因此判据用 InetAddress.isLoopbackAddress()（localhost / ::1 / 127.0.0.2 都算回环），解析不出来按非回环处理（那多半是主机名写错了， 让它在启动期暴露）。回环 + 无密钥仍然允许，那是「本机跑一次」的刻意缺省。

另外记住：绑定失败也退 3（启动条件不具备），不是 4。

密钥的两条通道

通道类型必填默认值含义示例
JELLYFISH_SERVER_API_KEY 环境变量 选填（但绑非回环时必配，否则拒绝启动） 无（缺省不鉴权） 服务端 API key，推荐用法：不会出现在 ps 输出里 JELLYFISH_SERVER_API_KEY=$(openssl rand -hex 32) java -jar ... -server --host 0.0.0.0
--api-key 命令行参数 选填 无 同上，走命令行。argv 会出现在 ps 里，同机其他用户看得见 --api-key <你的密钥>
密钥不要走 query 参数

不接受用 query 参数传密钥（URL 会进访问日志、浏览器历史与 Referer）。 密钥比较是常时比较；密钥短于 16 位会在启动日志里告警，但不拒绝启动。

命令域与对话域同权：POST /sessions/{id}/commands 能执行 /reload 等系统命令，因此密钥泄露等于整机权限泄露。

鉴权与来源校验

情形行为
没配密钥（缺省） 不鉴权：任何能访问该端口的人都能建会话、跑命令、读全部会话正文。对只绑回环的本地场景够用
配了密钥 除 GET /health 外所有接口都要 Authorization: Bearer <密钥>，否则 401 + {"error":"UNAUTHORIZED"} 并带 WWW-Authenticate: Bearer realm="jellyfish"
写请求（POST / PUT / PATCH / DELETE）带 Origin 其主机必须与本服务一致，否则回 403（不带 Origin 时退到 Referer；两个头都不带则放行）。Origin 为字面量 null 一律拒绝
GET /health 不校验：探活必须能在「还没有密钥」的场景下工作；路径按归一化后比对（尾斜杠等价）
为什么写请求要查 Origin

这挡的是浏览器被恶意页面指使去驱动你本机的 agent——浏览器对 text/plain 这类「简单请求」会照常发出并执行副作用，只是响应不可读，因此仅靠「只绑回环」挡不住 （请求确实来自本机，只是由别人的页面发起）。不带这两个头的客户端（curl、SDK）不受影响。

跑通一次（完整 curl 示例）

是什么
建会话 → 对话（恒为 SSE）→ 从流里读结论。这是所有接入方的最小流程。
怎么用
# 1. 探活（不需要密钥）
curl -s localhost:9096/health

# 2. 建会话，取出 sessionId
SID=$(curl -s -X POST localhost:9096/sessions | jq -r .sessionId)

# 3. 对话：恒为 SSE，用 -N 关掉 curl 的缓冲，才能看到增量
curl -sN -X POST localhost:9096/sessions/$SID/chat \
     -H 'Content-Type: application/json' -d '{"message":"总结这个项目"}'

配上密钥后，除 GET /health 外的每个请求都要带这个头：

curl -s -X POST localhost:9096/sessions \
     -H "Authorization: Bearer <你的密钥>" \
     -H 'Content-Type: application/json' -d '{}'

是什么
Server 暴露的全部接口，一条不多、一条不少。
方法路径说明
POST/sessions建会话（body 可选 agentId / provider / model）
GET/sessions会话摘要列表（不含消息正文）

GET/asks跨会话最早的那一条待答提问（同上）

接入方必须知道的规则

是什么
这一小节里的每一条都对应一个真实的失败模式。
规则具体行为
同会话同时只允许一个回合 第二个请求返回 409；要打断用 POST /sessions/{id}/cancel，或直接断开 SSE 连接（服务端据此取消回合）。这是内核不变量，槽位占位早于 AgentHarness.chat
命令端点有一道闸门 /new、/resume、/reload、/session、/delete 这类「改进程级状态或按参数操作别的会话」的命令回 403 COMMAND_NOT_ALLOWED——本外壳按会话 id 寻址，建会话用 POST /sessions、删会话用 DELETE /sessions/{id}。GET /commands 仍会如实列出全部命令（过滤器与闸门是两件事）
/sessions/{id}/commands 先校验会话存在 不存在回 404（与 /chat、GET /sessions/{id} 同口径）；命令自身不认识则回 404 + kind=UNKNOWN，两者靠 kind 与状态码并存可区分
人工审批必须按会话寻址 流里推 approval_required，拿 requestId 调 POST /sessions/{id}/approvals/{requestId}：要求 requestId 属于路径里那个会话、且是它的头槽位，否则 404。头槽位每会话一个，会话之间互不排队；同一会话内是 FIFO 队列、上限 8 条，超出只拒新请求、已排队的不受影响
GET /approvals 是只读的发现入口 跨会话最早那一条，带 sessionId——子代理的审批落在它自己的会话上，按主会话订阅的流看不到它，没有这个入口就只能等超时被拒
向用户提问同理 流里推 ask_required，拿 requestId 调 POST /sessions/{id}/asks/{requestId}，请求体给 {"optionId":"…"} 或 {"text":"…"}；两种都不给回 400（「用户自己填的答案」与「客户端写错了请求」必须能分开）
带体的请求要声明 application/json 回 415 的是 text/plain 这类浏览器能跨站发出的内容类型
错误体统一 {"error":"CODE","message":"…"}，且 message 不携带调用方给的文本
POST /chat 不执行命令、不解析输入指令 要与命令域打交道走 /commands；输入指令 ! / @ 也在这里被忽略
带 handoff 的命令只走半程 POST /sessions/{id}/commands 是纯 JSON，与 /chat 的 SSE 契约分开，因此「让模型接着干」的命令（如 /init）需要客户端拿回那段文本再 POST 一次 /chat。TUI / CLI 由内核一次做完
并发流有上限 并发 SSE 流用 maxStreams 封顶（缺省 16，超限 503）。慢客户端会一直占着它那条许可与一个线程直到断开，这是刻意的
单主体模型 一个 API key 就是一个信任域，内核不认识「哪个调用方」。按调用方区分的会话归属与审批归属在 Spring starter 的 user 包里——不要用本服务做多租户
-server 明确不做 自带 Web 前端、TLS

SSE 事件（POST /sessions/{id}/chat）

事件说明
turn_start回合开始
text助手正文增量
thinking思考过程增量
tool_start工具调用开始
tool_output工具执行期的实时输出（可丢，按待发条数封顶；权威结果是 tool_done 的 output）
tool_done工具调用结束（权威结果）；metadata 里 terminal 取值含 FAILED 与 REJECTED，前端据字段渲染失败标记，不要解析 output 首行文案
approval_required需要人工审批
approval_resolved审批已裁决（不带结论）

ask_resolved提问已被作答（或超时 / 收敛），不带答案——结果随后以 tool_done 到达
shell_notice插件推的一条通知，载荷 {owner,sessionId,key,severity,lines}（尽力 lane、可丢、不落盘、不进模型上下文）
shell_invalidated插件说「我贡献的内容脏了」，载荷 {owner,sessionId,what}
input_handled终态：输入被插件接过去了，根本没有回合（不带 turnId，也不占在途回合槽位）
done终态：回合正常结束
cancelled终态：回合被取消
turn_blocked终态：回合被插件在开始前拦下，载荷 {turnId,sessionId,reason}
error终态：回合出错
run_started子代理 run 开始（与回合事件穿插，不参与流的终态判定）
run_finished子代理 run 终结

写出终态事件后流结束；空闲超时写 : keepalive 注释帧。 shell_notice / shell_invalidated 是尽力 lane：与回合没有关系、 可丢、时延最多一秒，客户端不得把它们当状态真源。

done 事件的载荷：notice 不是回答

回合收敛时 done 的载荷是：

{turnId, sessionId, content, rounds, truncated, notice}
  • truncated=true 表示「达到最大轮次仍未收敛」，此时 content 是一句可读提示而非模型回答；
  • notice 表示「收敛了，但有一处从正文看不出来的例外」——目前是回复被输出上限截断或模型一个字都没回，没有例外时为 null；
  • notice 不是回答：它应当用提示样式渲染，不要拼进 content 之后当正文显示（那会让用户以为模型说过这句话）。

要接进已有的 Java 程序，还要按用户隔离 Spring Boot Starter 内核不认识「哪个调用方」，多用户护栏（SessionOwnerStore / ApprovalGateway）只在 Starter 的 user 包里
要脚本化：一条命令进、一条结果出 -cli stdout / stderr 分离、重定向安全、退出码可判；代价是没有审批界面，askTools 一律拒绝
要人机交互：多轮、看轨迹、逐次审批 -tui 浮层式审批与提问、命令输出面板、插件面板；代价是必须真终端，管道 / CI 里直接退 3
要给别人调（前端、其它服务、跨语言） -server REST + SSE、审批走 HTTP；代价是要自己处理 Bearer 鉴权、来源校验、同会话单回合与 409
可以先在 -tui 里试，再照抄成 -cli

三种外壳命令一致（输入以 / 开头即走命令域），所以你在 -tui 里调顺的那串命令与参数，几乎可以直接搬进 -cli -p "..."。反过来不要：-cli 下 askTools 一律被拒，那是一次跑不通的体验，不是配置问题。

常见问题

-tui 启动就退出 3？

是什么
它在管道、CI、被重定向的 shell 或 IDE 的非真终端控制台里都会这样（这是有意的：否则终端界面会永久挂住）。
怎么用
在真实终端里运行，或按「在 IDEA 里调试」一节用远程调试挂接。确认终端可用却被拦下时用 -Djellyfish.tui.skipTerminalCheck=true 跳过检查。

为什么 jellyfish --verbose 报「请指定启动模式」？

是什么
兜底只认「一个参数都不带」。带了参数就必须显式给模式，因此 --verbose 改不了这个结论。
怎么用
jellyfish -cli --verbose -p "..."，或 jellyfish -tui --verbose。

-server 起不来，退出码是 3？

是什么
两条已知的启动期拒绝：绑非回环地址却没配密钥，以及绑定失败 （启动条件不具备，算 3 而不是 4）。
怎么用
先配密钥再用 --host 0.0.0.0。测「绑定失败」请用不可用地址，不要用「占端口」—— macOS 上 Undertow 会设 SO_REUSEPORT，已占端口仍可能绑上。

想让 agent 无人值守地跑，但工具总被拒绝？

是什么
-cli 没有审批界面，askTools 里的工具一律按拒绝处理（绝不静默放行）； -server 恰好相反，审批被显式搬到 HTTP 层。
怎么用
要么把该工具从 askTools 里拿掉（见 07 agents.json 与工具权限）， 要么换 -tui / -server 安排人（或程序）来裁决。

-server 有没有单次退出码？

是什么
没有。它是常驻进程，因此没有 -cli 那套单次退出码语义， 一轮对话的结果只能从 SSE 流里读。
怎么用
客户端按终态事件判断这一轮结束（done / cancelled / turn_blocked / input_handled / error），权威回答在 done 的 content， 权威工具结果在 tool_done 的 output。
Jellyfish/README.md「常见问题」（-tui 启动退出 3、-cli 下工具被拒）、Jellyfish/docs/constraints.md「Server」（绑定失败退 3、测绑定失败的正确方法）、Jellyfish/docs/constraints.md「会话语义」（-server 没有单次退出码语义、终态事件）

关键结论

  1. 三种外壳一个内核、一份装配，差异收在 RunMode；命令一致，能力都由插件提供。插件还能读到进程级事实 RuntimeInfo（shell / hasUI / supportsApproval / interactive）。
  2. 兜底只有一处：一个参数都不带 = -tui；带了任何参数就必须显式给模式，否则退 2。
  3. --agent / --model / -p / --show-thinking / --show-tool-args 只归 -cli；其余模式带上它们一律退 2（拒绝而不是静默忽略）。--api-key 只出现在 Server 模式一节。
  4. 退出码是机器契约，归类看「失败发生在哪一步」：bootstrap 期间任何运行时异常都是 3，内核起来之后一律 4。
  5. CLI：回答走 stdout、诊断走 stderr，重定向安全；工具轨迹默认两行，--show-tool-args 单行最多 200 字且不脱敏。
  6. TUI：Ctrl+S 发送、Enter 换行；命令输出进 DOCK 面板不进消息区；审批优先级最高且 Esc 是「拒绝并中断」，提问的 Esc 是「放弃作答」。
  7. Server：默认只绑 127.0.0.1；绑非回环却未配密钥拒绝启动退 3；除 GET /health 外都要 Bearer；写请求查 Origin/Referer；同会话只允许一个回合（第二个 409）；审批按会话寻址。
  8. 选型判据：要接进自己的程序用 Starter，要脚本化用 -cli，要人机交互用 -tui，要给别人调用 -server。
