02 安装与环境准备

这一页的目标只有一个：你的机器上出现一个能跑的 jellyfish-cli-0.1.1.jar， 旁边放好插件，而且你亲手验证过它能起来——验证用的是不需要模型、不需要密钥的命令， 所以整个安装过程跟「有没有 API key」无关。

学习目标

  • 核对四项环境要求（JDK / Maven / 终端 / 模型），并知道每一项在哪个文件的哪一行；
  • 用一条命令构建出 fat jar，并知道产物路径与 alias 怎么写；
  • 记住开发期最常用的五条 Maven 命令，包括单类单测与 -Pserver-it 端到端；
  • 用两种方式装官方插件，并说清「什么必须重启、什么 /reload 就够」；
  • 在改插件之前先 mvn install 内核，避免「编译看不到内核改动」这类假故障；
  • 用不需要模型的命令验证安装成功，并在 IDEA 里通过远程调试挂上 -tui。

环境要求：先把这四项备齐

四项里有三项是「装上就有」，只有模型是可选的——没有模型也能跑命令域， 所以你可以先完成安装与验证，再去配模型。

字段类型必填默认值含义示例
JDK 版本要求（text） 必填 【不适用】（外部先决条件，无程序缺省值） 源码与目标版本都是 1.8；运行只需 JRE 8+。不要使用 Java 9+ 的 API 或语法 8（JDK 8；运行可用 JRE 8）
Maven 版本要求（text） 必填 【不适用】 构建用；3.2.5 以上（pom.xml 里打包插件的版本线以此为准）。只运行不需要 Maven 3.2.5+
终端 环境能力（boolean 含义） 选填 【不适用】 -tui 需要可交互终端；-cli / -server 不需要。管道、CI、被重定向的 shell、IDE 的非真终端控制台都算「没有」 真实 TTY（Terminal 标签页或系统终端）
模型 外部服务（OpenAI 兼容） 选填 无（未配置时对话不可用） 一个 OpenAI 兼容的 API；没有也能跑命令。密钥放环境变量，不要写进配置文件 OPENAI_API_KEY=sk-***

这张表的「默认值」一列写 【不适用】：这四项是外部先决条件而不是配置字段， 不存在由程序填入的缺省值——配置文件里的字段才有默认值（见 05 配置体系总览）。唯一有「缺省行为」的是模型： 没配模型时命令照常能用，一发对话就会提示没有可用模型。

插件仓库与 Starter 的要求与内核一致
  • 插件仓库：JDK 8（与内核一致，不要用 Java 9+ 的 API 或语法）、Maven 3.2.5 以上，另外要求内核已 mvn install 到本地仓库。
  • Spring Boot Starter：JDK 8、Spring Boot 2.7（已在 2.7.18 上验过）、内核 io.github.zcd0831:jellyfish-di:0.1.1（来自中央仓库）。

从源码构建

构建内核 fat jar（jellyfish-cli-0.1.1.jar）

是什么
把 Jellyfish 内核仓库构建成一个可执行 fat jar。三种模式 （-cli / -tui / -server）都用同一个 jar 启动， 这是内核交付的唯一可执行入口。
怎么用
克隆、构建两步。README 给的原始命令如下（注意 -o 是离线模式）： 
git clone https://github.com/zcd0831/Jellyfish.git && cd Jellyfish
mvn -o clean package              # 全量构建 + 单测；-DskipTests 可跳测
产物路径固定为： 
jellyfish-cli/target/jellyfish-cli-0.1.1.jar
嫌路径长就设个别名： 
alias jellyfish='java -jar /绝对路径/jellyfish-cli/target/jellyfish-cli-0.1.1.jar'

配置

字段类型必填默认值含义示例
-o（Maven 离线开关） 命令行旗标 选填 无（README 的命令行里带上了它） 离线构建：只用本地仓库里已有的依赖，不联网下载。-o 不是硬性要求：README 的安装命令与 IDEA 调试命令带它，而 AGENTS.md「常用命令」那一组一条都不带，仓库里也没有 .mvn/maven.config、mvnw 或 CI 配置把离线定为默认。首次构建建议先去 -o：本机 ~/.m2 还没攒齐依赖时，离线会直接报「找不到依赖」 mvn clean package（去掉 -o）
-DskipTests 命令行旗标 选填 不跳过（默认跑单测） 跳过单测只打包，构建更快。README 明确把它标为「可跳测」 mvn -q package -DskipTests
-q 命令行旗标 选填 不静默（输出完整日志） 只输出警告与错误；README 的「常用构建命令」一组都带它 mvn -q compile

完整示例

# 1. 克隆并进入内核仓库
git clone https://github.com/zcd0831/Jellyfish.git && cd Jellyfish

# 2. 构建（第一次可以先跳过单测，更快）
mvn -o package -DskipTests

# 3. 确认产物就位
ls jellyfish-cli/target/jellyfish-cli-0.1.1.jar

# 4. 设个别名，后面就不用敲长路径
alias jellyfish='java -jar /path/to/Jellyfish/jellyfish-cli/target/jellyfish-cli-0.1.1.jar'

# 5. 用不需要模型的方式验证它能启动
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "/help"

常见问题

  • 构建报「找不到依赖」？README 给的命令带 -o（离线），依赖必须已在本机 ~/.m2 里；先去掉 -o 跑一次联网构建。文档之间的差别也在这里：AGENTS.md 的「常用命令」全都不带 -o，可见它不是必须的。
  • 构建成功后 jar 在哪？只在 jellyfish-cli/target/ 下，文件名带版本号 0.1.1——它同时也是启动时的版本号来源。
  • mvn package 与 mvn test 有什么区别？package 会顺带跑单测（除非 -DskipTests）；但两者都不跑 *IT 端到端，Server 端到端要单独用 -Pserver-it。
  • 改了代码要重新装到本地仓库吗？只有插件仓库或 Starter 需要你这么做，见下文「插件仓库是独立的 reactor」。
工作目录里已经有一份 jar？先确认它是不是你要的

当前工作目录（三个仓库的聚合目录）下存在一个 jellyfish-cli-0.1.1.jar（16,400,210 字节，约 16.4 MB）。 能核实的两点：它的文件名与版本号跟本仓库的打包配置一致（产物名由 jellyfish-cli/pom.xml 的 shade 配置决定），而且它不是 GitHub Releases 的资产（那边只有 v0.1.0 的 jellyfish-cli-0.1.0.jar）； 但它由谁、在什么状态下构建并拷进来，三个仓库的文档里没有任何记载，【需核实】。 核实方法：自己跑一次 mvn -q package -DskipTests，再比对 shasum -a 256 jellyfish-cli-0.1.1.jar 与 shasum -a 256 jellyfish-cli/target/jellyfish-cli-0.1.1.jar（两者相同才说明它是一次可复现构建的产物）；unzip -p jellyfish-cli-0.1.1.jar META-INF/MANIFEST.MF 里还有 Implementation-Version。只想要一个能跑的 jar 可以先用它验证；但凡涉及「我改的代码有没有生效」，请按上面的步骤自己从源码构建。

常用构建命令

下面五条来自内核仓库文档，够覆盖日常开发。约定：都带 -q（只输出警告与错误）， 因此「没输出」通常是好事。

命令用途说明
mvn -q compile 只编译 不打包、不跑测试。改一行代码想快速看语法错时用
mvn -q package -DskipTests 只打包 产出 jellyfish-cli/target/jellyfish-cli-0.1.1.jar；跳过单测
mvn -q package 打包 + 全量单测 不带 -DskipTests 时，打包过程会跑单测
mvn -q test 全量单测 JUnit5 + Mockito + JaCoCo；不跑 *IT 端到端
mvn -q -Dtest=ChatStateTest test 单类单测 把类名换成你的目标测试类；循环调一个类时用它
mvn -q -Pserver-it test Server 模式端到端 真 Undertow + 真内核，走本机回环。改 Server 相关代码必须跑它
插件仓库的端到端不在内核仓库里

插件端到端测试（script-it / shell-it / mcp-it）在 Jellyfish-Plugins 仓库里跑，用它们各自的 profile： mvn -q -Pshell-it test、-Pmcp-it、-Pscript-it。 在内核仓库里敲这些 profile 不会跑到插件的用例。

安装官方插件

把插件 jar 放进扫描目录（两种方式）

是什么
插件是独立打包的 PF4J jar，内核在启动期扫描目录并加载它们。 装插件＝把 jar 放进扫描目录＋重启进程。不装插件时内核几乎干不了事 （见 01 Jellyfish 是什么「能力从哪来」）。
怎么用
方式一：全量（脚本）——插件仓库文档里的做法是 mvn -q package -DskipTests 把全部插件打包，然后跑 ./cpPlugins.sh 把 target/*.jar 拷进扫描目录： 
mvn -q package -DskipTests      # 打包全部插件
./cpPlugins.sh                  # 把 target/*.jar 拷进扫描目录（缺省 ~/.jellyfish/plugins/）
方式二：只装用得到的几个——手动 cp 单个 jar： 
mvn -q package -DskipTests
mkdir -p ~/.jellyfish/plugins
cp jellyfish-plugin-tools/target/jellyfish-plugin-tools-*.jar ~/.jellyfish/plugins/
装完重启 jellyfish——扫描目录与插件集合只在启动期确定。

配置

字段类型必填默认值含义示例
plugins.roots string[] 选填 ["~/.jellyfish/plugins/"] 插件扫描目录，写在 config.json 里。顺序即扫描顺序；相对路径相对进程工作目录解析，行首 ~ 展开为用户主目录。PF4J 只在目录下一层找 plugin.properties ["~/.jellyfish/plugins/"]
plugins.enabled string[]（pluginId） 选填 未声明 = 不额外限定（全部加载） 启用名单。「未声明」与「声明为空」是两回事：显式写 [] 表示一个都不启用 ["jellyfish-plugin-tools"]
plugins.disabled string[]（pluginId） 选填 不声明（= []，不禁用任何插件） 禁用名单。同一 pluginId 同时出现在两份名单里时按禁用处理，并发一条配置告警 ["jellyfish-plugin-todo"]

需重启 plugins.roots 与新增 / 删除插件 jar——扫描目录与插件集合只在启动期确定。 /reload 生效 plugins.enabled / plugins.disabled 与 逐插件配置段 plugins.configurations.<pluginId>（后两者写在 jellyfish.json，不在 config.json）。

完整示例

{
  "processName": "Jellyfish",
  "model": {
    "globalPath": "~/.jellyfish/models.json",
    "projectPath": "./.jellyfish/models.json"
  },
  "agent": {

常见问题

  • 装了却看不到插件的命令？先确认 jar 在 plugins.roots 指向的目录里（PF4J 只在目录下一层找 plugin.properties），再确认没被 jellyfish.json 的 plugins.disabled 排掉；新增 jar 必须重启。
  • 改了插件配置段要重启吗？不用，/reload 会只重启配置段变了的插件；但改 config.json、增删 jar 必须重启进程。
  • 插件加载失败会让内核起不来吗？不会——但要在启动日志里找原因；加载失败与内核启动失败是两件事，退出码也不同。
关于工作目录下的 cpPlugins.sh：路径前缀不一样
  • 插件仓库 README 与 AGENTS.md 写的都是 ./cpPlugins.sh（在插件仓库根执行）， 但当前工作目录的 Jellyfish-Plugins/ 里没有这个文件。
  • 工作目录根上的 cpPlugins.sh 每一行都带 Jellyfish-Plugins/ 前缀 （例如 cp Jellyfish-Plugins/jellyfish-plugin-tools/target/jellyfish-plugin-tools-0.1.1.jar ~/.jellyfish/plugins）， 所以它应当在聚合工作目录根执行。
  • 该脚本做的事有两类：拷 13 个官方插件 jar 到 ~/.jellyfish/plugins； 并把 examples/scripts/python/ 下的 web / stock / stockpanel 拷到 ~/.jellyfish/scripts/python/（拷前会先 rm -rf 目标目录）。

插件仓库是独立的 reactor：改插件前先装内核

Jellyfish-Plugins 里的 jellyfish-api 不来自同级目录的内核源码树， 而是本地 Maven 仓库里那一份。所以只要内核改过（尤其是 jellyfish-api 里的契约）， 插件那边就先要拿到新版本： 

(cd ../Jellyfish && mvn -q install -DskipTests)
忘了这一步的表现，以及为什么必须 clean
  • 表现一：「内核明明改了，插件这边编译却看不到」——你编的是旧 jellyfish-api。
  • 表现二（更糟）：编译问题被伪装成运行期问题。增量编译会复用按旧 jellyfish-api 编出的 target/，例如内核给 SessionSnapshot 加字段之后，不带 clean 报的是 11 条 NoSuchMethodError。
  • 做法：内核升级后的检查顺序是 (cd ../Jellyfish && mvn -q install -DskipTests) → mvn -q clean package → 三个 -P*-it 端到端，只有全绿才算真的没问题。
  • Starter 同理：它平时从中央仓库解析 jellyfish-di:0.1.1， 只有你在本地改了内核时才需要先 mvn install；忘了这一步的表现是「内核明明改了，这边编译却看不到」， 或更糟——用到的是本地仓库里的旧快照。
# 内核升级后，插件仓库的完整检查顺序
(cd ../Jellyfish && mvn -q install -DskipTests)   # 0. 不能省
mvn -q clean package                              # 1. 必须 clean
mvn -q -Pshell-it test                            # 2. 三个端到端 profile
mvn -q -Pmcp-it test
mvn -q -Pscript-it test

验证安装：用不需要模型的命令

用 -cli -p "/help" 确认 jar 起得来

是什么
不需要模型配置就能跑命令，用它确认 jar 起得来、装配没坏。 这是安装的验收动作，也是排错时的第一步。
怎么用
java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "/help"
看到命令清单就说明装好了。输入以 / 开头即走命令域，三条外壳命令一致。

配置

这一步没有配置项：它刻意绕开 models.json。唯一相关的约定是 回答与命令结果走 stdout，诊断、工具进度与日志走 stderr，因此重定向是安全的： 

java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "总结这个项目" > answer.txt 2> diag.txt
echo "/help" | java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli

完整示例（离线可用的命令清单）

命令别名离线可用说明
/help [命令]/h、/?是显示命令帮助；装插件后插件命令也会出现在这里
/session/sessions是列出全部会话（有内容可列需要持久化插件）
/status是显示当前会话概要
/model [provider/model]是查看或切换模型（无会话时改 SessionDefaults）

/compact [preview]否把更早的对话压成摘要——需要压缩策略插件（jellyfish-plugin-compact）
/reload内核自带重新加载配置（模型 / agent / 插件）

另有五个命令由 -tui 外壳处理，不在 /help 列表里： /exit、/ui、/thinking、/toolargs、/mouse。 插件会带来更多命令（例如待办插件的 /todo、skills 插件的 /skills、shell 的 /shell）， 装了就出现在 /help 里——这也是「插件到底加载上没有」最省事的判据。

在 IDEA 里调试

用远程调试挂接 -tui

是什么
IDEA 的运行控制台默认不是真终端，直接跑 -tui 会命中「需要可交互终端」的检查并退 3。 官方推荐的做法是：在真实终端里启动进程，用 IDEA 远程调试挂接上去。
怎么用
mvn -o package -DskipTests
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 \
     -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -tui
然后 Run → Edit Configurations → + → Remote JVM Debug（默认就是 5005）→ 点 Debug。

配置

字段类型必填默认值含义示例
-agentlib:jdwp=…address=5005 JVM 启动参数 选填 不开启调试端口 要用远程调试时加它：JDWP 调试端口，IDEA 的 Remote JVM Debug 缺省也是 5005 -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005
suspend 枚举 y / n 选填 n n：立刻启动、等你去挂接；y：等调试器连上才继续——想在内核启动阶段（DI 装配、bootstrap）下断点就改成 y suspend=y
-Djellyfish.tui.skipTerminalCheck 系统属性（boolean） 选填 false（做检查） 跳过「TUI 需要可交互终端」的检查。只在确认终端可用却被拦下时用 -Djellyfish.tui.skipTerminalCheck=true

完整示例

# 1. 打包（跳过单测更快）
mvn -o package -DskipTests

# 2. 在真实终端里启动，并开放 5005 调试端口；想在装配阶段下断点就把 suspend 改成 y
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 \
     -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -tui

# 3. IDEA：Run → Edit Configurations → + → Remote JVM Debug（缺省 5005）→ Debug

# 备选：IDEA 内置的 Terminal 标签页是真 PTY，也可以直接在那里运行

常见问题

  • IDEA 里点 Run 就退 3？控制台不是真终端。用上面的远程调试方案，或改用 IDEA 内置 Terminal 标签页。
  • 断点进不去 bootstrap？把 suspend=n 改成 suspend=y，进程会等你挂上再继续。
  • 确认终端可用却被拦下？加 -Djellyfish.tui.skipTerminalCheck=true。
  • 只想看日志不想断点？不需要调试器：--verbose 把日志级别降到 DEBUG，等价写法是 -Djellyfish.log.level=DEBUG。

安装检查清单

按顺序走一遍，全过就算装好了。第 6、7 项是「可选但推荐」——第 6 项能一次性证明插件确实被加载了。

#检查项怎么做通过标准
1 JDK 8 可用 用 JDK 自带的版本查询命令（java -version / javac -version） 版本为 1.8.x；不要用 Java 9+ 编译本项目
2 Maven 版本够 mvn -v ≥ 3.2.5
3 能编译 mvn -q compile 无报错退出（-q 下「没输出」是正常的）
4 fat jar 产出 构建后看 jellyfish-cli/target/jellyfish-cli-0.1.1.jar 文件存在、文件名版本号是 0.1.1
5 jar 能起、命令域能跑 java -jar jellyfish-cli/target/jellyfish-cli-0.1.1.jar -cli -p "/help" 打印命令清单，退出码 0（这一步不需要模型）
6 插件 jar 就位并被加载 先确认 ~/.jellyfish/plugins/ 里有 jellyfish-plugin-*.jar，重启后再跑一次 -cli -p "/help" 命令清单里出现插件命令（例如 /todo、/skills、/shell）
7 （可选）模型可用 配好 models.json 后跑 -cli -p "你好" 得到一次回答；没配模型时应提示没有可用模型，而不是崩
8 （可选）要用的项目级配置被信任 需要 ./.jellyfish/*.json 生效时，启动加 --trust-project-config 项目级配置生效（该旗标仅本次进程有效、不落盘；缺省不加载项目级配置）

表中第 1、2 项的 java -version / javac -version / mvn -v 是 JDK 与 Maven 自带的版本查询命令，不是本项目的命令，仓库不单独收录它们（判定标准见上表）； 但「该到哪个版本」仓库是写明的：见 Jellyfish/README.md 的「环境要求」表——JDK 8、Maven 3.2.5 以上。其余各条都直接来自内核仓库的安装与验证章节。

关键结论

  1. 四项环境要求里，JDK 8 与 Maven 3.2.5+ 是硬要求；-tui 额外需要可交互终端；模型是唯一可选项（没它也能跑命令）。
  2. 内核唯一交付的可执行入口是 jellyfish-cli/target/jellyfish-cli-0.1.1.jar，三种模式都用它启动；README 给的构建命令带 -o（离线），首次构建若失败先去掉 -o 重试。
  3. 插件安装＝把 jar 放进扫描目录（缺省 ~/.jellyfish/plugins/，由 config.json 的 plugins.roots 决定）＋重启进程；启用 / 禁用名单与逐插件配置段写在 jellyfish.json，改它们 /reload 就够。
  4. Jellyfish-Plugins 是独立 reactor，jellyfish-api 来自本地仓库：改插件前先 (cd ../Jellyfish && mvn -q install -DskipTests)，并且必须 clean，否则编译问题会被伪装成运行期问题。
  5. 验证安装用的是不需要模型的命令：-cli -p "/help" 看到命令清单即成功；/help /session /status /model /compact preview 都属离线可用。
  6. 仓库不提供官方二进制发行包：可核实的获取路径只有源码构建；中央仓库只发内核五个构件与 Starter，插件按 cpPlugins.sh 装。GitHub Releases 是否有附件请在仓库页面自行核实。
  7. 在 IDEA 里调 -tui 用远程调试（-agentlib:jdwp=…,suspend=n,address=5005）；想在 bootstrap 阶段下断点改成 suspend=y。
