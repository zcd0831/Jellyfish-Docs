Jellyfish 使用指南/06 models.json 详解

06 models.json 详解

要配的只有三件事：每个 provider 怎么访问（type / apiKey / baseUrl）、它有哪些模型、按需调参。 这一页按「先抄一份、再逐字段、最后看坑」的顺序展开：所有键名与取值都逐字来自仓库文档， sampling 与 vendorBody 的边界、四家厂商的思考强度写法、 prompt cache 要花的那笔钱，都会讲清楚。

学习目标

  • 照着抄一份能跑的 models.json，并说清每一段在管什么；
  • 记住 providers.<name> 的八个字段与 models[] 的七个字段，知道哪些只有 provider 级、哪些只有模型级；
  • 选对 type（含 google / anthropic 两个别名），并知道写错时会得到什么报错；
  • 避开 maxTokensField 的 400 陷阱，知道 OpenAI 的推理模型与 gpt-5 之后只认 max_completion_tokens；
  • 把 sampling 的七项参数对应到 OpenAI 系 / Claude / Gemini 的协议字段，并接受「不认这项就不下发」；
  • 用 vendorBody 配思考强度、vendorHeaders 配自定义请求头，并知道哪些键会被丢弃；
  • 按需要开 prompt cache（promptCacheKey / keepAliveSeconds），并知道保活是要花钱的。

先看一份完整的 models.json

下面这份就是 README 里的示例，逐段加了注释说明它在管什么。 注释里的 // 在 JSON 里是非法的，抄的时候请删掉——本页「多厂商完整配置示例」 一节另给了一份可直接复制的干净版本。想先跑起来、不想读长文档的，直接看下面那个 callout 里的最小版本。 

{
  // 全局默认：/model 不带参数时用它；agent 也可以用 model 字段覆盖
  "defaultProvider": "openai",
  "defaultModel": "gpt-4o",

  "providers": {
    // 这里的 key（openai）是自取的名字，也就是 /model 里 provider/model 的前半段
    "openai": {
      "type": "openai",                        // 用哪套传输实现：openai / claude / deepseek / gemini / minimax（含别名）
      "apiKey": "${OPENAI_API_KEY}",           // 密钥一律走环境变量，不要写进这个文件

      // provider 级：缓存治理两项，缺省都是关的
      "cache": {
        "promptCacheKey": false,               // true = 把会话标识作为缓存路由键下发给厂商
        "keepAliveSeconds": 0                  // >0 = 空闲时每隔这么久续一次缓存 TTL（要花钱）
      },

      // provider 级：采样参数基线，给这家所有模型用
      "sampling": { "temperature": 0.2, "topP": 0.95, "stop": ["</done>"] },

      // provider 级：内核不解释、原样透传进请求体的厂商私有字段
      "vendorBody": { "service_tier": "flex" },

      // provider 级：原样加进出站请求的自定义请求头（模型级没有这个字段）
      "vendorHeaders": { "x-tenant": "team-a" },

      "models": [{
        "id": "gpt-5",                         // 模型标识：/model 里后半段，也是发给厂商的模型名
        "name": "gpt-5",                       // 展示名，缺省与 id 相同
        "contextLength": 400000,               // 上下文窗口（token），内核用它算压缩预算
        "maxOutputTokens": 8192,               // 单次最大输出 token，内核按次下发
        "maxTokensField": "max_completion_tokens",  // 输出上限写进哪个请求体字段名；只有模型级有它
        "sampling": { "temperature": 1 },       // 模型级覆盖：只改这一项，其余沿用 provider 级
        "vendorBody": { "reasoning_effort": "low" }  // 模型级直通，与 provider 级深合并
      }]
    }
  }
}

  "defaultProvider": "openai",
  "defaultModel": "gpt-4o",
  "providers": {

      "models": [{

      }]
    }
  }
}

providers.<name> 的八个字段

<name> 是自取的名字，也是 /model 里 provider/model 的前半段。 同一个 name 在项目级出现时会整对象覆盖全局级（见 05）。

字段类型必填默认值含义示例
type string 必填 无（留空会报 provider type must not be blank） 用哪套传输实现，取值见下一节；写错会报错并列出内核认识的类型 "openai"
apiKey string 选填 未配置（空） 访问密钥。建议写 ${ENV_VAR} 由环境变量注入，不要把密钥写进配置文件 "${OPENAI_API_KEY}"
baseUrl string 选填 该 type 的官方地址（https://api.openai.com / https://api.deepseek.com / https://api.anthropic.com / https://generativelanguage.googleapis.com / https://api.minimax.io） 服务地址。必须填最终地址：客户端不跟随重定向 "https://gateway.example.com/v1/chat/completions"
models array 选填 空列表 该 provider 下的模型清单，字段见下一节；被插件接管时会整体替换 [{ "id": "gpt-4o", … }]
cache object 选填 promptCacheKey=false、keepAliveSeconds=0 缓存治理两项，只影响命中率（详见本节后的 cache 专节） { "promptCacheKey": true, "keepAliveSeconds": 240 }
sampling object 选填 七项都不表态（不下发） 采样参数基线；模型级逐字段覆盖它 { "temperature": 0.2, "topP": 0.95 }
vendorBody object 选填 空映射 原样透传进请求体的厂商私有字段；内核只搬运、不解释、不校验 { "service_tier": "flex" }
vendorHeaders object 选填 空映射 原样加进出站请求的自定义请求头；只有 provider 级，同名时覆盖内核的头 { "x-tenant": "team-a" }

三个字段的边界值得单独记一遍：type 决定「用哪套传输」；sampling 是内核定义的封闭字段集， 带校验、带「未表态」语义；vendorBody / vendorHeaders 是厂商定义的自由字段， 内核不解释。名字上先分开，是为了「配了不生效」时你至少知道该怀疑哪一边。

baseUrl 要填最终地址：出站请求不跟随重定向

Claude 的密钥走 x-api-key、Gemini 走 x-goog-api-key，而 OkHttp 在跨主机重定向时 只剥 Authorization——跟随重定向就等于允许上游把一个我们的密钥头送到任意主机去。 因此上游真回 301/302 时请求会失败，错误信息里写明「重定向被禁止」以及目标主机与路径 （只给主机与路径，不复制 Location 的 query，那里可能挂着一次性凭据）。

type 的合法取值

取值别名接到哪个客户端该 type 的缺省 baseUrl说明
openai — OpenAiLlmClient https://api.openai.com OpenAI 及一切 OpenAI 兼容端点（走 /v1/chat/completions 那一套）
claude anthropic ClaudeLlmClient https://api.anthropic.com Anthropic Messages 格式；密钥走 x-api-key
deepseek — DeepSeekLlmClient https://api.deepseek.com DeepSeek 官方端点（OpenAI 兼容格式）
gemini google GeminiLlmClient https://generativelanguage.googleapis.com Google Gemini；密钥走 x-goog-api-key
minimax — MiniMaxLlmClient https://api.minimax.io MiniMax 官方端点（OpenAI 兼容格式）

别名是独立注册的类型：google 与 gemini 接到同一个客户端， anthropic 与 claude 同理。匹配时忽略大小写与首尾空白， 因此 "type": "OpenAI " 也能命中。

type 写错：报错会列出内核认识的类型

报错长这样（把已注册的类型一并列出来，让你能直接把配置改成能跑的那个）：

unsupported provider type: <你写的值> (provider=<provider 名>); builtin types: [openai, deepseek, minimax, gemini, google, claude, anthropic]. 装一个提供该类型的插件，或把它改成上面已支持的类型

报错发生在创建客户端时，而不是加载配置时——也就是「真正用到这个 provider」的那一刻。

type 也可以由插件提供，但内核自带的挤不掉

自建网关、私有协议、本地 llama.cpp 这类场景，可以让插件注册一个新 type，配置里写一个指向它的 provider 即可（见 13 插件进阶与发布）。两条硬规则：

  • 内核自带的 type 不能被插件顶替。这不是优先级问题：传输请求里带的是已解析好的 apiKey，能顶替 openai 的插件等于把所有用户的密钥转发到自己的服务器上。 重复注册只记 WARN 并忽略，插件卸载也不会把内核类型一起带走。
  • models 可以由插件动态发现。被插件接管的 provider 会被问一次 「现在有哪些模型」，非空时整体替换这里写的 models； 发现结果不落盘——models.json 始终是模型的唯一持久事实，删掉插件后配置里那份依旧有效。

目录发现只换规格：插件报回的目录按 id 覆盖 contextLength / maxOutputTokens，而用户写的 sampling / vendorBody / maxTokensField 按 id 带过来——否则一次元数据刷新会悄悄清掉配置里还写着的参数。

models[] 的七个字段

字段类型必填默认值含义示例
id string 必填 无 模型标识：/model 里 provider/model 的后半段，也是发给厂商的模型名 "gpt-4o"
name string 选填 与 id 相同 展示名 "GPT-4o"
contextLength int 选填 0（＝未配置，此时内核不做上下文裁剪） 上下文窗口（token），内核用它算压缩预算 128000
maxOutputTokens int 选填 未配置（OpenAI 系兼容端点不下发该字段；Claude 未配时内核发的是 4096） 单次最大输出 token，内核按次下发 8192
maxTokensField string 选填 max_tokens 承载输出上限的请求体字段名：max_tokens 或 max_completion_tokens；写别的值会在加载时告警并回退 "max_completion_tokens"
sampling object 选填 七项都不表态（沿用 provider 级） 在这个模型上覆盖 provider 的采样基线（逐字段覆盖，没写的沿用 provider 级） { "temperature": 1 }
vendorBody object 选填 空映射 在这个模型上覆盖 provider 的直通字段（深合并，model 级优先） { "reasoning_effort": "low" }

maxTokensField：只有模型级，写错就是一次 400

输出上限的字段名由配置决定

是什么
maxOutputTokens 由内核下发，但承载它的请求体字段名各家不同、同一家不同代际也不同。 maxTokensField 就是回答「写进哪个字段」的那一项。内核不按模型名猜—— 「哪个模型认哪个字段」是厂商知识，交给配置显式声明。
怎么用
按模型填：推理模型（OpenAI o 系）与 gpt-5 及之后填 "max_completion_tokens"； DeepSeek / MiniMax / OpenRouter 这类兼容端点用缺省的 "max_tokens"（可以不写这一项）。 
{
  "models": [{
    "id": "gpt-5", "name": "gpt-5", "contextLength": 400000, "maxOutputTokens": 8192,
    "maxTokensField": "max_completion_tokens"
  }]
}

配置

字段类型必填默认值含义示例
maxTokensField string 选填 max_tokens 只认两个取值：max_tokens（缺省）、max_completion_tokens；其他值在加载时告警并回退缺省 "max_completion_tokens"

/reload 生效 它是模型级字段：同一个端点下 gpt-4o 与 gpt-5 认的字段名不一样， 端点级给不出一个成立的缺省。另外它只对 OpenAI 兼容客户端有意义——Claude 的 Messages API 固定叫 max_tokens（且必填），Gemini 的生成参数固定住在 generationConfig.maxOutputTokens， 两者都不看这个字段。

常见问题

  • 报 Unsupported parameter 400？给推理模型 / gpt-5 之后填了 max_tokens。改填 max_completion_tokens。
  • 反过来会怎样？给只认 max_tokens 的兼容端点填 max_completion_tokens，同样是 400（或该字段被忽略）。
  • 写了个不认识的值？加载时告警并回退到 max_tokens，不阻断启动。
  • 为什么不留成 provider 级？同一端点下不同模型答案不同，provider 级没有成立的缺省值。

sampling：内核定义的七项参数

收录标准只有一条：多家厂商有「同名同义」的对应物。内核只声明意图， 由各客户端翻成自家协议字段，不认这一项的客户端不下发它（且不报错）。

字段类型必填默认值含义（校验）示例
temperature number 选填 未表态（不下发） 采样温度；非负且有限才下发。上限各家不同（OpenAI 系 0–2、Anthropic 0–1），内核只校验它确定的那部分 0.2
topP number 选填 未表态（不下发） 核采样概率；要求落在 (0, 1] 0.95
topK int 选填 未表态（不下发） Top-K 采样；要求正整数（0 与负数被丢弃） 40
seed int 选填 未表态（不下发） 随机种子，任意整数；厂商只说「尽力而为」，不保证可复现 42
frequencyPenalty number 选填 未表态（不下发） 频率惩罚；要求落在 [-2, 2] 0.3
presencePenalty number 选填 未表态（不下发） 存在惩罚；要求落在 [-2, 2] 0.3
stop string[] 选填 空列表（不下发） 停止序列；丢弃空白项，有效条目原样保留（空格 / 换行可能就是它的一部分） ["</done>"]

内核声明的意图，各客户端翻成什么（「—」＝该家没有这个字段，配了也不会下发，不报错）：

字段校验OpenAI 系ClaudeGemini
temperature非负且有限temperaturetemperaturegenerationConfig.temperature
topP(0, 1]top_ptop_pgenerationConfig.topP
topK正整数—top_kgenerationConfig.topK
seed任意整数seed—generationConfig.seed
frequencyPenalty[-2, 2]frequency_penalty—generationConfig.frequencyPenalty
presencePenalty[-2, 2]presence_penalty—generationConfig.presencePenalty
stop丢弃空白项stopstop_sequencesgenerationConfig.stopSequences
两条口径必须记住
  • 没写的字段不下发：厂商自己的缺省才是缺省——内核不替厂商猜缺省值（猜错就是一次 400）。
  • 非法值丢弃并告警，不阻断启动：例如 "temperature": -1 会被丢掉并记一条告警（SamplingSettings.warnings()，同时进 ConfigWarningEvent）。
为什么推理控制不在 sampling 里

DeepSeek 是 thinking.type 加 reasoning_effort、OpenAI 只有 reasoning_effort、Anthropic 换成了 thinking.type: adaptive 加 output_config.effort、Gemini 是 thinkingConfig.thinkingLevel—— 四家四种形状、四种取值，内核认了就等于替厂商背书一个不成立的抽象。这些走下一节的 vendorBody。

另外两类也被排除：n / candidateCount（与内核「一个候选对应一条 assistant 消息」 的逻辑冲突，且被列为保留键）；response_format / service_tier / logit_bias / logprobs（单家能力）。

合并规则：sampling 在 provider 级给基线、模型级逐字段覆盖； null（没写）的含义是「沿用」而不是「清空」——代价是模型级无法单独关掉 provider 级已配的某项， 要关掉就把那一项从 provider 级拿下来。

vendorBody 与 vendorHeaders：直通字段

厂商私有字段直通

是什么
这两段里的键由厂商定义，内核只搬运、不解释、不校验： reasoning_effort、thinking、service_tier、 generationConfig.* 这些各家专有的东西都从这儿走。 代价是明说过的——键名逐字抄厂商文档、大小写敏感，拼错就是静默无效（厂商多半忽略不认识的字段）。
怎么用
vendorBody 往请求体里加字段（provider 级与模型级都可写）； vendorHeaders 往出站请求加头（只有 provider 级）。排查办法： vendorBody 生效时会在 DEBUG 日志里打一行实际下发的键名（不打值）。 
java -jar /path/to/jellyfish-cli-0.1.2.jar -cli --verbose -p "你好"

配置

字段类型必填默认值含义示例
provider.vendorBody object 选填 空映射 provider 级直通请求体字段；解析配置时就已清洗（保留键 / 超深子树 / 非法值丢弃并 WARN） { "service_tier": "flex" }
model.vendorBody object 选填 空映射 模型级直通字段，与 provider 级深合并（对象递归、数组与标量整体替换，model 级优先） { "reasoning_effort": "low" }
provider.vendorHeaders object 选填 空映射 出站请求头；同名时覆盖内核的头（写 anthropic-version 就能试新版本） { "x-tenant": "team-a" }

/reload 生效 两段都随 models.json 一起热更新。

完整示例：provider 级放公共字段，模型级只写这一个模型要多加的东西

{
  "providers": {
    "gemini": {
      "type": "gemini",
      "apiKey": "${GEMINI_API_KEY}",
      "baseUrl": "${GEMINI_BASE_URL:-https://generativelanguage.googleapis.com}",
      "vendorHeaders": { "x-tenant": "team-a" },
      "models": [{
        "id": "gemini-1.5-pro",
        "name": "gemini-1.5-pro",

常见问题

  • 配了没反应？键名拼错（静默无效），或这个模型不认这个键。先把日志级别调低，看它实际下发了哪些键名。
  • 为什么不能拿它改 temperature？采样类键已有正式入口（sampling），写在 vendorBody 里会被丢弃并告警——同一参数两个入口，迟早起冲突。
  • 模型级能写请求头吗？不能。请求头是端点属性，同一 provider 下所有模型共享同一套地址与网关规则，因此 vendorHeaders 只有 provider 级。

会被丢弃的键（保留键表）

它们要么决定请求形状，要么已经有正式入口。保留键在任意嵌套深度都挡—— Gemini 的生成参数在 generationConfig 里，只看顶层等于给同一个参数留了后门。

类别键为什么挡住
请求形状与缓存前缀 model messages contents system systemInstruction tools toolConfig tool_choice stream stream_options prompt_cache_key prompt_cache_retention 覆盖 messages 等于换一份对话发出去
候选数 n candidateCount 内核只解析第一个候选，配了只会让计费翻倍
采样类 temperature top_p topP top_k topK seed frequency_penalty frequencyPenalty presence_penalty presencePenalty stop stop_sequences stopSequences max_tokens max_completion_tokens maxOutputTokens 已有正式入口（sampling / maxOutputTokens / maxTokensField），两个入口迟早起冲突
Anthropic 缓存断点 cache_control 内核按断点数与 TTL 在 system / messages / tools 块上标注，用户再标一份会与块级 TTL 冲突（Anthropic 对不一致的 TTL 直接 400）
过深嵌套 —（超过 8 层） 整棵子树丢弃。真需要嵌套的字段只有两三层，写超了多半是配错了层级

vendorHeaders 另有六个头会被丢弃

Content-Type、Accept、Host、Content-Length、 Accept-Encoding、Range——这六个由内核 / HTTP 客户端按协议语义生成， 用户覆盖它只会弄坏请求（其中 Accept-Encoding 与 Range 尤其隐蔽： 一旦自带，传输层就不再走透明解压那条路径，响应体会以压缩字节送进 JSON 解析）。 反过来，鉴权类头部是放行的：网关要求的自定义鉴权头正是这条路的正经用途，而密钥本来就是用户自己的。

头名按 HTTP 语义大小写不敏感地判重与判保留（Content-Type 与 content-type 是同一个头），下发时保留你写的原始形式。头名须为 HTTP token、 头值只允许可见 ASCII 与制表符；不合规的条目丢弃且日志只记头名—— 头值可能就是密钥。

思考强度怎么配

思考强度（reasoning effort）

是什么
控制模型「想多久」的那一组参数。内核没有 thinkLevel / reasoningEffort 这类字段——四家的形状与取值全不通约，不符合 sampling 的收录标准， 因此统一从 vendorBody 走。
怎么用
键名与取值逐字抄厂商文档（大小写敏感），写进 vendorBody； 想确认真的发出去了，就打开 DEBUG 日志看它下发的键名。

cache：让缓存更可能是热的

prompt cache 的两项旋钮

是什么
让厂商侧的前缀缓存更容易命中的两个开关。它们挂在 provider 上而不是全局—— 两条都与具体厂商的缓存实现绑死（TTL 是 5 分钟还是几小时、是否支持显式缓存路由键，各家都不一样）。
怎么用
想要「同一会话的请求尽量落到同一台机器上」就打开 promptCacheKey； 想「空闲时把缓存 TTL 续上」就设 keepAliveSeconds——但先读完它的代价。 
{
  "providers": {
    "openai": {
      "type": "openai",
      "apiKey": "${OPENAI_API_KEY}",
      "cache": { "promptCacheKey": true, "keepAliveSeconds": 240 }
    }
  }
}

配置

字段类型必填默认值含义示例
cache.promptCacheKey boolean 选填 false 把会话标识作为缓存路由键下发给厂商，让同一会话的请求尽量落到同一台机器上。 目前明确支持的是 OpenAI 系（prompt_cache_key 字段）；缺省关闭，因为老模型 / 老端点收到不认识的字段可能直接报错 true
cache.keepAliveSeconds int 选填 0（关闭） 空闲时每隔这么久重发一次「复用同一前缀」的最小请求，把缓存 TTL 续上。 它是要花钱的；每个空闲期最多续 3 次；上限 1 小时（3600 秒）， 再长就没有续 TTL 的意义了 240

/reload 生效 两项都随 models.json 热更新；非法值（负数、超过上限）回退到缺省值， 不阻断启动。

常见问题

  • 为什么最多只续 3 次？一次保活命中按约 0.1× 计费，而它要防的是一次未命中（约 1×）：续 3 次的总代价约 0.3× 前缀，只要它能换掉一次未命中就是净赚；再往上续则开始有亏的风险，而那时用户多半已经离开。
  • 保活失败会怎样？只记 DEBUG 日志。症状是「配了保活但命中率没改善」——怀疑时先关掉它。
  • Anthropic 需要额外做什么吗？不需要用户做——你不标 cache_control 它一个字节都不缓存，而内核默认替它标两个断点（插件可用 RequestTuningRequest 接管）。这也是 cache_control 被列为保留键的原因。

七个坑

  1. 表里没有的字段 = 不支持。 不报错、也不生效（未知键是静默忽略的）。vendorBody 同理——键名拼错就是静默无效， 排查靠把日志级别调低，看它实际下发了哪些键名（不打值，值可能含凭据）。
  2. 采样参数与思考模式互相挑食。 DeepSeek 思考模式下 temperature 与两个惩罚项完全无效（不报错），而 top_p 反过来 只在思考模式下生效、且被夹到 0.95–1.0；OpenAI 旧 GPT-5 系对非缺省温度直接 400， gpt-5.1 之后只在 reasoning_effort 为 none 时才接受。「温度没反应」先查这一条。
  3. Claude 的两处代际差异。 新代际不再接受 temperature / top_p / top_k（设非缺省值 400）， 这类参数要按 model 级 sampling 分开配；老代际用 thinking.budget_tokens 时 它必须小于当次下发的 max_tokens（未配 maxOutputTokens 时内核发的是 4096），而报错只提 max_tokens，不会提 maxOutputTokens。
  4. keepAliveSeconds 是要花钱的，还会踩两个坑。 保活请求按「最省输出」只发极小输出（Claude 发 max_tokens: 0），因此与 Claude 的 thinking.budget_tokens 互斥（会被 400 拒）；部分新模型对输出上限有最小值要求（如 GPT-5 是 16）。 保活失败只记 DEBUG 日志，症状是「配了保活但命中率没改善」——怀疑时先关掉它。 另外 Anthropic 不标 cache_control 就一个字节都不缓存，内核默认替它标两个断点。
  5. 想看见思考文本要两边都开。 厂商侧（Claude 要 display: "summarized"、Gemini 要 includeThoughts: true） 加外壳侧（-cli 的 --show-thinking 打到 stderr，或 TUI 的 Ctrl+T / /thinking）。
  6. sampling 里「没写」与「写了 0」是两回事。 没写就不下发（厂商自己的缺省才是缺省），写了 0 就发 0。 温度上限各家不同（OpenAI 系 0–2、Anthropic 0–1），内核只校验它确定的那部分，越界由厂商拒。
  7. 密钥一律走环境变量。 "apiKey": "${DEEPSEEK_API_KEY}"。注意 ${VAR} 缺失会让整份配置加载失败， 想容错就写 ${VAR:-默认值}（详见 05 配置体系总览 的插值一节）。

怎么切换模型

/model 支持查看或切换，参数就是 provider/model（也就是配置里 providers 的 key 与 models[].id 拼起来）。/model 不需要模型配置， 离线也能用来看当前值。 

# 看当前用的是哪个
java -jar /path/to/jellyfish-cli-0.1.2.jar -cli -p "/model"

# 切到 gpt-5（配置文件里已配好 openai 这个 provider）
java -jar /path/to/jellyfish-cli-0.1.2.jar -cli -p "/model openai/gpt-5"

# 切到 DeepSeek 的推理模型
java -jar /path/to/jellyfish-cli-0.1.2.jar -cli -p "/model deepseek/deepseek-reasoner"

# 交互界面里同样直接敲
# /model claude/claude-3-5-sonnet

另外两条相关入口：启动参数 --model <provider/模型> 在新建会话时指定模型， 而且必须含 /（只归 -cli，见 04 三种运行模式）； agent 的 model 字段可以给某个 agent 指定偏好模型（见 07 agents.json 与工具权限）。 模型解析是三级回落：会话显式 → agent.model → 全局默认。

常见问题

  • 改了 models.json 不生效？ 内容类配置要敲 /reload；只有 config.json、插件 jar 增删、项目级配置的信任需要重启。 另外先确认改的是哪一份——项目级同名 provider 会整对象覆盖全局级（见 05 页的双源一节）。
  • 报「没有可用模型」？ 先确认 defaultProvider / defaultModel 指向的 provider 与模型 id 确实在文件里； 再确认项目级配置到底有没有被加载（未被信任时只发一条告警）。命令本身不需要模型，可以先 /model 看当前值。
  • 加了模型但 /model 里看不到？ id 必须是 models[] 里真实存在的那一项；被插件接管的 provider， 它报回的目录会整体替换你写的那份。
  • 请求 400 / Unsupported parameter？ 按顺序查三件事：maxTokensField 是否与模型代际匹配（推理模型与 gpt-5 之后只认 max_completion_tokens）、温度类参数是否被该模型拒收（Claude 新代际）、 vendorBody 是否写进了该端点不认的键。
  • 配了 temperature 没变化？ 先看是不是思考模式吃掉了它（坑 2）；再确认它没被写进 vendorBody（那是保留键，会被丢弃并告警）； 最后确认值本身合法（非法值丢弃并告警，日志与事件面都有一条）。
  • 能不能把同一份 provider 配两次（比如同厂商两个网关）？ 可以——providers 的 key 是自取的名字，写两个条目分别指向不同 baseUrl 即可， /model 里用不同的前半段区分。
  • minimax 用哪种格式？ 走 OpenAI 兼容的 Chat Completions 格式（与 openai / deepseek 同一条路）， 因此思考强度也按 Chat Completions 那一列的键名写。

关键结论

  1. models.json 只需回答三件事：provider 怎么访问（type / apiKey / baseUrl）、有哪些模型（models[]）、按需调参（sampling / vendorBody / cache）。
  2. type 的合法取值是 openai / claude / deepseek / gemini / minimax 加两个别名 anthropic / google；写错时报错会列出内核认识的类型，插件可以新增类型但顶不掉内核自带的。
  3. maxTokensField 只有模型级，且只对 OpenAI 兼容客户端有意义：推理模型与 gpt-5 之后只认 max_completion_tokens，DeepSeek / MiniMax / OpenRouter 这类只认 max_tokens——用错就是 400。
  4. sampling 是内核定义的七项封闭字段集，没写就不下发、不认就不下发、非法值丢弃并告警，一切由客户端翻成自家协议字段；推理控制不在其中。
  5. vendorBody / vendorHeaders 是「厂商定义、内核不解释」的直通段：键名拼错静默无效，排查靠 DEBUG 日志里的键名；保留键、超深子树、六个 HTTP 头会被丢弃并告警。
  6. 思考强度从 vendorBody 配，四家键名与取值全不同，而且同一家还会随协议变（DeepSeek 三协议对照表）。
  7. cache 的两项都缺省关闭：promptCacheKey 下发会话级缓存路由键，keepAliveSeconds 会真的产生费用（每个空闲期最多续 3 次）。

  • 想知道这些参数怎么影响花费与上下文：读 09 会话与上下文，contextLength 与压缩预算、工具结果落盘都在那里。
  • 手上有自建网关或私有协议：读 13 插件进阶与发布，看插件如何注册一个新的 provider type。
