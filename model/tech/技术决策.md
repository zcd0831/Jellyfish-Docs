## 使用规则

1. **一条决策一节**，编号固定（D01、D02…），不删不改；被推翻时在该节标注 `状态: 被 Dxx 取代`。
2. 每节只写四段：**背景**（一句）、**选项**（2–3 个）、**结论**、**影响面**（会影响哪些文档/代码）。
3. 状态只有三种：`待定` / `已定` / `被取代`。
4. 代码是事实，文档是解释：实现与本文冲突时，只有两个合法动作——改代码，或改本文并注明原因。

## D01 与现有 `Jellyfish` 内核的关系

**状态**：已定

**背景**：现有 `Jellyfish` 仓库已实现 Agent Loop、工具系统、权限审批、会话持久化、子代理、TUI/CLI/Server 三外壳与插件 SPI。本次领域模型是一次重新设计，需要先确定与旧实现的关系。

**选项**
- **A. 重构替代（绞杀者模式）**：在 `Jellyfish` 仓库内按新分层重建，新实现逐步包住并替换旧 Agent Loop，插件 SPI 与工具生态保留。
- **B. 并行新实现**：新建仓库/模块独立实现，与旧内核并存。
- **C. 仅作参考**：不落代码，模型只用于指导后续人工重构。

**结论**：**A 的变体——同仓库、全量重建（不破不立）**。
在 `Jellyfish` 仓库内按新分层从零实现；旧内核代码与旧插件**全部删除、不复用**，不做绞杀式渐进替换。
恢复手段只有一条：**git 历史 + 清空前的发布 tag**。

**影响面**：D02（仓库与模块）、D04（DI 选型不再受旧实现约束）、D05（TUI 事件循环是否重写）、D11（错误体系不受旧代码兼容约束）、测试与发布流程、`Jellyfish-Plugins` 仓库走向。

### D01.1 清理边界（"全量"落到目录级）

**状态**：已定

**背景**："全量清理"必须先划清六类东西，否则容易误伤工具链或留下不可回退的空白。

| # | 类别 | 可选项 | 说明 |
|---|---|---|---|
| ① | 内核源码（Agent Loop / 工具 / 会话 / 子代理 / 装配） | 全删 | 已定：全删 |
| ② | 外壳（TUI / CLI / Server 渲染层、键位、命令解析） | 全删 / 保留 / 只保留命令行骨架 | 代码量最大的一块；模型要求"外壳只调用 6 个用例"，耦合很薄，但渲染细节与用例无关 |
| ③ | 构建与发布（`pom.xml`、CI、打包、发行脚本） | 保留骨架 / 重写 | 与领域设计无关；建议保留骨架，避免重建发布链路 |
| ④ | 第三方依赖（Spring、JLine、Jackson、日志…） | 借机重选（见 D04） | 库不是"旧代码"，但版本与用法可以更新 |
| ⑤ | 插件仓库 `Jellyfish-Plugins` 与插件 SPI | 清空 / 归档 tag 后清空 / 仅停止维护 | 影响已发布插件的用户；删除后需版本跳变与发布说明 |
| ⑥ | 数据目录格式（`~/.jellyfish` 旧结构） | 不兼容 / 提供一次性迁移 | 旧会话数据是否还要能读 |

**结论**：

| # | 类别 | 结论 |
|---|---|---|
| ① | 内核源码 | **全删** |
| ② | 外壳（TUI / CLI / Server） | **全删、重写**。理由：现有外壳与内核耦合严重（Run 语义、旧会话状态机、权限提示、`ask` 交互），保留会制约内核重构 |
| ③ | 构建与发布 | **保留骨架、内容重写**：保留 Maven 聚合结构与发布流程外形，`pom.xml` / CI 配置按新模块重写（不手写一套新的发布链路） |
| ④ | 第三方依赖 | 随 D04 重新选型；不复用旧版本的用法约定 |
| ⑤ | 插件仓库与 SPI | **归档 tag 后清空**：`Jellyfish-Plugins` 打 `v0.x-final` tag、清空内容、停止维护；插件 SPI 与新内核一起重新设计；已发布插件不提供兼容层 |
| ⑥ | 旧数据目录 | **不兼容、不迁移**。启动检测到旧格式时给出明确提示（备份后删除或指定新目录），不做自动转换 |

**执行纪律（避免把"破"变成"事故"）**

1. 清空前在 `Jellyfish` 与 `Jellyfish-Plugins` 各打一个最终 tag（如 `v0.1.2-final`），**保留 git 历史，不做 history rewrite**；
2. 删除用一次 `git rm -r` 提交完成，保证可整体 revert；
3. 版本号跳变（大版本或 `0.x → 1.0.0-alpha`），发布说明里写清"不兼容、插件失效、旧数据需备份"；
4. 新代码合入前，CI 只保留"能编译 + 能跑单测"的最小校验，避免旧流水线挡住重建。

**影响面**：工作量（外壳占比重写）、D02/D04/D05、发布节奏、老用户升级路径。

## D02 代码仓库与模块划分

**状态**：已定

**背景**：决定代码落在哪个仓库、单模块还是多模块。

**选项**
- A. 落在 `Jellyfish` 仓库，单模块（新增包，不分模块）
- B. 落在 `Jellyfish` 仓库，多模块（`domain` / `application` / `infrastructure` / `shell`）
- C. 新建仓库（如 `Jellyfish-Agent`），多模块

**结论**：**B —— 多模块，依赖即规则**。

```
jellyfish-domain          ← 纯 JDK，无内部依赖
jellyfish-application     → domain            （用例、应用组件、端口定义）
jellyfish-infrastructure  → application        （实现端口）
jellyfish-shell           → application        （TUI；本期不含 CLI/Server，见 D12.1）
jellyfish-di              → application, infrastructure, shell   （Dagger 组件与 Provider，见 D04）
jellyfish-boot            → di                 （读配置、创建组件、main）
```

`jellyfish-di` 是**纯装配层**：它认识所有模块，但**没有任何模块依赖它**（只有 `boot` 依赖），因此它无法把容器概念反向渗透进业务代码。

好处：领域模型文档里的三条纪律变成**编译错误**——领域层不可能 import 文件/网络；外壳不可能绕过用例摸仓储；基础设施只能通过端口反向暴露能力。

代价：6 个 `pom.xml`、跨模块改签名要动两处、IDE 索引稍慢（本项目规模可接受）。

**影响面**：D03 包结构、构建脚本、发布产物（单 jar vs 多 jar 的打包方式）。

## D03 包结构：认知模块 × 分层

**状态**：已定

**背景**：模型有两个正交维度——认知模块（感知 / 行动 / 规划 / 记忆）与分层（domain / application / infrastructure）。包要按其中一个切，或交叉切。

**结论**：**分层由模块承担（D02），认知模块由包承担**。包名前缀 `io.github.zcd0831.jellyfish.*`。

### 三条切分原则

1. **domain / application 按认知模块切**；**infrastructure 按技术手段切**（刻意不对称：`FileCommitScope` 同时服务四个认知模块，按领域切会把它劈成四份）。
2. **只有 domain 内部严格**：聚合之间只能通过 Id 互看；**application 内部允许跨认知模块直接调用**（`ExecutionLoop` 必然要调 `ContextWindowService`）。
3. **一个聚合一个包**，聚合内部实体（`PlanStep` / `Attempt` / `Record`）做**包内可见**，从编译期强制"只能通过聚合根入口"。

### 域层：12 个聚合 = 12 个包

**`shared` 的准入规则**

- **全部 Id 一律进 `shared`**：Id 是无行为、无依赖的类型标签，"跨不跨上下文"会随演进而变，搬来搬去只是噪音；
- **其它值类型**只有被 **≥2 个认知模块**引用时才进 `shared`（例如 `RecordRange` 只在规划、`ContextUsage` 只在感知，各自留在所属聚合包）；
- `DomainError` **接口**在 `shared`，但**各上下文的错误枚举不在**——它们跟着自己的包（见 D11）；
- **禁止**放聚合、领域服务、或"暂时不知道放哪"的类。

> 命名说明：这里叫 `shared` 而不是 `shared-kernel`——Evans 的 Shared Kernel 指**限界上下文之间**共享模型（含跨团队协同成本），
> 我们这里是同一上下文内的公共词汇，两者不是一回事；且 Java 包名不允许连字符。

## D04 依赖注入与启动方式

**状态**：已定

**背景**：6 个模块、23 个端口、22 个适配器；本地终端应用，启动延迟是体验的一部分；同时希望"换 DI 实现时只改一处"。

**选项**
- A. Spring（`spring-context`，不用 Boot 自动装配）：能力强，启动 0.5–1.5s，依赖重
- B. 手写装配：启动最快，但装配与 main 混在一起，换实现要动业务装配代码
- C. **独立 DI 层（`jellyfish-di`）+ Dagger**：编译期生成、零反射、启动近 0；容器概念被隔离在一个模块里

**结论**：**C —— 独立 `jellyfish-di` 模块，本版本用 Dagger（`dagger-compiler` 注解处理器）。**

### 为什么单独一层

| 好处 | 说明 |
|---|---|
| **换容器只改一个模块** | Spring → Dagger → 手写，都只动 `jellyfish-di` + `boot` 里的一行创建代码 |
| **容器概念不渗入业务** | `application` / `infrastructure` / `shell` **不依赖** `jellyfish-di`，编译期就不可能 import 容器类型 |
| **启动近 0** | Dagger 是编译期生成 `DaggerAppComponent`，无反射扫描 |
| **装配可被测试** | 装配自检测试放在 `di` 模块里，断言"每个端口恰好一个实现" |

### 五条装配规则

1. **DI 注解只允许出现在 `jellyfish-di`**：一律使用 `@Module` + `@Provides` 显式 `new`，**不在** application / infrastructure / shell 的类上加 `@Inject`、`@Component`、`@Singleton`。
   - 代价：约 40–60 行 Provider 代码；
   - 收益：业务与基础设施对容器**零依赖**，真正实现"DI 与业务解耦"。
2. **组件按认知模块拆分**：`PerceptionModule` / `ActionModule` / `PlanningModule` / `MemoryModule` / `InfrastructureModule` / `PluginModule` / `ShellModule`（**7 个 `@Module`**），再用一个 `AppComponent` 聚合，与 D03 的包结构一一对应。
3. **单例作用域只给"持有资源"的适配器**（`InstanceLock`、HTTP 客户端、`TuiHumanInteraction` 等）。用例与应用组件**不加作用域**——它们无状态，每次取用即新建。
4. **`boot` 只做三件事**：解析配置（`BootOptions`）→ `DaggerAppComponent.builder()` → 启动外壳（`TuiApp`）。**不出现业务逻辑，也不出现 `new` 业务对象**——装配只剩两个模块实例（`InfrastructureModule` / `ShellModule`），其余由 Dagger 生成。
5. **测试不用 DI**：单元/集成测试直接 `new` 真实现或假端口；DI 只服务生产装配。
6. **运行时可变性不交给容器**：Dagger 是**编译期**绑定，"有插件就注入插件、否则注入默认"在绑定图里表达不了。因此需要运行期切换的端口（`Clock`、`TokenCounter`、`ModelInvocationPort`、`ExternalToolPort`、`HumanInteractionPort`、`ProgressPort`）与编排扩展点 `SessionRunner`，**Dagger 注入一个"路由器"**，由它在每次调用时查当前启用者（插件实现实时生效，见 D24）。容器概念仍在 `di` 模块内，业务代码只认接口。

### 配套

- **JDK 8**（运行环境约束）；Dagger 2 完整支持 Java 8
- Maven 编译需配置 `annotationProcessorPaths`（`dagger-compiler`），并固定 `-source/-target 1.8`；生成类 `Dagger<Component>` 只被 `boot` 引用
- 插件加载未来走 `ServiceLoader`，**不进 Dagger 容器**

### D04.1 JDK 8 的约束与配套

**状态**：已定（A：Lombok，限定用法）

**背景**：JDK 8 没有 `record` / `sealed` / `var` / 文本块 / 虚拟线程 / `ProcessHandle`；项目里值对象约 60 个，并发模型见 D05。

| 约束 | 影响 | 结论 |
|---|---|---|
| 无 `record` | 每个 VO 要手写构造器 / `equals` / `hashCode` / `toString` | **用 Lombok `@Value`**（见下） |
| 无 `ProcessHandle` | 原设计"读 PID 判断进程存活"不可行 | **`FileChannel.tryLock`**（随 D05 一并定） |
| 无虚拟线程 | 并发模型回到平台线程 | 见 D05（A） |
| 无 `var` / 文本块 | 可读性略降 | 接受 |

**关于 Lombok 的依赖传导（已澄清）**

- Lombok 是**编译期**注解处理器：生成的 `equals/hashCode/toString` 与构造器直接写进 `.class`，**运行时不依赖 Lombok**；
- Maven 必须用 `provided` + 放进 `annotationProcessorPaths`，否则会白白进入依赖树；
- 唯一残留的"传导"是**开发者侧**：阅读源码需要 IDE 的 Lombok 插件（IDEA 默认已内置支持，需开启注解处理）；
- 退出路径存在：需要摆脱它时可跑一次 `delombok`，把注解展开成源码，再删依赖。

**Lombok 使用规则（硬约束）**

1. **只允许在 `domain` 的值对象上使用 `@Value`**；
2. **禁止** `@Data` / `@Setter` / `@Builder` / `@EqualsAndHashCode`（可变或语义模糊，破坏值对象不变量）；
3. **禁止**在 `application` / `infrastructure` / `shell` 的类上加任何 Lombok 注解；
4. 构建配置：`lombok` 与 `dagger-compiler` 同时列入 `annotationProcessorPaths`，`-source/-target 1.8`。

**结论**：A —— Lombok `@Value`，按上述四条约束使用。

**影响面**：D07 序列化（Lombok 生成的 getter 命名要与 JSON 字段一致）、D13 测试（构造 VO 的方式）、构建配置。

## D05 并发与线程模型

**状态**：已定（A）

**背景**：模型已定"单写者 + 工具串行 + 子代理并行 + `ask` 阻塞"。JDK 8 没有虚拟线程，因此只能在平台线程上落地，并且要解决"`ask` 阻塞主循环时 UI 仍可响应"。

**选项**
- **A. 平台线程（主循环线程 + UI 输入线程 + 有界子代理线程池）**
  `ask` 用 `BlockingQueue.take()` 阻塞主循环线程；UI 输入线程 `put` 唤醒；取消用 `interrupt()`。
- B. 单线程 + 非阻塞 IO（NIO / 异步 HTTP）：不阻塞，但要为每个等待点写续跑逻辑，与"阻塞同步"的领域语义相悖。
- C. **Actor 风格**：所有写操作投递到一个单线程"写者"，其余线程只读/计算。写入天然串行，但每次提交都要跨线程传递，事务边界变模糊。

**结论**：**A —— 平台线程 + 有界线程池**，配四条硬约束：

| # | 约束 | 原因 |
|---|---|---|
| 1 | 主循环独占一个平台线程；`ask` 阻塞该线程 | 与领域语义一致（阻塞同步） |
| 2 | `HumanInteractionPort` **单队列 + 串行呈现** | 多线程同时 `ask` 也只呈现一个问题 |
| 3 | 子代理用**有界线程池**（默认 `min(4, CPU)`，可配） | 平台线程昂贵，必须限并发；同时这也是业务上可接受的并行度 |
| 4 | 取消必须能打断阻塞：`ask` / `join` / HTTP 都要响应 `interrupt` | 否则 Ctrl-C 只关 UI、后台还在跑 |

补充：JDK 8 有 `java.util.concurrent`（`ExecutorService`、`CompletableFuture`、`BlockingQueue`），足够实现上述模型；**不使用** `ForkJoinPool.commonPool` 承载子代理（避免与并行流争用）。

### 子问题：子代理写不写盘

- **甲**：子代理只算不写，结论回主循环统一落盘（子代理就没有自己的 `recordRange`）
- **乙**：单写者指"每个会话一个写者"——子代理各自持有 `CommitScope` 写自己的目录，用目录隔离代替进程单写者

**结论**：**乙 —— 子代理写盘，且落在主会话目录之下**（目录形状见 D05.1）。理由：子代理是"完整会话"，必须有自己的流水（否则"子代理轨迹可回看"不成立）；`InstanceLock` 防的是"两个进程同时写"（真正的损坏风险），不是"一个进程内多个会话并发写"。因此锁实现用 **`FileChannel.tryLock`**（进程级互斥），而非 PID 探测。

**影响面**：应用层文档 §10 并发模型、`HumanInteractionPort` 实现、`CancellationToken` 唤醒机制、`jellyfish-di` 的线程池 Provider、基础设施的锁实现。

### D05.1 子会话目录布局

**状态**：已定（甲 + `sub/` + 可重建索引）

**背景**：D05 定为"子代理写入主会话目录之下"。子会话深度恒为 1（子代理不得再开子代理），因此布局最多两层。

**候选布局**

- **甲（推荐）** `sub/` 子目录，子会话结构与主会话完全同构：

```
sessions/<rootId>/
├── meta.json                 # 主会话：parentId = null
├── budget.json               # 会话族台账，只有主会话有
├── records-0001.jsonl
├── plans/  reports/  reflections/  artifacts/
│   └── <planId>.json …
└── sub/
    └── <childId>/
        ├── meta.json         # 子会话：parentId = <rootId>
        ├── records-0001.jsonl
        └── plans/  reports/  reflections/  artifacts/
        （无 budget.json）
```

- **乙** 同上，但子目录命名为 `children/`（更直白，更长）
- **丙** 保持扁平：`sessions/<childId>/`，仅靠 `meta.parentId` 关联（即当前基础设施文档的写法）

**两个细节（已定，见结论表）**

1. **命名**：`sub/` vs `children/`。
2. **按 id 寻址**：嵌套后 `childId → 路径` 需要先知道 `rootId`。两种做法：
   - **a** `meta.json` 里存 `parentId`，由基础设施维护一份**可重建的索引**（放 `$TMPDIR` 缓存，丢了就扫 `sessions/*/meta.json` 与 `sessions/*/sub/*/meta.json`，深度 ≤ 2）；
   - **b** `Attempt.childSessionIds` 改为存**相对路径**（`sub/<childId>`）——**不推荐**，会让存储布局渗进领域模型。

**结论**：

| 项 | 结论 |
|---|---|
| 布局 | **甲**：子会话放在主会话的 `sub/` 下，目录结构与主会话**同构**；`budget.json` 只在主会话出现 |
| 命名 | **`sub/`** |
| 寻址 | **a**：`meta.json` 存 `parentId`；基础设施维护**可重建索引**（`$TMPDIR/jellyfish/index/sessions.json`），索引缺失时扫 `sessions/*/meta.json` 与 `sessions/*/sub/*/meta.json`（深度 ≤ 2） |
| 深度 | 固定 1 层；`sub/` 下不应再出现 `sub/`，启动对账时检查并告警 |
| 领域模型 | `Attempt.childSessionIds` **仍然只存 `sessionId`**，不存路径 |

**影响面**：`SessionRepository` / `RecordStore` / `ArtifactStore` 的路径解析、归档与删除的递归语义、启动清理规则、`模块-基础设施层.md` §4 的目录树（已回填）。

## D06 流式输出如何进入 `Record`

**状态**：已定（A + 双方法 + 断流不落）

**背景**：模型普遍支持流式；但 `Record` 是"一条完整事实"，`CommitScope` 按条追加。TUI 若没有打字机效果体验会明显落后。

**选项**
- **A. 流式只喂 UI，收完后一次性落一条 `ASSISTANT` Record**
- B. 边收边落多条（每块一条）
- C. 收完落一条，不给 UI 打字机

**结论**：**A**。四条配套约定：

1. **端口两个方法，职责分离**：
   ```java
   ModelInvocationResult invoke(ModelInvocationRequest request);                    // 非流式
   ModelInvocationResult invokeStreaming(ModelInvocationRequest request, ChunkSink sink); // 流式
   ```
   `ChunkSink` 定义在应用层（`application.shared`），实现由外壳提供（写终端）；基础设施只负责把字节流转成 chunk 推给 sink。
2. **落盘时机**：流结束后一次性提交一条 `ASSISTANT` Record（新增事务 `TA`，与 T1–T12 并列）。
3. **usage 取值**：以最后一块返回的 usage 为准；厂商只在非流式给 usage 时，用 `TokenCounter` 计。
4. **断流（用户取消 / 网络中断）不落这条 Record**——半截输出不算事实，与"半截工具调用视为失败"一致；attempt 按中断/失败收尾，屏幕上已打出的字保留但不进历史。

**影响面**：`ModelInvocationPort` 签名、`ReActLoop` 的调用分支、`ProgressPort` 的 chunk 事件、事务清单（新增 TA）、基础设施 `ModelInvoker` 的两种实现路径。

## D07 序列化契约

**状态**：已定

**背景**：文件即数据库，字段一旦写进用户目录就不能随便改。

**结论**：

### 1. 基础约定

| 项 | 约定 |
|---|---|
| 库 | **Jackson 2.17.x**（最后一个支持 Java 8 的稳定线） |
| 命名 | JSON 一律 **camelCase**，与 Java 字段同名（不做转换） |
| 枚举 | 存**枚举名**（`ACTIVE` / `SUPERSEDED`），不存序号。**改名 = 破坏性变更，必须走迁移** |
| null | **不写**（`@JsonInclude(NON_NULL)`）；缺失即"没有这个字段" |
| Id | 一律字符串（UUID 或 `builtin.` 前缀） |
| 时间 | **epoch 毫秒整数**（`1739520600000`）；日志与界面负责格式化成可读时间 |
| 数字 | 整数不加引号；比例类用 `double`（如 `systemRecordRatioLimit: 0.5`） |

### 2. 值对象与 Jackson 的对接

`@Value` 生成不可变类，Jackson 需要能定位构造器。做法：

- 项目根加 `lombok.config`：`lombok.anyConstructor.addConstructorProperties = true`
- Lombok 会给构造器加 `@ConstructorProperties`，Jackson 原生支持 ⇒ **不需要** `jackson-module-parameter-names`，也不需要逐类写 `@JsonCreator`

### 3. 版本与容错

- 版本号**只放全局** `schema.version`（单整数），文件内不写版本字段；
- 读：**未知字段忽略**（debug 日志，便于新旧互读）；**必填字段缺失或类型不符**视为损坏——`records-NNNN.jsonl` 跳过该行并告警，`meta.json` 损坏则该会话拒绝加载；
- 写：内部状态**紧凑单行**；配置文件（`tools`/`providers`/`models`）**2 空格美化**；流水一行一个 JSON 对象。

### 4. 三条硬规则

1. **禁止万能字段**（`extra: {}`）：字段要么建模、要么不存；
2. **禁止存派生态**（`retryCount`、窗口内记录列表、token 用量）——与"可推导状态不落库"一致；
3. **枚举与字段改名视为迁移**：必须提升 `schema.version` 并写迁移逻辑。

**影响面**：`jellyfish-infrastructure/codec`、所有 VO 的注解、测试夹具、迁移脚本。

## D08 tokenizer 与计量口径

**状态**：已定（策略链 + jtokkit 优先 + usage 校准）

**背景**：`ContextUsage` 是"**准备发出去的窗口**"的本地计数，用于**调用前**决定是否折叠；厂商的 `usage` 是**调用后**才会拿到的真实消耗。两者时序不同、用途不同，不能互相替代。

```
事前：本地计数（决定折不折叠）  →  调用  →  事后：厂商 usage（记账 + 校准）
```

**结论**：

### 1. 两条计量线

| 线 | 来源 | 用途 | 精度要求 |
|---|---|---|---|
| **事前计数** | `TokenCounter` 端口（见下） | `ContextUsage.usedTokens` → 与 `inputCeiling` 比较 | 估算即可，**保守偏大** |
| **事后台账** | 厂商响应里的 `usage` | `Budget.consumedTokens` | **精确**，不估算；厂商不给时才回退估算 |

### 2. 事前计数：策略链（端口不变，实现可扩展）

```
应用层端口（已有，不新增）
  TokenCounter.count(messages, modelId) → int

基础设施实现
  CompositeTokenCounter
    ├─ JtokkitStrategy          默认首选（OpenAI 系 cl100k / o200k 精确；其他模型为近似）
    ├─ ProviderCountApiStrategy 可选：Anthropic / Gemini 的 count API（有网络开销）
    └─ EstimatorStrategy        兜底：CJK ×1.0、其他 ÷4、每条消息 +4，向上取整（宁可高估）
  选择规则：按 modelId 命中 supports() 依次尝试；异常 / 超时 / 不支持 → 降级到下一个
```

- **Jtokkit 优先**：即便对 Claude / Gemini 只是近似，通常也比字符估算准；偏差由下面的校准吸收。
- jtokkit 需选**仍支持 Java 8** 的版本（实现前用最小样例验证）。
- 估算**必须偏大**：高估只会多折叠一次；低估会撞 API 400。
- 因为 jtokkit 是本地毫秒级操作，**不需要"临近阈值才精确计数"的 80% 触发规则**（原方案 C 的复杂度可以去掉）。

### 3. 事后校准（EWMA）

- `UsageCalibrator`（实现放基础设施，状态放 `$TMPDIR` 缓存，可丢弃）：
  - 每次调用后，记 `estimate / actual` 的比值，按模型做 EWMA（系数 0.3）；
  - 样本数 ≥ 5 且偏差 > 10% 时才启用；系数 **clamp 到 [0.8, 1.5]**，避免异常值把估算带飞；
  - 只修正**事前估算**，**不影响** `Budget` 台账（台账永远用厂商 usage）。
- 缓存目录被清空只会让校准从零开始，不影响正确性。

### 4. 明确不做的事

- **不给 `ContextUsage` 加 `countedBy` 字段**（不引入领域模型改动）；排查时看日志里的 `TokenCounter` 命中策略即可。
- **不按厂商各写一套分词器**：由校准机制收敛偏差。

**影响面**：`jellyfish-infrastructure/tokenizer` 新增包；基础设施适配器清单里的 `ProviderTokenCounter` 更名为 `CompositeTokenCounter`（文档同步）；`settings.json` 不新增参数（校准系数是常量）。

## D09 凭据存储

**状态**：已定（只做环境变量注入）

**背景**：`ApiCredential` 只存 `apiKeyRef`；真实密钥不能明文落在 `~/.jellyfish`；JDK 8、多平台、本地终端应用。

**选项**
- A. 系统钥匙串（`security` / `secret-tool` / `cmdkey`）：安全但在容器、最小化 Linux、CI 上常不可用
- B. 本地加密文件 + 主密码：零依赖但每启动要输密码
- **C. 环境变量 / 外部注入**：应用**完全不落盘**

**结论**：**只做 C**。

### 规则

1. **`ApiCredential.apiKeyRef` = 环境变量名**（如 `"OPENAI_API_KEY"`），不是密钥本身，也不是文件路径。
2. **配置入口 = 编辑文件 + 重启**：改 `providers/<providerId>.json` 里的 `credential.apiKeyRef`，重启应用生效；**不做**运行期密钥输入、不做钥匙串、不做加密文件。
3. **密钥只在内存里短暂存在**：仅由 `ModelInvoker` 读取环境变量并放入请求头；**不进日志、不进错误信息、不进异常栈**（异常只打印 `providerId`）。
4. **缺失即不可用，不阻塞启动**：启动时若某 provider 的环境变量不存在，标记该 provider 不可用并提示一条（形如 `provider openai: 环境变量 OPENAI_API_KEY 未设置`），其它 provider 照常。
5. **`ManageCatalogUseCase` 不处理密钥**：它只管理 endpoint、模型列表、启用状态；凭据改动只走"编辑文件 + 重启"。

### 已知代价（记录在案，接受）

| 代价 | 说明 |
|---|---|
| 同机其他进程可能读到环境变量 | 同一用户下的进程（`/proc/<pid>/environ`）可见；属于本机单用户场景的可接受风险 |
| shell 历史泄露风险 | 文档里提示用 `export` 前加空格或使用 `env` 文件，不写进 shell 历史 |
| 每次启动需要环境 | 由用户的 shell profile 负责；不提供持久化 |

**影响面**：`ModelInvoker` / `Provider` 适配器、启动自检、`providers/*.json` 的字段语义、`模块-行动.md` 中 `ApiCredential` 的说明（需回填"= 环境变量名"）。

## D10 网络重试与"模型降级"的边界

**状态**：已定（A：同模型有限重试；按次数不按总时长）

**背景**：三层重试容易混——业务重试（attempt，消耗重试名额）、模型降级（结构性故障）、网络重试（瞬时故障）。

**结论**：**A —— 网络层只对同一模型做有限次重试，仍失败才交给降级链。**

### 1. 错误分流表

| 类别 | 典型 | 处理 |
|---|---|---|
| **可重试** | 连接超时、读超时、连接重置、`429`、`500`、`502`、`503`、`504` | **同模型**退避重试 |
| **不可重试 → 降级** | `401` / `403`（凭据）、`404`（模型下线）、`400`（请求非法） | 立刻交给 `ModelInvoker` 备用链 |
| **不可重试 → 请求超限** | `400` 中的上下文超限类 | 抛「请求超限」（应用层 §9：强制折叠一次后重试） |
| **业务层** | 模型正常返回但内容不合预期 | 与网络无关，走验证链 |

### 2. 重试参数

| 项 | 值 |
|---|---|
| 最大重试次数 | **3 次**（即最多 4 次请求） |
| 退避序列 | `500ms → 1.5s → 4s`（带 ±20% 抖动） |
| `429` | 优先遵守 `Retry-After`；**`Retry-After > 60s` 则放弃等待、直接降级** |
| 总时长上限 | **不设**——**按次数封顶**，边界即"次数 ×（单次超时 + 单次等待上限）" |
| 参数位置 | **写死常量**，不进 `settings.json` |

### 3. 与业务重试的隔离

- 网络重试**不消耗 attempt 重试名额**、**不触发反思**、**不改变 `Plan` 状态**；
- 只有"降级发生了"才 raise `ModelSwitched`（由 `Session.switchModel` 触发）。

### 4. 等待期间的可观测

- 每次安排重试前通过 `ProgressPort` 发一条 `RetryScheduled{attempt, delayMs, reason}`，界面可据此显示倒计时（界面细节留到外壳阶段）；
- 退避等待必须响应 `CancellationToken`（用户 Ctrl-C 立即中止，不再重试）。

### 5. 已知边界（记录在案）

无总时长上限时，最坏等待 ≈ `3 × (单次请求超时 + 60s)`。以 `单次超时 120s`、`Retry-After 60s` 为例约 9 分钟——**这是"按次数不按总时长"的必然代价**，由界面的倒计时与取消能力兜底。

### D10.1 单次请求超时参数

**状态**：已定

| 项 | 值 | 说明 |
|---|---|---|
| 连接超时 | **10s** | 建连失败快速失败，避免"网络断了"看起来像"模型在思考" |
| 读超时（非流式） | **120s** | 长上下文 + 推理模型经常超过 60s |
| 流式"空闲超时" | **60s** | **收到任意 chunk 即重置**；避免长回答被误杀 |
| 是否可配 | **否**（写死常量） | 与 D10 一致 |

补充：流式**不用**总时长超时（3 分钟的长回答是正常的），只用空闲超时；一次超时算一次失败，进入 D10 的重试序列。

**影响面**：`ModelInvoker` 的 HTTP 客户端配置、`ProgressPort` 事件、取消路径、D14 日志（重试要留痕）。

## D11 错误体系与用户可见文案

**状态**：已定（边界 Result + 内部异常；错误码按上下文拆）

**背景**：三类"不顺利"性质不同，必须分开表达：**不变量违反**（程序 bug）、**预期内的业务失败**（正常分支）、**环境/技术异常**（需告警与降级）。

### 1. 分层表达

```
domain          不变量违反 → 抛 DomainInvariantViolation（RuntimeException，表示 bug）
application     用例返回 Result<T, UseCaseError>；每个用例只有一个包装点
infrastructure  技术异常（IOException 等）→ 在端口实现处显式映射为对应上下文的 DomainError
shell           只做两件事：把 code 翻译成文案；把 DomainInvariantViolation 变成"内部错误"
```

**四条硬约束**

| # | 约束 | 说明 |
|---|---|---|
| 1 | **只包"预期内的失败"** | `DomainInvariantViolation` 必须冒到最外层：记 `error` 日志 + 保存现场快照；**不得**被包成 `Result.failure` |
| 2 | **每个用例只有一个包装点** | 用模板方法/装饰器统一包装，禁止散落的 `try/catch` |
| 3 | **异常 → 错误码的映射必须显式** | 禁止 `catch (Exception e) → UNKNOWN`；`IOException` 在 `RecordStore` 里意味着 `S_CORRUPTED`，在 `InstanceLock` 里意味着 `S_LOCKED` |
| 4 | **端口写清抛出契约** | 非受检异常不进签名，端口 javadoc 必须写明"可能抛 `TechnicalException`" |

补充：`CommitScope.commit()` 失败时**不得返回 success**；包装点在事务之外，部分落库由启动对账兜底。

### 2. 错误码：按限界上下文拆，统一 code 命名

**为什么不使用单一枚举**：单一 `ErrorCode` 会成为共享内核热点（每个上下文都往里加值），并把技术分类（`T_TIMEOUT`）与领域概念（`P_REPLAY_EXHAUSTED`）混在一起。

```java
// 唯一共享的东西：一个方法的接口（domain/shared）
interface DomainError { String code(); }

// 各上下文自己的错误枚举（放在各自包里）
enum PlanningError implements DomainError { REPLAY_EXHAUSTED("P_REPLAY_EXHAUSTED"), ... }
enum ModelError    implements DomainError { UNAVAILABLE("M_UNAVAILABLE"), ... }
enum PluginError   implements DomainError { INCOMPATIBLE("PL_INCOMPATIBLE"), ... }
enum SessionError  implements DomainError { NOT_FOUND("S_NOT_FOUND"), ... }
enum PolicyError   implements DomainError { INVALID_VALUE("C_INVALID_VALUE"), ... }
...
```

**code 前缀表**（包 → 前缀，用单测强制）

| 包 | 前缀 | 示例 |
|---|---|---|
| `domain.planning.*` | `P_` | `P_REPLAY_EXHAUSTED`、`P_INVALID_PLAN` |
| `domain.perception.session` | `S_` | `S_NOT_FOUND` |
| `domain.perception.policy` | `C_` | `C_INVALID_VALUE` |
| `domain.action.model` | `M_` | `M_UNAVAILABLE`、`M_AUTH_FAILED` |
| `domain.action.tool` | `T_` | `T_TIMEOUT`、`T_DENIED_BY_USER` |
| `domain.action.agent` | `A_` | `A_BUILTIN_IMMUTABLE` |
| `domain.action.plugin` | `PL_` | `PL_INCOMPATIBLE`、`PL_PORT_CONFLICT`、`PL_INVALID_ID`、`PL_NOT_FOUND` |
| `domain.action.budget` | `B_` | `B_OVER_LIMIT`（当前只预警，预留） |
| `domain.memory.*` | `E_` | `E_NOT_FOUND` |
| `infrastructure.*` | `X_` | `X_CORRUPTED`、`X_LOCKED`、`X_IO_FAILED` |

**检查机制**：一个单测扫描所有 `DomainError` 实现，断言 code 前缀与包名映射一致 —— 把约定变成机器检查。

### 3. 应用层出口与文案

```java
final class UseCaseError {   // Lombok @Value
  DomainError error;   // 上下文自己的错误
  String detail;       // 技术细节，只进日志
  Object context;      // 可选：providerId / toolId / fieldName
}
```

- **取消不是错误**：`CancellationToken` 触发时走独立的 `Cancelled` 分支，外壳**不**弹错误提示（与 `Answer.kind = CANCELLED` 对齐）。
- **文案放 shell**：`shell/src/main/resources/messages.properties`，key = code（`P_REPLAY_EXHAUSTED=计划已重试用尽…`）；缺 key 时回退显示 code 本身，保证不崩。
- **界面只展示人话 + 可行动建议**，不出堆栈、不出 HTTP 原文；`detail` 只进日志。

**影响面**：`domain/shared` 增加 `DomainError` 与 `DomainInvariantViolation`；每个上下文一个错误枚举（`PlanningError` / `SessionError` / `PolicyError` / `ModelError` 等）；`application/shared` 增加 `UseCaseError` 与 `Result`；外壳增加资源文件（`messages.properties` + `Messages` 类）与翻译器；单测增加前缀一致性检查。

## D13 测试策略

**状态**：已定（C：四层测试，脚本化假模型，全部仓储做契约测试）

**背景**：文件系统是数据库、模型是外部依赖，两者都需要可替换的替身。

**结论**：

### 1. 四层测试

| 层 | 做法 | 关键约束 |
|---|---|---|
| **领域单测** | 纯内存直接 `new` 聚合 | 只测状态机与不变量；不碰文件、不碰线程 |
| **应用层测试** | 假端口：`ScriptedModelInvocationPort`、`InMemory*Repository`、`FakeHumanInteraction`（预置答案队列） | 断言"提交顺序"（事实 → 追加 → 替换）与"三条出口" |
| **基础设施契约测试** | 抽象 `RepositoryContractTest`，文件实现继承它 | **全部 9 个仓储都做**：Session / RecordStore / Plan / Report / Reflection / Experience / Budget / Policy / Catalog；另加 `CommitScope` 的"中途失败可对账"用例 |
| **无头端到端** | 用 `ScriptedModelInvocationPort` 跑完整链路：输入 → 内循环 → `generate_plan` → 执行 → `submit_step` → 验证 → 完结 | **不测 TUI 渲染**；断言落盘结果与状态迁移 |

### 2. 技术选型

- **JUnit 5**（Java 8 兼容）；契约测试用抽象基类 + 子类，不引参数化框架
- **假端口优先，需要时才用 Mockito**（4.11.x，Java 8 兼容线）：针对"只需一个端口返回固定值"的场合，避免为一个方法写一个假实现类；**仍禁止** `mock 一切`（聚合与领域服务必须用真实对象）
- **JaCoCo**（0.8.12）出覆盖率数据供参考：**只出报告，不设门槛、不纳入 CI 卡点**（覆盖率不等于规则被覆盖，关键规则仍看断言）
- 每个用例用 `--data-dir` 指向**临时目录**，`@AfterEach` 删除
- 断言只依赖 JUnit 原生 + 少量自写辅助方法，**不引断言库**

### 3. 明确不做

| 不做 | 原因 |
|---|---|
| TUI 渲染测试 | 渲染随终端库演进，投入产出低；改为测"外壳调了哪个用例、传了什么" |
| CI 调用真实模型 | 不稳定、需密钥、有成本 |
| 录制真实响应回放 | 易漂；改用**脚本化假模型**（可读、可断言） |
| 用覆盖率当验收门槛 | 覆盖率只作参考数据（JaCoCo 报告）；验收看"关键规则有断言"：三条出口、提交顺序、5 条对账规则、D10 错误分流、错误码前缀一致性 |

### 4. 必测清单（验收口径）

1. 三条出口：继续 / 结束 / 挂起；
2. `submit_step` 后的验证分支（PASSED / FAILED / UNDETERMINED / 免验证）；
3. `CommitScope` 的固定顺序与"事实先落、状态后落"；
4. `StartupReconciler` 的 5 条对账规则；
5. 模型不可用 / 请求超限 / 工具失败 三条错误路径；
6. 经验奖惩不对称、容量淘汰、检索分配；
7. 目录布局（`sub/` 嵌套、`records` 滚动、`artifacts` 落点）；
8. 错误码前缀与包名一致（反射扫描）。

**影响面**：各模块 `src/test`、测试夹具（fixture）设计、CI 时长、D13 依赖（JUnit 5 + surefire 3.x）。

## D14 日志、审计与脱敏

**状态**：已定（C：结构化 key=value；7 天；不做独立审计）

**背景**：`logs/` 只记技术事件（领域事实已在 `records/`、`reports/`）。排障常问"为什么折叠了、为什么降级了、花了多少 token"，日志要能答，又不能写进对话内容。

**结论**：

### 1. 格式：结构化 key=value 单行

```
2026-02-14T09:30:00Z INFO  s=01J9… plan=P-7 step=2 att=1 ev=verification.vote
                            code=P_VERIFY_FAILED durMs=1834 tokIn=12043 tokOut=312 model=claude-x
```

**字段固定**（禁止自由发挥）：`ts level thread s plan step att ev code durMs tokIn tokOut model tool retry`

### 2. 四条硬规则

| # | 规则 |
|---|---|
| 1 | **绝不记录**：密钥、`Authorization` 头、完整对话正文、工具结果原文、文件内容。需要定位时记 `hash`（SHA-256 前 8 位）+ 长度 |
| 2 | **`trace` 级别才可记录"请求/响应摘要"**（模型名、消息条数、总字节数、usage），**仍不记正文** |
| 3 | **敏感字段统一脱敏**：任何 key 命中 `key` / `token` / `secret` / `password` / `authorization` / `cookie` → `***`；在日志适配器统一处理，不靠调用方自觉 |
| 4 | **只记技术事件，不重复领域事实**：不记"步骤完成了"（已在 `reports/` 里），记"验证耗时 1834ms、命中第 2 层" |

### 3. 滚动与保留

- `logs/` 按天滚动，保留 **7 天**；单文件超 32 MiB 切分（与 `records` 同策略）。
- **不做独立审计日志**：审计靠 `records/` + `reports/` + `reflections/`（带时间戳、不可变），再记一份就是第三套真相。

**影响面**：`jellyfish-infrastructure` 的日志实现、`--log-level` 参数（D12）、排障文档。

## D20 TUI 的终端层：JLine 3（只做输入）

**状态**：已定

**背景**：界面形态定为"单栏流式"（见 D12.1）。输入侧需要行编辑、历史、`/` 命令补全、多行粘贴；输出侧需要"流式打字机 + 就地暂停 + 状态行覆盖"。两者对终端的要求不同。

**选项**
- A. 裸 ANSI：零依赖，但输入要自己实现行编辑/历史/补全/粘贴
- B. **JLine 3（只用 `LineReader` 做输入）**：白得行编辑、历史、补全、括号粘贴；输出仍由自己的渲染器写 ANSI
- C. Lanterna 3：全屏 + 控件；`Screen` 会接管整个终端，与"单栏滚动"冲突

**结论**：**B** —— JLine 3 只承担**输入**，不接管屏幕。

| # | 约定 |
|---|---|
| 1 | 依赖 `org.jline:jline`（3.2x，Java 8 兼容线），只用 `Terminal` / `LineReader` |
| 2 | 输出（流式、提问、状态行）由 `shell/tui` 自己的渲染器生成 ANSI，**不接管屏幕**：读取空闲时直写 stdout；**读取进行中**（提问暂停、子代理进度）的异步输出经 `LineReader.printAbove` 提交，由 JLine 负责"擦提示符 → 打印 → 重绘提示符"。不使用 JLine 的 Display 做整屏管理 |
| 3 | 历史只放内存（不落盘）：数据目录布局里没有"历史文件"这一项，不为它新增（D05.1） |
| 4 | 补全候选只来自 `/` 命令表与"会话/技能/工具"的只读列表，不做动态查询 |
| 5 | 两个信号：**第一次 Ctrl-C = 取消当前轮**（外壳把 SIGINT 转成 `CancellationToken.cancel()`，令牌回调执行 `Call.cancel()` 让阻塞读立刻失败，阻塞中的 `ask` 返回 `CANCELLED`），**第二次 Ctrl-C 或 `exit` = 退出**（D12.1） |
| 6 | 提问期间**暂停输入框**：提问由输入线程从队列取出、串行呈现并标注来源（D05-2）；渲染器负责"就地暂停"而不是整屏重绘 |
| 7 | **终端能力由 JLine 下结论，不做自定义探测**：外壳建 `Terminal` 后看 `type == "dumb"`。**输入侧**（stdin 是否 TTY）决定是否启用行编辑：非 TTY 用原始行读取，读到 EOF 正常退出。**输出侧**（stdout 是否 TTY）决定是否重绘：非 TTY 不用 `\r` 状态行、不输出 ANSI 颜色，一行一条纯文本。两侧分开判（`cat 提示.txt \| jellyfish` 要"能读管道、仍能彩色输出"） |
| 8 | **写者归属（落地 D05 约束 1/2）**：stdin 只由输入线程读；stdout 只有"输出单写者"写——主循环的流式输出直写，其他线程（子代理进度、预算预警、取消提示）一律投递到输出队列，由单写者按第 2 条转发。**渲染器只负责格式，不决定写到哪里** |

**影响面**：`jellyfish-shell`（`TuiApp` / `AnsiRenderer` / `OutputGateway` / `QuestionBroker` / `TuiHumanInteraction` / `TuiProgressReporter` / 补全器）、`pom.xml`、`boot/Main`。

## D22 会话没有状态：存在即可用，归档是存放策略

**状态**：已定

**背景**：会话本是持久化容器，却被建模成三态机（`RUNNING / RESUMABLE / ARCHIVED`）：「在跑」是**运行时事实**，却写进了磁盘状态；而 `StartupReconciler` 的 5 条规则里没有一条负责擦掉崩溃后残留的 `RUNNING`，于是会话会永久卡在"在跑"，界面上无从判断。

**选项**
- A. 保持三态，补一条"启动时把 `RUNNING` 归位"的规则
- **B. 去掉状态**：`sessions/<id>/` 存在即可用，不存在即不可用；归档 = 压成包移走
- C. 两态（`AVAILABLE / ARCHIVED`）：仍是持久状态，只是少一个值

**结论**：**B**。状态机不是会话的职责，"封存/压缩"属于仓储的存放策略，不属于聚合不变式。C 保留了一个可以由**位置**推出的字段，属于冗余。

| # | 约定 |
|---|---|
| 1 | 会话**没有状态字段**；可用性 = `sessions/<id>/` 是否存在。取消、挂起、收敛都只改 plan/attempt，不改会话 |
| 2 | **"在跑"不落盘**：它是进程内事实，前提是数据目录单实例（`FileInstanceLock`） |
| 3 | **归档 = 压缩后移走**：`archive/<id>.zip`（先写 `.tmp` → 改名 → 删原目录）；此后应用**不再列出、不再加载**它。解档 = 用户自己解包放回 `sessions/` |
| 4 | 归档中间态对账：`.tmp` 包直接丢弃；包已完整但原目录还在 → 补删原目录（幂等） |
| 5 | 打不开会话只有一个原因：**不存在**（`S_NOT_FOUND`）；不再有"已归档"错误码 |
| 6 | 界面选择会话靠**列出存在的目录**（`SessionRepository.list()`），不靠状态过滤 |

**影响面**：`domain`（删除 `SessionStatus` 与相关行为）、`application`（`SessionRepository` 端口、`ManageSessionUseCase`、`RunSessionUseCase`、`StartupReconciler`）、`infrastructure`（`meta.json` 去掉 `status`、归档改压缩、列出实现）、`shell`（`/sessions`、`/open`、`/archive` 语义）。

## D18 日志实现

**状态**：已定

**背景**：D14 定了日志的格式、保留期与脱敏要求，但没有选实现；手写一个"按天滚动 + 32 MiB 切分 + 保留 7 天 + 并发安全"的日志器属于重复造轮子。

**选项**
- A. 手写追加 + 定时滚动（零依赖，但要自己处理并发、切分、清理）
- B. **Log4j2**（2.x 仍支持 Java 8；`RollingFile` 内置按天/按大小滚动与 `max` 上限；支持自定义 `Layout` 做统一脱敏）

**结论**：**B —— Log4j2 2.24.x**（Java 8 兼容线）。

| # | 约定 |
|---|---|
| 1 | 输出：`logs/jellyfish.log`，`TimeBasedTriggeringPolicy`（1 天）+ `SizeBasedTriggeringPolicy`（32 MiB），`DefaultRolloverStrategy max=7`（D14-3） |

| 3 | 脱敏：自定义 `Layout` 包一层 `PatternLayout`，把 key 命中 `key/token/secret/password/authorization/cookie` 的值统一替换为 `***`（D14-2 规则 3，**适配器统一处理**） |

| 5 | 不做独立审计（D14 明确） |

**影响面**：父 POM、`jellyfish-infrastructure/log` 包、`boot/Main`（在初始化日志前设置数据目录系统属性）、D14 的实现落点。

## D16 模型调用的线协议与系统提示词映射

**状态**：已定

**背景**：领域侧的 `ModelInvocationRequest` 是协议中立的（`systemPrompt` + `ChatMessage` 列表 + `ToolCall`），但三家供应商的线格式不同：OpenAI 用 `messages` 里的 `role=system` 承载系统提示词，Anthropic 用**顶层 `system` 字段**（"输入消息里没有 system 角色"），Gemini 用 `systemInstruction`。

**选项**
- A. 只实现 **OpenAI 兼容的 `/chat/completions`**（自定义 baseUrl；vLLM / Ollama / OpenRouter / 中转站均兼容）
- B. 三家各写一套适配器
- C. 引第三方 SDK（openai-java / anthropic-java）

**结论**：**A**，配六条约定：

| # | 约定 |
|---|---|
| 1 | 端点：`Provider.apiEndpoint` 是 **baseUrl**，请求路径由协议实现决定（`OPENAI_CHAT` 为 `/chat/completions`）；`Model.modelName` 原样填 `model` |
| 1.1 | **协议选择靠 `Provider.protocol`**（`OPENAI_CHAT` / `ANTHROPIC_MESSAGES` / `GEMINI`，缺省 `OPENAI_CHAT`）：厂商（OpenAI / DeepSeek / Kimi / MiniMax）差异是数据，协议差异是适配器；新增厂商零代码，新增协议 = 一个实现类 + 一个枚举常量 |
| 2 | 系统提示词：`request.systemPrompt` → 首条 `{"role":"system"}`。其它协议若将来接入，由各自适配器映射到顶层 `system` / `systemInstruction`，**领域层不感知差异** |
| 3 | 工具：`ToolSchemaSnapshot` → `tools:[{type:"function",function:{name,description,parameters}}]`；响应 `choices[0].message.tool_calls[]` → `ToolCall`；结果回灌 `{"role":"tool","tool_call_id":callId,"content":…}` |
| 4 | 计量：`usage.prompt_tokens / completion_tokens` → `ModelUsage.inputTokens / outputTokens`；流式无 usage 时由 `TokenCounter` 估算（D06-3） |
| 5 | HTTP 客户端：**OkHttp 4.12.0**（Java 8 兼容、仍在维护；传递依赖 okio + kotlin-stdlib）。理由见下方"为什么不用 JDK 自带"；超时按 D10.1；取消用 `Call.cancel()` |
| 6 | 错误映射：按 D10 分流表落到 `M_*`（401/403 → `M_AUTH_FAILED`、404 → `M_MODEL_NOT_FOUND`、400 上下文超限 → `M_CONTEXT_EXCEEDED`、5xx/429 → 可重试） |

**为什么不用 JDK 自带 `HttpURLConnection`（原第 5 条，已被 M14 取代）**

| 能力 | `HttpURLConnection` | OkHttp |
|---|---|---|
| 取消在途请求 | 不支持，只能等读超时 | `Call.cancel()` 让阻塞读立刻失败 |
| 超时粒度 | connect / read | connect / read / write / callTimeout |
| 连接复用 | 难控制 | 连接池 + HTTP/2 |
| 测试替身 | 手搭 `HttpServer` | `MockWebServer` 可声明延迟、`429 + Retry-After`、断流 |
| TLS 维护 | 跟 JVM 版本 | 库跟踪 TLS 生态（安全补丁） |

代价：多约 2 MB 传递依赖；换来"取消语义可落地"（D05-4、D10-4）与可测性。3.14.9 虽然纯 Java 且更轻，但 2020 年后停更，不作为选择。

**影响面**：`infrastructure/model` 的 `ModelInvoker` 与 JSON 映射；`providers/*.json` 的 `apiEndpoint` 语义（= baseUrl）；D10 错误分流的实现点；模型改动已记录在 `实现过程的模型改动记录.md` M01–M03、M14。

2. 切片内可以临时简化（例如 S2 的验证只实现确定性层），但**不许跳过落盘与对账**——那两条是后面所有切片的地基。

## D23 技能自动沉淀：单聚合 + `mutable`，front-matter 即事实

**状态**：已定（M37）

**背景**：记忆只沉淀"经验"（陈述性知识），`SkillDefinition`（程序性知识）是纯人写资产、系统只读（M23 / D12）。要让系统从成功路径里学出 SOP，必须先回答三件事：机学产物存在哪、谁能改、怎么淘汰。约束来自三条既有纪律：① 文件即事实（D07）；② 不做候选态、不引入多余状态机（D22 的价值取向）；③ 领域层不依赖技术与配置。

**选项**

- A. 拆两个聚合：`HumanSkill`（文件即事实、只读）+ `LearnedSkill`（机写、带版本与置信度）。语义最干净，但两套检索、两套生命周期、`load_skill` 要分叉。
- B. 单聚合 + `source`（人写/机学）+ `mutable` 两个标志位。信息最全，但"来源"没有任何领域规则依赖它（容量数总数、淘汰靠删文件），属于为将来付账。
- C. **单聚合 + 一个 `mutable`**：人写与机学同构，唯一差别是"系统有没有权改写正文"。状态与可变性都写在 `SKILL.md` 的 front-matter 里，系统只读写正文（且仅当 `mutable`）。

**结论**：**C**，配八条约定。

| # | 约定 |
|---|---|
| 1 | `SkillDefinition` 增加 `boolean mutable`（默认 `true`；jar 内置恒 `false`；人写技能在 front-matter 写 `mutable: false` 即锁死）。`mutable = false ⇒ revise()` 抛不变量违反，守护在聚合内 |
| 2 | **删除 `activate()` / `deprecate()`**（M23 之后已无调用路径）：`status` 三值只由 front-matter 决定，系统只读；下线 = 用户删目录或改 `status: deprecated` |
| 3 | **无候选态**：机学技能写出即 `ACTIVE`、立即可用；`skillCapacity`（默认 30，ACTIVE 总数、含人写、不含 jar 内置）到限即停止沉淀并发提醒 |
| 4 | **无改进历史**：`revise()` 整篇覆盖，不落 revision 链；改动依据留在产出它的子代理会话流水里（`Attempt.childSessionIds` 可达） |
| 5 | **正文是自由文本**：五节骨架（适用 / 步骤 / 每步判据 / 验证 / 常见坑）靠子代理 prompt 约定，**系统不解析、不校验、不渲染**；`InstructionTemplate.variables` 与 `render()` 一并删除 |
| 6 | **快照只冻结浅层**：`SkillSummarySnapshot` 扩为 `name + description + triggerCondition`；**正文不冻结**（`load_skill` 现读，接受漂移）；会话中途新沉淀的技能只进新会话 |
| 7 | **判定在计划完结、一次调用、互斥产物**：本次 plan 用过技能 ⇒ 判改进（`MERGE`）；没用过 ⇒ 判沉淀（`CREATE`）并同时判"是不是经验"，同一件事只进一边（`PlanCompletionCurator`） |
| 8 | **全局资产写段**：每个会话（含并行子会话）都能沉淀，`skills/` 与 `experience/` 不走"每会话一个写者"，而是进程内串行的全局写段，容量"读—判—写"在该段内完成 |

**明确不做**：技能质量分/置信度、连续失败自动淘汰、`meta.json`、`SkillRevision` 历史、从经验自动升级为技能、技能自动激活（`triggerCondition` 仍只是给模型看的判断依据）。

**已知风险（记录在案）**：① 子代理会话的 plan 常无验证声明，其沉淀出的技能天然"证据不足"，本期不加门槛；② `mutable: true` 的人写技能会被 LLM 覆盖，用户手改与系统改写共享同一文件，**没有冲突检测**（纪律：要手改先置 `mutable: false`）；③ 只看本次结果 ⇒ 单次偶发失败即可能触发改写，且无回滚。

**影响面**：`模块-记忆`（聚合/服务/事件/§7.3/§8.5-8.6）、`模块-感知`（快照 VO 与冻结语义、`skillCapacity`）、`模块-规划`（`Attempt.usedSkillIds`、`Plan.recordSkillUsage`）、`模块-应用层`（2 个组件、T13/T14、端口方法、全局写段）、`模块-基础设施层`（front-matter、`saveSkill`、全局写段）、`模型图`。

## D24 插件与扩展点：PF4J 进程内 + 端口路由 + 安装时一次信任

**状态**：已定（M42）

**背景**：D01.1 把旧插件机制（拷 jar 进进程）连同 `Jellyfish-Plugins` 一起归档清空，并留下"插件 SPI 与新内核一起重新设计"。现在要回答两件事：**能不能用插件加工具**、**能不能用插件改造内核**。定位是**本地实验性 Agent**：不推荐安装未知来源的第三方插件，鼓励用户自己写——安全策略因此选择"换取自由度"。

**选项**

- A. 只做声明式（工具/技能/代理 = 数据，执行一律 REST/MCP）。
- B. 只做进程内代码（PF4J），一切皆可替换。
- C. **分层**：工具走"声明 + 宿主执行"（含进程内 handler），端口与编排可被插件替换；进程内无沙箱，信任靠安装时一次同意。

**结论**：**C**，配十条约定。

| # | 约定 |
|---|---|
| 1 | **插件 = 一组工具声明 + 若干端口实现 + 一份 `plugin.json`**。领域只多 `PluginManifest` 聚合与 `PluginRepository` / `PluginRuntimePort` 两个端口 |
| 2 | **PF4J 3.16.0**（class major 52 = Java 8 字节码，实测）；装/启/停/卸可在运行期完成，**同 id 升级要求重启** |
| 3 | **`ToolSource.type` 增 `PLUGIN`，只作来源标记**：执行仍走同一个处理器注册表（`InternalToolHandler`），不新增处理器接口、不新增受限上下文（用户自己写的插件按"善意"假设设计） |
| 4 | **落盘只存用户意图**：`plugin.json` 存 `trusted / grantedAt / grantedCapabilities`；"已加载/失败"是进程内事实，不落盘（与 D22 同构）。卸载 = 删目录 |
| 5 | **可替换面**：6 个端口（`HumanInteractionPort`、`ProgressPort`、`Clock`、`TokenCounter`、`ExternalToolPort`、`ModelInvocationPort`）+ 1 个编排扩展点 `SessionRunner`（默认实现 `ExecutionLoop`）。内层编排组件不单独开放 |
| 6 | **端口路由**（D04-6）：Dagger 图不变，注入路由器；路由表可变、每次调用查当前启用者 |
| 7 | **启用按能力逐项**：`grantedCapabilities ⊆ declaredCapabilities`；**同一端口至多一个启用者**，冲突在启用时拒绝；运行期失败**不回退**默认实现 |
| 8 | **信任 = 安装时一次同意**：`trusted=true` 后其工具免放行审批（I3 语义不变，信任来源多一种）；不再提供逐次审批 |
| 8.1 | **宿主 API 版本 = `1`**：插件的 `Plugin-Requires` 必须等于它，否则拒绝安装/启用（`PL_INCOMPATIBLE`）；插件不得重复打包宿主已提供的依赖（Jackson / OkHttp / networkjit… 见 `conflictsOf`），命中即拒绝（`PL_DEPENDENCY_CONFLICT`） |
| 9 | **声明与实现分开**（丙）：工具清单/schema/技能清单随会话快照冻结；端口实现与编排实时生效 |
| 10 | **让渡与保留**：让渡 = 进程内无沙箱/无强杀、D09 只对默认实现成立、会话内行为不保证可复现、`RuntimePolicy` 不再是唯一来源；保留 = 事实只追加、落盘只经 `CommitScope`、聚合合法迁移、`Budget` 只累加、**副作用审批** |

**明确不做**：沙箱/进程外插件、插件市场与签名、热升级（同 id 换 jar）、插件间依赖解析的高级策略（只用 PF4J 的 `Plugin-Dependencies` 基础能力）、插件改领域模型。

**已知风险（记录在案）**：① 进程内插件权限 = 用户权限，唯一防线是"用户自己写"；② `ModelInvocationPort` 可被替换 ⇒ 插件能读全部 provider 密钥；③ 卸载后类可能泄漏（靠"升级即重启"缓解）；④ 插件锁定内部 API（`SessionRunner`/`RunContext`）后，我们改默认编排会破坏它——L3 标 `experimental`、不承诺跨版本兼容。

**影响面**：`模型图`（§一/§三/§四/§5.9/§八）、`模块-行动`（聚合/端口/§7.1/§7.6/§8.1）、`模块-规划`（`SessionRunner`/`RunOutcome`/`RunContext`）、`模块-应用层`（第 7 个用例、`PluginAssembler`、T15/T16）、`模块-基础设施层`（两个适配器、目录、§11）。

## D25 本地工具与工作区根：8 个 `NATIVE` 工具 + 启动目录即工作区 + 命令绊线

**状态**：已定（M45）

**背景**：内置 5 个工具全是编排类，读不了一个文件、跑不了一次测试——**会说不会做**。要让它在真实项目里干活，必须补上"看 → 改 → 验 → 查"的闭环；而只要能写文件、能跑命令，就必须同时回答"手能伸多远"和"什么情况下先问人"。

**选项**

- A. 只补只读工具（`read_file`/`grep`/`list_dir`），改动交给用户自己做——安全，但没有闭环。
- B. 全量补，写与命令一律逐次审批——闭环有了，但一次任务问几十次，人会开始闭眼按 y，闸门退化成形式。
- C. **补全 8 个工具，把审批按"破坏半径是否有界"分档**：有界（路径先过工作区校验）⇒ 整包信任；无界（shell）⇒ 默认放行 + 高危绊线。

**结论**：**C**，配九条约定。

| # | 约定 |
|---|---|
| 1 | **工具集 = 8 个**：`read_file` / `list_dir` / `grep` / `fetch_url`（只读）、`edit_file` / `write_file` / `delete_file`（写）、`run_command`（不可逆）。`delete_file` 存在的理由是**减少绕过动机**——没有它，模型会改用 `run_command` 里的 `rm`，那条路无法校验路径 |
| 2 | **来源标记 `NATIVE`，执行仍走同一张处理器注册表**（与 D24-3 对 `PLUGIN` 的裁决同构）：不新增处理器接口、不新增端口、`ExternalToolPort` 不再承担 `NATIVE` |
| 3 | **工作区根 = 进程启动时的工作目录**，启动时求一次 `toRealPath()`，**不做配置项**；所有本地工具路径必须落在根内（相对拼根下、绝对也必须在根内、判定基于 real path、目标不存在判父目录）；越界是普通工具错误结果 |
| 4 | **审批按破坏半径分档**：只读四个免审；写三个首次问一次"允许本会话在此工作区内**写入与删除**文件？"，同意后记在**运行期的按会话信任集**里（进程内、会话间隔离、退出即失效，**不落盘、不进 `RuntimePolicy`**）——持久信任一条写权限是用户自己该做的决定，不该由一次点击替他做；`run_command` 不走这一档 |
| 5 | **`run_command` 默认放行 + 绊线**：命中毒性特征、**或解析失败、或 `sh -c` 嵌套超 2 层 ⇒ 审批**（fail-closed）。命中即审批、不拒绝；文案带规则名与原始命令 |
| 6 | **判定不用正则，用浅结构解析**：引号消解后得到每段的 `程序 / 参数集合 / 操作数 / 重定向` 与段间拓扑，`sh -c` / `eval` 的实参递归解析。**危险是结构性的**，字符串模式匹配会在引号、参数顺序、嵌套三处同时误判与漏判 |
| 7 | **解析器是安全组件，纪律是"只做加法"**：解析成功 + 判定项全过才放行；任何异常路径落到审批。**解析器的 bug 只能导致多问，不能导致少拦** |
| 8 | **硬限制**（都走规则 6 截断 + 归档）：行数、条数、深度、字符数、超时；`run_command` 超时**杀进程树**，只回尾部 200 行 + 退出码 |
| 9 | **让渡三条**：① `run_command` 默认放行——I3 的宾语从"每个不可逆动作"变成"看起来危险的动作"；② `run_command` 可绕过写入审批（重定向、`sed -i`、子进程）；③ 无沙箱——`run_command` 能 `cd / && rm -rf`，工作区根是**防手滑**不是**防恶意** |

**明确不做**：`git` 独立工具（被 `run_command` 覆盖）、`apply_patch`、`move_file`、软删除/回收站（偷偷备份会让人以为可撤销）、POSIX 与 Windows 命令语法的双实现（按 POSIX shell 判定）。

**已知风险（记录在案）**：① 绊线拦不住动态拼接、间接执行与**项目自己的脚本**（`npm run build`、`mvn clean`）——这几类恰好是最常见的真实事故；② `delete_file recursive=true` 对子目录是一次全灭，落在"已信任工作区"语义内，与 `edit_file` 覆盖文件同量级；③ 解析器是自研安全组件，语法覆盖不全即等于放行面变大（由 fail-closed 兜住）。

**影响面**：`模块-行动`（§3.1 工具表、§5 三个 VO/Port 行、§7.1 规则 5/9/10、§8.1 漏斗与绊线图）、`模块-应用层`（§5.1 `CommandParsing`/`CommandRules`、§6 `ExternalToolPort` 口径）、`模块-基础设施层`（§3.2、jar 内 13 份工具声明）、`技术决策`（D04 包树）。
