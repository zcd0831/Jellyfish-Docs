第 4 章

感知模块

感知模块只回答一个问题：模型此刻能看到什么。 它把「外部输入」（你、工具结果、模型输出、技能注入）和「运行环境」（全局策略、模型能力、可用工具清单） 变成一条可追溯的上下文流水，长了就折叠。

聚合 2 领域服务 4 端口 1（声明） 领域事件 4 应用事件 1

4.1模块定位与边界

方向内容
本模块聚合Session、RuntimePolicy
本模块声明的端口（由外部实现）ModelInvocationPort（由【基础设施层】ModelInvoker 实现：选模型 / 降级 / 调用 / 计量 / 提供模型档案）
本模块对象所在的层领域层：Session、RuntimePolicy、SystemPromptAssembler；应用层：ContextWindowService、SessionTitleGenerator、StartSessionUseCase（见 第 8 章）
被本模块引用的外部 ID（仅 ID）AgentId、ModelId、ToolId、SkillId
被外部引用的本模块对象Session（被规划持有 sessionId、被行动持有 rootSessionId）、RuntimePolicy（被规划 / 行动 / 记忆只读）
依赖纪律

SystemPromptAssembler 不自己去查工具/技能定义——内容由调用方（外循环 / 应用层）取好作为入参传入； 模型调用一律走 ModelInvocationPort。这样感知模块不依赖任何其它模块的具体实现。

4.4聚合清单

聚合简介不变量
Session 一次会话（可嵌套）的全部上下文事实：记录流水、系统提示词快照、窗口与摘要。由 parentSessionId 组成会话树 ① Record 只追加，不得修改、不得删除；② 快照在会话开启时冻结，运行中不再变；③ Agent 不可切换，Model 可切换；④ 父会话终止时级联终止子会话；⑤ 没有状态：会话是持久化容器，存在即可用
RuntimePolicy 全局唯一的运行环境策略，只有用户能改，立即生效 ① 全局唯一；② 不进会话冻结快照；③ 参数只能由用户调整

简介
会话族的一个节点。承载"模型能看到的世界"：SystemPromptSnapshot + Record 序列；窗口与用量由 buildContextForLlm() 推导产出，不落库。
关联
agentId、activeModelId（行动）、parentSessionId（自身）、Record（内部）

4.5领域服务清单

服务层简介跨模块依赖

4.7领域事件

事件谁发出什么时候

4.8聚合生命周期与规则

4.8.1 Session 的生命周期

诞生变更终结重建
会话开启（用户发起对话）
子代理派遣（spawn_subagents）		 迭代中不断追加 Record；上下文折叠；模型降级；终止 归档（压成 zip 移走，应用不再可见）
会话销毁（物理删除）		 会话续跑（按 sessionId 加载，StartupReconciler 先对账）

规则清单（23 条）

  1. 唯一创建入口：只有应用层 StartSessionUseCase 能创建会话；两个触发点——用户发起对话、主会话发起子代理。创建成功后 Session raise SessionStarted（由应用层提交后派发，只供界面 / 审计，不驱动任何动作）；内部 fork 型子会话（反思 / 沉淀）不发——它不进会话列表（8.9.7），事件只为“界面上看得见的会话”而发。
  2. 创建时必须指定 agentId 与 modelId（缺省取默认）；Agent 在会话内不可切换，Model 可切换（降级或用户显式切换）。切换只允许在工具轮已闭合之后：存在未拿到结果的 TOOL_REQUEST 时拒绝切换（模型私有状态无法跨模型/跨厂商续接）。
  3. 标题：由 LLM 依据首次输入的意图生成；失败则用首句截断兜底。
  4. 快照冻结：SystemPromptSnapshot 在会话开启时生成并冻结（内容快照）；运行中工具/技能定义变更不影响进行中的会话。 技能有两层，冻结的只有浅层：可见清单（哪些 skillId）+ 三件套（name / description / triggerCondition）冻结；SOP 正文不冻结——load_skill 每次现读 SKILL.md，因此同一会话前后两次 load_skill 可能拿到不同正文（技能被改进时）。这是有意接受的漂移：正文是外部资产，不是会话事实，也不受 Record 的 append-only 约束。会话中途新沉淀的技能不进当前清单，下个会话才可见。
  5. 流水只追加：Record 不得修改、不得删除（本地应用的磁盘控制只能靠归档 / 导出）。
  6. 会话树：parentSessionId 组树；父会话终止 ⇒ 级联终止所有子会话（终止信号经令牌传到子会话，见第 8 章 8.9.4.1）；子代理不得再开子代理（深度恒为 1）。
  7. 没有状态：sessions/<id>/ 存在即可用，不存在即不可用（含已归档，见《模块-感知》§7.1 规则 7）。“在跑”是进程内事实，不落盘；归档 = 压成包移走，此后应用不再认识它。删除 = 物理消失。续跑是重新装载既有事实，不是状态迁移，因此不重发 SessionStarted；界面要提示“续跑中”用应用事件 SessionResumed（见 4.7）。
  8. 销毁：物理删除该会话族的 Record、Plan、Budget；已沉淀的 Experience 保留（记忆模块全局资产）。
  9. 上下文组装（buildContextForLlm(policy)）是两区 + 累积窗口，没有“条数上限”：
    • 不可变区 A = SystemPromptSnapshot：不落 Record、随会话冻结、永远占据请求的 system 字段、不参与任何裁剪，也不进摘要素材。它跨请求逐字节一致，因而成为提示词缓存的稳定前缀（折叠也只作废可变区，不动这一段）。
    • 可变区 B = 全部 Record 流水，含 role = SYSTEM 的运行期注入（SOP 注入 + 工具注入 + 经验注入）；经验注入由外循环在步骤启动前写一条带 step=<id> 标记的 SYSTEM 记录，正文来自 ExperienceRepository.find(id)，同一步只注入一次。
    • 窗口记录 = 最新一条 SUMMARY（若有）+ sequence > summaryCoversUpTo 的全部 B 区记录，按 turnId 整轮对齐（规则 14）；不设条数上限——前沿（覆盖边界）固定，后沿随对话持续下移，直到折叠把窗口收回配置条数（见 4.9.2）。
  10. SUMMARY 不参与轮对齐与条数计数；role = SYSTEM 的注入记录参与窗口，但同样不参与整轮分组。SYSTEM 注入只能被覆盖边界淘汰（折叠时随区间一起进摘要并要求保留其要点），不再有“系统占比超限整体降级”——原第 ④ 步与 systemRatioLimit 已废弃。
  11. 可推导状态不落库：窗口边界与用量都是推导结果，不持久化；会话续跑时重新推导。例外：SUMMARY.summaryCoversUpTo 是“这份摘要覆盖了哪些记录”的事实，不可重算，必须落库。
  12. 窗口推导不读任何配置：buildContextForLlm(estimator, inputCeiling) 只接收计量器与有效上限，既无策略值对象、也不引用 RuntimePolicy；需要阈值的地方（折叠、保留条数）全在应用层判定。
  13. 系统提示词与流水分离：system 字段只有冻结快照；SYSTEM 记录只承载运行期注入（load_skill 的 SOP、工具/经验注入），发给模型时并入 messages、按 sequence 归位（与普通记录同受覆盖边界约束）。快照不参与裁剪，也不进摘要素材——它是缓存的稳定前缀。
    “当前步骤”这类运行期时序提示例外：它由 Plan 推导，不落 Record，每次请求以一条瞬时尾部消息追加在 messages 末尾（“当前步骤（第 N 步）：…”）。判据不是“可推导所以不许记录”——“当时模型被告知了哪一步”在重划之后并不可重算，它是真事实；判据是提示与注入的语义不同：load_skill 的 SOP、工具 / 经验注入是信息增量（窗口里原本没有，不落库就永久丢失 ⇒ 必须落）；“当前步骤”与摘要指令是信息重述（内容已在 Plan / 窗口里，每轮重建即可复原，不落库零信息损失）。 落进 append-only 流水等于给它加上“永久有效”的语义，代价是真实的：同一 step 的每次内循环请求各追加一条（maxReActRounds 默认 20），重划后新旧“第 N 步”并存，模型看到的是互相冲突的现行指令而不是历史；这些 SYSTEM 记录参与 collapseRetainRecordCount 的条数计数（规则 10 只把 SUMMARY 排除），一个用满轮次的 step 就能把保留区占满、把真正的工具结果挤出去；而且每轮请求多一次落盘提交。时效性只能靠“每轮重建”表达，append-only 流水没有“仅当轮有效”这个维度——要支持它就得给 Record 加时态字段，并为窗口推导 / 折叠 / 摘要素材 / Attempt.recordRange 全部补一条过滤规则。
  14. 模型输出轮是窗口的原子单位：一轮 = [ASSISTANT] + (TOOL_REQUEST + TOOL_RESULT)⁺（无工具调用则只有 ASSISTANT）。折叠划定保留区时不得切在轮中间：首条落在一轮中间 ⇒ 把该轮起点整轮拉进保留区（collapseRetainRecordCount 是软上限）；尾部出现未闭合的 TOOL_REQUEST ⇒ 不变量违反（不静默修补）。理由：请求合法性的最小单位是这个轮，不是单条记录。
  15. 模型私有状态只回放给产者：reasoning（DeepSeek 的 reasoning_content；Anthropic 的签名 thinking、Gemini 的 thoughtSignature 同理）是模型私有状态，必须与 producerModelId 一起记录。回放规则：只有目标模型 == producerModelId 时才回传；切换模型后旧状态一律丢弃（签名/语义都不可跨模型搬运）。它计入 token 计量（真占输入），不进摘要、不进展示；fork 型子会话会按同模型回放规则看到它（沉淀/反思的“素材即窗口”，见《模块-记忆》§7.9.6）；半截输出不落（流式中断 ⇒ 整条 assistant 输出连同 reasoning 都不落）。
  16. 一个响应 = 一条 assistant 消息：同一 turnId 的 content（若有）与全部 tool_calls 在回放时必须合成一条 assistant 消息，其 TOOL_RESULT 按 callId 顺序紧随其后；不得把一个响应拆成“文本一条 + 每个调用一条”。这是 OpenAI / Anthropic / Gemini 共同的原生形态，拆开会被端点拒绝（错误文案可能完全与形态无关）。
  17. 最新 SUMMARY 必须真的发给模型：它由窗口推导带出，调用方（ReActLoop）把它作为一条 user 消息放在 messages 最前；只参与计量不发出去，等于折叠后模型完全丢失历史。
  18. 折叠判定挂在内循环每一次模型请求之前，不是“每个外层迭代一次”；并且 messages 必须按最新窗口每轮重建——否则一次内循环里的多轮工具调用会把请求撑爆，折叠了也用不上。触发条件是 usedTokens + 摘要指令估算 > inputCeiling（摘要请求 = 主请求 + 指令，必须把指令 token 算进去）。
  19. 摘要是“影子主请求”：同一快照、同一 tools 快照、messages = 当前窗口 + 末尾追加一条 user 摘要指令。指令不落 Record；模型回复只用于生成 SUMMARY，不落 ASSISTANT 记录、不生成 turnId、不参与轮对齐。指令必须放在末尾（放最前会破坏缓存前缀，也会被长对话淹没）。
    指令不落库的理由同规则 13：它是对已有窗口的处理请求（信息重述，不是新事实）。落库会让它以“永久有效”的姿态常驻窗口——下一次普通请求模型就会照着再摘要一遍（自噬）；它也不是执行证据，进 Attempt.recordRange 会污染区间（依据同规则 23 排除 SUMMARY 的口径）。
  20. 折叠后窗口回落到配置条数：保留区 = 覆盖边界之后最近的整轮、累计记录条数 ≥ collapseRetainRecordCount；summaryCoversUpTo = 保留区前一条的 sequence，且单调不减。新摘要吞并旧摘要（素材天然含旧摘要正文——它本来就在窗口最前），旧 SUMMARY 记录留在流水里但不再进窗口。
  21. 摘要指令必须要求保留：用户目标与约束、已确认事实、已完成的步骤及其结论/失败原因、已做操作与结果、待办、已加载技能与经验要点。理由：沉淀与反思只 fork 当前窗口，长计划早期步骤的原文已被折叠，证据只能来自摘要（见《模块-记忆》§8.6）。
  22. 折叠失败分两种，不可合并处理：① 因输入超限失败 ⇒ 从待摘要区间的最旧一整轮开始丢弃素材后重试，被丢弃的区间必须在摘要正文里声明“更早的 N 条记录（seq a..b）因超出输入上限未纳入摘要”；丢弃不得触及保留区。② 因模型不可用/终止 ⇒ 返回、不推进任何状态、不落半截 SUMMARY、不丢任何记录。
  23. 折叠只能发生在工具轮闭合之后、下一次请求之前：折叠边界必须落在轮边界，否则窗口里会留下"半截工具轮"、请求直接非法（规则 14）。摘要请求里模型若返回 tool_calls ⇒ 不执行，按摘要失败处理。

4.8.2 RuntimePolicy 的生命周期

诞生变更终结重建
平台初始化（应用启动载入默认值） 策略调整（用户修改，立即生效） 无（应用生命周期内常驻） 平台初始化

规则清单（8 条）

  1. 全局唯一，只有用户能调整；任何 Agent 都不能覆盖。
  2. 立即生效、不进会话快照：与"工具/技能定义、系统提示词在会话开启时冻结"形成对照。
  3. 反思阈值与最大重试独立配置：reflectionThreshold > maxRetries ⇒ 永不反思。
  4. 唯一硬闸 maxReActRounds：按"自上次用户输入以来的连续轮数"计，用户介入即重置。
  5. 信任清单：工具级粒度，语义 = 免审批，可覆盖不可逆工具；未命中且工具非只读 ⇒ 执行前放行审批。
  6. 预算参数：单位 token、只预警不中断、同一会话族只报一次。
  7. 变更即通知：adjust() 成功后 raise PolicyAdjusted，避免其它模块各自缓存常量快照。
  8. 聚合不变量不依赖自身取值：策略只改变"外循环选择哪条迁移"，不改变任何聚合的合法状态迁移。

4.9领域服务的具体操作

4.9.1 Session.create(...)（领域工厂）

会话开启的端到端时序见 第 8 章 8.9.2 StartSessionUseCase.start(...)，此处不重复。感知模块只负责其中的两件事：

  • Session.create(agentId, modelId, snapshot)：领域工厂方法——造聚合、定初始状态 RUNNING、挂已冻结的快照；
  • SystemPromptAssembler.assemble(...)：内容快照的纯组装（见 4.9.3）。

预算创建、标题生成、持久化与提交都在应用层；startSubSession 由应用层 SubagentLauncher 调用，不自建 Budget（沿 parentSessionId 上溯到根）。

4.9.2 ContextWindowService.ensureWithinLimit(session)（应用层）

在内循环每一次模型请求之前保证上下文不超限；必要时折叠。方案是“累积窗口 + 折叠收回”：前沿固定在摘要覆盖边界，后沿随对话持续下移；一旦估算用量（含摘要指令）超过有效上限，就把窗口收回配置条数。

sequenceDiagram
    autonumber
    participant IL as 内循环 ReActLoop
    participant CW as ContextWindowService
    participant RP as RuntimePolicy
    participant PORT as ModelInvocationPort（行动）
    participant S as Session

    IL->>CW: 每次模型请求前 ensureWithinLimit(session)
    CW->>RP: summarizationTokenThreshold / collapseRetainRecordCount / inputSafetyMargin
    CW->>PORT: describe(activeModelId) 取模型档案
    CW->>CW: inputCeiling = min(策略阈值, maxInputTokens − inputSafetyMargin)
    CW->>S: buildContextForLlm(estimator, inputCeiling)
    S-->>CW: ContextWindow（窗口记录 + ContextUsage）
    alt usedTokens + 摘要指令估算 ≤ inputCeiling
        CW-->>IL: 直接返回，按当前窗口发请求
    else 需要折叠
        CW->>CW: 保留区 = 覆盖边界之后最近的整轮<br/>累计条数 ≥ collapseRetainRecordCount（软上限）
        CW->>CW: 待摘要区间 = 旧 SUMMARY 正文 + 覆盖边界之后到保留区之前的记录
        CW->>CW: 应用事件 SummarizationStarted（界面显示“压缩中”）
        CW->>PORT: invoke(影子主请求)<br/>同一快照 + 同一 tools + 窗口 + 末尾摘要指令<br/>指令不进 Record
        PORT-->>CW: 摘要文本（token 记账到会话族根）
        CW->>S: markSummarized(summary, 保留区前一条 sequence)
        S->>S: appendRecord(SUMMARY)<br/>窗口下次推导自动排除被覆盖记录
        S-->>CW: raise SummarizationCompleted
        CW-->>IL: 返回（窗口回落为：新 SUMMARY + 保留区）
    end

要点（12 条）

  1. 触发点在内循环每一次模型请求之前（不是每个外层迭代），且 messages 必须按最新窗口每轮重建：否则一次内循环里的多轮工具调用会一路把请求撑爆，折叠了也用不上。
  2. 摘要是影子主请求：同一快照、同一 tools 快照、messages = 当前窗口 + 末尾一条 user 摘要指令。指令不进 Record（理由见 4.8.1 规则 13：提示是信息重述，不是事实；落库会让它常驻窗口并诱发重复摘要）；回复只用于生成 SUMMARY，不落 ASSISTANT 记录、不生成 turnId。指令必须在末尾：放最前会破坏缓存前缀，也会被长对话淹没。
  3. 触发条件必须计入指令：usedTokens + 摘要指令估算 > inputCeiling。否则摘要请求总比它要解决的那个请求先超限。
  4. 折叠就是“把窗口收回配置条数”：保留区 = 覆盖边界之后最近的整轮、累计记录条数 ≥ collapseRetainRecordCount（软上限，默认 20）；summaryCoversUpTo = 保留区前一条的 sequence，且单调不减。折叠只发生在工具轮闭合之后。
  5. 新摘要吞并旧摘要：素材 = 旧 SUMMARY 正文 + 覆盖边界之后到保留区之前的全部记录（含 SYSTEM 注入）。旧摘要本来就在窗口最前，所以“吞并”天然成立；旧 SUMMARY 记录留在流水里但不再进窗口。
  6. 摘要指令必须要求保留：目标与约束、已确认事实、已完成的步骤及其结论/失败原因、已做操作与结果、待办、已加载技能与经验要点（沉淀与反思只 fork 当前窗口，早期证据只能靠它）。
  7. 失败分两种：① 因输入超限失败 ⇒ 从待摘要区间最旧一整轮开始丢素材后重试，被丢区间必须在摘要正文里声明（不得触及保留区）；② 因模型不可用/终止 ⇒ 返回、不推进状态、不落半截 SUMMARY、不丢记录。
  8. 有效上限 = min(summarizationTokenThreshold, maxInputTokens − inputSafetyMargin)（inputSafetyMargin 默认 10000）。它的语义是“主请求与摘要请求共用的安全余量”（抵御估算偏差、摘要指令与快照边角），不是输出预留——输入与输出是两个独立上限。
  9. 计量口径唯一：本服务不自己实现 tokenizer，一律经 ModelInvocationPort 计量；摘由当前会话模型生成，token 记到会话族根。摘要请求里模型若返回 tool_calls ⇒ 不执行，按失败处理。
  10. 承接“请求超限”的补充折叠：行动 ModelInvoker 抛「请求超限」时，外循环调本服务强制折叠一次再重试；不消耗重试名额；仍超限则同“模型不可用”返回并提示。这条与前置判定要去重，同一轮不得折两次。
  11. 摘要必须进请求：最新 SUMMARY 由窗口推导带出，ReActLoop 把它作为一条 user 消息放到 messages 最前（固定前缀）；只记账不发送等于折叠后丢失全部历史。
  12. 折叠不写 reasoning：被折叠的旧工具轮不再进窗口，它们 reasoning 也不需要回放；摘要文本里不得包含 reasoning（只汇总可见内容与工具结果）。

4.9.5 Session.buildContextForLlm(estimator, inputCeiling) → ContextWindow（领域）

把"记录流水"推导为"本次发给模型的窗口 + 用量"。它是纯函数式的推导行为：不改状态、不落库、不读配置聚合。
