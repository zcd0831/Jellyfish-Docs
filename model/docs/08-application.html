第 8 章

应用层

应用层回答一个问题：一次用例，按什么顺序、在什么事务里、通过哪些端口，把领域对象推动起来。 它不含业务规则（规则在领域层），也不含技术细节（文件、网络、终端都在基础设施层）。

一句话：领域层只决定，应用层只执行。

用例 6 应用组件 12 端口 21 不含业务规则

8.1定位与边界

方向内容
本层对象7 个用例服务 + 15 个应用内组件
本层依赖领域层（聚合方法、领域服务、领域策略）——只读调用，不实现规则；23 个端口（只认接口）
谁依赖本层外壳（本期只做 TUI；端口契约不变）只调用例服务
本层不负责状态机与不变量（领域层）、文件与网络与终端（基础设施层）
三条纪律
  1. 用例服务里不写业务判断——"算不算完成""该不该淘汰""哪些层要验证"，都问领域对象；
  2. 绝不跨 IO 持事务——模型调用、工具执行、ask 阻塞、子代理 join 全在提交之外；
  3. 本层不出现 File、Path、HttpClient、System.out——一切经端口。

SessionToolScope会话作用域工具白名单：声明本会话允许调用哪些工具（默认空、fail-closed）。fork 型子会话（反思 / 沉淀）、“结论交付”轮与重划调用（白名单 = {replan_plan}）共用这套闸门；由 ToolExecutor 在合法性校验阶段执行；白名单显式授权的工具不受“代理绑定”限制（授权优先）。越权 ⇒ 返回失败 TOOL_RESULT（不抛异常，否则工具轮不闭合）；连续 N 次越权 ⇒ 结束会话

ProgressEvent 是 ProgressPort 的入参值对象（Kind + message），面向界面、可丢弃，不属于领域事实。

Kind 共 13 种，按用途分三类：阶段类（SUMMARIZING / SUMMARY_DONE / RETRY_SCHEDULED / MODEL_SWITCHED / SUBAGENTS_RUNNING）、计划类（PLAN_CREATED / PLAN_REPLAN / STEP_STARTED / STEP_FINISHED）、工具类（TOOL_STARTED / TOOL_FINISHED），外加用量类 USAGE 与上下文类 CONTEXT_USAGE。约定：

  • 计划类事件的 message 必须带进度：计划：<goal>（N 步）、重划（第 2 代）：<goal>（4 步）、第 3/5 步：<描述>、第 3/5 步 完成/失败（原因）。步数只计未被 SUPERSEDED 的步骤（重划会保留被替换的旧 step，算进去会让 N 越来越大）；
  • 计划播报按 planId 去重，不是“每次 run 一次”：同一次 run 里前一个计划完结（或失败）后，模型可以在“结论交付”轮里再次 generate_plan，那是新的 planId，必须重新播报 PLAN_CREATED 并重新分配经验；重划不改变 planId，只用 PLAN_REPLAN、不发 PLAN_CREATED；
  • 工具类事件的 message 必须带工具名与结果：read_file（参数摘要）、read_file 成功 12ms / read_file 失败：原因；ask_user 不重复发（问题本身已呈现）；
  • USAGE 的 message 带本轮与累计用量：+1.2k / 累计 3.1k / 上限 1.0M；
  • CONTEXT_USAGE 的 message 带“最近一次请求的输入用量 / 模型输入上限”：18.2k / 50k。数值是 Budget.lastPrompt*——厂商返回的 prompt_tokens（精确值），厂商没给时为本地估算并加 ≈；没有可用的观测（新会话、刚折叠、换了模型）时为 — / 50k。每轮组装上下文后、以及主循环每次响应记账后各发一次（后者让界面立刻看到本轮实际用量），供界面在一轮结束时的汇总行里展示；折叠判定仍用请求前的估算，两者不混用；
  • 外壳按 Kind 决定呈现方式（状态行 or 常驻行），应用层不关心排版。

相对早期设计的两处收缩
NATIVE 不进任何端口
NATIVE 工具由基础设施实现 InternalToolHandler 并注册进同一张处理器注册表（行动 5.9.1）。路径能否落地由基础设施的 Workspace 保证，判定"要不要审批"由本层的 CommandParsing / CommandRules 负责——这是应用层唯一出现 shell 语义的地方。

8.8事务与提交顺序

8.8.1 文件系统没有跨文件原子性，所以用「顺序 + 幂等 + 对账」代替

CommitScope 的契约：应用层只管 stage 要写什么，执行顺序由基础设施强制：

① 不可变事实（reports / reflections / experience 新文件）
② 追加流水（records-NNNN.jsonl 追加一行）
③ 替换聚合（meta.json / plans/*.json / budget.json / settings.json）

这样任何崩溃点都只落在「事实已存在、状态未推进」，永远不会出现「状态推进了、事实不存在」。恢复方向因此是单向补齐。

全局资产写段
T11 / T13 / T14 都在 CommitScope 的全局资产写段内执行：并行子会话可能同时沉淀，容量"读—判—写"必须在该段内完成。一次计划完结中，T11 与 T13/T14 至多发生一个（同一件事只进一边）。
环境故障时的 T4：本轮已发出、还没拿到结果的工具调用，由 ReActLoop 在异常上抛前补一条 TOOL_RESULT（内容为“本轮中止：…”）；它是流水事实，不是状态推进，因此不占用 T7，也不消耗重试。
沉淀幂等键在写入侧：T11/T13/T14 写入前先比对来源 planId（经验可多值 sourcePlanIds），已包含则整段跳过——包括 T17 的告知记录。流水里的 planId 标记只负责“不重复播报”，不能当作唯一幂等凭据（落盘成功、写记录失败时标记并不存在）。
T17 的顺序不可颠倒：先落盘、后告知。反过来会出现“模型告诉用户已沉淀、资产却没落盘”。
T12（会话状态）也承接模型切换：SwitchModelUseCase 只改 meta.json 里的 activeModelId 并派发 ModelSwitched；它不动流水——旧模型的 reasoning 靠 producerModelId 在回放时自动失效。

8.8.3 三条纪律

  1. 绝不跨 IO 持事务——模型、工具、ask、子代理 join 全在 commit() 之外。
  2. 事件在提交后发，且不得驱动任何 IO 长任务；沉淀/检索由 ExecutionLoop 显式调用。
  3. 一个事务只服务一个用例的一次状态转移，不为了"少提交一次"而合并不相关的写。

8.9.4.1取消令牌怎么到阻塞点

外壳创建并持有唯一实现（本期 ShellCancellationToken，每轮开始复位）；ManageSessionUseCase.cancel 与 Ctrl-C 都调它的 cancel()。令牌只下传到轮次边界：RunSessionUseCase.run(..., token) → ExecutionLoop 每轮开头检查，命中即抛 CancellationException，走 8.9.4 的 Cancelled 分支。

重试的终止不靠令牌，而靠传输层的取消标记：Call.cancel() 之后 HttpJsonClient 记下“本次调用被用户取消”，ModelInvoker 见到这个标记直接抛 CancellationException（不重试、不降级）。这样令牌不必穿进 ContextWindowService、VerificationRunner、ExperienceRetriever、ExperienceDistillationService——它们都在轮次内，在途请求同样被立刻打断，只是“不再重试”由传输层保证。轮次外的调用（SessionTitleGenerator、测试复跑）拿不到令牌，用“永不取消”的 CancellationToken.never()。

取消是终态：不进重试、不降级、不弹错误（取消不是错误，见《模块-应用层》§9）。会话没有状态，取消只把 plan 里 RUNNING 的 attempt 置 INTERRUPTED（见《模块-感知》§7.1 规则 7）。

flowchart LR
    K["Ctrl-C / ManageSession.cancel"] -->|cancel| T["ShellCancellationToken（外壳持有，每轮复位）"]
    T -->|onCancel| H["HttpJsonClient.cancelActive()：在途读立刻失败"]
    T -->|throwIfCancelled| R["RunSessionUseCase.run(..., token)"]
    R --> E["ExecutionLoop 每轮开头检查"]
    E --> X["CancellationException"]
    H -->|传输层取消标记| M["ModelInvoker：不重试、不降级"]
    M --> X
    X --> C["Cancelled 分支：不弹错误"]
    C --> S["attempt = INTERRUPTED + SessionCancelled"]

8.9.4.2查看 / 回放（transcript(sessionId, limit)）

ManageSessionUseCase.transcript(sessionId, limit) 是只读分支：会话头 + 最近 limit 条记录（多取一条判断“还有更早的”），返回 SessionTranscript。外壳用它实现“打开历史会话时把以前的对话显示出来”；它不参与上下文组装（模型侧窗口由 ContextWindowService 推导），也不改任何状态。

回放口径由外壳决定：只展示用户与助手正文，工具调用压成一行、摘要一行、SYSTEM 注入与 reasoning 不展示（reasoning 是模型私有状态，只回放给产者）。

视图同时带上 contextLabel（“最近一次请求的用量 / 输入上限”，取 Budget.lastPrompt*，见第 5 章 5.9.4）：打开历史会话时可用来展示；没有观测时是 — / 50k。

要点

  1. "安装"与"授权"分开：装只落自己的 plugin.json（trusted=false、granted=∅），插件此时还没有任何效果；授权才让它进入世界。
  2. 信任只发生在安装：trusted 一旦为真不再变（要收回就卸载重装），这是"安装时一次同意"的落点。
  3. 冲突在授权时判，不在安装时判：两个插件可以都声明 Clock，但只有一个能被授权。
  4. 真实生效靠 PluginAssembler：用例只改"意图"，装载/卸载与路由表切换在装配层完成——所以插件崩溃或加载失败不会污染授权意图。

8.9.7 fork 型子会话（反思 / 沉淀）与落盘播报

反思与沉淀不再是“组装一段素材再调一次模型”，而是把父会话的生效窗口原样 fork 成内部子会话（sub/<id>/，与子代理会话同构、无 budget.json），只在末尾追加不同指令。这样信息量完整，且能命中父请求写下的提示词缓存前缀。

子会话的四条硬约束

  1. 只走内循环：由 InternalSessionRunner 直接跑一次 ReActLoop，不建 Plan、不进 plans/、不触发验证、不可再 fork（工具白名单为空即无 spawn_subagents；反思/沉淀失败也不得再触发反思/沉淀）。
  2. 它是普通子会话，不是一个新字段：落在 sessions/<root>/sub/<id>/，由此天然不进会话列表、不参与父会话的沉淀递归；不需要在 meta.json 里加标记。
  3. 工具快照不可变：为保缓存前缀，tools 原样拷贝父会话快照（哪怕大部分用不到）；限制靠 SessionToolScope 白名单在执行层拦，越权返回失败 TOOL_RESULT。
  4. 提示词追加在末尾 user：system 保持快照；末尾 = 反思/沉淀指令（+ 反思时带上失败原因）。代理的 basePrompt 也归入末尾指令，不得作 system，否则前缀作废。
  5. 只产出 Draft，不写任何状态：产物是一段结构化文本（经验草案 / 技能草案，互斥二选一），由父侧解析。子会话流水只作审计，不作证据；用量经 settleFromSubSession 归集，不写 prompt 观测。

8.10错误与恢复策略

情形语义应用层动作聚合落点
工具自身失败（超时/异常/半截）一种工具结果回灌模型，ReAct 继续只追加 TOOL_RESULT
模型不可用（备用链全挂）环境故障RunSession 立即返回；不触发反思/重划/重试；把本轮未闭合的工具调用补记为中止 TOOL_RESULT不推进 plan / budget；Attempt 不落终态；流水多一条中止事实
请求超限业务预算问题强制折叠一次后重试；仍失败按模型不可用处理追加 SUMMARY，不动 plan
摘要请求失败分两种，不可合并① 输入超限：从待摘要区间最旧一整轮开始丢素材重试，摘要正文声明被丢区间；② 模型不可用 / 取消：返回、不推进状态、不落半截 SUMMARY、不丢记录① 追加 SUMMARY（带覆盖边界）；② 无
重划失败（未调 replan_plan / 校验不过 / 模型不可用）重划用尽不再重划，直接 terminate()；随后沉淀 + 结论交付轮（若还能发请求）Plan.terminate()
结论交付轮失败尽力而为静默收敛，RunOutcome 不变；不得触发新的反思/沉淀无（结局已定）
fork 型子会话越权调用工具作用域限制返回失败 TOOL_RESULT（“该工具在本会话不可用”）；不弹审批；连续 N 次 ⇒ 结束该子会话无
沉淀 Draft 不可解析 / 互斥冲突本次不产出不落盘、不写告知记录、不播报；会话继续无
用户中断用户主动ask 返回 CANCELLED；当前 attempt 收尾Attempt.outcome = INTERRUPTED（不耗重试）
切换模型被拒（工具轮未闭合）用户操作与回合边界冲突返回 S_TOOL_ROUND_OPEN，不改任何状态；提示等本轮收尾后再切无
崩溃残留进程非正常退出StartupReconciler 按下列 5 条补齐视规则而定

StartupReconciler 的 5 条规则

#现场补齐动作
1有 PASSED 报告，但 step 仍 RUNNING / VERIFYING按报告里的 attemptNo 补 markStepSucceeded
2有 FAILED 报告，但 step 仍 RUNNING补 markStepFailed
3流水末尾有 TOOL_REQUEST 无 TOOL_RESULT该 attempt 判失败（计一次重试）；环境故障已在 ReActLoop 内补记中止结果，不会落到这条，这里只接崩溃/强杀残留。该半截请求无法回放，本期不做回放自愈：会话需人工清理（重建）
4归档中间态（.zip.tmp 残留 / 包已完整但原目录还在）丢弃半截包；包完整则补删原目录（幂等，见《模块-感知》§7.1 规则 7）
5budget.json 缺失或损坏重建为 0 并写告警（预算不精确可接受）

技术残留（*.tmp、写了一半的行、未释放的锁）由基础设施层的启动清理处理，不在这里重复。

错误码、Result 与用户文案的组织方式见《模块-应用层》§9：应用层返回 Result<T, UseCaseError>，Cancel 是独立分支，文案由外壳按 code 查表。

8.11并发模型

并发点机制约束
用例执行外壳（TUI）单线程调用；同一 sessionId 同时只有一个 RunSession应用层用 sessionId 做内存互斥，不依赖文件锁
内循环与工具工具严格串行（多个工具调用逐个执行、各自成败）无并发工具调用
子代理SubagentLauncher 内部并行；各自独立超时；join-all子代理不得再开子代理
人机交互HumanInteractionPort 单队列，所有来源排队逐个呈现必须显示来源；cancellation 可唤醒
持久化单写者（InstanceLock）；CommitScope 串行同一时刻只有一个实例写数据目录
全局资产skills/、experience/、plugins/ 的写入走全局资产写段（进程内串行）并行子会话会同时沉淀，容量判定与写入必须原子；这里不是"一个会话一个写者"
端口路由表插件启停改的是共享可变表，必须原子替换（AtomicReference / ConcurrentHashMap）插件实现实时生效，所以路由不能缓存 final 引用；与"每会话一个写者"无关
UI 更新ProgressPort 单向推送丢弃进度不影响业务
