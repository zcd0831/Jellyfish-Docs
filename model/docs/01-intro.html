第 1 章

整体介绍

先把一件容易搞混的事说清楚：这份文档不是"技术方案"，而是这门生意的规则手册。 它规定"什么东西存在、谁能改它、什么时候算做完"。代码可以重写，这些规则不能随便改。

1.1这个系统在做什么

Jellyfish 是一个跑在你终端里的 AI Agent（智能体）。你输入一句话，它不一定马上回答，而可能：

  • 先想一下这活儿要几步，写个计划；
  • 一步一步做，每一步去调工具（读文件、跑命令、查网页、调外部接口）；
  • 做完一步检查一下是不是真做对了，没做对就重做或改计划；
  • 遇到拿不准的事反问你；
  • 把这次的教训记下来，下次遇到类似情况少走弯路。

听起来像个员工。所以建模时我们真的按"一个员工在公司里干活"来拆：他看到了什么、他怎么打算、 他做了什么、他学到了什么。这四件事，正好是四个模块。

一个前提约束

它是本地单机、面向单个用户的终端应用。所以"多租户、组织架构、权限体系、按金额计费" 这些概念刻意没有建模。如果你以后要做云端多用户版本，需要在这里加一整层。

1.2为什么需要领域模型

没有领域模型会怎样？常见三种惨状：

惨状典型症状
同一件事有好几个名字代码里"任务""步骤""轮次""尝试"混着叫，产品说的"重试"和开发说的"重试"不是一回事
没有边界任何一个服务都能改任何一张表，"谁把计划改坏了"永远查不出来
规则散落"失败几次才反思""什么时候该问用户"这些规则散在 if-else 里，改一处崩三处

领域模型要解决的就是这三件事，对应三个产出：

产出 1
统一语言
产品、开发、测试说同一个词时指的是同一件事。第 2 章
产出 2
边界（聚合）
一组必须"同时改对"的数据被绑在一起，改动只能从它的"根"进去。第 3 章
产出 3
规则（不变量）
"什么情况下这个状态不可能出现"被写成硬规则，而不是靠人记得。第 3 章

1.3四个模块：像一个人做事

整个模型被切成四块，每一块只回答一个问题。它们单向依赖： 规划能叫行动和记忆，记忆能叫行动和感知，但感知谁都不叫——因为它只负责"呈现世界"。

    P["感知<br/>我看到什么"] -->|当前上下文| PL["规划<br/>我下一步做什么"]
    PL -->|要执行的动作| A["行动<br/>我真的去做"]
    A -->|工具结果| P
    PL -->|沉淀素材| M["记忆<br/>我学到了什么"]
    M -->|可复用的经验| PL

模块用人打比方它管什么它不管什么
感知 眼睛和耳朵 + 工作台 对话流水、系统提示词快照、上下文窗口、超过长度时压缩 不判断对错、不做决定
规划 脑子里的计划表 计划、步骤、尝试、验证、什么时候重试 / 改计划 不直接调工具、不存历史
行动 手 + 工具箱 + 钱包 工具定义与执行、模型与凭据、代理身份、token 花销 不组装上下文、不决定做什么
记忆 笔记本 反思、经验库、技能（SOP） 不推进当前任务

1.4两个循环：内循环与它的老板

这是整套模型最需要先理解的一点。Agent 干活有两个层次的循环，它们是嵌套的。

内循环：ReAct（想 → 做 → 看 → 再想）

模型每次只能做一件事：决定调一个工具，或者决定说完了。调完工具，结果回到上下文， 它再决定下一步。这个"想—调—看"的循环就是 ReAct（Reason + Act）。

它的唯一出口是：模型不再调用工具。就这么简单——没有"任务完成"的判断， 它只负责"这一轮我说完了"。

外循环：Plan-and-Execute（要不要拆任务、拆完怎么推）

外循环是个 do-while 循环。它每转一圈，就跑一次内循环：

  • 如果还没有计划：跑一次不带步骤的内循环。模型可能只是聊两句，也可能调 generate_plan 生成计划；
  • 如果已有计划：取当前那一步，让内循环去执行；执行完走验证，再决定"推进 / 重试 / 重划"；
  • 计划做完了：再跑一次不带步骤的内循环，让模型把各步结果汇总成给你的答复——这就是"交付结论"。
flowchart TD
    U["用户输入"] --> C{"有可执行计划？"}
    C -- 有 --> D["取当前步骤<br/>（同一 Attempt 继续）"]
    C -- 无 --> E["本轮不带步骤"]
    D --> F["内循环：ReAct"]
    E --> F
    F --> G{"模型不再调工具？"}
    G -- 否 --> F
    G -- 已达轮次上限 --> R["该 Attempt 判失败<br/>重试 / 反思 / 重划"]
    R --> C
    G -- 是 --> B{"是否存在当前步骤？"}
    B -- 是 --> H{"提交了 submit_step？"}
    H -- 否 --> P["本轮结束：Attempt 挂起<br/>不消耗重试，等你再说一句"]
    P --> U
    H -- 是 --> I["验证链 → 推进 / 重试 / 重划"]
    I --> C
    B -- 否 --> L["本轮交互结束<br/>（计划完成后另跑一轮自由内循环交付结论）"]

关键设计：一切都是工具

"生成计划""提交这一步做完了""问用户一句话""开子代理""加载技能"——这五件事全部是工具， 和"读文件""跑命令"没有本质区别。模型看到的就是一份工具清单，它自己决定调哪个。

好处是：没有隐藏的控制流。不存在"调了某个工具就偷偷跳转"的魔法， 所有行为都能在对话记录里被看见、被审计、被复现。

1.5一次对话的完整生命周期

把上面两个循环走一遍，一次对话大致是这条时间线：

时刻发生了什么谁负责
会话开启建会话、建这个会话族的 token 台账、冻结一份提示词快照、用模型起个标题感知
内循环检查和压缩（必要时）上下文 → 模型思考 → 调用工具 → 结果回到上下文 → 再回第一步，直到不再调工具规划（驱动）+ 行动（执行）+ 感知
模型决定拆任务（内循环中）调 generate_plan，校验通过后计划诞生，并给每步分配历史经验规划（+ 记忆）
每步执行内循环跑这一步 → （如果做完了）模型调 submit_step 声明做完了规划
每步验收按这一步声明的验证类型跑验证链；通过就固化，不通过就重试 / 反思 / 重划规划
计划完结成功或失败都会触发一次"复盘"，把教训蒸馏成经验记忆
交付再跑一轮不带步骤的内循环，模型把结果汇总成答复规划

1.6五条贯穿全模型的设计原则

后面四章会反复出现这些原则。它们决定了"为什么这个规则长这样"。

原则一句话解释它挡住了什么问题
收敛 ≠ 完成 模型说完了，只代表这次执行结束；算不算做成，由验证判定 模型只输出了一句"我需要你确认…"就被当成任务完成
故障不是业务失败 模型连不上、请求超长，都不是"这一步失败了" 用业务失败掩盖环境问题，把计划判死、白白消耗重试次数
聚合不读配置 阈值、上限这类配置由"调用方"判断，聚合只保证状态迁移合法 改一个配置导致历史数据"不合法"
定义冻结、策略不冻结 会话开始时把工具/技能/提示词"拍快照"；但用户改的策略立即生效 跑到一半有人改了工具定义，正在跑的任务行为漂移
谁拥有，谁修改 记忆模块不能直接改计划；它只返回"建议",由计划自己改 跨模块互改对方数据，出问题查不清

1.7后面四章怎么读

每一章的结构完全一样，可以按需跳读：

  1. 模块定位与边界——它管什么、不管什么、依赖谁
  2. 模块总览图——这一块里有哪些对象，彼此什么关系
  3. 对象操作图——谁调用谁、谁改谁
  4. 聚合清单——有几个聚合，各自的红线（不变量）是什么
  5. 领域服务清单——跨对象编排的那些"动作"
  6. 其他实体 / 值对象——配角们
  7. 领域事件——发生了什么、谁关心
  8. 生命周期与规则——每个聚合从生到死经历哪些节点、有哪些硬规则
  9. 服务操作详解——时序图级别的"到底怎么跑"
先看哪章？

如果只想搞懂"它怎么把一件事做完"，直接跳到 第 6 章 规划模块， 那是整个系统的心脏。看完再回头看感知和行动会轻松很多。
