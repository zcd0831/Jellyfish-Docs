第 7 章

记忆模块

记忆模块回答一个问题：学到的东西怎么留下来、下次怎么用上。 它持有两类知识资产：陈述性知识（Experience：踩过的坑）与 程序性知识（SkillDefinition：怎么做好一件事的 SOP）， 以及两者之间的蒸馏中间态（Reflection）。

7.1模块定位与边界

方向内容
本模块聚合Experience、Reflection、SkillDefinition
本模块端口在 application.memory.port 声明 SkillSopProvider（只声明接口，由基础设施 FileSkillSopProvider 实现）；本模块不实现任何端口。检索/归纳所需的内置代理能力由 ModelInvocationPort 提供（builtin.retrieve / builtin.distill 的 prompt，不建子会话）
被本模块引用的外部 ID（仅 ID）PlanId、StepId（规划）、RecordRange / SessionId（感知）
被外部引用的本模块对象ExperienceId（规划 PlanStep.assignedExperienceIds）、ReflectionId（规划 Attempt.reflectionId）、SkillId（行动 AgentDefinition.skillIds）、RuntimePolicy 中的经验参数（只读）
本模块对象所在的层领域层：Experience、Reflection、SkillDefinition（含其规则）；应用层：检索 / 沉淀 / 反馈三个服务；端口：SkillSopProvider（接口在 application.memory.port，实现 FileSkillSopProvider 在基础设施）
依赖纪律：记忆不回写别人的聚合
  • 需要"把经验分配给 step"时，它只返回分配结果（Map<StepId, List<ExperienceId>>），由【规划】的 Plan.assignExperiences() 自己改状态；
  • 需要"读本 Plan 的执行事实"时，由调用方组装 DistillationInput 值对象传入，而不是让记忆去遍历 Plan 聚合；
  • 需要"读原始对话"时，按 RecordRange 只读 Session.Record（含子会话）—— 读操作不算依赖，且绝不追写。

7.4聚合清单

聚合简介不变量
Experience 全局经验库的一条经验：适用场景 + 教训 + 置信度 + 使用统计。只有一种经验：失败后翻盘的反思教训 ① 置信度恒在 [0,1]；② 不绑定任何 Agent / 工具 / 技能；③ ARCHIVED 后不再参与检索；④ 容量不得超上限
Reflection 一次失败的反思结论，是"经验蒸馏"的中间态与"重试回注"的素材 ① 生成后不可变；② 一条 reflection 归属唯一 (planId, stepId, attemptNo)
SkillDefinition 程序性知识：描述 + 触发条件 + SOP 正文；纯提示词资产。人写与机学同构，只有 mutable 区分"系统能不能改" ① 只有 ACTIVE 才进入会话快照；② 不含任何工具 ID 列表；③ mutable = false 时 revise() 必须失败；④ 四件套非空；⑤ status 只由 front-matter 决定，聚合不产生状态迁移

7.4.1 Experience

沉淀于计划完结时；检索于计划诞生 / 重划时；语义不绑定任何维度，全局共享。被 PlanStep.assignedExperienceIds 引用（规划）。

7.4.2 Reflection

重试达阈值后由反思子代理产出；双消费者：回注本 step 的下一次 attempt（作为失败原因）、作为经验沉淀素材。被 Attempt.reflectionId 引用（规划）。

7.4.3 SkillDefinition

渐进披露：会话快照只挂 name + description + triggerCondition；模型调 load_skill 才注入 SOP 全文（role = SYSTEM 的 Record）。人写与机学同构，唯一差别是 mutable。被 AgentDefinition.skillIds 引用（行动）；由基础设施 SkillSopProvider 读；被 SkillDistillationService 创建/改进（记忆）。

字段语义
mutable系统有没有权改写正文。默认 true；人写技能在 front-matter 写 mutable: false 即可锁死；jar 内置恒 false
statusDRAFT / ACTIVE / DEPRECATED，只由 front-matter 决定（系统只读）。DRAFT = 人写草稿；DEPRECATED = 人手动下线（或直接删目录）

7.8聚合生命周期与规则

7.8.1 Experience

诞生变更终结重建
计划完结（PlanCompleted / PlanFailed 后由内置代理 builtin.distill 产出） reinforce / penalize（step 结束回写）、合并（语义重复时提置信度）、archive（置信度 < 阈值或容量淘汰） ARCHIVED（不再参与检索，保留供审计） 应用启动时载入

规则清单（11 条）

  1. 只有一类经验：失败后翻盘的反思教训；终局失败（PlanFailed）的反思也沉淀（初值与其它经验相同，不另开起跑线）。
  2. 沉淀时机：只在计划完结时发生，不在失败瞬间、不在 step 结束时发生。
  3. 每 Plan 条数上限：experiencePerPlan（用户可调，默认 1）。
  4. 去重：与库内经验语义重复 ⇒ 合并 + 提置信度，不新建。
  5. 置信度：范围 [0,1]；初值统一为 experienceInitialConfidence（0.5，不为终局失败单独设参数）；reinforce +step、penalize −step（experienceConfidenceStep = 0.1）；低于 experienceRetireThreshold（0.2）淘汰。
  6. 容量与淘汰：总量上限 experienceCapacity；超限时优先淘汰"最早且最少被使用"（createdAt 升序 + appliedCount 升序）。
  7. "被应用"的判定：检索为该 step 分配的经验即视为被应用——分配就是注入，两者是同一份集合，实现里没有独立的"标注"环节。
  8. 回写范围：成功 reinforce 与失败 penalize 作用于同一份"本次分配的经验集合"（FeedbackInput.experienceIds）。不区分"建议"与"注入"——原设想的"奖惩不对称"（成功只奖励被建议的、失败惩罚全部注入的）在现实现里不成立，如实记录于此（M49）。
  9. 事件：新建 ⇒ ExperienceCreated；reinforce() 成功 ⇒ ExperienceReinforced；penalize() 成功 ⇒ ExperiencePenalized；语义重复的合并归入 ExperienceReinforced。
  10. 不绑定维度：不绑 Agent、不绑工具、不绑技能 —— 全局单一库，跨代理共用。
  11. 命中检测：检索走语义筛选，不做关键词匹配；经验只存"适用场景"自然语言 + 教训正文。

7.8.2 Reflection

诞生变更终结重建
步骤重试（有效重试次数达 reflectionThreshold） 无（不可变） 随会话销毁而删除（其价值已由 Experience 承接） 会话续跑时按 ID 读取

规则清单（6 条）

  1. 触发条件：reflectionThreshold ≤ maxRetries 且有效重试次数达到阈值；reflectionThreshold > maxRetries ⇒ 永不反思（直接回注验证失败原因）。
  2. 产者：内置反思代理（BUILT_IN Agent，prompt 固定、工具集写死）——与检索/沉淀/裁判同一形状：一段文本进、一段结论出，直连 ModelInvocationPort，不建子会话（建会话要多付一次标题模型调用与一份流水，而反思没有任何并行或独立生命周期需求）。代理缺失或调用失败 ⇒ 本次不反思：把错误文案存成反思结论比不反思更糟。
  3. 双消费者：① 作为下一次 attempt 的失败原因回注（Reflexion）；② 作为经验沉淀素材。
  4. 不可变：生成后任何角色不得修改。
  5. 归属唯一：一条 reflection 对应唯一的 (planId, stepId, attemptNo)。
  6. 不消耗重试名额：反思本身不是一次 attempt。

7.8.3 SkillDefinition

诞生变更终结重建
平台初始化（jar 内置，mutable = false）/ 用户手写（skills/<id>/SKILL.md）/ 计划完结沉淀（SkillDefinition.create，mutable = true） 仅 revise()（要求 mutable = true）；status 只能改 front-matter 用户删目录，或 front-matter 改 status: deprecated（不再进入新会话快照）；系统从不删除 应用启动时载入（CatalogRepository 合并 jar 内置 + 磁盘）

规则清单（10 条）

  1. 纯提示词资产：只有描述、触发条件、SOP 正文；不含工具依赖（toolIds 已删除）。正文是自由文本，系统不解析、不渲染、不做变量替换，load_skill 原样注入。
  2. 两个来源、同一聚合：人写（skills/<id>/SKILL.md，front-matter + 五节正文）与机学（同一文件形态，由系统写入）在模型上完全同构，唯一差别是 mutable。
  3. 可变性由聚合守护：mutable = false ⇒ revise() 抛不变量违反。人写技能默认 mutable = true（"人写的不一定更好"），想锁死就在 front-matter 写 mutable: false；jar 内置恒 false。
  4. 无候选态、无自动淘汰：机学技能写出即 ACTIVE、立即可用；淘汰 = 用户直接删 skills/ 目录（应用不做删除/弃用操作）。
  5. 无改进历史：revise() 整篇覆盖，不留版本链；改动理由与依据是本次任务输入（结果 + 验证报告 + 现有正文），不依赖任何会话流水。
  6. 渐进披露：快照只挂 name + description + triggerCondition；SOP 正文只能通过 load_skill 注入。
  7. 注入形态：SOP 注入为一条 role = SYSTEM 的 Record，此后不参与滑窗（除非 SYSTEM 占比超限被整体裁剪）。
  8. 只有 ACTIVE 技能进入新会话快照；DEPRECATED 不占容量额度。
  9. 一致性：SOP 正文里提到的工具必须在 AgentDefinition.toolIds 内；否则由感知组装快照时告警（不阻断）。机学技能靠骨架约定（"适用"节必须写清何时用），不做代码校验。
  10. 正文不是会话事实：它不受 Record 的 append-only 约束，也不能被 RecordRange 当作证据；快照冻结清单与三件套，不冻结正文（正文每次 load_skill 现读，接受漂移，S3）。

7.9领域服务的具体操作

7.9.1 ExperienceRetriever.retrieveAndAssign(RetrievalInput)

计划诞生 / 每次重划后，为各 step 分配经验。它只返回分配结果，不写 Plan。

sequenceDiagram
    autonumber
    participant OL as ExecutionLoop（规划）
    participant R as ExperienceRetriever
    participant RP as RuntimePolicy（感知）
    participant E as Experience 库
    participant MI as ModelInvocationPort（基础设施）

    OL->>R: retrieveAndAssign(RetrievalInput{planId, steps})
    R->>RP: experienceTopN / experienceCapacity
    R->>E: 取全部 status = ACTIVE 的经验
    E-->>R: 经验列表（适用场景 + 教训）
    R->>MI: 内置检索代理 prompt 一次调用（整库 + 各 step 描述）
    MI-->>R: 每个 step 分配到的经验（≤ Top-N）
    R->>R: 汇总 Assignment（Map‹StepId, List‹ExperienceId››）
    R-->>OL: Assignment
    OL->>OL: Plan.assignExperiences(stepId, ids)

要点

  1. 全库交子代理语义筛选，不做关键词预筛（关键词在中文/领域术语上漏召严重）。
  2. 只在计划诞生与计划重划两个时点发生；无 Plan 的自由 ReAct 不检索（经验按 step 分配）。
  3. 分配结果就是"被应用"的判定依据（供 7.9.3 回写）：Plan.assignExperiences 落下的那份集合，injectExperiences 原样注入，反馈也原样回写。

7.9.2 ExperienceDistillationService.apply(ExperienceDraft, sessionId)（应用层）

职责：只做写入——把编排者（7.9.6）判定出来的经验产物落成聚合变更。素材、裁剪、内置代理调用都在编排者那边，本服务不碰模型、不读别人的流水。

flowchart TD
    A[收到 ExperienceDraft<br/>applicableScenario + instruction + expectedOutcome] --> B{与库内经验语义重复?}
    B -- 是 --> C[合并：保留更清晰表述 + 提置信度<br/>raise ExperienceReinforced]
    B -- 否 --> D{已达 experienceCapacity?}
    D -- 是 --> E[按"最早 + 最少被使用"淘汰后新建]
    D -- 否 --> F[新建 Experience<br/>raise ExperienceCreated]
    E --> G[提交 + 派发事件]
    F --> G
    C --> G

要点

  1. 零 LLM 依赖：本服务不持有 ModelInvocationPort，因此"经验规则"可以在没有任何假模型的单测里断言（这是把编排拆出去的收益）。
  2. 读而不写别人的聚合：它不读 Session.Record；轨迹由编排者按 RecordRange 只读取好。
  3. 每 Plan 上限：experiencePerPlan 仍是硬上限；编排者每个计划只交一份产物，因此天然满足。
  4. 终局失败也沉淀：PlanFailed 同样会走到这里，初值统一为 experienceInitialConfidence（无单独参数）；是否值得保留交给后续 reinforce / penalize 自然收敛。

7.9.3 ExperienceFeedbackService

step 结束时把结果回写到经验统计；成功与失败作用于同一份集合，只是动作相反。

sequenceDiagram
    autonumber
    participant OL as ExecutionLoop（规划）
    participant F as ExperienceFeedbackService
    participant E as Experience
    participant RP as RuntimePolicy（感知）

    OL->>F: onStepSucceeded(FeedbackInput{stepId, experienceIds})
    F->>RP: experienceConfidenceStep
    loop 本次分配的每一条经验
        F->>E: reinforce()
        E->>E: confidence += step（上限 1）
        E->>E: appliedCount += 1
    end

    OL->>F: onStepFailed(FeedbackInput{...})
    loop 同一份集合
        F->>E: penalize()
        E->>E: confidence −= step（下限 0）
        alt confidence < experienceRetireThreshold
            E->>E: archive()
        end
    end

要点：失败惩罚不做相关性归因（有意为之：宁可错杀）；置信度跌到阈值以下即 archive()，不再参与检索。既然成功与失败覆盖同一集合，一条经验在一次成功后再遇失败会把奖励抵消——这是"分配即应用"的直接后果，接受。

7.9.4 SkillSopProvider.sop(skillId)（基础设施，被 load_skill 调用）

sequenceDiagram
    autonumber
    participant TE as ToolExecutor（行动）
    participant L as SkillSopProvider（基础设施）
    participant SK as SkillDefinition
    participant IL as ReActLoop（规划）

    TE->>L: handle({skillName})
    L->>SK: 按 name 查 ACTIVE 技能
    alt 未找到或非 ACTIVE
        L-->>TE: 返回“技能不可用”结果
    else 找到
        L->>SK: 读 SKILL.md 正文（原样，不渲染）
        SK-->>L: SOP 全文
        L-->>TE: SOP 文本
        TE-->>IL: 工具结果
        IL->>IL: 追加一条 role = SYSTEM 的 Record（不滑出）
    end

要点：SkillSopProvider 只负责"读文件"；把它注入成 SYSTEM Record 是内循环的职责（记忆模块不写别人的会话）。因为正文是现读的，同一会话前后两次 load_skill 可能拿到不同正文——这是 S3 明确接受的漂移（快照冻结的是清单与三件套）。

7.9.5 SkillDistillationService.apply(SkillDraft, sessionId)（应用层）

职责：把内置代理产出的技能草案落成聚合变更，并原子重写 SKILL.md。

flowchart TD
    A[收到 SkillDraft] --> B{四件套非空?<br/>name / description / triggerCondition / sopBody}
    B -- 否 --> X[本次沉淀失败<br/>不发事件、不占额度]
    B -- 是 --> C{action}
    C -->|CREATE| D{ACTIVE 技能数<br/>小于 skillCapacity?}
    D -- 是 --> E[SkillDefinition.create<br/>status=ACTIVE, mutable=true]
    D -- 否 --> Y[不沉淀 + 进度提醒]
    C -->|MERGE target| F{target 存在且 id 合法?}
    F -- 否 --> X
    F -- 是 --> G{target 是 ACTIVE<br/>且 mutable=true?}
    G -- 否 --> H[降级为 CREATE]
    G -- 是 --> I[target.revise 四件套<br/>id 不变、不占新额度]
    H --> D
    E --> J[stageFact / stageReplace 写入<br/>skills/<id>/SKILL.md]
    I --> J
    J --> K[raise SkillLearned / SkillRevised]

要点

  1. 两处失败刻意区分：target 不存在/非法 ⇒ 整次作废（内置代理幻觉，不奖励）；target 存在但不可变或非 ACTIVE ⇒ 降级 CREATE（正常冲突：人写技能不许改，已下线技能不许借 MERGE 复活）。
  2. 容量判定必须原子：skills/ 是全局资产，并行子会话会同时沉淀，容量"读—判—写"在 CommitScope 的全局资产写段内完成。
  3. 写入的唯一路径：技能正文只由本服务经聚合（create / revise）→ CatalogRepository.saveSkill 落盘；内置代理只产出文本，不碰文件（否则 mutable 失效）。
  4. 零计数、零质量分、零阈值：是否需要改进由内置代理看"本次结果 + 验证报告 + 现有正文"判断，系统不累计任何统计量。

7.9.6 PlanCompletionCurator.curate(DistillationInput)（应用层）

职责：计划完结时的唯一归纳入口——起一次子代理，产出"经验?"或"技能?"中的至多一个，再分派给 7.9.2 / 7.9.5。

sequenceDiagram
    autonumber
    participant OL as ExecutionLoop（规划）
    participant C as PlanCompletionCurator
    participant MI as ModelInvocationPort（基建·ModelInvoker）
    participant D as ExperienceDistillationService
    participant SD as SkillDistillationService

    OL->>C: curate(Session, DistillationInput)
    C->>C: 收集本次 plan 的 usedSkillIds（含子会话）
    C->>C: 按 RecordRange 只读 Session.Record（含子会话）<br/>裁剪成"失败后翻盘"的区间，超长按截断阈值截短
    alt 本会话用过技能
        C->>MI: 内置代理一次调用（逐个技能判定"是否需要改进 SOP"）
        MI-->>C: SkillDraft（MERGE 或空）
        C->>SD: apply(SkillDraft)
    else 本会话没用技能
        C->>MI: 同一内置代理（"是否值得沉淀一条技能" + "是否是一条经验"）
        MI-->>C: DistillationOutcome（experience? / skills?，两者不同时非空）
        alt 归经验
            C->>D: apply(ExperienceDraft, sessionId)
        else 归技能
            C->>SD: apply(SkillDraft)
        end
        C->>C: 另一侧不产出（同一件事只进一边）
    end

要点

  1. 一次调用、一个判定：经验与技能的互斥由同一次子代理判定保证；分成两个子代理各判一次，必然出现双写。
  2. 素材归属：按 RecordRange 只读 Session.Record、裁剪"失败后翻盘"区间、拼成消息——全在本服务；两个写入器都拿到成品，不再各自读轨迹。
  3. 谁有权学：每个会话（含子代理会话）在计划完结时都会走本流程——学习入口因此不是唯一的，容量上限（skillCapacity）与 MERGE 收敛是唯一的闸门。
  4. 子会话的质量证据更弱：子代理 plan 常无验证声明，其技能产物天然"证据不足"；本期不加额外门槛（接受此风险）。
  5. 沉淀失败不阻塞：本服务任何一步失败都只是"这次没学到"，不影响会话继续（ExecutionLoop 不因沉淀失败而改变计划状态）。
