第 9 章

基础设施层

基础设施层回答一个问题：端口背后到底是什么 —— 文件、模型、终端、时钟。 它只做两件事：实现端口、承载技术细节（格式、原子性、并发、迁移、日志）。 它不含业务规则，也不决定顺序。

适配器 22 实现端口 21 数据根 ~/.jellyfish 只实现，不判断

9.1定位与边界

方向内容
本层对象22 个适配器（实现 21 个端口；HumanInteractionPort / ProgressPort 由外壳实现，见《模块-基础设施层》「模块边界」④）
本层依赖只依赖端口接口（application）与 JDK。实现端口时可以使用领域类型（端口签名所必需）：允许重建与读取（rehydrate 工厂 / getter / Id）；不得驱动聚合的状态迁移（不调业务方法、不改不变量）。聚合 ↔ 文件的映射只在本层 *Dto / *Mapper，不在聚合上留存储痕迹
谁依赖本层启动装配（组装端口实现并注入应用层）
本层不负责业务判断、状态机、事务的"决定"（只执行既定的提交顺序）
三条纪律
  1. 适配器之间只通过端口协作，不直接引用彼此的实现类；
  2. 一切写入落地都要经过原子写协议（.tmp → fsync → rename → fsync 目录）；
  3. 本层不认识聚合——它只认"路径 + JSON 文本"和"记录行"。
  4. 本层不实现任何与终端相关的端口（HumanInteractionPort / ProgressPort）：界面归外壳（见「模块边界」④）。

9.6原子写与 fsync 协议

write(path):
    tmp = path + ".tmp"
    writeAll(tmp, bytes)        # 同目录，保证同一文件系统
    fsync(tmp)
    rename(tmp, path)           # 原子替换
    fsync(parentDir)
append(path, line):
    open(path, APPEND)
    write(line + "\n")
    fsync(path)                 # 单写者保证不交错

同一路径的写入按目标路径串行化：子代理并行改同一个 budget.json、或在同一 sub/ 下建目录时，不会互相覆盖临时文件或撞"目录已存在"。

FileCommitScope.commit() 的固定顺序：

① 所有 stageFact   → 原子写（只新建，若已存在则跳过，幂等）
② 所有 stageAppend → 追加 + fsync
③ 所有 stageReplace → 原子替换
④ fsync 涉及的目录

全局资产写段（globalWrite）：skills/、experience/、plugins/ 不属于任何会话目录，会被并行子会话同时写入（每个会话都能沉淀）。因此这条路径在进程内串行执行，且"容量读—判—写"必须在同一段内完成，否则并行的两次 CREATE 会一起越过 skillCapacity。

9.7启动技术清理

应用层的 StartupReconciler 管业务语义（报告与状态不一致等 5 条）；本节只管文件层面的残留，两者不重叠。

残留处理
*.tmp直接删除（rename 未完成 ⇒ 旧文件仍有效）
records-NNNN.jsonl 末尾半行（无换行）截断到最后一条完整行
locks/jellyfish.lock 存在但无人持锁由 FileChannel.tryLock 判定（进程退出由 OS 释放），可直接重新获取
sub/ 下出现第二层 sub/违反"子代理不得再开子代理"，告警并忽略该目录
archive/<id>.zip 存在但 sessions/<id>/ 仍存在删除 sessions/<id>/（归档已完成，含其 sub/）
cache/启动时视为不可信，必要时整目录清空重建
plugins/<id>/ 目录名与 jar 内 Plugin-Id 不一致告警并忽略该目录（不装载），避免同一 id 两个目录导致卸载漏删

9.8并发与锁

点机制
多实例InstanceLock：locks/jellyfish.lock 上 FileChannel.tryLock（进程级互斥，进程退出由 OS 释放）；获取失败则拒绝启动并提示
写并发每个会话一个写者：主循环写主会话目录，子代理各自写 sub/<childId>/；同一会话内由 CommitScope 串行。全局资产（skills/、experience/）例外：走全局资产写段，进程内串行
读并发读操作无锁（依赖 rename 的原子性：读到的要么是旧版本、要么是新版本）
终端输入由外壳的读取线程负责（应用层 §10）；本层不碰 stdin / stdout / ANSI

9.9日志与可观测

通道内容实现
logs/运行日志（按天滚动，保留 N 天）；只记技术事件，不记领域事实本地文件
ProgressPort面向用户的进度：压缩中、子代理并行、步骤推进、模型降级终端渲染，可丢弃

三者语义不同，不可合并：日志是排障、进度是给人看、领域事件是业务事实。

9.10迁移

  • schema.version 存单个整数；
  • 启动顺序：取锁 → 读 schema.version → 顺序执行内置迁移 → 写回版本号；
  • 迁移只做向前（不提供回滚），失败即中止启动并保留原目录；
  • 不引入自动 DDL 式迁移，每一步都显式写在代码里。

9.11ModelInvoker 的实现要点

它是唯一带技术策略的适配器。

sequenceDiagram
    autonumber
    participant CALLER as 调用方（应用层）
    participant MI as ModelInvoker
    participant POL as PolicyRepository
    participant API as 模型 API

    CALLER->>MI: invoke(request: 目标模型/当前模型 + estimatedPromptTokens)
    MI->>POL: load() → modelFallbackChain
    MI->>MI: describe(modelId) 取 contextLimit
    alt 硬校验不通过（estimatedPromptTokens > maxInputTokens）
        MI-->>CALLER: 抛「请求超限」（不改任何状态）
    end
    MI->>API: 调用（凭据来自 Provider）
    alt 调用失败
        MI->>MI: 按备用链逐个降级，每次换模型后**重新硬校验**
        alt 链内全部失败
            MI-->>CALLER: 抛「模型不可用」
        end
    end
    MI-->>CALLER: ModelInvocationResult（文本 + usage）
    Note over CALLER: usage 由调用方交给 BudgetService 记账（适配器不记账）
  1. 适配器不记账：只返回 usage，由调用方交给 BudgetService —— 否则会出现"基础设施 → 应用层"的反向依赖。
  2. 降级要重新硬校验：备用链里可能是小上下文模型，maxInputTokens 必须按实际要用的模型重新比较。
  3. 线协议由 Provider.protocol 选择：ModelInvoker 按协议查 ChatProtocolAdapter，共享同一个 OkHttp 客户端（见本条第 5 条）。三家都实现：ChatCompletionsProtocol（/chat/completions，Authorization: Bearer）、AnthropicMessagesProtocol（/v1/messages，x-api-key + anthropic-version，max_tokens 必填）、GeminiProtocol（/v1beta/models/{model}:generateContent 或 :streamGenerateContent?alt=sse，x-goog-api-key）。映射细则：request.systemPrompt → OpenAI 首条 system / Anthropic 顶层 system / Gemini systemInstruction；ChatMessage → messages / content blocks / parts；ToolCall → tool_calls / tool_use / functionCall；工具结果 → tool 消息 / 同轮 user 的 tool_result / 同轮 user 的 functionResponse；usage 字段名各家不同，统一映射到 ModelUsage；servedModelId 回填实际模型（降级后与目标不同）。
  4. 不碰聚合：ModelInvoker 只回填 servedModelId，switchModel 由调用方在收到结果后执行（见《模块-行动》§8.2）。
  5. 阻塞与流式共用一份失败映射：流式路径先把 HTTP 状态码交回 ModelInvoker，由 mapFailure 统一分流——400/401/403/404 不重试（确定性错误，重试只会把同样的非法请求再发三遍），429/5xx 才退避重试，网络/读超时属于可重试。流式不得把 4xx 包成“可重试失败”。
  6. reasoning_content 的映射（见 §10 第 3、5 条）：解析时收进 ModelInvocationResult.reasoning；组装时只有在目标模型就是产者且 reasoning 非空时才输出该字段（产者由应用层按 producerModelId 判定）。流式累加器必须同时累加 delta.content 与 delta.reasoning_content；流断在中途 ⇒ 整条不落（“半截输出不落 Record”）。
  7. 消息形态由适配器吸收：适配器拿到的是 canonical ChatMessage（content 与 tool_calls 可能同处一条）；OpenAI 直接透传，Anthropic 要翻成 content blocks 并把同轮的 tool_result 归到紧接的 user turn，Gemini 要翻成 parts 并保序（其配对语义与 id 不同）。ModelInvoker 不参与任何字段映射。
  8. 私有状态的载荷由产者协议自己解释：Record.reasoning 是不透明字符串——OpenAI 系放原文 reasoning_content；Anthropic 放它自己的 thinking blocks JSON（含 signature），回放时排在 text/tool_use 之前；Gemini 的 thoughtSignature 尚未进入 canonical 私有状态，开启 thinking 的 Gemini 工具轮暂不保证可续接（后续切片）。

9.12插件运行时（PF4J）的实现要点

#约定
1PF4J 3.16.0：实测其 class 文件 major version = 52（Java 8 字节码），JDK 8 可用；内部用 multi-release jar 把 module-info 放在 META-INF/versions/9/
2关掉 PF4J 自带的状态持久化（默认会写一份启停状态）：否则与 plugin.json 形成两份真相，违反"落盘只存用户意图"
3动态装载可用：loadPlugin(Path) / startPlugin(id) / stopPlugin(id) / unloadPlugin(id) 都是运行期 API，装/启/停/卸不需要重启
4同 id 升级要重启：重新装载同一 Plugin-Id 会与旧 PluginClassLoader 撞车；卸载后类可能仍被线程/静态缓存引用（泄漏），所以升级走"停进程 → 换 jar → 起进程"
5插件不得重复打包宿主已提供的依赖（Jackson / OkHttp / networknt / Log4j 等）：装了就在类加载器里打架。安装时检查 jar 内依赖清单，命中即拒绝
6apiVersion 用 Plugin-Requires 校验：宿主版本由运行时提供，不匹配拒绝装载
7工具声明从 jar 内读：META-INF/jellyfish/tools/*.json，与 BuiltinAssets 同构（内存读、不落盘、卸载即消失）
8扩展实例由 PluginAssembler 注册：PF4J 的扩展对象不经过 DI 容器（"容器概念不渗入业务"仍成立——插件实现的是端口接口，装配只发生在 di 层）
