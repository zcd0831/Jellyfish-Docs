## M01 模型调用端口补齐"角色 + 工具调用 + 实际模型 + 输入/输出用量"

**日期**：2026-10-24　**触发切片**：S1（无计划对话）　**状态**：有效

**为什么改**：S1 要跑"一句话 → 多轮工具 → 最终答复"，但原模型的端口表达不了三件必需的事——对话的角色、模型请求调用的工具、降级后实际服务的模型；用量也只有一个 `usageTokens`，与 D08 的"台账要精确、分输入输出"不符。

**改了什么**

| 项 | 前 | 后 |
|---|---|---|
| `ModelInvocationRequest.messages` | `List<String>`（无角色） | `List<ChatMessage>` |
| `ModelInvocationRequest.systemPrompt` | 不存在 | **新增** `String`（见 M02） |
| `ModelInvocationResult` | `text` + `long usageTokens` | `text` + `List<ToolCall> toolCalls` + `ModelUsage usage` + `ModelId servedModelId` |
| `ChatMessage` | 不存在 | **新增 VO**：`RecordRole role`、`String content`、`List<ToolCall> toolCalls`、`String toolCallId` |
| `ToolCall` | 不存在 | **新增 VO**：`String callId`、`String name`、`String argumentsJson` |
| `ModelUsage` | 不存在 | **新增 VO**：`long inputTokens`、`long outputTokens` |

**为什么是这三个值对象**：`ChatMessage.role` 直接复用 `RecordRole`（`SYSTEM / USER / ASSISTANT / TOOL_REQUEST / TOOL_RESULT / SUMMARY`），因为 `Record` 本来就按角色存、`buildContextForLlm` 本来就是"把记录搬成窗口"——端口只是把同一套语义搬到请求/响应上，没有引入新概念，也不改变任何聚合不变量。`servedModelId` 让"降级"有数据来源，同时保持 `ModelInvoker` 不碰聚合（`switchModel` 由调用方执行）。

**涉及文件**

- `模型图.md`：行动模块的 `ModelInvocationRequest` / `ModelInvocationResult` 字段；新增 3 个 VO；行动内部关系补 4 条组合线。
- `模块-行动.md`：类图新增"模型调用值对象"命名空间；§5 值对象表新增 3 行、改写 2 行；§8.2 补两条口径（系统提示词独立传递、降级后由调用方切换模型）。
- `模块-基础设施层.md`：§10 新增两条约定（线协议映射、不碰聚合）。

**代码落点**：`application/action/port`：`ChatMessage`、`ToolCall`、`ModelUsage`、`ModelInvocationRequest`、`ModelInvocationResult`；`infrastructure/model/ModelInvoker` 的映射。

**验收方式**：S1 假模型（`ScriptedModelInvocationPort`）能返回"文本 + 一次工具调用"，`ReActLoop` 能把工具结果按 `TOOL_RESULT` 角色回灌，并在第二次响应得到最终文本；降级用例断言 `Session` 收到 `switchModel`。

## M02 系统提示词不落 `Record`，作为 `systemPrompt` 独立传给模型

**日期**：2026-10-24　**触发切片**：S1　**状态**：有效

**为什么改**：原写法（`模块-感知` §7.1-9 ①）把"系统提示词快照渲染"和"SOP / 工具 / 经验注入"混在"取出全部 `role=SYSTEM` 记录"这一句里，导致两个问题：① 需要把基础提示词也塞成一条 `Record`，与"快照在会话开启时冻结、不落流水"的定位打架；② 模型侧协议里系统提示词与对话是分开的（已核实：OpenAI 用首条 `role=system` 消息承载，Anthropic 用**顶层 `system` 字段**且输入消息里没有 system 角色，Gemini 用 `systemInstruction`），把它混进 `messages` 会让适配层反复拆分。

**改了什么**

| 项 | 前 | 后 |
|---|---|---|
| `模块-感知` §7.1-9 ① | 取全部 `role=SYSTEM` 记录（**系统提示词快照渲染** + SOP 注入 + 工具注入 + 经验注入） | 取全部 `role=SYSTEM` 记录（**仅运行期注入**：SOP / 工具 / 经验）；基础提示词来自 `SystemPromptSnapshot`，不落 `Record`，作为 `systemPrompt` 单独传 |
| `模块-感知` §7.1 | 规则 1–12 | 新增规则 13：系统提示词与流水分离；降级只保留快照 = 丢弃全部注入 |
| `模块-感知` §8.5 流程图 | ① 节点含"系统提示词渲染" | ① 节点改为"仅运行期注入；系统提示词来自快照，不落 Record" |

**不变的部分**：`Session` 的不变量、`ContextUsage.systemTokens` 的口径、第 ④ 步降级的语义都不变——只是把"系统提示词"从流水里拿出来，注入仍以 `SYSTEM` 记录形式存在。

**发给模型时的拼装规则**：`systemPrompt` = 快照渲染结果（+ 未降级时按序拼接的 `SYSTEM` 注入内容）；`messages` = 其余角色记录。降级（第 ④ 步）时 `systemPrompt` 只留快照，注入整段丢弃。

**涉及文件**：`模块-感知.md`（§7.1、§8.5）；`模块-行动.md` §8.2 第 2 条（系统提示词独立于消息列表）。

**代码落点**：`Session.buildContextForLlm` 返回的窗口里 `SYSTEM` 记录只含注入；`ReActLoop` 负责把快照 + 注入拼成 `request.systemPrompt`。

**验收方式**：S1 的 `Session.buildContextForLlm` 单测断言"流水里没有系统提示词记录、窗口含注入"；假模型断言收到的 `systemPrompt` 非空且 `messages` 首条不是 SYSTEM。

## M04 内置资产按数据交付：jar 资源分目录与命名规则

- 切片内按需追加，不在 S1 一次性交齐：

| 资产 | 交付切片 | 说明 |

| `builtin/tools/ask_user.json` | S1 | 内置工具 schema |

**涉及文件**：`模块-基础设施层.md` §4（已有"内置代理不落盘"表述，无需再改）；本记录。

## M05 `Provider` 增加 `protocol` 字段与 `ChatProtocol` 枚举

**日期**：2026-10-24　**触发切片**：S1　**状态**：有效

**为什么改**：要同时接 OpenAI / DeepSeek / Kimi / MiniMax 且保持可扩展。四家都是 OpenAI 形状，但 MiniMax 的旧端点路径不是 `/chat/completions`；如果路径写死在代码里，"新增厂商 = 改代码"。同时将来接 Anthropic / Gemini 需要完全不同的请求体。因此必须把**厂商差异（数据）**与**协议差异（适配器）**分开，而 `Provider` 现在没有承载"用哪种协议"的字段。

**改了什么**

| 项 | 前 | 后 |
|---|---|---|
| `Provider` 字段 | `id / name / apiEndpoint / credential / status` | 增加 `ChatProtocol protocol`（**缺省 `OPENAI_CHAT`**，旧 `providers/*.json` 无需迁移） |
| `ChatProtocol` | 不存在 | **新增枚举**：`OPENAI_CHAT / ANTHROPIC_MESSAGES / GEMINI` |
| 线协议选择权 | 隐含"固定 OpenAI 形状"（D16 原文） | 由 `Provider.protocol` 决定；`ModelInvoker` 按协议查实现 |

**边界说明**：`protocol` 只影响**基础设施选哪个协议实现**，不参与任何聚合不变量（与"聚合不变量不依赖配置"一致）；枚举按名字存（D07），新增常量不需要 `schema.version` 迁移。

**涉及文件**：`模型图.md`（行动模块 `Provider` + 新枚举 + 关系线）、`模块-行动.md`（类图、§3.2、§5 表、§7.2 规则 ④）、`模块-基础设施层.md` §10-3、`tech/技术决策.md` D16 第 1 / 1.1 条。

**代码落点**：`domain/action/model/ChatProtocol`、`Provider.protocol`；`infrastructure/model/ChatCompletionsProtocol` + `ModelInvoker` 的协议分派。

**验收方式**：`providers/*.json` 缺 `protocol` 时按 `OPENAI_CHAT` 读取（兼容用例）；同一 `ModelInvoker` 换 `protocol` 只改变请求体与路径，不改调用方代码。

## M06 落地 S1 必需的四处契约细化

**日期**：2026-10-24　**触发切片**：S1　**状态**：有效（§7.1-9③ / §8.5 正文已于 M35 回填）

**M06-1 窗口推导的入参：`buildContextForLlm(policy)` → `buildContextForLlm(policy, estimator, inputCeiling)`**

文档 §8.5 要求该方法"④ 计算 `usedTokens / systemTokens / summaryTokens`"，但领域层不允许依赖 `TokenCounter` 端口（§7.1 规则 12 的同一条纪律）；`inputCeiling` 也要先向 `ModelInvocationPort` 取模型档案才能算。结论：**把"怎么数"和"上限多少"作为入参传入**——新增 `domain.shared.TokenEstimator`（`int estimate(String)`，与 `ContextWindowPolicy` 同为值/函数入参），`inputCeiling` 由 `ContextWindowService` 算好后传入。领域层仍不持有分词器、不读配置。

## M38 经验侧与技能侧对齐：`apply` 取代 `distill`

**日期**：2026-10-25　**触发切片**：M37 代码实现　**状态**：有效

**为什么改**：M37 写下的两份规则互相冲突——§8.6 说 `PlanCompletionCurator` **起一次子代理**并拿到 `DistillationOutcome`，而 `ExperienceDistillationService.distill(DistillationInput)` 的入参只含"事实摘要 + 轨迹区间"，**不含判定结果**，因此它必须自己再读轨迹、再调一次模型。结果：① 违反"一次调用、一个判定"，互斥保证失效；② 模型成本翻倍；③ 经验侧与技能侧在同一对称位置上契约形状不同（技能侧收的是 `SkillDraft`）。

**改了什么**

| 项 | 前 | 后 |
|---|---|---|
| `ExperienceDistillationService` | `distill(DistillationInput)`：自己读轨迹 + 调子代理 + 解析 + 写入 | **`apply(ExperienceDraft, SessionId)`**：只做写入（去重合并 / 新建 / 淘汰） |
| 素材与子代理 | 在经验服务内 | 上移到 `PlanCompletionCurator`（按 `RecordRange` 只读 `Session.Record`、裁剪"失败后翻盘"区间、唯一一次调用） |
| `ExperienceDraft` | 不存在（只有内部 `Candidate` 类） | **新增 VO**：`applicableScenario` / `instruction` / `expectedOutcome`，与 `SkillDraft` 对称 |
| 关系线 | `ExperienceDistillationService ..> Reflection : 只读素材` | 移到 `PlanCompletionCurator ..> Reflection : 只读素材` |
| §8.2 | 含素材口径与裁剪 | 只讲写入；素材口径并入 §8.6 |

**为什么不是"合并成一个服务"**：那会让一个类同时拥有三种变更理由（素材与调用 / 经验规则 / 技能规则），且写入规则被迫依赖模型端口而无法脱离假模型测试。写入器零 LLM 依赖是可测性的关键（见 M38 讨论记录）。

**涉及文件**：`模型图.md`（§一 记忆 namespace）、`模块-记忆.md`（§1 类图与关系线、§4 服务表、§5 VO 表、§8.2、§8.6）、`模块-应用层.md`（§5 该行的关键协作列）、`docs/03-overview.html` / `07-memory.html` 同步。
