## M49 规则 ⑦⑧：分配即被应用，`FeedbackInput` 只剩一个集合

**日期**：2026-10-26　**触发切片**：M39 与代码复核　**状态**：有效

**为什么改**：§7.1 规则 ⑦ 写"被应用的判定**不靠是否注入猜测**，而靠检索子代理的标注建议"，规则 ⑧ 写"成功只奖励被建议的、失败惩罚注入的全部"。但代码里 `ExecutionLoop.feedbackOf` 把 `suggested` 与 `injected` **传成同一份 `assignedExperienceIds()`**，`injectExperiences` 又原样注入——"分配 = 注入 = 被应用"三者恒等，那个"标注"环节从来不存在，"奖惩不对称"在生产路径上不成立。

| # | 项 | 前 | 后 |
|---|---|---|---|
| 1 | 规则 ⑦ | 被应用靠**检索子代理的标注建议**判定 | 检索为该 step **分配的经验即视为被应用**（分配就是注入，没有独立的标注环节） |
| 2 | 规则 ⑧ | **回写不对称**：成功只奖励被建议的、失败惩罚注入的全部 | **回写范围**：成功 `reinforce` 与失败 `penalize` 作用于**同一份**集合；原设想的不对称在现实现里不成立，如实记录 |
| 3 | `FeedbackInput` | `injectedExperienceIds` + `suggestedExperienceIds`（两个集合） | **`experienceIds`（一个集合）**；类图、§5 表、`模型图` §5.5 同步 |
| 4 | §8.1 要点 3 | 标注建议是被应用的判定依据 | **分配结果就是**被应用的判定依据（`assignExperiences` → `injectExperiences` → 反馈，同源） |
| 5 | §8.3 | 标题"（奖惩不对称）"、两个 loop 分别写"仅被建议的"/"本次注入的全部" | 标题改为陈述职责；两个 loop 分别为"本次分配的每一条"/"同一份集合"，并补一句"一次成功后再遇失败会把奖励抵消" |

**未变**：`Experience` 聚合的 `reinforce` / `penalize` 规则（±step、阈值淘汰）不动；`ExperienceFeedbackService` 仍分两个方法（动作不同），只是覆盖集合相同。

**代价（记录在案）**：原设计的"失败宁可错杀、成功精准奖励"退化为"同一集合奖惩"——**奖励的信噪比下降**（一条只沾边的经验也会因 step 成功而加分）。要恢复，需要让检索真的产出"建议子集"，那是行为变更，另开记录。

**涉及文件**：`模块-记忆.md`（§1 类图、§4 服务行、§5 `FeedbackInput`、§6 事件行、§7.1 规则 ⑦⑧、§8.1 要点 3、§8.3）、`模型图.md`（§5.5 反馈行与 `FeedbackInput` 字段）、`docs/{03,07}.html` 同步。

**代码落点**：`application/memory/FeedbackInput`（单集合）、`application/memory/ExperienceFeedbackService`（两个方法都读 `experienceIds`）、`application/planning/ExecutionLoop.feedbackOf`（不再传两份）、`boot/S4MemoryTest`（用例改为"成功与失败作用于同一份分配经验"）。

**验收方式**：`mvn -o test` 全绿（293 例）；`model-check.py` 零漂移。

## M51 反思改为内置代理，删除 `childSessionIds` 死字段

**日期**：2026-10-26　**触发切片**：M50 的反向评估　**状态**：有效（**行为变更**）

**为什么改**：M50 刚给反思保留子会话找了理由——"结论的依据要留在子会话流水里（`Attempt.childSessionIds` 可达）"。复核代码发现**这条链根本没实现**：`Attempt.addChildSession(...)` 在主代码里**零调用**，`SubagentResult.sessionId` 只被拼进工具输出的 JSON 文本，没人写进 `Attempt`。于是"子会话"只剩三样东西：一个会话目录、一份流水、**一次额外的标题模型调用**（`startSubSession` 里 `retitle(...)`）。同时暴露一个缺陷：反思失败时 `SubagentResult.conclusion` 是 `"超时未完成"` / `"子代理失败：…"`，这串错误文案会被**当成反思结论存进 `Reflection`**，再作为失败原因回注与沉淀素材。

| # | 项 | 前 | 后 |
|---|---|---|---|
| 1 | 反思的调用方式 | `subagentLauncher.launch(...)`，建完整子会话（多一次标题调用、一份流水、独立超时策略） | **直连 `ModelInvocationPort`**：`builtin.reflect` 的 prompt 作 systemPrompt、任务文本作 USER 消息、`budgetService.recordUsage` 记账——与检索/沉淀/裁判同一形状 |
| 2 | 失败语义 | 失败文案被**存成反思结论** | **本次不反思**（代理缺失、调用抛错、结论为空都跳过）：把错误文案存成结论比不反思更糟 |
| 3 | 超时口径 | `subagentExecutionTimeoutMillis` | D10.1 的读超时（不单独设超时） |
| 4 | `Attempt.childSessionIds` | 字段 + `addChildSession` + getter + DTO 读写 + 模型关系边（**从未被写入**） | **删除**（域对象、`PlanDto`、`模块-规划` §1 类图与关系边、`模型图` §一 与 §5 关系表、`03-overview.html`） |
| 5 | `StepTrace.childSessionIds` | 恒为空的沉淀素材 | **删除**（构造参数一并去掉，`模块-记忆` §5/§5.5 同步） |
| 6 | `ExecutionLoop` 依赖 | 需要 `SubagentLauncher` | 去掉该依赖（反思是它在此处的唯一用法） |
| 7 | `模块-记忆` §7.2 规则 2 / §8.5 | "走 `SubagentLauncher`…依据留在子会话流水" | 改为"与其余三个同一形状、直连端口"；技能改进的依据改为"本次任务输入"，不再宣称依赖会话流水 |

**取舍（记录在案）**：失去"反思的完整子会话流水"（prompt + 模型原始回答的可观测副本）。换来的是每次反思省一次 LLM 调用、省一个会话目录，并且修掉"错误文案当结论"的缺陷；结论本身仍落在 `Reflection` 聚合里。
